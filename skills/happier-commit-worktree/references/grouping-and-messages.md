## 1. Reconnaissance model

Classify every changed path along several axes before forming commits:

| Axis | Questions |
| --- | --- |
| Domain | Which product behavior or bounded context owns it? |
| Role | Contract, owner, adapter, consumer, test, fixture, migration, docs, generated output, or artifact? |
| Change kind | Feature, fix, refactor, migration, mechanical update, removal, test correction, or content? |
| Dependency | What must land before or with it for the repository state to make sense? |
| Provenance | Was it authored, generated by a canonical command, downloaded, built, captured by QA, or produced accidentally? |
| Confidence | Is its intent proven, inferred, or still unknown? |

Use symbols, imports, call sites, test names, routes, config keys, schemas, and Git history to connect paths. Directory adjacency is supporting evidence, not a grouping rule.

## 2. Coherence tests

A candidate group is coherent when a reviewer can answer one sentence: "This commit establishes/fixes/migrates **X**." Apply these tests:

- **Reversion test:** reverting only this commit removes one understandable capability or correction without removing unrelated behavior.
- **Explanation test:** every file is explainable from the subject and body without an "also updates miscellaneous files" clause.
- **Completeness test:** the canonical owner, consumed wiring, defining tests, and required compatibility pieces are present.
- **Dependency test:** the commit does not depend on a later commit to compile or express its claimed contract unless the campaign explicitly permits an intermediate mechanical state.
- **Noise test:** formatting, generated churn, artifacts, and unrelated refactors are absent.
- **Hunk test:** mixed-purpose files are split rather than assigned wholesale.

Do not split implementation and its defining test merely to increase commit count. Do not combine separate fixes merely because they share a package or test command.

## 3. Sizing and batching

Optimize for review cost and throughput together:

- Prefer 5-50 files for ordinary multi-file changes.
- Use 20-100+ files for demonstrably uniform mechanical work, provider/backend fan-out, one icon-system migration, locale/catalog updates, snapshots, or required generated output.
- Keep a one- or two-file commit when that is the entire natural behavior slice.
- Split a large domain program by canonical owner, behavior boundary, migration phase, provider family, or independently revertible outcome.
- Never use a file target as a quota. A 200-file coherent migration is better than ten arbitrary directory batches; a 20-file mixed dump is still wrong.

Accelerate by analyzing several disjoint domains in parallel, preparing manifests and messages in batches, and running independent checks concurrently. Keep HEAD mutation serial unless every writer uses disjoint scope, private indexes, CAS, and stale-parent recovery.

## 4. Artifact and provenance decisions

For unfamiliar or suspicious paths, collect evidence:

```bash
git check-ignore -v -- <path>
git log --all --oneline -- <path>
git ls-files -- <path>
rg -n --fixed-strings '<path-or-parent>' .
stat -f '%Sm %z %N' -t '%Y-%m-%dT%H:%M:%S%z' <path>  # macOS
file <path>
```

Ask:

1. Is the path consumed by source, packaging, release, or tests?
2. Is there a canonical generator, and does repository policy track its output?
3. Is it reproducible build/cache/download output?
4. Does it contain machine-local state, private evidence, credentials, or QA captures?
5. Has this class recurred enough to justify a narrow ignore rule?

An old modification time supports cleanup but does not prove a path is disposable. A source reference supports retention but does not prove generated bytes should be tracked. Require the owning contract.

Check candidate binary sizes before committing:

```bash
find <candidate-roots> -type f -size +90M -print
```

Treat 90 MB as a warning threshold for hosts with a 100 MB hard limit. Inspect private-index blobs as well if the worktree can change between checks.

## 5. Human-understandable messages

Use a Conventional Commit subject:

```text
<type>(<scope>): <specific outcome in imperative mood>
```

Good subjects describe the established behavior:

- `fix(cli): preserve pending turns across daemon reconnects`
- `feat(ui): add provider-aware session creation controls`
- `refactor(protocol): centralize connected-service auth materialization`
- `chore(ui): migrate session actions to the shared icon set`

Avoid vague inventory language:

- `update CLI files`
- `misc fixes`
- `commit remaining changes`
- `large UI update`
- `refactor components and tests`

Write a body for any non-trivial packet. Prefer two to four short paragraphs or a compact flat list covering:

1. **Outcome:** what behavior, contract, or architecture now exists.
2. **Ownership:** where the canonical decision lives and which consumers moved to it.
3. **Important semantics:** compatibility, failure/recovery behavior, persistence, platform differences, removals, or why a broad mechanical batch is one unit.
4. **Evidence:** tests or invariants added or updated; do not paste a command transcript.

Example:

```text
fix(cli): preserve pending turns across daemon reconnects

Keep pending delivery owned by the session client while transports reconnect,
so a temporary daemon disconnect cannot silently end or duplicate a turn.

Route reconnect and terminal-drain behavior through the same queue state and
retain the existing no-respawn policy. Update the integration coverage for
disconnect, resume, and terminal completion ordering.
```

The body must explain why the files belong together, not enumerate filenames. Mention a major deletion or compatibility decision when a reviewer could otherwise misread it as accidental.

## 6. Group review checklist

Before staging, answer:

- What exact outcome does this group establish?
- Which file is the canonical owner?
- Are all included consumers/tests required by that outcome?
- Are any required siblings missing?
- Does any file contain an unrelated hunk?
- Is any output generated, private, temporary, oversized, or unexplained?
- Can the subject distinguish this commit from every neighboring commit?
- Does the body explain ownership and non-obvious semantics?
- Which focused checks decide whether the group is sound?
