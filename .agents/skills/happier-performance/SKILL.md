# Happier Performance

Performance is a product requirement here (root `AGENTS.md`, "Product priorities"). This skill owns _how_ to keep paths cheap. `happier-implement`, `happier-testing`, `happier-review` and `happier-plan` defer to it for performance. It doesn't replace their workflow, TDD, mock or owner rules.

These rules come from the PERF-E2E program (2026-10-20 → 26). Three days of fixes traced back to one habit: work triggered by "something may have changed" or "we might need this" instead of "a consumer needs this changed fact", with no test measuring cost at real scale. Evidence: `.project/plans/2026-10-20-performance-program/status-2026-10-23.md`.

## 0. Product rules on these paths

Root `AGENTS.md` "Product priorities" points here. These rules apply to every change on a user-facing, sync, transcript, terminal, provider, server or daemon path, whether or not it is framed as performance work.

- Live state is pushed, not polled. Deliver changes through the existing push paths (socket rooms, change feeds with cursors, daemon-to-server events). A timer, interval, periodic fetch, lease renewal or revalidation loop needs a named reason push cannot serve it (an external API without events, a lease TTL, a real deadline); it then has one owner per host or connection, a cadence derived from that contract, stops while hidden or unconsumed, fetches only what changed, and has a fire-count test. Liveness (heartbeats, last-seen, alive timestamps) never bumps a content record's version or republishes it; consumers read it from a key-scoped liveness fact.
- Pushes and notifications carry typed, producer-set facts about what changed; per-arrival consumers must not re-derive them or traverse state on a generic signal. Apply the push-read cost contract in §3 below.
- Delivery follows consumption. Before adding or widening a sync, socket, list or snapshot payload, name each consumer and the facts it reads; send full content only to clients currently consuming it and route others through the canonical delivery classifier (bodyless facts, versions or nothing). Demand derives from current activity and ends with it: retained, last-used, cached or historical state is not demand.
- Reconcile incrementally and checkpoint only what is applied. Row-level changes update rows and gather missing documents through the canonical batch owner; full list or snapshot refreshes are for structural, unknown or gap cases. A known row-level change never reaches the structural branch through a default, a missing hint or an overloaded flag, and foreground/resume refreshes what can have changed while away rather than re-reading full lists. Never advance a cursor, watermark or sequence past data that is not yet materialized; a timeout, cancellation or superseded wait never authorizes advancement.
- Producers publish only real changes. An unchanged refresh, declaration update, re-subscription or rebuild keeps the identity of unchanged items and emits nothing. Ids and keys derived from it stay stable and within their wire bounds, and an update to one input never cancels or restarts consumers of another. Apply the producer-audit cost contract in §3 below.
- User-initiated recovery (Retry, reconnect, foreground) must be able to supersede in-flight work promptly: reads keep cancellation through body completion, a superseded run's waits are cancellable, and an unbounded retry or backoff cycle never holds a fresh user-initiated attempt.
- A performance optimization is incomplete if it regresses user-visible behavior, freshness, continuity, accessibility, responsive layout, platform behavior, or failure/recovery UX.

## 1. Five invariants

A violation is a defect even when every correctness test passes.

1. **Work ∝ real change.** A producer publishes only facts that changed and keeps the identity of unchanged nested values. Nothing is republished just because a cursor, `observedAt`, revision carrier or array was rebuilt, or because two projections of the same fact disagree.
2. **Reads ∝ need.** A narrow question gets a narrow read: exact id or kind selection at the query owner, bodies only for open or visible items. Never page a whole inventory to find a few items. Never fetch what an existing canonical owner already holds; reuse its admitted rows (one loader per resource).
3. **Idle ≈ 0.** On a settled Home, server or daemon, nothing runs except **named liveness**: a presence heartbeat, a real deadline, an opted-in alert, each with its contract written beside it. Closed surfaces don't load. Never-presented tabs don't mount. Hidden documents don't animate.
4. **Fix the producer; don't guard the consumer.** An equality guard, compare-before-publish, memo, cache, WeakMap reuse, digest, `setImmediate`/yield, coalescing timer, retry or slower interval is a **band-aid** unless the producer has been shown to emit only real changes. Fix the producer, then delete the guard. Yield only for fairness during real, necessary work outside held resources; never inside a DB transaction or lock, and never to mask cost. Usage's per-row yield inside a capture transaction lengthened transaction tenure (2026-11).
5. **Bounds come from real boundaries.** Pool sizes, batch sizes, page sizes and limits are derived from an external contract: the DB `connection_limit`, Postgres's 32,767 bind parameters, a platform limit, a protocol budget. Never from host core count, a nearby number or a guess. Root `AGENTS.md` "Risk-weighted execution" owns the rules for any new limit.

## 3. Landing checks for a perf-relevant change

- **Cost contract in the RED.** Assert a count, never wall time, at the owner boundary: renders or commits per arrival, SQL statements per request, requests per idle minute, bodies fetched per open, inventory pages per operation, timer fires per settled minute. It must fail on the old code for the intended reason. These are observable performance contracts, not the "incidental call counts" that `happier-testing` forbids. Assert the contract (N unrelated arrivals → 0 renders of unaffected rows), not how often an internal helper is called.
- **Settings and sync owners.** A change to a settings or sync owner adds one count test for idle traffic and writes: requests per idle minute, writes per toggle or per gesture (Voice, 2026-11-05: a settings stale-head loop issued 177,710 requests in one test run with no idle shape test).
- **Push read contract.** Assert N unrelated pushes → 0 reads; one relevant change → exactly the needed reads, through the real consumer of the producer-set change facts.
- **Own-producer audit and real-change control.** Each program audits its corridor's producers and write paths for pattern 3: count writes and publications per user action and per unchanged refresh; prove N identical refreshes → 0 writes/publications with the same identities, and one changed fact → one replaced identity while unchanged identities survive. Pair every cost assertion with a genuine authority or data change reaching a real consumer in the same test (a revision, version or membership advance acted on downstream); a quiet-path-only fix can suppress a consumed fact. (2026-10-26: Machine row retention swallowed daemon-state-version advances; UI refinements 2026-11-04: ~7.2k empty New Session drafts and inventory rebuilds from an empty map.)
- **Same-pattern sweep before closing.** Search the corridor and its twins for the same shape: other supervisors and loops, publishers, routes, plugins, platforms. Fix or route every reachable instance and list what you checked.
- **Scale-shaped fixture** whenever N matters: thousands of Artifacts, about 1k Sessions, 100+ Machines, about 55k changed files in a working tree (`packages/tests/src/testkit/stress`). Pickers, menus, quick-open and search count their per-interaction work at that size (rows mounted, entries scanned or serialized per open, keystroke or measurement). Assert that work stays O(changed), not O(total). Size it from a real Account's census (count the rows a heavy QA or dev Account actually holds), not from a round number: a 512-row approval fixture passed while 43,000 real approvals exposed a full pass. Measure selection ratios as well as row counts on a live Account before trusting fixture timings; Usage fixture pruning gains did not transfer to the live data shape (2026-11). For publishers and projections, drive the fixture through the real cold-load sequence of publications (initial, each genuine arrival, unchanged republications) and count work per publication, not one call: a single-publication benchmark showed −98% comparisons while the loaded build ran a per-pair key 899,144 times and cold CPU rose 170% (2026-11-04).
- **Real Postgres** for any query or ORM shape change. A SQLite pass is not evidence for Postgres limits or plans.
- **Compiled-bundle check** for any added or changed dynamic import or interop-sensitive dependency.
- **Consumer inventory:** apply the writer/reader and twin sweep in [happier-implement §4](../happier-implement/SKILL.md#4-select-the-smallest-coherent-systemic-change) before changing a seam contract.
- **Push-not-poll check:** list every timer, interval, periodic fetch, lease or revalidation the change adds or touches, with its reason push cannot serve it and its fires per idle minute, in the report. Replacing a poll with a push must keep the user-visible freshness and recovery it provided.
- **Delete what the fix makes obsolete** (guards, caches, timers, yields) in the same change, and say so in the report.
- **Keep the freshness, approval, revocation and currentness the owner requires** (performance plan R8). A check at the owner's natural boundary (admission, next request, reconnect, next secret acquisition) stays; make it cheap, don't skip it. Per-step or per-call re-evaluation of an admitted decision is not required: revocation takes effect at the next natural boundary, and server per-call checks on admitted work are a cheap "this admitted job is still active" lookup.

## 4. Measure before and after

Every optimization claim needs a measured before and after, or an explicit reason measurement wasn't feasible. Recipes, pitfalls and the CI tiers are in [references/measurement.md](references/measurement.md). In short:

- validate the measuring tool with a control run before trusting its result; use the readiness and instrumentation checks in the measurement pitfalls;
- count-based contracts gate;
- timings, heap and CPU are reported, not gated, until calibrated;
- profile a real loaded runtime identity; a CPU or memory fix closes only on the loaded measurement, never on its benchmark;
- compare heap and CPU only across matched histories (same predecessor route and steps): Session→Language read 66 MB above Home→Language on the same build (2026-11-04);
- turn our own telemetry sampler off;
- run timing milestones on an export build, not the dev bundle.

Before a storage or derived-state experiment starts, write its measured workload profile and kill criteria. Profile → attribute → cheapest fix at the canonical owner comes before new tables or rollups. Usage's two dormant projection experiments cost about a day; profiling-led pruning won (2026-11).

## 5. Review output

For each finding, give:

- the verdict: **ROOT** (removes the cause), **MITIGATION** (reduces the symptom; name the root and its owner), **BAND-AID** (masks it), **OVER-ENGINEERED** (machinery without a real requirement; deletion test) or **REGRESSION RISK**;
- `file:line`;
- the producer or owner;
- the user-facing effect (an idle tab using cores, a list re-rendering, a slow first open, a never-settling Home);
- the simplest root fix, often a deletion.

Then list **same-pattern leads** elsewhere in the tree, with their reachability. A fix is incomplete while the same reachable pattern remains in its corridor (root `AGENTS.md`, "Scope-preserving solution economy").
