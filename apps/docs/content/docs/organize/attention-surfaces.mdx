Happier has several **attention surfaces**. They all answer the same question:

> What needs attention, and where is the safest place to handle it?

The same session event can appear in different places depending on your settings, device, privacy mode, quiet hours, and whether you are already looking at the session.

## What can trigger attention

Happier routes these event types through the attention policy:

- a session is ready after a turn
- a permission request needs approval
- a user-action request needs an answer
- a session starts
- a task is acknowledged
- a task completes or fails
- a resource limit needs attention
- a probe or diagnostic event is detected

The strongest states, such as permission requests and user-action requests, are prioritized over passive unread updates.

## Where attention can appear

Happier can deliver attention through these channels:

- **Inbox** for the durable in-app queue of approvals, requests, unread sessions, and follow-up work
- **Push notifications** for re-entry when you are away from the app
- **Local notifications** for device-local reminders
- **Desktop overlay** for a small always-available desktop island
- **Live Activities and Dynamic Island** on iOS
- **Home widgets** for glanceable iOS state
- **Badges** for count-based attention
- **Webhooks** for automation and external routing

These are channels, not separate systems. Happier builds the attention state once, then each surface renders the amount of detail it is allowed to show.

When you use several [Homes](/accounts/multi-server) on one device, the app-icon badge shows the count from whichever Home updated it last while the app is closed, because the operating system keeps a single badge number per app. Open Happier and the badge returns to the exact total across all of your Homes.

## Webhook destinations

A webhook payload carries session titles, preview text, and the channel signature, and it is sent from the machine your sessions run on. Happier therefore checks the destination before every delivery:

- A destination on the public internet must use **HTTPS**. A plain `http://` public URL is refused.
- A destination on your own machine or local network is delivered only when the URL you configured **names it directly** — for example `http://127.0.0.1:8123/api/webhook/...` or a `localhost` address. A public-looking hostname that resolves to a loopback, private, link-local, or otherwise non-routable address is refused, so DNS cannot redirect a delivery into your local network.
- The address checked is the address connected to, and **redirects are not followed**. If your receiver moves, configure the new URL as the channel destination.

A refused destination is not delivered and does not retry. If a webhook channel stops arriving after configuring it, check that the URL is HTTPS and points where you expect.

## Privacy modes

Surfaces can use one of three preview modes:

- **Status only**: show state such as ready, pending, or permission required without session details.
- **Title only**: show the session title, but hide preview content.
- **Include preview**: show the title and safe preview text when available.

You can set a default privacy mode and override specific surfaces. For example, you may want the desktop overlay to include previews, while Live Activities or widgets only show status on the lock screen.

In development builds, permission and user-action notification previews are controlled separately from ready-message previews. Remote push and Live Activity request previews default on and can be disabled through the request event privacy policy. Long Live Activity previews are shortened to fit their payload and alert limits while retaining session routing. Webhook request previews also default on; disabling previews for a destination or restricting them in the shared policy omits command and question content. See [Notifications](/extras/notifications-setup) for the content and payload limits.

Direct actions from lock-screen style surfaces are also privacy-aware. A Live Activity or widget action can execute immediately only when the surface is allowed to expose enough context and Happier can verify the target session/server. If privacy is restricted or the target cannot be verified, Happier opens the session instead.

## Quiet hours

Quiet hours can deliver, silence, or suppress attention:

- **Deliver**: send normally.
- **Silent**: update the surface without making noise.
- **Suppress**: do not deliver on that channel during quiet hours.

Default behavior is tuned by channel:

- Push and local notifications are suppressed during quiet hours.
- Webhooks, badges, and the desktop overlay keep delivering.
- Live Activities and home widgets keep updating silently.

This means lock-screen and glanceable surfaces can stay useful without waking you up.

## Notification sounds

Happier includes bundled notification tones:

- **Soft** for general attention.
- **Urgent** for permission requests and user-action requests.

You can also use the native system default or make notifications silent. Unknown custom sound ids are treated as custom values and are not passed as bundled app sounds unless the platform can support them.

On Android, bundled sounds map to dedicated notification channels so request notifications can be tuned separately from general ready notifications.

## Desktop overlay

The desktop overlay is the compact activity island on desktop. It summarizes active attention without requiring you to open the full app.

**Unreleased 0.3 development builds:** the compact island shows **Needs you**,
**N working**, or no status word. An admitted request from any Session can bring
it into view. Working Sessions and unread completions remain available in the
opened list; selected Bot faces can also keep the island visible. Completions
alone do not bring it into view.

The companion pet uses the same activity and desktop-overlay delivery policy,
including in the phone and browser app shell. Each Home's delivery restrictions,
mutes and privacy apply before pet content appears. The character keeps its own
enable and selection preferences. Its activity tray is hidden while the enabled
desktop island is available, and returns when the island is disabled or
unavailable. Dismissing a tray item leaves its approval unanswered; a later ask
can appear again.

It can show:

- the current primary session
- total attention counts
- permission cards
- user-question cards
- quota or resource summaries
- completion states

Permission cards classify request risk. Low-risk read-only requests can show quick allow options, including an **Always allow** shortcut. High-risk requests do not show the blanket allow shortcut; they keep review-oriented actions visible instead.

User-question cards can show numbered choices. When a single question has direct options, the overlay can also offer **Other** so you can answer in context with free text.

### Notch preferences

**Unreleased 0.3 development builds:** open **Settings → Desktop app → Notch**
to configure this computer’s notch. **Show the notch** turns it on; **Dock**
chooses Top, Left, Right, or Floating, **Display** chooses its screen, and
**When idle** chooses Tip, Full, or Hidden. **Keep on top of full-screen apps**
controls whether it stays above full-screen windows. These preferences belong to
this device.

The notch is a barely-off-black glass in every app theme and on every dock.
**Settings → Appearance → Glass** still applies: lower Tint shows more of the
desktop through it, and Solid or the system's Reduce Transparency keeps it
opaque. On macOS the desktop blurs behind it; on Windows and Linux it stays
opaque.

**Show Bots** chooses which of your rail Bots appear: **When they need you**,
**While working**, or **Always**. A Bot that needs you always appears. The stored
choice is kept when upgrading; if you have not chosen one, the default is
**When they need you**. **Open Bot conversations** chooses **In the overlay**
or **In a window** for a Bot click. The context menu lets you choose the other
presentation for an individual conversation.

The former running, attention, ready, preview, and auto-hide controls are retired;
they do not override Show Bots or the idle choice. Removing the old preview switch
does not relax a Home’s or this device’s privacy rules. The separate pet activity
modes also retire without changing Show Bots. A pet previously limited to
attention remains on screen while enabled. Account pet enable and selection
defaults, and each device’s inheritance or explicit overrides, are preserved.

### Bots in the notch

**Unreleased 0.3 development builds:** your Bots appear as faces in the island,
in the same order as the rail: up to four, then **+N**. A ring around a face means
the Bot is working; an amber dot means it needs you. On the left and right docks
the faces stack vertically.

- **Click a face** (or press Enter on it) to pin the island open on that Bot: its
  name and state, its last reply, any request waiting for you, and a reply field
  for that Session. **Back** returns to the list; Esc, the pin, or a click outside
  closes it. If the Home or this device shows only status on this surface, the
  reply and the request stay hidden and **Open in a window** reads them.
- **Open in a window** (the icon beside the pin) opens the same Session in its own
  window.
- **Right-click a face** or a Bot row (or press Shift+F10 or the Menu key) for
  **Open in new window** and **Open in the overlay**.
- The opened list shows your Bots first, each followed by its pending request,
  then your other Sessions.

The pinned reply field is that Session's own draft, the same one its window and the
main app show. Switching to another Bot is immediate and shows that Bot's draft;
text you typed stays with the Bot you typed it for.

Completion states are queued by priority. Pending tool work is shown before a normal turn completion, and subagent completion can remain sticky so it is not lost behind a faster-changing session.

## Live Activities, Dynamic Island, and widgets

On iOS, Happier can mirror the current session state into Live Activities, Dynamic Island, and home widgets.

These surfaces are designed for glanceable attention:

- ready and unread state
- thinking/pending state
- permission required
- action required
- overflow counts when more sessions need attention than the surface can show

Live Activities can update locally while the app is active or recently available. If your server and device are configured for remote updates, the server can also update or end an existing Live Activity after the app has registered the ActivityKit target. See [Live Activity remote updates](/self-hosting/live-activity-remote-updates) for the deployment side.

## How Happier chooses the primary item

When multiple sessions need attention, Happier selects a primary item for compact surfaces. The selection uses shared dwell timing so the primary item does not flicker between sessions too aggressively.

In practice:

- urgent requests beat passive unread state
- stale entries age out
- the currently selected item is held briefly when it remains eligible
- each surface can use its own display limits and freshness budget

## Common workflows

### Answer a permission request from desktop

1. Hover or open the desktop overlay.
2. Review the permission card.
3. Use the quick action if it is low-risk, or open the session for review if it is high-risk.

### Answer a question from a surface

1. Open the overlay, notification, Live Activity, or widget action.
2. Choose a numbered option when one is available.
3. Use **Other** or open the session when you need to type a custom answer.

### Keep the lock screen private

1. Open notification or activity-surface settings.
2. Set Live Activities or widgets to **Status only** or **Title only**.
3. Leave direct actions enabled only for surfaces where you are comfortable showing enough context.

### Reduce noise without losing state

1. Configure quiet hours.
2. Let push notifications suppress or silence during those hours.
3. Keep Live Activities, widgets, badges, and desktop overlay available for silent glanceable state.
