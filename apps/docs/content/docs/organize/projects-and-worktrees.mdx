---
title: Projects & worktrees
description: Use Happier projects as persistent repository surfaces, switch between worktrees safely, keep your place, and turn project review comments into a new session.
---

Happier projects are the repository-focused surface you use **outside an active session**.

Use a project when you want to:

- browse a repository before starting a session
- inspect **Files** and **Source control** without opening a transcript first
- keep project-specific tabs, editors, and review state around between visits
- switch between the main checkout and Git worktrees
- collect review comments and then launch a new session from that exact checkout context

Projects and sessions share the same underlying repository tooling, but they solve different jobs:

- **Projects** are for persistent repository context and preparation
- **Sessions** are for agent conversation and execution

## What a project looks like

<Callout type="info">
The Project pages, Sources, Open and dashboards described here are unreleased
0.3 development behavior. Their integrated validation is still in progress.
</Callout>

The Project header identifies the Project and selected checkout. Use its checkout
selector to choose the machine and branch you want to work in. The main column
opens Project pages such as **Overview**, **Code**, **Changes** and **Scripts**;
companion panels keep repository tools available beside the page.

Phones open those destinations as pages rather than squeezing the desktop
columns together. The same Project and exact checkout remain selected.

## Sources and Open

A Source remembers repository metadata for reuse or sharing. It is separate
from an accepted checkout and from your private Project. Open a Source's detail
to inspect its repository, audience, attached dashboards and **Your checkouts**.
Seeing a Source does not grant Git credentials or Machine access; see
[Source and document sharing](/accounts/session-sharing#project-sources-and-attached-documents-03-development).

**Open** can prepare a folder or repository choice without starting an Agent
Session. The destination remains qualified to its Home and machine. On phones,
Open and a standalone Source detail have a Back control in the page header.
Open returns to Projects when there is no previous route; Source detail falls
back to Sources. This includes a Source detail that is still loading or has
become unavailable.

## Open a folder in a remote workspace

Remote workspace attachment is unreleased 0.3 development behavior.
You need an online Happier machine to reach the workspace. This machine is
the **controller**. The Project folder stays on the remote workspace, and
Happier uses a small helper there while it needs access.

To attach an existing Coder workspace, make sure the controller has the Coder
Machines plugin available and connect your Coder account through **Connected
services**.

1. In **Projects**, open **Add project** and choose **A folder on a server…**.
2. Choose the connected Coder account, then select an existing workspace.
3. Choose the folder in that workspace and select **Use**, then **Open project**.

For a saved SSH host, follow the [Remote hosts steps](/apps/remote-hosts#use-ssh-folders-in-a-project).

### Work in the remote folder

Open **Code** to browse and preview remote **Files**, inspect **Git** status
and diffs, and search the checkout. Text search uses ripgrep (`rg`) in the
workspace. Open the Project's **Shell** to run commands from the remote
checkout. These tools can run before you start an Agent session.

Start **New session** from the remote Project with its checkout selected to
run the Agent on the server in that folder. Edits are made in place. To work
in a copy, choose **Open this branch on another machine** from the checkout
selector and create a copy on the controller. Open the copied checkout and
start the session there.

### Start, reconnect or forget

If a Coder workspace is stopped, select **Start** when Files or Git offers it.
Happier can refresh those panes once the workspace is running. If the
controller goes offline, the Project keeps previously loaded content when
available. Bring the controller back online to resume access to the folder.

To remove the remote Project from Happier, choose **Remove**, then **Forget**.
The remote workspace and its files stay where they are.

## Shared setup (0.3 development)

The unreleased setup flow can accept a Source's protected setup publication into
your private Project. The accepted copy stays usable when the publisher changes
it or you lose Source access. Updates are explicit: review the before-and-after
effective definition before replacing your accepted copy. Shared declarations
override corresponding repository declarations; your personal overrides apply
last. Detaching shared setup preserves your personal overrides and checkout files.

One update decision can accept the reviewed copy and approve its lifecycle
**This time** or **Until it changes**. Keeping the existing copy changes neither
content nor consent. If Team setup flags a change to a repository’s shared
setup, open that repository’s review to see what would change on your checkout.
Approval covers setup, teardown and executable autostart
effects together; a teardown-only change still needs review during acceptance.
Setup approval does not run teardown. An Agent can request acceptance but cannot
create remembered execution consent. Integrated validation is still in progress.

## Setup environment inputs (0.3 development)

The in-progress Project setup implementation can import variable names from
`.env.example` without copying its values. New names start as optional config
requirements so you can choose which need secrets or must be present. Existing
requirements keep their classification, including requirements inherited from
shared setup. Import into your personal setup draft keeps these declarations
private; saving that draft does not change the repository or shared publication.

At launch, the selected checkout's `.env`, `.env.development`, `.env.local` and
`.env.development.local` supply private defaults in that order. Deliberate
Project, Profile and launch choices take precedence. A declared secret uses your
selected secret reference; a value in an environment file cannot satisfy it.
These runtime values are excluded from shared setup and review. This flow is
unreleased and its integrated validation is still in progress.

## Overview dashboards

In the 0.3 development flow, Overview has a default dashboard and can hold named
dashboards. Create, rename, reorder or delete a named dashboard through its
dashboard controls. The default dashboard cannot be deleted. Selecting a
dashboard changes the view; it does not change its audience.

Sharing a dashboard uses its document access sheet. Attaching it to a Team
Source is a separate operation and does not grant access. On an attached shared
dashboard, Can read permits viewing, Can edit permits editing and renaming, and
the owner or Admin can manage sharing. The recipient cannot reorder or delete
it from the owner's dashboard inventory.

## Dev servers

In the 0.3 development flow, open **Logs** from a managed service's menu in
**Dev servers** to read that run's native output. Use Follow to see new lines
while the log pane is open, or pause it to read the lines already loaded. With
Local capture enabled for the service's checkout, the pane also shows
OpenTelemetry logs captured for that worktree.

## Databases and telemetry

These surfaces are in unreleased 0.3 development source. With the Database
workbench available on your Machine, open **Databases** from the Project's
development services, or use **Database** in the Project or Session side rail.
The picker lists databases for the selected checkout. It can discover a network
database URL in a dotenv file if Project Setup declares that config variable.
When a running service uses the same variable for its database, the service takes
precedence. To connect manually, choose **Connect a database** and select or add
a Saved Secret for the connection. Use **Test and connect**, then **Try again**
if the database is offline. **Forget database** removes the checkout association
and keeps the Saved Secret available. The picker can show the
database endpoint and the Machine that runs the workbench. Managed databases open
from the deployment's Database page.

To open a SQLite database already in the selected checkout, choose
**Connect a database** → **Use a SQLite file**. Enter its path relative to the
checkout and choose **Open SQLite file**.

On a database's **Overview**, check its size, connections, and statement
statistics where the engine shares them. Expand a schema to see its tables.
When the database has an **Automations** section, it shows automations for that
target.

For a Worktree database with local capture, open **Insights → Queries** to see
statements captured for the selected database. PostgreSQL connections to another
database on the same service appear only in Worktree capture. Open a statement
for its masked detail. If it belongs to a captured request, choose **Inspect
request** to see any likely N+1 findings for that request.

In 0.3 development builds, a finding can trigger an automation when the Machine's
own Account starts the service and the selected database allows agent reads at
Start. If you start a service as a guest on someone else's Machine, you can still
inspect your findings in Workbench. If you change the database's agent access,
restart the service for the change to apply to finding automations.

An agent reading Worktree capture must select a database. The database's agent
access level determines whether the agent can read its captured queries.

To change how often **Activity** refreshes, go to **Settings → Plugins →
Database Workbench → Activity** and edit **Activity refresh interval (ms)**.
You can also search Settings for **Activity refresh interval**. The plugin
saves the interval for your Account. Activity refreshes every 5,000 ms by
default while open. Enter 0 to refresh manually. If the selected database’s
Machine goes offline, Activity keeps its last sample and pauses refresh until
the Machine reconnects.

In the full workbench, open **Read only** or **Can edit** to view the agent
access level. For worktree and manually connected databases, choose a level and
select **Save**. The Machine that runs the Workbench stores that setting.

For a deployed database, choose **Open Environment settings**, then find
**Database access**. An Environment manager can turn editing off, allow editing
by Project managers or by Project members who can deploy, or choose people,
groups, and Teams from the Project audience. Preview Environments inherit the template's
policy. Agent levels are **None**, **Read**, **Read and write (asks first)**, and
**Read and write (no approval)**. Acting as an agent never expands the person's
access. A person's stricter approval settings still apply.

Stage changes in the Workbench and review them before choosing **Apply**. A
production review names the destination Environment and shows available backup
controls. Choose **Back up now** to run a configured backup before applying.
If a writer is missing, an Environment manager can use **Set up write login**
on their own server. For a managed database, select **Save write connection**
to use the Environment's direct writer connection. Choose its Saved Secret first
if the Environment does not already identify it.
After setup succeeds, apply the same staged changes again.

If someone changes a row before you apply, **Review** keeps your drafts and marks
the conflicting change. Select **Reload** to see that row's current values in the
comparison before applying again, or **Take back** to remove the change from the
batch.

- In a table, open a row and use **Referenced by** to jump to rows in another
  table that point to it. The destination opens with the selected row's key
  values as filters.
- In the **Console**, enter SQL with placeholders for the selected engine.
  Happier adds a field for each bind slot it finds. Each field starts as Text.
  Choose a different type when the query needs one. The Console identifies the
  database where the query runs. **History** keeps the SQL on this device for
  that target. A query that returns zero rows still shows its result columns.

PostgreSQL **Insights** excludes the catalog queries Workbench runs to inspect
the database. SQL you run in the **Console** still counts. **Activity** omits
Workbench's own database connections. PostgreSQL may retain catalog entries
from earlier Workbench versions until it evicts them from `pg_stat_statements`.

If PostgreSQL statement statistics need setup, **Insights** shows the required
setting and offers **Enable statistics** when the connected target supports it.
**Ask an agent to enable pg_stat_statements** prepares an editable Session
draft when the target needs help with setup. For a worktree, **Add telemetry
to this app** prepares an editable draft for the selected checkout, even when
the Insights rail has no database yet. Review the draft before sending it.

### Check for index suggestions

In **Insights**, open **Statements**, select a PostgreSQL statement, and choose
**Check for index suggestions**. The check uses a direct connection to PostgreSQL
16 or later and the database's existing read login. It handles simple
schema-qualified `SELECT *` statements with an integer equality filter, an
integer sort column, or both. The statement text must be visible to that login.

A suggestion names the table and column and shows the estimated planner cost
before and after the hypothetical index. The check tests one B-tree at a time
and shows candidates that at least halve that cost. Planner costs can differ
from actual latency. The check leaves the database's indexes intact.

If Insights shows **Index suggestions need the hypopg extension**, ask a
database administrator to set it up in the selected database, then choose
**Retry**.

| PostgreSQL host | Administrator setup |
| --- | --- |
| Your own server | Install HypoPG for the server's PostgreSQL major version and run `CREATE EXTENSION hypopg`. [HypoPG installation](https://hypopg.readthedocs.io/en/rel1_stable/installation.html) |
| Docker | Build an image with the matching HypoPG extension files and run `CREATE EXTENSION hypopg` in the database. [PostgreSQL Docker image extensions](https://github.com/docker-library/docs/blob/master/postgres/README.md#additional-extensions) |
| Supabase | Enable HypoPG in **Database → Extensions** or run `CREATE EXTENSION hypopg WITH SCHEMA extensions`. Connect through the direct PostgreSQL endpoint. [Supabase HypoPG](https://supabase.com/docs/guides/database/extensions/hypopg) |
| Neon | Run `CREATE EXTENSION hypopg` in the selected database on the branch and use the direct endpoint. [Neon extensions](https://neon.com/docs/extensions/pg-extensions) |
| Railway | Deploy a custom PostgreSQL image with matching HypoPG extension files, then run `CREATE EXTENSION hypopg`. [Railway PostgreSQL extensions](https://docs.railway.com/databases/postgresql#extensions) |

If your administrator restricts extension permissions, the read login needs
`USAGE` on the HypoPG schema and `EXECUTE` on `hypopg_create_index(text)` and
`hypopg_reset()`, along with its existing access to the table and statistics.

**Optional administrator step.** PostgreSQL hides statement text and query IDs
for workload run by other logins. An administrator can run
`GRANT pg_read_all_stats TO happier_ro` if that read login should see other
users' query text, query IDs, and restricted statistics across the PostgreSQL
instance. Grant this only after reviewing that broader visibility. Happier
never grants this role automatically. [PostgreSQL statement statistics](https://www.postgresql.org/docs/16/pgstatstatements.html)

In **Insights**, open **Findings** and select a statement, table, index, or
activity item to see its evidence. **Prepare brief** opens a preview for a
Session. **Create workflow from finding** opens a draft with the selected
source and an editable condition for the kind of finding. **Dismiss finding**
hides that evidence for your Account on the
Machine that runs the workbench. A later observation with changed evidence can
appear again.

In **Databases** on the Project's development services page, use **Turn on
capture** under **Local capture**, then start or restart the service. The
switch applies to the Project's worktrees on that Machine. Happier can observe
queries through eligible PostgreSQL connections and receive traces and logs
from an instrumented service. A collector you configure in the service's
environment takes precedence over Happier's local OpenTelemetry endpoint.

To correlate a PostgreSQL execution with its OpenTelemetry database span,
generate a fresh UUIDv4 for each execution. Add it as the span's
`happier.db.execution_id` attribute and put both the same ID and the database
span's W3C `traceparent` in a SQL commenter block before the statement's
terminating semicolon. For example, the block accepts
`/*traceparent='00-<trace-id>-<database-span-id>-01',happier.db.execution_id='<uuid>'*/`.
Capture retains both observations and counts a proven pair once in the request.
Matching SQL or a reused ID leaves the observations separate.

Use **Check capture status** for the selected worktree. The status shows
**Preparing capture** while a service launch is opening its capture listeners.
**Retry capture** resumes recording after a coverage failure. If capture could not start with a
service, check **Review output** on its row in **Dev servers** and use that row’s
**Restart** to retry. **Clear capture** clears data for that worktree. Turning
off capture stops recording and keeps running services connected until they
stop.

A service that was already running when you turned capture on needs to restart
to pick up capture settings. In the selected managed service's Capture view,
choose **Restart** from the restart message or the **More** menu. From Worktree
Capture, open **Dev servers** and use the affected service's row.

When an Environment has a collector, its **Telemetry** tab shows **Endpoints**,
**Traces**, **Logs**, and **Queries** for the selected time window. Open a trace
to inspect the request and the steps that contributed to its duration. Use the
tab's menu to open Settings. An offline collector leaves captured data
unavailable until the Machine reconnects.

On a wide **Services → Apps** list, enable **Requests · 24 h** from **Columns**
to see each Environment's request volume and trend when available. A dash
means the collector has no value for the row. A measured zero appears as zero.
Project deployment lists share these column choices. **What runs here** on a
Machine uses its own columns. On a phone, Services rows keep their deployment
details and can show up to two additional facts on the second line.

From Home's **Add to Home** picker, choose **Check** for a saved Monitoring
check, including a saved key-flow check. To graph application data, choose
**App metric** from Telemetry and select an Environment and metric. Request
metrics can be narrowed to a route when the collector offers route choices.
Telemetry also offers **App vitals** and **Slowest routes**.

## Project root vs selected worktree

This is the most important mental model:

- the **project** stays the same repository
- the **selected worktree** changes the checkout context used by Files, Source control, terminals, and new sessions

Selecting a worktree does **not** turn the project into a different project.

The project overview stays anchored to the base repository, while the selected checkout affects:

- the Files browser
- Source control status and diff review
- review comments scope
- terminal launches
- the default folder when you start a new session from that project

## Worktree service ports (0.3 development)

Worktree port allocation is opt-in in the Project definition. This development
implementation is still undergoing integrated validation; it is not a released
availability claim.

`slots` declares exactly how many ordinary ports each workspace receives. There
is no automatic count inferred from detected services or previously assigned
ports. Declare the count when enabling this option; named listener ports remain
separate from these slots.

For example, two listening services can select separate slots:

```json
{
  "version": 1,
  "worktreePorts": { "enabled": true, "slots": 2 },
  "services": {
    "web": { "source": { "kind": "command", "command": "./start-web" }, "runtime": { "primary": true } },
    "api": { "source": { "kind": "command", "command": "./start-api" }, "runtime": { "portSlot": 1 } }
  }
}
```

Each worktree keeps its own assigned numbers on its execution machine. Commands
receive `HAPPIER_WORKTREE_PORT` and numbered values such as
`HAPPIER_WORKTREE_PORT_1`; a listening service's `PORT` defaults to its selected
slot. Deliberate Project environment values take precedence. A script or Compose
publication with a fixed literal port still needs to be parameterized; allocation
does not rewrite repository files or reserve an OS socket until the app binds.

Stopping a service retains its numbers. Happier releases the assignment when
worktree removal succeeds, including when Storage retires a live worktree. A
failed teardown that stops removal leaves the assignment in place.
An unrelated app can occupy a retained number while stopped. That failure is
visible on Start; choosing replacement numbers requires the worktree's affected
executions to be stopped.

## Worktrees list behavior

The Project header's checkout selector lists known checkouts and worktrees.

That list includes:

- the project’s main/root checkout
- visible live Git worktrees for that repository

Use a local worktree entry to change the Project's active checkout context.
Entries on another machine open that exact accepted checkout.

### What happens when you select one

When you select a row:

1. the project keeps the same identity
2. the active checkout switches to that root/worktree
3. Files and Source control immediately start using that checkout
4. the URL and remembered project state are updated

This means you can inspect one worktree, switch to another, open a terminal there, then start a session in that same checkout.

## What happens if a worktree was deleted

Happier treats deleted/prunable worktrees as invalid selections.

If the currently remembered or deep-linked worktree no longer exists:

- Happier automatically falls back to the main project root
- the stored project selection is repaired
- the route is normalized
- a recovery toast tells you the missing worktree was reverted to the project root

Deleted worktrees should not leave the project stranded in a broken state.

## Reopening a project

Projects are designed to reopen where you left them.

Happier remembers project state such as:

- the last active mobile sub-screen
- the selected worktree/root
- right-panel state
- open details tabs
- local draft/edit state owned by those panes

### Desktop

On desktop, reopening a project restores the same project pane scope instead of dropping you back to a blank overview every time.

In 0.3 development builds, right-click a project or file tab in the browser
and choose **Open in a window**. The pop-up shows that tab on its own and uses
the same site's sign-in. The original tab stays open.

### Mobile

On mobile, opening a project from the project list returns to:

1. the last active project screen for that project, if one exists
2. otherwise **Overview**

The selected worktree is also restored when possible.

## Terminal from a project

The Project menu's **Terminal** command opens the bottom terminal pane for the
selected checkout.

That means:

- if you switched to a worktree, the terminal starts there
- if you are on the main checkout, the terminal starts from the project root

## Project command definitions

<Callout type="info">
The Scripts page, project-definition inspection and guarded manifest editing
describe unreleased 0.3 development behavior. Integrated validation is still in
progress; this is not a stable or preview availability claim.
</Callout>

Open **Scripts** for the selected checkout's commands and setup. If it has no
project file, **Create project file** opens the editor and **Set up with an agent**
prepares an ordinary editable new-session draft. Review it and explicitly send
when ready; opening the draft does not start the Agent. **Edit project file**
offers Form and raw editing for an existing definition.

When a setup-authoring Session is associated with this checkout, Scripts shows
its private Session name and time once they are readable. The line reserves its
space while that Session loads, including before a project file exists. It
records the authoring relationship, not proof that setup ran or succeeded.
On a wide Scripts page, **Changes** returns to the stored authoring context when
that context is available. Older checkouts without a recorded relationship may
only discover it after the Session has loaded; historical Sessions are not
backfilled.

For declared scripts, the Overview **Scripts** widget shows each script's status
and opens existing output when selected. Run commands from the Scripts page or
companion list; the widget's script rows have no Run button. Setup has its own
review and status row. While its review awaits your decision, it says
**Waiting for your approval**; opening that review does not run setup.

The development Action catalog projects inspection as `happier project inspect`
and saving as `happier project manifest update`. Both take a qualified checkout:
its Home/server, workspace, machine and root path. Inspection returns the project
file and its basis, detected definitions and import candidates. Saving takes the
reviewed basis and intended file text and uses the shared configurable **Ask first**
default. Form, raw, import, remove and reorder use the same save operation.

Keep a project's commands in their native tool files, or declare them in
`.happier/project.json` in the selected checkout. Passive inspection finds static
definitions without evaluating project code, running hooks, starting commands or
creating a project file. A detected command retains its native tool, file and
target; adding it to the project file stores that reference rather than copying
the command body:

```json
{
  "version": 1,
  "toolchain": { "kind": "toolchain", "tool": "mise", "configPath": "mise.toml" },
  "scripts": {
    "build": {
      "source": {
        "kind": "native",
        "tool": "package_script",
        "file": "package.json",
        "target": "build"
      }
    }
  }
}
```

Scripts and services are separate declarations. Inspection also reports toolchain
and Devcontainer selections separately. When a file cannot be read or a definition
needs native evaluation, inspection retains the definitions it did find and reports
partial coverage with a diagnostic for that file. Finding a definition does not
mean its tool is installed or its setup has succeeded.

Import candidates distinguish available, unavailable, unresolved and ambiguous
offers. Only verified available, unambiguous commands are preselected; other
offers stay in the inspection results without being preselected. A declared tool
version is not proof that the version is installed: inspection does not run version
commands. Unproved versions remain unresolved. Passive plugin offers also remain
unresolved because inspection does not run their command or toolchain effects.

Unknown JSON keys produce diagnostics while valid known declarations remain usable.
Structured edits preserve untouched fields and their values, including unknown
fields; raw saves preserve the submitted text exactly. Invalid raw text stays in
the draft, with Form and save disabled until it is valid. Missing or invalid
required fields still need fixing before a save can succeed. Native reference paths
must stay within the selected checkout.

Every save checks the file basis from the previous read. Creating a file requires
it still to be absent; updating one requires its contents still to match that read.
If another editor changed it, keep your draft, read the current file and review the
changes before saving again. This check is best effort: it does not lock out an
external editor. Inspection and saving do not run setup or grant setup approval.

Setup approval with **Until it changes** covers the reviewed lifecycle commands,
selected toolchain and the current contents of the checkout files they run.
For a plain command, that means a script
named as the program, sourced, or passed to an interpreter, such as `./setup.sh`,
`source scripts/env.sh`, `bash -e scripts/setup.sh` or
`pwsh -File scripts/setup.ps1`, including after `env`, `sudo` or `cmd /c`. Editing,
adding or relinking one of those files asks again. A program linked outside the
checkout, such as `.venv/bin/python`, is reviewed by where it points. For a folder,
as in `node server`, the review covers its `package.json` and the entry file that
names (`main`, or `index.js`), not what that file imports.
In 0.3 development builds, tsx and bun also record TypeScript entry candidates,
including `app.ts` when the operand is `app.js`. Bun commands record the cwd's
`bunfig.toml`; bare names such as `bun run app` also record `package.json` and
`node_modules/.bin/app` in the cwd and its checkout ancestors, since these can
select a different program.
Explicit configuration files and checkout-relative Node preloads are recorded,
and `bun --cwd` selects the directory in which inputs are resolved. Files loaded
by a config or preload still need `workspace.setupInputs`, just like imports.
Happier does not follow
inline `-c` code or what a script sources or reads. Commands such as
`npm run setup` or `make setup` read their own definition files, so declare them
with the native source kinds (`package_script`, `make` and so on) or list those
files in `workspace.setupInputs` to make their changes ask again too. A native
source covers its definition file and the checkout files that the selected task's
commands run, read the same way:

- `package_script`: the script, its `pre`/`post` scripts and the package scripts
  it runs by name.
- `make` and `just`: the recipe and the recipes it depends on in the same file.
- `taskfile` and `mise` tasks: the task's commands, its dependencies, its `dir`, and
  a mise task's `file`.
- `devbox` scripts: the script and the `init_hook` that runs before it.
- `turbo`: the package scripts the task and its `dependsOn` tasks run in each
  package, and every `package.json` under `turbo.json`, so adding a script to a
  package asks again.
- `compose` and `flox`: the definition file only. Their effects are images and
  environments, not checkout scripts.

The selected toolchain is covered the same way. For `nix_flake` and `devenv`, Nix
evaluates more than the config file, so the review includes every `.nix` file
under its folder that your repository does not ignore, plus `flake.lock` (and
`devenv.lock` and `devenv.yaml` for devenv). Editing any of those asks again.
For devbox, the review includes what `init_hook` runs (a devbox `include` is not
supported for review yet, so setup refuses it).
For mise, it includes the files `_.source` loads, including `{{config_root}}` paths;
`_.file` and `_.path` are not covered, so list those in `workspace.setupInputs`.
Files a Nix expression names as a path literal outside its folder, and scripts started
through runners such as `run-s` or `concurrently`, are not followed either.

List other files a command reads in `workspace.setupInputs`:

```json
{
  "version": 1,
  "workspace": {
    "setup": [{ "kind": "command", "command": "bash scripts/setup.sh" }],
    "setupInputs": ["scripts/lib.sh", ".tool-versions"]
  }
}
```

In the 0.3 development removal flow, an accepted checkout's teardown runs inside
the removal operation before its files are removed. A cleanup failure preserves
the checkout. A person can explicitly skip cleanup; unattended removal uses only
remembered consent and can skip cleanup when that consent is unavailable. Forgetting
a Project relationship and deleting checkout files remain separate choices.

## Running commands on workers

<Callout type="info">
Worker placement, the finite command queue and worker-copy retirement are in
development on the 0.3 line. They still require integrated package and live
validation; this is not a stable or preview availability claim. New-machine
acquisition, cold wake and foreign-requester source preparation are separate
integration work, not available fallbacks.
</Callout>

The development flow selects a destination for a finite Project command from
existing eligible worker copies. The source declaration determines the requested
command and resource demand. An accepted command enters that machine's first-in,
first-out queue; acceptance does not mean it has started. When capacity is
available, its reservation covers copying current source files, reviewing the
destination's definitions and setup, and running the command. Setup approval and
successful setup are separate facts. Passive inspection does not evaluate native
setup; readiness stays unknown when the captured files and references cannot decide it.

Inspect the same retained operation to distinguish queued, copying, setup and
running, and to read or copy its output. Canceling a queued command can prevent
launch. Once preparation or execution has begun, an uncertain Stop keeps custody
and capacity occupied until cleanup is confirmed; inspect or explicitly Stop that
occurrence rather than submitting another Run. Long-lived Services are separate
from this finite command queue. A Service without a declared port may have an
observed HTTP address, but no address is invented when listeners are ambiguous.

In the 0.3 development implementation, an explicitly portable Service can use a
worker's native command or selected toolchain. Happier copies current files
through Sync before reviewing that destination's native facts and setup. Changed
copied configuration or an unavailable native adapter prevents launch; it does
not silently run in the host environment. Integrated package and live validation
remain required, and native tool support still depends on the destination's
qualified platform and version.

Service destinations also offer the existing New Machine preset or one-off
selection in the 0.3 development implementation. Choosing it does not acquire a
machine: explicit Start or confirmed Move begins acquisition and waits for real
enrollment before continuing. A running Service stays where it is during
enrollment. Back or Cancel retires the continuation; an uncertain acquisition or
Start is inspected rather than automatically submitted again. This flow does
not create an agent Session and still needs integrated and live validation.

Before retiring a worker copy, dispose of the actual work that depends on it;
retirement reports queued commands, preparation, processes, Services or Sync
dependencies rather than silently canceling them. Leaving the files and removing
them are separate choices. If the relationship was retired but file removal is
uncertain, inspect the current relationship and copy before trying again. An
uncertain result is not proof that the files were removed or that retirement was
rolled back. Service placement-save plus Move remains a separate integration
boundary, not an automatic transfer of a running Service.

## Devcontainer child machines

<Callout type="info">
Managed Devcontainer children are in development on the 0.3 line. Integrated
validation and the real Docker journey are still pending; this is not a stable
or preview availability claim.
</Callout>

A Devcontainer child is an ordinary Happier machine running inside a container.
Its files, source control, terminals and sessions use the child's observed user
and workspace folder, which can differ from the Docker host's folder. Selecting
a Devcontainer does not turn host commands into container commands automatically.

Choose Docker container on a computer you control to start from a container image,
optionally with a setup script. Docker or Podman is needed on
that computer. The workspace folder is optional: without a host folder the child
uses a container-owned volume. A Dev Container file or inline configuration is
available for advanced setups. Presets, Team presets, pools and retention use the
existing managed Machine flows.

You can save or edit a container preset without a connected computer. It stores
your image, setup script and configuration choices. Image presets can be used
directly: the selected computer checks the image and runs the saved child setup.
Advanced file or inline configurations require native effect review for each
creation. Those reviewed effects belong to that creation, rather than the
reusable preset. Delegated Team creation from advanced configurations remains
unavailable; a Team member cannot supply the custodian's native review.

The image must provide a Linux shell and the `id`, `chown` and `sleep` commands.
Happier replaces the image's entrypoint and command to keep the child running;
Dev Container metadata hooks are not run in image mode. The setup script runs
as the image's default user on creation and rebuild, not on stop and start. The
named workspace volume is retained on rebuild and container deletion.

Image creation and rebuild pass the selected Home endpoint's hostname and the
creating computer's resolved addresses to Docker or Podman through `--add-host`.
This preserves private DNS resolution without changing the container's network
mode. The container still needs a working route to Home; this does not create
a VPN or forward the computer's Home connection. Advanced Dev Container
configuration keeps its reviewed native networking settings.

For advanced configuration, creation reviews host initialization and child
image, build, Compose, Features, mounts, networking and lifecycle effects before
running them. Rebuild is a separate reviewed operation with an **Ask first**
default. If the reviewed effects change, review them again before continuing.
Configuration inspection does not run initialization or lifecycle hooks.

The Docker host controls Start, Stop and Rebuild. When it is offline, these
operations are unavailable; a running child that is still reachable can continue
using its ordinary Happier connection. There is no offline restart or automatic
controller replacement.

Bind-mounted source has one synchronization writer on the host, while execution
stays on the child. Independent child storage is a separate workspace. Changed
native identity, missing roots or an unavailable bind controller stop preparation
before copying or launching; Happier does not silently create another mirror.

Stop retains source and volumes. Rebuild replaces the container without deleting
bind sources or external volumes and requires fresh enrollment. Session history
and drafts remain; running sessions are not moved to the replacement. An uncertain
native result needs inspection of that same managed resource before retrying.

## Make a workspace available on another machine

<Callout type="info">
Linked workspace creation is development-only on the 0.3 line. It requires matching workspace
operation support and the managed sync component on the participating machines; it is not a
stable or preview availability claim. An unavailable component or unsupported operation asks
for an update instead of falling back to another file-transfer system.
</Callout>

Open the selected workspace's details and choose **Add machine** under **Available on**.
Choose the destination machine and folder, then decide how that copy will be used:

- **Replica** carries source changes to the destination while preserving destination-only files.
- **Exact replica** can remove destination-only files and requires explicit approval for that
  continuing behavior.
- **Editable copy** accepts changes from either endpoint and surfaces differences it cannot
  reconcile for review.

Using an existing folder and creating one from the source are separate choices. Attaching an
existing editable checkout does not silently replace it with the source: its differences are
reconciled through the link. Creating from the source can replace existing destination content,
so Happier first asks for approval when replacement is required. Advanced options control each
link's file selection; different copies can intentionally exclude different files.

You can add several copies around one main workspace. If you start from an already linked
copy, the form identifies that set's main workspace as the source. It does not create a second
link between the two copies. Several editable copies share live work in progress, not an
immutable revision or a file-history archive. Separate Git worktrees remain useful when agents
need to work independently.

Linking does not start a session. Return to **Available on** to inspect status, compare conflicts,
pause a link, or stop syncing while leaving its folders in place. If cancellation or a lost
connection leaves the result uncertain, inspect the relationship before trying again; canceling
does not mean that committed linking or file changes were rolled back. See
[workspace status and conflict resolution](/sessions/session-handoff#living-with-a-synced-workspace).

## Review comments in projects

Projects support the same review-comment drafting model as session repository surfaces.

You can create review comments from:

- **file details** views
- **diff review** views

This is useful when you want to prepare a review-driven prompt before starting a session.

### How review comments are scoped

Review comments are stored per exact workspace scope:

- server
- machine
- root path / worktree path

That means review comments are isolated correctly between:

- the main repository root
- each Git worktree
- the same repo on a different machine

If you switch from one worktree to another, you see that worktree’s review comments, not a merged global bucket.

## Start a new session from project review comments

When the current project checkout has saved review comments, the project details header shows a **new session** action.

Use it when you want to turn your project review notes into a real agent task.

When you open the new-session screen from that project:

- the selected machine is preserved
- the selected directory is the current project root or worktree
- project shortcuts can reuse the newest session setup from that project when **Remember last project session selections** is on
- the new-session screen automatically discovers review comments for that exact path

For the full shortcut model, see [New session shortcuts](/sessions/new-session-shortcuts).

## Review comments in the new-session screen

The new-session screen now uses one unified path-based model.

If the current machine + directory match saved review comments, Happier shows a **Review comments (N)** chip with a small switch.

Important behavior:

- the chip is shown for project-launched flows and generic `/new` flows
- it is **enabled by default** when matching review comments exist
- the switch can be turned off without deleting the saved drafts
- changing the selected directory or machine updates discovery automatically
- if the new path has no review comments, the chip disappears

This avoids two competing systems such as “project-seeded review comments” vs “generic new-session review comments”.

There is only one rule:

- if the current new-session path matches saved review comments, Happier offers them for that path

## What gets sent when review comments are enabled

When you create the session with the review-comments chip enabled:

- Happier creates the session first
- then it sends a follow-up message containing the review comments payload
- any additional initial message text is included in the same follow-up

If the same new-session flow also includes file attachments:

- attachments are uploaded first
- the review-comments follow-up includes the attachment file references too

This keeps the first actionable message coherent: the agent sees the review comments and any related attachments together.
