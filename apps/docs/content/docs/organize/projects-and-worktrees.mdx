---
title: Projects & worktrees
description: Use Happier projects as persistent repository surfaces, switch between worktrees safely, keep your place, and turn project review comments into a new session.
---

Happier projects are the repository-focused surface you use **outside an active session**.

Use a project when you want to:

- browse a repository before starting a session
- inspect **Files** and **Source control** without opening a transcript first
- keep project-specific tabs, editors, and review state around between visits
- switch between the main checkout and Git worktrees
- collect review comments and then launch a new session from that exact checkout context

Projects and sessions share the same underlying repository tooling, but they solve different jobs:

- **Projects** are for persistent repository context and preparation
- **Sessions** are for agent conversation and execution

## What a project looks like

On desktop and wider layouts, a project is split into three cooperating surfaces:

- a **header** with back, worktrees, and terminal actions
- a **main content area** that stays anchored to the project itself
- a **right panel** with **Source control** and **Files**

On phone-sized layouts, the same project is shown as route-based screens:

- **Files**
- **Source control**
- **Details / overview**

The same project header model is used on both desktop and mobile:

- back button to return to the project list
- project title
- current-worktree-aware title when you are not on the main checkout
- worktrees button
- terminal button

## Project root vs selected worktree

This is the most important mental model:

- the **project** stays the same repository
- the **selected worktree** changes the checkout context used by Files, Source control, terminals, and new sessions

Selecting a worktree does **not** turn the project into a different project.

The project overview stays anchored to the base repository, while the selected checkout affects:

- the Files browser
- Source control status and diff review
- review comments scope
- terminal launches
- the default folder when you start a new session from that project

## Worktrees list behavior

The project overview includes a searchable worktrees list.

That list includes:

- the project’s main/root checkout
- visible live Git worktrees for that repository

Use it to move the project’s active checkout context without leaving the project.

### What happens when you select one

When you select a row:

1. the project keeps the same identity
2. the active checkout switches to that root/worktree
3. Files and Source control immediately start using that checkout
4. the URL and remembered project state are updated

This means you can inspect one worktree, switch to another, open a terminal there, then start a session in that same checkout.

## What happens if a worktree was deleted

Happier treats deleted/prunable worktrees as invalid selections.

If the currently remembered or deep-linked worktree no longer exists:

- Happier automatically falls back to the main project root
- the stored project selection is repaired
- the route is normalized
- a recovery toast tells you the missing worktree was reverted to the project root

Deleted worktrees should not leave the project stranded in a broken state.

## Reopening a project

Projects are designed to reopen where you left them.

Happier remembers project state such as:

- the last active mobile sub-screen
- the selected worktree/root
- right-panel state
- open details tabs
- local draft/edit state owned by those panes

### Desktop

On desktop, reopening a project restores the same project pane scope instead of dropping you back to a blank overview every time.

### Mobile

On mobile, opening a project from the project list returns to:

1. the last active project screen for that project, if one exists
2. otherwise **Files**

The selected worktree is also restored when possible.

## Opening the worktrees overview

The worktrees button in the header is an explicit project view mode.

- If you are already in Files, Source control, or Details, pressing it opens the worktrees overview
- If details tabs already exist, the overview still opens
- Opening a new details action from overview exits overview and returns to the detailed surface

In other words, “show me worktrees” is treated as explicit user intent, not as something suppressed just because details already exist.

## Terminal from a project

The terminal action in the project header always opens a terminal details tab for the current selected checkout.

That means:

- if you switched to a worktree, the terminal starts there
- if you are on the main checkout, the terminal starts from the project root
- if you were looking at the worktrees overview, opening the terminal exits overview and opens the details tab

## Project command definitions

<Callout type="info">
Project-definition inspection and guarded manifest editing are in development on
the 0.3 line. The Action contracts and CLI command projections below still await
integrated package and live validation; the visual Scripts editor is a later
integration step. This is not a stable or preview availability claim.
</Callout>

The development Action catalog projects inspection as `happier project inspect`
and saving as `happier project manifest update`. Both take a qualified checkout:
its Home/server, workspace, machine and root path. Inspection returns the project
file and its basis, detected definitions and import candidates. Saving takes the
reviewed basis and intended file text and uses the shared configurable **Ask first**
default. Form, raw, import, remove and reorder use the same save operation.

Keep a project's commands in their native tool files, or declare them in
`.happier/project.json` in the selected checkout. Passive inspection finds static
definitions without evaluating project code, running hooks, starting commands or
creating a project file. A detected command retains its native tool, file and
target; adding it to the project file stores that reference rather than copying
the command body:

```json
{
  "version": 1,
  "scripts": {
    "build": {
      "source": {
        "kind": "native",
        "tool": "package_script",
        "file": "package.json",
        "target": "build"
      }
    }
  }
}
```

Scripts and services are separate declarations. Inspection also reports environment
and Devcontainer selections separately. When a file cannot be read or a definition
needs native evaluation, inspection retains the definitions it did find and reports
partial coverage with a diagnostic for that file. Finding a definition does not
mean its tool is installed or its setup has succeeded.

Import candidates distinguish available, unavailable, unresolved and ambiguous
offers. Only verified available, unambiguous commands are preselected; other
offers stay in the inspection results without being preselected. A declared tool
version is not proof that the version is installed: inspection does not run version
commands. Unproved versions remain unresolved. Passive plugin offers also remain
unresolved because inspection does not run their command or environment effects.

Unknown JSON keys produce diagnostics while valid known declarations remain usable.
Structured edits preserve untouched fields and their values, including unknown
fields; raw saves preserve the submitted text exactly. Invalid raw text stays in
the draft, with Form and save disabled until it is valid. Missing or invalid
required fields still need fixing before a save can succeed. Native reference paths
must stay within the selected checkout.

Every save checks the file basis from the previous read. Creating a file requires
it still to be absent; updating one requires its contents still to match that read.
If another editor changed it, keep your draft, read the current file and review the
changes before saving again. This check is best effort: it does not lock out an
external editor. Inspection and saving do not run setup or grant setup approval.

## Running commands on workers

<Callout type="info">
Worker placement, the finite command queue and worker-copy retirement are in
development on the 0.3 line. They still require integrated package and live
validation; this is not a stable or preview availability claim. New-machine
acquisition, cold wake and foreign-requester source preparation are separate
integration work, not available fallbacks.
</Callout>

The development flow selects a destination for a finite Project command from
existing eligible worker copies. The source declaration determines the requested
command and resource demand. An accepted command enters that machine's first-in,
first-out queue; acceptance does not mean it has started. When capacity is
available, its reservation covers copying current source files, reviewing the
destination's definitions and setup, and running the command. Setup approval and
successful setup are separate facts. Passive inspection does not evaluate native
setup; readiness stays unknown when the captured files and references cannot decide it.

Inspect the same retained operation to distinguish queued, copying, setup and
running, and to read or copy its output. Canceling a queued command can prevent
launch. Once preparation or execution has begun, an uncertain Stop keeps custody
and capacity occupied until cleanup is confirmed; inspect or explicitly Stop that
occurrence rather than submitting another Run. Long-lived Services are separate
from this finite command queue. A Service without a declared port may have an
observed HTTP address, but no address is invented when listeners are ambiguous.

Before retiring a worker copy, dispose of the actual work that depends on it;
retirement reports queued commands, preparation, processes, Services or Sync
dependencies rather than silently canceling them. Leaving the files and removing
them are separate choices. If the relationship was retired but file removal is
uncertain, inspect the current relationship and copy before trying again. An
uncertain result is not proof that the files were removed or that retirement was
rolled back. Service placement-save plus Move remains a separate integration
boundary, not an automatic transfer of a running Service.

## Devcontainer child machines

<Callout type="info">
Managed Devcontainer children are in development on the 0.3 line. Integrated
validation and the real Docker journey are still pending; this is not a stable
or preview availability claim.
</Callout>

A Devcontainer child is an ordinary Happier machine running inside a container.
Its files, source control, terminals and sessions use the child's observed user
and workspace folder, which can differ from the Docker host's folder. Selecting
a Devcontainer does not turn host commands into container commands automatically.

Creation reviews the selected configuration's host initialization and child
image, build, Compose, Features, mounts, networking and lifecycle effects before
running them. Rebuild is a separate reviewed operation with an **Ask first**
default. If the reviewed effects change, review them again before continuing.
Configuration inspection does not run initialization or lifecycle hooks.

The Docker host controls Start, Stop and Rebuild. When it is offline, these
operations are unavailable; a running child that is still reachable can continue
using its ordinary Happier connection. There is no offline restart or automatic
controller replacement.

Bind-mounted source has one synchronization writer on the host, while execution
stays on the child. Independent child storage is a separate workspace. Changed
native identity, missing roots or an unavailable bind controller stop preparation
before copying or launching; Happier does not silently create another mirror.

Stop retains source and volumes. Rebuild replaces the container without deleting
bind sources or external volumes and requires fresh enrollment. Session history
and drafts remain; running sessions are not moved to the replacement. An uncertain
native result needs inspection of that same managed resource before retrying.

## Make a workspace available on another machine

<Callout type="info">
Linked workspace creation is development-only on the 0.3 line. It requires matching workspace
operation support and the managed sync component on the participating machines; it is not a
stable or preview availability claim. An unavailable component or unsupported operation asks
for an update instead of falling back to another file-transfer system.
</Callout>

Open the selected workspace's details and choose **Add machine** under **Available on**.
Choose the destination machine and folder, then decide how that copy will be used:

- **Replica** carries source changes to the destination while preserving destination-only files.
- **Exact replica** can remove destination-only files and requires explicit approval for that
  continuing behavior.
- **Editable copy** accepts changes from either endpoint and surfaces differences it cannot
  reconcile for review.

Using an existing folder and creating one from the source are separate choices. Attaching an
existing editable checkout does not silently replace it with the source: its differences are
reconciled through the link. Creating from the source can replace existing destination content,
so Happier first asks for approval when replacement is required. Advanced options control each
link's file selection; different copies can intentionally exclude different files.

You can add several copies around one main workspace. If you start from an already linked
copy, the form identifies that set's main workspace as the source. It does not create a second
link between the two copies. Several editable copies share live work in progress, not an
immutable revision or a file-history archive. Separate Git worktrees remain useful when agents
need to work independently.

Linking does not start a session. Return to **Available on** to inspect status, compare conflicts,
pause a link, or stop syncing while leaving its folders in place. If cancellation or a lost
connection leaves the result uncertain, inspect the relationship before trying again; canceling
does not mean that committed linking or file changes were rolled back. See
[workspace status and conflict resolution](/sessions/session-handoff#living-with-a-synced-workspace).

## Review comments in projects

Projects support the same review-comment drafting model as session repository surfaces.

You can create review comments from:

- **file details** views
- **diff review** views

This is useful when you want to prepare a review-driven prompt before starting a session.

### How review comments are scoped

Review comments are stored per exact workspace scope:

- server
- machine
- root path / worktree path

That means review comments are isolated correctly between:

- the main repository root
- each Git worktree
- the same repo on a different machine

If you switch from one worktree to another, you see that worktree’s review comments, not a merged global bucket.

## Start a new session from project review comments

When the current project checkout has saved review comments, the project details header shows a **new session** action.

Use it when you want to turn your project review notes into a real agent task.

When you open the new-session screen from that project:

- the selected machine is preserved
- the selected directory is the current project root or worktree
- project shortcuts can reuse the newest session setup from that project when **Remember last project session selections** is on
- the new-session screen automatically discovers review comments for that exact path

For the full shortcut model, see [New session shortcuts](/sessions/new-session-shortcuts).

## Review comments in the new-session screen

The new-session screen now uses one unified path-based model.

If the current machine + directory match saved review comments, Happier shows a **Review comments (N)** chip with a small switch.

Important behavior:

- the chip is shown for project-launched flows and generic `/new` flows
- it is **enabled by default** when matching review comments exist
- the switch can be turned off without deleting the saved drafts
- changing the selected directory or machine updates discovery automatically
- if the new path has no review comments, the chip disappears

This avoids two competing systems such as “project-seeded review comments” vs “generic new-session review comments”.

There is only one rule:

- if the current new-session path matches saved review comments, Happier offers them for that path

## What gets sent when review comments are enabled

When you create the session with the review-comments chip enabled:

- Happier creates the session first
- then it sends a follow-up message containing the review comments payload
- any additional initial message text is included in the same follow-up

If the same new-session flow also includes file attachments:

- attachments are uploaded first
- the review-comments follow-up includes the attachment file references too

This keeps the first actionable message coherent: the agent sees the review comments and any related attachments together.
