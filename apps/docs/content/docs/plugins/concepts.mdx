title: Plugin concepts
description: Ownership boundaries used by Happier plugins and agent runtimes.

## Plugin

A plugin is an installable package with a cold manifest and optional executable daemon and client code. It is the unit of trust, projection, host-access review, and executable registration.

## Built-in plugin enablement

In 0.3 development builds, built-in plugins are enabled by default for both
the Account and each Machine. Open a plugin in Plugins to change its Account
and selected Machine switches. Both must be on for the plugin's contributions
to be available on that Machine.

Disabling a plugin keeps its data and credentials. Work already admitted can
finish at its natural boundary; enabling both scopes makes the contributions
available again. If an Agent plugin is disabled, a Session can report
`plugin_disabled` and offer **Manage plugin** so you can re-enable it.

The `plugins.enable` and `plugins.disable` Actions also accept an optional
`scope` of `account` or `machine`. If omitted, the Action applies to the
Machine. Required host-import packages remain part of the distribution even
when their contributions are disabled.

## Manifest

The manifest declares stable projected facts:

- plugin identity and version
- daemon and development entrypoints
- host-access disclosures and requests for independently owned resources
- actions, tools, commands, hooks, settings, UI surfaces, events, MCP descriptors, agents, and managed dependencies
- model Provider contributions, which describe model sources but do not contain configured connections, grants, or credentials
- agent runtime capabilities and surface declarations

Manifest data is validated before executable code runs.

## Catalog, admission, and custody

The host can project cold manifest facts into a catalog without loading daemon
code. A catalog entry makes a contribution discoverable; it does not prove the
contribution is executable or currently serving.

The daemon owns admission. It validates a candidate, requests any required
authority decision, and publishes one process-local occurrence only after those
checks succeed. New invocations use that occurrence. A failed development edit
keeps the previous occurrence serving while the daemon remains alive, rather
than leaving two author-selected implementations active.

Managed npm, archive, and non-development local installs retain immutable
installation generations so an exact installed package remains available.
Bundled first-party code instead belongs to the exact CLI version root or a
pinned runner snapshot. Trusted development and drop-in code stays owned by its
selected source; a daemon restart rebuilds current source and does not promise
historical last-known-good recovery.

## Realms and surfaces

A realm is where code runs, while a surface is where a declared capability is
made available. Daemon code runs from the daemon entrypoint; React Native code
runs as trusted code in a supported client realm; declarative UI is rendered
by the host. Packaged hosted web availability is reported per host: a host either names
the one frame adapter it constructed or reports a typed unavailable reason. A declaration can project to several
surfaces without giving one handler more than one lifecycle owner or making
state shared across realms.

## Activation

For ordinary author modules, activation binds executable code through the
named `activate(api)` export generated by `definePlugin(...)`. Daemon
contributions activate in the daemon. A client-target Action names one exact
client artifact/module/export/platform target and uses the same activation ABI
in that invoking client; it does not acquire a fallback daemon registration.
Its `PluginClientApi` registers handlers for the same projected local ids only.
Static registration returns `void`; a code-defined `setup` callback may return
one cleanup function.

Client-target Action activation is part of a Developer Preview contract whose
packaged web/iOS/Android certification remains in progress.
The public package surface has not yet been released for supported use, and no
released build currently provides this capability.

Activation does not receive invocation services. Daemon Action and hook
handlers receive a bounded `PluginInvocationContext`; client Action handlers
receive only their client-safe identity, cancellation, invocation-surface,
current-UI, and bounded UI context. That UI context can open a surface or
invoke another eligible Action through the host's existing dispatcher. A
nullable, host-owned ephemeral scope can also share one plugin-local value
with mounted UI from the same Account and current plugin occurrence; authors
lease values with a versioned local key and release the lease when the
operation ends. Agent session factories receive their own runtime context.

## Invocation context

`PluginInvocationContext` supplies plugin/contribution identity, cancellation, and bounded services such as storage, settings, logging, events, and availability. Services are operation-scoped: activation receives `PluginApi` registration methods, not a general services container.

## Agent runtime

`AgentRuntime` is the executable integration point for a custom AI Agent. It
is supplied as `agents.<id>.factory` to `definePlugin(...)`, whose generated
activation performs the registration. It registers exactly one runtime
factory — either:

- `sessions` for session creation and control, or
- `executionRuns` for execution-run creation and control

plus optional typed Agent capabilities and message adapters. A session-capable
Agent's finite Execution Runs are host-derived from its `sessions` factory; the
runtime never supplies both factories.

A declarative ACP Agent does not have a plugin-owned `AgentRuntime`; the host
opens its declared transport.

## Surfaces

Agent capabilities are the optional operations a native runtime actually
supports. Auxiliary features such as External Sessions keep their own
contribution and lifecycle owner; they are not folded into the primary
`AgentRuntime`.

## Agent leaf

An agent leaf is the plugin-owned code that knows a specific agent CLI, protocol, or runtime behavior. It maps native commands, events, permissions, transcripts, and auth into Happier contracts. Model providers are a separate domain.

## Model Provider contribution

A model Provider contribution is immutable plugin-authored metadata for a model source: endpoints, protocols, credential requirements, catalog facts, compatibility evidence, and optional bounded local discovery. A Provider connection is separate account-owned configuration. It holds the selected contribution or custom template, endpoint overrides, and identity used by grants and structured model selections. Plugins never store connection state or secret values in the contribution.

Model Provider authoring imports its public contracts from
`@happier-dev/plugin-sdk/providers`. Bundled Providers and in-app custom
Provider connections are separate product capabilities. An ordinary Provider
is descriptor-only. A Provider that declares the optional cold
`managedRuntime` facet supplies one matching `providers.<id>.runtime`; generated
activation performs that registration, while supervised child lifecycle remains
host-owned through the managed-services contract.

## Runtime host

The runtime host is Happier-owned code that resolves Agents, constructs bounded
invocation and Agent contexts, creates session runtimes, executes session
loops, handles execution-runs, publishes runtime identity, routes permissions,
and projects transcript/state changes.
