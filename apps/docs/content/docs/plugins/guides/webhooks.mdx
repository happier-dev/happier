---
title: Webhook ingress
description: Declare verified webhook ingress and exercise the admitted Action contract without owning endpoint lifecycle.
---

Use `webhooks` for a verified external delivery routed by the host to one
declared Action. The installed SDK's `capability-matrix.json` is the
availability authority; this guide is the task-oriented workflow for the
available webhook family. “Available” here means the current source author
contract, not public package or release availability.

## Declare the verifier and handler Action together

The declaration names a host-supported verifier and the exact plugin-local
`handlerAction`. The host owns the endpoint, secrets, and queue: a plugin does
not bind an HTTP listener, store a signing secret, mint an endpoint URL, or
create another delivery queue.

A bundled, development, or drop-in plugin needs no published release for its
webhooks to be current: the daemon running it claims the plugin's declaration
for the Account, as described in
[Account Collections](/plugins/guides/account-collections#where-the-current-writer-comes-from).

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';
import {
  decodePluginWebhookActionRawBody,
  PluginWebhookActionInputSchema,
  PluginWebhookActionResultSchema,
} from '@happier-dev/plugin-sdk/webhooks';

export const { manifest, activate } = definePlugin({
  id: 'com.example.github-events',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    'receive-github': {
      title: 'Receive GitHub event',
      surfaces: ['plugin'],
      execution: { target: 'daemon' },
      async run(rawInput) {
        const input = PluginWebhookActionInputSchema.parse(rawInput);
        const rawBody = decodePluginWebhookActionRawBody(input);

        // Parse only the verified, admitted raw body for this contribution.
        void rawBody;
        return PluginWebhookActionResultSchema.parse({
          kind: 'settled',
          disposition: 'accepted',
        });
      },
    },
  },
  webhooks: {
    'github-events': {
      title: 'GitHub events',
      verifier: {
        kind: 'github_hmac_sha256_v1',
        routing: 'accountEndpoint',
      },
      handlerAction: { localId: 'receive-github' },
    },
  },
});
```

Decode the raw body only after `PluginWebhookActionInputSchema` admits the
input. The verifier has already authenticated the delivery; the Action should
perform plugin-domain parsing and return the bounded result shape. Do not
repeat signature verification, persist a second delivery record, or retry by
calling the endpoint yourself.

## Durable push and redelivery

Webhook ingress is the host-owned verified delivery boundary, not an Automation
Event durability boundary by itself. Durable push is a Developer Preview
transport with a best-effort window. The provider receives `202 Accepted` only
after the server durably commits the verified delivery. From that point,
queueing, deduplication, retry, and Automation occurrence idempotency are
durable; a daemon outage or handling failure is retried and can eventually move
the delivery to the dead-letter queue. Before that commit — for example, when
verification, admission, or the durable commit fails — Happier holds no custody
of the delivery. Design the provider side so such an attempt can be recovered
through an independently requested provider redelivery or the next checkpointed
pull, and keep checkpointed pull as the authoritative transport whenever
completeness matters.

The Happier server reads each bounded raw webhook body in process memory before
it can verify the provider signature and seal the admitted content. This is also
true for E2EE Accounts: E2EE protects the durable payload after sealing, not the
provider-to-server request in transit. Unverified bodies are not persisted.

For GitHub, redelivery is never automatic: it happens only when you or a
provider operator requests one, and only to the unchanged endpoint URL. A
redelivered attempt can present the same provider event again under a new
attempt id. Parse the delivery into a stable domain occurrence id, such as
repository + event type + provider delivery id or the provider's own immutable
object/update id, and feed that id to the Automation Event admission helper.
Never use the webhook attempt number or a local receipt as the Automation
dedupe key. Advance your provider cursor only after the Event helper returns a
checkpoint-safe result.

## Test the public boundary

Use `definePluginWebhookTestFixture` to construct the same schema-checked
input/result contract consumed by webhook dispatch. It is a fixture helper, not
endpoint setup.

```ts
import { definePluginWebhookTestFixture } from '@happier-dev/plugin-sdk/webhooks';

const fixture = definePluginWebhookTestFixture({
  webhookEndpointId: 'wh_ep_AAAAAAAAAAAAAAAAAAAAAA',
  input: {
    v: 1,
    endpoint: {
      webhookContribution: {
        pluginId: 'com.example.github-events',
        localId: 'github-events',
      },
      sourceInstanceId: 'github:primary',
    },
    delivery: {
      deliveryId: 'delivery-1',
      attempt: 1,
      replay: 0,
      receivedAtMs: 1,
      providerDeliveryId: 'provider-delivery-1',
    },
    request: {
      contentType: 'application/json',
      headers: [{ name: 'x-github-event', value: 'issues' }],
      rawBodyBytes: 2,
      rawBodyBase64: 'e30=',
    },
    verified: {
      verifier: 'github_hmac_sha256_v1',
      eventType: 'issues',
    },
  },
  result: { kind: 'settled', disposition: 'accepted' },
});
```

Pass the fixture's `input` to the Action's public boundary and assert its
settled, retry, or dead-letter result. That proves the plugin's parser without
manufacturing endpoint, secret, queue, or host admission authority in a test.

## Shared-installation routing

The generic `providerInstallation` routing seam stays supported: verified
GitHub bodies are parsed for their installation id only after signature
verification, and the route resolves the exact installation-bound endpoint
with durable handoff and idempotency. Production setup of a shared GitHub App
remains deferred in Preview, so there is no current shared-App setup workflow
to configure here.
