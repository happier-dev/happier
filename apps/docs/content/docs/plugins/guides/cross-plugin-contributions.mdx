---
title: Cross-plugin contributions
description: Bind feature-owned descriptors, Actions, and embedded surfaces through one contribution protocol.
---

A **cross-plugin contribution protocol** lets one plugin declare bounded
descriptor, operation, and embedded-surface roles, then lets another plugin
bind its existing Actions and renderers to those roles. The host owns discovery,
admission, currentness, and execution. A
contributor does not self-register with the target, and the target does not scan Actions
or build a second Action map.

Use a feature-owned protocol value in ordinary plugin code. Only a package that
defines a reusable feature protocol imports the generic constructors.

The feature protocol is its own versioned package dependency; it is not hidden
inside `@happier-dev/plugin-sdk`. Use the exact package and `/v1` entrypoint the
target feature documents, then verify that `pluginContributionPoints` and
`targetedPluginContributions` are **Available** in the installed SDK's
`capability-matrix.json`. Do not guess a package name from a feature label or
copy its declarations into your plugin. The maintained repository
[`operation-only-channel-provider`](https://github.com/happier-dev/happier/tree/v0.3/packages/plugin-sdk/examples/operation-only-channel-provider)
package is the beginner Channels provider reference, and the repository
[`action-contract-producer`](https://github.com/happier-dev/happier/tree/v0.3/packages/plugin-sdk/examples/action-contract-producer)
and
[`action-contract-consumer`](https://github.com/happier-dev/happier/tree/v0.3/packages/plugin-sdk/examples/action-contract-consumer)
pair shows package discovery, target observation, and contributor binding from
public entrypoints. These examples are maintained source code, not installed
or published packages: a loaded development stack validates them, and any
published copy inside a released SDK is release-owned, not the maintained
source.

## Everyday target and contributor authors

### Managed database targets in 0.3 development source

Use a `deploymentTargets` contribution with `role: 'data'` and a
`dataV1.database` declaration for a database already linked to a Deployment
Environment. The declaration pairs the engine ID with a
`DeploymentTargetDatabaseRuntimeV1` from `@happier-dev/plugin-sdk`.
`listTargets` discovers databases under the admitted link. `open` receives the
selected database, placement, and authorized read or write class, and returns
the descriptor and a connection with `execute` and `close` methods.

Use the invocation context's admitted credential services for that selection.
For a direct write connection, read the deployment's bound `write` data role
through `context.services.secrets.readDataRole` and use the daemon database
engine service when it is available. Read access can use a restricted provider
endpoint or the bound read-only login. Adapters that support setting up a direct
read-only login can implement `readRoleEndpoint` to return the selected provider
endpoint without credentials. Keep connection URLs and provider credentials out
of descriptors and Action results.

A managed adapter can return a descriptor during discovery and open a native
connection only for the exact selected database. In this example,
`listProviderDatabases` and `readProviderConnectionString` are functions your
provider implements using the admitted preparation and invocation context.

```ts
import { PluginError, type DeploymentTargetDatabaseRuntimeV1 } from '@happier-dev/plugin-sdk';
import {
  DatabaseDescriptorV1Schema,
  DatabaseTargetsListResultV1Schema,
  type DatabaseDescriptorV1,
  type DatabaseManagedDeploymentTargetV1,
} from '@happier-dev/plugin-sdk/database';

function describe(
  target: DatabaseManagedDeploymentTargetV1,
  placement: DatabaseDescriptorV1['placement'],
) {
  return DatabaseDescriptorV1Schema.parse({
    target,
    label: target.database,
    engine: 'postgresql',
    origin: { label: 'Acme database' },
    placement,
    capabilities: [{ operation: 'statement.run', available: true }],
  });
}

const runtime: DeploymentTargetDatabaseRuntimeV1 = {
  async listTargets({ preparation, target, placement }, context) {
    const databases = await listProviderDatabases(preparation, context);
    return DatabaseTargetsListResultV1Schema.parse({
      targets: databases.map(database => describe({ ...target, database }, placement)),
      completeness: { complete: true },
    });
  },
  async open({ preparation, target, access, placement }, context) {
    const engines = context.services.databaseEngines;
    if (!engines) throw new PluginError({ code: 'plugin_service_unavailable' });
    const descriptor = describe(target, placement);
    const connectionString = await readProviderConnectionString(preparation, target, access, context);
    const connection = await engines.open('postgresql', { connectionString, access, signal: context.signal });
    return { descriptor, connection };
  },
};
```

Set `dataV1.database` to `{ engineId: 'postgresql', runtime }` in your
[data target declaration](/plugins/manifest/contributions#deployment-target-declarations-03-development-source).
The Environment must link that exact contribution and have the provider
custody required by the host. A link to another contribution or Environment
does not select this adapter. The declaration by itself grants no connection or
write access. Use matching 0.3 development components and inspect the installed
[SDK API surface](/plugins/api/surface) before using this preview contribution.

### Database insight source declarations in 0.3 development source

The Workbench discovers enabled sources at its Insight contribution point.
Bind `list` and `detail` to safe Actions in your own plugin. Both Actions
receive the selected database target. Detail also receives the record key
returned by List. Use the full target to look up evidence and scope record keys
to the same target, so a key from one database cannot retrieve a neighbor's
finding. Incomplete or expired evidence should retain its typed failure.

```ts
import {
  DATABASE_INSIGHT_SOURCES_POINT_REF_V1 as point,
  DatabaseInsightSourceDescriptorV1ProtocolSchema,
  DatabaseInsightSourceOperationSchemasV1 as insight,
} from '@happier-dev/plugin-sdk/database';

// Include this entry in definePlugin alongside the two bound Actions and
// the declared finding-changes Resource. IDs below are local to the plugin.
const contributesTo = {
  [point.pluginId]: {
    [point.pointId]: {
      checks: {
        protocol: point.protocol,
        descriptor: DatabaseInsightSourceDescriptorV1ProtocolSchema.parse({
          displayName: 'Acme checks',
          targetKinds: ['managed_deployment'],
          evidenceSchema: {
            type: 'object',
            properties: { records: { type: 'integer', minimum: 0 } },
            required: ['records'],
            additionalProperties: false,
          },
          changeResourceRef: { pluginId: 'acme.database-checks', localId: 'finding-changes' },
        }),
        operations: { list: 'findings-list', detail: 'findings-detail' },
      },
    },
  },
} as const;

const listInput = insight.listInput;
const detailInput = insight.detailInput;
```

Use `listInput` and `detailInput` as the corresponding Action input schemas.
Parse the source's result with `insight.listResult` or `insight.detailResult`
before returning it. List returns display summaries and source-local keys.
Detail resolves one key under the same target and supplies evidence for the
Workbench brief. The Resource identifies a source change. Keep findings in the
source's own evidence store and let the finite Actions read them.

Matching 0.3 development builds support the finite Workbench reads. A
`changeResourceRef` declaration alone does not enable signed live updates
across plugins. Check that the target host supports that continuation before
depending on automatic refresh.

### Machine access descriptors in 0.3 development source

The development SDK exports `defineAccessProviderSchemas` and descriptor types
from `@happier-dev/plugin-sdk/access-providers`. Declare non-secret configuration
and purpose-bound credential references in `accessProviders`; use the shared
schema builder for the ordinary plugin Actions named by that descriptor.
Machine Inspect and Configure use the host's installed descriptor selection and
reviewed parent Action. A plugin does not create its own child authorization.

For signed-in Home Relay access, declare the `homeRelay` target and the
`inspect`, `configure` and `disable` roles. The person selects the enrolled
hosting Machine in Home Reach. The host supplies the reviewed route to the
roles. Return `needsAuth` and an HTTPS `authorizationUrl` if the person needs
to approve access with the provider. The initial Relay install uses the built-in
bootstrap catalog before an Account and daemon occurrence exist.

Native membership belongs in the descriptor's finite `membership.join` and
`membership.leave` Machine recipes. Configure runs those programs through the
reviewed root setup interpreter, rather than running a join command as the
daemon user. The join recipe receives a protected root-only credential-file
path; do not put the key in configuration, Action results or review text.
If Inspect receives `membershipIntent`, it can return the selected native
profile ID and non-secret flags in `facts.membership`. Join and leave recipes
can branch on those flags with an `includes` condition on `membership.flags`.

This is an unreleased development contract, not a statement that every built-in
network adapter or the Home setup UI uses it. The maintained
[`access-provider author fixture`](https://github.com/happier-dev/happier/blob/v0.3/packages/plugin-sdk/fixtures/external-targeted-packages/target/src/accessProvider.ts)
demonstrates the public descriptor/schema imports and deliberately returns
`native_adapter_unavailable`; it is not an operational network adapter. Consult
the [generated API surface](/plugins/api/surface) for the installed SDK's exports.

### Email transports in 0.3 development source

The Email Channels plugin owns MIME parsing, sender authentication, thread
identity, content shaping, and reply composition. An email transport supplies
raw RFC 5322 messages and delivery facts through its `transports` point. This
contract is development source; verify that your installed toolchain includes
the Email Channels package before depending on it.

Import `EmailTransportsContributionProtocolV1` from
`@happier-dev/email-transports-protocol/v1`, then contribute to
`happier.channel.email` at `transports` with the same `.contribute()` and
`.bind()` pattern below. Declare each Action using the corresponding operation's
`.declaration`, so its input, result, surfaces, and danger level stay in sync.
The public protocol package exports the operation schemas and inferred types
for handlers; `/testing/v1` supplies declarative conformance assertions.

Every operation receives a selected `credentialRef` and transport-owned `config`.
Credentials belong in Connected Accounts. `listSince` receives the opaque
checkpoint, requested `waitMs`, and batch `limit`; it returns message references
and `checkpointAfterBatch`, or a typed history gap when continuity is lost.
`fetchRaw` returns `mimeBase64` for a reference. It must also accept an RFC
Message-ID reference, including angle brackets, so replies and lazy attachment
fetches can read the same message after a process restart. It searches the
configured mailbox, including sent messages needed for reply context.

`submitRaw` receives `mimeBase64`, the composed `messageId`, and an explicit
SMTP `envelope` (`from` and `to`). Send those bytes and recipients unchanged:
the email owner already composed the headers and resolved the audience through
Channels. Submission returns the existing Channels delivery result; an
ambiguous result must stay ambiguous. `connectionTest` verifies access and
returns the authenticated mailbox address. Optional `findSent` searches by
Message-ID and returns `found` or `notFound`; absence of that operation, or a
missing sent copy, leaves ambiguous delivery for Channels' existing resolution
flow. It never authorizes an automatic resend.

Transport Actions are plugin-only, and `submitRaw` declares `writesRemote`.
Accept only the host-stamped `happier.channel.email` caller. The target selects
an admitted contribution through the existing platform service and executes
the original opaque operation handle; transports need no private registration
or routing API. The first-party IMAP/SMTP transport uses this same contract.

### Issue Watch options in 0.3 development source

A PRs & Issues source can offer Issue Watch setup by declaring `issueWatch` in
its `TriageSourcesContributionProtocolV1` descriptor. Use `publication: 'scan'`
when the source scans a connected account for transitions or `publication:
'commit'` when an Account-data source publishes transitions as it commits them.
Omit `issueWatch` if your source offers neither.

```ts
import {
  createTriageIssueEventSetupInputHintsV1,
  createTriageIssueWatchOptionsV1,
} from '@happier-dev/triage-sources/runtime';

const source = { pluginId: 'example.tracker', localId: 'tracker' };
const issueWatch = { publication: 'scan' } as const;
const options = createTriageIssueWatchOptionsV1(source);
const inputHints = createTriageIssueEventSetupInputHintsV1(source, issueWatch);
```

Use the same `issueWatch` value in the source descriptor and your setup Action.
Register `options.inputTypes` and `options.resources` on your plugin, then set
`inputHints` on the setup Action. The registered options use Triage's Account
Actions to read active instances of the admitted source and configured
investigations for that source. The setup Action resolves the selected instance
before saving the Watch.

### Task kinds and creation places in 0.3 development source

Declare the task kind and what people may set when creating or editing it in
the source descriptor. Declare the source's scope labels and provider-side sort
fields at the same point. Bind `listScopeUnits` to supply the source's available
scopes for selection. Use `initialStatuses` for choices offered on create and
`transitions` for changes to existing tasks. Keep source-native IDs stable.

```ts
import { TriageSourcesContributionProtocolV1 } from '@happier-dev/triage-protocol/v1';

const { operations } = TriageSourcesContributionProtocolV1;
export const sourceContribution = TriageSourcesContributionProtocolV1.contribute({
  descriptor: {
    v: 1, displayName: 'Example Tracker', purpose: 'tracker-api',
    scopeUnit: { singularLabel: 'Project', pluralLabel: 'Projects' },
    sortFields: ['created', 'updated'],
    kinds: [{
      id: 'ticket', workflowSubject: 'issue', displayName: 'Ticket',
      pluralDisplayName: 'Tickets', task: true,
      taskCapabilities: {
        createFields: ['title', 'body', 'projectId'],
        editFields: ['title', 'body'],
        initialStatuses: [{ id: 'open', label: 'Open', state: { presentation: 'active' } }],
        transitions: [{ id: 'done', label: 'Done', state: { presentation: 'resolved' } }],
      },
    }],
  },
  operations: {
    listInstances: operations.listInstances.bind('tracker/list-instances'),
    scan: operations.scan.bind('tracker/scan'),
    get: operations.get.bind('tracker/get'),
    listScopeUnits: operations.listScopeUnits.bind('tracker/list-scope-units'),
    listCreationPlaces: operations.listCreationPlaces.bind('tracker/list-places'),
    create: operations.create.bind('tracker/create-task'),
    edit: operations.edit.bind('tracker/edit-task'),
    transition: operations.transition.bind('tracker/transition-task'),
  },
});
```

Implement the named Actions with the corresponding public operation schemas.
`listCreationPlaces` receives the configured instance, optional search `query`,
and an optional `cursor`. Return a `page` of places with `status: 'complete'`
when the provider read succeeded, and include `nextCursor` while more places
remain. To make a parent selection lead to a more specific place, return a
`childScopeId`. Triage sends that value back as `scopeId` when it reads children.
Return each writable place's `kindId`, creation `fields` and optional opaque
`placeId`. Triage passes the selected operands to the `create` role. Authorize the
actual write in that Action using the current configured instance and place.

### PRs & Issues agent actions in 0.3 development source

A plugin can add an agent action, such as "Investigate this issue", to the action
buttons PRs & Issues shows on an item. Contribute to `happier.triage` at
`agent-actions` with `TriageAgentActionsContributionProtocolV1` from
`@happier-dev/triage-protocol/v1`. The protocol is a declaration only, so pass
`operations: {}`:

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';
import { TriageAgentActionsContributionProtocolV1 } from '@happier-dev/triage-protocol/v1';

export const { manifest, activate } = definePlugin({
  id: 'example.tracker',
  version: '1.0.0',
  entrypoints: { daemon: './dist/index.js' },
  contributesTo: {
    'happier.triage': {
      'agent-actions': {
        'triage-issue': TriageAgentActionsContributionProtocolV1.contribute({
          descriptor: {
            label: 'Investigate this issue',
            appliesTo: ['issue'],
            workspaceMode: 'repository',
            launchMode: 'review',
            instruction: 'Reproduce this issue, label it, and propose the smallest fix.',
          },
          operations: {},
        }),
      },
    },
  },
});
```

`appliesTo` names the item kinds the action is offered on: `issue`,
`pullRequest`, `errorIssue`, `other`, `deploymentReceipt` or
`deploymentEnvironment`. `workspaceMode` is `reference_only` (read the item) or
`repository` (work in the project). `launchMode` is `start` (run in the
background) or `review` (open the prefilled composer first). `instruction` is the
task text the agent receives until the person picks a Prompt Library entry.

The action's id is `<your plugin id>/<local id>`, so it never collides with
another plugin's. It starts through the same flow as the built-in actions, and
agents can list and run it through the same catalog Actions. People edit it in
PRs & Issues settings like any other action. If your plugin is disabled or
removed, an action nobody edited disappears. One someone edited stays theirs and
shows as unavailable until the plugin is back.

### Channels provider bindings

Channels publishes its provider protocol as a feature-owned value. An ordinary
target calls `.point()` on that value:

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';
import {
  ConversationProvidersContributionProtocolV1,
} from '@happier-dev/channels-protocol/v1';

export const targetPlugin = definePlugin({
  id: 'com.example.channels-target',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  contributionPoints: {
    providers: ConversationProvidersContributionProtocolV1.point(),
  },
});

export const { manifest, activate } = targetPlugin;
```

A provider plugin imports that same feature protocol, derives each ordinary
Action's role-owned facts from its immutable `.declaration`, and binds its own
local Action id with `.bind()`:

```ts
import {
  ConversationProvidersContributionProtocolV1,
} from '@happier-dev/channels-protocol/v1';

const connectionTest = ConversationProvidersContributionProtocolV1.operations.connectionTest;
const declaration = connectionTest.declaration;

export const connectionTestAction = {
  inputSchema: declaration.input.schema.jsonSchema,
  resultSchema: declaration.resultSchema.jsonSchema,
  surfaces: declaration.surfaces,
  dangerLevel: declaration.dangerLevel,
};

export const connectionTestBinding = connectionTest.bind('acme/connection-test');
```

`declaration` is frozen authoring evidence. It owns the role's input mode,
result schema, required Action surfaces, and danger level. A role's input mode
is fixed by the feature protocol itself, so code consuming the maintained
protocol value never guards on it — admission rejects a mismatched input
schema instead. For a
`contributorDefined` input, the contributor supplies its own input schema; it
still uses the role's result, surface, and danger facts. Do not copy those
facts into a second table, reach through a raw manifest, or discover a role by
searching Actions.

The contributor then binds every required feature role in one
`.contribute()` value. The local ids remain arbitrary plugin-local Action ids:

```ts
const providers = ConversationProvidersContributionProtocolV1;

const channelProvider = providers.contribute({
  operations: {
    setup: providers.operations.setup.bind('acme/setup'),
    connectionTest: providers.operations.connectionTest.bind('acme/connection-test'),
    messageDeliver: providers.operations.messageDeliver.bind('acme/message-deliver'),
  },
});
```

Place that value under the target plugin id, target point id, and the
contributor's own local contribution id in `contributesTo`. The source author
API is `contributionPoints` plus `contributesTo`; raw `contributes` remains the
host-normalized manifest form and is not author input.

## Feature-protocol authors (advanced)

Only the feature-protocol package owns its protocol schema and generic
constructors. Define one only when a real feature has its own domain
vocabulary, public `/v1` contract, maintained target, and maintained
contributor proof; today Channels Protocol is unpublished prepublication
development at `0.0.0`, not an independently published npm package.
Ordinary plugins consume that feature-owned value instead.

Descriptor, operation, and embedded-surface roles are public authoring
contracts. A feature protocol declares the roles; a target observes only the
admitted snapshot for its own point; and a contributor binds its descriptor,
Actions, and renderer chain through the same protocol value.

```ts
import {
  defineProtocolLiteral,
  defineProtocolObject,
  defineProtocolString,
  defineProtocolUnion,
} from '@happier-dev/plugin-sdk/protocol';
import {
  defineContributionPoint,
  defineContributionProtocol,
} from '@happier-dev/plugin-sdk/contributions';

const inspectResult = defineProtocolObject({
  inspected: defineProtocolUnion([
    defineProtocolLiteral(true),
    defineProtocolLiteral(false),
  ]),
}, { policy: 'closed' });

export const externalReviewersV1 = defineContributionProtocol({
  id: 'external-reviewers',
  version: 1,
  descriptor: defineProtocolObject({
    label: defineProtocolString({ minLength: 1 }),
  }, { policy: 'closed' }),
  operations: {
    inspect: {
      required: true,
      input: { kind: 'contributorDefined' },
      resultSchema: inspectResult,
      action: { surfaces: ['plugin'], dangerLevel: 'safe' },
    },
  },
  surfaces: {
    detail: {
      required: true,
      inputSchema: defineProtocolObject({
        entryId: defineProtocolString({ minLength: 1 }),
      }, { policy: 'closed' }),
      presentation: 'content',
    },
  },
});

export const externalReviewersPointV1 = defineContributionPoint([externalReviewersV1], {
  maxContributionsPerContributor: 1,
});
```

`defineContributionPoint([v1, v2], options?)` is for a target that accepts
multiple compatible protocol epochs. `protocol.point()` is the ordinary
single-protocol shortcut. Neither constructor belongs in an everyday provider
plugin that merely consumes a feature-owned value.

Feature protocol values are strict JSON-shaped contracts, not arbitrary
JavaScript objects. Compose them with the validator-neutral constructors, such
as `defineProtocolObject`, `defineProtocolLiteral`, and
`defineProtocolUnion`, and pass the resulting `ProtocolComposableSchema`
directly to the protocol declaration. Each value owns its executable parser and
its `.jsonSchema` projection; `.jsonSchema` is a plain projection and carries
no hidden inference or second validation owner. SDK data constructors cover
bounded UTF-8 strings, strict ordinary JSON with an owner-declared aggregate
serialized-byte ceiling, and unique JSON arrays. Generic public node, depth,
string, key, array, or object-count quotas are not part of this authoring
surface.

## Target observation and surface rendering

Only a target observes the contributions admitted for its own point. Start an
observation through `context.services.targetedContributions.observeForSelf(...)`,
read its current snapshot, and dispose it when the target no longer needs it.
The returned descriptors, operation handles, and surface handles are already
admitted for that exact target point; do not decode a second manifest view or
derive a competing catalog.

```ts
async function readSelectedSource(context, selectedSource) {
  const observation = context.services.targetedContributions.observeForSelf(
    targetPlugin.contributionPoints.providers,
    { onInvalidated: () => refreshSourceList() },
  );

  try {
    const snapshot = await observation.readCurrent({ signal: context.signal });
    const admitted = snapshot.contributions.find((contribution) => (
      contribution.contributor.pluginId === selectedSource.pluginId
        && contribution.contributor.contributionId === selectedSource.contributionId
    ));
    if (!admitted) return undefined;

    return admitted;
  } finally {
    observation.dispose();
  }
}
```

A point may admit several contributors, so select the one your own domain
chose. Taking the first entry silently binds an unrelated contributor's surface
to your row as soon as a second plugin contributes.

Inside a mounted UI surface the same selection is a pure lookup over the
host-stamped `SurfaceContext` snapshot — no observation lifecycle is involved,
because the host already filtered it to your target and its current occurrence:

```ts
import {
  selectTargetedContributionSurface,
} from '@happier-dev/plugin-sdk/ui';

const surface = selectTargetedContributionSurface(context.targetedContributions, {
  pointId: 'sources',
  protocol: { id: sourcesProtocol.id, version: sourcesProtocol.version },
  contributor: {
    pluginId: selectedSource.pluginId,
    contributionId: selectedSource.contributionId,
  },
  role: 'detail',
});
```

`selectTargetedContribution` and `selectTargetedContributionOperation` are the
contribution and operation-role counterparts. All three return the exact
admitted object, or `undefined` when the current snapshot has no single match.

For a React target, pass that exact handle to the public `TargetedSurface`
component. The component delegates to the existing host surface owner; it does
not create a target-local renderer, lifecycle, or currentness path.

```tsx
import { TargetedSurface, Text } from '@happier-dev/plugin-ui';
import type { ContributionSurfaceHandle } from '@happier-dev/plugin-sdk/contributions';

type DetailSurface = ContributionSurfaceHandle<Readonly<{ entryId: string }>>;

export function SourceDetail({ surface }: Readonly<{ surface: DetailSurface }>) {
  return (
    <TargetedSurface
      surface={surface}
      input={{ entryId: 'issue-42' }}
      instanceKey="issue-42"
      fallback={<Text>Loading source detail</Text>}
    />
  );
}
```

For a declarative target, use the surface role's `.node(...)` helper. Supply the
point and contributor identity from the admitted handle, together with the
role's typed input. The helper creates a symbolic `targetedSurface` node; the
host rematches the current admitted surface when it renders the node.

```ts
function createDetailNode(detailSurface) {
  if (!detailSurface) return undefined;

  return externalReviewersV1.surfaces.detail.node({
    pointId: detailSurface.point.pointId,
    contributor: {
      pluginId: detailSurface.contributor.pluginId,
      contributionId: detailSurface.contributor.contributionId,
    },
    input: { entryId: 'issue-42' },
    instanceKey: 'issue-42',
    fallback: { kind: 'state', state: 'loading', title: 'Loading source detail' },
  });
}
```

The absence guards are part of the contract. A contributor can be disabled,
replaced, or withdrawn between snapshots; do not assert that a selected
contribution or surface exists, reconstruct a handle from ids, or keep an old
handle as a fallback.

## Trust and ownership

For private notice evidence and its investigation handoff, see
[private host-health evidence](/plugins/services/notifications#private-host-health-evidence).

Cross-plugin protocol schemas, bounds, role typing, and exact-occurrence
currentness make interoperability deterministic. They do not sandbox a plugin
or make a child semantically read-only. Daemon and React Native code remain
trusted package code under the one concise install and authority decision;
review the package and its dependencies before enabling it. See the
[trust model](/plugins/security/trust-model) for the security boundary.

The host's normalized catalog is the only admission and observation owner.
Targets consume admitted current snapshots; contributors keep their unrelated
Actions usable when a target is absent or incompatible. Do not add a callback
registry, polling loop, Action dispatcher, catalog cache, or compatibility
fallback around this contract.
