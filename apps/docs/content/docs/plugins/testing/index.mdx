After building the plugin, run its source-controlled suite through the normal
CLI command:

```bash
hdev plugins test .
```

The default delegates to the plugin author-test owner and runs
`test/index.test.mjs`. The generated suite imports `dist/index.js`, passes its
exported `manifest` and `activate` through `createPluginTestkit`, and includes an
example invocation of the declared `save-note` Action. The untouched scaffold
therefore has a meaningful passing test. Use that test as the pattern for your
first domain-specific contract before changing plugin behavior.
It does not start a daemon or mutate installed plugin state. Plugin manifests
have no reserved test target; the package's source-controlled test suite owns
which declared contributions it exercises. Use
`hdev plugins dev typecheck .` and `hdev plugins dev build .` for
the other focused checks.

`hdev plugins test . --packed` is reserved for packed, real-host integration.
It packs the project, starts a product-owned authenticated daemon with an
isolated disposable home, completes Install and trust there, verifies the
daemon-owned catalog, and invokes a safe CLI action that accepts `{}` when one
is available. It then restarts the daemon, rejects the stopped incarnation,
verifies that the plugin is still current, and invokes the action again. A
plugin without a suitable action is still installed, activated, and checked
across restart. The disposable home is removed afterward and the user's
installed plugin state is never read or mutated.

To prove a target together with its contributor, test the target and pass the
contributor as a packed prerequisite:

```bash
hdev plugins test ./target --packed --with-plugin ./contributor
```

The target is the test subject. Each `--with-plugin` path or archive is packed,
installed, and admitted in the same disposable daemon before the target is
exercised. When these source packages resolve the SDK from an approved registry,
pass the same registry origin to the test command:

```bash
hdev plugins test ./target --packed --with-plugin ./contributor --sdk-registry <origin>
```

## Plugin testkit

`createPluginTestkit` validates the module's canonical manifest projection,
activates its generated `definePlugin` module through `PluginApi`, enforces
manifest-declared registration ids, invokes registered actions, and disposes
registration plus activation cleanup.

```ts
import { afterEach, expect, test } from 'vitest';
import { createPluginTestkit } from '@happier-dev/plugin-sdk/testing';
import * as module from '../src/index';

let plugin: Awaited<ReturnType<typeof createPluginTestkit>> | undefined;

afterEach(async () => {
  await plugin?.dispose();
  plugin = undefined;
});

test('runs the declared echo action', async () => {
  plugin = await createPluginTestkit({ manifest: module.manifest, module });

  await expect(plugin.invokeAction('echo', { text: 'hello' }))
    .resolves.toEqual({ text: 'hello' });
});
```

Pass explicit `services` or `presentation` fixtures only for real host
boundaries the handler uses. The defaults fail closed instead of silently
faking those boundaries.

## Semantic UI fixture

`createPluginUiTestkit` from `@happier-dev/plugin-sdk/testing` drives the same
public host-API client that an authored surface receives through a supplied
semantic adapter. Use its role/text queries, `press`, context updates, Resource
invalidation, `retire`, and `dispose` operations to test author-visible state,
cancellation, and stale-target handling. Provide handlers only for genuine host
boundaries; a handler may return a typed `PluginError`.

This fixture does not expose a raw React or React Native tree. It does not prove
layout, styling, native reconciliation, CSP/origin, platform navigation,
accessibility-runtime behavior, or a packaged artifact. It also does not prove
installed discovery, on-demand activation, generation replacement, machine
routing, trust, installation, or Surface Registry admission. Use the packed
test and the appropriate loaded-host lane for those claims.

### Mount and refusal diagnostics

The normal no-`mount` call returns a `PluginUiTestkit`. A test that has already
received the host's canonical availability fact may instead pass
`mount: { availability }`. `PluginUiTestkitMountAvailability` is that exact
host fact, with an admission state, a nonempty reason, and diagnostics; the
fixture does not calculate destination, platform, policy, renderer, or
hosted-web admission.

For a non-available fact, the result is
`{ kind: 'refused', availability }`: the exact reason and diagnostics are
preserved and the semantic adapter is never mounted. For an available fact, the
result is `{ kind: 'mounted', fixture }`. Test the branch your host supplied;
do not turn a fixture refusal into a second destination resolver or fallback
policy.

## Test layers

- cold manifest validation and no-execute projection
- activation registration and cleanup
- contribution behavior through its public boundary
- Agent runtime session and execution-run behavior
- cancellation, process cleanup, and failure paths
- UI artifact build and packaged file inspection
- install, trust, development, update, and uninstall flows in a real host

The in-process testkit and default CLI test do not prove real-host integration.
Use `hdev plugins test . --packed` for the canonical packed daemon smoke,
then exercise any additional claimed user flows and uninstall behavior on the
relevant supported hosts before distribution.
