`contributes` is the manifest section that declares plugin-owned projected capabilities.

## Common contribution families

| Family | Purpose | Code-defined author field |
| --- | --- | --- |
| `actions` | User, CLI, MCP, and session-agent operations | daemon root: `actions.<id>.run`; client leaf: `activate(api)` → `api.actions.register(...)`. See [Actions, tools, and commands](/plugins/api/actions-tools-commands#invocation-surface-and-execution-target). |
| `hooks` | Host extension points | `hooks.<id>.handler` |
| activation cleanup | Plugin-owned resources from a successful activation | cleanup function returned by `setup` |
| `events` | Plugin-authored event ids and payload schemas | The declaration family and `context.services.events` are available in the current generated matrix. |
| `agents` | AI agent declarations and runtime metadata | custom Agents: `agents.<id>.factory`; declarative ACP: host-owned |
| `providers` | Model-provider declarations, catalogs, connection facts, and an optional cold managed-runtime facet | ordinary Providers are descriptor-only; a managed Provider uses `providers.<id>.runtime` |
| `connectedAccountDescriptors` | A plugin-produced account service and authentication modes | `connectedAccountDescriptors.<id>.runtime` |
| `backgroundServices` | Daemon-occurrence background work | `backgroundServices[].runner` |
| `secretSources` | Live external Saved Secret acquisition, metadata listing and vault storage (0.3 development source) | `secretSources.<id>.declaration` and `.runtime.acquire(input, context)`, with optional `.list` and `.store`; see [Secrets service](/plugins/services/secrets#external-secret-sources-03-development). |
| `projectNativeAdapters` | Native project detection, commands, environments and existing-service lifecycle | `projectNativeAdapters.<id>.runtime`; declare the matching roles. Development `nativeServiceLifecycle` provides inspect, stop and [bounded log reads and watch callbacks](/plugins/guides/background-services#read-bounded-native-logs-in-development), plus optional [discovery, Start/Restart and accounting callbacks](/plugins/guides/background-services#control-an-existing-native-service-in-development). Their Machine consumers are still under integration. |
| `scmHostingProviders` | Remote forge and hosting-service integration | `scmHostingProviders.<id>.runtime` |
| `scmBackends` | Local repository and working-tree integration | `scmBackends.<id>.runtime` |
| `settings` | Typed settings descriptors | `context.services.settings` in invoked handlers |
| `workflows` | Reusable, read-only Workflow definitions shown under From plugins | `workflows.<id>`: `title`, optional `description`, and `definition` |
| `registrySources` | Data-only catalogs shown alongside built-in and personal sources | `registrySources.<id>`: `title`, `format`, `kinds`, and either a remote `url` or app-only `packageContent.path` (0.3 development) |
| `storeKinds` | Plugin-owned Store items, parsing, presentation and acquisition (0.3 development source) | `storeKinds.<id>`: `title`, `viewId` and `operations` referencing declared same-plugin Actions; see [Store item kinds](#store-item-kinds-03-development-source). |
| `backupDestinations` | Declarative restic storage access (0.3 development source) | `backupDestinations.<id>`: closed nonsecret configuration, credential roles, transport/locality facts and qualified `test` / `open` Actions |
| `deploymentTargets` | Runtime and managed-data target declarations (0.3 development metadata only) | `deploymentTargets.<id>`: closed target/link schemas and same-plugin Action/Resource references; executable target integration is not yet available |
| `healthCheckKinds` | Finite check declarations (unreleased 0.3 development source) | `healthCheckKinds.<id>`: recursively closed configuration and a same-plugin read-only daemon Action returning the canonical health result; see [Health check kinds](/plugins/guides/background-services#health-check-kinds-development-source). |
| `machineRecipes` | Typed Machine setup effects (unreleased development contract) | `machineRecipes.<id>`: revision, presentation, closed input schema and checked steps; data only |
| `machineSetupPresets` | Reusable Machine setup content (unreleased development contract) | `machineSetupPresets.<id>`: revision, presentation and the same setup part used by Account/Team Presets; data only |
| `languageServers` | Machine-side language-server declarations | `languageServers.<id>`: static language mapping, declared executable and initialization/configuration data |
| `skills` | Packaged, read-only skills in the Skills library | `skills.<id>`: `directory` |
| `botTemplates` | Packaged cold Bot template releases (0.3 development source) | `botTemplates.<id>`: `path`; no runtime registration. See [Bot templates](#bot-templates-03-development-source). |
| `openableContentViewers` | Declarative matching for host-opened content and its plugin-owned viewer | direct same-plugin `contributes.ui.views` destination |
| MCP servers | Hosted or managed MCP server descriptors | `mcp.servers.<id>.runtime` when dynamic |
| MCP discovery | Runtime MCP discovery | `mcp.discoverySources.<id>.discover` |
| UI | Host-rendered descriptors or React Native surfaces; hosted web availability is reported per host, and an unavailable host reports a typed reason | generated artifact tree where executable UI is declared |
| `managedDependencies` | Host-managed tool/runtime dependencies | declarative descriptor only; the host owns resolution, installation, validation, update, and removal |
| `voiceModelPacks` | Immutable STT/TTS model and voice assets for host-owned engines | none; declarative data only |
| `voiceProviders` | Conversation, STT, and TTS providers with strict settings, catalogs, limits, and credential declarations | `voiceProviders.<id>.runtime` when the declared realm needs one |
| `sessionHeaderActions` | Declarative Session-header actions | manifest action reference |
| `searchProviders` | Declarative universal-Search providers | manifest action reference |

The generated `capability-matrix.json` in a proven published SDK artifact is the
availability authority for that exact artifact. This catalog describes shapes
and author fields; it does not create a second availability list. A `deferred`
row is not supported or advertised for ordinary author use; do not rely on it;
consult its unblock condition.
Runtime demand is derived from the contribution declarations; Manifest V2 has
no separate `uses[]` owner.

In 0.3 development source, annotate an exported Action with
`PluginActionDefinition` from `@happier-dev/plugin-sdk/actions` when it needs a
portable declaration type. This public authoring type includes the declaration
and its execution target's runtime handler. For a specific target, use
`PluginActionDefinition<Extract<PluginActionDeclaration, { execution: { target: 'account' } }>>`;
import `PluginActionDeclaration` from the same entrypoint.

### Shared-save secrets (0.3 development source)

Secret declarations describe custody and Settings presentation; they are not
permission gates for trusted plugin code. Saving a generated value as a shared
Saved Secret does not require a declaration or a `saveShared` opt-in. It uses
the invocation's captured Account custody, separately from any machine-local
secret binding with the same id.

The parent Action must admit the exact selected id, purpose and reviewed
audience. The matching controller host and current Account custody remain
prerequisites; declarations cannot widen that audience or supply another
invocation's authority. See the [Secrets service](/plugins/services/secrets) for
the explicit-id save and registered raw-read examples. This is an unreleased
source contract, not a claim that an installed release supplies the service.

Do not infer availability from this shape catalog. Consult the generated matrix
for each family's source availability, optional maintained consumer evidence,
unblock condition, loaded-platform evidence, and release availability. This keeps
mutable support status in one generated owner rather than duplicating it here.

## Bot templates (0.3 development source)

Package reusable Bots as JSON releases. In `definePlugin(...)`, `botTemplates`
is a keyed record: each key supplies the contribution's local `id`, and its
`path` points to a JSON file relative to the plugin package root. A package can
contribute several templates:

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.bot-templates',
  version: '1.0.0',
  entrypoints: { daemon: './dist/index.js' },
  displayName: 'Research and review Bots',
  botTemplates: {
    researcher: { path: 'templates/researcher.json' },
    reviewer: { path: './templates/reviewer.json' },
  },
});
```

The projected manifest uses `contributes.botTemplates`, an array of `{ id, path }`
descriptors. Paths use portable forward slashes; an optional leading `./` is
accepted, while absolute paths, parent traversal and backslashes are rejected.
Include the referenced JSON files in the package's packed files.

Each file contains a `BotTemplateReleaseV1` value: `v: 1`, a deliberate `version`,
`releasedAtMs`, `changelog`, and portable `content`. Content includes identity,
instructions, selected reusable memory rules, packaged skills, and software,
connected-account and MCP needs. The public
[authoring example](https://github.com/happier-dev/happier/tree/dev/packages/plugin-sdk/examples/public-authoring)
contains `botTemplates.ts` and two complete release files under `templates/`.
Use those files as the starting point; private drafts, source Session addresses
and credentials do not belong in the release.

These are cold descriptors: discovering or previewing a template does not
activate plugin code, and there is no `botTemplates` runtime registration.
The Store's Bots flow selects a contribution and reads its packaged release
through the shared template preview and copy flow. With several contributions,
the person chooses which template to copy. See
[authoring and publishing templates](/plugins/packaging/authoring-cli#publish-a-bot-template)
for the package workflow. This contract describes unreleased 0.3 development
source; check the [availability matrix](/plugins/manifest/availability) for the
SDK artifact you use.

## Store item kinds (0.3 development source)

Add a kind to a plugin that declares its parser and lifecycle Actions and an
app-page view:

```ts
storeKinds: {
  themes: {
    title: 'Themes',
    viewId: 'theme-store',
    operations: {
      list: 'list-themes', read: 'read-theme', installed: 'installed-themes',
      prepare: 'prepare-theme', acquire: 'acquire-theme', manage: 'manage-theme',
    },
  },
},
```

The key becomes `your.plugin/themes`. `viewId` names a view declared by the
same plugin with `container: 'appPage'` and `target: { kind: 'app' }`.
Every operation names a declared Action callable from plugin surfaces. Keep
parsing in those Actions and declare their actual schemas and effects. Reads,
preparation and acquisition use the ordinary Action API and approval policy;
opening Store never means permission to acquire an item.

The renderer reads `context.launchInput.store` using the SDK's
`StoreKindLaunchInputV1` type. It receives `mode` (`browse`, `search`, `listing`
or `installed`), the query or exact item selection when present, current directory
`filters`, and qualified `operations`. Apply those conditions in the view's
ordinary list or installed Action input so machine/project/status conditions
keep their meaning. The common `PluginStoreItemV1` descriptor carries `sourceId`,
`itemId`, `title`, optional `version`, `description`, `installed`, and opaque
JSON `value`; your Action schemas own the item's detailed format. Preserve the
selected version through preparation and acquisition.

Use `createPluginStoreItemHref` from the SDK root to open an item by its stable
`storeKind` reference. Store retains this reference when the plugin is disabled
or missing and offers Manage plugin recovery. The existing surface loader
loads code only when the kind is shown. Views should pause reads when their
presentation becomes inactive and refresh installed status through their
existing data owner after an acquisition or management Action.

This extends Store through existing contributions, views and Actions. It does
not add arbitrary kinds or formats to `registrySources`: those catalogs retain
their existing kind and parser contracts. The maintained external example is
`packages/plugin-sdk/examples/public-authoring/storeKinds.ts`. Check the
generated [availability report](/plugins/manifest/availability) for your SDK and
host; this section describes unreleased 0.3 source.

## Deployment target declarations (0.3 development source)

Declare runtime target metadata through `definePlugin`. For a plugin that already
declares the four referenced Actions, add:

```ts
deploymentTargets: {
  runtime: {
    role: 'runtime', targetKind: 'example-runtime',
    title: 'Example runtime', icon: 'server-outline',
    targetSchema: { type: 'object', properties: {}, additionalProperties: false },
    linkSchema: { type: 'object', properties: {}, additionalProperties: false },
    actions: {
      inspect: 'inspect', link: 'link', deploy: 'deploy', observe: 'observe',
    },
  },
},
```

Record keys become manifest ids. References name declared Actions from the same
plugin. Their input and result schemas must be explicitly and recursively closed;
read roles use safe effects and mutation roles declare their actual effects.
Actions may run on the Account or daemon, except `uploadDeploy`, which requires
daemon placement. Association unlink remains a host operation, not a target role.
An invalid target is withdrawn individually with a contribution diagnostic.
The canonical role input/result contracts are checked at admission: lifecycle
roles must use their exact role schemas; `inspect` and `link` must retain the
preparation coordinates, without fabricating a deployment receipt.

The unreleased Vercel and Cloudflare implementations expose
`happier.deploy.vercel/actions/targets-inspect-v1` and
`happier.deploy.cloudflare/actions/targets-inspect-v1`. Connect and Check again
use the same read-only inspection Action. Their declared input types resolve
dependent choices from a global `target-options` Resource using the partial
draft through [the existing input-options contract](#typed-inputs-in-development);
the platform-link UI remains under integration.

Import those contracts from the SDK root. The values are the same canonical
Protocol schemas used by host admission:

```ts
import {
  DeploymentTargetRoleInputProtocolSchemasV1,
  DeploymentTargetRoleResultV1ProtocolSchema,
  DeploymentTargetPreparationBaseV1ProtocolSchema,
  hasDeploymentTargetPreparationCoordinatesV1,
} from '@happier-dev/plugin-sdk';

const deploySchemas = {
  inputSchema: DeploymentTargetRoleInputProtocolSchemasV1.deploy,
  resultSchema: DeploymentTargetRoleResultV1ProtocolSchema,
};

declare const preparationInput: unknown;
const preparation = DeploymentTargetPreparationBaseV1ProtocolSchema.parse(preparationInput);
const hasCoordinates = hasDeploymentTargetPreparationCoordinatesV1(preparation);
```

The preparation base supports product-specific composition; retain the
coordinate check after composing it. Public role input, result, preparation,
credential-principal and provider-identity types use the same SDK root.

In unreleased 0.3 source, deployment outcomes use the Machine-services
`deployment-failed` and `deployment-succeeded` Events for every target, including
Cloudflare. Runtime target declarations do not name a separate transition Event
or define its payload. Implement the target's finite `observe` Action; the host's
`deployments.receipts.observe` Action dispatches it for pending receipts. The
generic receipt producer owns outcome selection, and the host platform adapter
adds provider-specific details to deployment notices from retained receipts.

For a managed-data target, use `role: 'data'` instead of a runtime `actions` arm:

```ts
deploymentTargets: {
  database: {
    role: 'data', targetKind: 'database',
    title: 'Managed database', icon: 'server-outline',
    targetSchema: { type: 'object', properties: {}, additionalProperties: false },
    linkSchema: { type: 'object', properties: {}, additionalProperties: false },
    dataV1: {
      projects: { list: 'projects/list', listAction: 'projects/list-action' },
      query: { readOnly: 'query/read-only' },
    },
  },
},
```

This example requires a declared dynamic `projects/list` Resource and declared
safe, explicitly read-only `projects/list-action` and `query/read-only` Actions
from the same plugin. The Resource forwards its surface launch input through the
existing `readAction` bridge; its backing Action receives the same qualified
`projects.list` role as a direct invocation.
`dataV1` and each group/leaf are optional: missing means unsupported.
`projects.list`, `projects.provisionOptions`, and `branches.list` reference dynamic
Resources; `projects.provision`, `branches.create`, `branches.delete`, and
`connectionSecret.save` reference mutation Actions. `projects.link` references a
safe read-only Action that inspects exact native identity before the host's link
Action writes the association. `projects.provisionOptionsAction` and
`branches.listAction` supply the other Resource-backed reads. `query.readOnly`
references a safe read-only Action. Data roles have no runtime `actions` arm. These declarations
grant no secret custody or authority to execute a mutation.

This unreleased source contract admits and projects metadata and validates
target-role input/result contracts. It does not yet provide installed target
invocation or platform upload. Native managed-data execution remains a separate integration.
A projected entry grants no filesystem, secret,
or deployment authority. Check the generated
[availability report](/plugins/manifest/availability) for your exact SDK and host.

## Machine setup declarations (unreleased development contract)

These additions target unreleased 0.3 source. Check the generated
[availability report](/plugins/manifest/availability) for the exact SDK and host
you target. An author declaration does not establish native platform support or
completed install/apply support.

Declare both families through `definePlugin`. Local record keys become the
manifest declaration ids. A Preset references a recipe by its exact plugin id,
recipe id and declaration revision; an unavailable revision is refused rather
than replaced with a newer one.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.machine-setup',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  displayName: 'Machine setup author reference',
  machineRecipes: {
    fonts: {
      revision: '1',
      title: 'Fonts',
      icon: 'file',
      software: true,
      inputSchema: {
        type: 'object',
        properties: { identity: {
          type: 'object', properties: { name: { type: 'string', enum: ['fonts-dejavu-core', 'fonts-noto-core'] } },
          required: ['name'], additionalProperties: false,
        } }, required: ['identity'], additionalProperties: false,
      },
      inputHints: { fields: [{
        path: 'identity.name', title: { key: 'fonts.package', fallback: 'Font package' }, widget: 'text', required: true,
      }] },
      steps: [{
        id: 'fonts', kind: 'package', manager: 'apt',
        packages: [{ kind: 'input', path: 'identity' }],
      }],
    },
  },
  machineSetupPresets: {
    'browser-bot': {
      revision: '1',
      title: 'Browser bot tools',
      description: "Fonts for this bot's own browser tools",
      setup: {
        items: [{
          kind: 'softwareRecipe',
          selection: {
            ref: {
              pluginId: 'com.example.machine-setup',
              recipeId: 'fonts', revision: '1',
            },
            inputs: { identity: { name: 'fonts-dejavu-core' } },
          },
        }],
      },
    },
    'ordered-scripts': {
      revision: '1',
      title: 'Ordered script reference',
      description: 'Run browser setup checks in declaration order',
      setup: { scripts: [
        { body: '\r\necho Browser tools ready\r\n', affects: 'none' },
        { body: 'echo Browser setup checked\n', affects: 'none',
          check: { executable: 'test', args: ['-f', '/tmp/browser-setup-ready'], unsatisfiedExitCodes: [1] } },
      ] },
    },
  },
});
```

Both families have no activation demand. The generated `activate` export follows
the ordinary plugin ABI; there is no recipe registration, execution callback or
privileged plugin module. The host validates declarations and references, checks
the selected Machine, reviews exact effects, and owns admission and execution.
Optional `inputHints` describe declared input paths using localized titles and
static choices. They cannot request host option sources, semantic input types or
Connected Account inventories. Omitting hints leaves the closed `inputSchema`
as the input contract.
Set `software: true` on recipes offered as Software. The existing
`action.options.resolve` Action reads `machines.setup.software.available` for
the plan/apply source-item reference field on the explicitly selected Home and
Machine. Listing declarations does not run native package checks; a missing
target or unavailable catalog is not an empty list. Toolchains and language
runtimes retain their existing owner rather than becoming package recipes.

Software choices can include the recipe's optional `icon` token, an admitted
plugin `brand` resource descriptor, catalog `source`, and declaring plugin
`version`. These are presentation facts, not trust or execution authority.
`version` is not the recipe revision or an installed native package version.
Missing brand/source facts remain absent; listing does not load logo bytes.

For selected recipe configuration, pass exact qualified recipe refs in the
same Action's `values`. The optional `machineRecipeDetails` result contains
only those selected software declarations, including their closed
`inputSchema`, static `inputHints` and declared `removeSteps`. Ordinary browsing
does not include these details. An unavailable revision is refused, not replaced
with a newer one. This metadata does not report installed packages or native
support; absent removal steps do not imply an automatic inverse operation.

Supported declaration fields can bind reviewed public input with
`{ kind: 'input', path: 'receiver.username' }`. Paths use the shared dot-separated
Action input-path contract. A referenced value must exist and pass the concrete
field validator; values are not coerced or recursively interpreted. Keep private
keys and secret bytes out of inputs and template variables; secret-backed files
use `secretGrant` references.

Package declarations accept an input reference for the whole `packages` array
or for an individual identity, as in the example. Binding an identity object
lets ordinary text fields write object paths without a consumer-side array
mapper. The host still validates the resulting manager, exact package name,
optional pin and manager-specific fields with the native package contract.
Homebrew identities require their declared formula/cask kind; WinGet source and
scope are optional. Removal uses explicit `removeSteps`, not an inferred inverse.

For the target daemon's actual primary group or username, bind a supported declaration
field such as `group`, or a template variable, with
`{ kind: 'targetFact', fact: 'daemon.primaryGroup' }` or `fact: 'daemon.username'`.
These are the supported target facts in the development contract. The host resolves them from its existing
daemon-identity observation once per Plan request, rather than accepting an identity in
the recipe's public inputs. Missing evidence returns
`machine_recipe_target_fact_unavailable`; no username or group is inferred. The resolved
value is covered by the reviewed effect-plan digest and is replanned at Apply.
Credentials continue to use admitted secret-grant references.

File templates retain their `value`/`variables` shape and render once:

```ts
content: {
  kind: 'template',
  value: 'restrict,command="internal-sftp" {senderKey}\n',
  variables: {
    senderKey: { kind: 'input', path: 'senderPublicKey' },
  },
}
```

The same input-reference shape binds receiver and administrator user fields in
`sshd` candidate-validation and effective-probe contexts. Optional `checks`
contain package or checked-command declarations and never run as mutation steps.
An effect can use ordered guards:

```ts
when: [
  { input: { op: 'truthy', path: 'aptPackages' } },
  { checkId: 'apt-package', status: ['satisfied', 'drifted'] },
]
```

The input arm uses the existing Action predicate grammar. Check guards name a
declared check and a nonempty unique set drawn from `satisfied`, `drifted`,
`packageUnavailable` and `packageManagerUnavailable`. Only an explicit native
package-availability refusal can match `packageUnavailable`; a missing manager
or denied permission cannot select installer fallback.

For ordered package-manager alternatives, a later branch can require a native
missing-manager result from an earlier supplied choice. `ifInput` skips that
check guard when its input predicate is false, so an omitted earlier choice is
neither bound nor probed:

```ts
when: [
  { input: { op: 'truthy', path: 'dnfPackages' } },
  {
    checkId: 'apt-package', status: ['packageManagerUnavailable'],
    ifInput: { op: 'truthy', path: 'aptPackages' },
  },
  { checkId: 'dnf-package', status: ['satisfied', 'drifted'] },
]
```

Both check ids must be declared in `checks`. `packageManagerUnavailable` matches
the native package owner's missing-manager fact; package, pin, permission and
metadata failures cannot impersonate it. Guards run in order and stop at the
first mismatch. Unreached branches neither bind nor probe. These development
declarations do not establish native backend availability or source-list Apply.

Native commands require a read-only idempotency check. Input object schemas are
recursively closed, including nested objects. Optional `removeSteps` declare
exact removal; omission does not authorize an inferred inverse or data deletion.

In the 0.3 development contract, a Linux systemd user manager can retain old
supplementary groups after an account membership change. Check its actual
process credentials rather than only whether its unit is active:

```ts
{
  id: 'refresh-daemon-manager',
  kind: 'command',
  executable: 'systemctl',
  args: ['restart', '--', 'user@1000.service'],
  check: { kind: 'userManagerGroups', username: 'happier' },
}
```

Use the reviewed account's actual UID in the unit name. The check compares the
active manager's UID, primary GID and supplementary groups with the account's
current native membership. Missing or ambiguous process facts refuse Apply.
This requires a host supporting this check; older strict recipe readers reject
it. Restarting the manager can interrupt its sessions, including the requesting
daemon. A lost result is unknown, not permission to replay effects or proof of
effective isolation.

For journal access, a group step can require
`{ kind: 'journalReadGroup', group: { kind: 'input', path: 'journalGroup' } }`
and bind its `name` to that same reviewed input. Use `existingOnly: true` to
require an existing group. The host verifies the actual system-journal GID and
effective ACL route, including directory traversal; a familiar group name or
its existence is insufficient. The bundled `journal-reader` recipe names only
`happier`, never the agent, and discloses access to every system log. Declared
`group` removal with `state: 'absent'` revokes the listed supplementary
memberships without deleting the group or journal data. Changed membership
still requires a supervised daemon restart and effective journal-read proof;
these declarations and prerequisite checks do not establish that live lifecycle.

Bundled setup Presets use the same `MachineSetupV1` setup part as Account/Team
Presets, with ordered setup/software/app intent. They have no creation or
controller fields and need no synthetic managed-Machine record. Saving or
declaring one performs no Machine effects. Arbitrary setup scripts remain a
separately reviewed ordered `setup.scripts` list; each entry has its exact `body`
and optional `affects` and `check`. Execution uses the existing platform shell
under daemon-user admission. Recipes may instead declare a `script` step in
`steps` or `removeSteps` with `shell: 'sh' | 'bash'`, exact `body`, optional
`check: { body, unsatisfiedExitCodes }` and optional `affects`. These literal
bodies and checks appear in the same Plan and digest and run through the existing
administrator interpreter after ordinary approval. A successful check skips
the body; a declared unsatisfied exit runs and verifies it. An unchecked body
runs on every Apply and completes on successful exit. POSIX script steps are
unsupported on Windows. Script checks do not establish removal ownership: the
existing native installation footprint must prove initial absence. This is an
unreleased 0.3 development contract. New `setup.scripts` writes use the
list. Retained single-script records read as a list of one without changing the
stored row. Capturing a Machine's setup copies every script verbatim in source
attachment order, including empty bodies; it does not concatenate scripts.
Bootstrap enrollment remains host orchestration rather than a serialized recipe
language.

The maintained public-authoring example exports `machineSetupAuthoring` with
this declaration. Its installed-author conformance test reads software options
from the installed projection, prepares the exact bundled Preset through
`machines.setup.plan`, and passes that expanded plan to the host interpreter.
It checks a no-op reapply and unavailable-revision refusal. This in-process
proof does not establish the full attached-Preset Apply flow or live native
platform support. Descriptor browsing must not launch native package checks.

## Backup destination declarations (0.3 development source)

A destination describes storage access through the existing manifest catalog.
Declare it with `definePlugin({ backupDestinations: { repository: descriptor } })`;
the host supplies its local id. There is no destination runtime registration:
the plugin declares and registers the referenced Actions through the ordinary
Action ABI.

`BackupDestinationContributionV1` is exported from the SDK root. For example:

```ts
import type { BackupDestinationContributionV1 } from '@happier-dev/plugin-sdk';

const descriptor = {
  id: 'repository',
  title: 'Object storage',
  configSchema: {
    type: 'object',
    properties: { endpoint: { type: 'string' }, bucket: { type: 'string' } },
    required: ['endpoint', 'bucket'],
    additionalProperties: false,
  },
  credentialRoles: [
    { role: 'repositoryPassword' }, { role: 'accessKeyId' }, { role: 'secretAccessKey' },
    { role: 'sessionToken', optional: true },
  ],
  resticTransport: 's3',
  locality: 'unknown',
  actions: {
    test: { pluginId: 'com.example.backups', localId: 'destination/test' },
    open: { pluginId: 'com.example.backups', localId: 'destination/open' },
  },
} as const satisfies BackupDestinationContributionV1;
```

Configuration is nonsecret data; close nested object schemas too. Declare
credential roles rather than embedding values in configuration or schema
defaults. The host's admitted binding/custody owner retains credential access.
In 0.3 development source, each role entry may declare `optional: true`;
omission or `false` means required. S3's session token is optional. This metadata
travels with the same descriptor so setup can label optional credential inputs.
Open uses a qualified contributed Action. Test accepts either a qualified
contributed Action or `{ kind: 'hostAction', actionId: 'deployments.backups.test' }`
for the host's read-only repository probe. The descriptor has no cleanup callback,
backup engine or scheduler.

An authored test Action owns its probe and reports any cleanup failure within
that invocation. In 0.3 development source, declare open as a
read-only Action on the `plugin` surface. Its input is `{ config, credentialRoles }`;
its result uses the SDK root's `BackupDestinationOpenV1ProtocolSchema`:
`{ repository, credentialBindings, s3?: { region?, addressing? } }`.
Binding identities have `purpose: 'backupDestination'`, `configKey: 'destination'`
and a declared role; they contain no credential bytes or executable commands.
The host opens the configured destination through this Action and retains the
exact Environment credential custody. The first-party S3 descriptor selects the
native `deployments.backups.test` Action. Invoke it through the ordinary Action
executor with the exact saved Environment, target, deployment and configuration
revision operands. It reads the repository configuration through the existing
restic 0.19.1 runner and Environment credential bindings. The result reports
`reachable` or `failed`, with a typed remedy and native exit code when available;
credential values and native output are never returned. It takes no backup and
does not establish write access, durability or restore integrity. Other native
transport and backup configuration lifecycles are not supported yet.

Use the read-only `deployments.backups.history` Action with the same exact target
operands to read retained operation facts, including failed attempts, pruned
snapshot ids and the last verification. It does not open the repository. This
history follows the existing operation retention and is not a permanent audit log.

Local repositories declare `locality: 'local'` and remain same-disk/local recovery,
not off-site protection. Other destinations can declare `unknown` or `offHost`;
an off-host claim requires proof from the admitted configuration, never the
transport name alone. Off-host does not promise durability or a verified restore.

Current source projects these declarations through the existing CLI/UI family
and occurrence-currentness paths. Check the generated availability matrix for the
published SDK/host you target; older strict hosts refuse an unsupported family.
Use the existing engine/toolchain compatibility admission for the new family;
do not strip it before passing a manifest to an older parser. Package SemVer and
host protocol compatibility remain separate contracts; see
[Versioning and compatibility](/plugins/packaging/versioning-compat).

The maintained `backupDestinationAuthoring` companion in
`packages/plugin-sdk/examples/public-authoring/index.ts` uses public SDK exports
to declare one external destination and bind its two ordinary Actions. Both
return an example-owned unavailable result, with no storage access, credential
bytes or command output. It proves the authoring shape, not a working native
transport. Its README describes that boundary, and source conformance tests
exercise the declaration and Action binding. The smaller typed
descriptor fixture remains in
`packages/plugin-sdk/fixtures/external-targeted-packages/backup-destination-descriptor.ts`.

## Language servers in development

In **unreleased 0.3 development source**, `definePlugin.languageServers` adds
language intelligence on the Machine where your plugin is installed and enabled.
It is a declaration, with no `api.languageServers.register` call or activation
callback. Happier starts the server on an explicit language request rather than
when someone merely opens a file. Check your SDK artifact's generated
[availability matrix](/plugins/manifest/availability) before targeting a published
host; a source declaration does not establish released support.

This example declares the native TypeScript server for Linux x64. A plugin
supporting other Machines supplies their corresponding pinned assets too.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.typescript-language',
  version: '1.0.0',
  entrypoints: { daemon: './dist/index.js' },
  languageServers: {
    typescript: {
      title: 'TypeScript',
      languageIds: { typescript: 'typescript', tsx: 'typescriptreact' },
      executable: { kind: 'managedDependency', id: 'typescript-native' },
      args: ['--lsp', '--stdio'],
      initializationOptions: {
        userPreferences: { tsserver: { automaticTypeAcquisition: { enabled: false } } },
        disablePushDiagnostics: true,
      },
    },
  },
  managedDependencies: {
    'typescript-native': {
      title: 'TypeScript language server',
      executable: 'tsc',
      platforms: ['linux'],
      architectures: ['x64'],
      sources: [{
        kind: 'pinnedArchive', installId: 'dep.example-typescript-native', version: '7.0.2',
        assetsByPlatform: {
          'linux-x64': {
            archiveUrl: 'https://registry.npmjs.org/@typescript/typescript-linux-x64/-/typescript-linux-x64-7.0.2.tgz',
            sha256: '7ecad6f67377e831856367ab062ef394f21506a611405bf8ac0ff039348637d3',
            executableSubpath: 'package/lib/tsc',
          },
        },
      }],
    },
  },
});
```

`languageIds` maps the app's language name to the server's LSP language id; they
can differ, as `tsx` and `typescriptreact` do here. Optional `filePatterns` add
matching fallbacks. To add a language the app does not recognize, use your own
language key, for example `languageIds: { example: 'example-lsp' }`, alongside
`filePatterns: ['*.example']`. The pattern selects the server and the single
declared LSP id is sent when opening the document. Multiple keys may map to the
same LSP id; a pattern-only match with several distinct ids cannot choose a
language and is unavailable. Avoid mapping `text` to your language, since that
also selects unrelated plain-text files.

Leave `rootMarkers` absent to use the workspace root; declare
markers only when your server needs root selection. `initializationOptions` go
to the server once during initialization. Use optional `settings` for JSON
configuration that the server requests by a dotted section name.

The executable must reference a declared managed dependency or system tool.
Use a checksummed managed archive when your plugin supplies the binary, keeping
any companion files the server requires. A free command string, project-local
binary, resolver callback, environment override and custom timeout are rejected.
Installing a plugin on a different Machine does not supply a server to this
workspace. Disabling or removing it retires its declarations through the normal
plugin lifecycle.

## Typed inputs in development

In **0.3 development authoring**, an Action field can request the existing Saved
Secret picker with `inputType: { hostType: 'savedSecretReference' }` and
`widget: 'select'`. Its selected JSON value is exactly
`{ ref: 'happier:shared-secret:v1:<resource-id>', resourceRevision: <positive-integer> }`.
The picker reads catalog metadata, not secret bodies. Dismissal or a retired
Account cancels selection; personal ids, plaintext and pending `person_selects`
values are not selections. Selecting a reference neither grants access nor
applies a deployment binding: those operations still require their canonical
Action and approval flow. See the SDK's `examples/public-authoring/inputTypes.ts`
for a typed field declaration. This source authoring contract does not certify
the deployment binding journey in a published runtime.

In **0.3 development / Developer Preview authoring**, `inputTypes` declares
reusable primitive or semantic inputs for Action forms, Workflow inputs and
widgets. Each plugin-local descriptor has a `title`, `semantic` identity and
self-contained `valueSchema`; it can reference a declared options Resource and
an existing picker in `ui.renderers`. Fields refer to the type through its
qualified `{ pluginId, localId }` identity. Typed fields may declare static
`options` containing schema-admitted JSON values to narrow the available choices;
options never widen the type schema or its declared Resource choices. If a type
has an options Resource, field choices intersect that Resource and fail closed
while it is unavailable. Neutral widget fields may instead use an explicit
`optionsSourceId`; its resolved choices also narrow the schema and declared
Resource choices. Pickers, mounted values and
headless contributed Action submissions share this validation, including
disabled-choice rejection and comparison before host normalization. Choices are
needed to pick or submit a value, not to show one: a widget that already stores
a value keeps showing it while its choices load or cannot be read, and only
choices that are known and no longer contain it retire it. Workflow
inputs retain their existing exclusion between a type and an explicit source or
enum, and public plugin Action hints still reject arbitrary `optionsSourceId`.
Choice discovery
still requires the admitted consuming descriptor and its existing grants.

In **0.3 development authoring**, a dynamic options Resource receives the
existing `action.options.resolve` request operands in `options.query`: its
`draftInput`, `fieldPath`, search `query` and optional `cursor`. Read the partial
draft to select dependent account, product or project choices; it is input, not
credential authority. Keep credential acquisition in an ordinary declared
read-only Action invoked with `options.readAction`. Headless discovery uses a
`global` Resource, or a `session` Resource when the operation needs a Session;
it does not fabricate a mounted surface.

The Resource may return JSON containing an options array or
`{ options, nextCursor? }`. Each option still passes the input type's value
schema. The host returns `nextCursor` through the same options Action; pass it
as `cursor` to continue. Query-bearing reads have a finite callback lifetime,
are cancelled with their request and do not share or publish the Resource's
ordinary global or Session snapshot. See
[`examples/public-authoring/inputTypes.ts`](https://github.com/happier-dev/happier/blob/dev/packages/plugin-sdk/examples/public-authoring/inputTypes.ts)
for a request-aware options producer.

Fields share one input-hints contract. Keep `title` as a short noun, such as
`Repository`, and optionally declare `prompt: 'Which repository?'` for the
setup question. Widget setup, group Inputs, saved-group Add and shared
Action/Workflow forms show `prompt` when present and otherwise use `title`.
The optional prompt supports the same localization as the title; it changes
presentation only, leaving input values, validation, requiredness and authority
unchanged. Summaries continue to use the noun title. This field is part of the
current 0.3 development authoring contract.

For personal usage in **0.3 development authoring**, a field can instead declare
`inputType: { hostType: 'usageQuery' }`. This is a host semantic reference, not a
plugin contribution or a read grant. The generic picker validates the same query
that headless callers send to `usage.query` in `{ queries: [query] }`. Each query
retains its own resolved period, filters, cost basis and presentation; identical
resolved queries share a keyed snapshot slice. Available accounting remains
readable while other sources are pending. `usage.export` returns only explicitly
selected accounting sections as JSON, CSV or text file bytes. Its `asOfMs` is the
source timestamp, or `null` when freshness is unknown; saving or sharing
those bytes is a separate explicit client operation. See the generated
[host Actions](/plugins/api/host-actions) for the exact Action projection.

Built-in Usage scope inputs share the toolbar's accounting choices, including
standalone Home copies; an empty selection means all. Ordinary Usage widgets
offer one **Group by** choice without changing the query's array-valued breakdown
contract. Previously saved multi-dimension arrays remain selectable, while the
Breakdowns widget explicitly offers several dimensions. Advanced query callers
can still request every supported breakdown dimension.

`connectedAccountOptions: true` is a separate marker for a `select` field, not
an `inputType`. Do not combine it with static options, `optionsSourceId` or
`inputType`. Widget discovery uses `action.options.resolve` with the admitted
widget consumer and returns the viewer's active qualified accounts for the
declared Resource purpose's permitted services. These choices contain references,
not credentials. Personal pins do not require a current purpose selection;
viewer bindings use that existing selection, and shared Boards reject pins.

`definePlugin` projects these descriptors. Register executable Resource and
renderer leaves through their ordinary activation owners; `inputTypes` adds no
new callback registration right. The host admits the consuming field, grants,
current plugin occurrence and referenced Resource before discovery. An input
schema or picker declaration grants neither token access nor execution routing.

Headless callers receive the same schema and admitted options through
`action.options.resolve`. Picker results are checked against the schema and
available choices; cancellation changes nothing, and a replaced occurrence
cannot settle an old picker. A type without an options Resource has no choice
read. Removed types preserve saved values for repair.

In current development source, Action fields, Workflow inputs, widget setup
and native plugin Forms connect admitted picker mounts through the same host
provider and ephemeral-input presenter. Loaded all-consumer validation has not
been completed; source wiring is not a released-runtime support claim. Check
the generated [SDK surface](/plugins/api/surface),
[host Action reference](/plugins/api/host-actions) and
[availability matrix](/plugins/manifest/availability) for your exact SDK artifact.

## Cross-plugin contribution points

A target declares `contributionPoints` with a feature-owned protocol's
`.point()` value. A contributor uses `contributesTo` and that same feature
protocol's `.contribute()` value to bind its existing plugin-local Actions to
the protocol's named roles. The operation's `.bind(localId)` retains the
ordinary qualified Action identity; it does not register a new handler or let
the target search Actions by local id.

An operation's immutable `.declaration` supplies the required input mode,
result schema, Action surfaces, and danger level for its ordinary Action
declaration. Do not duplicate those facts in a feature-owned table or infer
them from a raw manifest. Required roles must be bound; optional roles may be
absent. The host admits compatible current target and contributor occurrences,
so a contributor remains otherwise usable when its target is absent.

Descriptor, operation, and embedded-surface roles are public authoring
contracts. A target reads its exact admitted point with
`context.services.targetedContributions.observeForSelf(...)`; a contributor
binds the declared descriptor, Actions, and renderer chain through the same
feature-owned protocol value. A role does not itself select a renderer, route,
container, `appPage`, or callback registration.

`contributes` is the host-normalized manifest shape. Source authors do not
write it directly: use `contributionPoints` and `contributesTo` so the typed
feature protocol remains the one authoring owner. See
[Cross-plugin contributions](/plugins/guides/cross-plugin-contributions) for
the ordinary target and contributor workflow.

### Email transports in development

The 0.3 development Email plugin owns the targeted `transports` point on

`EmailTransportsContributionProtocolV1` from
`@happier-dev/email-transports-protocol/v1`, binds its own Actions with each
`protocol.operations.<role>.bind(localId)`, and places
`protocol.contribute({ operations })` under
`contributesTo['happier.channel.email'].transports.<contributionId>`.

`listSince`, `fetchRaw`, `submitRaw` and `connectionTest` are required;

protocol outcomes, while the Email core owns MIME parsing, sender trust, content
shaping and the core-selected recipient envelope. Require the host-stamped Email
core caller before I/O and retain operation-handle lifecycle fencing.

protocol access without duplicating email semantics or Channels delivery custody.
See [Email channel](/extending/email-channel#add-an-email-transport) for the
operator-facing boundary and setup. This is a source contract, not a published

## Descriptor-first families

Settings, UI surfaces, managed dependencies, notification categories, agent runtime capabilities, and projected display metadata should be descriptor-first. The manifest describes them; executable code only handles the dynamic behavior the descriptor references.

### Registry sources in development

In **0.3 development / Developer Preview authoring**, `definePlugin` accepts a
`registrySources` record keyed by plugin-local id. Remote declarations supply a
`title`, credential-free HTTPS `url`, `format`, and nonempty, format-compatible
`kinds` array. Git declarations may additionally select `path` and `ref`.
Existing formats remain `git`, `claude-marketplace`, `mcp-registry`,
`acp-registry`, and `happier-catalog`, with their supported `skill`,
`mcpServer`, `agent`, and `plugin` kinds.
The development `app` kind uses `happier-catalog`, `coolify-templates`, or
`dokploy-templates`; the two imported template formats support apps only.

An app catalog can instead ship as inert package data:

```ts
registrySources: {
  apps: {
    title: 'Packaged apps',
    format: 'happier-catalog',
    kinds: ['app'],
    packageContent: { path: 'resources/apps.json' },
  },
},
```

The file contains `{schemaVersion: 1, apps: [{itemId, app}]}`; `app` is the
strict normalized deployment template descriptor. See the maintained
`appRegistrySourceAuthoring` example in the public SDK conformance companion.
The path must stay within the package. This arm has no URL, token, Git ref,
or resolver callback. The host reads through the installed supplier, binds
the plugin version and current occurrence, and records the selected descriptor's
content digest. Listing projects summaries; selection validates the descriptor.
Disabling or removing the supplier withdraws future reads. These are unreleased
0.3 source contracts, not a claim of support in an installed release.

These are descriptors, not executable adapters: there is no activation callback
or registry registration API. The host projects admitted declarations through
the existing lazy contribution catalog and merges them with built-in sources
and the Account's personal `registry-sources` row. Users may disable a supplied
source, but cannot edit or remove its plugin-owned declaration. Removing its
supplier removes the source from discovery.

Do not embed tokens, npm profiles, or credentials in a declaration. Catalog
reads use the canonical registry Actions and fetch-placement owner; declaring
a URL neither grants credential access nor installs the catalog's contents.
See [Registry sources](/extending/registries) and
[Marketplace integration](/plugins/packaging/marketplace) for consumption.

### Library skills in development

In **0.3 development / Developer Preview authoring**, a plugin can package a
skill and declare its directory in the existing `definePlugin(...)` module:

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.my-plugin',
  version: '0.1.0',
  displayName: 'My plugin',
  entrypoints: { daemon: './dist/index.js' },
  skills: {
    'check-project': { directory: './resources/skills/check-project' },
  },
});
```

The directory must stay inside the plugin package and contain `SKILL.md` with
a valid skill name in its frontmatter, for example:

```markdown
---
name: check-project
description: Check the project's local conventions before changing code.
---

Read the project instructions and run its documented checks.
```

Include it and its supporting files in the package's deliberate `files`
inventory; see [Package anatomy](/plugins/manifest/package-anatomy). Happier
reads the skill's name, description, `user-invocable` and
`disable-model-invocation` flags from `SKILL.md` frontmatter. Declare only the
directory here, so the manifest and skill cannot disagree about that metadata.
The cold projection carries the local `id` and `directory`; this family needs
no activation callback or skill registration API.

The library projection marks the skill as plugin-owned and uses the normal
reach rules and Session delivery. Its initial reach is seeded once;
later plugin updates or re-enablement preserve the person's rules. The packaged
content is read-only and follows the plugin's version. The existing
`skills.duplicate` Action creates an editable skill owned by the person.
Disable or uninstall the plugin to
retire its supplied skills; retained rules have no effect while the declaration
is absent. An independent copy remains in the person's library.

These declarations are separate from skills found in an Agent's native plugin
folders. See [Skills](/extending/skills) for the library and Found workflows.
Check the generated [availability matrix](/plugins/manifest/availability) and
[SDK surface](/plugins/api/surface) for your exact SDK artifact; this
development-source contract is not a published-package availability claim or
verification of the Skills UI integration.

### Workflow definitions

In 0.3 development source, `workflows` declares reusable definitions with the
same input and step grammar as the Workflow library. In `definePlugin`, use a
`workflows` record keyed by plugin-local id; each value carries a `title`, an
optional `description`, and a `definition`. The host projects these values into
the cold manifest's `contributes.workflows` array with the local `id` included.
Check your SDK artifact's generated capability matrix before using this family.

Within a contributed definition, a local Action reference such as `post` resolves

unchanged. Happier rejects invalid Workflow graphs before catalog publication;

Happier projects these descriptors into **From plugins** in the Workflow library

## Openable content viewers

`contributes.openableContentViewers` declares a plugin-owned viewer for content
the host can open. Each row has a local `id`, a required `destination`, and one
or more `contentClasses`; it can further narrow matching with normalized
`mimeTypes` and `extensions`.

`destination` is a same-plugin local reference to `contributes.ui.views`. It is

## Search providers

`contributes.searchProviders` declares a provider for the universal Search
surface. Each row is a local `id` and one `action`: a same-plugin Action id.

```jsonc
{
  "searchProviders": [{ "id": "entries", "action": "entries/search-v1" }]
}
```

Everything else comes from that Action, so nothing here is restated. The
referenced Action must be declared by the same plugin as a `safe`, `global`,
`ui`-surface read with no ordinary placement (`placementBindings: []`), and it
must declare the canonical search schemas:

```ts
import {
  PluginSearchQueryV1Schema,
  PluginSearchResultV1Schema,
} from '@happier-dev/plugin-sdk';
```

The Action receives `{ query, limit }` and returns `{ items, truncated }`. Each
item carries a provider-stable `id`, a `title`, an optional `subtitle` and
`icon` token, and one `command` from the ordinary
`executeAction | openSurface` semantic union. `truncated` is required so a
bounded answer is never presented as a complete one.

The host owns everything a provider does not declare: debounce, minimum query
length, empty-query policy (no request is made on an empty query), section
order, row caps, loading, empty and error states, row rendering, focus,
virtualization, and activation. Cancellation reaches the Action handler through
its ordinary `context.signal`, and a disabled, updated, uninstalled, or retired
plugin loses its section before a stale row can be activated.

Results carry no callbacks, URLs, router paths, relevance scores, HTML, preview
metadata, pagination cursors, or React components. Provider order is preserved
exactly as returned; scores from different providers are never compared because
no score crosses the wire.

### `searchProviders` is not `composerReferences`

The two families answer different questions and must not be merged or aliased:

| | `composerReferences` | `searchProviders` |
| --- | --- | --- |
| Question | "what context should this message carry?" | "which entities match what I typed?" |
| Result | reference candidates resolved to model-facing text | host-rendered entity rows |
| Effect of picking one | inserted into the composer draft | opened or executed through its declared command |
| Trigger | a composer trigger character | the universal Search surface |

A plugin that wants both declares both.

## Voice model packs

`contributes.voiceModelPacks` is a versioned declarative asset contract. A V1 row declares a plugin-local id, the daemon and/or native-device execution hosts, the built-in runtime family and ABI it requires, compatible host/platform/architecture facts, immutable file SHA-256 digests and byte counts, provenance, and license metadata. The host combines the local id with the installed plugin id; plugins must not construct filesystem paths or attempt to override built-in/default packs.

Artifact roles are an explicit family-discriminated ABI. `sherpa_zipformer_streaming` and `sherpa_parakeet_offline` require file roles `encoder`, `decoder`, `joiner`, and `tokens`. `sherpa_kokoro_offline` requires file roles `model`, `voices`, and `tokens`, plus a `data` role whose `type` is `directory_prefix`. Each role declares its safe relative path; every listed file must have exactly one role owner, and a directory prefix must own at least one listed child. The host never guesses meaning from filenames or `files[]` order. Unknown/missing/duplicate/overlapping/unowned roles fail before network access. Unsupported families such as Moonshine, VAD, and semantic endpointing are not valid public V1 declarations.

File paths use canonical NFC POSIX-relative spelling and a portable filesystem
subset. The host rejects parent/child file conflicts, case or Unicode aliases,
control characters, NTFS alternate-stream syntax, and reserved device names
before it opens staging or network resources.

The host independently checks installed-plugin trust and source digest, signature/authenticity evidence, enablement and revocation, scoped `network` grants, license acceptance, resource limits, runtime compatibility, redirects/DNS destinations, and downloaded bytes. A manifest cannot grant itself any of those facts. Required and final download origins must remain within the plugin's existing scoped network authority; model-license acceptance is a separate user decision when the declared license requires it.

This family can add data for an inference family already compiled into Happier. It cannot register a voice provider, connection factory, protocol parser, transcript mapper, credential callback, native module, daemon worker, codec, server adapter, UI callback, or executable inference engine. Use the existing generic `contributes.settings` for plugin-local host-rendered settings and the existing documented voice hook ids for lifecycle/transcript observation; there is no `voiceSettings` family.

## Voice providers

`contributes.voiceProviders` is one strict discriminated family for browser or
mobile conversations and daemon speech. Every row has one plugin-local `id`;
the host derives its only qualified identity as `(pluginId, id)`. Catalogs,
settings, credentials, and runtime registration use that identity. Do not add a
nested provider id.

| `kind` | Declaration | Runtime realm and import |
| --- | --- | --- |
| `conversation` | `roles`, client `platforms`, turn `capabilities`, and a required `client` leaf | generated client leaf; `RealtimeVoiceProviderRuntime` from `@happier-dev/plugin-sdk/voice/client` |
| `speech` | STT/TTS `roles`, `platforms`, optional bounded settings/catalogs/limits | daemon leaf; `SpeechProviderRuntime` from `@happier-dev/plugin-sdk/voice/speech` |

Realm-neutral declarations, credential access, and the single
`VoiceProvidersRegistrationApi` transaction live at
`@happier-dev/plugin-sdk/voice`. Runtime and wire types stay on the client or
speech leaf named in the table; authors can derive the union accepted by
`register` as `Parameters<PluginApi['voiceProviders']['register']>[1]`.

### Credentials and readiness

A contribution may declare one `credentials` slot with one effective source:
`none`, one SavedSecret, or one of up to four qualified Connected Account
services. Sources are alternatives, never credentials combined at runtime.
Readiness follows the slot's `requirement`, current non-secret settings, the
selected source, binding, and grant.

`credentials.hostMediated.operations` declares exact bounded provider requests.
Each source maps a supported operation through one `operationProjections` row:
SavedSecret uses `recipientCredential`; Connected Accounts uses
`materializedHttpHeaders`. Provider code receives the already-bound
`credentials.mediated` service for that operation and phase.

Raw materialization is explicit. Each `rawGrants` row names one exact source,
realm, phase, and headers/environment/files request. There are no independent
realm or phase arrays and no implicit combinations. Raw access requires the
current selection/resource grant and explicit credential-disclosure approval;
plugin code can copy returned material, so install and update UI must say so.

This complete SavedSecret example permits one host-mediated mint during
`prepare` and one separately approved raw browser-header projection during
`connection`:

```json
{
  "credentials": {
    "slot": {
      "id": "api_key",
      "purpose": "voice.client-auth",
      "title": "API key"
    },
    "requirement": { "kind": "always" },
    "sources": [
      {
        "kind": "savedSecret",
        "secretKinds": ["apiKey"],
        "operationProjections": [
          {
            "kind": "recipientCredential",
            "operation": "client-auth",
            "phase": "prepare",
            "format": "bearer"
          }
        ],
        "rawGrants": [
          {
            "realm": "web",
            "phase": "connection",
            "request": {
              "kind": "httpHeaders",
              "origin": "https://voice.example.test",
              "headerNames": ["authorization"]
            }
          }
        ]
      }
    ],
    "hostMediated": {
      "operations": [
        {
          "id": "client-auth",
          "purpose": "voice.client-auth",
          "credentialSlotId": "api_key",
          "effect": "read",
          "request": {
            "origin": "https://voice.example.test",
            "pathTemplate": "/v1/session",
            "queryTemplate": [],
            "headerTemplate": [],
            "bodyTemplate": { "kind": "none" },
            "method": "POST",
            "credential": {
              "kind": "httpHeader",
              "name": "authorization",
              "format": "bearer"
            },
            "redirect": "error",
            "maxBodyBytes": 0,
            "contentTypes": []
          },
          "parameters": {
            "schema": {
              "type": "object",
              "properties": {},
              "additionalProperties": false
            },
            "mapping": []
          },
          "response": {
            "maxBytes": 32768,
            "contentTypes": ["application/json"]
          }
        }
      ]
    }
  }
}
```

The host constructs `VoiceCredentialAccess` for the exact `settings`,
`prepare`, `connection`, or `speech` phase. Provider code cannot select an
account, SavedSecret, slot, or qualified contribution. Async materialization is
fenced before and after the source call; a stale result is discarded rather
than retried against a new selection.

### Settings, catalogs, actions, and limits

Voice settings are bounded non-secret text, number, static-select,
catalog-select, switch, or JSON fields. Speech can declare at most one `models`
catalog and one `voices` catalog, each bound to a declared setting field.
Provider limits only tighten the host's input/output limits.

Settings operations that perform provider work use the generic declarative
settings-action contract and the runtime's `settingsActions.execute`. The host
owns confirmation, cancellation, busy state, result validation, and the atomic
patch to that contribution's allowed fields. There is no public provisioning
method or Voice-specific settings writer.

### One code-defined runtime field

Both runtime kinds use the same non-disposable
`voiceProviders.<id>.runtime` author field when their declared realm needs a
runtime. `definePlugin(...)` generates the matching low-level registration. The
local id and runtime kind must match the cold declaration. Missing, duplicate,
extra, wrong-kind, or wrong-realm registrations fail before graph publication.

The public-authoring fixture in
`packages/plugin-sdk/examples/public-authoring/` contains full strict
conversation, raw-credential, STT, and TTS declarations. External, development,
and bundled plugins use the same declaration, registration, credential, and
lifecycle owners.
