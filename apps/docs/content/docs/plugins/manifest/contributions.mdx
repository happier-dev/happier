`contributes` is the manifest section that declares plugin-owned projected capabilities.

## Common contribution families

| Family | Purpose | Code-defined author field |
| --- | --- | --- |
| `actions` | User, CLI, MCP, and session-agent operations | daemon root: `actions.<id>.run`; client leaf: `activate(api)` → `api.actions.register(...)`. See [Actions, tools, and commands](/plugins/api/actions-tools-commands#invocation-surface-and-execution-target). |
| `tools` | Declarative tool-facing wrappers around actions | manifest action reference |
| `commands` | Declarative CLI entries around actions | manifest action reference |
| `hooks` | Host extension points | `hooks.<id>.handler` |
| activation cleanup | Plugin-owned resources from a successful activation | cleanup function returned by `setup` |
| `events` | Plugin-authored event ids and payload schemas | The declaration family and `context.services.events` are available in the current generated matrix. |
| `agents` | AI agent declarations and runtime metadata | custom Agents: `agents.<id>.factory`; declarative ACP: host-owned |
| `providers` | Model-provider declarations, catalogs, connection facts, and an optional cold managed-runtime facet | ordinary Providers are descriptor-only; a managed Provider uses `providers.<id>.runtime` |
| `connectedAccountDescriptors` | A plugin-produced account service and authentication modes | `connectedAccountDescriptors.<id>.runtime` |
| `backgroundServices` | Daemon-occurrence background work | `backgroundServices[].runner` |
| `scmHostingProviders` | Remote forge and hosting-service integration | `scmHostingProviders.<id>.runtime` |
| `scmBackends` | Local repository and working-tree integration | `scmBackends.<id>.runtime` |
| `settings` | Typed settings descriptors | `context.services.settings` in invoked handlers |
| `workflows` | Reusable, read-only Workflow definitions shown under From plugins | `workflows.<id>`: `title`, optional `description`, and `definition` |
| `openableContentViewers` | Declarative matching for host-opened content and its plugin-owned viewer | direct same-plugin `contributes.ui.views` destination |
| MCP servers | Hosted or managed MCP server descriptors | `mcp.servers.<id>.runtime` when dynamic |
| MCP discovery | Runtime MCP discovery | `mcp.discoverySources.<id>.discover` |
| UI | Host-rendered descriptors or React Native surfaces; hosted web availability is reported per host, and an unavailable host reports a typed reason | generated artifact tree where executable UI is declared |
| `managedDependencies` | Host-managed tool/runtime dependencies | declarative descriptor only; the host owns resolution, installation, validation, update, and removal |
| `voiceModelPacks` | Immutable STT/TTS model and voice assets for host-owned engines | none; declarative data only |
| `voiceProviders` | Conversation, STT, and TTS providers with strict settings, catalogs, limits, and credential declarations | `voiceProviders.<id>.runtime` when the declared realm needs one |
| `sessionHeaderActions` | Declarative Session-header actions | manifest action reference |
| `searchProviders` | Declarative universal-Search providers | manifest action reference |

The generated `capability-matrix.json` in a proven published SDK artifact is the
availability authority for that exact artifact. This catalog describes shapes
and author fields; it does not create a second availability list. A `deferred`
row is not supported or advertised for ordinary author use; do not rely on it;
consult its unblock condition.
Runtime demand is derived from the contribution declarations; Manifest V2 has
no separate `uses[]` owner.

Do not infer availability from this shape catalog. Consult the generated matrix
for each family's source availability, optional maintained consumer evidence,
unblock condition, loaded-platform evidence, and release availability. This keeps
mutable support status in one generated owner rather than duplicating it here.

## Entity drag sources and drop targets

In **0.3 development / Developer Preview authoring**, `definePlugin` accepts
`dragSources` and `dropTargets` records keyed by plugin-local id. A source
declares a `title`, a JSON `referenceSchema`, and its client artifact/export
reference and platforms. A target declares a `title`, `acceptedKinds`, an
`actions` allowlist and the same client execution fields. Packing projects
these into the manifest's existing contribution families; activation registers
their handlers with `api.dragSources.register` and `api.dropTargets.register`.

Custom kinds use `plugin:<pluginId>/<sourceId>`. Targets can also accept declared
built-in kinds such as `session` and `repository-file`; Happier supplies their
qualified identity. Kind acceptance and an Action allowlist do not grant
access or bypass approval. The client occurrence owns registration lifetime,
so an undeclared id or retired occurrence cannot register a usable target.

The development `work-board-widget` kind also uses host-built Board/instance
identity. Putting those fields in a custom source's JSON reference does not
turn it into a built-in item: it remains the declared plugin kind.

See [Entity drag and drop](/plugins/ui/react-native#entity-drag-and-drop-development)
for mounting and resolver behavior, and the generated
[SDK availability](/plugins/manifest/availability) for the installed artifact's
support facts. These source contracts are not a published-runtime guarantee.

## Typed inputs in development

In **0.3 development / Developer Preview authoring**, `inputTypes` declares
reusable primitive or semantic inputs for Action forms, Workflow inputs and
widgets. Each plugin-local descriptor has a `title`, `semantic` identity and
self-contained `valueSchema`; it can reference a declared options Resource and
an existing picker in `ui.renderers`. Fields refer to the type through its
qualified `{ pluginId, localId }` identity. The type owns its choices, so do not
also declare field-level static options or a competing options source.

`connectedAccountOptions: true` is a separate marker for a `select` field, not
an `inputType`. Do not combine it with static options, `optionsSourceId` or
`inputType`. Widget discovery uses `action.options.resolve` with the admitted
widget consumer and returns the viewer's active qualified accounts for the
declared Resource purpose's permitted services. These choices contain references,
not credentials. Personal pins do not require a current purpose selection;
viewer bindings use that existing selection, and shared Boards reject pins.

`definePlugin` projects these descriptors. Register executable Resource and
renderer leaves through their ordinary activation owners; `inputTypes` adds no
new callback registration right. The host admits the consuming field, grants,
current plugin occurrence and referenced Resource before discovery. An input
schema or picker declaration grants neither token access nor execution routing.

Headless callers receive the same schema and admitted options through
`action.options.resolve`. Picker results are checked against the schema and
available choices; cancellation changes nothing, and a replaced occurrence
cannot settle an old picker. A type without an options Resource has no choice
read. Removed types preserve saved values for repair.

In current development source, Action fields, Workflow inputs, widget setup
and native plugin Forms connect admitted picker mounts through the same host
provider and ephemeral-input presenter. Loaded all-consumer validation has not
been completed; source wiring is not a released-runtime support claim. Check
the generated [SDK surface](/plugins/api/surface),
[host Action reference](/plugins/api/host-actions) and
[availability matrix](/plugins/manifest/availability) for your exact SDK artifact.

## Cross-plugin contribution points

A target declares `contributionPoints` with a feature-owned protocol's
`.point()` value. A contributor uses `contributesTo` and that same feature
protocol's `.contribute()` value to bind its existing plugin-local Actions to
the protocol's named roles. The operation's `.bind(localId)` retains the
ordinary qualified Action identity; it does not register a new handler or let
the target search Actions by local id.

An operation's immutable `.declaration` supplies the required input mode,
result schema, Action surfaces, and danger level for its ordinary Action
declaration. Do not duplicate those facts in a feature-owned table or infer
them from a raw manifest. Required roles must be bound; optional roles may be
absent. The host admits compatible current target and contributor occurrences,
so a contributor remains otherwise usable when its target is absent.

Descriptor, operation, and embedded-surface roles are public authoring
contracts. A target reads its exact admitted point with
`context.services.targetedContributions.observeForSelf(...)`; a contributor
binds the declared descriptor, Actions, and renderer chain through the same
feature-owned protocol value. A role does not itself select a renderer, route,
container, `appPage`, or callback registration.

`contributes` is the host-normalized manifest shape. Source authors do not
write it directly: use `contributionPoints` and `contributesTo` so the typed
feature protocol remains the one authoring owner. See
[Cross-plugin contributions](/plugins/guides/cross-plugin-contributions) for
the ordinary target and contributor workflow.

## Descriptor-first families

Settings, UI surfaces, managed dependencies, notification categories, agent runtime capabilities, and projected display metadata should be descriptor-first. The manifest describes them; executable code only handles the dynamic behavior the descriptor references.

### Workflow definitions

In 0.3 development source, `workflows` declares reusable definitions with the
same input and step grammar as the Workflow library. In `definePlugin`, use a
`workflows` record keyed by plugin-local id; each value carries a `title`, an
optional `description`, and a `definition`. The host projects these values into
the cold manifest's `contributes.workflows` array with the local `id` included.
Check your SDK artifact's generated capability matrix before using this family.

Within a contributed definition, a local Action reference such as `post` resolves
to that plugin's qualified Action id. Explicit host and qualified Action ids stay
unchanged. Happier rejects invalid Workflow graphs before catalog publication;
an unavailable referenced Action remains in the definition and prevents run
admission rather than being silently removed.

Happier projects these descriptors into **From plugins** in the Workflow library
and start pickers. People can run a plugin workflow or duplicate it into their
library to edit their own copy. Starting keeps the qualified plugin identity and
version with the accepted definition, so updating the plugin does not change an
already admitted Run. A Workflow contribution does not need an executable
registration callback.

## Openable content viewers

`contributes.openableContentViewers` declares a plugin-owned viewer for content
the host can open. Each row has a local `id`, a required `destination`, and one
or more `contentClasses`; it can further narrow matching with normalized
`mimeTypes` and `extensions`.

`destination` is a same-plugin local reference to `contributes.ui.views`. It is
not a renderer, route, placement, or host-projection binding. The referenced
view independently declares its direct V2 `container`, `target`, and `renderer`;
the viewer only associates matching openable content with that existing view.

## Search providers

`contributes.searchProviders` declares a provider for the universal Search
surface. Each row is a local `id` and one `action`: a same-plugin Action id.

```jsonc
{
  "searchProviders": [{ "id": "entries", "action": "entries/search-v1" }]
}
```

Everything else comes from that Action, so nothing here is restated. The
referenced Action must be declared by the same plugin as a `safe`, `global`,
`ui`-surface read with no ordinary placement (`placementBindings: []`), and it
must declare the canonical search schemas:

```ts
import {
  PluginSearchQueryV1Schema,
  PluginSearchResultV1Schema,
} from '@happier-dev/plugin-sdk';
```

The Action receives `{ query, limit }` and returns `{ items, truncated }`. Each
item carries a provider-stable `id`, a `title`, an optional `subtitle` and
`icon` token, and one `command` from the ordinary
`executeAction | openSurface` semantic union. `truncated` is required so a
bounded answer is never presented as a complete one.

The host owns everything a provider does not declare: debounce, minimum query
length, empty-query policy (no request is made on an empty query), section
order, row caps, loading, empty and error states, row rendering, focus,
virtualization, and activation. Cancellation reaches the Action handler through
its ordinary `context.signal`, and a disabled, updated, uninstalled, or retired
plugin loses its section before a stale row can be activated.

Results carry no callbacks, URLs, router paths, relevance scores, HTML, preview
metadata, pagination cursors, or React components. Provider order is preserved
exactly as returned; scores from different providers are never compared because
no score crosses the wire.

### `searchProviders` is not `composerReferences`

The two families answer different questions and must not be merged or aliased:

| | `composerReferences` | `searchProviders` |
| --- | --- | --- |
| Question | "what context should this message carry?" | "which entities match what I typed?" |
| Result | reference candidates resolved to model-facing text | host-rendered entity rows |
| Effect of picking one | inserted into the composer draft | opened or executed through its declared command |
| Trigger | a composer trigger character | the universal Search surface |

A plugin that wants both declares both.

## Handler id matching

`definePlugin` generates the registration methods that bind executable handlers
to manifest-declared ids. Invalid, missing, duplicate, or undeclared ids are
authoring errors. Happier should fail closed rather than silently accepting a
no-op registration for a declared required contribution.

## Dynamic runtime state is not a contribution

Agent-native commands, model lists, active account state, transcript lines, runtime status, and native session ids are runtime state. They flow through the native `AgentRuntime` and host-owned services, not through new static contribution identities.

## Voice model packs

`contributes.voiceModelPacks` is a versioned declarative asset contract. A V1 row declares a plugin-local id, the daemon and/or native-device execution hosts, the built-in runtime family and ABI it requires, compatible host/platform/architecture facts, immutable file SHA-256 digests and byte counts, provenance, and license metadata. The host combines the local id with the installed plugin id; plugins must not construct filesystem paths or attempt to override built-in/default packs.

Artifact roles are an explicit family-discriminated ABI. `sherpa_zipformer_streaming` and `sherpa_parakeet_offline` require file roles `encoder`, `decoder`, `joiner`, and `tokens`. `sherpa_kokoro_offline` requires file roles `model`, `voices`, and `tokens`, plus a `data` role whose `type` is `directory_prefix`. Each role declares its safe relative path; every listed file must have exactly one role owner, and a directory prefix must own at least one listed child. The host never guesses meaning from filenames or `files[]` order. Unknown/missing/duplicate/overlapping/unowned roles fail before network access. Unsupported families such as Moonshine, VAD, and semantic endpointing are not valid public V1 declarations.

File paths use canonical NFC POSIX-relative spelling and a portable filesystem
subset. The host rejects parent/child file conflicts, case or Unicode aliases,
control characters, NTFS alternate-stream syntax, and reserved device names
before it opens staging or network resources.

The host independently checks installed-plugin trust and source digest, signature/authenticity evidence, enablement and revocation, scoped `network` grants, license acceptance, resource limits, runtime compatibility, redirects/DNS destinations, and downloaded bytes. A manifest cannot grant itself any of those facts. Required and final download origins must remain within the plugin's existing scoped network authority; model-license acceptance is a separate user decision when the declared license requires it.

This family can add data for an inference family already compiled into Happier. It cannot register a voice provider, connection factory, protocol parser, transcript mapper, credential callback, native module, daemon worker, codec, server adapter, UI callback, or executable inference engine. Use the existing generic `contributes.settings` for plugin-local host-rendered settings and the existing documented voice hook ids for lifecycle/transcript observation; there is no `voiceSettings` family.

## Voice providers

`contributes.voiceProviders` is one strict discriminated family for browser or
mobile conversations and daemon speech. Every row has one plugin-local `id`;
the host derives its only qualified identity as `(pluginId, id)`. Catalogs,
settings, credentials, and runtime registration use that identity. Do not add a
nested provider id.

| `kind` | Declaration | Runtime realm and import |
| --- | --- | --- |
| `conversation` | `roles`, client `platforms`, turn `capabilities`, and a required `client` leaf | generated client leaf; `RealtimeVoiceProviderRuntime` from `@happier-dev/plugin-sdk/voice/client` |
| `speech` | STT/TTS `roles`, `platforms`, optional bounded settings/catalogs/limits | daemon leaf; `SpeechProviderRuntime` from `@happier-dev/plugin-sdk/voice/speech` |

Realm-neutral declarations, credential access, and the single
`VoiceProvidersRegistrationApi` transaction live at
`@happier-dev/plugin-sdk/voice`. Runtime and wire types stay on the client or
speech leaf named in the table; authors can derive the union accepted by
`register` as `Parameters<PluginApi['voiceProviders']['register']>[1]`.

### Credentials and readiness

A contribution may declare one `credentials` slot with one effective source:
`none`, one SavedSecret, or one of up to four qualified Connected Account
services. Sources are alternatives, never credentials combined at runtime.
Readiness follows the slot's `requirement`, current non-secret settings, the
selected source, binding, and grant.

`credentials.hostMediated.operations` declares exact bounded provider requests.
Each source maps a supported operation through one `operationProjections` row:
SavedSecret uses `recipientCredential`; Connected Accounts uses
`materializedHttpHeaders`. Provider code receives the already-bound
`credentials.mediated` service for that operation and phase.

Raw materialization is explicit. Each `rawGrants` row names one exact source,
realm, phase, and headers/environment/files request. There are no independent
realm or phase arrays and no implicit combinations. Raw access requires the
current selection/resource grant and explicit credential-disclosure approval;
plugin code can copy returned material, so install and update UI must say so.

This complete SavedSecret example permits one host-mediated mint during
`prepare` and one separately approved raw browser-header projection during
`connection`:

```json
{
  "credentials": {
    "slot": {
      "id": "api_key",
      "purpose": "voice.client-auth",
      "title": "API key"
    },
    "requirement": { "kind": "always" },
    "sources": [
      {
        "kind": "savedSecret",
        "secretKinds": ["apiKey"],
        "operationProjections": [
          {
            "kind": "recipientCredential",
            "operation": "client-auth",
            "phase": "prepare",
            "format": "bearer"
          }
        ],
        "rawGrants": [
          {
            "realm": "web",
            "phase": "connection",
            "request": {
              "kind": "httpHeaders",
              "origin": "https://voice.example.test",
              "headerNames": ["authorization"]
            }
          }
        ]
      }
    ],
    "hostMediated": {
      "operations": [
        {
          "id": "client-auth",
          "purpose": "voice.client-auth",
          "credentialSlotId": "api_key",
          "effect": "read",
          "request": {
            "origin": "https://voice.example.test",
            "pathTemplate": "/v1/session",
            "queryTemplate": [],
            "headerTemplate": [],
            "bodyTemplate": { "kind": "none" },
            "method": "POST",
            "credential": {
              "kind": "httpHeader",
              "name": "authorization",
              "format": "bearer"
            },
            "redirect": "error",
            "maxBodyBytes": 0,
            "contentTypes": []
          },
          "parameters": {
            "schema": {
              "type": "object",
              "properties": {},
              "additionalProperties": false
            },
            "mapping": []
          },
          "response": {
            "maxBytes": 32768,
            "contentTypes": ["application/json"]
          }
        }
      ]
    }
  }
}
```

The host constructs `VoiceCredentialAccess` for the exact `settings`,
`prepare`, `connection`, or `speech` phase. Provider code cannot select an
account, SavedSecret, slot, or qualified contribution. Async materialization is
fenced before and after the source call; a stale result is discarded rather
than retried against a new selection.

### Settings, catalogs, actions, and limits

Voice settings are bounded non-secret text, number, static-select,
catalog-select, switch, or JSON fields. Speech can declare at most one `models`
catalog and one `voices` catalog, each bound to a declared setting field.
Provider limits only tighten the host's input/output limits.

Settings operations that perform provider work use the generic declarative
settings-action contract and the runtime's `settingsActions.execute`. The host
owns confirmation, cancellation, busy state, result validation, and the atomic
patch to that contribution's allowed fields. There is no public provisioning
method or Voice-specific settings writer.

### One code-defined runtime field

Both runtime kinds use the same non-disposable
`voiceProviders.<id>.runtime` author field when their declared realm needs a
runtime. `definePlugin(...)` generates the matching low-level registration. The
local id and runtime kind must match the cold declaration. Missing, duplicate,
extra, wrong-kind, or wrong-realm registrations fail before graph publication.

The public-authoring fixture in
`packages/plugin-sdk/examples/public-authoring/` contains full strict
conversation, raw-credential, STT, and TTS declarations. External, development,
and bundled plugins use the same declaration, registration, credential, and
lifecycle owners.
