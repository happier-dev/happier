---
title: Capabilities and host access
description: Distinguish contribution support facts from runtime authority requests.
---

Manifest V2 derives runtime families from `contributes`; it has no top-level `uses` or `declares` lists. Adding an action, hook, Agent, MCP descriptor, or other contribution is sufficient to declare that family.

## Host access

Host integration needs are declared under `hostAccess.required[]` or
`hostAccess.optional[]`. Every request has a stable id, a capability-specific
scope, and a user-readable reason:

```json
{
  "hostAccess": {
    "required": [
      {
        "id": "service-api",
        "capability": "network",
        "reason": "Calls the plugin service API.",
        "scope": {
          "targets": [
            { "kind": "fixedOrigin", "origin": "https://api.example.com" }
          ],
          "methods": ["GET", "POST"]
        }
      }
    ],
    "optional": []
  }
}
```

Current public required HostAccess families are `network`, `network.client`,
`filesystem`, `process`, `environment`, `connectedAccounts`,
`sessions`, `terminal`, `storage.account`, and `mcp`. Their `scope` objects are
capability-specific and strict. Only `connectedAccounts`, `sessions`,
`storage.account`, and `mcp` may be optional.

`terminal` is available only through the host-owned Agent-session terminal lifecycle.
`requestInterceptors` is available to ordinary public authors as a trusted
installation-wide declaration, not a generic `hostAccess` permission. The installer
reviews and displays each declaration's exact origins and methods before the canonical
host policy chain registers it.
`network.intercept` is not a public HostAccess capability; no public `hostAccess`
request is required for a request interceptor. The canonical host policy chain can
deny a matching request or continue it with an in-scope URL, method, or
non-protected-header rewrite; it does not rewrite bodies, inject provider
authentication, or add a second fetch or interception chain.

When the host has attached a Connected Account credential to the request, the
chain may still deny it or rewrite its non-protected headers, but it may not
change the URL or method. That credential is authorized for one exact request,
so a retargeted call would carry the secret to a destination its owner never
approved; the host refuses the rewrite instead.

Credential, identity, cookie, token, signature, and API-key headers require an
explicit closed policy rather than name heuristics. The host always hides and
protects the exact credential-header names it injects for
the current request. It also hides and protects the closed V1 standard set:
`authorization`, `proxy-authorization`, `cookie`, `set-cookie`,
`www-authenticate`, `proxy-authenticate`, `authentication-info`,
`proxy-authentication-info`, `dpop`, `signature`, `signature-input`, `host`,
`origin`, `referer`, `forwarded`, `x-api-key`, `api-key`, `x-auth-token`,
`x-client-ip`, `x-real-ip`, `x-signature`, `x-hub-signature-256`, and headers
whose names begin with `sec-` or `x-forwarded-`. Other caller-supplied headers
are visible and mutable to a matching trusted installation-wide interceptor;
Happier does not infer additional protected headers from words such as “token” or
“identity”.

The Protocol retains `browser`, `clipboard`, and `externalLinks` as internal declarations;
the public SDK rejects them until a named maintained product consumer proves the complete
owner and lifecycle. The publication pipeline records each family's current disposition in
`packages/plugin-sdk/capability-matrix.json`; consult the matrix emitted with the
package rather than treating an internal Protocol declaration as author
availability.

These declarations do not all mean the same thing:

- filesystem, process, environment, and ordinary network rows disclose trusted
  executable behavior and configure cooperative host facilities; they do not
  sandbox equivalent direct Node or native access;
- connected accounts, sessions, Account storage, and MCP resources can be real
  host-owned selectable resources;
- the Agent-session terminal is a user-visible effect and may require present
  intent or an OS authorization at the operation boundary.

Contribution declarations reference a host-access request by its id when the operation needs that authority. For example, an action can declare `"hostAccess": ["service-api"]`.

## Contribution capabilities

Contribution-local capability objects describe what that contribution supports. Agent session and execution-run capabilities, SCM operations, Provider protocols, and UI host methods are support facts—not authority grants.

## Fail-closed behavior

Missing, malformed, or unauthorized access to a mediated facility or host-owned
resource is unavailable. Plugins must not infer authority from the presence of
a contribution, an Agent support flag, or a Provider capability. A denied
cooperative facility is not a claim that trusted code cannot perform an
equivalent direct local operation.

## Good authoring pattern

- Put static identity and support facts under the owning `contributes` family.
- Request only host capabilities with an implemented runtime checkpoint.
- Use `required` only when the plugin cannot work without the capability.
- Keep scopes narrow and reasons concrete.
- Reference host-access ids from contributions that exercise them.
