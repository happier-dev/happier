---
title: Projection and no-execute discovery
description: Happier projects catalogs and UI from manifests before importing executable plugin modules.
---

Happier must be able to inspect a plugin safely before running it. This is the no-execute projection rule.

## Projected without code execution

Happier should project these from manifest/protocol data:

- plugin listing and marketplace preview
- install and trust prompts
- settings forms
- agent settings forms
- action, tool, and command catalogs
- target-owned cross-plugin contribution points and contributor role bindings
- hook declarations
- event declarations and payload schema metadata
- agent catalogs
- agent runtime capabilities and selectable runtime targets
- Agent capability declarations and separately owned auxiliary contributions
- UI surface descriptors
- MCP server and discovery descriptors
- declared UI inputs and the host-generated artifact graph

## Why this matters

No-execute projection lets Happier:

- show install prompts before trusting code
- render settings before daemon activation
- validate manifests deterministically
- build catalogs without filesystem scanning
- reject invalid contribution ids before runtime
- reject invalid executable bindings before they serve requests

## Handler binding happens later

Executable handlers are bound through the Action's declared daemon or exact
client activation target. For a daemon target, an ordinary
`definePlugin({ actions: { ... } })` declaration projects the Action and its
generated root `activate(api)` binds the same local id. For a client target,
the declaration projects no root handler: the exact named client artifact
registers that local id through its own ordinary `activate(api)`. A catalog row
never relocates a missing client handler to the daemon or another client.

Cross-plugin contribution authoring follows the same rule: a feature protocol's
`.point()` and `.contribute()` helpers project the target point and contributor
role bindings as cold data. The host-normalized catalog owns later admission,
currentness, and execution. A target does not scan contributor Actions, and a
contributor does not create a callback registry or another dispatcher.

## Avoid split-brain declarations

Do not declare the same static contribution in both manifest data and a
handwritten activation module. `definePlugin` owns the projected identity and
the generated daemon binding; a declared client artifact may only register the
handler for that already-projected Action. The host-owned low-level ABI exists
only for conformance fixtures.

Likewise, do not handwrite raw `contributes` or copy a role's Action facts into
a second manifest-shaped map. The source author API is `contributionPoints` and
`contributesTo`; an operation's immutable `.declaration` and `.bind(localId)`
keep ordinary Action declarations and their role binding aligned.
