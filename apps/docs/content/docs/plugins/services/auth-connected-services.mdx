---
title: Connected accounts
description: Select and materialize host-managed account credentials.
---

Use `context.services.connectedAccounts` for host-managed account connections. Access is purpose-bound: a plugin declares why one contribution needs an account, and the host/user binds that purpose to one compatible account or account group. Plugins cannot enumerate unrelated accounts or choose a group member.

## Connection tests in development

In unreleased 0.3 source, a Connected Account runtime can implement optional
`testConnection(context, options)`. Use the selected account's read-only
credential context and an authenticated account, usage or model metadata
request. Do not generate inference, refresh credentials or exchange an API key
for another token as part of this test.

Return `status: 'ok' | 'needsReauth' | 'networkUnavailable' | 'unsupported'`,
with an optional secret-free `reason` and `code`. Return `unsupported` with a
plain reason for a credential mode without a characterized safe probe. The host
also returns unsupported when the callback is absent; it does not substitute
`status()` or infer remote success from stored credentials. UI and CLI callers
use the shared `connectedServices.accounts.testConnection` Action.

## Authentication-mode presentation in development

In unreleased 0.3 development source, a manual authentication mode can declare
`apiKey: true` when it accepts an API key. The authentication owner records this
as `accessMode: 'apiKey'` on successful completion. A runtime with an established
subscription or key contract can return `accessMode: 'subscription' | 'apiKey'`
directly; the public account and attempt projections preserve it. Leave the
declaration absent for device sign-in, native imports and other modes whose key
identity is unknown. Credentials and account details use that account metadata,
then an observed subscribed status when the mode is unknown. Stored credential
kind and sign-in provenance do not establish the mode. Observed usage owns plan
labels; an explicit API-key mode does not display a subscription plan.

## Install a service before signing in

In unreleased 0.3 development source, a manual authentication mode can declare
`machineSetup` to offer an existing Machine recipe before its sign-in form.
The Connect sheet collects the recipe's own inputs, reviews the normal Machine
setup Plan and follows its Apply operation. Sign-in appears after that operation
succeeds. People with an existing deployment can go directly to the same form.

The declaration names a recipe by plugin, recipe ID and revision. Optional
`inputPrefill` entries with `source.kind: 'privateNetworkHttps'` use the selected
Machine's observed ready private network and the declared access provider. An
unavailable observation leaves the field empty; the person can supply the URL.
This suggestion does not establish that a service or HTTPS endpoint is ready.

`afterApply` names the containing manual mode and maps recipe input paths through
`configurationFromInputs` to its public configuration fields. Credentials and
secret configuration are excluded from this mapping. Keep passwords in the
authentication form and runtime's existing attempt credential custody, rather
than recipe inputs, scripts or setup output. Account completion and purpose
binding continue through the ordinary connected-account flow.

## Request headers in development

In unreleased 0.3 development source, the public request-auth client returns the
complete header map required by a declared purpose. It supports API-key headers
and Basic authorization as well as Bearer authorization:

```ts
import { createConnectedAccountRequestAuthClient } from '@happier-dev/plugin-sdk/connected-accounts/request-auth';

const client = await createConnectedAccountRequestAuthClient({ capabilityFile });
const material = await client.lookupConnectedAccountRequestAuth({ purpose, signal });
const headers = material.headers;
```

Pass those headers to the declared upstream request. The result also includes
scalar `facts`, optional credential `expiresAt`, and the `credentialContext`
needed by the existing failure-reporting operations. A service runtime can omit
facts; the host supplies an empty map. Only the consuming plugin interprets its
fact keys. Keep these values local to the operation and preserve the returned
credential context when reporting an authentication or quota failure.

## Authorization-code callback in development

In 0.3 development source, an authorization-code Connected Account that declares
no `callbackUrl` uses the Home's Connected Account callback. That is
`https://cloud.happier.dev/oauth/connected-account/callback` for the hosted web
app. A Home that serves its own web app (`HAPPIER_WEBAPP_URL` or a bundled UI)
uses `<web app URL>/oauth/connected-account/callback` instead. Register the
callback of every Home that will use your OAuth app with the upstream service,
and require PKCE:

```ts
import type { PluginConnectedAccountAuthenticationModeV2 } from '@happier-dev/plugin-sdk/connected-accounts';

const oauthMode = {
  id: 'oauth',
  kind: 'oauthAuthorizationCode',
  credentialKind: 'oauth',
  // No callbackUrl: the attempt uses the Home's Connected Account callback.
  scopes: ['example.read'], // Use the upstream service's documented scopes.
  pkce: 'required',
  outcomeReconciliation: 'none',
} satisfies PluginConnectedAccountAuthenticationModeV2;
```

An authentication mode can declare the kind its successful results produce.
Return the observed `credentialKind` on each connected result so it can be saved
with the account. When the result omits the kind, consumers that require a known
kind can ask the user to refresh or reconnect.

The initiating daemon's existing authentication attempt supplies state and the
S256 challenge to the runtime's `begin` method. Its `complete` method receives
the authorization code, callback URL and verifier only after host validation.
Use the callback URL the host passes; the attempt already accepts only its own
callback, so a runtime does not compare it with a fixed address.
Implement exchange, refresh, revocation and identity/granted-scope verification in that
daemon runtime. The callback page never exchanges a code or contacts a vendor.

The page captures the answer once and removes the query before waiting for
authentication or Actions. It forwards only the OAuth response fields to an
opener at the exact callback origin. Without an opener, it reads the exact
attempt on reachable Machines in the signed-in Account and completes through
the existing authentication Action. A state prefix is a routing hint; it grants
no service, account, return-path or credential authority.

When signed out, on another Account, disconnected, or unfinished, the page keeps
the original callback URL available to copy into the initiating connection
screen. A denial never exchanges a code or cancels an attempt guessed from
state. The MCP callback keeps its existing URL and opener message through the
same controller.

This unreleased 0.3 behavior also applies when a callback opens in an already
running app. If the signed-in Account cannot find the exact attempt, the page
offers the original answer for Paste, as it does without a ready signed-in
Account. Opening the callback in a running app does not require restarting it.

This relay does not make any vendor's OAuth integration available. A service
still needs registration, permission and token-lifecycle validation; retain a
manual-token mode wherever that proof is missing.

### Home public OAuth clients

An authorization-code mode can use a public client registered by the Home
operator. Declare the mode on the plugin’s Connected Account service and put
its default OAuth scope tokens in the mode’s `scopes` array. If the scope IDs
depend on registration, ask the operator to supply them in their
[Home setting](/self-hosting/env#public-oauth-clients).
The host resolves the exact plugin ID, service ID and mode ID.
Read the selected client ID and scopes through
`context.configuration.getPublicOAuthClient({ signal })` when the attempt
begins and retain the client in the attempt’s credential store for completion.
The setting works for bundled and external plugins.

### Cloudflare deployment connections in development

In 0.3 development source, Cloudflare manual-token connections verify the
token's actual policies and the selected account before staging credentials.
Workers uses a [user-owned token](https://dash.cloudflare.com/profile/api-tokens):
the [Workers Builds API](https://developers.cloudflare.com/workers/ci-cd/builds/api-reference/)
requires that token type. Pages, Tunnel and DNS also support
[account-owned tokens](https://dash.cloudflare.com/?to=/:account/api-tokens).
One API token method shows a permission checklist for each feature. Choose the
token owner because Cloudflare uses different verification endpoints, and
restrict its permissions to the account ID configured for that connection.

Verification reads token activity, its matching policy record and the provider's
permission catalog. Workers requires script write access and **Workers Builds
Configuration (Edit)** on a user-owned API token for Builds writes.
Pages requires its project/deployment authority. Tunnel and DNS need their own
write permissions; DNS also checks the configured zone and its owning account.
The token needs read access to its policies, and Workers and Pages need account
identity read access. Validation reports the enabled features. An active token,
a read-only grant, another account's permissions or
a matching deny policy cannot complete the connection. Verification makes no
deployment, configuration or token-management writes. Zone routing and DNS
operations require their own exact permissions; connecting does not grant them.

Refresh checks the retained manual token rather than rotating it. Expired or
revoked credentials need a replacement through reconnect; revoke the old token
on its Cloudflare token page. The plugin has read-only token-management access
and reports that remote revocation must be done there. Materialization supplies
only the authorization header for the Cloudflare API origin.

Cloudflare OAuth uses a registered public client, the shared callback and required
S256 PKCE. In 0.3 development source, the Home operator may configure a
public client through [Home configuration](/self-hosting/env#cloudflare-public-oauth-client).
The same Sign in with Cloudflare method accepts your own registered client.
Those fields are optional Advanced configuration when the Home has a client,
and required when it has none. Cloudflare consent chooses authorized accounts;
Happier selects the sole account automatically or offers their names afterward.
Register Account Settings Read and the feature permissions your client offers:
Workers Scripts Write and Workers CI Write, Pages Write, Cloudflare Tunnel Write,
or DNS Write. The
runtime also requests `openid offline_access` for subject identity and refresh.
The [scope catalog](https://developers.cloudflare.com/api/resources/iam/subresources/oauth_scopes/methods/list/)
maps registered IDs to those permission names; it is not a token-grant endpoint.
Only the token response supplies the granted scopes. Identity and grants validate
before temporary attempt custody; exact selected-account access must validate
before the connection can be saved.

OAuth setup does not prove effective write rights. Cloudflare enforces permission
on each operation, which retains the typed missing-permission refusal. A member's
role is never used to infer permission. Expired access cannot be materialized;
the host's existing refresh lifecycle stages a verified replacement. A revoked
refresh grant requires reconnecting. Revocation uses Cloudflare's documented
endpoint, and an uncertain response stays unknown without automatically retrying.
Real consent, refresh and revocation with an authorized registered client remain
release checks; this describes development source, not released availability.


## Declare a purpose

An Agent declares purposes in its contribution:

```json
{
  "id": "example-agent",
  "connectedAccounts": [
    {
      "purpose": "upstream",
      "title": {
        "key": "connectedAccounts.upstream",
        "fallback": "Upstream service"
      },
      "service": {
        "pluginId": "example.accounts",
        "localId": "api"
      },
      "materializationKinds": ["httpHeaders"]
    }
  ]
}
```

`purpose` is a machine identifier, not display text. Give the host an optional
localized `title` for the selection UI; it may be a plain string or a
`{ key, fallback }` value. The host uses that same declaration detail for
built-in and external contributions, so do not derive a user-facing label from
the raw purpose ID.

An action or hook uses the ID of its existing `connectedAccounts` HostAccess
request as the purpose. Do not declare that purpose a second time. The request's
`serviceRefs` are compatible alternatives for one binding.

In unreleased 0.3 development source, `operations` and `materializationKinds`
remain accepted installation-consent metadata. They do not veto service methods
or credential forms at runtime. The host still requires a known purpose, its
compatible service and the exact selected Account or authorized group member.
An invocation pinned to a captured purpose subject cannot change that selection.

## Inspect and select the binding

`getBinding(purpose, options?)` returns a redacted binding summary or `null` when the declared purpose is unbound. A summary contains the local purpose, selected service reference, target kind (`account` or `group`), and a display name. It does not expose internal account/group IDs, scheduler state, revisions, or credentials.

`requestSelection({ purpose, reason }, options?)` opens the host-owned selection flow and returns the resulting binding. A purpose whose request lists several compatible services still selects exactly one service and one account or group. Declare separate purposes when one operation needs multiple services.

Only `requestSelection()` requires an available current-session interaction
owner. If the user cancels, it fails with `plugin_interaction_cancelled`; if no
interaction owner is available, it fails with `plugin_interaction_unavailable`.
An already-bound, currently authorized purpose can still use `getBinding()` and
`watch()` outside a session, and can use `materialize()` there when the selected
binding is authorized. The selection flow never returns the host-private
account inventory to the plugin.

In 0.3 development source, Settings pages can open the same host purpose setup
without a current Session using
`hostApi.openConnectedAccounts({ service, purpose: { consumer, purpose } })`.
The returned `OpenConnectedAccountsResult` is
`{ kind: 'connected' | 'selected', account }` or `{ kind: 'dismissed' }`.
Use the qualified `account` reference to select the result in your draft; it
contains no credentials. Older hosts return `undefined`, so re-read your
account options in that case. Existing callers can keep ignoring the result.
The consumer is the qualified Action or Resource whose installed declaration
owns the purpose. The host validates that declaration in the invoking Account,
or on the exact invoking Machine when one is supplied,
offers compatible accounts and pools, and saves the choice through the existing
approval-controlled `connectedServices.purposes.default.set` Action. Agents use
that Action directly with the qualified `purpose` and an account or group
`target`. Omit `machineId` for Account-origin configuration, which works without
an online Machine; supply it for Machine-origin configuration, which requires
that exact Machine and never falls back to the Account declaration. Creating a
connection alone does not select a purpose.
Triage source authors supply `connectedAccountPurpose` to the shared source
settings factory; setup owns selection.

## List the accounts authorized for a purpose

`listAccounts({ purpose, limit? }, options?)` returns non-secret metadata for
the exact current target of that declared purpose. A direct account binding
lists only that account. A group binding lists only the group's currently
enabled members. Use it when one contribution legitimately reads from several
members of its bound group — for example discovering each organization a user
has connected — not to enumerate arbitrary accounts from the same service.

Each entry carries the exact account reference, a host display name, the
connection `state` (`connected`, `expired`, `reconnectRequired`, or
`unavailable`), and `connectedAccountOrigins`: every host-normalized,
credential-free configured origin that account owns. An account whose
authentication mode declares no configured origin returns an empty array; the
host never selects a preferred origin.

Each entry also carries `connectedAccountBases`: the same configuration seen as
service bases. A base is an origin plus the path segment a deployment lives
beneath — an organization, a collection, or a path-prefixed self-hosted install
— and it is what a source routes requests by. Every base begins with one of that
account's `connectedAccountOrigins`, preserving the configured origin identity.
Declare a base with a `connectedAccountBase`
configuration field; a `connectedAccountOrigin` field keeps meaning exactly
`scheme://host[:port]` and rejects a path.

The result is bounded, not paginated. `status` is `complete` only when the
returned array is the whole authorized set; any elision — the host-clamped
`limit` or a storage cap — reports `status: 'truncated'`. There is no cursor.

```ts
const listed = await context.services.connectedAccounts.listAccounts({
  purpose: 'upstream',
});
const usable = listed.accounts.filter((account) => account.state === 'connected');
```

The listing exposes no credential, configuration value, capability list, group
catalogue, or same-service account outside that target, and it never changes the
selected binding. Re-read it after a `watch()` resync rather than caching it.
This listing and its exact-account counterpart are ratified host-custodied
external-authoring capabilities: any author may consume them for a purpose the
host has authorized, while the host retains custody of the account inventory,
authorization, currentness, and the selected binding.

## Credential materialization

`materialize(purpose, request, options?)` returns a point-in-time credential snapshot in the requested form:

This raw-material service is available in admitted daemon contexts. Account-placed
Actions do not receive `context.services.connectedAccounts`. For Account HTTP,
the development request contract uses `context.services.http.request` with
`credentialBinding: { kind: 'connectedAccountPurpose', purpose: 'upstream',
origin: 'https://api.example.com', method: 'GET', headerNames: ['authorization'] }`.
The binding's required `method` is the issued HTTP method, independent of the
request's actual method. Finite and streaming requests use the same binding.
This requires a host with Account-purpose HTTP composition; the SDK declaration
alone does not establish runtime availability. The host retains the selected
binding and credential bytes, checks the issued origin and method before
injection, and redacts provider echoes. Declare the purpose and network access
on the Action; this request does not select an Account or grant access.

- HTTP headers for a declared HTTPS origin and bounded header names
- environment variables for bounded keys
- files for bounded file ids

```ts
const binding = await context.services.connectedAccounts.getBinding('upstream');
if (!binding) {
  await context.services.connectedAccounts.requestSelection({
    purpose: 'upstream',
    reason: 'Choose the account used for this request',
  });
}

const credential = await context.services.connectedAccounts.materialize(
  'upstream',
  {
    kind: 'httpHeaders',
    origin: 'https://api.example.com',
    headerNames: ['authorization'],
  },
);
```

Materializing an unbound purpose fails with the host's canonical resource-not-selected error. For a group binding, each call resolves the current member; a plugin cannot select a member per request.

`materializeListedAccount({ purpose, account, materialization }, options?)` is
the exact-account counterpart to `listAccounts()`. It takes an account reference
returned by the current listing and returns the same point-in-time credential
forms. The host re-verifies that the account is still authorized for the
declared purpose before and after materialization: it must still be the direct
target or a current enabled member of the bound group. An account from the same
service but outside that scope is rejected. For an `httpHeaders` request, an
account with configured origins requires the requested origin to remain among
its current `connectedAccountOrigins`. The selected service's materialization
adapter owns the credential's recipient contract, including when no configured
origins exist. Manifest network targets do not supply a separate origin grant.
Display text, configuration bytes and credential contents cannot widen that
recipient contract.

`materializeListedAccount()` uses the same purpose and credential-owner admission as
`materialize()`. It is not a selector: it neither reads nor changes the selected
binding, and an account that has left the authorized set fails closed.

The host owns credential storage, refresh, scoping, selection UX, and log redaction. Do not persist returned credentials in plugin storage or emit them in events, diagnostics, artifacts, or messages. The public service has no failure-reporting, refresh, receipt, generation, or scheduler API.

### Machine-native materialization in development

In 0.3 development, a Connected Service may declare
`authentication.native: { systemTool: 'acme-login' }` and implement the optional
`ConnectedAccountRuntime.materializeNative(request, context, options)` callback.
The tool id uses the System Tool contribution's local-id grammar. The callback
receives the selected service, invocation services and cancellation signal; it
does not receive a saved Account, credentials or Account configuration. An authorized consumer can pass
that qualified service as `nativeService` in the ordinary `materialize()`
options. The host uses it only for an unbound purpose; an explicit account
selection, even if invalid or unavailable, never falls back to the native login.
The service must be among the consumer purpose's compatible services.
The daemon invokes only that service's callback; a missing callback is a typed
native-authentication unavailability. Requesters whose custody forbids host
native credentials are refused before the callback can acquire credentials.

GitHub's adapter obtains authorization from the executing machine's GitHub CLI,
including the admitted Enterprise host. The returned credential is ephemeral;
the native service choice is not a Connected Account and must not be replaced
with a fabricated account id. A lost login returns a typed authentication
failure requiring sign-in with `gh` on that machine.

An Action's Connected Account purpose declaration can pair `path` with
`nativeServicePath` so its schema admits exactly one configured-account or native
selection. Both UI and agent invocations use that same canonical admission.

## Observe invalidation

In unreleased 0.3, `watch(purpose, listener)` installs an occurrence-local subscription and schedules an initial `{ kind: 'resync', authorityChanged: false }` event. Later presentation changes also carry `false`; refresh displayed metadata without restarting a Session or reconnecting its runtime. Binding, current group member, credential, revocation, configured-origin, or producer changes carry `true`. Coalescing preserves a pending authority change. Use the current binding on the next credential acquisition or admission. Already-admitted finite work retains its snapshot until completion or explicit cancellation/disposal.

The subscription does not deliver every intermediate change, expose a cursor, or make copied bytes revocable. Dispose it when no longer needed. The host also disposes it when the invoking plugin occurrence retires; a replacement occurrence must receive fresh authorization and materialize again.

Fail closed when a required account is unavailable, expired, or denied. Agent session authentication refresh uses the session runtime's host services rather than Agent-global state.

## Request-time authentication transport

Plugins that speak to a provider on every model request cannot round-trip through
the action-based service on each attempt. The host custodies a request-time
authentication transport for them, published as host-custodied external
authoring alongside the target-scoped listing above:

- `buildConnectedAccountRequestAuthClientSource({ capabilityPathEnv, ... })`
  emits a self-contained, transport-only ESM source fragment. The fragment owns
  no selection, refresh, quota, retry, or caching decision — the host keeps all
  of those. Each call rereads the private capability file the host atomically
  rotates, posts to the host's loopback endpoint, and returns the complete
  header map, scalar facts, optional expiry, and credential context, or a typed
  failure (`request_auth_unavailable`, a normalized authentication or quota
  failure with evidence).
- The capability file binds the transport to one materialization: a bounded
  materialization id, a subject-scope digest the host computes, a private
  capability value, and the current loopback port. A valid `401` means that one
  capability tuple is retired; the fragment stays retry-safe and the next call
  observes the rotated tuple. Responses are validated against the
  protocol-owned request-auth schema before any field is trusted.

This is a generic authoring surface: it declares no first-party fact fields or
provider policy. Failure reports carry structured evidence, and provider-specific
retry classification stays in each Agent plugin's own provider-limit classifier.

Import the generic listing contracts, request-auth source builder, and
provider-limit classifier from `@happier-dev/plugin-sdk/connected-accounts`.
In the 0.3 development API, built-in Agent facts come from exported Protocol
leaves: Claude, Codex, and Antigravity OAuth profiles use
`@happier-dev/protocol/agents/<agentId>/oauth-profile`,
and Claude materialization/setup-token policy uses
`@happier-dev/protocol/agents/claude/connected-account-materialization`.
Do not infer supported Provider identities or policy from another Agent's facts.

## Produce a connected account service

A producer contribution declares one service with one or more named
authentication modes. The default names the mode initially offered by the
host; it does not create a separate service or account namespace:

```json
{
  "id": "forge",
  "title": "Forge",
  "authentication": {
    "defaultModeId": "device",
    "modes": [
      {
        "id": "device",
        "kind": "oauthDeviceCode",
        "title": "Sign in with a device code",
        "outcomeReconciliation": "providerCheck",
        "scopes": ["repository.read"]
      },
      {
        "id": "token",
        "kind": "manual",
        "title": "Use an access token",
        "outcomeReconciliation": "none",
        "fields": [
          {
            "id": "token",
            "title": "Access token",
            "schema": { "type": "string", "minLength": 1 },
            "secret": true
          }
        ]
      }
    ]
  }
}
```

In 0.3 development source, a producer can add
`"ui": { "category": "cloud-machines" }` to this descriptor. The setup catalog
preserves that presentation hint for bundled and installed plugins. Omit it to
keep the host's existing service classification. It grants no authentication,
Machine availability, permission or HostAccess authority; those still come
from the normal declaration and admission owners.

The same unreleased descriptor can provide a compact `ui.shortName` and setup
presentation through `ui.setup`. Set `order` for catalog placement,
`firstRun: true` to offer the service during first setup, and
`catalogDescription` for its sign-in description. The description accepts the
same string or `{ key, fallback }` localized value as the descriptor's title.
Omitting these fields keeps the host's generic presentation. Bundled services
can also name a packaged SVG Resource from their own plugin with
`ui.iconResourceId` when their service mark differs from the Agent mark.

In an ordinary author module, put the same descriptor (without its `id`) and
runtime under `connectedAccountDescriptors.forge`; `definePlugin(...)`
generates the matching activation binding:

```ts
connectedAccountDescriptors: {
  forge: {
    declaration: forgeDeclaration,
    runtime: {
      authentication: {
        modes: {
          device: {
            kind: 'oauthDeviceCode',
            begin,
            poll,
            cancel,
            reconcile,
          },
          token: {
            kind: 'manual',
            complete,
          },
        },
      },
      refresh,
      revoke,
      status,
      quota,
      materialize,
    },
  },
},
```

In the unreleased 0.3 API, `oauthDeviceCode` also supports browser sign-in
protocols that return a URL and require polling without issuing a user code.
Return `awaitingDeviceAuthorization` with the verification URL and poll interval;
omit `userCode` and `expiresAtMs` when the provider supplies neither. The host
uses its existing authentication-attempt lifetime when no provider deadline is
available, including after recovery of the attempt. Keep polling inside the
runtime's `poll` callback; the host owns scheduling and cancellation.

The host rejects missing or extra runtime modes, kind mismatches, and
reconciliation mismatches. `providerCheck` requires one safe `reconcile`
implementation for the original transaction. `lateEvidence` and `none`
forbid it. Do not implement reconciliation by repeating `begin`, `complete`,
or another possibly effective provider exchange. When a remote effect may
have happened but cannot yet be proved, return `outcomeUnknown`.

Authentication context distinguishes a first connect from reconnecting one
exact qualified account. On first connect, include the successful result's
optional top-level `accountId` only when the provider supplies a truthful
immutable service-local identity. Otherwise omit it and the host mints an
opaque canonical ID that is independent of the authentication attempt and is
reused for ambiguous settlement rereads. Reconnect remains bound to the exact
admitted account. Provider account ID/email, display name, and scopes are
mutable metadata:

```ts
return {
  status: 'connected',
  ...(providerResponse.immutableServiceLocalId
    ? { accountId: providerResponse.immutableServiceLocalId }
    : {}),
  providerIdentity: {
    accountId: providerResponse.subject,
    email: providerResponse.email,
  },
  displayName: providerResponse.displayName,
  scopes: providerResponse.scopes,
};
```

OAuth modes may declare descriptor-driven configuration:

```json
{
  "configuration": {
    "scope": "service",
    "changeBehavior": "reconnect",
    "fields": [
      {
        "id": "baseUrl",
        "title": "Base URL",
        "schema": { "type": "string", "minLength": 1 },
        "required": true,
        "presentation": { "control": "text" }
      }
    ]
  }
}
```

Configuration fields reuse the Plugin Settings field vocabulary but cannot
use `presentation.binding`: they are already bound to their exact service or
account target. Runtime leaves receive one daemon-normalized snapshot with
that target and mode, its revision, non-secret `values`, and bounded
`getSecret(fieldId)`. Descriptors and UI projection contain the field schema
and whether each field is secret, never secret values.

The optional `getPublicOAuthClient({ signal })` reads the Home operator's public
client for this exact service and mode. It returns `{ clientId, scopes }` or
`null`; older hosts may omit the method. Treat either absence as unavailable,
and retain the selected client with the existing attempt before consent:

```ts
const client = await context.configuration.getPublicOAuthClient?.({ signal: context.signal });
if (!client) return { status: 'unavailable', diagnostic: {
  code: 'public_client_unavailable', message: 'Configure your own OAuth client or use a token.',
} };
await context.attemptCredentials.set('oauthClientId', client.clientId, { signal: context.signal });
await context.attemptCredentials.set('oauthScopes', JSON.stringify(client.scopes), { signal: context.signal });
```

Exchange, refresh and revocation use the retained selection, even after the Home
default changes. This public metadata proves neither granted scopes nor API
permission; the runtime still verifies the provider's token response and identity.

For a first connect, required account-scoped values may need to exist before
the producer returns a canonical account ID. That authentication call receives
an operation-local `attempt` configuration target containing only the attempt,
service, and mode identities. It never receives a fake or provisional account
ID. Successful connection promotes the staged configuration to the producer's
returned exact account; reconnect and established operations use the canonical
account target.

### Manual authentication provenance

In 0.3 development source, a manual mode may declare
`credentialOrigin: 'authentication'` only when its runtime completion actually
verifies provider authentication. Use `credentialOrigin: 'native_import'` when
importing an existing native login instead. Omission means unknown: importing
or saving credentials does not establish when the person originally signed in.
An Account-direct key-save receipt never establishes a provider sign-in fact,
even when the same mode's Machine-backed verifier declares `authentication`.

### Account-direct manual credentials

The 0.3 development line supports `accountDirectSave: true` on a manual
authentication mode whose field ids and string values are already the canonical
credential payload. When only the stored key differs, declare
`accountDirectSave: { fieldKeys: { token: 'apiKey' } }` instead. This is a simple
source-field-to-credential-key projection: values are unchanged, source fields
must be declared, and effective credential keys must be valid and unique.
The Account save validates the declared fields and uses the
Account's current encryption mode; it does not contact a Machine, run the plugin,
or verify the key with the provider. Do not declare this for a mode that needs
value transformation, runtime validation, or configuration. Configuration-bearing
modes cannot opt in. This declaration is independent of `directExport`, which
governs Team export rather than field transformation or Account save admission.

The optional Account Action `connectedServices.accounts.credentials.save` accepts
an exact `account` reference, `modeId`, and live-only `fields`. Its successful
receipt is `{ applied: true, account }`, not an authentication-attempt result or
proof of provider sign-in. A lost or unreadable acknowledgement is an unknown
outcome: inspect that exact Account before retrying, and retain its creation id
for any explicit retry rather than creating another Account. Ordinary
authentication modes retain their existing Machine-backed flow.
For example, Gemini's API key needs only the declared `token` → `apiKey`
projection; its service-account JSON mode still needs runtime processing.
Modal and Crabbox token modes require account configuration and remain
Machine-backed.

The setup form's optional personal name is stored through the existing Account
label Action after the credential acknowledgement, not as provider identity.
If that optional name update fails, the saved account still opens; its Account
page owns an explicit name retry without creating another credential.

### Quota recovery credits

In the 0.3 development line, a service that can consume quota-reset credits
declares `recoveryCredits: { supported: true }` and implements the optional
runtime `recoveryCredits.read` and `recoveryCredits.consume` methods. This
declaration does not enable automatic spending: the host also requires the
automatic-reset feature and the account pool's explicit opt-in.

The host selects an available, unexpired credit from the inventory, or uses
the available aggregate count when the service exposes no individual credit
IDs. Consumption receives a host-owned idempotency key and the selected credit
ID, if any. Both methods use the exact established account context and its
credential revision; network requests still require the plugin's existing
HostAccess authority. A successful reset must be followed by a fresh quota
observation before the host treats the account as recovered.

If a consume result is lost or malformed after the operation starts, the
daemon retains an uncertain receipt and prevents further automatic spending
for that account during the current coordinator lifetime, even after a newer
quota observation. This is not a cross-restart exactly-once guarantee. The
facet does not add a manual reset control to the connected-account or session
UI.

Public producer descriptors do not declare host adapters, origins,
permissions, purposes, or HostAccess IDs. Network calls use
`context.services.http` only when the plugin's existing `network` HostAccess
request authorizes the exact `connectedAccountOrigin`; final HTTP policy
remains authoritative.
