---
title: Connected accounts
description: Select and materialize host-managed account credentials.
---

Use `context.services.connectedAccounts` for host-managed account connections. Access is purpose-bound: a plugin declares why one contribution needs an account, and the host/user binds that purpose to one compatible account or account group. Plugins cannot enumerate unrelated accounts or choose a group member.

## Declare a purpose

An Agent declares purposes in its contribution:

```json
{
  "id": "example-agent",
  "connectedAccounts": [
    {
      "purpose": "upstream",
      "title": {
        "key": "connectedAccounts.upstream",
        "fallback": "Upstream service"
      },
      "service": {
        "pluginId": "example.accounts",
        "localId": "api"
      },
      "materializationKinds": ["httpHeaders"]
    }
  ]
}
```

`purpose` is a machine identifier, not display text. Give the host an optional
localized `title` for the selection UI; it may be a plain string or a
`{ key, fallback }` value. The host uses that same declaration detail for
built-in and external contributions, so do not derive a user-facing label from
the raw purpose ID.

An action or hook uses the ID of its existing `connectedAccounts` HostAccess request as the purpose. Do not declare that purpose a second time. The request's `serviceRefs` are compatible alternatives for one binding, and its operations authorize methods:

- `select` permits `requestSelection()`.
- `use` permits `getBinding()`, `listAccounts()`, and `watch()`.

Raw credential materialization additionally requires the declaration or
HostAccess scope to list the exact requested `materializationKinds` value:
`httpHeaders`, `environment`, or `files`. A `connectedAccounts` HostAccess
scope may list these kinds only when its operations include `use`. When
present, the list must be nonempty and contain no duplicates. Omitting
`materializationKinds` still permits binding inspection and observation, but
permits no raw credential materialization.

## Inspect and select the binding

`getBinding(purpose, options?)` returns a redacted binding summary or `null` when the declared purpose is unbound. A summary contains the local purpose, selected service reference, target kind (`account` or `group`), and a display name. It does not expose internal account/group IDs, scheduler state, revisions, or credentials.

`requestSelection({ purpose, reason }, options?)` opens the host-owned selection flow and returns the resulting binding. A purpose whose request lists several compatible services still selects exactly one service and one account or group. Declare separate purposes when one operation needs multiple services.

Only `requestSelection()` requires an available current-session interaction
owner. If the user cancels, it fails with `plugin_interaction_cancelled`; if no
interaction owner is available, it fails with `plugin_interaction_unavailable`.
An already-bound, currently authorized purpose can still use `getBinding()` and
`watch()` outside a session, and can use `materialize()` there when its exact
requested kind is authorized. The selection flow never returns the host-private
account inventory to the plugin.

## List the accounts authorized for a purpose

`listAccounts({ purpose, limit? }, options?)` returns non-secret metadata for
the exact current target of that declared purpose. A direct account binding
lists only that account. A group binding lists only the group's currently
enabled members. Use it when one contribution legitimately reads from several
members of its bound group — for example discovering each organization a user
has connected — not to enumerate arbitrary accounts from the same service.

Each entry carries the exact account reference, a host display name, the
connection `state` (`connected`, `expired`, `reconnectRequired`, or
`unavailable`), and `connectedAccountOrigins`: every host-normalized,
credential-free configured origin that account owns. An account whose
authentication mode declares no configured origin returns an empty array; the
host never selects a preferred origin.

Each entry also carries `connectedAccountBases`: the same configuration seen as
service bases. A base is an origin plus the path segment a deployment lives
beneath — an organization, a collection, or a path-prefixed self-hosted install
— and it is what a source routes requests by. Every base begins with one of that
account's `connectedAccountOrigins`, because HostAccess still admits network
access by origin alone. Declare a base with a `connectedAccountBase`
configuration field; a `connectedAccountOrigin` field keeps meaning exactly
`scheme://host[:port]` and rejects a path.

The result is bounded, not paginated. `status` is `complete` only when the
returned array is the whole authorized set; any elision — the host-clamped
`limit` or a storage cap — reports `status: 'truncated'`. There is no cursor.

```ts
const listed = await context.services.connectedAccounts.listAccounts({
  purpose: 'upstream',
});
const usable = listed.accounts.filter((account) => account.state === 'connected');
```

The listing exposes no credential, configuration value, capability list, group
catalogue, or same-service account outside that target, and it never changes the
selected binding. Re-read it after a `watch()` resync rather than caching it.
This listing and its exact-account counterpart are ratified host-custodied
external-authoring capabilities: any author may consume them for a purpose the
host has authorized, while the host retains custody of the account inventory,
authorization, currentness, and the selected binding.

## Credential materialization

`materialize(purpose, request, options?)` returns a point-in-time credential snapshot in only the requested and declared form:

- HTTP headers for one origin and bounded header names
- environment variables for bounded keys
- files for bounded file ids

```ts
const binding = await context.services.connectedAccounts.getBinding('upstream');
if (!binding) {
  await context.services.connectedAccounts.requestSelection({
    purpose: 'upstream',
    reason: 'Choose the account used for this request',
  });
}

const credential = await context.services.connectedAccounts.materialize(
  'upstream',
  {
    kind: 'httpHeaders',
    origin: 'https://api.example.com',
    headerNames: ['authorization'],
  },
);
```

Materializing an unbound purpose fails with the host's canonical resource-not-selected error. For a group binding, each call resolves the current member; a plugin cannot select a member per request.

`materializeListedAccount({ purpose, account, materialization }, options?)` is
the exact-account counterpart to `listAccounts()`. It takes an account reference
returned by the current listing and returns the same point-in-time credential
forms. The host re-verifies that the account is still authorized for the
declared purpose before and after materialization: it must still be the direct
target or a current enabled member of the bound group. An account from the same
service but outside that scope is rejected. For an `httpHeaders` request, the
origin must also still be admitted — either a declared fixed origin or one
member of that account's current `connectedAccountOrigins`. Pass only a value
the listing returned; display text, configuration bytes, and credential contents
can neither choose nor widen the origin.

`materializeListedAccount()` needs the same `materializationKinds` authority as
`materialize()`. It is not a selector: it neither reads nor changes the selected
binding, and an account that has left the authorized set fails closed.

The host owns credential storage, refresh, scoping, selection UX, and log redaction. Do not persist returned credentials in plugin storage or emit them in events, diagnostics, artifacts, or messages. The public service has no failure-reporting, refresh, receipt, generation, or scheduler API.

## Observe invalidation

`watch(purpose, listener)` installs a generation-local subscription and then schedules an initial opaque `{ kind: 'resync' }` event. Binding, current group member, credential, revocation, configured-origin, or producer changes may coalesce into another resync. On every resync, discard reliance on the previous snapshot and call `getBinding()`, `listAccounts()`, or a materialization again.

The subscription does not deliver every intermediate change, expose a cursor, or make copied bytes revocable. Dispose it when no longer needed. The host also disposes it when the invoking plugin generation retires; a replacement generation must receive fresh authorization and materialize again.

Fail closed when a required account is unavailable, expired, or denied. Agent session authentication refresh uses the session runtime's host services rather than Agent-global state.

## Request-time authentication transport

Plugins that speak to a provider on every model request cannot round-trip through
the action-based service on each attempt. The host custodies a request-time
authentication transport for them, published as host-custodied external
authoring alongside the target-scoped listing above:

- `buildConnectedAccountRequestAuthClientSource({ capabilityPathEnv, ... })`
  emits a self-contained, transport-only ESM source fragment. The fragment owns
  no selection, refresh, quota, retry, or caching decision — the host keeps all
  of those. Each call rereads the private capability file the host atomically
  rotates, posts to the host's loopback endpoint, and returns one bounded lease
  (access token, optional required headers, credential context) or a typed
  failure (`request_auth_unavailable`, a normalized authentication or quota
  failure with evidence).
- The capability file binds the transport to one materialization: a bounded
  materialization id, a subject-scope digest the host computes, a single-use
  capability value, and the current loopback port. A valid `401` means that one
  capability tuple is retired; the fragment stays retry-safe and the next call
  observes the rotated tuple. Responses are bounded (256 KiB) and validated
  against the protocol-owned request-auth schema before any field is trusted.

This is a generic authoring surface: it carries no first-party agent facts or
policy of its own. Pinned provider-terminal evidence identities (for example,
which producer versions and terminal signatures the host admits) are owned by
the shared protocol vocabulary, and provider-specific retry classification
stays in each Agent plugin's own provider-limit classifier.

Import the generic listing contracts and request-auth source builder from
`@happier-dev/plugin-sdk/connected-accounts`. Happier's built-in OAuth profiles,
Claude materialization/setup-token policy, and provider-limit classifier live on
the explicit `@happier-dev/plugin-sdk/first-party/connected-accounts` subpath.
Third-party plugins should not infer provider policy or supported identities
from those first-party facts.

## Produce a connected account service

A producer contribution declares one service with one or more named
authentication modes. The default names the mode initially offered by the
host; it does not create a separate service or account namespace:

```json
{
  "id": "forge",
  "title": "Forge",
  "authentication": {
    "defaultModeId": "device",
    "modes": [
      {
        "id": "device",
        "kind": "oauthDeviceCode",
        "title": "Sign in with a device code",
        "outcomeReconciliation": "providerCheck",
        "scopes": ["repository.read"]
      },
      {
        "id": "token",
        "kind": "manual",
        "title": "Use an access token",
        "outcomeReconciliation": "none",
        "fields": [
          {
            "id": "token",
            "title": "Access token",
            "schema": { "type": "string", "minLength": 1 },
            "secret": true
          }
        ]
      }
    ]
  }
}
```

In an ordinary author module, put the same descriptor (without its `id`) and
runtime under `connectedAccountDescriptors.forge`; `definePlugin(...)`
generates the matching activation binding:

```ts
connectedAccountDescriptors: {
  forge: {
    declaration: forgeDeclaration,
    runtime: {
      authentication: {
        modes: {
          device: {
            kind: 'oauthDeviceCode',
            begin,
            poll,
            cancel,
            reconcile,
          },
          token: {
            kind: 'manual',
            complete,
          },
        },
      },
      refresh,
      revoke,
      status,
      quota,
      materialize,
    },
  },
},
```

The host rejects missing or extra runtime modes, kind mismatches, and
reconciliation mismatches. `providerCheck` requires one safe `reconcile`
implementation for the original transaction. `lateEvidence` and `none`
forbid it. Do not implement reconciliation by repeating `begin`, `complete`,
or another possibly effective provider exchange. When a remote effect may
have happened but cannot yet be proved, return `outcomeUnknown`.

Authentication context distinguishes a first connect from reconnecting one
exact qualified account. On first connect, include the successful result's
optional top-level `accountId` only when the provider supplies a truthful
immutable service-local identity. Otherwise omit it and the host mints an
opaque canonical ID that is independent of the authentication attempt and is
reused for ambiguous settlement rereads. Reconnect remains bound to the exact
admitted account. Provider account ID/email, display name, and scopes are
mutable metadata:

```ts
return {
  status: 'connected',
  ...(providerResponse.immutableServiceLocalId
    ? { accountId: providerResponse.immutableServiceLocalId }
    : {}),
  providerIdentity: {
    accountId: providerResponse.subject,
    email: providerResponse.email,
  },
  displayName: providerResponse.displayName,
  scopes: providerResponse.scopes,
};
```

OAuth modes may declare descriptor-driven configuration:

```json
{
  "configuration": {
    "scope": "service",
    "changeBehavior": "reconnect",
    "fields": [
      {
        "id": "baseUrl",
        "title": "Base URL",
        "schema": { "type": "string", "minLength": 1 },
        "required": true,
        "presentation": { "control": "text" }
      }
    ]
  }
}
```

Configuration fields reuse the Plugin Settings field vocabulary but cannot
use `presentation.binding`: they are already bound to their exact service or
account target. Runtime leaves receive one daemon-normalized snapshot with
that target and mode, its revision, non-secret `values`, and bounded
`getSecret(fieldId)`. Descriptors and UI projection contain the field schema
and whether each field is secret, never secret values.

For a first connect, required account-scoped values may need to exist before
the producer returns a canonical account ID. That authentication call receives
an operation-local `attempt` configuration target containing only the attempt,
service, and mode identities. It never receives a fake or provisional account
ID. Successful connection promotes the staged configuration to the producer's
returned exact account; reconnect and established operations use the canonical
account target.

Public producer descriptors do not declare host adapters, origins,
permissions, purposes, or HostAccess IDs. Network calls use
`context.services.http` only when the plugin's existing `network` HostAccess
request authorizes the exact `connectedAccountOrigin`; final HTTP policy
remains authoritative.
