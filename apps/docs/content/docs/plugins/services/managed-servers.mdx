---
title: Managed services
description: Supervise plugin-owned local services through context.services.managedServices.
---

Use `context.services.managedServices.supervise(...)` from a daemon runtime for plugin-owned loopback services. It is not callable from a browser, React Native, or other client realm. For managed-spawn mode, declare the consumed managed dependencies and executable access in the cold manifest first. External-attach mode uses its declared endpoint and applicable host-access policy without inventing a launch dependency.

A managed model Provider uses this same exact-handle lifecycle from its runtime
context. The Provider adapts its protocol; the host owns connection/adoption,
credential materialization, currentness, and child retirement. See
[Add a model Provider](/plugins/guides/providers) before creating a
Provider-local supervisor or credential cache.

The service can own process launch, explicit managed-spawn or external-attach mode, port allocation, health checks, startup timeout, bounded credentials, durable log policy, snapshots, exact-handle requests, and cleanup.

## Endpoint-free and native lifetime (0.3 development)

An owned process that does not listen uses `spawn.endpoint: { kind: 'none' }`.
Its snapshot can be `running` without an address; the host does not invent a
port or call it HTTP-healthy. Exact-handle requests need an observed endpoint,
and a health-only wait needs an actual health capability, such as an admitted
command check. A missing capability returns typed unavailable.

A native resource whose lifetime outlasts its starter uses `mode.kind: 'native'`
with its admitted launch and exact native instance. The manifest-declared
`projectNativeAdapters` service lifecycle reports phase, readiness and an
optional observed endpoint together. Starter exit does not mean the resource
stopped. A definitive native stop settles the handle; an accepted-only stop
needs a stopped observation. Unsupported or unconfirmed stop retains custody
and does not permit replacing the resource as though it had stopped.

In 0.3 development source, a native lifecycle may also supply
`logs(instance, { maxBytes, signal }, context)` for failure diagnostics. Use the
exact admitted instance and the provided byte budget to bound the native read;
tools with line-based tails can use their bounded tail granularity. The host
sanitizes and retains the result within that UTF-8 byte budget as
`native_service_output` on the service snapshot. Collection happens on a failure
transition or one explicit failed health inspection. Healthy and unchanged
watchdog samples do not read logs. This callback is optional: omitting it keeps
inspection and Stop working, and the failure remains reportable without output.
It does not provide a live log stream or promise a Services-page output viewer.

These are development-source contracts, not a claim that sessionless Project
Services or every native tool is available. Native supervision requires the
current admitted lifecycle role; an unavailable role refuses before launch.

## Retained workload observation (0.3 development)

Inside a host-admitted native workload invocation, attach to an existing service:

```ts
const result = await context.services.managedServices.observeWorkload({ serviceId });
if (result.kind === 'ready') {
  const workload = result.workload;
  const observation = workload.observe(row => render(row));
  const current = workload.snapshot(); // health, endpoint and projected ports
  const logs = await workload.readLogs();
  await workload.control('restart'); // requires admitted mutation authority
  observation.dispose();
  await workload.dispose(); // detach; leave the native workload serving
}
```

The host admits the Machine and resource once. A service identifier alone does
not grant access; ordinary invocations return typed unavailable. Daemon deployment
roles receive their admitted Environment binding. Observe/link roles can read
without acquiring native mutation authority. Native controls and logs retain the
existing adapter's supported operations and unavailable results. No additional
Windows or macOS native adapter is introduced by this API.

After daemon restart, a new invocation joins the existing Environment recovery
and attaches to the recovered generation. The handle is process-local; do not
persist it or create another native scan or supervisor. Invocation cleanup and
handle disposal detach observations and log watches. Explicit Stop remains a
separate admitted effect. These are development-source contracts, not a claim
of loaded-runtime certification.

## Exact-handle HTTP requests

The following HTTP example requires an endpoint-producing specification.

```ts
const service = await context.services.managedServices.supervise(spec, {
  signal: context.signal
});

await service.waitUntilHealthy({ signal: context.signal });

const response = await service.request({
  pathAndQuery: '/v1/events',
  interactive: true,
  signal: context.signal
});
```

`request(...)` resolves only against this exact handle's validated loopback
endpoint. In the unreleased 0.3 SDK, an optional `timeoutMs` bounds request
establishment through validated response headers; omission adds no request
deadline. The timeout does not cover the response body. An admitted finite
request completes across credential or scope revocation; the next request is
refused. Caller cancellation and explicit Stop or disposal still end that work.
Set `interactive: true` for open-ended event subscriptions, as above, so scope
retirement also closes the stream. The host rejects redirects, absolute
URLs, caller authorization headers, path ambiguity, stale handles, and retired
invocation scopes before exposing a response.

The snapshot may expose the validated `baseUrl` needed by declaration contracts
such as MCP discovery, but not a separate host, port, PID, token, password, or
custody identity. `clientAccess` defaults to `{ kind: 'none' }`. Generated access
is spawn-only: `{ kind: 'hostBearer', ... }` is limited to a canonical
managed-Provider start, while `{ kind: 'hostBasic', ... }` is limited to an
owned Session-runner spawn. Attach accepts `{ kind: 'none' }` (or omission) or
`{ kind: 'declaredSecretBasic', passwordSecretId, ... }`. The latter names a
Settings field declared with `secret: { custody: 'daemon' }`; the host resolves
that daemon-local secret and applies Basic authentication to health probes and
exact-handle requests. Authors declare destinations and secret identifiers,
never values. The host generates or resolves the value and applies the matching
request header internally; plugin code receives no generated bearer, password,
declared secret, or encoded `Authorization` header.

Use the exact handle's `request(...)` method for authenticated service traffic
rather than adding a second HTTP transport or reconstructing endpoint and
authentication state from `baseUrl`.

Dispose the returned handle with its owning invocation, Agent runtime, or Session.

## Good practices

- Bind managed services to loopback.
- Prefer exact-handle `request(...)`; reserve `baseUrl` for contracts that must return an absolute endpoint.
- Declare only the narrow child authentication injection needed by an owned spawn.
- Keep external-attach and managed-spawn modes explicit.
- Redact durable logs.
- Fail closed when post-start health or authentication validation fails.
