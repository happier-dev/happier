---
title: Secrets service
description: Store plugin-owned secrets without exposing values through projection.
---

Use `context.services.secrets` for plugin-owned values and Saved Secret references.

## Availability

Available in the current source contract. The [capability matrix](/plugins/manifest/availability)
records loaded-platform and release evidence separately from source
availability. The public external-author reference below provides maintained
source-shape coverage for the service.

## Choose secret custody

Secret declarations describe Settings and custody; they do not grant trusted
plugin code permission to use an identifier. A `secret` Settings field or the
top-level `secrets` list can select custody:

```ts
secrets: [{ id: 'document-review-webhook-token' }],
```

Identifiers without declarations use the invocation's captured Account custody.
Omitting `custody` also selects Account custody. Daemon declarations select the
separate machine-local store; they do not change the Account or its lifetime.

## Operations

- `status(id)` reports configured, missing, denied, or unavailable without returning the value.
- `get(id, options)` reads a value from the selected custody.
- `readSavedSecret(ref, { resourceRevision?, signal? }?)` reads a Saved Secret reference in the unreleased 0.3 contract.
- `set(id, value, options)` stores a value.
- `delete(id, options)` removes a value.

Mutation results carry a revision. Use `expectedRevision` when a caller must reject a conflicting update.

## External secret sources (0.3 development)

The unreleased 0.3 authoring contract adds `secretSources` to `definePlugin`.
Each local id has `declaration: { title }` and a runtime with
`acquire({ account, reference }, context)`. Optional
`list({ account, vaultId?, itemId? }, context)` returns vault/item/field
identities, names and kinds, never values. Return
`{ ok: true, fields, vaults? }`, where each vault is `{ id, name }`. Include empty
vaults in `vaults` so people can choose them when saving or exporting a secret.
Existing field-only results remain supported. Optional
`store({ account, vaultId, title, value }, context)` returns only
`{ ok: true, account, reference }` or a typed failure. The authoring adapter
derives the cold `list` and `store` capability flags from these methods;
acquire-only runtimes remain supported. The declaration projects to the
manifest; `activate(api)` registers its executable runtime through
`api.secretSources.register(localId, runtime)`.

The host lists source metadata through the existing `secrets.list` Action.
In unreleased 0.3 source, `secrets.usedBy` reads the references to a managed Saved
Secret in the invocation's own Account:

```ts
const result = await context.services.actions.execute('secrets.usedBy', {
  ref: savedSecretReference,
}, { signal: context.signal });
```

The result contains `references` with owner, path and optional referrer metadata,
never credential values. An empty array means no references were found; `null`
means the host does not have complete census coverage. The read uses the same
approval policy as `secrets.list` and accepts no Account selector. It does not
report another Account's use of a shared resource. The maintained
`examples/public-authoring/sharedSecrets.ts` demonstrates this typed call.

Listing and linking a reference do not acquire its value. At a trusted
consumer's next secret acquisition, the executing Machine activates the selected
contribution and supplies the operation's cancellation signal. Return
`{ ok: true, value }` privately to that acquisition, or a typed unavailable
result with a repair hint. Keep native stdout and stderr out of Action results
and logs. The host does not cache external values or poll for rotation.

Bulk linking creates one Saved Secret reference per selected field in one
operation, including a whole-vault selection. `storeIn` on secret creation and
confidential Save writes to the vault before saving the resulting reference.
Export stores an existing inline value and converts that same Saved Secret to
the returned reference using its current revision. A failed export leaves the
original unchanged. Selected exports return per-secret outcomes. Connected
configuration references keep their identity and acquire the vault value at use
time; rotating OAuth credential records remain in Happier.

The 1Password source reads the selected field with the Machine's native
`op read` command. Interactive reads use that Machine's 1Password setup;
unattended reads link an inline Saved Secret to the plugin's service account
token setting and require 1Password CLI 2.18 or newer. The runtime requests that bootstrap value with
`secrets.get(id, { sourceKind: 'inline', signal })` and supplies
`OP_SERVICE_ACCOUNT_TOKEN` only to its native command environment. An external
reference cannot bootstrap another external acquisition. See the official
[1Password read command](https://www.1password.dev/cli/reference/commands/read)
and [service account setup](https://www.1password.dev/service-accounts/use-with-1password-cli).

The bundled source also enumerates native item JSON and writes with managed
`op item create -`, passing its JSON template through stdin. Secret values never
enter command arguments. A lost write response or conflicting Saved Secret
revision may leave a vault item to recover manually; the host does not replay
the write. See the official [item commands](https://www.1password.dev/cli/reference/management-commands/item).

## Save generated credentials as shared references

The unreleased 0.3 source contract adds
`saveShared(id, { label, bytes, audience }, options?)`. It is available only with
the invocation's captured Account custody and the parent Action's reviewed id,
purpose and audience. It needs no secret declaration or opt-in. Controller
Account Actions require the matching host service projection.

Use the exact id and audience reviewed for the current invocation. For example,
inside the provider Action that receives generated credential bytes:

```ts
const saved = await context.services.secrets.saveShared(
  'database-password',
  { label: 'Database password', bytes: generatedPassword, audience: reviewedAudience },
  { signal: context.signal },
);
return { ref: saved.ref, resourceRevision: saved.resourceRevision };
```

`generatedPassword` holds UTF-8 credential bytes in a `Uint8Array` within that invocation. It must not be
an Action input, logged value or returned provider response. A separate reviewed
invocation selects `migration-password` and its own audience; declaration order
does not choose an id. `audience` uses the existing Saved Secret
`accountGrants`, `teamGrants` and `groupGrants` fields. It must equal the admitted
audience after host normalization and cannot widen access.

An id or purpose outside the parent review, changed audience, cancellation or
retired Account custody refuses the write. A successful save creates a Saved Secret and returns
only its exact shared reference and revision; binding it to an Environment is a
separate step through the existing bindings Action.

Plain Accounts need no encryption key. An authorized E2EE controller with current
material can save locally. Without that material or authorized settlement, the
host returns `secret_save_client_required` before creating a resource.

## Read a Saved Secret and send an HTTP body

In the unreleased 0.3 contract, `readSavedSecret` returns the requested value to
trusted plugin code and registers it for invocation redaction before returning.
The plugin builds an ordinary `Uint8Array` HTTP body:

```ts
const password = await context.services.secrets.readSavedSecret(saved.ref, {
  resourceRevision: saved.resourceRevision,
  signal: context.signal,
});
const response = await context.services.http.request({
  url: 'https://api.example.com/variables',
  method: 'POST',
  redirect: 'error',
  headers: { 'content-type': 'application/json' },
  body: new TextEncoder().encode(JSON.stringify({
    name: 'DATABASE_PASSWORD', value: password, publicValue: 'visible',
  })),
}, { signal: context.signal });
```

The read uses the Account captured when the invocation was created. An Account
switch cannot redirect it to another Account. The Saved Secret owner checks
current audience, encryption mode and the requested revision at acquisition;
omitting `resourceRevision` reads the current authorized value. Missing or
withdrawn material refuses the read. Unmet E2EE custody returns
`secret_use_client_required` before this example sends a provider request.
After the read, ordinary HTTP does not acquire the secret again.

A cross-origin `307` or `308` redirect that would resend a body containing a
registered secret returns the non-retryable `credential_request_redirect_refused`
failure before the second request. Same-origin redirects may follow the normal
HTTP policy. Provider responses remain available to trusted plugin code;
successful Action results redact registered values before delivery to an Agent.
Ordinary non-secret response content remains readable. Controller selection and
offline recovery belong to the parent Action relay, with no browser or server
HTTP fallback.

The CLI's separate [incremental read method](/plugins/security/network#incremental-reads-in-development)
is bodyless. It retains the
admitted authentication purpose and redaction lease through EOF or disposal;
it does not provide a way to read shared secret values.

## Rules

- Do not store tokens in the manifest, settings, plugin storage, or UI descriptors.
- Do not log or emit secret values.
- Ask for a secret only at the point it is needed and provide a user-readable reason.
- Use `context.services.connectedAccounts.materialize(purpose, request)` for host-managed account credentials instead of copying them into plugin storage.

Saved Secrets belong to the host catalog, not to the plugin secret service. In current development
source that catalog can resolve personal and shared Saved Secret references for an admitted host
operation. An installed external plugin and a bundled plugin receive the same declared public
service and Account custody. Reads remain subject to the Saved Secret owner's
audience, revision and encryption-mode checks. Shared Saved Secrets remain a development-only
product and must not be advertised until their complete consumer and live validation gates pass.

## Worked example

The public external-author reference `packages/plugin-sdk/examples/action-contract-producer`
declares one plugin secret and rotates it from an Action: it reads `status` for the incumbent
revision, passes that revision as `expectedRevision` so a concurrent rotation
loses instead of overwriting, reads the value back at the point of use with a
reason, and returns only the state and revision.
