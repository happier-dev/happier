---
title: Secrets service
description: Store plugin-owned secrets without exposing values through projection.
---

Use `context.services.secrets` for plugin-owned secret values.

## Availability

Available in the current source contract. The [capability matrix](/plugins/manifest/availability)
records loaded-platform and release evidence separately from source
availability. The public external-author reference below provides maintained
source-shape coverage for the service.

## Declare the secret first

The service resolves only declared identifiers. Declare each plugin-owned secret
in the manifest, either as a `secret` Settings field or through the top-level
`secrets` list:

```ts
secrets: [{ id: 'document-review-webhook-token' }],
```

An undeclared identifier is rejected with `plugin_secret_undeclared`; it is not
created on first write. Omitting `custody` selects Account custody.

## Operations

- `status(id)` reports configured, missing, denied, or unavailable without returning the value.
- `get(id, options)` reads a value when the host grants access.
- `set(id, value, options)` stores a value.
- `delete(id, options)` removes a value.

Mutation results carry a revision. Use `expectedRevision` when a caller must reject a conflicting update.

## External secret sources (0.3 development)

The unreleased 0.3 authoring contract adds `secretSources` to `definePlugin`.
Each local id has `declaration: { title }` and a runtime with
`acquire({ account, reference }, context)`. Optional
`list({ account, vaultId?, itemId? }, context)` returns vault/item/field
identities, names and kinds, never values. Return
`{ ok: true, fields, vaults? }`, where each vault is `{ id, name }`. Include empty
vaults in `vaults` so people can choose them when saving or exporting a secret.
Existing field-only results remain supported. Optional
`store({ account, vaultId, title, value }, context)` returns only
`{ ok: true, account, reference }` or a typed failure. The authoring adapter
derives the cold `list` and `store` capability flags from these methods;
acquire-only runtimes remain supported. The declaration projects to the
manifest; `activate(api)` registers its executable runtime through
`api.secretSources.register(localId, runtime)`.

The host lists source metadata through the existing `secrets.list` Action.
Listing and linking a reference do not acquire its value. At a trusted
consumer's next secret acquisition, the executing Machine activates the selected
contribution and supplies the operation's cancellation signal. Return
`{ ok: true, value }` privately to that acquisition, or a typed unavailable
result with a repair hint. Keep native stdout and stderr out of Action results
and logs. The host does not cache external values or poll for rotation.

Bulk linking creates one Saved Secret reference per selected field in one
operation, including a whole-vault selection. `storeIn` on secret creation and
confidential Save writes to the vault before saving the resulting reference.
Export stores an existing inline value and converts that same Saved Secret to
the returned reference using its current revision. A failed export leaves the
original unchanged. Selected exports return per-secret outcomes. Connected
configuration references keep their identity and acquire the vault value at use
time; rotating OAuth credential records remain in Happier.

The 1Password source reads the selected field with the Machine's native
`op read` command. Interactive reads use that Machine's 1Password setup;
unattended reads link an inline Saved Secret to the plugin's service account
token setting and require 1Password CLI 2.18 or newer. The runtime requests that bootstrap value with
`secrets.get(id, { sourceKind: 'inline', signal })` and supplies
`OP_SERVICE_ACCOUNT_TOKEN` only to its native command environment. An external
reference cannot bootstrap another external acquisition. See the official
[1Password read command](https://www.1password.dev/cli/reference/commands/read)
and [service account setup](https://www.1password.dev/service-accounts/use-with-1password-cli).

The bundled source also enumerates native item JSON and writes with managed
`op item create -`, passing its JSON template through stdin. Secret values never
enter command arguments. A lost write response or conflicting Saved Secret
revision may leave a vault item to recover manually; the host does not replay
the write. See the official [item commands](https://www.1password.dev/cli/reference/management-commands/item).

## Rules

- Do not store tokens in the manifest, settings, plugin storage, or UI descriptors.
- Do not log or emit secret values.
- Ask for a secret only at the point it is needed and provide a user-readable reason.
- Use `context.services.connectedAccounts.materialize(purpose, request)` for host-managed account credentials instead of copying them into plugin storage.

Saved Secrets belong to the host catalog, not to the plugin secret service. In current development
source that catalog can resolve personal and shared Saved Secret references for an admitted host
operation. An installed external plugin and a bundled plugin receive the same declared public
service and host-policy decision; neither can enumerate the Account's secret store or turn a Saved
Secret reference into unrestricted read authority. Shared Saved Secrets remain a development-only
product and must not be advertised until their complete consumer and live validation gates pass.

## Worked example

The public external-author reference `packages/plugin-sdk/examples/action-contract-producer`
declares one plugin secret and rotates it from an Action: it reads `status` for the incumbent
revision, passes that revision as `expectedRevision` so a concurrent rotation
loses instead of overwriting, reads the value back at the point of use with a
reason, and returns only the state and revision.
