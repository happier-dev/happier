---
title: Actions, tools, and commands
description: Register executable operations and expose them across CLI, MCP, and session-agent surfaces.
---

Actions are the canonical executable operation model. Tools and commands are convenience surfaces over the same idea.

## Actions

Declare actions and their handlers together with `definePlugin(...)`.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.echo',
  version: '0.1.0',
  actions: {
    echo: {
      title: 'Echo',
      run: async (input) => ({ input }),
    },
  },
});
```

Action handlers return JSON-safe values. Throw a typed plugin error when the operation cannot complete:

```js
{ value: 1 }
```

Prefer stable error codes over parsing text.

## Calling host Actions

The generated activation from `actions.<id>.run` binds a Plugin's own
manifest-declared handlers (the low-level ABI method is
`api.actions.register(...)`). When a handler needs an existing host operation,
call the same canonical Action through `context.services.actions.execute(...)`;
do not create a parallel RPC or duplicate host handler. Use an exact action id
documented by the feature that owns that operation; the SDK deliberately does
not maintain a second author-facing dump of every host action id, safety rule,
or input shape. The owning action contract remains the source of truth.

```ts
const result = await context.services.actions.execute('action.spec.get', {
  id: 'session.status.get',
}, {
  signal: context.signal,
});
```

## Tools

Tools expose plugin actions to tool-capable surfaces. The manifest owns tool metadata and references the action that supplies executable behavior; tools do not have a second runtime registration path.

Use tools when the operation is meant to be called by agents or MCP-compatible tool clients.

### Worked tool example

Declare the tool under `contributes.tools[]`. The `surfaces` list makes it available to agent/tool surfaces, and the handler target points at the runtime registration id.

```json
{
  "contributes": {
    "tools": [
      {
        "id": "notes.add",
        "name": "session_notes_add",
        "title": "Add session note",
        "description": "Store a note for the current plugin.",
        "surfaces": ["agent", "mcp"],
        "inputSchema": {
          "type": "object",
          "additionalProperties": false,
          "properties": {
            "note": { "type": "string" }
          },
          "required": ["note"]
        },
        "action": "notes.add"
      }
    ]
  }
}
```

Define the referenced action in the same `definePlugin(...)` declaration. Action
handlers receive JSON-safe input and a `PluginInvocationContext` with
plugin-scoped services.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.notes',
  version: '0.1.0',
  actions: {
    'notes.add': {
      title: 'Add session note',
      run: async (input, context) => {
        const note = String((input as { note?: unknown }).note ?? '');
        const existing = await context.services.storage.daemon.get<string[]>('notes');
        const notes = [...(existing ?? []), note];
        await context.services.storage.daemon.set('notes', notes);
        context.services.logger.info('Stored session note', { count: notes.length });
        return { note, count: notes.length };
      },
    },
  },
});
```

## Commands

Commands expose CLI-facing entries. Command declarations specify their path, visibility, availability, and canonical action reference; they do not register a parallel command handler.

## Approvals

Dangerous actions should declare danger level and confirmation metadata in the manifest. Runtime approvals should use the host action approval service instead of prompting through agent-specific side channels.

## Design rules

- Keep operation identity in the manifest.
- Keep executable code in handlers.
- Keep user-facing placement and availability descriptor-driven.
- Do not create parallel RPC handlers for operations that fit the action model.
