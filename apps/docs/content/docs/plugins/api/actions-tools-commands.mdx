---
title: Actions, tools, and commands
description: Declare executable operations, their invocation surfaces, and their execution target.
---

Actions are the canonical executable operation model. Tools and commands are convenience surfaces over the same idea.

## Actions

Declare actions and their handlers together with `definePlugin(...)`.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.echo',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    echo: {
      title: 'Echo',
      execution: { target: 'daemon' },
      run: async (input) => ({ input }),
    },
  },
});
```

Action handlers return JSON-safe values. Throw a typed plugin error when the operation cannot complete:

```ts
import { PluginError } from '@happier-dev/plugin-sdk';

throw new PluginError({
  code: 'notes.invalid_input',
  retryable: false,
});
```

Prefer stable error codes over parsing text. See
[Diagnostics](/plugins/testing/diagnostics) for the public guard and the
diagnostic workflow.

## Keep a long daemon Action visible in Activity

> **Development status:** Tracked plugin Actions are part of the current
> Developer Preview contract and have not shipped in a public Happier release.

A daemon Action can opt into a host-owned operation view. The user may
**Collapse** the running view, navigate elsewhere, and reopen it from Activity
without cancelling or starting the Action again.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

async function indexFile(path: string) {
  await Promise.resolve(path); // Replace with the plugin's real indexing work.
}

export const { manifest, activate } = definePlugin({
  id: 'com.example.indexer',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    'rebuild-index': {
      title: 'Rebuild index',
      execution: { target: 'daemon' },
      operation: {
        version: 1,
        visibility: 'activity',
        progress: 'reported',
        presentation: { onStart: 'current' },
      },
      async run(_input, context) {
        context.operation?.update({
          phase: 'discovering',
          label: 'Discovering files',
        });

        const files = ['notes.md', 'decisions.md'];
        for (const [index, file] of files.entries()) {
          await indexFile(file);
          context.operation?.update({
            phase: 'indexing',
            label: 'Indexing files',
            current: index + 1,
            total: files.length,
          });
        }

        return { indexed: files.length };
      },
    },
  },
});
```

`presentation.onStart` is required and states what the invoking surface does
the moment the host accepts the operation. `current` keeps the user exactly
where they are and lets them collapse the running view themselves; `detail`
opens the operation detail view immediately; `activity` collapses the
invoking surface so the work continues in Activity. It does not change
custody: the daemon owns the operation in every case.

Use `progress: 'indeterminate'` when the handler cannot report honest phases
or bounded numeric progress. For `reported` progress, `update(...)` accepts an
optional bounded `label` and `phase`, or finite non-negative `current` and
`total` values where `total` is greater than zero and `current <= total`.
Invalid updates are rejected by the host. `context.operation` is
invocation-scoped and optional, so the handler can keep its existing terminal
execution behavior when invoked through a surface that does not provide a
tracked-operation reporter.

The host, not the plugin, owns `accepted`, `running`, and terminal lifecycle
transitions. Returning the validated Action result succeeds the operation;
throwing fails it; host-owned cancellation uses the invocation signal when
supported. There is deliberately no `complete()` or `fail()` API.

Tracking requires a daemon Action (a root `run` handler); a client-targeted
Action cannot declare `operation`. Once accepted, tracking survives modal close,
navigation, ordinary reconnect, and browser visibility changes while the same
daemon process remains alive. The operation history is held in daemon memory,
so daemon restart may make its status unavailable. It is not an offline queue,
durable job store, restart-replay mechanism, or exactly-once guarantee.

The operation snapshot does not retain raw Action input, form drafts, tokens,
credentials, attachments, or arbitrary plugin state. Keep secret input in the
ordinary invocation only, and never copy it into progress labels or results.
Existing public HTTP and generated SDK Action execution still wait for and
return the terminal Action result; the tracked accepted receipt is not a new
public HTTP/SDK response shape.

The maintained source example is
[`examples/tracked-action`](https://github.com/happier-dev/happier/tree/v0.3/packages/plugin-sdk/examples/tracked-action).

## Invocation surface and execution target

An Action is declared and implemented once. Its `surfaces` say who may invoke
it; its execution target says where its one handler runs. Those are
independent decisions.

The **External API & SDK** surface is host-owned rather than author-declared.
Every installed daemon Action participates in API discovery and dynamic
invocation through its qualified `<pluginId>/actions/<localId>` identity,
subject to the Account's setting for that exact Action. For those daemon
Actions, an author-declared `surfaces` list neither grants nor removes API Token
access. Client-target Actions remain local to the invoking client and are not a
daemon Action API fallback.

Adding another invocation surface does not create another handler. Every
admitted surface resolves the same current declaration and its one registered
target handler through the canonical dispatcher.

- A root `run` handler makes a daemon Action: `definePlugin` emits
  `execution: { target: 'daemon' }` for it, so you do not write that field.
  The Action runs through the daemon Action executor.
- `execution: { target: 'client', ... }` names one exact client artifact,
  module, export, and supported platform list. A client Action has no `run`.
- Omitted `scopes` default to `['global']` and omitted `dangerLevel` defaults
  to `'safe'`; declare them only when an Action differs.
- `host` is not a public plugin target; canonical host ActionSpecs keep their
  existing host executor.
- `surfaces` may include `ui`, `plugin`, `voice`, `agent`, `mcp`, or `cli`.
  Adding `voice` to an Action does not add Voice to the separate Tool surface
  grammar.

A daemon target's `run` handler is bound by the root module's generated
`activate(api)`. A client target has no root `run`: its exact client artifact
exports the ordinary named `activate(api)` function and registers the same
local Action id with `api.actions.register(...)`. That client API exposes only
Action and Voice registration, not daemon services or daemon contribution
families.

A client target is client-local: it is intended to execute in the exact web,
iOS, or Android process that invoked it. Missing or retired local activation
must fail unavailable; it must not fall back to a daemon, move to another
client, or enter a cross-client queue.

> **Development status:** The explicit `daemon | client` declaration is part
> of the current Developer Preview contract, whose implementation remains in
> progress, as is loaded web/iOS/Android certification. This capability has not
> shipped in a public Happier release.

For example, the root declaration names the exact client artifact without an
inline handler:

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.details',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    'open-details': {
      title: 'Open details',
      surfaces: ['ui', 'voice'],
      placementBindings: ['detailsPanel'],
      execution: {
        target: 'client',
        client: {
          artifactId: 'action-client',
          exportName: 'activate',
        },
        platforms: ['web', 'ios', 'android'],
      },
    },
  },
});
```

The declared artifact exports that one handler exactly once:

```ts
import type { PluginClientApi } from '@happier-dev/plugin-sdk';

export async function activate(api: PluginClientApi) {
  api.actions.register('open-details', async (_input, context) => {
    await context.ui.openSurface('details');
    return null;
  });
}
```

Expose that module through the package export matching
`execution.client.artifactId`; this target is executable client code and does
not need a `contributes.ui.renderers` entry:

```json
{
  "exports": {
    "./happier-plugin-ui/action-client": "./src/client-runtime.ts"
  }
}
```

Run `happier-plugin-build-ui --project-root .` to emit its one portable
CommonJS artifact. See [UI artifacts](/plugins/ui/ui-artifacts#build-contract)
for the export, output, and digest rules.

Client handlers receive a client-safe context, including cancellation,
invocation surface, plugin identity, current-UI context when available, and a
bounded `ui` capability for opening a surface or invoking another eligible
Action. The nullable `ephemeralSharedScope` can lease plugin-local in-process
state shared with mounted UI in the same Account and current plugin
occurrence. Use a versioned local key, handle a refused acquisition, and always
release the lease; do not replace a refusal with a global cache. Client handlers
do not acquire daemon services. Input schema
validation, availability, occurrence currentness, cancellation, danger
classification, confirmation, effect custody, and no-blind-retry rules remain
canonical for every surface and target. A client handler's result is trusted
plugin output: the host returns it as-is rather than re-validating it against
the declared `outputSchema`.

## Calling host Actions

Bundled and externally installed plugins use this same service and dispatcher.
External plugins are not placed on a smaller Action allowlist: once the user
trusts the plugin, eligible host Actions are available according to the
Account's **Trusted plugins** Action settings. The host still stamps plugin
identity, occurrence, cancellation, and `account_automation` authority, so a
plugin cannot impersonate a present user or another plugin.

The generated root activation from a daemon `actions.<id>.run` binds a Plugin's
own manifest-declared handler (the low-level ABI method is
`api.actions.register(...)`). When a daemon handler needs an existing host
operation, call the same canonical Action through
`context.services.actions.execute(...)`; do not create a parallel RPC or
duplicate host handler. Use an exact action id from [Host actions](/plugins/api/host-actions), which is
generated from the canonical ActionSpec registry — so every id it lists is
reachable through `execute(...)`, and it cannot drift from the host. The owning
action contract remains the source of truth for behaviour; that page is the
index of what exists.

```ts
const result = await context.services.actions.execute('action.spec.get', {
  id: 'session.status.get',
}, {
  signal: context.signal,
});
```

The same call reaches another plugin's Action by its exact
`{ pluginId, localId }` reference. When that Action's handler throws a
`PluginError`, the rejection you catch carries the target's own `code`,
`retryable`, and published payload — see
[Diagnostics and errors](/plugins/testing/diagnostics#errors-across-a-plugin-to-plugin-action-call)
for what does and does not cross.

For Session input, prefer the typed Session service when you need the trusted
plugin authoring shape. Resolve the handle with
`await context.services.sessions.get(sessionId)`, then call `session.send(...)`.
It accepts the same optional Execution Run recipient as `session.message.send`,
plus manifest-declared Composer attachments and host-stamped source metadata.
The host qualifies the plugin identity and runs the ordinary attachment
preparation and dispatch lifecycle; plugin code does not manufacture those
trusted stamps. The public API Token/SDK Action keeps its intentionally smaller
strict input and rejects host-only `source`, attachment, or structured-launch
fields instead of accepting them as untyped JSON. That difference is an
authority boundary, not a smaller capability set for externally installed
plugins.

Omit the recipient to send to the main Session. A recipient of
`{ kind: 'execution_run', runId }` uses the Session's Pending queue and exact
Run admission. The separate `execution.run.send` host Action is only for a
detached Run with `sessionId: null`; it must not be used as a shortcut around
Session permissions, encryption, or target recovery.

### Host Actions that run in a connected app

> **Development status:** Connected-app delivery for host Actions is part of
> the current 0.3 development source and has not shipped in a public Happier release.

Host Actions such as Find, Next and workspace tab controls execute through the
answering app's existing owners. An admitted Session Agent, MCP or daemon-hosted
caller can reach a connected app on its machine through the existing reverse
channel. The caller's authority, enabled invocation surface and required
approval are checked before delivery; the app keeps that authority and surface
when executing the admitted request.

The channel selects one eligible connected app using its existing routing rule.
An Action that names a Session, composer or mounted surface still needs that
exact owner on the answering app. With no connected handler, Find and the prompt
picker return `unavailable` with `reason: 'noClient'`, Next returns
`status: 'unavailable'`, and other Actions return an `unavailable` failure.
An older app that does not advertise the method is unavailable in the same way.
If a response is lost after dispatch, `outcome_uncertain` means the operation may
have run; the host does not automatically retry it.

Standalone CLI commands remain unavailable for these client-placed host Actions.
Plugin-declared `execution: { target: 'client', ... }` Actions keep the separate
artifact and plugin-lifecycle contract described above. The generated
[host Action reference](/plugins/api/host-actions) identifies each Action's
declared invocation surfaces; declaration alone does not guarantee that its
required mounted owner is present.

### Widgets and current-Session presentation in development

Use qualified `widgets.*` host Actions to discover, configure and arrange
widget instances; use public plugin-ui `WidgetSurface` to embed a declared native
page area, or a declarative `widgetArea` node. Hosted HTML pages manage widgets
through ordinary widget Actions without embedding host areas. The generated
[host Action reference](/plugins/api/host-actions) supplies
the exact schemas, while [personal widget areas](/plugins/ui/react-native#personal-widget-areas-in-development)
explains the component's host-owned layout and context.

`session.presentation.apply` and the optional daemon `context.ui.present`
capability expose reversible presentation for the exact current Session. Their
public types arrange readable built-in, shared Board-item and pane references.
Direct Companion widget-instance payloads, input/rename intents and conditional
instance-removal captures are host-internal; author widget operations use the
qualified widget Actions instead. This author subset shares the host's
validators and current-viewer admission. It supplies neither another window's
presentation owner nor additional read or write authority.

These are 0.3 development / Developer Preview contracts. Consult the generated
[SDK surface](/plugins/api/surface) and [availability matrix](/plugins/manifest/availability)
for your artifact's public projection and support evidence.

### Authority comes from the invocation, not from Session content

Your plugin's authority is the principal the host admitted for this invocation.
It does not change with the conversation. If two collaborators take turns sending
input to the same Session, the runtime keeps the same stamped principal
throughout: the latest message author is correlation for the turn you are
serving, not a credential, and no `requestedBy`-style field, quoted selection, or
source identifier delegates that person's Account or lends you their private
settings. Every operation is still checked against the Action's declared surface,
its required caller authority, and current resource access at the moment it runs.

Host operations that write into a Session record the actual admitted execution
Account together with Agent producer provenance, so an Agent-made post reads as
Agent-produced rather than as a message from the person who asked for it. Public
Account HTTP cannot forge that provenance. Idempotency, creator-only affordances,
and erasure all follow the stored identity, and asking an Agent to post creates no
personal involvement or subscription for the requester.

Two boundaries this does not move. Confirmation and authorization stay separate —
an approval or an explicit user waiver satisfies a confirmation requirement and
never supplies missing Session access, surface enablement, or endpoint consent.
And conversation attribution is not a filesystem boundary: a Session's
attribution, selected folder, or discussion scope does not contain broad shell
access. The OS and Agent sandbox configuration the user already runs is the actual
containment, and a plugin cannot widen it.

Reach all of this through the public SDK seam — `context.services.*` and the
`activate(api)` ABI. Do not import host internals to make a first-party example
work; an installed external plugin has the same trusted surface, so anything that
needs a host-internal import is a missing SDK contract to raise, not a shortcut
to take.

When `session.spawn_new` should create or reuse a Git worktree, pass the public
`checkoutCreationDraft` projection with the rest of the authored Session input:

```ts
checkoutCreationDraft: {
  kind: 'git_worktree',
  displayName: 'review/42',
  baseRef: 'main',
  branchMode: 'new',
}
```

The host sends that projection through the same canonical Session target
preparation used by the first-party new-Session flow. Plugin authors do not
resolve checkout paths themselves and do not receive the host's internal spawn
options or directory-approval evidence.

## Tools

Tools expose plugin actions to tool-capable surfaces. The manifest owns tool metadata and references the action that supplies executable behavior; tools do not have a second runtime registration path.

Use tools when the operation is meant to be called by agents or MCP-compatible tool clients.

> **Development status:** Tools are available in the current source contract.
> The capability matrix records loaded-platform and release evidence separately;
> do not treat an unrecorded loaded proof as a published release claim.

### Worked tool example

Declare the tool under `contributes.tools[]`. The `surfaces` list makes it available to agent/tool surfaces, and the handler target points at the runtime registration id.

```json
{
  "contributes": {
    "tools": [
      {
        "id": "notes-add",
        "name": "session_notes_add",
        "title": "Add session note",
        "description": "Store a note for the current plugin.",
        "surfaces": ["agent", "mcp"],
        "inputSchema": {
          "type": "object",
          "additionalProperties": false,
          "properties": {
            "note": { "type": "string" }
          },
          "required": ["note"]
        },
        "action": "notes-add"
      }
    ]
  }
}
```

Define the referenced action in the same `definePlugin(...)` declaration. Action
handlers receive JSON-safe input and a `PluginInvocationContext` with
plugin-scoped services.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.notes',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    'notes-add': {
      title: 'Add session note',
      execution: { target: 'daemon' },
      run: async (input, context) => {
        const note = String((input as { note?: unknown }).note ?? '');
        const existing = await context.services.storage.daemon.get<string[]>('notes');
        const notes = [...(existing ?? []), note];
        await context.services.storage.daemon.set('notes', notes);
        context.services.logger.info('Stored session note', { count: notes.length });
        return { note, count: notes.length };
      },
    },
  },
});
```

## Commands

Commands expose CLI-facing entries. Command declarations specify their path, visibility, availability, and canonical action reference; they do not register a parallel command handler.

> **Development status:** Command declarations and canonical host-catalog
> wiring are available in the current source contract. The capability matrix
> records loaded-platform and release evidence separately; do not treat an
> unrecorded loaded proof as a published release claim.

### Current-UI commands

The current-UI contract keeps contextual commands as data, not callbacks. A
mounted surface may contribute bounded presentation and
one existing semantic command: either `executeAction` or `openSurface`. Voice
and other readers see only a snapshot-scoped opaque command id plus its title
and optional description; the executable payload stays local to the client.

Immediately before execution, the client re-reads its current snapshot and
resolves that opaque id again. A changed selection, retired surface, stale
occurrence, or unknown id produces no effect. This preserves the existing
Action and navigation owners instead of creating a screen-specific Voice
handler or callback registry.

The mounted publication contract is documented under
[Plugin UI](/plugins/ui#publish-mounted-semantic-context).

## Approvals

Dangerous actions should declare danger level and confirmation metadata in the manifest. Runtime approvals should use the host action approval service instead of prompting through agent-specific side channels.

Approval is one policy decision, not authority. The host still checks the
Action's declared surface, required caller authority, current resource access,
endpoint consent, and the Account's Action setting. A waiver can skip the
confirmation step where policy permits; it cannot grant missing Session access
or turn an automation caller into a present user.

When a person runs an Action from Happier's own UI or from Voice, Happier asks
for confirmation once, in the app, before the Action is sent, whether the Action
runs on the client or on a daemon. It asks when the Action is not `safe`, or
when the person set that Action to **Ask first**. The dialog uses the Action's
declared `confirmation` wording, or its title and description when it has none.
Declining sends nothing and leaves no pending approval. Agents, MCP clients, the
CLI, the public API and automations are not present in the app, so their
requests for the same Action create an approval request instead.

For a deferred approval, the host records the immutable admitted execution
origin before it asks. Applying the decision later revalidates current policy
and resource access and replays with that original Action, caller authority,
Home, and target. The person who approves does not replace the original caller
or retarget the operation. Historical approval records that lack sufficient
origin evidence remain readable but are not executable.

These shared rules apply equally to host Actions called by built-in and
externally installed trusted plugins. Trust admits the plugin to the same public
host Action service; it does not bypass per-Action settings, approval, or domain
authorization.

## Design rules

- Keep operation identity in the manifest.
- Keep executable code in handlers.
- Keep invocation surfaces independent from the single execution target.
- Keep user-facing placement and availability descriptor-driven.
- Do not create parallel RPC handlers for operations that fit the action model.
