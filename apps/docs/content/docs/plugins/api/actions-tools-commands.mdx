description: Declare executable operations, their invocation surfaces, and their execution target.

Declare an operation once as an Action. Its optional `tool` and `cli` fields give
that same operation a named tool and a friendly CLI path.

## Actions

Declare actions and their handlers together with `definePlugin(...)`.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.echo',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    echo: {
      title: 'Echo',
      execution: { target: 'daemon' },
      run: async (input) => ({ input }),
    },
  },
});
```

Action handlers return JSON-safe values. Throw a typed plugin error when the operation cannot complete:

```ts
import { PluginError } from '@happier-dev/plugin-sdk';

throw new PluginError({
  code: 'notes.invalid_input',
  retryable: false,
});
```

### Plugin subject identities (0.3 development source)

Declare domain identities, such as tickets, in `definePlugin({ subjectKinds: ... })`.
Each keyed descriptor supplies `label`, optional `icon`, a recursively closed
`identitySchema`, and `listAction`, the local id of an ordinary same-plugin
read-only Action. Use `PluginSubjectKindListInputV1Schema` and
`PluginSubjectKindListResultV1Schema` from `@happier-dev/plugin-sdk/automations`:
the requested page is `{ query?, limit?, cursor? }` and the result is
`{ items: [{ identity, label }], nextCursor: string | null }`.
The read Action owns pagination; Happier forwards a limit only when the caller supplies one.

An effectful Action identifies its operand through its existing `approvalScope`:
`{ kind: 'plugin', subjectKindId: 'ticket', identityField: 'ticket' }` reads the
identity from the `ticket` field of its input. The host validates that identity
against the declaring kind. Subjects are qualified by Home, plugin id and local
kind id; equal ticket ids in another plugin or Home remain separate. Plugin
subjects are owner-only, including when their Workflow is shared.

### Scheduled and Event-driven Actions (0.3 development source)

The existing Automation API accepts a contributed Action as its execution
recipe. Use this recipe in `POST /v3/automations`, alongside the existing Machine
assignments and schedule or plugin Event triggers:

```ts
const executionRecipe = {
  v: 1, templateVersion: 1, triggerEvidence: null,
  target: {
    kind: 'contributedAction',
    action: { pluginId: 'com.example.jobs', localId: 'refresh' },
  },
  template: {
    t: 'plain',
    v: {
      v: 1, prompt: '',
      actionInput: { kind: 'literal', value: { project: 'demo' } },
    },
  },
};
```

For plugin Event triggers, `actionInput: { kind: 'eventPayload' }` passes the
admitted occurrence's payload. Webhook delivery reaches the same path through
the plugin's existing Event admission. Literal inputs also work for Events.
E2EE Accounts encrypt the template with the existing Account-scoped
`automation_template_payload` envelope; the plaintext example is for plain
Accounts only.

The server schedules and freezes each occurrence; an assigned Machine invokes
the ordinary Action executor with Automation Run provenance. The Action retains
its declared placement, schema and approval policy. A client-only or missing
executor produces a visible typed failure. An Action that defers to present-user
approval reports `approval_required`, rather than reporting an unexecuted effect
as successful. Reclaim preserves the frozen recipe;
it does not promise exactly-once external effects. Cancellation aborts the local
Action signal; a running effect may retain an uncertain outcome. Workflow
recipes continue through their existing coordinator. This is an unreleased
0.3 development API; the Workflow editor remains a Workflow authoring surface.

### Work Item transitions (0.3 development source)

When a `workItems` contribution names a `transitionAction`, declare that Action
with the public SDK's canonical input schema:

```ts
import { PluginWorkItemTransitionInputV1Schema } from '@happier-dev/plugin-sdk';

const inputSchema = PluginWorkItemTransitionInputV1Schema;
// Use inputSchema on the named Action. Its handler receives exactly:
// { serverId: string, itemId: string, transitionId: string }
```

The schema is composable and rejects extra operands before the handler runs.
The Action keeps its ordinary execution target and approval policy. This is an
unreleased development contract; check the generated SDK API for your toolchain.
Live Work Item `resolve` and `findLinked` callbacks receive the portable Account
Action context. `watch(request, onChange, context)` receives that same context
as its third argument; use `context.signal` to retire pending observations.

### Input hints (0.3 development source)

Declare the exact `inputSchema` once. In current development source, the Action
catalog derives hints for uncovered top-level fields, including readable titles,
required fields, primitive controls and string-enum choices. Structured values,
unions and opaque fields use a JSON editor. Root-object union fields are required
only when every arm requires them. The schema still validates the complete input.

Use `inputHints` to add meaningful labels, localized copy, semantic choices,
conditional fields and consequence descriptions. Authored fields keep their
order and take precedence; a nested authored field also suppresses a generated
editor for its parent object while uncovered siblings receive their own hints.
Confidential paths still require an explicit
`secret` widget; field names never establish confidentiality. Literal dotted
property names and non-object roots do not fit the existing field-path grammar.
These hints support discovery and form consumers; they do not make an Action
automatically request MCP elicitation or change its approval policy.

Provisioner options Actions can declare `role: 'cpu' | 'memory' | 'disk'` on
numeric size fields. Saved configuration receipts and preset offers use these
roles to describe size without interpreting field names. CPU values are cores;
memory and disk values are GiB, or bytes when the field declares `unit: 'bytes'`.
For example, `{ path: 'ram', title: 'Memory', widget: 'integer', role: 'memory',
unit: 'bytes' }` describes a byte-valued memory choice. Older declarations without
roles retain their ordinary saved-choice presentation.

If your Action opens its own editor, declare exactly `inputHints: { fields: [] }`
to omit the host input form. Hints containing only a form title, description or
submit label still derive fields. The input schema continues validating operands
supplied by programmatic callers.

### Exact deployment Artifact reads (0.3 development source)

Deployment Environment and receipt reads return headers, not their private
content. In unreleased development source, open the referenced Artifact through
the ordinary host Action and validate its exact id, header/body revisions and
kind before selecting a deployment-owned field:

```ts
import {
  DEPLOYMENT_ENVIRONMENT_ARTIFACT_KIND_V1,
  ProtocolArtifactGetOutputV1Schema,
  ProtocolDeploymentPreviewProvenanceV1Schema,
  readDeploymentArtifactJsonBodyV1,
} from '@happier-dev/plugin-sdk/protocol';

const opened = ProtocolArtifactGetOutputV1Schema.parse(
  await context.services.actions.execute(
    'artifact.get', { artifactId: environment.contentArtifactId },
    { signal: context.signal },
  ),
);
const content = readDeploymentArtifactJsonBodyV1(
  environment, opened.artifact, DEPLOYMENT_ENVIRONMENT_ARTIFACT_KIND_V1,
);
if (!content.ok) return;
const body = content.body;
if (typeof body !== 'object' || body === null || !('previewProvenance' in body)) return;
const provenance = ProtocolDeploymentPreviewProvenanceV1Schema.safeParse(body.previewProvenance);
if (!provenance.success) return;
```

These values project the same canonical deployment parsers; they do not grant
access, validate the whole Environment document, or establish current Source,
receipt, policy or URL authority. The caller must still admit those facts through
their owning host Actions. For receipt `sourceIntent`, use
`DEPLOYMENT_RECEIPT_ARTIFACT_KIND_V1` and
`ProtocolDeploymentSourceIntentV1Schema` after the same exact-reference check.
An unavailable or changed Artifact is not permission to use retained content.
Check the generated SDK API for the target toolchain; these source exports are
not a published release or a claim of loaded-runtime verification.

### Pinned fresh clones (0.3 development source)

When creating a new repository checkout with `scm.repository.clone`, matching
0.3 development host and SDK sources accept an exact initial `main` or detached pin:

```ts
import type { ScmRepositoryCloneInput } from '@happier-dev/plugin-sdk/scm';

// Reuse the reviewed provider, repository, destination and confirmation input.
const request = {
  ...reviewedCloneInput,
  initialCheckout: { branch: 'main', commit: reviewedCommit },
} satisfies ScmRepositoryCloneInput;
```

`reviewedCommit` must be a full Git commit id. The Git clone owner sets `main`
before publishing the new directory; an existing destination is refused.
Set `initialCheckout.branch` to `null` to check out that commit with a detached
HEAD instead. SCM callbacks implementing this input must return the observed
`branch.headOid` and `branch.detached` in the normal snapshot, together with the
branch name for an attached checkout. The observed commit and attached or
detached state must match the request. An ignored pin returns `SCM_SOURCE_CHANGED`;
missing head evidence returns `COMMAND_OUTCOME_UNKNOWN`. The failure retains
`destinationPath` when a checkout was created: inspect that checkout before
retrying. Omitting `initialCheckout` keeps ordinary clone behavior. This is an
unreleased source contract; check the generated API for your target toolchain.

For `projects.open` with clone materialization, a full commit `ref` selects this
detached checkout when no explicit `initialCheckout` is supplied. If checking out
a branch ref after cloning returns a known terminal failure, Open returns
`kind: 'refused'` with the SCM failure in `code` (for example, `COMMAND_FAILED`)
and an optional canonical `failureCause` whose `phase` is
`project_open.checkout_ref`. Its nested `errorCode` can be `null`; read the outer
`code` for the SCM result. An uncertain Account acknowledgement or worktree
effect still returns `kind: 'outcomeUnknown'`.

### Session targets (0.3 development source)

Declare `sessionTarget: { field: 'sessionId', cardinality: 'one' }` on an Action
whose input names a Session. Keep the handler's input schema exact, such as a
string `sessionId`: the host resolves selectors before validating that input or
entering the handler. Use `cardinality: 'many'` when the Action can run once per
selected Session. The declaration's field must identify an operand in the
declared object input schema.

Discovery advertises this declaration for installed plugins. Inspect a target
with `session.targets.resolve`, passing the Action's qualified discovery id
(`com.example.plugin/actions/inspect`) and `target`, for example
`{ selector: 'workers' }`. Invoke it through `action.invoke` with
`action: { pluginId: 'com.example.plugin', localId: 'inspect' }` and the selector
in `input.sessionId`. Exact Session ids continue to work.

The host refuses a one-target expansion that selects several Sessions.
A restricted Session caller stays within its proved subtree: safe reads can
address its children while writes retain their existing restrictions. Missing
selector backing returns an unavailable result. Approval retains the concrete selection, so
membership changes do not add recipients on replay. Selecting a Session grants
no additional access or mutation authority. This describes unreleased 0.3
behavior; use the generated API and availability references for your target
toolchain.

In current 0.3 development source, declare
`confirmationWhen: { presentUserUi: false }` for a reversible operation that
people invoke in your UI, such as completing or reopening an item. The scoped
value also accepts an input predicate when the consequence depends on the input.
Keep accurate `dangerLevel` and `confirmation` wording: Agent, MCP, API,
Voice and automation routed through UI retain their normal defaults. A flat
input predicate in `confirmationWhen` instead controls the default on every
surface. CLI `writesLocal` Actions default to Direct unless an applicable
`cli`, `default`, or flat input predicate declares confirmation. Use
`confirmationWhen: { presentUserUi: false, cli: true }` when a local operation
has a consequence that still needs CLI review. Destructive and outward
operations, and confidential reads with confirmation metadata, retain Ask.
The person's explicit Ask setting takes precedence. Approval waivers change
prompts, not the caller's execution authority.

Prefer stable error codes over parsing text. See
[Diagnostics](/plugins/testing/diagnostics) for the public guard and the
diagnostic workflow.

In **unreleased 0.3 development source**, host Action discovery includes optional
`permissionChanging: true` metadata for effects that change permission policy.
Use this value for disclosure when presenting an Allowed preference; do not infer
it from the Action id, title, danger level or confidential fields. Missing means
false. Mixed Settings Actions are classified by their canonical declaration: a
whole-Action preference covers permission-changing settings, while an admitted
ordinary setting does not. The host resolves input-dependent metadata; discovery
never carries its executable resolver.

For example, a plugin that presents discovered host Actions can read the public
SDK result without maintaining its own sensitive-Action list:

```ts
import type { DiscoveryActionResultById } from '@happier-dev/plugin-sdk/actions';

function changesPermissions(result: DiscoveryActionResultById['action.spec.get']) {
  return result.actionSpec.permissionChanging === true;
}
```

This flag does not grant authority, make approval nonwaivable, or replace the
host's effective approval decision. A scope preference changes confirmation only;
the host admits the actual Machine or Environment scope. Restoring Ask first must
target that same Action, audience and scope, leaving neighbouring preferences
unchanged. Older hosts may omit this development metadata.

In **unreleased 0.3 development source**, an Action's single host confirmation
can include reviewed input operands alongside its static consequence:

```ts
confirmation: {
  title: 'Merge this pull request?',
  body: 'This merge cannot be undone.',
  inputFields: [
    { path: 'skippedRequirements.[].label', title: 'Skipping' },
  ],
}
```

Each path must resolve in the Action's declared input schema. Use dot-separated
paths and `[]` for array members; a path may belong to only one input union arm.
Titles accept the same literal or `{ key, fallback }` text as other Action
declarations. The host reads values from the admitted input bound to this
confirmation, using its existing approval operand presenter. Missing operands
add no line. Declared confidential values stay redacted. This works through the
same native and hosted UI Action path; no plugin dialog or executable text
template is needed. The public `ActionConfirmationInputField` type is available
from `@happier-dev/plugin-sdk/actions`. Check the generated API for the target
SDK/host before using this declaration; older strict declarations reject it.

For a person's button that prepares current input, use
[`Action.Control`](/plugins/ui/react-native#host-rendered-action-controls-03-development-source).
Its host gesture invokes the Action with person authority; raw plugin calls and
`Action.Execute` retain plugin automation authority. The same reviewed operands
and explicit Ask policy still apply. Return `null` from preparation to cancel,
honor its signal, and preserve the settlement envelope: pending approval or an
accepted operation is not completion, and unknown acceptance must not trigger
an automatic replay. This host-control API is unpublished 0.3 development work.

For a mounted UI that writes Account KV or Collections directly, current 0.3
development source provides `hostApi.admitAction(action, input, { signal })`.
Await it before calling your existing domain writer. It returns `false` when
the person declines, rejects an Off Action with `denied`, and rejects cancelled,
retired or unavailable requests. Run the writer only after `true`, using the
same signal. Account authorization, validation and conflict handling stay with
that writer, and no daemon needs to be reachable.

This operation checks the Action's conservative default when a condition would
require validated input; it never treats unvalidated JSON as a confirmation
waiver. Check the host's advertised methods before offering the operation on
older hosts: a missing `admitAction` rejects with `unsupported_method`. Ordinary
`confirm` is presentation, not a substitute for this Action admission.

Secret-bearing Action inputs must declare each confidential path in
`inputHints.fields` with `widget: 'secret'` and a readable `title`, including
inputs exposed only to CLI, MCP or Agents. A top-level `secrets` declaration
names stored secrets; it does not mark an Action input confidential.

Plugins are [trusted code](/plugins/security/trust-model). In current development
source, the host keeps declared-secret raw values out of approval Artifacts,
Workflow progress and journals, replay input and approval presentation. Host-run
diagnostic projections withhold values at or below confidential paths from both
raw and normalized Action input, including issue-path suffixes of any JSON type.
This covers parser issues, `PluginError` details, failure data and structured log
fields. Plugin-authored free text receives best-effort string-secret scrubbing.
As an author, you are responsible for deliberate re-encoding of secrets in your
own prose or as unrelated non-string values; keep diagnostics at their declared
paths and never publish secrets in results.

In current development source, approvals for declared-secret inputs or
SecretString carriers keep the raw input only in the waiting invocation.
The approval Artifact contains a redacted projection, confidential field labels
and the exact public operands. Approval can continue that live invocation;
after it retires, replay returns `approval_stale` and the caller must submit a
new invocation. Inputs without confidential values return
`approval_request_created` with an Artifact id immediately to CLI, MCP, Agent and
API callers. Read the request with `approval.request.get {artifactId}` and decide
it through `approval.request.decide`; replay revalidates the original input,
policy and execution origin. While a confidential invocation waits, another
invocation can find it with `approval.request.list {status: 'open'}` and read the
same redacted request. Reading an approval does not grant permission to decide it.
Do not infer confidentiality from a field's name or copy secrets into labels,
summaries, progress or results.

In current 0.3 development source, contributed Action calls through
`executeWithExecutionOrigin` or
`executeAdmittedTargetedOperationWithExecutionOrigin` can supply the closed
`expectedExecutionRouting` option: `{ serverIdentityId, machineId, pluginId }`.
The host compares it with the resolved target before running the handler; it
is an equality precondition, not a target selector or Action input. Use this
when retained configuration follows the current admitted plugin on one Home
and machine. `getPluginMachineExecutionRouting` projects a host-stamped origin
and `arePluginMachineExecutionRoutingsEqual` compares routes through the shared
owner. A mismatch returns `plugin_action_execution_origin_mismatch` before
handler effects. The returned `executionOrigin` is the origin admitted before
the handler ran: if the target is replaced while it runs, you still receive the
handler's result, and a later call that expects the replaced origin is refused
before effects. The existing `expectedExecutionOrigin` option keeps its full
exact-custody meaning for operations that require it, including approval
continuation.

### Prepare a catalog app (0.3 development source)

Implementation is incomplete: the typed SDK projection has not been published,
and signed Project-defaults reads and the mounted UI entry still have open
validation gates. The example below describes the intended caller contract,
not an available SDK API.

Pass the exact pinned app reference from the catalog reader, together with the
selected Project Source revision and Machine installation, through the host
Action service:

```ts
import type { ActionsService, DeploymentsActionInputById } from '@happier-dev/plugin-sdk/actions';

function prepareCatalogApp(
  actions: ActionsService,
  input: DeploymentsActionInputById['deployments.publish.prepare'],
) {
  return actions.execute('deployments.publish.prepare', input);
}
```

This unreleased read returns an inert draft: the catalog's native variable,
domain and first-run declarations, plus creation defaults and their provenance.
It neither applies the template nor creates resources, secrets or deployment
records. Team Projects do not inherit personal Account defaults. A changed pin
or unavailable selection remains a refusal, not an invitation to substitute the
latest version. Check the host's advertised Actions before offering the entry;
the later Publish operation retains its independent review and approval.

### Stop a deployment rollout (0.3 development source)

Use the existing host Action service with the exact receipt revision you read:

```ts
import type { ActionsService, DeploymentsActionInputById } from '@happier-dev/plugin-sdk/actions';

function stopRollout(
  actions: ActionsService,
  receipt: DeploymentsActionInputById['deployments.cancel'],
) {
  return actions.execute('deployments.cancel', receipt);
}
```

This unreleased Action needs current Source deployment permission and follows
the host's Environment-scoped approval policy. Handle approval deferral before
reading the domain result, just as for other host Actions. It can record the
cancellation while the controller is offline: the receipt becomes
`outcome_unknown` without rewriting its recorded member evidence or undoing
native effects. A successful response is not proof that a process stopped.
Stale receipt revisions refuse; read current state before deciding what to do
next. See the generated [host Action reference](/plugins/api/host-actions) for
the target toolchain's inputs and results.

### Deployment handoffs and native reads (0.3 development source)

The generated deployment family includes typed Publish and repository-Prepare
handoffs. Submit the reviewed input through the same host Action service:

```ts
import type { ActionsService, DeploymentsActionInputById } from '@happier-dev/plugin-sdk/actions';

function prepareRepository(
  actions: ActionsService,
  input: DeploymentsActionInputById['deployments.prepare'],
) {
  return actions.execute('deployments.prepare', input);
}
```

This is an **unreleased registration contract**, not a complete deployment
workflow. Hosts without the corresponding composer, workspace handoff or admitted
native reader return an unavailable or unsupported result. Keep that result
visible; do not substitute another Machine or repeatedly resubmit the Action.
The generated [host Action reference](/plugins/api/host-actions) owns the exact
input and result shapes for the target toolchain.

Publish and Prepare retain default Agent approval and the host's current
configurable policy. Prepare returns Session/child-operation references when
handoff succeeds; that is not proof that source changes were completed, merged
or deployed, and does not approve later Session or SCM writes. Publish's reviewed
parent host is separate from the Environment controller, builder and runtime.

The health, drift and log read Actions are safe reads, with no approval by default
and configurable Environment-scoped policy. Use the exact receipt, target,
Machine installation and stable service identity supplied by their owners.
Native reader authorization and redaction must be available before disclosure;
missing observations remain unknown, and unavailable log redaction remains
unavailable. Registration does not supply those runtime producers or authorize
a probe, scan or repair.

## Choose where a plugin runs

In 0.3 development source, **Run on** remembers a Machine on the answering
device, separately for each Account and Home. UI, Agent, MCP and CLI callers use
the same `plugins.execution_origin.list`, `.set` and `.clear` Actions. List the
admitted origins, pass one exact `origin` to set, or clear the local preference;
no Account settings version is required. In 0.3 development, list returns
`answeringClientId` and eligible `answeringClientIds`; pass an id as `clientId`
to address that exact connected app from CLI or MCP. Reads, set and clear use
the same client-choice rule: without `clientId`, use the sole eligible app or
the app with the unique most recent focus transition observed through the
existing focus push. Missing or tied focus
history returns `client_ambiguous` with candidate ids in `details.clients` and
the `clientId` remedy, before an app executes the Action. A disconnected or
ineligible exact id returns `client_not_available`; it never selects another
app. Ids expire on reconnect. Only the answering device's choice changes.

That optional selector also applies to other client-routed host Actions in 0.3
development. For a contributed client Action, put `clientId` alongside `action`
and `input` in the host `action.invoke` envelope, not inside the plugin's
business input. Non-client contributed Actions refuse that selector with
`client_routing_not_applicable`.

An explicit unavailable Machine remains named and its operations stay blocked.
Clear it or choose an available Machine to change where effects run. Without an
explicit choice, Happier automatically picks an online admitted Machine in the local
Home after its Machine list completes. It prefers the rendered release's version,
then the Machine last used for this plugin on this device, this device's own
Machine when known, and the most recently active eligible Machine. If an automatic
pick becomes unavailable, Happier picks again. List results report
`selectionSource` as `auto`, `pinned`, or `null` when no Machine is selected.
The remembered choice does not pin a source directory or code version:
each operation resolves the Machine's current admitted source. Session panels
retain their separate mounted contextual choice.

If your plugin's work depends on choosing a particular Machine, declare
`executionTarget: { autoPick: false }` in `definePlugin(...)`. This optional
manifest field defaults to automatic selection when omitted. With `false`, a
sole eligible candidate is still automatic, and several candidates ask the user.
The existing `default: 'installation'` hint may share the same object. Target a
host that admits this declaration through the SDK's engine compatibility contract;
older strict manifest parsers reject it rather than ignoring placement policy.

## Keep a long daemon Action visible in Activity

> **Development status:** Tracked plugin Actions are part of the current
> Developer Preview contract and have not shipped in a public Happier release.

A daemon Action can opt into a host-owned operation view. The user may
**Collapse** the running view, navigate elsewhere, and reopen it from Activity
without cancelling or starting the Action again.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

async function indexFile(path: string) {
  await Promise.resolve(path); // Replace with the plugin's real indexing work.
}

export const { manifest, activate } = definePlugin({
  id: 'com.example.indexer',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    'rebuild-index': {
      title: 'Rebuild index',
      execution: { target: 'daemon' },
      operation: {
        version: 1,
        visibility: 'activity',
        progress: 'reported',
        presentation: { onStart: 'current' },
      },
      async run(_input, context) {
        context.operation?.update({
          phase: 'discovering',
          label: 'Discovering files',
        });

        const files = ['notes.md', 'decisions.md'];
        for (const [index, file] of files.entries()) {
          await indexFile(file);
          context.operation?.update({
            phase: 'indexing',
            label: 'Indexing files',
            current: index + 1,
            total: files.length,
          });
        }

        return { indexed: files.length };
      },
    },
  },
});
```

`presentation.onStart` is required and states what the invoking surface does
the moment the host accepts the operation. `current` keeps the user exactly
where they are and lets them collapse the running view themselves; `detail`
opens the operation detail view immediately; `activity` collapses the
invoking surface so the work continues in Activity. It does not change
custody: the daemon owns the operation in every case.

Use `progress: 'indeterminate'` when the handler cannot report honest phases
or bounded numeric progress. For `reported` progress, `update(...)` accepts an
optional bounded `label` and `phase`, or finite non-negative `current` and
`total` values where `total` is greater than zero and `current <= total`.
Invalid updates are rejected by the host. `context.operation` is
invocation-scoped and optional, so the handler can keep its existing terminal
execution behavior when invoked through a surface that does not provide a
tracked-operation reporter.

The host, not the plugin, owns `accepted`, `running`, and terminal lifecycle
transitions. Returning the validated Action result succeeds the operation;
throwing fails it; host-owned cancellation uses the invocation signal when
supported. There is deliberately no `complete()` or `fail()` API.

Tracking requires a daemon Action (a root `run` handler); a client-targeted
Action cannot declare `operation`. Once accepted, tracking survives modal close,
navigation, ordinary reconnect, and browser visibility changes while the same
daemon process remains alive. The operation history is held in daemon memory,
so daemon restart may make its status unavailable. It is not an offline queue,
durable job store, restart-replay mechanism, or exactly-once guarantee.

The operation snapshot does not retain raw Action input, form drafts, tokens,
credentials, attachments, or arbitrary plugin state. Keep secret input in the
ordinary invocation only, and never copy it into progress labels or results.
Existing public HTTP and generated SDK Action execution still wait for and
return the terminal Action result; the tracked accepted receipt is not a new
public HTTP/SDK response shape.

The maintained source example is
[`examples/tracked-action`](https://github.com/happier-dev/happier/tree/v0.3/packages/plugin-sdk/examples/tracked-action).

## Invocation surface and execution target

An Action is declared and implemented once. Actions are discoverable to Agents
and MCP clients by default, subject to the canonical per-Action exposure policy.
Optional `tool` and `cli` metadata customizes named entry points; neither is a
prerequisite for generic Action discovery. Invocation exposure and the execution
target, which says where the one handler runs, are independent decisions.

The canonical default for Agent/MCP exposure is `discoverable_only`: callers
can find an eligible Action with `action.spec.search` and `action.spec.get`,
then invoke it through `action_execute`. To request a direct tool, set
top-level `toolExposure: { agent: 'direct', mcp: 'direct' }` on the Action.
This per-surface override also accepts `discoverable_only` for `agent`, `mcp`,
and `cli`. The person's per-Action settings and current availability still
apply, and exposure does not waive approval or grant authority.

The **External API & SDK** surface is host-owned rather than author-declared.
Every installed daemon Action participates in API discovery and dynamic
invocation through its qualified `<pluginId>/actions/<localId>` identity,
subject to the Account's setting for that exact Action. For those daemon
Actions, an author-declared `surfaces` list neither grants nor removes API Token
access. Client-target Actions remain local to the invoking client and are not a
daemon Action API fallback.

Adding another invocation surface does not create another handler. Every
admitted surface resolves the same current declaration and its one registered
target handler through the canonical dispatcher.

- A root `run` handler without explicit execution makes a daemon Action: `definePlugin` emits
  `execution: { target: 'daemon' }` for it, so you do not write that field.
  The Action runs through the daemon Action executor.
- `execution: { target: 'client', ... }` names one exact client artifact,
  module, export, and supported platform list. A client Action has no `run`.
- In 0.3 development source, `execution: { target: 'account', account:
  { artifactId, exportName } }` names one portable Account handler. Its root
  `run` binds through `activateAccount`; the same handler can run from a UI or
  an authenticated headless host without acquiring Machine services.
- Omitted `scopes` default to `['global']` and omitted `dangerLevel` defaults
  to `'safe'`; declare them only when an Action differs.
- `host` is not a public plugin target; canonical host ActionSpecs keep their
  existing host executor.
- `surfaces` may include `ui`, `plugin`, `voice`, `agent`, `mcp`, or `cli`.

A daemon target's `run` handler is bound by the root module's generated
`activate(api)`. A client target has no root `run`: its exact client artifact
exports the ordinary named `activate(api)` function and registers the same
local Action id with `api.actions.register(...)`. That client API exposes only
Action and Voice registration, not daemon services or daemon contribution
families.

A client target is client-local: it is intended to execute in the exact web,
iOS, or Android process that invoked it. Missing or retired local activation
must fail unavailable; it must not fall back to a daemon, move to another
client, or enter a cross-client queue.

Account handlers receive `PluginAccountActionContext`: Account storage,
settings, targeted contributions and the ordinary Action service. The host may
also supply authenticated `accountScope` and admitted `sessionTargetsV1`.
In unreleased 0.3 CLI execution, optional `services.http` and `services.secrets`
project the existing admitted HTTP and declared-secret owners. Narrow both
members before using them; portable UI execution omits them. The projection
does not provide Exec or filesystem access. See [secret custody and HTTP
placeholders](/plugins/services/secrets#use-a-shared-reference-in-an-http-body).
These are invocation facts, never input-based authorization or an implicit
execution Machine. If a required fact is absent, refuse that operation rather
than borrowing the active Account or selecting another Session.

An admitted controller invocation in unreleased 0.3 CLI source can also supply
optional `services.machineConnectorSecrets`. After obtaining a connector token
inside the Account handler, call
`write({ token: bytes, subject: { provider, connectorId } })` and return only its
opaque `{ grants: [{ machineId, installationId, grantRef }] }`. The host captures
the controller, every receiving Machine and installation, receiver public keys
and admitted operation. Each receiver gets a separately sealed grant from the
same token acquisition. The token stays out
of Action input and results, Saved Secrets and logs. Zero caller-owned bytes
in `finally`; do not retain the sink or retry a write whose outcome is uncertain.
Portable UI execution and invocations without that admitted controller omit it.
See the maintained [Account author fixture](https://github.com/happier-dev/happier/tree/dev/packages/plugin-sdk/fixtures/account-actions).

For a selected Session, use `session.status.get` with its exact host-admitted
`sessionAddress`. Current development hosts may return `agentTarget` derived
from readable owner metadata; `includeAcceptedWorkspace: true` requests the
existing checkout proof. Older hosts may omit either proof. Do not infer an
Agent or checkout from presentation metadata.

For dynamic host Action data, `parsePluginHostActionInvocation(action, input)`
validates the identifier and input through the canonical plugin-surface schemas
before calling ordinary `services.actions.execute`. It grants no approval or
target admission. Separate `isPluginActionApprovalRequestCreated(result)` before
reading a domain result; an approval deferral is not a successful Session read.
Headless status reads return the public status contract, not a partial UI
`SessionStateV1`.

An Account handler's optional `ui` capability is present only for a finite UI
invocation, never a read observation. Use it for the ordinary compose/draft flow; headless execution must handle
its absence explicitly. Sending still uses the ordinary Session Actions and
their approval, cancellation and uncertain-result recovery. A portable handler
does not create a second launcher or waive Action policy. The maintained
development-source example is `accountActionAuthoring` in the public-authoring
SDK companion.

> **Development status:** The explicit `daemon | client | account` declaration is part
> of the current Developer Preview contract, whose implementation remains in
> progress, as is loaded web/iOS/Android certification. This capability has not
> shipped in a public Happier release.

For example, the root declaration names the exact client artifact without an
inline handler:

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.details',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    'open-details': {
      title: 'Open details',
      surfaces: ['ui', 'voice'],
      placementBindings: ['detailsPanel'],
      execution: {
        target: 'client',
        client: {
          artifactId: 'action-client',
          exportName: 'activate',
        },
        platforms: ['web', 'ios', 'android'],
      },
    },
  },
});
```

The declared artifact exports that one handler exactly once:

```ts
import type { PluginClientApi } from '@happier-dev/plugin-sdk';

export async function activate(api: PluginClientApi) {
  api.actions.register('open-details', async (_input, context) => {
    await context.ui.openSurface('details');
    return null;
  });
}
```

Expose that module through the package export matching
`execution.client.artifactId`; this target is executable client code and does
not need a `contributes.ui.renderers` entry:

```json
{
  "exports": {
    "./happier-plugin-ui/action-client": "./src/client-runtime.ts"
  }
}
```

Run `happier-plugin-build-ui --project-root .` to emit its one portable
CommonJS artifact. See [UI artifacts](/plugins/ui/ui-artifacts#build-contract)
for the export, output, and digest rules.

Client handlers receive a client-safe context, including cancellation,
invocation surface, plugin identity, current-UI context when available, and a
bounded `ui` capability for opening a surface or invoking another eligible
Action. The nullable `ephemeralSharedScope` can lease plugin-local in-process
state shared with mounted UI in the same Account and current plugin
occurrence. Use a versioned local key, handle a refused acquisition, and always
release the lease; do not replace a refusal with a global cache. Client handlers
do not acquire daemon services. Input schema
validation, availability, occurrence currentness, cancellation, danger
classification, confirmation, effect custody, and no-blind-retry rules remain
canonical for every surface and target. A client handler's result is trusted
plugin output: the host returns it as-is rather than re-validating it against
the declared `outputSchema`.

## Calling host Actions

### Review and accept Project setup (0.3 development source)

The unreleased Project setup contract uses the same host Action service.
`projects.inspect` with `reviewSharedSetup: { sourceId }` returns the proposed
effective definition, target-produced readiness and lifecycle review. Use
`projects.setup.set` to accept the exact reviewed selection, detach shared setup
or save personal overrides. Content acceptance preserves the private accepted
copy independently of later Source access and never grants execution consent.

`projects.prepare` owns execution consent. A human's **This time** or **Until it
changes** choice resumes the retained preparation operation with its reviewed
effect digest; an automation or plugin cannot self-grant remembered Trust. The
digest covers setup, teardown and executable autostart together, including teardown-only
definitions. Use the target's readiness result rather than inferring no effect
from an empty setup list or a missing review. An accepted update whose preparation
cannot continue remains an accepted copy with an unavailable consent result.

For names-only environment import, request `projects.inspect` with
`read: { kind: 'imports' }`. Its `environmentImport` contains requirements and
diagnostics from `.env.example`, never the example values. Keep existing
requirement classifications when adding missing names to a personal setup draft.
See [Projects and worktrees](/organize/projects-and-worktrees#shared-setup-03-development)
for the composition and lifecycle behavior, and [Host actions](/plugins/api/host-actions)
for the generated Action reference. Integrated validation remains in progress.

### Share plugin documents with a Team (0.3 development source)

Use `context.services.actions.execute('artifact.create', { header, body })` to
create an ordinary document, then `artifact.access.grants.set` with
`{ artifactId, principal: { kind: 'team', teamId }, accessLevel: 'edit' }`.
The [maintained Team Artifact example](https://github.com/happier-dev/happier/blob/dev/packages/plugin-sdk/examples/public-authoring/README.md#team-documents-through-artifacts-03-development-source)
includes author code and a composed source test for Plain and E2EE Accounts.

Check `isPluginActionApprovalRequestCreated` after each Action before starting
dependent work. Keep the document id if sharing defers for approval; do not
recreate the document. The recipient uses their own invocation's `artifact.get`
and `artifact.update`, preserving the read revision as `expectedRevision`.
The host owns encryption and recipient key delivery. Missing E2EE material
returns typed unavailable; a grant alone does not prove the recipient can open
the content. If the grant reports pending preparation, reopen as a key holder
to recover key delivery before claiming success. Private indexed state remains
in Account Collections; document access does not confer execution authority.

Bundled and externally installed plugins use this same service and dispatcher.
External plugins are not placed on a smaller Action allowlist: once the user
trusts the plugin, eligible host Actions are available according to the
Account's **Trusted plugins** Action settings. The host still stamps plugin
identity, occurrence, cancellation, and `account_automation` authority, so a
plugin cannot impersonate a present user or another plugin.

The generated root activation from a daemon `actions.<id>.run` binds a Plugin's
own manifest-declared handler (the low-level ABI method is
`api.actions.register(...)`). When a daemon handler needs an existing host
operation, call the same canonical Action through
`context.services.actions.execute(...)`; do not create a parallel RPC or
duplicate host handler. Use an exact action id from [Host actions](/plugins/api/host-actions), which is
generated from the canonical ActionSpec registry — so every id it lists is
reachable through `execute(...)`, and it cannot drift from the host. The owning
action contract remains the source of truth for behaviour; that page is the
index of what exists.

```ts
const result = await context.services.actions.execute('action.spec.get', {
  id: 'session.status.get',
}, {
  signal: context.signal,
});
```

The same call reaches another plugin's Action by its exact
`{ pluginId, localId }` reference. When that Action's handler throws a
`PluginError`, the rejection you catch carries the target's own `code`,
`retryable`, and published payload — see
[Diagnostics and errors](/plugins/testing/diagnostics#errors-across-a-plugin-to-plugin-action-call)
for what does and does not cross.

For Session input, prefer the typed Session service when you need the trusted
plugin authoring shape. Resolve the handle with
`await context.services.sessions.get(sessionId)`, then call `session.send(...)`.
It accepts the same optional Execution Run recipient as `session.message.send`,
plus manifest-declared Composer attachments and host-stamped source metadata.
The host qualifies the plugin identity and runs the ordinary attachment
preparation and dispatch lifecycle; plugin code does not manufacture those
trusted stamps. The public API Token/SDK Action keeps its intentionally smaller
strict input and rejects host-only `source`, attachment, or structured-launch
fields instead of accepting them as untyped JSON. That difference is an
authority boundary, not a smaller capability set for externally installed
plugins.

Omit the recipient to send to the main Session. A recipient of
`{ kind: 'execution_run', runId }` uses the Session's Pending queue and exact
Run admission. The separate `execution.run.send` host Action is only for a
detached Run with `sessionId: null`; it must not be used as a shortcut around
Session permissions, encryption, or target recovery.

### Prepare and confirm a deployment restore (0.3 development source)

In unreleased 0.3 development source, a backup restore uses the ordinary host
Action service. Prepare the restore with the reviewed capture receipt and
current target. Preparation returns the exact backup and destination evidence,
including any required safety snapshot, for review:

```ts
const selection = {
  serverId: 'home',
  environmentId: 'production',
  machineId: 'runtime',
  installationId: 'installed-runtime',
  targetLinkId: 'current-target',
  deploymentId: 'backup-capture-receipt',
  restoreBackupId: 'backup',
  expectedRevision: 3,
};
const prepared = await context.services.actions.execute(
  'deployments.backups.restore',
  { ...selection, mode: 'prepare' },
  { signal: context.signal },
);
if (prepared.kind !== 'prepared') return prepared;
```

After the person reviews `prepared.evidence`, offer a separate Confirm
invocation using the same selection and the returned operation id:

```ts
const outcome = await context.services.actions.execute(
  'deployments.backups.restore',
  { ...selection, mode: 'confirm', prepareOperationId: prepared.operationId },
  { signal: context.signal },
);
```

Both calls keep normal scoped Action approval. An `approval_request_created`
result belongs to the host approval flow; the plugin cannot approve itself.
Keep the prepared operation id for the later invocation. Do not send receipt
evidence back as input: the host reads it from the retained preparation.
See the generated [restore contract](/plugins/api/host-actions#deploymentsbackupsrestore)
for input guidance. This example requires matching development host and SDK
sources and does not describe a public release.

### Host Actions that run in a connected app

> **Development status:** Connected-app delivery for host Actions is part of
> the current 0.3 development source and has not shipped in a public Happier release.

Host Actions such as Find, Next and workspace tab controls execute through the
answering app's existing owners. An admitted Session Agent, MCP or daemon-hosted
caller can reach a connected app on its machine through the existing reverse
channel. The caller's authority, enabled invocation surface and required
approval are checked before delivery; the app keeps that authority and surface
when executing the admitted request.

The channel selects one eligible connected app using its existing routing rule.
An Action that names a Session, composer or mounted surface still needs that
exact owner on the answering app. With no connected handler, Find and the prompt
picker return `unavailable` with `reason: 'noClient'`, Next returns
`status: 'unavailable'`, and other Actions return an `unavailable` failure.
An older app that does not advertise the method is unavailable in the same way.
If a response is lost after dispatch, `outcome_uncertain` means the operation may
have run; the host does not automatically retry it.

CLI availability follows each Action's declared surfaces. An Action that enables
CLI still needs an eligible connected app to reach its mounted or device-local
owner.
Plugin-declared `execution: { target: 'client', ... }` Actions keep the separate
artifact and plugin-lifecycle contract described above. The generated
[host Action reference](/plugins/api/host-actions) identifies each Action's
declared invocation surfaces; declaration alone does not guarantee that its
required mounted owner is present.

Opening the OS file picker inside a standalone third-party embed is an explicit
parity exclusion. Choosing local files remains a human UI interaction; agents
attach files through the existing attachment Actions instead. Connected-app
delivery does not identify that standalone frame as a picker recipient. See
[embedded attachments](/extending/embed#appearance-and-controls).

### Widgets and current-Session presentation in development

Use qualified `widgets.*` host Actions to discover, configure and arrange
widget layout items; use public plugin-ui `WidgetSurface` to embed a declared native
page area, or a declarative `widgetArea` node. Hosted HTML pages manage widgets
through ordinary widget Actions without embedding host areas. The generated
[host Action reference](/plugins/api/host-actions) supplies
the exact schemas, while [personal widget areas](/plugins/ui/react-native#personal-widget-areas-in-development)
explains the component's host-owned layout and context.

In the unreleased 0.3 contract, `widgets.item.*` addresses placements, including
groups on Home and personal areas. Group operations use the same layout owner;
saved-group fragment operations create library content that is added as an
independent copy. The generated reference supplies their current schemas and
approval metadata. These source contracts do not claim a completed loaded UI
journey.

`session.presentation.apply` and the optional daemon `context.ui.present`
capability expose reversible presentation for the exact current Session. Their
public types arrange readable built-in, shared Board-item and pane references.
Direct Companion widget-instance payloads, input/rename intents and conditional
instance-removal captures are host-internal; author widget operations use the
qualified widget Actions instead. This author subset shares the host's
validators and current-viewer admission. It supplies neither another window's
presentation owner nor additional read or write authority.

These are 0.3 development / Developer Preview contracts. Consult the generated
[SDK surface](/plugins/api/surface) and [availability matrix](/plugins/manifest/availability)
for your artifact's public projection and support evidence.

### Authority comes from the invocation, not from Session content

[Public-profile publication](/accounts/public-profiles) has a consumed workflow
in unreleased 0.3 development source: preview, Publish, Update and facts-only
Refresh use the shared preparation and disclosure owners. First Publish reviews
the prepared public edition; later Apply and Undo use ordinary Action policy.
Publishing includes daily refresh, while explicit Ask or Off still suppresses
unattended execution. A private widget edit or generated snippet supplies no
publication approval. Consult the generated host Action reference for your
host's exposed operations. A feature-missing server cannot serve the workflow;
the public-eligible query must never fall back to private Usage. Supported skew
and native blocking Ask-result delivery remain integration checks.

Your plugin's authority is the principal the host admitted for this invocation.
It does not change with the conversation. If two collaborators take turns sending
input to the same Session, the runtime keeps the same stamped principal
throughout: the latest message author is correlation for the turn you are
serving, not a credential, and no `requestedBy`-style field, quoted selection, or
source identifier delegates that person's Account or lends you their private
settings. Every operation is still checked against the Action's declared surface,
its required caller authority, and current resource access at the moment it runs.

Host operations that write into a Session record the actual admitted execution
Account together with Agent producer provenance, so an Agent-made post reads as
Agent-produced rather than as a message from the person who asked for it. Public
Account HTTP cannot forge that provenance. Idempotency, creator-only affordances,
and erasure all follow the stored identity, and asking an Agent to post creates no
personal involvement or subscription for the requester.

Two boundaries this does not move. Confirmation and authorization stay separate —
an approval or an explicit user waiver satisfies a confirmation requirement and
never supplies missing Session access, surface enablement, or endpoint consent.
And conversation attribution is not a filesystem boundary: a Session's
attribution, selected folder, or discussion scope does not contain broad shell
access. The OS and Agent sandbox configuration the user already runs is the actual
containment, and a plugin cannot widen it.

Reach all of this through the public SDK seam — `context.services.*` and the
`activate(api)` ABI. Do not import host internals to make a first-party example
work; an installed external plugin has the same trusted surface, so anything that
needs a host-internal import is a missing SDK contract to raise, not a shortcut
to take.

When `session.spawn_new` should create or reuse a Git worktree, pass the public
`checkoutCreationDraft` projection with the rest of the authored Session input:

```ts
checkoutCreationDraft: {
  kind: 'git_worktree',
  displayName: 'review/42',
  baseRef: 'main',
  branchMode: 'new',
}
```

The host sends that projection through the same canonical Session target
preparation used by the first-party new-Session flow. Plugin authors do not
resolve checkout paths themselves and do not receive the host's internal spawn
options or directory-approval evidence.

## Tools

Actions already participate in generic Agent/MCP discovery. To expose an
additional named direct tool, put its presentation on the
Action's `tool` field; its handler, input and result schemas, input hints, safety,
availability, and approval policy remain owned by that Action.

Use tools when the operation is meant to be called by agents or MCP-compatible tool clients.

> **Development status:** Tools are available in the current source contract.
> The capability matrix records loaded-platform and release evidence separately;
> do not treat an unrecorded loaded proof as a published release claim.

### Worked tool example

For a named direct tool, declare `tool.name` and include `agent` and/or `mcp` in
the Action's `surfaces`, with `toolExposure` requesting `direct` for those
surfaces.
The tool can override its title and description and add examples,
`promptSnippet`, or `promptGuidelines`. Omitted presentation uses the Action's
title and description. The following declaration also gives the same operation
a CLI path:

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.notes',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    'notes-add': {
      title: 'Add session note',
      description: 'Store a note for the current plugin.',
      surfaces: ['agent', 'mcp', 'cli'],
      tool: { name: 'session_notes_add' },
      toolExposure: { agent: 'direct', mcp: 'direct' },
      cli: { path: ['notes', 'add'] },
      execution: { target: 'daemon' },
      dangerLevel: 'writesLocal',
      confirmation: {
        title: 'Add session note?',
        body: 'Store this note in the plugin\'s daemon storage.',
      },
      inputSchema: {
        type: 'object',
        additionalProperties: false,
        properties: { note: { type: 'string' } },
        required: ['note'],
      },
      run: async (input, context) => {
        const note = String((input as { note?: unknown }).note ?? '');
        const existing = await context.services.storage.daemon.get<string[]>('notes');
        const notes = [...(existing ?? []), note];
        await context.services.storage.daemon.set('notes', notes);
        context.services.logger.info('Stored session note', { count: notes.length });
        return { note, count: notes.length };
      },
    },
  },
});
```

## Commands

For a friendly CLI command, include `cli` in the Action's `surfaces` and put its
path on `cli.path`, as in the example above. Optional `cli.aliases` supplies
additional paths, `cli.visibility` chooses `default` or `advanced`, and
`cli.tmux` chooses `inherit`, `required`, or `forbidden`. The CLI uses the same
Action input and result schemas, input hints, availability, and approval policy.
There is no separate command handler or command contribution declaration.

> **Development status:** Command declarations and canonical host-catalog
> wiring are available in the current source contract. The capability matrix
> records loaded-platform and release evidence separately; do not treat an
> unrecorded loaded proof as a published release claim.

### Current-UI commands

The current-UI contract keeps contextual commands as data, not callbacks. A
mounted surface may contribute bounded presentation and
one existing semantic command: either `executeAction` or `openSurface`. Voice
and other readers see only a snapshot-scoped opaque command id plus its title
and optional description; the executable payload stays local to the client.

Immediately before execution, the client re-reads its current snapshot and
resolves that opaque id again. A changed selection, retired surface, stale
occurrence, or unknown id produces no effect. This preserves the existing
Action and navigation owners instead of creating a screen-specific Voice
handler or callback registry.

The mounted publication contract is documented under
[Plugin UI](/plugins/ui#publish-mounted-semantic-context).

## Approvals

Dangerous actions should declare danger level and confirmation metadata in the manifest. Runtime approvals should use the host action approval service instead of prompting through agent-specific side channels.

Approval is one policy decision, not authority. The host still checks the
Action's declared surface, required caller authority, current resource access,
endpoint consent, and the Account's Action setting. A waiver can skip the
confirmation step where policy permits; it cannot grant missing Session access
or turn an automation caller into a present user.

When a person runs an Action from Happier's own UI or from Voice, Happier asks
for confirmation once, in the app, before the Action is sent, whether the Action
runs on the client or on a daemon. It asks when the Action is not `safe`, or
when the person set that Action to **Ask first**. The dialog uses the Action's
declared `confirmation` wording, or its title and description when it has none.
Declining sends nothing and leaves no pending approval. Agents, MCP clients, the
CLI, the public API and automations are not present in the app, so their
requests for the same Action create an approval request instead.

For a deferred approval, the host records the immutable admitted execution
origin before it asks. Applying the decision later revalidates current policy
and resource access and replays with that original Action, caller authority,
Home, and target. The person who approves does not replace the original caller
or retarget the operation. Historical approval records that lack sufficient
origin evidence remain readable but are not executable.

These shared rules apply equally to host Actions called by built-in and
externally installed trusted plugins. Trust admits the plugin to the same public
host Action service; it does not bypass per-Action settings, approval, or domain
authorization.

## Design rules

- Keep operation identity in the manifest.
- Keep executable code in handlers.
- Keep invocation surfaces independent from the single execution target.
- Keep user-facing placement and availability descriptor-driven.
- Do not create parallel RPC handlers for operations that fit the action model.
