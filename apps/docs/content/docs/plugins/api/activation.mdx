---
title: Activation
description: Bind executable plugin behavior to manifest-declared local ids.
---

Ordinary root/daemon plugin modules use `definePlugin(...)`. It is the single
authoring path for daemon behavior: one declaration produces the cold manifest
and the matching named `activate` ABI without maintaining a second handwritten
module.

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.echo',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  actions: {
    echo: {
      title: 'Echo',
      execution: { target: 'daemon' },
      run: async (input) => input,
    },
  },
});
```

The generated root activation is registration-only. It receives `PluginApi`,
not invocation or session services, and binds only daemon-target ids declared
in the matching manifest family. Missing, undeclared, duplicate, or
wrong-family registrations fail validation.

A client-target Action is different: its root declaration has no `run`. The
exact client artifact named by `execution.client` exports its own ordinary
`activate(api)` function, receiving the narrow `PluginClientApi` for Action
and Voice registrations only. See [Actions, tools, and commands](/plugins/api/actions-tools-commands)
for that two-module shape.

Static manifest-declared registration methods return `void`. Dynamic watches
or subscriptions may return `Disposable` when their documented lifetime is
genuinely author-owned.

## Low-level daemon ABI conformance

Handwriting a root/daemon `activate` that receives the broad `PluginApi` is only
for low-level ABI conformance or host-owned test fixtures. It is not a second
normal daemon authoring path. This restriction does not apply to the ordinary
client artifact `activate(api)` above: that module receives `PluginClientApi`
and is the documented Developer Preview authoring shape for client Action and
Voice registrations. See the linked capability guides for their incomplete
implementation and proof status.

A low-level daemon ABI module still uses the registration-only contract and may
return one cleanup function after successful registration:

```ts
import type { PluginApi } from '@happier-dev/plugin-sdk';

export async function activate(api: PluginApi) {
  const connection = await openPluginOwnedConnection();
  api.actions.register('query', (input) => connection.query(input));
  return async () => connection.close();
}
```

Happier calls a returned cleanup function at most once when that successful
activation is retired or later validation fails. If activation throws before
returning, no cleanup function exists yet. Protect directly acquired timers,
sockets, processes, and other trusted-code resources with local `try`/`finally`;
Happier can automatically unwind only registrations and resources acquired
through host APIs.

Do not perform user-visible effects, start Agent sessions, read secrets, or
write transcripts during activation. Those operations belong to invoked
handlers or native Agent session operations.
