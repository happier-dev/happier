This maintained task map is derived from the author-owned `index.public.ts`
sources and the current package export map. It gives each import path a purpose
without reproducing a symbol-level API dump. The publisher generates a
symbol-level inventory from those same sources when an SDK artifact is ready;
that generated output is not a second authoring owner.

The SDK is one package-level **Developer Preview** source contract, and the
workspace package is private at `0.0.0` on a prepublication hold. Treat these
paths as current source contracts, not as an offer to install a published
package or a released-semver stability promise. The generated inventory maps
the public surface; it does not create a separate stability tier per export.

## Import rules

- Start with `@happier-dev/plugin-sdk` and `definePlugin(...)` for an ordinary
  author module.
- Import a final domain path when you need an explicit type annotation or a
  value that lives outside the root. Most host services are called through
  `context.services`; their type-only paths remain useful for annotations.
- The table's namespace examples identify a type-heavy module without forcing a
  runtime import. In production code, import the specific type or value you
  need from the same path.
- `host/*` paths are intentionally public to Happier host packages, not to
  installed plugins. `ui/build` is only for a build configuration, and
  `ui/client` is only for a hosted-web client.
- A normal target or contributor imports a feature-owned protocol package. Only
  a reusable feature-protocol package imports the browser-safe `/protocol`
  schema constructors and `/contributions` contribution constructors.

## Choose a route by task

| You are trying to… | Start here | Follow-on route when needed |
| --- | --- | --- |
| Define a normal Plugin | package root and `definePlugin(...)` | `/actions`, `/hooks`, `/agents`, or the capability family it declares |
| Call host behavior from an invoked handler | `/actions` through `context.services.actions` | use the exact action contract documented by the feature that owns it |
| Build a daemon integration | the final daemon capability path | `/exec`, `/fs`, `/http`, `/storage`, or `/connected-accounts` |
| Add a custom Agent | `/agents` | `/agents/runtime`, `/sessions`, and `/sessions/work-state` |
| Render Plugin UI | `/ui` | `/ui/build` for packaging or `/ui/client` only in hosted-web code |
| Declare and use data | `/settings`, `/collections`, or `/resources` | `/storage` for daemon persistence contracts |
| Test a Plugin module | `/testing` | use the source owner’s capability path for precise types |
| Work on Happier host code | `/host/registration` or `/host/fs/json-owner-file-lock` | never import these paths from an installed Plugin |

## Advanced feature-protocol authoring

`@happier-dev/plugin-sdk/protocol` is the browser-safe authoring boundary for
validator-neutral JSON schema facts. `@happier-dev/plugin-sdk/contributions`
owns the cross-plugin authoring boundary for a feature package that defines a
reusable contribution protocol. Neither path exports host services, admitted
snapshots, or runtime controls.

```ts
import {
  defineContributionPoint,
  defineContributionProtocol,
} from '@happier-dev/plugin-sdk/contributions';
```

Everyday plugin authors should instead import the feature-owned value, call
`.point()` for a target or `.contribute()` for a contributor, and derive normal
Action facts from an operation's immutable `.declaration`. `.bind(localId)`
only pairs a named role with an existing same-plugin Action; it is not an Action
search, registry, or second dispatcher. See
[Cross-plugin contributions](/plugins/guides/cross-plugin-contributions).

## One `/resources` path, three resource workflows

`@happier-dev/plugin-sdk/resources` is one retained public path, not an alias
or a second Resource owner. Its exports serve three related author workflows:

1. **Manifest-declared Resources:** use `PluginResourceDefinition`, packaged
   Resource contribution types, and `PluginDynamicResourceRuntime` when a
   plugin publishes bytes through a declared packaged or dynamic Resource. The
   host owns byte admission, digest/currentness, and `readResource` as the
   snapshot authority. `ResourcesService` is the daemon invocation-service
   type for describing, reading, and watching one declared Resource.
2. **Prompt assets and registries:** `PromptAsset*` and `PromptRegistry*`
   types describe prompt-library content, adapters, discovery, and mutation.
   They are not UI Resource subscriptions and do not create a parallel content
   reader.
3. **Runtime UI Resource consumption:** UI code uses its bound host API's
   `readResource` and, for genuinely dynamic Resources, `watchResource`. The
   UI-side `ResourceContent` and `ResourceSubscriptionEvent` types live at
   `@happier-dev/plugin-sdk/ui`; a watch is an invalidation signal, so UI code
   re-reads rather than treating it as a bytes channel.

This naming guide keeps the established `./resources` contract intact while
making the prompt-asset and UI-consumer vocabulary explicit. Do not introduce a
new import alias or import `/resources` into client UI merely to obtain its host
Resource API.

## What `/testing` proves

`@happier-dev/plugin-sdk/testing` is for deterministic author-facing contracts:
manifest validation, activation and handler behavior, cancellation/cleanup, and
the bounded semantic UI fixture, including selectable `option` targets. It does
not prove installed discovery, on-demand activation, generation replacement,
machine routing, native reconciliation, Account encryption, or packaged-artifact
behavior; use the
real CLI, daemon, and UI validation paths for those lifecycle claims.

## Detailed reference and examples

When the publisher produces an SDK artifact, its generated `API.md` is the
symbol-level index for that artifact. It is not an authoring tutorial and does
not make the currently private package publicly available. Start with the
[quickstart](/plugins/quickstart), then use the route map above for explicit
types and the relevant concept guide for lifecycle and product behavior.
