This maintained task map is derived from the author-owned `index.public.ts`
sources and the current package export map. It gives each import path a purpose
without reproducing a symbol-level API dump. The publisher generates a
symbol-level inventory from those same sources when an SDK artifact is ready;
that generated output is not a second authoring owner.

The SDK is one package-level **Developer Preview** source contract. In this
checkout, `@happier-dev/plugin-sdk` is a private workspace package versioned
`0.0.0` on a prepublication hold. Treat these paths as current source
contracts, not as an offer to install a published package or a released-semver
stability promise. The generated inventory maps
the public surface; it does not create a separate stability tier per export.

## Import rules

- Start with `@happier-dev/plugin-sdk` and `definePlugin(...)` for an ordinary
  author module.
- Import a final domain path when you need an explicit type annotation or a
  value that lives outside the root. Most host services are called through
  `context.services`; their type-only paths remain useful for annotations.
- Import SCM identity and pull-request types from `/scm`, including
  `ProtocolScmHostingProviderKind`, `ScmHostingRepositoryIdentityV1` and
  `ScmPullRequestSummary`. Their composable
  `ScmHostingRepositoryIdentityV1ProtocolSchema` and
  `ScmPullRequestSummaryProtocolSchema` values live on `/protocol` for declaring
  feature schemas, in both Node and browser bundles.
- The table's namespace examples identify a type-heavy module without forcing a
  runtime import. In production code, import the specific type or value you
  need from the same path.
- `ui/build` exposes build-realm toolchain compatibility facts, and `ui/client`
  is only for a hosted-web client. Host implementation helpers and first-party
  Agent projections stay with their owning workspace packages; they are not
  SDK entrypoints. Plugin authors declare `observeRead` beside their Action
  handler.
- A normal target or contributor imports a feature-owned protocol package. Only
  a reusable feature-protocol package imports the browser-safe `/protocol`
  schema constructors and `/contributions` contribution constructors.

## Choose a route by task

For a feature handoff that carries an Artifact id, the development `/protocol`
entrypoint exposes the canonical `artifact.get` result projection. Re-read the
Artifact through the host Action, then apply the feature's source, audience,
revision and target admission. The [maintained author example](https://github.com/happier-dev/happier/tree/dev/packages/plugin-sdk#fresh-artifact-reads-in-feature-handoffs-03-development-source)
shows this boundary; carrying an id grants no access or mutation permission.

| You are trying to… | Start here | Follow-on route when needed |
| --- | --- | --- |
| Define a normal Plugin | package root and `definePlugin(...)` | `/actions`, `/hooks`, `/agents`, or the capability family it declares |
| Call host behavior from an invoked handler | `/actions` through `context.services.actions` | use the exact action contract documented by the feature that owns it |
| Build a daemon integration | the final daemon capability path | `/exec`, `/fs`, `/http`, `/storage`, or `/connected-accounts` |
| Add a custom Agent | `/agents` | `/agents/runtime`, `/sessions`, and `/sessions/work-state` |
| Render Plugin UI | `/ui` | exact `./happier-plugin-ui/<artifactId>` package exports, `/ui/build` for toolchain facts, or `/ui/client` only in hosted-web code |
| Declare and use data | `/settings`, `/collections`, or `/resources` | `/storage` for daemon persistence contracts |
| Test a Plugin module | `/testing` | use the source owner’s capability path for precise types |

## Portable HTTP request signing in development

Unreleased 0.3 source exports `computeHttpContentMd5Hex` and
`computeHttpHmacSha256` from `@happier-dev/plugin-sdk/http` for vendor protocols
that need content checksums or request signing in Account code. They accept UTF-8
strings or bytes without importing Node built-ins. MD5 is only for legacy vendor
checksums; use the root `computeSha256HexDigest` for SHA-256 digests.

```ts
import { computeHttpContentMd5Hex, computeHttpHmacSha256 } from '@happier-dev/plugin-sdk/http';

const checksum = computeHttpContentMd5Hex([archivePath, contents]);
const signingKey = computeHttpHmacSha256(secret, canonicalRequest);
```

The HMAC helper returns raw bytes, so it also supports protocols with successive
key derivations, such as S3 SigV4.

## Machine enrollment intent in development

In unreleased 0.3 source, declare the intended kind of Machine with optional
`enrollmentRole: 'server' | 'personal' | 'sandbox'` on a `machineProvisioners`
descriptor. Declare the known guest OS as `guestPlatform`
(`linux`, `darwin` or `windows`) in the options base or a dimension option.
The base or option may also declare `enrollmentRole`; its selected value
overrides the descriptor role without creating a second provisioner entry.

```ts
// Include these in the provisioner descriptor:
const enrollment = {
  enrollmentRole: 'server',
  platforms: ['darwin'], // The controller runs here.
} as const;

// Return this in options.dimensions.image:
const imageOption = {
  id: 'linux', title: 'Linux guest', assignments: [],
  guestPlatform: 'linux', // The selected guest runs here.
  nativeFacts: { image: { id: 'linux', title: 'Linux guest' } },
} as const;
```

Use `projectMachineProvisionerSelectionV1` from
`@happier-dev/plugin-sdk/machine-provisioners` to project the selected facts.
The shared Add review drafts a dedicated `happier` user-service with editable
Preauthorized administrator access only for declared Linux servers. Personal
Machines keep their existing user; sandboxes use the guest process. Missing role,
or a server without platform facts, keeps the existing personal-user default.
A declared macOS or Windows server keeps that path with an explanation that
dedicated-user enrollment is unsupported. Explicit enrollment choices are preserved, and bootstrap still
checks the real guest. Do not infer identity from a provisioner id, transport,
image name or controller OS.

The maintained [public author fixture](https://github.com/happier-dev/happier/blob/dev/packages/plugin-sdk/fixtures/authoring-inference/machineProvisioners.ts)
shows these declarations alongside options and ordinary Action activation.

### Prerequisites and repair Actions

In **0.3 development**, declare executable prerequisites in `managedDependencies`
and reference them from the provisioner's `prerequisites`. Use
`readManagedDependencyExecutable(dependencies, id, signal)` from
`@happier-dev/plugin-sdk/managed-services` to read availability. Offer an install
repair when it returns `missing`. An `unknown` result leaves installation status
unresolved. An explicitly approved repair Action can call
`dependencies.ensure(id, { signal })` for an installable declared source. A
system-only source requires installation by the person; return its installation
guide rather than inventing a downloader. See the
[managed dependency declarations](/plugins/manifest/contributions).

When a check or options result reports an unavailable prerequisite, its
`repairAction` names an ordinary qualified Action and its admitted input:

```ts
const prerequisite = {
  requirement: {
    kind: 'managedDependency',
    id: { pluginId: 'examples.machine-provisioner', localId: 'fixture-tool' },
  },
  status: 'unavailable',
  repairAction: {
    action: { pluginId: 'examples.machine-provisioner', localId: 'repair' },
    input: { machineName: 'guest' },
  },
} as const;
```

The host invokes that Action through normal surface admission and approval; a
repair reference grants no permission by itself. Declare `ui`, `agent`, `mcp`,
`cli` and `plugin` surfaces when each can perform the repair. Native installers
keep their normal confirmation. A client Action that opens installation guidance
can return the guide URL to automated callers; it still needs an answering App
through the existing client Action route. Recheck availability after repair.
The maintained fixture's repair simulates the effect; it is not a native installer.

### Conditional credentials and picker groups

Use `credentialPurposeRequirements[].optionalWhen` on the provisioner for a
launch variant that does not need a declared credential purpose. For example:

```ts
const credentialPurposeRequirements = [{
  purpose: 'native-connection',
  optionalWhen: { op: 'eq', path: 'name', value: 'local' },
}] as const;
```

Only a true predicate with every referenced selector present waives the purpose.
Missing selectors keep it required, including broad picker checks. The host's
credential requirement owner evaluates this for configuration and acquisition;
do not repeat the decision in UI or native handlers. `optionalWhen` changes
whether the purpose is needed, not how credentials are stored or granted.

Picker groups use the same declaration facts: `billing.location: 'local'` places
a provisioner with computers the person controls; cloud provisioners with
`enrollmentRole: 'sandbox'` appear with cloud sandboxes, and other cloud
provisioners appear with cloud servers. A selected option may refine the
enrollment role. Declare these facts rather than adding a group registry or
inferring a group from a plugin id.

## Native deletion notices in development

In matching unreleased 0.3 SDK and host builds, native observations and reviewed
retention capabilities can carry `deletionNotices`. A `stopped-storage` notice
with `consequence: 'disk-deleted'` describes the provider's own deletion rule.
Its `rule: { kind: 'after-stop', afterMs: 0 }` means the disk is deleted as soon
as the Machine stops. Positive `afterMs` values describe the retention delay
after Stop. Omit `at` when the provider supplies no deletion deadline; the host
keeps the rule without guessing a Stop time or scheduling a reminder.

## Native choice refusals in development

In matching 0.3 development SDK and host builds, an options `base` or dimension
with `available: false` can return `unavailableReason: { code, status, fieldPath? }`.
Use a stable native code, localized `status`, and an optional declared input path
that the person can change. The selection projector retains this reason even
when the launch is incomplete or invalid. The configurator shows the native
reason beside Create and at the named field, rather than blaming another choice.

For example, a refused driver can supply
`{ code: 'driver_unavailable', status: { key: 'driver.unavailable', fallback: 'Choose another VM driver.' }, fieldPath: 'vmType' }`.
The maintained author fixture linked above includes a refused options result.
These closed result shapes require matching development readers; this does not
change acquisition authority or the executable launch schema.

## Managed allocation presentation in development

In matching 0.3 development SDK and host builds, use
`classifyManagedMachineAllocationV1` from
`@happier-dev/plugin-sdk/machine-provisioners` to distinguish allocation from
active creation:

```ts
const state = classifyManagedMachineAllocationV1(row, currentCreationOperation);
```

## Native HTTP and guest execution in development

In matching 0.3 development builds, use the machine-provisioner SDK bridge
instead of copying a fetch adapter into a native client:

```ts
import {
  createMachineProvisionerFetch,
  createMachineProvisionerMaterializedFetch,
  buildMachineProvisionerShellCommand,
  buildMachineProvisionerDaemonStartScript,
} from '@happier-dev/plugin-sdk/machine-provisioners';

const request = createMachineProvisionerFetch(context, {
  purpose: 'cloud-api',
  origins: ['https://api.example.com'],
  headerName: 'authorization',
});
const reply = await request('https://api.example.com/resources');

// For a role that captures its API credential once and uses guest tokens:
const capturedRequest = createMachineProvisionerMaterializedFetch(context, {
  purpose: 'cloud-api', origin: 'https://api.example.com',
  headerName: 'authorization', methods: ['GET', 'POST', 'DELETE'],
  isGuestUrl: url => url.origin === 'https://guest.example.com',
});

// Native text-only exec APIs can carry separate binary streams and exit status.
const command = buildMachineProvisionerShellCommand(argv, stdinBase64);
const startupFile = buildMachineProvisionerDaemonStartScript(environment, detachedDaemonStartArgv);
```

The first bridge uses the host-captured Connected Account purpose. During an
explicit authentication attempt, pass formatted `credential` headers instead;
those headers are not persisted by the bridge. The materialized bridge reads
once per role and strips its API header from guest requests, preserving the
guest-specific headers supplied by the native client. Both bridges preserve
bytes, refuse redirects and combine role cancellation with request cancellation.
They do not add retries or native lifecycle decisions.

The shell command returns JSON with `exitCode`, `stdoutBase64` and
`stderrBase64`. Omit the second argument when the native API carries stdin in
its own field. The vendor adapter still interprets native transport errors and
parses this command result; it never treats command acceptance as success.
The startup-file builder renders the host-provided environment and argv; the
native adapter still owns private staging, publication and startup registration.

Use `readMachineProvisionerCredentialRefusal(reply.status)` when the vendor API
rejects the selected credential. A `credential_unavailable` check result lets
the host offer reconnection. Confirm deletion through the vendor’s exact resource
readback and pass the observation to `projectMachineProvisionerDeleteReadback`.

For a native preparation Action, build the command after staging the CLI inputs.

```ts
import { buildMachineProvisionerPreparationInstallScript } from '@happier-dev/plugin-sdk/machine-provisioners';

const script = buildMachineProvisionerPreparationInstallScript({
  cli: definition.cli,
  stageDirectory,
  setupScript: definition.setupScript,
});
```

The script checks that the installed CLI is executable before it runs setup.
Keep output from authored install and setup scripts private. Public command
failures can carry the exit code without the script’s stderr.

## Cloud-init SSH bootstrap in development

In unreleased 0.3 source, a daemon-realm cloud provisioner can build first-boot
`user_data` from the managed row's public key and select the matching SSH identity:

```ts
import {
  buildMachineProvisionerCloudInit,
  MACHINE_PROVISIONER_CLOUD_SSH_USER,
} from '@happier-dev/plugin-sdk/machine-provisioners/ssh';

const userData = buildMachineProvisionerCloudInit(bootstrapSshPublicKey);
const connection = {
  address: publicAddress,
  user: MACHINE_PROVISIONER_CLOUD_SSH_USER,
};
```

Pass `userData` in the cloud's create request and use `connection` when calling
`resolveMachineProvisionerSshBootstrap` with the invoked handler's exec service
and retained credential reference. The helper creates the key-only `happier-bootstrap`
user with its own home, bash and passwordless sudo, and disables SSH password
authentication. For dedicated-daemon enrollment, the host uses this principal for
bootstrap and creates the separate locked `happier` account with its reviewed
administrator policy. The daemon
does not inherit the bootstrap user's sudo grant or vendor-issued root password.
This create-time configuration
does not modify an existing guest. Host-key observation still requires the host's
ordinary trust approval before installation.

## Agent skill delivery in development

In unreleased 0.3 source, an Agent receives resolved skills on
`AgentSessionOpenRequest.skills` or `AgentExecutionRunOpenRequest.skills`, typed
by `AgentSessionSkillDelivery` from `/agents/runtime`. Each item carries its
library `skillId`, frontmatter `name`, content `digest` and required absolute
`directory`. The host materializes that read-only directory and owns its lifetime.

Use `item.directory` for file reads, copies and catalog identity matching. An
imported source folder can differ from `item.name`, including after a library
rename. A private-home copy keeps the basename of `item.directory`, so references
between selected sibling skills still resolve. Root-based native integrations
continue to receive `skillsRoot` or `pluginRoot`.

This replaces the earlier unpublished item shape: update Agent adapters and test
fixtures to carry `directory`; do not reconstruct a fallback from `name`.
`runAgentSkillDeliveryContract` from `/testing` checks this with a source folder
different from the skill name, alongside its launch, supporting-file and cleanup
checks. The contract applies to external and bundled Agent plugins alike.

## Advanced feature-protocol authoring

`@happier-dev/plugin-sdk/protocol` is the browser-safe authoring boundary for
validator-neutral JSON schema facts. `@happier-dev/plugin-sdk/contributions`
owns the cross-plugin authoring boundary for a feature package that defines a
reusable contribution protocol. Neither path exports host services, admitted
snapshots, or runtime controls.

```ts
import {
  defineContributionPoint,
  defineContributionProtocol,
} from '@happier-dev/plugin-sdk/contributions';
```

Everyday plugin authors should instead import the feature-owned value, call
`.point()` for a target or `.contribute()` for a contributor, and derive normal
Action facts from an operation's immutable `.declaration`. `.bind(localId)`
only pairs a named role with an existing same-plugin Action; it is not an Action
search, registry, or second dispatcher. See
[Cross-plugin contributions](/plugins/guides/cross-plugin-contributions).

## One `/resources` path, three resource workflows

`@happier-dev/plugin-sdk/resources` is one retained public path, not an alias
or a second Resource owner. Its exports serve three related author workflows:

1. **Manifest-declared Resources:** use `PluginResourceDefinition`, packaged
   Resource contribution types, and `PluginDynamicResourceRuntime` when a
   plugin publishes bytes through a declared packaged or dynamic Resource. The
   host owns byte admission, digest/currentness, and `readResource` as the
   snapshot authority. `ResourcesService` describes, reads, and watches a
   declared Resource in its admitted invocation context.
2. **Prompt assets:** `PromptAsset*` types describe external prompt assets and
   their mutation contracts. In 0.3 development source, registry discovery and
   library skill changes instead use the typed host Actions; the retired
   `PromptRegistry*` adapter types are not a registry extension API. Neither
   path creates a parallel UI Resource reader.
3. **Runtime UI Resource consumption:** UI code uses its bound host API's
   `readResource` and, for genuinely dynamic Resources, `watchResource`. The
   UI-side `ResourceContent` and `ResourceSubscriptionEvent` types live at
   `@happier-dev/plugin-sdk/ui`; a watch is an invalidation signal, so UI code
   re-reads rather than treating it as a bytes channel.

This naming guide keeps the established `./resources` contract intact while
making the prompt-asset and UI-consumer vocabulary explicit. Do not introduce a
new import alias or import `/resources` into client UI merely to obtain its host
Resource API.

In unreleased 0.3 source, await `ResourcesService.watch(...)` to receive its
`Disposable`. A dynamic producer's `observe` callback can also return its
disposable asynchronously. Subscription admission waits for attachment;
failure rejects rather than reporting a live watch, and cancellation or
authority retirement disposes an attachment that finishes late. Check the
installed SDK contract before using this development-source signature.

## How published names are shaped

Two shapes recur across every entrypoint, and each one carries information.
Read them when you consume the surface; apply them when you add to it.

**`V<n>` marks a versioned contract, never a new spelling.** A published name
carries `V1`, `V2`, … only when the concept behind it has a real schema version
that its Protocol owner can evolve: a wire payload, a persisted shape, a
manifest contribution family, or a bound constant that ships with the contract.
`PluginUiSemanticCommandV1` is suffixed because
`PluginUiSemanticCommandV1Schema` exists and versions it. A runtime-only shape
cannot be versioned — an object holding an `AbortSignal`, a callback, or a live
service handle never crosses a wire or a disk — so it takes no suffix:
`PluginClientActionContext`, `PluginInvocationContext`, `ActionHandler`. A
suffix added for symmetry with a neighbouring name is drift: it promises a
schema version that does not exist, and it implies a `V2` you will never be
able to ship.

**One concept, one published name.** The `Plugin` prefix disambiguates a
declaration whose bare noun would collide with a host, platform, or
ecosystem-common identifier. It is not a badge for everything a plugin touches,
and it must not produce two spellings of one type. Re-exporting a declaration
under a second name at a path boundary — publishing both `PluginSettingDescriptor`
and `SettingDescriptor` for one declaration — gives an author two names with no
signal that they are the same, and it defeats the duplicate-name guard in
`api-surface`, which compares export names. Pick the name at the declaration and
publish that one everywhere.

## What `/testing` proves

`@happier-dev/plugin-sdk/testing` is for deterministic author-facing contracts:
manifest validation, activation and handler behavior, cancellation/cleanup, and
the bounded semantic UI fixture, including selectable `option` targets. It does
not prove installed discovery, on-demand activation, occurrence replacement,
machine routing, native reconciliation, Account encryption, or packaged-artifact
behavior; use the
real CLI, daemon, and UI validation paths for those lifecycle claims.

## Present Action failures (0.3 development source)

Use the host's localized failure copy from native or hosted-web plugin UI:

```ts
import { presentActionFailure } from '@happier-dev/plugin-sdk/ui';

const presented = await presentActionFailure(hostApi, failure);
// Render presented.reason, optional presented.nextStep, and the
// presented.technicalDetails lines in TechnicalDetailsDisclosure.
```

Pass the failed Action result unchanged: `ok: false`, `errorCode`, `error`,
and its optional `failureCause`, `details` and `requestId`. In 0.3 development,
optional authored `message` and `remediation` retain the producer’s reason and
recovery; the app’s code copy is used only when that reason is absent. A code-only failure may omit `error`; unknown codes then use the app presenter’s generic fallback. The helper checks
`hostApi.version().methods` for `presentActionFailure`. On older hosts it
shows the producer message with Code and Request ID. Hosts with the method use
the app presenter and its safe technical details. The current presenter combines
reason and recovery in `reason`; `nextStep` is null. Do not add plugin-local
error-code translations.
