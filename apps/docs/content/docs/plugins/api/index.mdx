title: Plugin API

The plugin runtime has three principal public contexts:

- `PluginApi`: nested, registration-only ABI consumed by the generated
  `activate(api)` export from `definePlugin(...)`.
- `PluginInvocationContext`: invocation-scoped identity, cancellation, and services passed to action and hook handlers.
- `AgentRuntimeFactoryContext`: factory-scoped identity and lifecycle data passed to Agent runtime factories.

## Activation API

`definePlugin(...)` projects executable handlers into the matching nested
`PluginApi` family for manifest-declared contributions:

- agent runtimes
- actions
- hooks
- notification channels
- SCM hosting and repository integrations
- MCP servers and discovery contributions
- supported Voice contributions declared by the installed SDK version
- activation cleanup returned from the code-defined `setup` callback

This list describes source-level ABI families. Consult the installed
`capability-matrix.json` before author use: a `deferred` family is conformance
reference material until a maintained plugin proves its canonical lifecycle.

## Runtime context

Use the services and `context.ui` on `PluginInvocationContext` from invoked handlers. Agent runtimes receive their own bounded factory/session contexts.

- `context.services.storage`
- `context.services.settings`
- `context.services.logger`
- `context.services.events`
- `context.services.availability(serviceId)`

## Rule of thumb

If it declares an identity, put it in the `definePlugin(...)` source. If it
binds executable behavior, use the matching code-defined family rather than a
handwritten activation module. Tools and commands reference actions
declaratively. Invoked handlers use their bounded invocation services; Agent
runtime factories use their factory context.

A feature-owned cross-plugin contribution protocol is the exception to a
single-plugin declaration: a target calls `.point()`, while a contributor binds
an existing Action with `.contribute()` and `.bind(localId)`. The role's
immutable `.declaration` supplies Action facts; neither side scans Actions or
adds another dispatcher. See
[Cross-plugin contributions](/plugins/guides/cross-plugin-contributions).
