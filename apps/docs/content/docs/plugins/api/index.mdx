---
title: Plugin API
description: Public daemon-side API surfaces for activating plugins and running plugin-owned handlers.
---

The plugin runtime has three principal public contexts:

- `PluginApi`: nested, registration-only API passed to `activate(api)`.
- `PluginInvocationContext`: invocation-scoped identity, cancellation, and services passed to action and hook handlers.
- `AgentRuntimeFactoryContext`: factory-scoped identity and lifecycle data passed to Agent runtime factories.

## Activation API

Use `PluginApi` to register executable handlers for manifest-declared contributions through the matching nested family:

- agent runtimes
- actions
- hooks
- notification channels
- SCM hosting and repository integrations
- MCP servers and discovery contributions
- request interceptors
- supported Voice contributions declared by the installed SDK version
- activation cleanup returned from the named `activate` function

## Runtime context

Use the services and `context.ui` on `PluginInvocationContext` from invoked handlers. Agent runtimes receive their own bounded factory/session contexts.

- `context.services.storage`
- `context.services.settings`
- `context.services.logger`
- `context.services.events`
- `context.services.availability(serviceId)`

## Rule of thumb

If it declares an identity, put it in the manifest. If it binds executable behavior, use the matching nested activation family. Tools and commands reference actions declaratively. Invoked handlers use their bounded invocation services; Agent runtime factories use their factory context.
