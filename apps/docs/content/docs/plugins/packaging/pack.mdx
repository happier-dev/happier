title: Pack plugins
description: Create a selected-file npm-compatible Plugin Platform archive.
---

Packing creates an installable archive from a local plugin directory.

```bash
hdev plugins pack /absolute/path/to/plugin --out /absolute/path/to/plugin-output.happier-plugin.tgz
```

The package metadata identifies the generated cold manifest in `package.json`:

```json
{
  "keywords": ["happier-plugin"],
  "happier": { "manifest": ".happier-plugin/plugin.json" },
  "files": [".agents/skills/happier-plugin-authoring", "dist"]
}
```

Use a deliberate `files` inventory. The pack owner stages
`.happier-plugin/plugin.json` from the `definePlugin(...)` projection into the
archive even though authors do not keep that file in the source tree. Packing
includes only selected regular files and rejects unsafe archive paths and
package lifecycle assumptions.

The archive output must be outside the plugin package root and must not already
exist (including its `.sha256` sidecar). When no `--out` is supplied, use the
archive path printed by `plugins pack`.

The same pack step writes generated `happier.compatibilityProjection` and
`happier.marketplaceDiscovery` data into the staged `package.json`. Do not add
or maintain those fields in source metadata: they are derived from the
canonical manifest and generated UI inventory, including the exact staged
manifest digest.

In the 0.3 development publisher, reviewed publication fields apply once to the
staged package. The effective runtime manifest, cold manifest, package metadata,
and discovery projection agree on that operation's version and listing while
the author source stays intact. See
[Publish a plugin](/plugins/packaging/authoring-cli#publish-a-plugin) for candidate
review, npm approval, and recovery.

## Repository-managed npm releases (0.3 development)

Opt-in plugins maintained in the Happier repository participate in the release
pipeline when their `package.json` declares `happier.bundled: false`. The
pipeline discovers these packages; authors do not maintain a separate release
list. Changes to the plugin's own directory propose its release. An SDK-only
change does not release every plugin.

Maintainers can include a plugin in a release of all changed components or
select only its `plugin:<directory-name>` target, such as `plugin:asciinema`.
The source package version remains a placeholder; publication allocates the
channel version. Production requires an approved exact version for each selected
plugin; preview and development allocate rolling
versions. Production uses npm's `latest` tag, preview uses `next`, and
development uses `dev`.

Publication waits for the Plugin SDK pair step. The packed plugin depends on
the exact Plugin SDK version published in that run, or the version already
published on the channel when the SDK was not selected. A channel without a
published SDK cannot release a plugin. The release host's toolchain must agree
with that exact SDK version.

The pipeline uses the normal plugin packer and installs the archive into a
temporary host before publication, including manifest and declared
`engines.happier` admission. A failed pack or install stops publication. The
same public SDK approval policy and npm provenance requirements apply.
This describes development-source release support, not an announcement that
any plugin package has been published. Plugin ids must also satisfy npm
registry admission; passing a local archive check does not grant a reserved
registry identity.

## Include

- the generated `.happier-plugin/plugin.json` cold projection
- the compiled, self-contained daemon entry
- runtime resources
- built UI artifact tree
- files needed by declared handlers

## Exclude

- local secrets
- build caches
- absolute-path artifacts
- unrelated source-control metadata
- agent CLI binaries

## Validate the artifact

The default `hdev plugins test .` command is daemon-independent. Its
`--packed` mode packs the selected files, installs and trusts the archive in an
authenticated disposable daemon home, verifies activation and currentness
across daemon restart, and invokes a safe empty-input CLI action when the
manifest exposes one. It never reads or mutates the author's installed plugin
state. Before distribution, also validate any claimed user flows that extend
beyond this canonical packed smoke and verify uninstall on the relevant hosts.
