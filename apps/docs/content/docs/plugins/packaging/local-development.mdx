```bash
happier plugins create my-plugin
cd my-plugin
happier plugins dev
```

The scaffold's code-defined module declares both entries:

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';

export const { manifest, activate } = definePlugin({
  id: 'com.example.my-plugin',
  version: '0.1.0',
  entrypoints: {
    daemon: './dist/index.js',
    development: './src/index.ts',
  },
});
```

The development entry is source input, not an installable production artifact.
Keep both entrypoint values relative to the plugin root and use portable `/`
separators. Absolute paths, paths that escape the root, unsupported extensions,
and missing development files are rejected before dependency materialization.
`plugins dev` is the automatic flow: the CLI observes the trusted author source
and submits each captured batch, while the daemon-owned candidate path creates
an operation-local copy, materializes dependencies, builds declared UI
artifacts, evaluates the candidate, and validates its canonical manifest
projection before adoption. The daemon owns runtime module import, named
activation, registration validation, and replacement of the serving plugin.

## Plugin UI in the development loop

When the package declares a plugin UI build config (`pluginUiBuild.ts`, written
by `happier plugins create --ui …`), the daemon runs the same
`happier-plugin-build-ui` builder that `happier plugins dev build .` runs
after the CLI submits the captured batch and before candidate adoption. The
development generation carries the resulting `dist/happier-plugin-ui` tree, so
each accepted edit produces a generation whose UI artifacts match the source
you just saved.

A failing UI build rejects the submitted candidate before adoption, so the
previously admitted generation stays current. Fix the source and save again.

This is a managed candidate replacement cycle, not a user-visible
hot-module-reload guarantee. A saved UI source edit can rebuild and replace the
admitted generation; authors must not rely on in-place component state
preservation, a separate UI watcher, or a manual browser/native reload path.

`plugins dev` reports the stage it actually reached — `source_validated`,
`built`, `admitted` or `projected` — in both its human output and `--json`.
`projected` means the daemon made the generation current and no surface
reconciliation is outstanding. The CLI stops there; whether a client actually
loaded and rendered the surface is not something it can observe, and it does not
claim to.

For an intentional watcher-free update, install the same package root as a
development source and reload from that package root:

```bash
happier plugins install . --dev
happier plugins reload
```

If the current directory maps to more than one development plugin, or if you
run the command elsewhere, select one explicitly: `happier plugins reload
com.example.my-plugin`. Both paths preserve the last accepted generation when
evaluation or validation fails.

The watcher-free path uses the same author-cycle coordinator: it prepares
declared dependencies when needed, rebuilds declared UI artifacts, and only
then submits the candidate. Do not run a separate manual UI reload or assume a
source-only replacement; a failed preparation or build preserves the last
accepted generation.

## Trust

The first use presents **Install & Trust** for the canonical local source.
Daemon and React Native plugin code is trusted arbitrary code, not sandboxed
code. Approval covers the displayed package identity, executable realms,
source identity, and current access disclosures. Ordinary edits under the same
approved development identity take effect without another prompt; relevant
identity, realm, root, or required-access changes are reviewed again.

## Edit loop

1. Edit `src/index.ts` or another selected source file in its dependency closure.
2. Read static or daemon activation diagnostics printed by `plugins dev`.
3. Exercise the contribution through its real UI, CLI, Agent, or MCP surface.
4. Fix a rejected edit and save again.

A rejected edit does not replace the serving plugin. Authors consume the
diagnostic and fix the source; the daemon owns safe replacement and cleanup.
Transient candidate-submission failures are reported without ending the watch
loop, so reconnecting the daemon and saving again retries the current source.
