title: Plugin authoring CLI

This page is the canonical command reference for plugin authors. Run commands
from the plugin root unless a command takes an explicit path. `--json` selects
the structured result for automation; it does not bypass review or trust. The
one explicit non-interactive trust decision is the `--trust` flag on a local
development install, documented in
[Install a development source without a prompt](#install-a-development-source-without-a-prompt).

## Create and develop

```bash
hdev plugins create my-plugin --id com.example.my-plugin
cd my-plugin
hdev plugins dev
```

`hdev plugins create <name> [--id <plugin.id>] [--name <display name>]
[--ui hostedWeb|reactNative]` creates the normal code-defined TypeScript
package. React Native is the executable UI option with supported client
realms. A hosted-web scaffold emits a real packaged artifact whose runtime
availability is reported per host rather than as a single global answer: a host
either names the one frame adapter it constructed or reports a typed
unavailable reason. See
[Hosted web UI](/plugins/ui/hosted-web#build-and-runtime-availability).

`hdev plugins dev [path] [--sdk-registry <origin>]` is the normal edit
loop. The CLI observes the source closure and submits each captured batch to the
daemon. After submission, the daemon-owned candidate lifecycle materializes
declared dependencies, builds declared UI artifacts, evaluates the candidate,
and validates it before adoption. On cold start the CLI also materializes the
author root itself when nothing has materialized it yet, so the directory you
edit resolves its declared dependencies; a root whose declared SDK already
resolves is left alone rather than reinstalled, and an interrupted first run is
repaired on the next start. Do not run
`hdev plugins dev install .` before this loop: it is the explicit repair
command, not a prerequisite. Pass
`--sdk-registry <origin>` only when the selected SDK must resolve from an
approved registry origin.

## Check the author package

```bash
hdev plugins dev typecheck .
hdev plugins dev build .
hdev plugins test .
hdev plugins test . --packed
```

- `hdev plugins dev install <path> [--sdk-registry <origin>]` prepares an
  external-author fixture, and repairs or refreshes an author root whose package
  tree is stale or wiped. It is not a prerequisite for `plugins dev`.
- `hdev plugins dev typecheck <path>`,
  `hdev plugins dev build <path>`, and
  `hdev plugins dev test <path>` run the managed focused check named by
  the subcommand. They prepare a missing author package tree once and otherwise
  reuse it; run `plugins dev install` when declared dependencies change or the
  tree needs an explicit refresh.
- `hdev plugins test [path]` runs the plugin's daemon-independent suite.
  Its `--packed` mode packs, trusts, installs, restarts, and invokes the
  package through a disposable daemon; it never reads or mutates the author's
  installed-plugin state. `--with-plugin <root-or-archive>` supplies an
  explicitly composed companion for that packed proof.
- `hdev plugins doctor [path]` evaluates the code-defined author module once
  and reports import or top-level evaluation diagnostics. It does not prove
  repeated evaluation is pure. Like the focused checks, it prepares a missing
  package tree but does not reinstall an already materialized one.
- `hdev plugins doctor --installed [<pluginId>]` inspects installed plugins
  instead of author source. It reads the immutable generation this machine
  currently commits and reports declared files that are missing, escaped
  through a symbolic link, no longer a regular file, no longer their recorded
  byte length, or whose manifest no longer loads, then names the command that
  restores the plugin. It reports structural and loadability facts only; it
  computes no content digest and makes no tampering claim.

Use [Diagnostics and errors](/plugins/testing/diagnostics) to distinguish
these owner-level checks from an admitted candidate or a loaded client surface.

## Pack and install

```bash
hdev plugins pack . --out ../my-plugin.tgz
hdev plugins install ../my-plugin.tgz --kind archive
```

`hdev plugins pack <path> [--out <archive.tgz>] [--sdk-registry <origin>]`
validates the package and writes its selected-file npm-compatible archive.
Packing derives the cold manifest from `definePlugin(...)`; authors do not keep
a second checked-in manifest. See [Pack plugins](/plugins/packaging/pack) for
archive contents. The output must be outside the plugin package root and must
not already exist (including its `.sha256` sidecar).

`hdev plugins install <path|archive|package> [--kind path|archive|npm]
[--selector <version>] [--integrity <sha256-SRI>] [--dev [--trust]] [--dry-run]`
submits one reviewed install to the active daemon. The daemon, rather than the
CLI, owns package activation, currentness, and retained last-known-good
behavior. Use `--dev` only for an intentional watcher-free package-root
development source, and `--trust` only to carry the trust decision for that
source on the command line.
[Install and trust](/plugins/packaging/install-trust) owns the detailed trust,
update, rollback, enable/disable, inspection, and uninstall contracts.

## Reload a development source

```bash
hdev plugins install . --dev
hdev plugins reload
```

`hdev plugins reload [developmentPluginId]` reruns the daemon-owned cycle
for the development source registered for the current directory. When more
than one registered source contains that directory, pass the explicit plugin
id. A failed replacement leaves the last accepted generation serving; do not
start a second watcher or invent a source-only reload path.

## Install a development source without a prompt

```bash
hdev plugins install . --dev --trust --json
hdev plugins reload --json
```

`--trust` carries one explicit non-interactive authorization for that exact
local development source, so the first install of a source root completes
without a terminal prompt. Use it whenever no present user can answer the
source-root question: a CI job, a script, or an Agent Session driving the loop.

The flag is deliberately narrow:

- It is valid only with `--dev` on a local path. Any other request fails with
  `plugin_explicit_trust_requires_development_path`.
- It decides source-root trust and package trust for that one resolved path. If
  the daemon's prepared review names a different source, the pending change is
  cancelled with `plugin_explicit_trust_target_mismatch` rather than approved.
- It selects no optional host resources; those remain available only through the
  reviewed prompt.
- It does not extend to consequential updates or secrets, which stay with a
  present user.

`hdev plugins dev` has no `--trust` equivalent, so this install route plus
`hdev plugins reload` is the headless edit loop. Once the source root is
trusted, later requests for that root skip source-root review, so no further
decision is required until the reviewed source identity changes.

## Review a pending change

An install or development request can return a daemon-issued pending change
ID. Review and decide that exact request:

```bash
hdev plugins change status <pendingChangeId> --json
hdev plugins change approve <pendingChangeId> --json
hdev plugins change reject <pendingChangeId> --json
```

`status` is read-only. `approve` and `reject` are explicit present-user
decisions on this pending-change route; apart from the `--trust` flag above, an
Agent may prepare a request but cannot decide it. A source-root
approval can return `reviewRequired` with the same pending ID when package
review remains. Review the reported package facts, then use `approve` again on
the same pending ID. `reject` cancels the request. Apart from the `--trust`
flag above, JSON or noninteractive installation never auto-approves, and a
direct noninteractive approval selects no optional host resources.

The same decision is available in the app. Settings -> Plugins lists every
change the machine's daemon is still holding, including one an Agent prepared,
and offers the same approve and reject decisions with the full review. Use it
when the initiating result is not in front of you.

Pending IDs are rejoinable only during the same daemon lifetime. If `status`
reports `expired` after restart, rerun the original request and review its new
facts. If a mutation reports `outcome_unknown`, inspect installed state before
replaying it. The listing is daemon-lifetime state, not a durable queue: a
restarted daemon holds nothing, so preserve the ID surfaced by the initiating
result whenever you can query that exact request.

## Other plugin administration

The `hdev plugins` command also owns these product and operator surfaces;
they are not alternate authoring lifecycles. Use their specific help output for
flags and the linked install, Settings, registry, or marketplace documentation
rather than repurposing them to prepare a source candidate.

| Surface | Commands |
| --- | --- |
| Installed inspection | `hdev plugins list`, `hdev plugins show <pluginId>`, `hdev plugins actions <pluginId>`, `hdev plugins logs <pluginId>` |
| Installed lifecycle | `hdev plugins enable <pluginId>`, `hdev plugins disable <pluginId>`, `hdev plugins rollback <pluginId>`, `hdev plugins uninstall <pluginId>` |
| Settings and secrets | `hdev plugins settings list <pluginId>`, `hdev plugins settings secret status`, `bind`, `unbind`, and `delete` |
| Private registries | `hdev plugins registry add`, `login`, `test`, `logout`, `remove`, and `list` |
| Marketplace sources | `hdev plugins marketplace sources list`, `add`, `enable`, `disable`, and `remove` |
| Marketplace listings | `hdev plugins marketplace list`, `show`, and `install` |
