This page is the canonical command reference for plugin authors. Run commands
from the plugin root unless a command takes an explicit path. `--json` selects
the structured result for automation; it does not bypass authority or
credential decisions. An explicit local-path install is itself the code-trust
decision, documented in
[Install a development source without a prompt](#install-a-development-source-without-a-prompt).
These commands describe 0.3 development source / Developer Preview authoring.

## Create and develop

```bash
hdev plugins create my-plugin --id com.example.my-plugin
cd my-plugin
hdev plugins dev
```

`hdev plugins create <name> [--id <plugin.id>] [--name <display name>]
[--ui hostedWeb|reactNative] [--template session-agent]` creates the normal
code-defined TypeScript package. `--template session-agent` scaffolds a custom
persistent Session Agent instead of the default action package — one Agent
declaration plus a distinct, import-safe Session-runner leaf — and takes no
`--ui`. React Native is the executable UI option with supported client
realms. A hosted-web scaffold emits a real packaged artifact whose runtime
availability is reported per host rather than as a single global answer: a host
either names the one frame adapter it constructed or reports a typed
unavailable reason. See
[Hosted web UI](/plugins/ui/hosted-web#build-and-runtime-availability).

`hdev plugins dev [path] [--sdk-registry <origin>]` is the normal edit
loop. The path may be a plugin project folder or an exact `.ts`, `.mts`, `.js`,
or `.mjs` plugin file. The command registers and trusts that exact source, prints the
daemon-owned development status, and may stay attached for status output. The
daemon observes the source, prepares dependencies when dependency inputs
change, builds declared UI artifacts, validates a candidate, and replaces only
that plugin's process-local occurrence after every blocking check succeeds.
The CLI does not watch files, compile candidates, or decide replacement. Do not
run `hdev plugins dev install .` before this loop: it is the explicit repair
command for a package tree, not a prerequisite. Pass
`--sdk-registry <origin>` only when the selected SDK must resolve from an
approved registry origin.

A project folder uses `src/index.ts` or `index.ts` (having both is an error).
When neither exists, set `package.json`'s `main` to the author module: an exact
`.ts`, `.mts`, `.js`, or `.mjs` file exporting `manifest` and `activate`. For
example, a plain-JavaScript package can use `"main": "./src/index.mjs"`.
The conventional TypeScript source takes precedence over a package's built
`main`; conditional `exports` do not select the development entry. Folder
development keeps dependency and UI-artifact preparation rooted at that package.

Use `hdev plugins status [--json]` from another terminal to read the canonical
roots, phases, current occurrences, UI digests, and bounded diagnostics.

## Check the author package

The scaffold's package scripts are aliases for these managed commands:
`npm run typecheck`, `npm run build`, `npm test`, and `npm run pack:plugin`.
They use the CLI invoker selected when the package was created.

```bash
hdev plugins dev typecheck .
hdev plugins dev build .
hdev plugins test .
hdev plugins test . --packed
```

- `hdev plugins dev install <path> [--sdk-registry <origin>]` prepares an
  external-author fixture, and repairs or refreshes an author root whose package
  tree is stale or wiped. It is not a prerequisite for `plugins dev`.
- `hdev plugins dev typecheck <path>`,
  `hdev plugins dev build <path>`, and
  `hdev plugins dev test <path>` run the managed focused check named by
  the subcommand. They prepare a missing author package tree once and otherwise
  reuse it; run `plugins dev install` when declared dependencies change or the
  tree needs an explicit refresh.
- `hdev plugins test [path]` runs the plugin's daemon-independent suite.
  Its `--packed` mode packs, trusts, installs, restarts, and invokes the
  package through a disposable daemon; it never reads or mutates the author's
  installed-plugin state. `--with-plugin <root-or-archive>` supplies an
  explicitly composed companion for that packed proof.
- `hdev plugins doctor [path]` evaluates the code-defined author module once
  and reports import or top-level evaluation diagnostics. It does not prove
  repeated evaluation is pure. Like the focused checks, it prepares a missing
  package tree but does not reinstall an already materialized one.
- `hdev plugins doctor --installed [<pluginId>]` inspects installed plugins
  instead of author source. It reads the immutable generation this machine
  currently commits and reports declared files that are missing, escaped
  through a symbolic link, no longer a regular file, no longer their recorded
  byte length, or whose manifest no longer loads, then names the command that
  restores the plugin. It reports structural and loadability facts only; it
  computes no content digest and makes no tampering claim.

Use [Diagnostics and errors](/plugins/testing/diagnostics) to distinguish
these owner-level checks from an admitted candidate or a loaded client surface.

## Pack and install

```bash
hdev plugins pack . --out ../my-plugin.tgz
hdev plugins install ../my-plugin.tgz --kind archive
```

`hdev plugins pack <path> [--out <archive.tgz>] [--sdk-registry <origin>]`
validates the package and writes its selected-file npm-compatible archive.
Packing derives the cold manifest from `definePlugin(...)`; authors do not keep
a second checked-in manifest. See [Pack plugins](/plugins/packaging/pack) for
archive contents. The output must be outside the plugin package root and must
not already exist (including its `.sha256` sidecar).

`hdev plugins install <path|archive|package> [--kind path|archive|npm]
[--selector <version>] [--integrity <sha256-SRI>] [--dev] [--dry-run]`
submits one reviewed install to the active daemon. The install store owns trust,
source, enablement, and selected-version intent. The daemon, rather than the
CLI, owns runtime admission, the current process-local occurrence, and its
in-process fallback. Use `--dev` only for an intentional watcher-free
package-root development source. Naming a local path explicitly is its
code-trust action.
[Install and trust](/plugins/packaging/install-trust) owns the detailed trust,
update, rollback, enable/disable, inspection, and uninstall contracts.

### Publish a Bot template

For an authored plugin package, declare a keyed `botTemplates` record in
`definePlugin(...)` and include each referenced release JSON file in the packed
package. This unreleased 0.3 development contract supports several templates in
one package and needs no runtime registration. Follow the
[cold-template contribution contract](/plugins/manifest/contributions#bot-templates-03-development-source)
and its public example, then use the ordinary check, pack and publication
workflow on this page. Each JSON file is a portable `BotTemplateReleaseV1`,
not a private draft or a reference to its author's Session.

## Reload a development source

```bash
hdev plugins install . --dev
hdev plugins reload
```

`hdev plugins reload [developmentPluginId]` reruns the daemon-owned cycle
for the development source registered for the current directory. When more
than one registered source contains that directory, pass the explicit plugin
id. A failed replacement leaves the last accepted process-local occurrence
serving for that daemon lifetime; do not start a second watcher or invent a
source-only reload path.

## Install a development source without a prompt

```bash
hdev plugins install . --dev --json
hdev plugins reload --json
```

The explicit command authorizes code from that exact local development source,
so the first install completes without a redundant terminal prompt. This works
for a CI job, script, or Agent Session driving the loop.

The decision is deliberately narrow:

- It decides source-root trust and package trust for that one resolved path. If
  the daemon's prepared review names a different source, the pending change is
  cancelled with `plugin_explicit_trust_target_mismatch` rather than approved.
- It selects no optional host resources; those remain available only through the
  reviewed prompt.
- It does not extend to new authority or credential grants, which stay with
  their canonical host owners.

This install route plus `hdev plugins reload` is the headless edit loop. Once the source root is
trusted, later requests for that root skip source-root review, so no further
decision is required until the reviewed source identity changes.

## Review a pending change

An install or development request can leave a daemon-retained candidate waiting
for review. In 0.3 development source, it uses an ordinary `plugins.install`
approval Artifact in the Happier Inbox. Review the evaluated manifest,
permissions, and host access there. A review still awaiting daemon evaluation
cannot be approved.

When development registration needs review, `plugins dev` hands the retained
candidate to this same install owner and returns the ordinary approval Artifact
ID. Decide it, then run `plugins dev` again to continue watching.

To reconnect to a retained development review, rerun `plugins dev` with the exact
source, or use the explicit install alternative to rejoin the same Artifact:

```bash
hdev plugins install <exact-source> --dev --json
```

Decide in the Inbox, or use the public `approval.request.decide` Action with
the ordinary approval Artifact ID returned by the proposal:

```bash
hdev actions invoke approval.request.decide --input-json '{"artifactId":"<approvalArtifactId>","decision":"approve"}' --json
hdev actions invoke approval.request.decide --input-json '{"artifactId":"<approvalArtifactId>","decision":"reject"}' --json
```

The same Action is available to agents and MCP callers. Decision authority
follows the user's approval policy; JSON output does not grant authority.
Optional host resources and Secrets retain their separate authority decisions.

A daemon pending change ID identifies preparation status, not the approval
Artifact. Preserve it for read-only inspection:

```bash
hdev plugins change status <pendingChangeId> --json
```

`status` does not publish or decide an approval. Use the original source flow
to rejoin a retained development review instead of preparing another candidate.

Pending IDs are rejoinable only during the same daemon lifetime. If `status`
reports `expired` after restart, rerun the original request and review its new
facts. If a mutation reports `outcome_unknown`, inspect installed state before
replaying it. Pending candidate custody lasts for that daemon lifetime; a
restart requires newly prepared facts even if an older approval Artifact remains
visible.

## Other plugin administration

The `hdev plugins` command also owns these product and operator surfaces;
they are not alternate authoring lifecycles. Use their specific help output for
flags and the linked install, Settings, registry, or marketplace documentation
rather than repurposing them to prepare a source candidate.

| Surface | Commands |
| --- | --- |
| Installed inspection | `hdev plugins list`, `hdev plugins show <pluginId>`, `hdev plugins actions <pluginId>`, `hdev plugins logs <pluginId>` |
| Installed lifecycle | `hdev plugins enable <pluginId>`, `hdev plugins disable <pluginId>`, `hdev plugins rollback <pluginId>`, `hdev plugins uninstall <pluginId>` |
| Settings and secrets | `hdev plugins settings list <pluginId>`, `hdev plugins settings get`, `hdev plugins settings set`, `hdev plugins settings reset`, `hdev plugins settings secret status`, `bind`, `unbind`, and `delete` |
| Private registries | `hdev plugins registry add`, `login`, `test`, `logout`, `remove`, and `list` |
| Marketplace sources | `hdev plugins marketplace sources list`, `add`, `enable`, `disable`, and `remove` |
| Marketplace listings | `hdev plugins marketplace list`, `show`, and `install` |
