---
title: Install and trust
description: Review plugin code before execution and let the daemon own installed state.
---

`hdev plugins install` validates package and manifest facts before executing
plugin code. When approval is required, an interactive terminal presents one
**Install & Trust** decision for the whole package and its declared executable
realms.

```bash
hdev plugins install <path-or-archive>
hdev plugins install @scope/package --kind npm --selector 0.1.0
```

The active daemon owns preparation, activation, validation, installed state,
enable/disable, update, and uninstall. A client does not import the plugin to
pre-validate it. If the displayed package, manifest, artifact, or source facts
change before approval is applied, the operation fails and must be reviewed
again.

For local authoring, use `hdev plugins dev`. The daemon owns replacement and
validation while the author command automatically observes the source. For an
intentional watcher-free refresh of a package root, use the same development
source and reload from that root:

```bash
hdev plugins install . --dev
hdev plugins reload
```

When the package root is ambiguous or the command runs elsewhere, select the
plugin explicitly: `hdev plugins reload com.example.my-plugin`. Both routes
preserve the last accepted generation when validation rejects a change.

### Trust a development source on the command line

An interactive terminal answers the source-root question with a prompt. When no
present user can answer it — a CI job, a script, or an Agent Session driving the
authoring loop — carry the same decision on the command line:

```bash
hdev plugins install . --dev --trust --json
hdev plugins reload --json
```

`--trust` is the only non-interactive approval Happier accepts. It is scoped to
the one development source it names:

- Valid only with `--dev` on a local path; any other request fails with
  `plugin_explicit_trust_requires_development_path`.
- Decides source-root trust and package trust for that one resolved path, and
  records the decision as an explicit CLI trust flag rather than a prompt.
- Cancels the pending change with `plugin_explicit_trust_target_mismatch` when
  the daemon's prepared review names any other source, so a substituted source
  is refused instead of trusted.
- Selects no optional host resources, and does not extend to consequential
  updates or secrets. Those remain present-user decisions.

Once the source root is trusted, later requests for that root skip source-root
review until the reviewed source identity changes.

Plugin cleanup is an author callback returned by `setup` in a successful
`definePlugin(...)` module; generated activation returns it after registration.
Happier calls it when that activation is no longer serving. Plugin code does
not persist or select installed state.

## Install, update, rollback, and uninstall

Install an archive emitted by `hdev plugins pack`:

```bash
hdev plugins install ./my-plugin-0.1.0.tgz --kind archive
```

Install an exact npm version:

```bash
hdev plugins install @scope/my-plugin --kind npm --selector 0.1.0
```

To update an installed plugin through the daemon's existing trusted channel,
run:

```bash
hdev plugins update com.example.my-plugin
```

For an approved curated npm channel with the `automatic` policy, this explicit
command selects a compatible newer release and can apply it without another
trust prompt only while the reviewed source binding, package identity, host
access, executable realms, and compatibility projection remain compatible.
`automatic` does not poll registries or install updates in the background.

To replace an archive or select an exact npm version yourself, use
`plugins install`. The daemon recognizes the existing plugin identity, applies
the source's update policy, and preserves the last applied generation if the
candidate fails validation:

```bash
hdev plugins pack . --out ../my-plugin-0.2.0.tgz
hdev plugins install ../my-plugin-0.2.0.tgz --kind archive
```

A new archive is a one-off source and requires review. An eligible trusted npm
channel or approved development source can reuse its existing update policy
only while the source identity and reviewed authority remain compatible.
Source substitution, widened executable realms, or widened required host access
requires review again.

Restore the retained prior generation through the same daemon owner:

```bash
hdev plugins rollback com.example.my-plugin
```

Rollback is available only while the prior immutable bytes are retained and
still verify. It is distinct from automatic last-known-good recovery.

Ordinary uninstall removes the installed plugin and preserves its storage,
settings, and valid secret/account references:

```bash
hdev plugins uninstall com.example.my-plugin
```

Irreversible data deletion is a separate explicit action:

```bash
hdev plugins uninstall com.example.my-plugin --delete-data --yes
```

Inspect installed state after an `outcome_unknown` result instead of blindly
replaying a mutation:

```bash
hdev plugins show com.example.my-plugin
```

## Review rejoin after a daemon restart

A pending review ID is rejoinable only during the same daemon lifetime. If
`hdev plugins change status <pendingChangeId> --json` reports `expired`
after a daemon restart, rerun the original development or install request and
review the newly prepared facts; do not reuse the old pending ID. This is not
the same as `outcome_unknown`: inspect installed state before deciding whether
to replay that mutation.

Settings -> Plugins lists the reviews the selected machine's daemon is still
holding, so a review you no longer have an ID for stays decidable there for
that daemon lifetime.
