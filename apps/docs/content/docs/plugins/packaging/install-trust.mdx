---
title: Install and trust
description: Review plugin code before execution and let the daemon own installed state.
---

`hdev plugins install` validates package and manifest facts before executing
plugin code. When approval is required, an interactive terminal presents one
concise install decision naming the trusted code, selected machine, executable
realms, and authority or credential access being granted. Technical package,
integrity, compatibility, and provenance evidence remains available in the
details; it does not create another decision.

```bash
hdev plugins install <path-or-archive>
hdev plugins install @scope/package --kind npm --selector 0.1.0
```

The active daemon owns preparation, activation, validation, installed state,
enable/disable, update, and uninstall. A client does not import the plugin to
pre-validate it. If the displayed package, manifest, artifact, or source facts
change before approval is applied, the operation fails and must be reviewed
again.

## Visibility and execution machines

In 0.3 development source, app-level plugin UI is discovered across the Account's
machines before an execution machine is chosen. Installing Channels on one machine
and Triage on another does not make either disappear when you change targets.
Missing declarations stay preparing, and conflicting versions or UI content stay
visible as a conflict rather than running an arbitrary copy.

Machine-free UI has no execution-machine picker. When a plugin needs a machine,
Happier uses your valid saved preference first, then the plugin's admitted
installation default, then a sole eligible compatible installation; otherwise you
choose a target. A saved offline target remains selected and unavailable until it
recovers or you explicitly change it. Invocation checks the exact target again,
including after approval.

Installation administration remains machine-specific: install, installation settings,
Secrets and Browse operate on the named administration machine. Appearing in the
Account's installed list does not mean a plugin is enabled, trusted or executable.

For local authoring, use `hdev plugins dev`. The daemon owns replacement and
validation while the author command automatically observes the source. For an
intentional watcher-free refresh of a package root, use the same development
source and reload from that root:

```bash
hdev plugins install . --dev
hdev plugins reload
```

When the package root is ambiguous or the command runs elsewhere, select the
plugin explicitly: `hdev plugins reload com.example.my-plugin`. Both routes
preserve the last accepted process-local occurrence when validation rejects a
change. A daemon restart evaluates current development source again; it does
not restore that earlier occurrence from an immutable installation.

### Trust a local path on the command line

Naming a local path in an explicit install command is the code-trust action, so
Happier does not ask the same question again:

```bash
hdev plugins install . --dev --json
hdev plugins reload --json
```

That intent is scoped to the exact resolved path:

- It decides source-root and package code trust for that resolved path.
- Cancels the pending change with `plugin_explicit_trust_target_mismatch` when
  the daemon's prepared review names any other source, so a substituted source
  is refused instead of trusted.
- Selects no optional host resources, and does not extend to consequential
  authority or credential grants. Those remain with their existing host owners.

Once the source root is trusted, later requests for that root skip source-root
review until the reviewed source identity changes.

Plugin cleanup is an author callback returned by `setup` in a successful
`definePlugin(...)` module; generated activation returns it after registration.
Happier calls it when that activation is no longer serving. Plugin code does
not persist or select installed state.

## Install, update, rollback, and uninstall

Install an archive emitted by `hdev plugins pack`:

```bash
hdev plugins install ./my-plugin-0.1.0.tgz --kind archive
```

In the current Developer Preview source, archive URLs keep all query parameters
for later updates. Happier saves the full URL in the selected machine's local
plugin state, including any credentials or signed access parameters it contains.
The install review warns about this retention. Use a URL you are comfortable
storing there; an expired or revoked URL can make a later update fail.
Parameters removed by an earlier build cannot be recovered from the saved
record. Reinstall with the original full URL and review it again to restore
that update source.

Install an exact npm version:

```bash
hdev plugins install @scope/my-plugin --kind npm --selector 0.1.0
```

To update an installed plugin through the daemon's existing trusted channel,
run:

```bash
hdev plugins update com.example.my-plugin
```

Every installed plugin has one update-eligibility setting under **Settings ->
Plugins**:

- **Pinned** — the update is refused until you choose another policy.
- **Updates allowed** — an authority-neutral update applies without another
  prompt. Happier asks only when the canonical comparison finds new or widened
  declared authority, and shows that delta. Identity, integrity, compatibility,
  and trusted-channel checks still reject a candidate that cannot be admitted.

No setting polls
registries or installs anything in the background — Happier selects and
stages a newer release only when you run `plugins update` or request the
update in **Settings -> Plugins**.

To replace an archive or select an exact npm version yourself, use
`plugins install`. The daemon recognizes the existing plugin identity,
reviews the candidate under the applicable update policy, and preserves the
last applied generation if the candidate fails validation:

```bash
hdev plugins pack . --out ../my-plugin-0.2.0.tgz
hdev plugins install ../my-plugin-0.2.0.tgz --kind archive
```

A newly supplied archive requires review, as does an exact npm version you
select yourself. Update requests carry no source of their own:
`plugins update` rebuilds the artifact request from the plugin's trust record
— the same saved archive path or URL, or the same npm registry origin, package,
and registry profile it was trusted from — so it cannot be pointed at a different
source.

An installed plugin is trusted code, so an update that only adds
contributions or ships a new executable realm (for example a new React
Native surface) applies without asking. What an update can ask about is the
reach you granted: widened required host access, new Connected Account
purposes, wider request-interceptor reach, or wider raw-credential access.
**Settings -> Plugins -> Update review** decides what happens then:

- **Confirm access changes** (the default) opens a delta-only decision.
- **Apply automatically** applies the update without asking. Optional access
  you granted carries over only where the new declaration still fits inside
  it; anything wider is dropped and stays off until you turn it on again.

The preference belongs to your Account, so it applies to every machine you
sign in on. It covers marketplace, npm, archive, and local path installs.
Development plugins never ask on change. The per-plugin update policy
(`allowed` or `pinned`) still decides whether an update is allowed at all.

### Private registries

A private registry is always your explicit choice on the machine that installs.
When an install needs a registry this machine has no usable registry profile
for — the registry refused an anonymous request, the marketplace source is not
bound to a profile, or the bound profile needs signing in again — the daemon
stops before anything is downloaded or reviewed and reports
`plugin_registry_profile_required` with the exact registry origin and package,
and the existing profile for that registry when there is one.

In **Settings -> Plugins -> Discover**, such a listing is marked as needing a
registry profile for its registry, and Install asks in place. The dialog opens the
registry profiles for that one listing: add a profile (prefilled with the
registry's address and the package's scope), sign in to it, and bind it to the
listing's marketplace source. **Continue** asks the daemon again, which prepares
the Install and Trust review or names what is still missing. **Cancel** ends the
install with nothing downloaded.

From the terminal, add or sign in to that profile with
`hdev plugins registry add|login`, bind it to the marketplace source when the
listing came from one, and run the install again. Signing in checks the token
against the registry at once, so a refused token is reported immediately;
`hdev plugins registry test` checks the profile again later.

Restore the retained prior generation through the same daemon owner:

```bash
hdev plugins rollback com.example.my-plugin
```

Rollback is available only while the prior immutable bytes are retained and
still verify. It is distinct from automatic last-known-good recovery.

Ordinary uninstall removes the installed plugin and preserves its storage,
settings, and valid secret/account references:

```bash
hdev plugins uninstall com.example.my-plugin
```

Irreversible data deletion is a separate explicit action:

```bash
hdev plugins uninstall com.example.my-plugin --delete-data --yes
```

Inspect installed state after an `outcome_unknown` result instead of blindly
replaying a mutation:

```bash
hdev plugins show com.example.my-plugin
```

## Review rejoin after a daemon restart

A pending review ID is rejoinable only during the same daemon lifetime. If
`hdev plugins change status <pendingChangeId> --json` reports `expired`
after a daemon restart, rerun the original development or install request and
review the newly prepared facts; do not reuse the old pending ID. This is not
the same as `outcome_unknown`: inspect installed state before deciding whether
to replay that mutation.

Settings -> Plugins lists the reviews the selected machine's daemon is still
holding, so a review you no longer have an ID for stays decidable there for
that daemon lifetime.

## Temporary computers install through this same review

A [Temporary computer](/sessions/temporary-computer) starts with no plugins
beyond the ones the Happier Runner artifact already carries. When the session's
agent is contributed by an installed plugin, the creator seals the exact
distribution commitment — plugin id, package name, registry origin, version,
integrity and manifest digest — into the reviewed launch material, taken from
the marketplace index of the machine whose Agent catalog the agent was chosen
in.

The endpoint prepares that install through the same canonical change owner
documented above, against the temporary computer's own activation-local Happier
home, and renders the resulting installation review inside the one consent
screen the endpoint user already decides on. Allow performs Install and Trust
and yields one immutable generation; Decline installs nothing. There is no
Runner-specific registry, trust tier, or installer, and an external plugin gets
the same capabilities a bundled one does.

Three boundaries follow from that:

- A plugin installed from a working folder or a local archive has no published
  listing, so no commitment exists for a fresh computer to acquire. Its agents
  are shown as unavailable for a Temporary computer with that reason.
- A listing from a catalog source only the creator's machine has configured is
  acquired from that same reviewed source: the endpoint adds it to the
  activation-local home without any registry profile.
- A plugin published on a private registry asks the endpoint user to sign in to
  that exact registry before the installation review appears. The token is
  stored only in the temporary computer's own registry profile and nothing from
  the creator's account or machine is used. Declining declines the request.
