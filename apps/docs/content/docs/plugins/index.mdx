Happier plugins extend the local runtime without changing Happier core source code. A plugin can contribute actions, tools, commands, hooks, UI surfaces, settings, MCP integrations, SCM integrations, and AI Agents.

Code-defined authoring source is the development authority. `definePlugin(...)`
projects the cold `.happier-plugin/plugin.json` manifest during packing, so
installed discovery can read catalogs, settings, requested host access,
installation review, and UI surfaces without executing plugin code. Executable
plugin code is trusted code, not sandboxed code.

## Core model

- **Author module**: `definePlugin(...)` declares identity, entrypoints, host
  access, contribution descriptors, and executable handlers in one typed
  source owner.
- **Manifest projection**: pack writes the cold JSON required for installed
  discovery from that author module.
- **Activation API**: the generated `activate(api)` binds the declared
  executable handlers through nested capability families.
- **Invocation context**: action and hook handlers receive bounded identity, cancellation, and services.
- **Cross-plugin contribution protocol**: a feature-owned value lets a target
  declare points and a contributor bind existing Actions to operation roles;
  the host retains admission, currentness, and dispatch.
- **Agent runtime**: a plugin-owned `AgentRuntime` for a custom Agent, supplied
  as `agents.<id>.factory` in `definePlugin(...)`. Generated activation binds
  it; declarative ACP Agents are host-owned and do not register a factory.
- **Runtime host**: Happier-owned session and execution-run orchestration. Agent leaves map Agent-specific behavior into shared runtime contracts.

## Preview authoring rules

- The author-owned `index.public.ts` sources and current package export map
  define intended author paths. Use the root or final capability path, such as
  `/agents/runtime`; do not use `experimental/*`, `internal/*`, or
  undocumented source paths. Publisher-generated inventories are derived
  artifacts, not a second authoring owner.
- Do not import Happier internal packages from a plugin.
- Keep projected facts and executable declarations together in
  `definePlugin(...)`; let pack produce the installed manifest.
- Bind executable code through the generated `activate(api)` and declared ids.
- Use host-provided invocation and Agent runtime contexts. Do not shell out or read host internals directly when a service exists.
- Keep Agent-specific behavior inside the plugin-owned Agent runtime leaf.
- Do not write Happier transcript rows, session rows, or execution-run state directly from agent code.

The SDK is one package-level **Developer Preview** source contract. The
workspace package is private at `0.0.0` on a prepublication hold, so this is
not an installable public release or a released-semver compatibility promise.
Use the current public entrypoint inventory and capability matrix for the
authoring contract; do not infer a different stability tier per export.
Preview status does not waive correctness, install safety, lifecycle cleanup,
security disclosure, or documentation.

## Where plugin code runs

Daemon plugin code runs through `entrypoints.daemon` or, in the development loop, `entrypoints.development`. React Native plugin UI runs as trusted code in a supported client realm. Packaged hosted web availability is per host: each host reports the one frame adapter it can construct, or a typed reason when it cannot, so the surface is available on some hosts and unavailable on others — see [Hosted web UI](/plugins/ui/hosted-web#build-and-runtime-availability). Declarative UI is rendered by the host. Installation is a whole-package trust decision across these surfaces.
