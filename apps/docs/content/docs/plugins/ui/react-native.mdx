title: React Native UI
description: Build trusted, native-feeling plugin UI for supported Happier clients.
---

React Native is the default executable UI model when a plugin needs a native-feeling, host-integrated surface. Its code is part of the trusted plugin package and runs in the supported client realm; it is not sandboxed.

## Scaffold

```bash
hdev plugins create ./my-plugin \
  --id com.example.my-plugin \
  --name "My plugin" \
  --ui reactNative

cd my-plugin
hdev plugins dev
```

The generated project includes the manifest contribution, semantic Plugin UI
source, compatible build dependencies, and a public SDK build configuration.
The release-owned toolchain packet supplies those versions; do not copy a
separate version matrix into the project.

Before choosing a component or hook, open the shipped [Plugin UI API
inventory](https://github.com/happier-dev/happier/blob/v0.3/packages/plugin-ui/API.md):
`node_modules/@happier-dev/plugin-ui/API.md` in the generated project is the
exact installed inventory. Do not guess exports from examples or app source.

## Coach evaluator values (0.3 development)

An evaluator declares an ordinary dynamic Resource and Action, then registers
them in `activate(api)` through `api.resources.registerDynamicResource` and
`api.actions.register`. The maintained
[public-authoring example](https://github.com/happier-dev/happier/blob/v0.3/packages/plugin-sdk/examples/public-authoring/usageCoach.ts)
returns `UsageCoachFinding` from `@happier-dev/plugin-sdk/actions`. There is no
separate public detector registration family; these registrations do not add a
detector to the built-in Coach. Use the type's closed detector and summary-code
vocabulary.

Each finding needs authorized evidence references and observation times, its
query and evidence keys, a half-open period, coverage and currentness, plus a
basis with dated citations, limitations and advice. `current` requires a
witnessed `asOfMs`; stale or unknown evidence cannot offer Apply. A remedy and
its Action must occur together and identify the same current evidence. Leave
both null for an informational observation, and do not label repeated reads as
measured savings. Reads and handlers honor cancellation; changing Resource
producers invalidate through `observe` and dispose subscriptions on retirement.
This is a development-source contract; check the installed SDK's capability
matrix before targeting a published host.

## Row status line (0.3 development)

Use `RowStatusLine` under a row title for compact status words and one next
action. `quiet` shows secondary text; `warn` and `bad` add a coloured trouble
indicator. `busy` adds a spinner without hiding that indicator or the action.
The caller supplies translated words and owns the operation's lifecycle.

```tsx
import { RowStatusLine } from '@happier-dev/plugin-ui/components';

<RowStatusLine
  text={signingIn ? 'Waiting for sign-in' : 'Sign in needed'}
  tone="warn"
  busy={signingIn}
  action={{ label: 'Sign in', onPress: startSignIn }}
/>
```

Rows default to one truncating line; pass `numberOfLines={2}` inside a card.
For an announcing notice, use `Status` instead. Check the installed package's
API inventory before using this development-source addition.

## Find and Search (0.3 development)

A trusted same-realm surface can join the host's Find shortcuts and `ui.find`
Action with `useFindSurfaceRegistration` from
`@happier-dev/plugin-ui/hostApi`. Register a plugin-qualified `surfaceId`, the
surface's `FindController`, and its current focus/open/input-focus callbacks.
Pass `null` while the surface has no findable content. The hook returns false
when no host registration binding is available; it does not install listeners
or search content itself. Hidden mounts cannot receive targeted Find commands.

Use `HappierFindBar` and the pure `matchFindText` from `/components` for shared
chrome and matching. `HappierFindHighlightedText` draws half-open UTF-16 ranges,
including overlapping selected matches, with caller-supplied `marks.all` and
`marks.current` styles. `sliceFindRanges` clips those ranges for a snippet.
Nest the renderer in `HappierText` (or your parent Text); it emits inline text segments.
Your surface owns its corpus, coverage, reveal and cancellation.

To add a source to universal Search, declare the existing
[`searchProviders` contribution](/plugins/manifest/contributions#search-providers)
and implement its referenced Action. Native Agent transcript search instead
uses the External Sessions source's `contentSearch` declaration and existing
transcript readers; it does not create a plugin-owned index.

## Host API

Export a semantic surface. `@happier-dev/plugin-ui`'s `defineUiSurface` owns
provider installation around the host-supplied render context, so components
and Actions share the same bound host API:

```tsx
import * as React from 'react';
import { Action, Card, defineUiSurface, Text } from '@happier-dev/plugin-ui';

function PluginPanel() {
  return (
    <Card>
      <Text variant="title" value="My plugin" />
      <Action.Execute action="save-note" input={{ note: 'hello' }} title="Save note" />
    </Card>
  );
}

export const renderSurface = defineUiSurface(PluginPanel);
```

The managed UI build targets the one initial **Host API 1.0.0** contract.
Authors do not configure an API range, select a second Host API tier, or add a
version-sniffing fallback: consume the bound host API supplied to the admitted
surface and handle its typed unavailable or cancellation result.

`@happier-dev/plugin-sdk/ui/client` is the hosted-web bootstrap client; do not
use it from a React Native renderer. Use the curated `plugin-ui` controls for
semantic UI. `react-native` is a host-provided framework singleton, not a
Happier component contract: a plugin-owned implementation may use compatible
primitives only when the generated toolchain declares framework support for
that artifact. Do not use them to recreate a curated control, host provider,
bridge, or navigation root, and do not assume host styling, overlay, focus, or
navigation behavior. Never manually install a host provider, pass a
host-internal surface or transport object, or import Happier app internals.

The `/components` entry is the author UI layer; the root re-exports it.
Trusted React Native and React Native Web authors who need custom composition
use those same `/components` exports for shared RN/RNW primitives and behavior
or `/environment` for theme, localization, accessibility, platform, and inset
facts, hooks, and a standalone fact provider. `/components` never re-exports
environment contracts, so import `/environment` directly for that role. Both
advanced tiers share canonical core implementations, remain prepublication work
in progress, and carry no released stability promise while the package is held.
`@happier-dev/plugin-ui/advanced` is reserved for isolated tests and complete
standalone mounts that genuinely own provider/Resource lifetime. It does not
permit an admitted surface to construct a host provider, access internal mount
state, or import app, host, or protocol internals. Keep
`defineUiSurface` as the sole provider installation boundary.

### Floating frames in development

`FloatingFrame` is the controlled frame shared with Happier's Session viewer.
The public component supplies theme and reduced-motion defaults; the neutral
primitive is also available as `HappierFloatingFrame` from `/components`. Supply the frame rectangle,
available space, body aspect and measured obstacles. The shared geometry owner
handles corner placement, usable minimum width and a request to dock when the
picture cannot fit. Your domain still owns the mode and settled rectangle.

In the native app, the host supplies finger drag through its optional
`companionNativeFrame` presentation binding. Only a floating frame with
`moveInput="surface"` moves by its body; use `moveInput="chrome"` while the
content owns input. In either mode, chrome backgrounds move the frame and the
corner grip resizes the picture while preserving its aspect ratio. Registered
no-drag controls keep their presses, and keyboard/menu placement remains
available. A custom same-realm host can supply `nativeBinding`, a React
component accepting `HappierFloatingFrameNativeBindingProps` from
`/components`; render its supplied `grip` with the host's resize binding. Keep native gesture/animation dependencies in that host, not
the plugin bundle. Without a native binding, placement is keyboard/menu only.
These are 0.3 development-source interfaces, not a shipped native-device QA
claim; Happier phone viewers continue using their sticky slot.

### Artifact presentation in development

The prepublication `/components` tier includes `HappierArtifactPreviewCard`,
`HappierHtmlSandboxFrame`, `HappierPublicLinkCard`, and
`HappierArtifactRevisionList`. Happier core uses these same presentation owners.
Supply localized labels, theme facts, and their typed rendering bindings rather
than importing app components. Preview cards consume already available content;
revision rows consume the canonical owner's saved revision facts.

These components do not authorize publication, fetch Artifacts, retain bearer
secrets, or restore revisions. Those operations remain with the admitted host
services. `HappierHtmlSandboxFrame` owns reading-area geometry and state
presentation only: its typed `renderFrame` binding must enforce the host's URL
admission, isolated origin, platform sandbox and navigation policy. Passing HTML
to a frame does not establish an execution sandbox. Consult the installed API
inventory for the exact bindings; this development surface is not a released
stability or platform-certification promise.

### Field boxes in development

For ordinary forms, use the semantic `Select` and `TextField` controls. Custom
adapters can use the same field visuals from
`@happier-dev/plugin-ui/components`. These are **unreleased 0.3 development
interfaces**; check your installed API inventory before using them.

`HappierFieldBoxTrigger` draws a select's box around `children`, with optional
`leading` and `trailing` content. Supply `colors` for the border and background,
and optionally its raised `edge` and `focusRing`. It is a visual, so its enclosing
trigger owns pressing, keyboard focus, accessible naming and expanded state.
`span` chooses content width (`content`, the default), a page-field column
(`column`), the whole row (`row`), or intrinsic toolbar width (`intrinsic`).
`density="chip"` uses a compact borderless pill. `boxRef` identifies the drawn
box for an adapter that anchors its choices there.

Use `resolveHappierFieldBoxLabel({ value, placeholder, colors })` to obtain
`{ text, placeholder, style }` for your text renderer: an empty, null or undefined
value shows the supplied placeholder. Its colors are `valueColor` and
`placeholderColor`. `HappierFieldBoxChevron` takes `open`, `color` and optional
`size`; it points up while open and is decorative.

`HappierFieldTextBox` frames your input and optional `error` node with the same
border/background/edge colors. Style the child input with
`resolveHappierFieldTextInputMetrics({ multiline, minLines,
nativeMinimumTargetSize, presentation })`. Match the box's `multiline` and
`presentation` to those metrics; `presentation="document"` gives long prose a
roomier reading treatment. Your input owns its value, label, caret, validation
and submission, and your error renderer owns its alert semantics.

`HappierSearchFieldBox` frames a child search input with `colors`, a `radius`,
optional `leading`/`trailing` content and `minimumTargetSize`. Supply
`onFocusInput` to focus your input when the field's padding or border is pressed.
The wrapper adds no keyboard stop or accessible name; label the input itself.
It does not search or retain a query. A custom material adapter may use
`renderSurface({ style, children })` while retaining the shared focus target.

## Collection filters and saved views (0.3 development)

The prepublication `/components` surface exposes the same pure filter evaluator
and typed field factory used by host collections: `compileEntityListFilterV1`,
`defineEntityFilterFieldV1`, and `createPluginListFilterFieldRegistryV1`.
Admit your plugin-owned field declaration and scalar, set, boolean or absolute
time value before supplying held facts. Missing or retired fields evaluate as
unavailable; they never silently turn a saved selection into a match-all view.
Evaluation does not activate a plugin, invoke Actions, read Resources or start
watches. Your existing source owns acquisition and retirement.

The same public import exposes `conditionModelFromFilter` and
`applyCollectionConditionEdit` for the shared condition editor. Its
`CollectionConditionBindings.evaluator` defaults to `list`; use `daemonRule`
only with fields whose registry declares that support. Unsupported fields are
not offered for new conditions, and stored unsupported conditions remain
unavailable. The current plugin-field adapter declares list support only.
Host Follow and matching-session routing editors use `daemonRule`, so list-only
Branch, Needs-you and plugin conditions cannot be saved as executable rules.

`useCollectionSavedViewsControl` supplies controlled select/create/rename/update/
delete presentation without owning storage. Give it admitted items, localized
labels, the selected identity, mutation callbacks and the captured authority's
stable `scope`. In an admitted surface, the existing `usePluginHostApi()` facade
is bound to that Account lifetime and can supply this scope. A scope change
retires private naming drafts, and stale callbacks cannot replace the next
scope's presentation. Create and rename callbacks return acceptance; a refused
write keeps the draft available for correction.

The shared picker does not prescribe persistence: Triage keeps saved views and
its selected view in Account storage, while host spaces keep their selection on
the device. Host Resource-backed row fields are deferred; a plugin-owned page
can supply its own held custom facts through the pure adapter without importing
host or protocol internals. These are development-source contracts; check the
installed Plugin UI inventory before targeting a published package.

## Resource states (0.3 development)

Pass the `resource` snapshot from `usePluginResource` or `useLivePluginResource`
directly to `State`, and pass the hook's `refresh` as `onRetry`. `State` keeps
admitted content mounted while refreshing or after a failed refresh, with one
freshness line and recovery action. Before the first successful read it shows
loading or an error with Retry. Set `isEmpty` when your decoded content is empty;
the component does not infer emptiness from Resource bytes.

For typed shared content in unreleased 0.3 source, keep a stable
`PluginUiResourceProjection` descriptor and use
`useLivePluginResourceProjection(reference, projection, selector, { enabled })`.
Its `decode(content, previous)` admits content once per descriptor at the
shared Resource entry and can retain unchanged domain values. The selector
receives the typed value and independent freshness, pending, error and
subscription dimensions; unchanged selections do not notify consumers.
Set `enabled: false` for an undemanded body so it opens no read or watch.
This hook uses the same Resource lifetime, not a separate reader or poller.
Check the installed Plugin UI inventory before targeting this source addition.

`SceneArt` from `/components` renders a built-in or authored scene through the
same host renderer used by `EmptyState`. A host without that renderer supplies
no art. These are development-source interfaces; check your installed API
inventory before using them.

## Chart family (0.3 development)

Use the shared chart family for hierarchical proportions, time series, capacity,
per-core load and a compact explanatory state. This family is approved for the
**0.3 development author API**, not shipped package availability. The author-layer
migration carries the family and its geometry helpers together into
`@happier-dev/plugin-ui/components`. The examples require that migration;
check your installed API inventory for these exports before using them.

Inside a `defineUiSurface` component, read `theme` with `usePluginTheme()` and
`reducedMotion` with `usePluginAccessibility()` from the package root. These are
public facts; none of the charts needs an app store or a host transport object.
The examples use this shared input:

```tsx
import {
  CapacityBar, CoreLoadBars, HappierStateLine, StackedSeriesChart, Sunburst, Treemap,
  type HappierChartPart,
} from '@happier-dev/plugin-ui/components';
import { Text, usePluginAccessibility, usePluginTheme } from '@happier-dev/plugin-ui';

const parts = [
  { key: 'projects', label: 'Projects', value: 60, valueLabel: '60 GB', tone: 'accent' },
  { key: 'archives', label: 'Archives', value: 40, valueLabel: '40 GB', tone: 'ink' },
] satisfies readonly HappierChartPart[];
const smallerLabel = (count: number) => `${count} smaller items`;
// In your component:
// const theme = usePluginTheme();
// const { reducedMotion } = usePluginAccessibility();
```

### Treemap

`Treemap` draws weighted rectangles with optional children. Its props type is
`HappierTreemapProps`. Supply `theme`, `items`, pixel `width` and `height`,
`minNodePx: { width, height }`, `accessibilityLabel` and a localized
`smallerLabel(count)`. Each `HappierChartPart` has a stable unique `key`, `label`,
nonnegative finite `value`, exact localized `valueLabel`, and `tone` (`ink`,
`accent` or `quiet`). Optional `children` describe the next level; `hatched`,
`dotted` and `locked` are visual facts, not permission enforcement.

Use `accentColor` to override the accent. `pointedKey` controls the highlighted
part; omit it for internal pointing, or pass `null` for no pointed part.
`onPointAt(key | null)`, `onOpen(key)`, `onCollect(key)` and `onUp()` let your
view own selection, drilling and collection. `renderTooltip(key)` adds context;
`testID` identifies the chart. No callback performs a storage operation itself.

The chart has one keyboard stop: arrows move between parts, including folded
smaller-items groups, Enter opens the pointed part or folded group with the same
key as pointer activation, Space collects, and Backspace/Escape goes up. Keep an
equivalent labelled list beside the picture for exact values and actions; a
tooltip alone is insufficient.
`reducedMotion` overrides the environment preference; reduced motion replaces
the level immediately rather than cross-fading it.

```tsx
<Treemap theme={theme} items={parts} width={400} height={240}
  minNodePx={{ width: 56, height: 20 }} accessibilityLabel="Storage map"
  smallerLabel={smallerLabel} reducedMotion={reducedMotion} />
```

For custom geometry, `layoutHappierTreemap(nodes, options)` returns `{ tiles }`
including `key`, `parentKey`, `depth`, `rect`, `value`, `labeled` and `folded`
keys. `HappierTreemapNode` contains only `key`, `value` and optional `children`;
`HappierTreemapLayoutOptions` takes `width`, `height`, `minNodePx` and optional
`gapPx`/`headerPx`. `squarifyHappierTreemap(items, bounds)` returns key/rectangle
pairs inside a `HappierTreemapRect` (`x`, `y`, `width`, `height`).
`createHappierTreemapHitGrid(tiles, size, cellPx?)` returns an `(x, y)` lookup
that selects the deepest matching tile or `null`. Coordinates are chart-local
pixels. `HAPPIER_TREEMAP_SMALLER_SUFFIX` identifies synthetic folded keys; keep
these distinct from authored keys. These pure helpers do not render, announce,
animate or grant actions.

### Sunburst

`Sunburst` shows hierarchical shares as concentric rings. `HappierSunburstProps`
shares the Treemap's `theme`, `items`, dimensions, accent, pointing, callbacks,
tooltip, localized smaller-items label, accessibility label and `testID`.
Supply `minArcDegrees`, `centerLabel` and `centerValue` as well. Optional
`upLabel` names the parent. `gapDegrees` reserves an uncounted wedge, and
`gapLabel: { name, note }` explains it; the gap is not another observation.

Keyboard arrows traverse the rings and their hierarchy, Enter opens, Space
collects, and Backspace/Escape goes up. Keep the same exact-value list as for a
Treemap. `reducedMotion` uses a short cross-fade instead of the normal geometry
morph; it does not mean every transition is instantaneous.
Pointer and touch hit tests follow the currently drawn arcs throughout a morph,
including when another drill retargets a transition already in progress.

```tsx
<Sunburst theme={theme} items={parts} width={400} height={408} minArcDegrees={2}
  centerLabel="Storage" centerValue="100 GB" accessibilityLabel="Storage rings"
  smallerLabel={smallerLabel} reducedMotion={reducedMotion} />
```

`layoutHappierSunburst(nodes, options)` returns `{ arcs }` with keys, parent keys,
ring `depth`, `a0`/`a1`, value and `folded` keys (or `null`). `HappierSunburstNode`
has `key`, `value` and optional `children`; options take `rings` (each
`HappierSunburstRing` has `inner`/`outer` pixel radii), `minArcPx` and optional
`gapRadians`. Geometry angles are **radians from twelve o'clock, clockwise**;
the component's angular props are degrees. `hitHappierSunburst(arcs, rings,
{ cx, cy }, x, y)` returns a key or `null`, including `null` in the central
hole. `HAPPIER_SUNBURST_SMALLER_SUFFIX` marks synthetic folds. These pure
helpers own neither motion nor interaction accessibility.

### StackedSeriesChart

`StackedSeriesChart` draws `bar`, `line` or `area` series at `inline`, `tile` or
`full` size. `StackedSeriesChartProps` requires `theme`, `label`, `series`,
`variant` and `size`. A `HappierSeries` has an `id`, `label`, optional color and
`points`; optional `detail`, `lineStyle` (`solid`/`dashed`/`dotted`),
`fillPattern="hatch"` and `fillOpacity` describe the series' ink and context.
Each point has a stable `id`, `x` label/coordinate and `y` number or `null`, with
optional `label`, `annotation`, `color` and `opacity`. Missing measurements stay
unknown, rather than becoming zero.

Series without an explicit `color` use the ordered ramp from
`theme.colors.dataAccent` against the theme surface. Older snapshots omit
`dataAccent`; the shared chart then uses `theme.colors.accent`.

Use `width`/`viewportHeight` for explicit plot room. `normalized` changes share
geometry while preserving exact numbers; `fitLine`, `minimumMaximum` and
`domain: { min, max }` control the value scale. `strokeWidth`, `plotInset`,
`scaleGutter`, `scaleTicks`, `axisTicks` and `valueFormatter` control its readable
geometry and formatting. `showAxis`, `showLegend`, `showGrid`, `showScaleValues`,
`showReadout`, `showPointLabels`, `showPeakValue` and `showAnnotations` choose
visible context. Provide localized `summary`, `unknownLabel`, `valuesLabel`
and `valuesCollapseLabel` where needed; `testID` identifies the chart.
Each `axisTicks` entry can be a `{ label, bucket }` pair, with a zero-based
bucket index, to put the label at that observation. String ticks spread in order
over the buckets, from the first observation to the last.

Full charts offer a Details control for exact values. Pass `valuesExpanded`
and `onValuesExpandedChange(expanded)` to control that disclosure from your
own UI or agent command. A press requests the next value through the callback;
the chart changes only when you supply the updated prop. Omit `valuesExpanded`
to keep the chart's own initially collapsed disclosure state.

`bands` uses `StackedSeriesBand` (`id`, `lowerSeriesId`, `upperSeriesId`, optional
`color`/`opacity`) to shade caller-produced line bounds. `reference` is a
labelled value; `threshold` adds a labelled warning/error level. `mirrored`
draws supplied negative values below zero while displaying their magnitudes.
`bucketShading` identifies background slots; `barRanges` adds labelled
lower/upper comparison outlines. None invents forecast or policy facts.
Bar geometry takes `barWidth`, `barMaxWidth`, `barSlotWidth`, `barLeadingInset`,
`barGap`, `barMinHeight`, `barTrackColor` and `barEmphasis` (`last`/`maximum`).

`onSelect(bucketId)` reports bucket selection. `onSeriesPress(seriesId)`,
`seriesPressLabel(series, selected)` and `selectedSeriesIds` support a controlled
legend drill; `leads` supplies series-id-keyed identity marks. Advanced render
slots (`renderLinePath`, `renderInk`, `renderBucket`, `renderFrame`,
`renderPlotOverlay`) receive the existing geometry or visual; keep exact values
and keyboard selection with the chart instead of recalculating its scale.
Use the generated API inventory for their full callback signatures.

Full charts expose exact values through their readout/values composition and
keyboard selection; name the chart and retain a useful textual `summary`.
`reducedMotion` disables chart motion. `liveMotion` takes caller-owned
`sampleKey`, `stepPx`, `durationMs` and optional `active`; there is no chart
polling timer. Optional `barMotion` supplies `identity` (`bucket`/`slot`),
`entrance: { durationMs, delaysMs? }` and
`change: { stiffness, damping, mass }`; omit it for static bars.

```tsx
<StackedSeriesChart theme={theme} label="CPU history" variant="line" size="full"
  width={400} reducedMotion={reducedMotion} summary="CPU rose from 20 to 40 percent"
  valueFormatter={(value) => `${value}%`}
  series={[{ id: 'cpu', label: 'CPU', points: [
    { id: 'first', x: '09:00', y: 20 }, { id: 'second', x: '09:01', y: 40 },
  ] }]} />
```

### IntervalTimeline

Import `IntervalTimeline` from `@happier-dev/plugin-ui/components` or the
package root. With `layout="lanes"`, native interaction is one adjustable scrub
target per track, at 44 pt on iOS or 48 dp on Android. Press or drag to select a
run; accessibility increment/decrement steps through the track. Web uses dense
per-run pointer controls. Details retains the exact rows when the plot cannot
fit. The renderer displays caller-supplied coordinates and labels; it does not
infer durations from point events.

### CapacityBar

`CapacityBar` compares an exact `value` against `capacity`. `CapacityBarProps`
requires `theme`, `label`, `value` and `capacity`; either number may be `null`.
Unknown or nonpositive capacity does not produce a scaled meter. `basis` names
the unit and `unknownLabel` localizes missing measurements. `evenPace` and
`projected` add optional values; `projection="remaining"` overlays the projected
remainder on the hatched current remainder, while `marker` uses a marker.

`size`, `height`, `color`, `trackColor`, `markerColor`, `pattern` (`solid` or
`hatched`), `style` and `testID` control presentation. The exact label/value/
capacity description remains accessible; `showCaption={false}` hides only its
visible caption, so a containing row should supply that wording. `animated`
opts into retargetable fill and color motion; `reducedMotion` and the
environment's preference suppress it.

```tsx
<CapacityBar theme={theme} label="Storage in use" value={100} capacity={200}
  basis="GB" animated reducedMotion={reducedMotion} />
```

### CompositionStrip and hatched segments

`CompositionStrip` takes `theme`, `label`, an explicit `total` and `segments`.
Each `CompositionSegment` has `id`, `label`, `value` (a number or `null`) and
optional `color`, `mark` and `pattern`. Use `pattern="hatched"` on a segment
to distinguish a set-aside share in that segment's color. Explain what the
hatch means in its label; the pattern alone carries no accessible meaning or
cleanup authority. This additive API is part of the unreleased 0.3 development
contract, available through `/components`.

The default strip draws the hatch in both its bar segment and legend swatch.
`variant="legend"` keeps only the legend, and `variant="bar"` only the bar;
the `waffle` picture uses solid cells even for a hatched segment, while its
legend retains the hatch. The whole comes from `total`, never a sum of the
segments. Unknown values or overlapping shares keep the exact legend without
inventing a proportional bar. `basis` names the unit and `unknownLabel`
localizes missing values. `valueFormatter` changes visible amounts while
accessible descriptions retain the source amount.

```tsx
import { CompositionStrip } from '@happier-dev/plugin-ui/components';

<CompositionStrip theme={theme} label="Storage in use" total={100} basis="GB"
  segments={[
    { id: 'kept', label: 'Keeping', value: 70 },
    { id: 'review', label: 'Selected for cleanup', value: 30, pattern: 'hatched' },
  ]} />
```

### Byte figures

Use `formatHappierDataBytes(bytes, { kind, locale? })` from `/components` for
byte amounts. `kind` is required: `storage` uses decimal steps of 1,000 for
disk, files, scans and Trash; `memory` uses binary steps of 1,024 for RAM,
processes, swap and ceilings. Both use the labels B, KB, MB, GB, TB and PB;
memory labels are GB rather than GiB. Choose the kind from what the amount
measures, not from the platform or its current magnitude.

```tsx
import { formatHappierDataBytes, formatHappierDataBytesParts }
  from '@happier-dev/plugin-ui/components';

formatHappierDataBytes(1_000_000_000, { kind: 'storage', locale: 'en-US' }); // '1 GB'
formatHappierDataBytes(1_073_741_824, { kind: 'memory', locale: 'en-US' }); // '1 GB'
formatHappierDataBytesParts(1_000_000_000, { kind: 'storage', locale: 'en-US' }); // { value: '1', unit: 'GB' }
```

`formatHappierDataBytesParts` returns localized `value` and `unit` separately
when a layout needs them. The formatter rounds to at most three significant digits;
it formats negative or non-finite inputs as zero, so represent an unknown
measurement explicitly before calling it. These helpers are unreleased 0.3
development API, not evidence of availability in a published package.

### CoreLoadBars

`CoreLoadBars` draws and wraps one bar per CPU core. `CoreLoadBarsProps` requires
`theme`, `label`, `cores` and `coreLabel(core)`. Each `CoreLoadBar` has its actual
`index`, `busyPct` (0–100, or `null` when not reported), and optional `cluster`
(`p` for performance or `e` for efficiency). Performance cores precede
efficiency cores, then unclassified cores; each group sorts by index.

Optional `width` fixes the available width; omission uses measured layout.
`legend: { p?, e? }` supplies localized cluster descriptions, and `testID`
identifies the group. `coreLabel` must name each core and its exact percentage
or unknown state for assistive technology. This owner requests static bars and
has no motion prop; it does not start a sampler or animation loop.

```tsx
<CoreLoadBars theme={theme} label="CPU cores" width={400}

  coreLabel={(core) => `Core ${core.index + 1}, ${core.busyPct === null
    ? 'not reported' : `${core.busyPct}% in use`}`} />
```

### HappierStateLine

```tsx
<HappierStateLine accessibilitySemantics="status">
```

## Personal widget areas in development

In **0.3 development / Developer Preview authoring**, an app-page View can
declare named `widgetAreas`, each with a `name` and a readable `contextSchema`.
Embed the host's personal area using the public component:

```tsx
import { WidgetSurface } from '@happier-dev/plugin-ui';

function PinnedWidgets() {
  return <WidgetSurface area="pinned" />;
}
```

The name must match an area declared by this page. Optional `context` supplies
readable values conforming to that area's schema. Widgets can follow those
values as **This page** or retain their own pinned inputs. The host derives
Home, Account, plugin/page/area identity and rights; context does not supply
machine routing, persistence callbacks or access authority.

The area uses the same Add surface, Edit inputs and frames as Home. Its
personal layout is an Account Artifact, separate from widget definitions and
from a shared Session Board. Copies keep independent inputs, order and
declared size; changing the page context keeps that layout identity. The
[widget size declaration](/plugins/ui#declare-useful-widget-sizes) determines
the useful choices offered by setup and the frame menu. A
declarative plugin page can use a `widgetArea` node against the same host port.
Such nodes are page composition, not Session Board or transcript content.

The host's shared layout tabs let people create a named layout, copy the current
one, switch layouts, rename, reorder and delete their views. Reset and Undo use
the same revision-checked widget Actions when the host supplies a preset;
without one, Reset returns typed unavailable. A page-local
`widgetArea` request can include `layoutId` to address a named layout without
supplying Home, Account or page identity. `widgets.area.layout.select` switches
the answering mounted area; without a mounted area it returns typed unavailable.
Use `widgets.item.list` to read a layout without selecting it. Area declarations
do not supply plugin-authored presets.

The **unreleased 0.3 group contract** lets Home and personal page areas arrange
widgets into non-nesting groups. Groups start with a Card frame and Lines;
each child keeps its own inputs and saved frame. Following inputs use the
group's values before the page's values, while pinned inputs keep their own
selection. A group grants no extra access to a Session, machine or Resource.
WorkBoards, Session Board and direct Companion keep individual widgets.

Saved groups are private Account library fragments, without people sharing or
public links. Adding one creates new group and child placements; editing the
saved group later does not change those placements. Reusable widget definition
references keep their ordinary edit behavior. Gallery's **Your widgets** entries
offer Rename, Duplicate and Delete through the fragment Actions. Delete removes
the saved library entry, not copies already placed in an area.

Host-owned core pages reuse the area layout owner and can supply named
presets. The host renders an absent preset without saving it, saves a personal
layout on the first edit, and guards Reset's Undo against later edits. Plugin
page context cannot supply a preset or create a core-page area.

Copies use the same pointer grip, staged keyboard and Move-to chooser as other
host widgets. Available destinations come from currently mounted surfaces and
their admitted inputs and rights; moving uses the existing widget Action, not
a page-owned layout writer. A retired page or Account cannot start a move.

The component renders its `fallback` where no host presentation bridge exists.
Hosted HTML pages do not embed host widget areas; they manage widgets through
ordinary [widget Actions](/plugins/api/host-actions). This is a development contract, not a released
or loaded-platform support claim; consult the generated
[SDK surface](/plugins/api/surface) and [availability](/plugins/manifest/availability).

### Public-profile templates are a separate development contract

Private widget support does not imply eligibility for
[public profiles](/accounts/public-profiles). Public template admission,
component exports and an end-to-end authoring example are still integration
work. There is no runnable public-profile template example to copy yet. Use the

## Code-defined UI declaration

Declare each executable surface with `@happier-dev/plugin-sdk`'s
`defineUiSurfaceDefinition` and include it in the `ui` family of `definePlugin(...)`.
Packing projects that one declaration into the cold manifest. `appPage` and
`settingsPage` derive the app target, while a Session or Project placement
requires an explicit target.

```ts
import { definePlugin, defineUiSurfaceDefinition } from '@happier-dev/plugin-sdk';

export const mainSurface = defineUiSurfaceDefinition({
  id: 'main',
  placement: 'appPage',
  title: 'My plugin',
  description: { key: 'main.purpose', fallback: 'Review incoming work.' },
  renderer: {
    kind: 'reactNative',
    requiredHostMethods: ['context', 'executeAction'],
  },
});

export const { manifest, activate } = definePlugin({
  id: 'com.example.my-plugin',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  ui: {
    surfaces: [mainSurface],
  },
});
```

`definePlugin(...)` projects the cold manifest and derives the renderer and
artifact id `main-renderer` from the surface id. Export that renderer entry from
the matching package path; the daemon-owned compiler resolves the exact export
and emits one universal CommonJS artifact:

```json
{
  "exports": {
    "./happier-plugin-ui/main-renderer": "./src/ui/mainRenderer.tsx"
  }
}
```

`hdev plugins create --ui …` generates this exact-export shape together with a
`src/index.ts` that projects the same artifact id into `ui.surfaces`. There is no
platform matrix or author-owned bundler configuration.

`requiredHostMethods` is a renderer admission requirement, not a
method-availability claim. Name only the host methods without which the
renderer cannot run. Before mounting, the host compares that declaration with
the mount's factual installed method set; if a requirement is absent, it does
not mount that renderer and can only consider its declared fallback chain. Do
not use this field to choose a container or target, probe for capability, or
invent a plugin-local feature gate.

A renderer names an execution format; a view names the host destination. The
host registry owns the valid renderer/target/container combinations and runtime
availability. Start with the generated `appPage` + `app` view instead of
constructing a guessed surface matrix or manual dispatch path.

When a mounted surface needs to open another declared view, use the host API's
single dispatcher. A local id resolves in the same plugin; the host performs
destination admission, scope compatibility, and navigation:

```tsx
import { Button, usePluginHostApi } from '@happier-dev/plugin-ui';

function OpenReviewDetails({ reviewId }: { reviewId: string }) {
  const hostApi = usePluginHostApi();

  return (
    <Button
      title="Open details"
      onPress={() => {
        void hostApi.openSurface('review-detail', { reviewId }, {
          subPath: `reviews/${reviewId}`,
        });
      }}
    />
  );
}
```

`subPath` addresses only a location under a full-page `appPage`; it is ignored
for a `rightSidebarTab`. Do not build a host URL, router, or a first-available
fallback destination.

## Entity drag and drop (development)

In **0.3 development / Developer Preview authoring**, mount a declared source
and target with the public components inside your ordinary `defineUiSurface`
surface:

```tsx
import { DragSource, DropTarget, Text } from '@happier-dev/plugin-ui';

function ReviewQueue() {
  return (
    <DropTarget targetId="review" input={{ queueId: 'review' }}>
      <DragSource sourceId="issue" reference="issue-42">
        <Text value="Issue #42" />
      </DragSource>
    </DropTarget>
  );
}
```

The local ids must match your [source and target
declarations](/plugins/manifest/contributions#entity-drag-sources-and-drop-targets).
The source's `reference` must satisfy its declared JSON schema. Its registered
`PluginDragSourceRuntime.describe` returns the carried item's readable title
and optional subtitle. The registered `PluginDropTargetRuntime.resolve`
receives the current item, semantic destination, input mode and target-local
input. Return `{ status: 'allowed', effect: { actionId, input, preview } }`,
where `preview` names the verb, target, optional consequence and optional
declared `glyph`, or
`{ status: 'refused', reason: { code, message } }` with an optional preview.
Keep this resolver free of writes: the host resolves again on release and
dispatches the admitted Action through its existing approval policy.

For example, a copy target can return
`preview: { verb: 'Copy', target: 'Review queue', glyph: 'copy' }`.
Choose a bounded named mark from `EntityDropPreviewV1['glyph']` in the SDK's
types (see the generated [SDK surface](/plugins/api/surface)); arbitrary icon
names are rejected. Omission uses the generic `add` mark.
Core and plugin targets use the same field; Happier does not interpret your
Action id or input to choose a mark. The released preview also supplies pending
and settled feedback; refused feedback uses the refusal mark. A mark is
presentation, not permission or a request to execute an Action.

For an early refusal, Happier describes the action as a denial: "Move to Project"
becomes "Can’t move to Project". If your resolver supplies its own complete
translated denial, such as "Can’t put it in Website", declare
`glyph: 'refused'` in that preview to retain its title. Hosts without specific
refusal vocabulary use a localized generic denial. The reason still explains
why the target cannot take the item and what to do next.

To make your reference attachable to a composer, set the source declaration's
`composerAttachment` to one of your own declared attachment local ids. Register
`toComposerAttachment(reference)` alongside `describe`; return a
`ComposerAttachmentAuthorValueV1`, or `null` when the reference cannot be
attached. The host checks the current source and attachment occurrences, then
uses the composer's existing revision-bound transaction to mint the attachment.
This leaves draft text and selection unchanged. Keep only the attachment's
identity and routing value in the draft; its existing dispatch resolver remains
responsible for reading current context when the message is sent.

Declare permitted host Actions with `{ kind: 'host', actionId }`, or a
contributed Action with `{ kind: 'plugin', action: 'local-action-id' }`.
Accepted kinds and permitted Actions constrain admission; they grant no
credentials or present-user authority. Return an explanation when the current
item cannot be used. Do not execute an Action carried inside reference data.

The host supplies current scope, geometry, release feedback and retirement.
Desktop uses the primary row while preserving secondary controls and text
selection. Set `organizing` on `DragSource` only while the surrounding touch
list is intentionally in Organize mode; normal long press remains available
to its menu. Staged keyboard movement and the destination chooser use the same
target resolver. Hidden or retired mounts cannot commit an unissued effect.
OS file handles and file bytes are not custom JSON references.

Declarative documents can use the closed `dragSource` and `dropTarget` nodes;
immutable document/snapshot profiles refuse these live nodes. Hosted documents
use the [public DOM bindings](/plugins/ui/hosted-web#entity-drag-bindings-development)
through their admitted host methods. All presentations join the same mounted
interaction owner. Generated APIs and source tests establish the author
contract; loaded browser/native and publication evidence remain separate.

## Lists, Resources, and Account data

Use `List`, `List.Section`, and `List.Item` from `@happier-dev/plugin-ui` for
host-like lists. Plugin UI owns filter and selection state local to the
component; the shared list owner retains row semantics, accessibility,
virtualization, and host presentation behavior. Do not replace it with a raw
list implementation just to reproduce a curated List surface.

In 0.3 development source, `leadHappierListRows` and
`HappierListOverflowFooter` are public `/components` and root exports for a
bounded list. Call `leadHappierListRows(rows, expanded)` and render its returned
`rows` in their existing order; short lists stay whole. Pass its `hidden` count
to the footer with `theme`, a list `label`, the held `total`, `expanded` and
`onToggle`. It offers Show all / Show less; `complete={false}` uses Show
available. Its optional `unlisted` sentence explains missing source data once
beside the toggle. Supply localized `labels` where needed. Expansion is
caller-owned and does not fetch missing pages.

For a virtualized list, use its `search` and `selection` props: `search` names
the visible filter control and receives the item's local filter predicate;
`selection` reports one stable row key. Both operate only on the `items` array
you passed to this List. They do not create, filter, or paginate a Data query;
keep Account-backed paging and query currentness with the declared Data UI
query instead.

In the **0.3 development / Developer Preview** source contract, an optional
`virtualizer` prop on `List` and `Collection` accepts the public
`CollectionVirtualizer` interface from the root or `/components`
entrypoint. The `presentation` entrypoint is host-internal and rejected by the
artifact build. Most authors should omit it and keep the default native lists.
A custom host adapter renders the supplied flat or sectioned window and its
semantic cells, reports actual scrolling/content size, and publishes a
positioning handle after mount (withdrawing it on unmount). It must preserve
the supplied accessibility and layout facts. Revealing a row mounts its
physical focus target; List still owns focus and selection, and Collection
still owns its viewport memory. An adapter does not expose native refs or
grant data/query authority. `Collection.virtualizer` covers its row and card
Lists; page-scrolling rows continue to use the page's scroller.

For a declared Resource, use `usePluginResource` from
`@happier-dev/plugin-ui`. Use `useLivePluginResource` only when the
surface needs dynamic invalidation: it reads through the same host owner and,
when `watchResource` is available, watches for invalidation rather than a new
payload. It does not poll. Preserve a useful admitted value while a refresh
fails, and do not create a second cache, lifecycle, or currentness owner. Add
the host methods the surface actually needs to `requiredHostMethods` (for
example, `readResource` and, for live updates, `watchResource`).

In the current development SDK, a retained surface marked hidden by its host
releases the Resource hooks' automatic read and watch subscriptions while
keeping the admitted snapshot. Showing it again refreshes through the same
Resource owner. A visible pane remains active even when another pane has focus;
presentation activity is not keyboard authority. A standalone mount without
host activity retains the existing live behavior. Raw imperative
`watchResource` calls remain caller-owned until their unsubscribe function runs.

For Account-backed rows, use `usePluginCollectionQuery` from
`@happier-dev/plugin-ui/data` with a same-plugin, statically declared Data UI
query. The Data owner validates the query, keeps cursor and Account currentness,
reacts to Account changes, and retains last-known-good rows. Do not issue an
arbitrary predicate/index query, construct a data cache, or treat a UI query as
a general Account-storage transport.

For the plugin's own small, Account-portable state — a remembered selection, a
collapsed section, a last-used filter — use `usePluginAccountKv` from
`@happier-dev/plugin-ui/data`. It is the same Account KV service the plugin's
daemon side gets from `services.storage.account.kv`, over the same Account row:
same keys, same per-key versions, the same `expectedVersion` conditional write,
and the same visible tombstone that stops a stale writer from resurrecting a
deleted key. It needs no daemon. Keep growing or queryable records in a
Collection and declared preferences in Plugin Settings; one value never has both
Settings and KV authority. Account KV is not available inside a hosted-web
surface, whose host bridge carries Collection UI queries only.

## A Collection with one detail body

A list that
scrolls with its page (`presentation="list"`, `scroll="page"`) can line figures up
in columns: mark a field `listColumn: true` and wide rows draw it as its own end
column at the field's `minWidth`, with the column titles once at the top of the
first sheet (a service's Ports, Memory and Up). A phone draws no columns; your
`byline` receives `{ fieldColumns }` so it can say those facts on the row's second
line instead. While the columns show, a row-aligned `titleMeta`
(`titleMetaAlign: 'row'`) gives its place to them, so declare that fact as a
field too. Groups that share one page section (`section` on each group) sit on one
sheet under sub-headings that keep their end: "customer-portal · Production"
shortens the shared start first.

In the **0.3 development / Developer Preview** source contract, `Collection`
uses one model and item anatomy for list, table, board and grid presentations.
Its `detail="auto"` adapts the same detail body to the available pane or pushed
phone layout. The caller supplies the route's `openKey` and updates that route
from `onOpenChange`; presentation switches do not create another selection.

This complete composition uses only public imports. `ItemsPage` receives the
route binding and the already-read items from your surface's own data owner:

```tsx
import * as React from 'react';
import { Button, Collection, Icon, Row, Stack, Step, Tabs, Text } from '@happier-dev/plugin-ui';
import {
  HappierDisclosure, HappierPressable, HAPPIER_INSTANT_DISCLOSURE_MOTION,
  useHappierCollection, type HappierCollectionPresentation,
} from '@happier-dev/plugin-ui/components';
import { useHappierUiAccessibility } from '@happier-dev/plugin-ui/environment';

type Item = { id: string; title: string; summary: string };
const keyOf = (item: Item) => item.id;

function ItemDetail({ item, headerHosted, close }: {
  item: Item; headerHosted: boolean; close(): void;
}) {
  const [tab, setTab] = React.useState('overview');
  const [expanded, setExpanded] = React.useState(false);
  const { reducedMotion } = useHappierUiAccessibility();
  return (
    <Stack>
      {!headerHosted && <Row><Text value={item.title} variant="title" /><Button title="Close" onPress={close} /></Row>}
      <Tabs value={tab} onValueChange={setTab} ariaLabel="Item detail">
        <Tabs.Item value="overview" title="Overview">
          <Step marker={{ kind: 'number', value: 1 }} title="The request">
            <Text value={item.summary} selectable />
          </Step>
          <HappierDisclosure
            expanded={expanded} onExpandedChange={setExpanded}
            reducedMotion={reducedMotion} motion={HAPPIER_INSTANT_DISCLOSURE_MOTION}
            showDivider={false}
            header={({ headerProps }) => (
              <HappierPressable {...headerProps}><Text value="More context" /></HappierPressable>
            )}
          >
            <Text value="Additional facts from this item's data owner." selectable />
          </HappierDisclosure>
        </Tabs.Item>
        <Tabs.Item value="activity" title="Activity">
          <Text value="The source's activity belongs here." />
        </Tabs.Item>
      </Tabs>
    </Stack>
  );
}

export function ItemsPage({ items, openKey, onOpenChange }: {
  items: readonly Item[]; openKey: string | null;
  onOpenChange(key: string | null): void;
}) {
  const [presentation, setPresentation] = React.useState<HappierCollectionPresentation>('table');
  const model = useHappierCollection({ items, keyOf, openKey, onOpenChange, expandable: true });
  return (
    <Stack style={{ flex: 1 }}>
      <Row>
        <Button title="Table" onPress={() => setPresentation('table')} />
        <Button title="Board" onPress={() => setPresentation('board')} />
      </Row>
      <Collection
        model={model} presentation={presentation} detail="auto" accessibilityLabel="Items"
        minListWidth={280} minDetailWidth={420} preferredListRatio={0.4}
        anatomy={{
          glyph: () => <Icon name="document-text-outline" />,
          title: (item) => item.title, accessibilityLabel: (item) => item.title,
          columnTitles: { title: 'Item' }, peek: (item) => <Text value={item.summary} />,
        }}
        detailHeader={(key) => ({ title: items.find((item) => item.id === key)?.title ?? 'Item' })}
        renderDetail={(key, { headerHosted }) => {
          const item = items.find((candidate) => candidate.id === key);
          return item ? <ItemDetail item={item} headerHosted={headerHosted} close={model.actions.close} /> : null;
        }}
      />
    </Stack>
  );
}
```

The measurements above are this example's readable pane sizes, not platform
breakpoints. An action inside a row's peek, a card or a detail header takes
`Button size="small"`: the host's desktop control height under a pointer, and
never less than the platform's touch target on a phone. Prose that is read rather
than scanned — a detail's description, a story step's body — takes
`Text variant="reading"`; `body` is the denser secondary line a row or a field uses.
A row's one loud fact is a `Badge variant="tinted"`, optionally led by an `icon`
token (`review`, `escalating`, …); the words still name it. The table's Entry cell can follow the title with a quiet
`titleSuffix` (the item's own designation, "#2481"). In the two-line list a
row's second line uses the anatomy's `byline` ("payments-api #2481 · Mara Okafor")
when it has one, and `glyphBadge` pins a small icon or live dot to the row's glyph
(`{ icon, tone }` or `{ live: true }`); the table shows neither, because its own
columns say the same. Pass the narrowings in force as `search.tokens`
(`{ key, qualifier, label, onRemove }`): they sit inside the search field, each one
press to remove. To put that search into your own toolbar row, pass `header` as a
render: `header={({ search, selection, pageActions }) => <Row>{search}{selection}{trailing controls}{pageActions}</Row>}`
receives the search field with its tokens at the toolbar's bounded width, the touch-sized
Select control (`null` when nothing can be selected) and the host's page actions, such as
the machine your page runs on (`CollectionHeaderSlots`). The list pane then draws none of
them, and placing `pageActions` in your row replaces the host's separate band. An empty
table cell reads "—". While the first rows load, a table
keeps its column titles and its skeleton rows fill the rows region from the top; in
every presentation the `empty` slot fills that same region. A `Select presentation="segmented"` option may carry an `icon`
that leads its label; pass `compact` in a narrow toolbar (a List | Board switch on a
phone) and each option that has an `icon` shows the icon alone, its `label` staying
the accessible name. The disclosure intentionally uses the public instant motion driver;
a custom animated composition may supply a public `HappierDisclosureMotionDriver`
while honoring `reducedMotion`. Its header receives the toggle and expanded
accessibility state together. Keep `defineUiSurface` as the provider boundary.

### Custom grid card bodies (0.3 development)

For `presentation="grid"`, `CollectionAnatomy.cardContent` replaces the generic
card head and description with your domain body. This is **unreleased 0.3
development API**. Supply `{ height, render(item), ownsFooter? }`: `height` is
the exact body height at normal text size, scaled with the reader's text size.
Every card shares that height, and the body must fit it. Unlike a static
`preview`, the rendered body may subscribe to live data through your existing
data owner.

Keep the body's own component under the shared card activation and focus

```tsx
import { Stack, Text, type CollectionAnatomy } from '@happier-dev/plugin-ui';

const gridAnatomy: CollectionAnatomy<Item> = {
```

The default keeps the anatomy's `reason` and `action` in their footer slots.
Set `ownsFooter: true` only when your body draws that footer area itself; the

card's body. List, table and board presentations retain their existing anatomy.

### Interactive row controls and spanning fields (0.3 development)

These additions describe **unreleased 0.3 development source**, not shipped
package availability. Check your installed API inventory before using them.

Put an interactive control beside a row's primary press target with
`anatomy.titleControls`: it follows `titleSuffix` in the table and ends the
byline in the list. Each control has its own press and focus target; activating
it does not open the row. Keep passive facts in `titleSuffix` or `byline`.
Never put a button inside the row's button.

For a row that cannot report its figures, `CollectionField.spanRest` lets one
field explain why across its own and the following field columns, suppressing
those later cells for that row. Other rows keep their figures. It applies only
to the table; keep the list's explanation in its own anatomy too:

```tsx
import { Button, type CollectionAnatomy } from '@happier-dev/plugin-ui';

type Connection = {
  id: string; title: string; online: boolean; cpu: string; memory: string;
};

function connectionAnatomy(inspect: (id: string) => void): CollectionAnatomy<Connection> {
  return {
    glyph: () => null,
    title: (item) => item.title,
    accessibilityLabel: (item) => item.title,
    columnTitles: { title: 'Connection' },
    byline: (item) => item.online ? item.cpu : 'Offline — figures unavailable',
    titleControls: (item) => (
      <Button title="Inspect connection" size="small" onPress={() => inspect(item.id)} />
    ),
    fields: [
      {
        key: 'cpu', title: 'CPU', minWidth: 120, priority: 1,
        render: (item) => item.online ? item.cpu : 'Offline — figures unavailable',
        spanRest: (item) => !item.online,
      },
      { key: 'memory', title: 'Memory', minWidth: 120, priority: 1, render: (item) => item.memory },
    ],
  };
}
```

A custom `List.Item` whose children contain controls can use
`contentBesidePressable` for the same sibling structure. Its content sits above
the row target; a custom control wrapper must opt into pointer events with
`pointerEvents="auto"`, while passive content lets presses through. Collection
handles that layering for `titleControls`. For a trailing control, use the
existing `accessory` and `accessoryOutsidePressable` instead.

For example, with your own `openServer` and `openPortMenu` handlers:

```tsx
import { View } from 'react-native';
import { Button, List } from '@happier-dev/plugin-ui';

<List.Item title="Development server" onPress={openServer} contentBesidePressable>
  <View pointerEvents="auto">
    <Button title="Port 5173" size="small" onPress={openPortMenu} />
  </View>
</List.Item>;
```

`detail="none"` suppresses the open/back/peek keyboard hint line; it does not
remove the window's coverage or continuation information. Do not add a manual
hint line for a collection that has no built-in detail.

### Phone headers and page sheets (0.3 development)

In the same unreleased contract, pass the page's `title` to Collection and place
the `title` slot from `header` beside its other controls. That slot is `null`
when the host navigation already shows the title, as on a phone; drawing the
title yourself would repeat it. With `detail="auto"`, a pushed phone detail
replaces the collection toolbar and uses the shared back control and
`detailHeader`. Its body should honor `headerHosted`, as in the example above.

For a page-scrolling `presentation="list"` (`scroll="page"`) in Happier's page
theme, an ungrouped list with an active field in `sort` keeps a compact header
on the same sheet as its rows and summary totals: `columnTitles.title` on the
left and the active field's sort control on the right. Grouped or unsorted
lists use their section anatomy without that header. Inside an existing page
section's sheet, Collection reuses the enclosing sheet rather than nesting
another one. Let the shared owner compose this phone layout.

In the 0.3 development contract, pass `Collection.sort` with the active `key`,
`direction` and `onChange(key)` to make `sortable` field titles interactive.
Optional `orders: [{ key, label }]` adds a named-order menu to the table's title
column. The column title itself is the trigger, quiet like its neighbours, naming the
active order ("Entry · Newest") with a caret. Its checked option follows `sort.key`;
field sorting leaves all named options unchecked. The caller still owns the
ordered data. The menu is absent in list and board; header controls can read
`useHappierCollectionLayout()?.composition` to keep a toolbar Order in those
presentations without repeating it above the table.

Use `Tabs tabList="host"` when an enclosing detail frame already draws the tab
strip and requests one panel. Use `layout="fill"` inside a bounded region for a
self-scrolling view. A retained `Tabs.Item retention="retain"` mounts only after
its first visit; its asynchronous work must consume `useTabPanelActivity()` and
stop when `activeSignal` aborts. Retention ends with the Tabs mount.

`Step` is a story or check, not a workflow runner. A numbered marker is
`{ kind: 'number', value: 1 }`; a checks marker is
`{ kind: 'state', state: 'passed', label: 'Passed' }` (also `running` or
`failed`). The label names the state for assistive technology; `titleKey` and
the state marker's `labelKey` resolve your plugin's declared translations, with
the supplied words as fallbacks. Put reading content in its body and quiet
context in `trailing`.

`HappierDisclosure` belongs to the public `/components` entry, while `Step`
and `Tabs` belong to the ordinary package entry. It is controlled by `expanded`
and `onExpandedChange`; spread its `headerProps` onto the actual press target
so toggle behavior and expanded accessibility state stay together. `keepMounted`
retains a stateful body, but does not grant that body's asynchronous work an
active lifetime. Supply reduced-motion facts and a public motion driver as in
the example; neither the disclosure nor a hosted Tabs strip owns domain reads.

When several tabs present one stateful renderer, provide it once as
`Tabs sharedPanel={...}` and update its panel input from the controlled tab value.
The renderer stays mounted and the visible panel remains labelled by the selected
tab. Inside that renderer, host-mode Tabs still own each panel's retention and
active interval. For a persistent outer `ScrollArea`, `scrollEnabled={false}` lets
a bounded child panel own scrolling without remounting the renderer.

For a PRs & Issues source, declare the panels on the source descriptor and render
only the requested panel. The [source detail and fix-link recipe](/plugins/ui#source-detail-panels-and-fix-pull-requests)
uses the public Triage feature protocol.

## Session tabs

A surface mounted as a session tab (`rightSidebarTab`) sits under the pane header
Happier already draws for that tab: its name on desktop, the large title on a
phone. Put the tab's add action and its one live fact there with
`PaneHeaderContent`, never in a header of your own:

```tsx
<PaneHeaderContent
  line={needsYou > 0 ? [{ text: `${needsYou} needs you`, attention: true }] : []}
  actions={<Menu trigger="Link a conversation" triggerIcon="add" triggerAccessibilityLabel="Link a conversation" items={bots} onSelect={link} open={open} onOpenChange={setOpen} />}
/>
```

The actions render in the header, outside your surface's tree, and keep your
plugin's context. Where the host mounts the surface without a pane header (a
page or a widget), `PaneHeaderContent` renders nothing, so keep an add path in
the body as well (an empty state's action). `triggerIcon` on `Menu` and `Popover`
draws the trigger as a glyph alone, the way the host's own "+" and ⋯ look. With
`triggerAppearance="control"` or `"primary"` the glyph leads the visible words
instead, exactly like a `Button`'s leading icon: use it for a primary action that
opens a choice ("+ Link a PR or issue"). The primary trigger is the same button as
`Button variant="primary"`. `triggerDisclosure` adds a caret after a plain `text`
trigger, for a title that opens a menu (a table's column header); labelled
appearances are buttons and ignore it. `triggerAppearance="well"` with a
`triggerIcon` draws the glyph in a round resting fill, for buttons that are the
object on their row (the phone toolbar's Filters and ⋯ beside the search).
`triggerTaskStatus` draws a task's status (`TaskStatusGlyph`: backlog, to do, in
progress, done, canceled) in the glyph's place: alone as the trigger of a task
row's status menu, or leading the words of a detail's Status button. The glyph is
decoration, so name the control in `triggerAccessibilityLabel` ("Change status, In
Review").

A `Popover`, `Dropdown` or `Menu` opened from anything but a field-box `Select`
sizes to its content: the trigger's width is only its minimum, so a narrow "Views"
button does not make a narrow menu. `Menu` and `Dropdown` take `showGroupLabels` to
draw each named group's heading above its rows, for one menu of labelled checkbox
groups (a Filters menu). `Status` takes `value`, a second quieter line under its
label ("Loaded 10:42"), so one notice can carry the reason beside its `action`.
`BrandMark size="small"` sits at text size beside a label; larger sizes keep their
image steps.

A `Popover` that holds a large panel (a form, a picker with search, a detail view) sets
`floatingRole="panel"`, so Happier draws it with the same heavier coat as its own dialogs and
panels and its words stay legible over the page. Leave it off for a small popover; menus keep the
lighter coat. The coat is Happier's to paint: there is no opacity or colour prop.

In the Developer Preview source contract, a page Collection can supply
`detailHeader(key)` with the item's `title`, optional `subtitle` and `actions`,
plus an optional `leading` mark beside the title (the item's own glyph) and a
`subtitleLeading` mark before the subtitle (where the item comes from, such as a
`BrandMark`). Marks stand on their own: do not wrap them in a tile, border or
fill. Happier renders them in its details band and supplies Close. `DetailsPane`
takes the same `leading` and `subtitleLeading`. The same
`renderDetail(key, { headerHosted, pushed })` body runs in every container; omit its
inline heading and close controls when `headerHosted` is true. Keep item
selection in the page location, and pair a pushed detail location with
`backLocation` so phone Back returns to the collection. `DetailsPane` also takes a
`footer`: the detail's one primary, pinned in thumb reach when the detail is pushed
inside the page (phones). It sits under a hairline above the home indicator and the
keyboard while the detail scrolls above it. Beside the page it is not drawn, so put
the same action in `actions`. Pass one primary, or the primary and one quiet
secondary; never two filled buttons.

A `Collection` detail is pushed by the Collection itself, so it draws that same
footer through `DetailsPaneFooter`: when `renderDetail` receives `pushed: true`,
end the detail's own full-height column with
`<DetailsPaneFooter>{primary}</DetailsPaneFooter>` after the part that scrolls.
Beside the list or in the host's details pane `pushed` is `false`: draw no footer
and keep the primary in the details header's `actions`.

A row can open in place: pass `expanded` and `expandedContent` to `List.Item`
and toggle `expanded` from its `onPress`. Put a few calm facts in it
(`Metadata`), then the row's own actions at the bottom as buttons, one of them
primary. Use it for what an item is to this tab, not for a page; open the page
with `openSurface` instead. The motion and reduced motion are the host's.

People are drawn with `Avatar({ name })`, the same mark Happier uses for people
elsewhere. It takes a name, never an image URL.

## Show a live session

A surface can show one of the Account's sessions live — the real transcript,
its prompts and its composer — rendered by Happier's own session view. The
plugin never draws a transcript or a composer itself.

Get a session id through Actions you already have (`session.spawn_new` or
`session.fork`, from UI or from `activate(api)`), keep it in your own storage,
and render it:

```tsx
import { SessionChat } from '@happier-dev/plugin-ui';

<SessionChat sessionId={leadSessionId} />                     // transcript, prompts and composer
<SessionChat sessionId={leadSessionId} variant="transcript" /> // read-only
```

For your own arrangement, put the parts under one `SessionProvider`. The provider
is the one controller for that session; the parts are views of it wherever they
sit, and each part appears at most once per provider (a duplicate renders
nothing, and so does a part outside a provider):

```tsx
import { ListDetailLayout, SessionComposer, SessionProvider, SessionTranscript } from '@happier-dev/plugin-ui';

<SessionProvider sessionId={leadSessionId}>
  <ListDetailLayout
    minListWidth={280} minDetailWidth={420} preferredListRatio={0.35}
    resizeKey="lead-session"
    list={<LeadFacts />}
    detail={<><SessionTranscript /><SessionComposer /></>}
  />
</SessionProvider>
```

In 0.3 development source, `ListDetailLayout` and `Collection` share a resizable
split rail. `resizeKey` remembers its width on this device in Happier, scoped to
your plugin. Without the host sizing port the width lasts for the mounted
component. For controlled geometry, pass `listWidthPx` and
`onListWidthChange`; persist on release with `onListWidthCommit`. A double-click
requests `onListWidthReset` and clears the remembered width. Resizing clamps to
the existing pane minima and preserves the mounted detail. You can provide the
handle's accessible name, hint and value text through `labels.resize`,
`labels.resizeHint` and `labels.resizeValue`.

These width controls govern the component's own split. When `Collection` opens
its detail in the app's details pane, the host keeps placement and pane-width
ownership; `listWidthPx` and `resizeKey` do not override that pane.

- **Bounded region.** The parts fill a bounded flex column: the transcript takes
  the remaining height and the composer keeps its natural height. There is no
  auto-height mode; an unbounded parent gives the session no room. On iOS and
  Android the composer part must be the bottom element of a region that reaches
  the screen bottom, because it carries the keyboard and safe-area lift.
- **Inside tabs.** `Tabs` sizes to its selected panel by default
  (`layout="content"`), which is right inside a scroll area but leaves a session
  no height. Pass `layout="fill"` so the tab root and the active panel take the
  parent's remaining height:

  ```tsx
  <Tabs value={tab} onValueChange={setTab} ariaLabel="Lead" layout="fill">
    <Tabs.Item value="facts" title="Facts"><LeadFacts /></Tabs.Item>
    <Tabs.Item value="chat" title="Chat"><SessionChat sessionId={leadSessionId} /></Tabs.Item>
  </Tabs>
  ```
- **Test ids.** `SessionChat`, `SessionTranscript` and `SessionComposer` take an optional `testID`.
- **Read-only.** `SessionProvider readOnly` (or `variant="transcript"`) shows no
  composer, and its permission and question prompts say to open the session to
  respond.
- **What the plugin gets.** Nothing: no transcript content, callbacks or approval
  authority. The session resolves only inside the Account the surface is mounted
  in; a session that is missing, deleted or out of reach shows one neutral
  "isn't available" state. The person approves prompts as themselves, exactly as
  in the full session.
- **No nesting.** Nothing inside the embedded session mounts a plugin surface,
  including the one showing it.
- **Where it renders.** React Native and React Native Web surfaces only. Hosted-web
  surfaces, isolated tests and hosts without the session view render the
  `fallback` you pass (nothing by default); for a web page outside Happier, use
  the embed. `createPluginUiRnwSemanticSurfaceAdapter({ sessions: true })` presents
  the parts in tests as semantic stand-ins (a group named `Session <id>`).

The session components are Developer Preview.

## Show an agent working on your surface

When an agent acts on something your surface shows (a board, a canvas, a
preview), use the same co-presence pieces Happier's browser and shared-window
viewers use. Render them inside the box they narrate; they position themselves
on its edges.

```tsx
import { AgentCursor, PresenceCapsule, StatusCapsule, usePluginHostApi } from '@happier-dev/plugin-ui';

const hostApi = usePluginHostApi();

<View style={{ flex: 1 }}>
  <Board />
  <AgentCursor target={activeTarget} testID="board-cursor" />
  <PresenceCapsule
    presence={presence}                 // { kind: 'agent' | 'stopping' | 'human' | 'unconfirmed' | 'idle', controlEpoch }
    agentName="Claude"
    agentTitle="Claude is editing the board"
    agentDetail="Moving “Launch plan”"
    onTakeControl={() => hostApi.executeAction('take-control')}
    onHandBack={() => hostApi.executeAction('hand-back')}
    testID="board-presence"
  />
  <StatusCapsule visible={reconnecting} busy text="Reconnecting to the board" testID="board-status" />
</View>
```

- **`PresenceCapsule`** says who is driving and offers the one control: Take
  control, then "Stopping Claude…" until `presence.controlEpoch` moves, then
  "You have control" with Hand back. `unconfirmed` never claims the person has
  control; pass `onCheckAgain` for the fresh look that confirms the stop. The
  capsule holds no authority: wire both buttons to your own Actions, and feed
  `presence` from whatever owns control of your surface. `placement="inline"` or
  `"strip"` puts it in flow, `onWatch` adds a Watch button, and
  `renderAgentMark` draws your mark (for example `BrandMark`).
- **`AgentCursor`** draws the agent's hand where it acts and a ring around the
  element. `target` is normalized to the page (0..1, with optional `width` and
  `height` for the ring); pass `pageRect` when the page is letterboxed inside the
  box. Actions can be shorter than a render, so also keep the agent's latest
  action as `point={{ id, target }}` (its request id and the same target) until
  the next action replaces it: each new `id` is shown once, arriving fully,
  holding while `target` is live, then leaving, even when the action began and
  ended between two renders. With reduced motion it appears at once and stays
  until you withdraw the point. It is decorative: it takes no input and is
  hidden from screen readers, so pair it with a `PresenceCapsule`.
- **`StatusCapsule`** is one quiet sentence at the top edge while something is
  not normal, with an optional `action` as the way out. Keep it mounted and flip
  `visible` so it leaves smoothly; healthy is quiet.

In a Happier window these use the app's own glass, type, buttons and motion. In
a hosted-web realm they draw a plain solid capsule and changes land at once.
Advanced authors find the shared owners in `/components`
(`HappierPresenceCapsule`, `HappierAgentCursor`, `HappierStatusCapsule`, and
`HappierStatusDot` with its `halo` ring). These components are Developer Preview.

### Capture previews and Session images

This media interface is under development in 0.3. Use these examples only when
your installed SDK and Plugin UI API inventories list the media exports below.

The Developer Preview `HappierLiveStream` presents a read-only capture in a
mounted Happier RN/RNW surface. Pass either your own manifest-declared source,
or a host source that the user approves for this viewing:

```tsx
import { HappierLiveStream, Text } from '@happier-dev/plugin-ui';

<HappierLiveStream
  reference={{ kind: 'plugin', source: { pluginId: 'acme.board', localId: 'preview' } }}
  testID="board-preview"
  fallback={<Text value="Open this preview in Happier" />}
/>
```

Declare `preview` in this plugin's `captureSources` contributions. The host
owns transport, decoding and cleanup; the plugin never receives a stream
address. A `{ kind: 'host', sourceId }` reference goes through the existing
`capture.view` Action approval for each viewer occurrence. Approval is required
by default; the user may waive it for a particular plugin in Action settings.
Replacing a source closes its viewing and does not inherit that consent. Your
plugin's own declared captures require no additional viewing consent. Viewing
does not give control: input and takeover remain host-owned, approved Actions.
Without an app renderer, including a caller-hosted HTML realm, the supplied
`fallback` renders instead.

Use `StoredImage` with a `StoredImageRefV1` from
`@happier-dev/plugin-sdk/ui`. Pass the complete file-backed native Session-image
reference, including its media identity, dimensions, byte size and `file` facts
(Session, storage, relative path, digest and MIME type). Capture, attachment,
snapshot and Session-event Actions can return these references. You may retain
a reference across surface remounts or pass it to another plugin; the receiving
plugin's declared Session scope still decides access. A reference grants no read
permission, and arbitrary file paths cannot replace native Session-image facts.

```tsx
import { StoredImage } from '@happier-dev/plugin-ui';

<StoredImage image={imageReference} accessibilityLabel="Captured page preview" />
```

Image reads require the plugin's declared `sessions` HostAccess **read** scope
(and the selected scope when access is optional), not the broader linked-Session
UI scope. The same scope owner applies on the daemon. Plain/E2EE mismatches or
unavailable encryption material return an unavailable image, never a plaintext
fallback. The app thumbnail and `StoredImage` share `HappierStoredImage` in
`/components`. These are development-source interfaces; package publication
and loaded-runtime verification remain separate.

The daemon also verifies the exact Session artifact bucket, real file path,
size, digest and image encoding. A result's producer does not grant broader read
access. `sessions.media.publishGenerated` returns publication status rather
than this native artifact reference; generated-media records are not a
`StoredImageRefV1`.

## Work lists and maps

A surface that shows agent work — runs your plugin started, steps it is waiting
on, work grouped by where it stands — can draw it with the primitives Happier's
own Work tab, Inbox and workflow maps use, from
`@happier-dev/plugin-ui/components`:

- `HappierWorkSection`: a group of a live work list (a compact title and a quiet
  count), or with `anatomy="page"` a configuration section laid flat on the pane.
  Supply `empty` for an explicitly empty source and `more` for a caller-owned
  disclosure. Loading retains the section header and skeleton instead.
- `HappierWorkRowShell` and `HappierWorkSummary`: a Work row's pressable shell
  and its identity leaf (mark, title, one line of facts, the state word at the
  trailing edge). On a `page` row, `trailingMeta` sets the date in one
  right-aligned column after the row's own control, so dates line up however
  wide each control is; pass `null` on a row with no date to keep that column.
- `buildHappierWorkMap` and `HappierWorkMapView`: a map of work built only from
  the parent each node declares, drawn as cards on a rail or in side-by-side lanes;
  `density="compact"` is the mini-map a row carries.
- The status language: map your own facts to
  `{ state, bucket, tone, attentionType, word }`, plus an optional semantic `glyph`
  (`HappierWorkStatusPresentation`). `state` is your own state id, and
  `attentionType` is the admitted attention classification (`null` when nothing
  asks for the person). Buckets read in `HAPPIER_WORK_STATUS_BUCKETS`
  order and `resolveHappierWorkStatusBucketLabel` labels them in the host's
  locale. `HappierWorkStatusWord` and `resolveHappierWorkStatusSurfaceStyle` draw
  the tone: a soft ring and tint only for work that needs the person or failed.
- `HappierWorkUpdateCard`: a result-card frame with mark, title, state, metadata,
  body, facts and actions. Your source owns the result and handlers; the frame
  owns their arrangement and status treatment.
- `HappierFactLine` and `joinHappierFacts`: draw or join ordered facts with the
  same separator. `resolveHappierWorkKindPresentation` and
  `resolveHappierRoleRunsAsPresentation` supply the shared glyph and label
  presentation; pass translated labels when composing your own domain copy.

Navigation and consent use the same shared entrypoint. `HappierBreadcrumb`
renders ordered items with optional link handlers; omit a handler for the
current location. `HappierDecisionBar` accepts the available approve, reject
and dismiss actions and a `Button` renderer. It owns order, emphasis, disabled
and busy state, while the renderer binds your supported button leaf. Only
offer dismissal when your consent contract permits it; rendering a bar does
not grant authority to approve a host Action.

These are development-source Developer Preview interfaces. Consult the
installed package's public inventory before importing them; source availability
does not establish package publication or loaded-platform validation.

The development-source `session.work.get` (`{ sessionId }`) and `inbox.get`
(`{}`) host Actions can read the answering client's existing mounted Work or
Inbox owner. Their results distinguish `ready`, `loading` and `unavailable`;
they do not open those surfaces, load a second projection or interpret
`unavailable` as empty. Calls are bound to the invoking Home and Account.
Use them only when your installed SDK's generated
[host Action reference](/plugins/api/host-actions) lists them. Rendering the
primitives below does not itself mount a host data source.

```tsx
import * as React from 'react';
import { useHappierUiLocalization } from '@happier-dev/plugin-ui/environment';
import {
  buildHappierWorkMap,
  HappierWorkMapView,
  HappierWorkRowShell,
  HappierWorkSection,
  HappierWorkStatusWord,
  HappierWorkSummary,
  resolveHappierWorkStatusBucketLabel,
} from '@happier-dev/plugin-ui/components';

function DeployWork({ deploys, onOpen }: DeployWorkProps) {
  const { translate } = useHappierUiLocalization();
  const waiting = deploys.filter((deploy) => deploy.status.bucket === 'needs_you');
  return (
    <HappierWorkSection
      testID="deploys-needs-you"
      title={resolveHappierWorkStatusBucketLabel('needs_you', translate)}
      count={String(waiting.length)}
      countTone="attention"
    >
      {waiting.map((deploy) => (
        <HappierWorkRowShell
          key={deploy.id}
          testID={`deploy:${deploy.id}`}
          accessibilityLabel={`${deploy.name}, ${deploy.status.word}`}
          onPress={() => onOpen(deploy.id)}
        >
          <HappierWorkSummary
            title={deploy.name}
            phase="attention"
            mark={<DeployMark />}
            facts={[deploy.environment, deploy.stepLabel]}
            trailingState={deploy.status}
            accessibilityLabel={`${deploy.name}, ${deploy.status.word}`}
          />
        </HappierWorkRowShell>
      ))}
    </HappierWorkSection>
  );
}

const map = buildHappierWorkMap({
  relationships: 'authored',
  nodes: [
    { nodeId: 'release', label: 'Release 4.2', parentNodeId: null, open: { kind: 'run', runId: 'release' } },
    { nodeId: 'smoke', label: 'Smoke checks', parentNodeId: 'release', open: { kind: 'run', runId: 'smoke' } },
  ],
});

<HappierWorkMapView
  map={map}
  selectedNodeId={null}
  testIDPrefix="release-map"
  accessibilityLabelForNode={(node) => node.label}
  renderStatus={(node) => <HappierWorkStatusWord tone="neutral" role="rowState">{wordFor(node)}</HappierWorkStatusWord>}
  onOpen={(node) => openRun(node.open)}
/>;
```

Inside a mounted surface these read the theme, page palette and text scale from
the surface environment. The words stay yours: a row says the owner's own state
("Waiting for approval"), never the bucket label. A row carries no answer
controls; open the place where the request is answered once.

## Page headers and group labels (0.3 development)

`PageHeader` is the header Happier's own pages draw. `actionsLayout` chooses how the
controls meet the title: `wrap` (the default) keeps them on the title row and wraps
them beneath when the title needs its width, `inline` keeps them on it, and `hang`
hangs the mark and controls from the title's line with the description and facts
beneath at full width. Use `hang` for an entity page with a long description.

A `meta` fact with `mono: true` is an address, path or id: one mono line that gives
up its middle rather than wrapping, names the whole value to assistive technology,
and copies it on tap through the host clipboard, saying "Copied" in its place.

`NavigationList.Group` takes `detail` and `detailEnd` for a quiet fact after the
title. `detailEnd` is the part that tells same-named groups apart (a machine's short
id, "Offline"): it stays whole while a narrow label shortens `detail` first.

```tsx
<PageHeader title={machine.name} leading={<BrandMark />} actionsLayout="hang"
  meta={[{ key: 'path', text: machine.home, mono: true }]} actions={<Menu />} />
<NavigationList.Group title={repo.name} detail={machine.name} detailEnd={`${machine.shortId} · ${t('Offline')}`} />
```

## Shared story components (0.3 development)

Use `Timeline` for an ordered activity rail. Supply `items`, `keyForItem`,
`accessibilityLabel` and `renderItem`; each item returns `glyph`, `heading`,
and optional `time`, `body` and `trailing` slots. The shared List owns scrolling
and prepend continuity. Your source still owns ordering, paging and event copy.

```tsx
<Timeline
  items={events}
  keyForItem={(event) => event.id}
  accessibilityLabel="Activity"
  renderItem={(event) => ({
    glyph: <Icon name="file" />,
    heading: event.title,
    time: event.timeLabel,
    body: <Text value={event.description} />,
  })}
/>
```

For quiet collection metadata, use
`<Status presentation="inline" tone="success" label="Checks passed" />`.
It keeps the words on one truncating line without announcing every row refresh.
`indicator={false}` omits a quiet state's dot; `leading` can carry its decorative
source mark. The default notice remains a polite status region.

Use `Metric caption="…"` for its visible contextual line below the value;
`label` names what the value counts for assistive technology.

`<Stack grow>` and `<Row grow>` fill available space and allow their contents to
shrink without hand-written flex styles. Use `ApprovalPrompt` for permission
requests, with `title`, `subtitle`, body children and decision controls in
`footer`. It shares Session chat's approval anatomy; it does not make decisions
or grant permission. Pass `tone="attention"` when the request is waiting on the
person: the card takes the same amber ring and tint as any work that needs them.
Leave it neutral for requests the person started.

Pass `chrome="compact"` where the request has little room (a notch, a popover row):
a small card with no ring, your small mark in `icon`, and everything on one edge.
`surfaceStyle` replaces its fill. `eyebrow` adds the source line above the title
("Bash"). Facts stay in the body and the decision stays in `footer`.

`<MotionFeedback trigger={confirmedSequence} decorative>` acknowledges a
confirmed result. Change the trigger only after success, and expose that result
in words outside decorative feedback. First mount is static; reduced motion
settles immediately. The shared motion owner supplies timing and easing.

Use `ModalHeader` for the title band of a dialog or sheet your surface draws.
It takes `title`, `subtitle`, an optional `leading` mark, context `actions` and
`onClose`. Pass `compact` on a phone: when there are actions, the title keeps
its row beside the close control and the subtitle and actions move beneath it,
the way Happier's own dialogs recompose. Happier's dialogs use the same
component.

```tsx
<ModalHeader
  title="Link a pull request"
  subtitle="Pick the change this review covers."
  actions={<RepositoryChip />}
  onClose={close}
  compact={onPhone}
/>
```

Use `TechnicalDetailsDisclosure` for the exact ids, codes and raw causes behind
a readable page, the way Happier's approval and Run step pages fold theirs. Pass
a translated `title` and `lines`, each `{ key, label, value }`. The row stays
folded until the person opens it; each value is then selectable in mono under
its label. With no lines it draws nothing, so you can always render it. Put the
readable outcome on the page and keep the code here.

```tsx
<TechnicalDetailsDisclosure
```

Centred state copy and capsule titles that need two lines split them evenly on
the web rather than leaving one word alone on the last line. `EmptyState`,
`LoadingState`, `ErrorState` and the capsules do this for you. For centred text
of your own, add `HAPPIER_BALANCED_TEXT_WRAP` from
`@happier-dev/plugin-ui/components` to its style; it is `null` on native.
Hosted HTML pages don't run these components: use a `<details>` element with a
`<summary>` for technical details, and CSS `text-wrap: balance` for centred copy.

These additions describe the current 0.3 development source. Check the installed
API inventory before using them in a published plugin.

Triage source authors can import `TriageStatusRow` from
`@happier-dev/triage-sources/ui` for checks, review and merge facts. Pass the
source's localized `name`, optional `status` and semantic `tone`; choose
`presentation="compact"`, `"summary"` or `"list"` for the container. Full list
rows accept `detail` and `actions`. Filtering, state vocabulary and operations
remain source-owned.

## Accessibility and offline snapshots

Use the semantic package's accessibility-aware controls and preserve a logical
reading and focus order. Read locale, direction, color scheme, contrast, text
scale, reduced motion, screen-reader state, and safe-area insets from the
semantic surface context rather than copying host state. Support Dynamic Type,
RTL and long strings, high contrast, reduced motion, and 44×44-point iOS or
48×48-dp Android targets.

In the 0.3 development author API, `HappierPressable` from
`@happier-dev/plugin-ui/components` accepts `checked?: boolean | 'mixed'` in its
exported `HappierPressableProps`. For a checkbox group, pass `false` when none
are checked, `'mixed'` when some are checked, and `true` when all are checked.
The same value becomes web `aria-checked` and native
`accessibilityState.checked`; keep the visible mark in agreement. Use `'mixed'`
with checkbox or checkbox-menu-item roles, not radio buttons or switches.

The host owns occurrence currentness. Do not retain a competing currentness
flag. If a host operation becomes unavailable, preserve useful rendered state
and present a recoverable status instead of assuming the mutation succeeded.

While disconnected, Happier can retain the mounted visual tree as a
non-interactive snapshot. It blocks pointer, touch, keyboard, focus,
accessibility actions, and host API mutations, then exposes a localized
host-owned static summary using the surface's declared display title. Provide
a meaningful localized title and make the last rendered visual state
understandable without requiring a control. Reconnect supplies a revalidated
context before interaction resumes.

## Build output

For a production artifact, `hdev plugins dev build .` writes the portable
UI artifact tree under `dist/happier-plugin-ui`. The generated
`--ui reactNative` project exposes one exact source entry through
`./happier-plugin-ui/<artifactId>`. The daemon compiler emits one minified
CommonJS bundle that web, iOS, and Android evaluate through the same host-module
contract. Do not run a second platform-specific bundler.

Artifact targets are not a mobile/tablet availability promise. The current host
registry admits every declared UI binding on web/desktop and native tablet. On
native phone it admits only `appPage`/`app`, `settingsPage`/`app`, App and
Session `rightSidebarTab`, `browserPanel`/`browser`, and
`servicesPanel`/`services`; Project phone and the other pane cells remain
unavailable. Let the mount result describe the exact outcome rather than
inventing a plugin-local fallback. Loaded mobile and tablet host validation is
separate from source-level admission.

The manifest declares the direct view and artifact references.
`ui-artifacts.json` describes the emitted files and digests. Authors do not
hand-author the final content digest.

## Failure isolation

Evaluation and render failures are contained to the affected local surface.
Happier presents the standard unavailable-surface state and may retain a
verified last-known-good visual. Crash containment is device-local and is not a
plugin projection or byte-selection input.

## Boundary

The host owns navigation, permissions, app state, session lifecycle, and native services. Use the Plugin UI host API for supported interactions. The package-level trusted-code decision covers this client code, daemon code, dependencies, and build artifacts together.

Cross-plugin contribution points and targeted contributions are available in
Developer Preview where the generated capability matrix marks both rows
`available`. Keep a direct view same-plugin unless a documented protocol package
defines the target relationship; do not copy another plugin's declaration or
invent a target renderer or navigation contract.
