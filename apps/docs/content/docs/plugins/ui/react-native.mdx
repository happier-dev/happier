React Native is the default executable UI model when a plugin needs a native-feeling, host-integrated surface. Its code is part of the trusted plugin package and runs in the supported client realm; it is not sandboxed.

## Scaffold

```bash
hdev plugins create ./my-plugin \
  --id com.example.my-plugin \
  --name "My plugin" \
  --ui reactNative

cd my-plugin
hdev plugins dev
```

The generated project includes the manifest contribution, semantic Plugin UI
source, compatible build dependencies, and a public SDK build configuration.
The release-owned toolchain packet supplies those versions; do not copy a
separate version matrix into the project.

Before choosing a component or hook, open the shipped [Plugin UI API
inventory](https://github.com/happier-dev/happier/blob/v0.3/packages/plugin-ui/API.md):
`node_modules/@happier-dev/plugin-ui/API.md` in the generated project is the
exact installed inventory. Do not guess exports from examples or app source.

## Host API

Export a semantic surface. `@happier-dev/plugin-ui`'s `defineUiSurface` owns
provider installation around the host-supplied render context, so components
and Actions share the same bound host API:

```tsx
import * as React from 'react';
import { Action, Card, defineUiSurface, Text } from '@happier-dev/plugin-ui';

function PluginPanel() {
  return (
    <Card>
      <Text variant="title" value="My plugin" />
      <Action.Execute action="save-note" input={{ note: 'hello' }} title="Save note" />
    </Card>
  );
}

export const renderSurface = defineUiSurface(PluginPanel);
```

The managed UI build targets the one initial **Host API 1.0.0** contract.
Authors do not configure an API range, select a second Host API tier, or add a
version-sniffing fallback: consume the bound host API supplied to the admitted
surface and handle its typed unavailable or cancellation result.

`@happier-dev/plugin-sdk/ui/client` is the hosted-web bootstrap client; do not
use it from a React Native renderer. Use the curated `plugin-ui` controls for
semantic UI. `react-native` is a host-provided framework singleton, not a
Happier component contract: a plugin-owned implementation may use compatible
primitives only when the generated toolchain declares framework support for
that artifact. Do not use them to recreate a curated control, host provider,
bridge, or navigation root, and do not assume host styling, overlay, focus, or
navigation behavior. Never manually install a host provider, pass a
host-internal surface or transport object, or import Happier app internals.

The root `@happier-dev/plugin-ui` entry is the ergonomic, curated author tier.
Trusted React Native and React Native Web authors who need custom composition
may additionally use `/presentation` for shared RN/RNW primitives and behavior
or `/environment` for theme, localization, accessibility, platform, and inset
facts, hooks, and a standalone fact provider. `/presentation` never re-exports
environment contracts, so import `/environment` directly for that role. Both
advanced tiers share canonical core implementations, remain prepublication work
in progress, and carry no released stability promise while the package is held.
`@happier-dev/plugin-ui/advanced` is reserved for isolated tests and complete
standalone mounts that genuinely own provider/Resource lifetime. It does not
permit an admitted surface to construct a host provider, access internal mount
state, or import app, host, or protocol internals. Keep
`defineUiSurface` as the sole provider installation boundary.

### Artifact presentation in development

The prepublication `/presentation` tier includes `HappierArtifactPreviewCard`,
`HappierHtmlSandboxFrame`, `HappierPublicLinkCard`, and
`HappierArtifactRevisionList`. Happier core uses these same presentation owners.
Supply localized labels, theme facts, and their typed rendering bindings rather
than importing app components. Preview cards consume already available content;
revision rows consume the canonical owner's saved revision facts.

These components do not authorize publication, fetch Artifacts, retain bearer
secrets, or restore revisions. Those operations remain with the admitted host
services. `HappierHtmlSandboxFrame` owns reading-area geometry and state
presentation only: its typed `renderFrame` binding must enforce the host's URL
admission, isolated origin, platform sandbox and navigation policy. Passing HTML
to a frame does not establish an execution sandbox. Consult the installed API
inventory for the exact bindings; this development surface is not a released
stability or platform-certification promise.

## Personal widget areas in development

In **0.3 development / Developer Preview authoring**, an app-page View can
declare named `widgetAreas`, each with a `name` and a readable `contextSchema`.
Embed the host's personal area using the public component:

```tsx
import { WidgetSurface } from '@happier-dev/plugin-ui';

function PinnedWidgets() {
  return <WidgetSurface area="pinned" />;
}
```

The name must match an area declared by this page. Optional `context` supplies
readable values conforming to that area's schema. Widgets can follow those
values as **This page** or retain their own pinned inputs. The host derives
Home, Account, plugin/page/area identity and rights; context does not supply
machine routing, persistence callbacks or access authority.

The area uses the same Add surface, Edit inputs and frames as Home. Its
personal layout is an Account Artifact, separate from widget definitions and
from a shared Session Board. Copies keep independent inputs, order and
declared size; changing the page context keeps that layout identity. The
[widget size declaration](/plugins/ui#declare-useful-widget-sizes) determines
the useful choices offered by setup and the frame menu. A
declarative plugin page can use a `widgetArea` node against the same host port.
Such nodes are page composition, not Session Board or transcript content.

Copies use the same pointer grip, staged keyboard and Move-to chooser as other
host widgets. Available destinations come from currently mounted surfaces and
their admitted inputs and rights; moving uses the existing widget Action, not
a page-owned layout writer. A retired page or Account cannot start a move.

The component renders its `fallback` where no host presentation bridge exists.
Hosted HTML pages do not embed host widget areas; they manage widgets through
ordinary [widget Actions](/plugins/api/host-actions). This is a development contract, not a released
or loaded-platform support claim; consult the generated
[SDK surface](/plugins/api/surface) and [availability](/plugins/manifest/availability).

## Code-defined UI declaration

Declare each executable surface with `@happier-dev/plugin-sdk`'s
`defineUiSurfaceDefinition` and include it in the `ui` family of `definePlugin(...)`.
Packing projects that one declaration into the cold manifest. `appPage` and
`settingsPage` derive the app target, while a Session or Project placement
requires an explicit target.

```ts
import { definePlugin, defineUiSurfaceDefinition } from '@happier-dev/plugin-sdk';

export const mainSurface = defineUiSurfaceDefinition({
  id: 'main',
  placement: 'appPage',
  title: 'My plugin',
  renderer: {
    kind: 'reactNative',
    requiredHostMethods: ['context', 'executeAction'],
  },
});

export const { manifest, activate } = definePlugin({
  id: 'com.example.my-plugin',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  ui: {
    surfaces: [mainSurface],
  },
});
```

`definePlugin(...)` projects the cold manifest and derives the renderer and
artifact id `main-renderer` from the surface id. Export that renderer entry from
the matching package path; the daemon-owned compiler resolves the exact export
and emits one universal CommonJS artifact:

```json
{
  "exports": {
    "./happier-plugin-ui/main-renderer": "./src/ui/mainRenderer.tsx"
  }
}
```

`hdev plugins create --ui …` generates this exact-export shape together with a
`src/index.ts` that projects the same artifact id into `ui.surfaces`. There is no
platform matrix or author-owned bundler configuration.

`requiredHostMethods` is a renderer admission requirement, not a
method-availability claim. Name only the host methods without which the
renderer cannot run. Before mounting, the host compares that declaration with
the mount's factual installed method set; if a requirement is absent, it does
not mount that renderer and can only consider its declared fallback chain. Do
not use this field to choose a container or target, probe for capability, or
invent a plugin-local feature gate.

A renderer names an execution format; a view names the host destination. The
host registry owns the valid renderer/target/container combinations and runtime
availability. Start with the generated `appPage` + `app` view instead of
constructing a guessed surface matrix or manual dispatch path.

When a mounted surface needs to open another declared view, use the host API's
single dispatcher. A local id resolves in the same plugin; the host performs
destination admission, scope compatibility, and navigation:

```tsx
import { Button, usePluginHostApi } from '@happier-dev/plugin-ui';

function OpenReviewDetails({ reviewId }: { reviewId: string }) {
  const hostApi = usePluginHostApi();

  return (
    <Button
      title="Open details"
      onPress={() => {
        void hostApi.openSurface('review-detail', { reviewId }, {
          subPath: `reviews/${reviewId}`,
        });
      }}
    />
  );
}
```

`subPath` addresses only a location under a full-page `appPage`; it is ignored
for a `rightSidebarTab`. Do not build a host URL, router, or a first-available
fallback destination.

## Entity drag and drop (development)

In **0.3 development / Developer Preview authoring**, mount a declared source
and target with the public components inside your ordinary `defineUiSurface`
surface:

```tsx
import { DragSource, DropTarget, Text } from '@happier-dev/plugin-ui';

function ReviewQueue() {
  return (
    <DropTarget targetId="review" input={{ queueId: 'review' }}>
      <DragSource sourceId="issue" reference="issue-42">
        <Text value="Issue #42" />
      </DragSource>
    </DropTarget>
  );
}
```

The local ids must match your [source and target
declarations](/plugins/manifest/contributions#entity-drag-sources-and-drop-targets).
The source's `reference` must satisfy its declared JSON schema. Its registered
`PluginDragSourceRuntime.describe` returns the carried item's readable title
and optional subtitle. The registered `PluginDropTargetRuntime.resolve`
receives the current item, semantic destination, input mode and target-local
input. Return `{ status: 'allowed', effect: { actionId, input, preview } }`,
where `preview` names the verb, target, optional consequence and optional
declared `glyph`, or
`{ status: 'refused', reason: { code, message } }` with an optional preview.
Keep this resolver free of writes: the host resolves again on release and
dispatches the admitted Action through its existing approval policy.

For example, a copy target can return
`preview: { verb: 'Copy', target: 'Review queue', glyph: 'copy' }`.
Choose a bounded named mark from `EntityDropPreviewV1['glyph']` in the SDK's
types (see the generated [SDK surface](/plugins/api/surface)); arbitrary icon
names are rejected. Omission uses the generic `add` mark.
Core and plugin targets use the same field; Happier does not interpret your
Action id or input to choose a mark. The released preview also supplies pending
and settled feedback; refused feedback uses the refusal mark. A mark is
presentation, not permission or a request to execute an Action.

To make your reference attachable to a composer, set the source declaration's
`composerAttachment` to one of your own declared attachment local ids. Register
`toComposerAttachment(reference)` alongside `describe`; return a
`ComposerAttachmentAuthorValueV1`, or `null` when the reference cannot be
attached. The host checks the current source and attachment occurrences, then
uses the composer's existing revision-bound transaction to mint the attachment.
This leaves draft text and selection unchanged. Keep only the attachment's
identity and routing value in the draft; its existing dispatch resolver remains
responsible for reading current context when the message is sent.

Declare permitted host Actions with `{ kind: 'host', actionId }`, or a
contributed Action with `{ kind: 'plugin', action: 'local-action-id' }`.
Accepted kinds and permitted Actions constrain admission; they grant no
credentials or present-user authority. Return an explanation when the current
item cannot be used. Do not execute an Action carried inside reference data.

The host supplies current scope, geometry, release feedback and retirement.
Desktop uses the primary row while preserving secondary controls and text
selection. Set `organizing` on `DragSource` only while the surrounding touch
list is intentionally in Organize mode; normal long press remains available
to its menu. Staged keyboard movement and the destination chooser use the same
target resolver. Hidden or retired mounts cannot commit an unissued effect.
OS file handles and file bytes are not custom JSON references.

Declarative documents can use the closed `dragSource` and `dropTarget` nodes;
immutable document/snapshot profiles refuse these live nodes. Hosted documents
use the [public DOM bindings](/plugins/ui/hosted-web#entity-drag-bindings-development)
through their admitted host methods. All presentations join the same mounted
interaction owner. Generated APIs and source tests establish the author
contract; loaded browser/native and publication evidence remain separate.

## Lists, Resources, and Account data

Use `List`, `List.Section`, and `List.Item` from `@happier-dev/plugin-ui` for
host-like lists. Plugin UI owns filter and selection state local to the
component; the shared list owner retains row semantics, accessibility,
virtualization, and host presentation behavior. Do not replace it with a raw
list implementation just to reproduce a curated List surface.

For a virtualized list, use its `search` and `selection` props: `search` names
the visible filter control and receives the item's local filter predicate;
`selection` reports one stable row key. Both operate only on the `items` array
you passed to this List. They do not create, filter, or paginate a Data query;
keep Account-backed paging and query currentness with the declared Data UI
query instead.

In the **0.3 development / Developer Preview** source contract, an optional
`virtualizer` prop on `List` and `Collection` accepts the public
`CollectionVirtualizer` interface from the root, components or presentation
entry point. Most authors should omit it and keep the default native lists.
A custom host adapter renders the supplied flat or sectioned window and its
semantic cells, reports actual scrolling/content size, and publishes a
positioning handle after mount (withdrawing it on unmount). It must preserve
the supplied accessibility and layout facts. Revealing a row mounts its
physical focus target; List still owns focus and selection, and Collection
still owns its viewport memory. An adapter does not expose native refs or
grant data/query authority. `Collection.virtualizer` covers its row and card
Lists; page-scrolling rows continue to use the page's scroller.

For a declared Resource, use `usePluginResource` from
`@happier-dev/plugin-ui`. Use `useLivePluginResource` only when the
surface needs dynamic invalidation: it reads through the same host owner and,
when `watchResource` is available, watches for invalidation rather than a new
payload. It does not poll. Preserve a useful admitted value while a refresh
fails, and do not create a second cache, lifecycle, or currentness owner. Add
the host methods the surface actually needs to `requiredHostMethods` (for
example, `readResource` and, for live updates, `watchResource`).

In the current development SDK, a retained surface marked hidden by its host
releases the Resource hooks' automatic read and watch subscriptions while
keeping the admitted snapshot. Showing it again refreshes through the same
Resource owner. A visible pane remains active even when another pane has focus;
presentation activity is not keyboard authority. A standalone mount without
host activity retains the existing live behavior. Raw imperative
`watchResource` calls remain caller-owned until their unsubscribe function runs.

For Account-backed rows, use `usePluginCollectionQuery` from
`@happier-dev/plugin-ui/data` with a same-plugin, statically declared Data UI
query. The Data owner validates the query, keeps cursor and Account currentness,
reacts to Account changes, and retains last-known-good rows. Do not issue an
arbitrary predicate/index query, construct a data cache, or treat a UI query as
a general Account-storage transport.

For the plugin's own small, Account-portable state — a remembered selection, a
collapsed section, a last-used filter — use `usePluginAccountKv` from
`@happier-dev/plugin-ui/data`. It is the same Account KV service the plugin's
daemon side gets from `services.storage.account.kv`, over the same Account row:
same keys, same per-key versions, the same `expectedVersion` conditional write,
and the same visible tombstone that stops a stale writer from resurrecting a
deleted key. It needs no daemon. Keep growing or queryable records in a
Collection and declared preferences in Plugin Settings; one value never has both
Settings and KV authority. Account KV is not available inside a hosted-web
surface, whose host bridge carries Collection UI queries only.

## A Collection with one detail body

In the **0.3 development / Developer Preview** source contract, `Collection`
uses one model and item anatomy for list, table, board and grid presentations.
Its `detail="auto"` adapts the same detail body to the available pane or pushed
phone layout. The caller supplies the route's `openKey` and updates that route
from `onOpenChange`; presentation switches do not create another selection.

This complete composition uses only public imports. `ItemsPage` receives the
route binding and the already-read items from your surface's own data owner:

```tsx
import * as React from 'react';
import { Button, Collection, Icon, Row, Stack, Step, Tabs, Text } from '@happier-dev/plugin-ui';
import {
  HappierDisclosure, HappierPressable, HAPPIER_INSTANT_DISCLOSURE_MOTION,
  useHappierCollection, type HappierCollectionPresentation,
} from '@happier-dev/plugin-ui/presentation';
import { useHappierUiAccessibility } from '@happier-dev/plugin-ui/environment';

type Item = { id: string; title: string; summary: string };
const keyOf = (item: Item) => item.id;

function ItemDetail({ item, headerHosted, close }: {
  item: Item; headerHosted: boolean; close(): void;
}) {
  const [tab, setTab] = React.useState('overview');
  const [expanded, setExpanded] = React.useState(false);
  const { reducedMotion } = useHappierUiAccessibility();
  return (
    <Stack>
      {!headerHosted && <Row><Text value={item.title} variant="title" /><Button title="Close" onPress={close} /></Row>}
      <Tabs value={tab} onValueChange={setTab} ariaLabel="Item detail">
        <Tabs.Item value="overview" title="Overview">
          <Step marker={{ kind: 'number', value: 1 }} title="The request">
            <Text value={item.summary} selectable />
          </Step>
          <HappierDisclosure
            expanded={expanded} onExpandedChange={setExpanded}
            reducedMotion={reducedMotion} motion={HAPPIER_INSTANT_DISCLOSURE_MOTION}
            showDivider={false}
            header={({ headerProps }) => (
              <HappierPressable {...headerProps}><Text value="More context" /></HappierPressable>
            )}
          >
            <Text value="Additional facts from this item's data owner." selectable />
          </HappierDisclosure>
        </Tabs.Item>
        <Tabs.Item value="activity" title="Activity">
          <Text value="The source's activity belongs here." />
        </Tabs.Item>
      </Tabs>
    </Stack>
  );
}

export function ItemsPage({ items, openKey, onOpenChange }: {
  items: readonly Item[]; openKey: string | null;
  onOpenChange(key: string | null): void;
}) {
  const [presentation, setPresentation] = React.useState<HappierCollectionPresentation>('table');
  const model = useHappierCollection({ items, keyOf, openKey, onOpenChange, expandable: true });
  return (
    <Stack style={{ flex: 1 }}>
      <Row>
        <Button title="Table" onPress={() => setPresentation('table')} />
        <Button title="Board" onPress={() => setPresentation('board')} />
      </Row>
      <Collection
        model={model} presentation={presentation} detail="auto" accessibilityLabel="Items"
        minListWidth={280} minDetailWidth={420} preferredListRatio={0.4}
        anatomy={{
          glyph: () => <Icon name="document-text-outline" />,
          title: (item) => item.title, accessibilityLabel: (item) => item.title,
          columnTitles: { title: 'Item' }, peek: (item) => <Text value={item.summary} />,
        }}
        detailHeader={(key) => ({ title: items.find((item) => item.id === key)?.title ?? 'Item' })}
        renderDetail={(key, { headerHosted }) => {
          const item = items.find((candidate) => candidate.id === key);
          return item ? <ItemDetail item={item} headerHosted={headerHosted} close={model.actions.close} /> : null;
        }}
      />
    </Stack>
  );
}
```

The measurements above are this example's readable pane sizes, not platform
breakpoints. An action inside a row's peek, a card or a detail header takes
`Button size="small"`: the host's desktop control height under a pointer, and
never less than the platform's touch target on a phone. Prose that is read rather
than scanned — a detail's description, a story step's body — takes
`Text variant="reading"`; `body` is the denser secondary line a row or a field uses. The disclosure intentionally uses the public instant motion driver;
a custom animated composition may supply a public `HappierDisclosureMotionDriver`
while honoring `reducedMotion`. Its header receives the toggle and expanded
accessibility state together. Keep `defineUiSurface` as the provider boundary.

Use `Tabs tabList="host"` when an enclosing detail frame already draws the tab
strip and requests one panel. Use `layout="fill"` inside a bounded region for a
self-scrolling view. A retained `Tabs.Item retention="retain"` mounts only after
its first visit; its asynchronous work must consume `useTabPanelActivity()` and
stop when `activeSignal` aborts. Retention ends with the Tabs mount.

When several tabs present one stateful renderer, provide it once as
`Tabs sharedPanel={...}` and update its panel input from the controlled tab value.
The renderer stays mounted and the visible panel remains labelled by the selected
tab. Inside that renderer, host-mode Tabs still own each panel's retention and
active interval. For a persistent outer `ScrollArea`, `scrollEnabled={false}` lets
a bounded child panel own scrolling without remounting the renderer.

For a PRs & Issues source, declare the panels on the source descriptor and render
only the requested panel. The [source detail and fix-link recipe](/plugins/ui#source-detail-panels-and-fix-pull-requests)
uses the public Triage feature protocol.

## Session tabs

A surface mounted as a session tab (`rightSidebarTab`) sits under the pane header
Happier already draws for that tab: its name on desktop, the large title on a
phone. Put the tab's add action and its one live fact there with
`PaneHeaderContent`, never in a header of your own:

```tsx
<PaneHeaderContent
  line={needsYou > 0 ? [{ text: `${needsYou} needs you`, attention: true }] : []}
  actions={<Menu trigger="Link a conversation" triggerIcon="add" triggerAccessibilityLabel="Link a conversation" items={bots} onSelect={link} open={open} onOpenChange={setOpen} />}
/>
```

The actions render in the header, outside your surface's tree, and keep your
plugin's context. Where the host mounts the surface without a pane header (a
page or a widget), `PaneHeaderContent` renders nothing, so keep an add path in
the body as well (an empty state's action). `triggerIcon` on `Menu` and `Popover`
draws the trigger as a glyph alone, the way the host's own "+" and ⋯ look.

In the Developer Preview source contract, a page Collection can supply
`detailHeader(key)` with the item's `title`, optional `subtitle` and `actions`.
Happier renders them in its details band and supplies Close. The same
`renderDetail(key, { headerHosted })` body runs in every container; omit its
inline heading and close controls when `headerHosted` is true. Keep item
selection in the page location, and pair a pushed detail location with
`backLocation` so phone Back returns to the collection.

A row can open in place: pass `expanded` and `expandedContent` to `List.Item`
and toggle `expanded` from its `onPress`. Put a few calm facts in it
(`Metadata`), then the row's own actions at the bottom as buttons, one of them
primary. Use it for what an item is to this tab, not for a page; open the page
with `openSurface` instead. The motion and reduced motion are the host's.

People are drawn with `Avatar({ name })`, the same mark Happier uses for people
elsewhere. It takes a name, never an image URL.

## Show a live session

A surface can show one of the Account's sessions live — the real transcript,
its prompts and its composer — rendered by Happier's own session view. The
plugin never draws a transcript or a composer itself.

Get a session id through Actions you already have (`session.spawn_new` or
`session.fork`, from UI or from `activate(api)`), keep it in your own storage,
and render it:

```tsx
import { SessionChat } from '@happier-dev/plugin-ui';

<SessionChat sessionId={leadSessionId} />                     // transcript, prompts and composer
<SessionChat sessionId={leadSessionId} variant="transcript" /> // read-only
```

For your own arrangement, put the parts under one `SessionProvider`. The provider
is the one controller for that session; the parts are views of it wherever they
sit, and each part appears at most once per provider (a duplicate renders
nothing, and so does a part outside a provider):

```tsx
import { ListDetailLayout, SessionComposer, SessionProvider, SessionTranscript } from '@happier-dev/plugin-ui';

<SessionProvider sessionId={leadSessionId}>
  <ListDetailLayout
    minListWidth={280} minDetailWidth={420} preferredListRatio={0.35}
    list={<LeadFacts />}
    detail={<><SessionTranscript /><SessionComposer /></>}
  />
</SessionProvider>
```

- **Bounded region.** The parts fill a bounded flex column: the transcript takes
  the remaining height and the composer keeps its natural height. There is no
  auto-height mode; an unbounded parent gives the session no room. On iOS and
  Android the composer part must be the bottom element of a region that reaches
  the screen bottom, because it carries the keyboard and safe-area lift.
- **Inside tabs.** `Tabs` sizes to its selected panel by default
  (`layout="content"`), which is right inside a scroll area but leaves a session
  no height. Pass `layout="fill"` so the tab root and the active panel take the
  parent's remaining height:

  ```tsx
  <Tabs value={tab} onValueChange={setTab} ariaLabel="Lead" layout="fill">
    <Tabs.Item value="facts" title="Facts"><LeadFacts /></Tabs.Item>
    <Tabs.Item value="chat" title="Chat"><SessionChat sessionId={leadSessionId} /></Tabs.Item>
  </Tabs>
  ```
- **Test ids.** `SessionChat`, `SessionTranscript` and `SessionComposer` take an optional `testID`.
- **Read-only.** `SessionProvider readOnly` (or `variant="transcript"`) shows no
  composer, and its permission and question prompts say to open the session to
  respond.
- **What the plugin gets.** Nothing: no transcript content, callbacks or approval
  authority. The session resolves only inside the Account the surface is mounted
  in; a session that is missing, deleted or out of reach shows one neutral
  "isn't available" state. The person approves prompts as themselves, exactly as
  in the full session.
- **No nesting.** Nothing inside the embedded session mounts a plugin surface,
  including the one showing it.
- **Where it renders.** React Native and React Native Web surfaces only. Hosted-web
  surfaces, isolated tests and hosts without the session view render the
  `fallback` you pass (nothing by default); for a web page outside Happier, use
  the embed. `createPluginUiRnwSemanticSurfaceAdapter({ sessions: true })` presents
  the parts in tests as semantic stand-ins (a group named `Session <id>`).

The session components are Developer Preview.

## Show an agent working on your surface

When an agent acts on something your surface shows (a board, a canvas, a
preview), use the same co-presence pieces Happier's browser and shared-window
viewers use. Render them inside the box they narrate; they position themselves
on its edges.

```tsx
import { AgentCursor, PresenceCapsule, StatusCapsule, usePluginHostApi } from '@happier-dev/plugin-ui';

const hostApi = usePluginHostApi();

<View style={{ flex: 1 }}>
  <Board />
  <AgentCursor target={activeTarget} testID="board-cursor" />
  <PresenceCapsule
    presence={presence}                 // { kind: 'agent' | 'stopping' | 'human' | 'unconfirmed' | 'idle', controlEpoch }
    agentName="Claude"
    agentTitle="Claude is editing the board"
    agentDetail="Moving “Launch plan”"
    onTakeControl={() => hostApi.executeAction('take-control')}
    onHandBack={() => hostApi.executeAction('hand-back')}
    testID="board-presence"
  />
  <StatusCapsule visible={reconnecting} busy text="Reconnecting to the board" testID="board-status" />
</View>
```

- **`PresenceCapsule`** says who is driving and offers the one control: Take
  control, then "Stopping Claude…" until `presence.controlEpoch` moves, then
  "You have control" with Hand back. `unconfirmed` never claims the person has
  control; pass `onCheckAgain` for the fresh look that confirms the stop. The
  capsule holds no authority: wire both buttons to your own Actions, and feed
  `presence` from whatever owns control of your surface. `placement="inline"` or
  `"strip"` puts it in flow, `onWatch` adds a Watch button, and
  `renderAgentMark` draws your mark (for example `BrandMark`).
- **`AgentCursor`** draws the agent's hand where it acts and a ring around the
  element. `target` is normalized to the page (0..1, with optional `width` and
  `height` for the ring); pass `pageRect` when the page is letterboxed inside the
  box. It is decorative: it takes no input and is hidden from screen readers, so
  pair it with a `PresenceCapsule`.
- **`StatusCapsule`** is one quiet sentence at the top edge while something is
  not normal, with an optional `action` as the way out. Keep it mounted and flip
  `visible` so it leaves smoothly; healthy is quiet.

In a Happier window these use the app's own glass, type, buttons and motion. In
a hosted-web realm they draw a plain solid capsule and changes land at once.
Advanced authors find the shared owners in `/presentation`
(`HappierPresenceCapsule`, `HappierAgentCursor`, `HappierStatusCapsule`, and
`HappierStatusDot` with its `halo` ring). These components are Developer Preview.

### Capture previews and Session images

This media interface is under development in 0.3. Use these examples only when
your installed SDK and Plugin UI API inventories list the media exports below.

The Developer Preview `HappierLiveStream` presents a read-only capture in a
mounted Happier RN/RNW surface. Pass either your own manifest-declared source,
or a host source that the user approves for this viewing:

```tsx
import { HappierLiveStream, Text } from '@happier-dev/plugin-ui';

<HappierLiveStream
  reference={{ kind: 'plugin', source: { pluginId: 'acme.board', localId: 'preview' } }}
  testID="board-preview"
  fallback={<Text value="Open this preview in Happier" />}
/>
```

Declare `preview` in this plugin's `captureSources` contributions. The host
owns transport, decoding and cleanup; the plugin never receives a stream
address. A `{ kind: 'host', sourceId }` reference goes through the existing
`capture.view` Action approval for each viewer occurrence. Approval is required
by default; the user may waive it for a particular plugin in Action settings.
Replacing a source closes its viewing and does not inherit that consent. Your
plugin's own declared captures require no additional viewing consent. Viewing
does not give control: input and takeover remain host-owned, approved Actions.
Without an app renderer, including a caller-hosted HTML realm, the supplied
`fallback` renders instead.

Use `StoredImage` with a `StoredImageRefV1` from
`@happier-dev/plugin-sdk/ui`. Pass the complete file-backed native Session-image
reference, including its media identity, dimensions, byte size and `file` facts
(Session, storage, relative path, digest and MIME type). Capture, attachment,
snapshot and Session-event Actions can return these references. You may retain
a reference across surface remounts or pass it to another plugin; the receiving
plugin's declared Session scope still decides access. A reference grants no read
permission, and arbitrary file paths cannot replace native Session-image facts.

```tsx
import { StoredImage } from '@happier-dev/plugin-ui';

<StoredImage image={imageReference} accessibilityLabel="Captured page preview" />
```

Image reads require the plugin's declared `sessions` HostAccess **read** scope
(and the selected scope when access is optional), not the broader linked-Session
UI scope. The same scope owner applies on the daemon. Plain/E2EE mismatches or
unavailable encryption material return an unavailable image, never a plaintext
fallback. The app thumbnail and `StoredImage` share `HappierStoredImage` in
`/presentation`. These are development-source interfaces; package publication
and loaded-runtime verification remain separate.

The daemon also verifies the exact Session artifact bucket, real file path,
size, digest and image encoding. A result's producer does not grant broader read
access. `sessions.media.publishGenerated` returns publication status rather
than this native artifact reference; generated-media records are not a
`StoredImageRefV1`.

## Work lists and maps

A surface that shows agent work — runs your plugin started, steps it is waiting
on, work grouped by where it stands — can draw it with the primitives Happier's
own Work tab, Inbox and workflow maps use, from
`@happier-dev/plugin-ui/presentation`:

- `HappierWorkSection`: a group of a live work list (a compact title and a quiet
  count), or with `anatomy="page"` a configuration section laid flat on the pane.
- `HappierWorkRowShell` and `HappierWorkSummary`: a Work row's pressable shell
  and its identity leaf (mark, title, one line of facts, the state word at the
  trailing edge).
- `buildHappierWorkMap` and `HappierWorkMapView`: a map of work built only from
  the parent each node declares, drawn as cards on a rail or in side-by-side lanes;
  `density="compact"` is the mini-map a row carries.
- The status language: map your own facts to `{ bucket, tone, word }`
  (`HappierWorkStatusPresentation`). Buckets read in `HAPPIER_WORK_STATUS_BUCKETS`
  order and `resolveHappierWorkStatusBucketLabel` labels them in the host's
  locale. `HappierWorkStatusWord` and `resolveHappierWorkStatusSurfaceStyle` draw
  the tone: a soft ring and tint only for work that needs the person or failed.

```tsx
import * as React from 'react';
import { useHappierUiLocalization } from '@happier-dev/plugin-ui/environment';
import {
  buildHappierWorkMap,
  HappierWorkMapView,
  HappierWorkRowShell,
  HappierWorkSection,
  HappierWorkStatusWord,
  HappierWorkSummary,
  resolveHappierWorkStatusBucketLabel,
} from '@happier-dev/plugin-ui/presentation';

function DeployWork({ deploys, onOpen }: DeployWorkProps) {
  const { translate } = useHappierUiLocalization();
  const waiting = deploys.filter((deploy) => deploy.status.bucket === 'needs_you');
  return (
    <HappierWorkSection
      testID="deploys-needs-you"
      title={resolveHappierWorkStatusBucketLabel('needs_you', translate)}
      count={String(waiting.length)}
      countTone="attention"
    >
      {waiting.map((deploy) => (
        <HappierWorkRowShell
          key={deploy.id}
          testID={`deploy:${deploy.id}`}
          accessibilityLabel={`${deploy.name}, ${deploy.status.word}`}
          onPress={() => onOpen(deploy.id)}
        >
          <HappierWorkSummary
            title={deploy.name}
            phase="attention"
            mark={<DeployMark />}
            facts={[deploy.environment, deploy.stepLabel]}
            trailingState={deploy.status}
            accessibilityLabel={`${deploy.name}, ${deploy.status.word}`}
          />
        </HappierWorkRowShell>
      ))}
    </HappierWorkSection>
  );
}

const map = buildHappierWorkMap({
  relationships: 'authored',
  nodes: [
    { nodeId: 'release', label: 'Release 4.2', parentNodeId: null, open: { kind: 'run', runId: 'release' } },
    { nodeId: 'smoke', label: 'Smoke checks', parentNodeId: 'release', open: { kind: 'run', runId: 'smoke' } },
  ],
});

<HappierWorkMapView
  map={map}
  selectedNodeId={null}
  testIDPrefix="release-map"
  accessibilityLabelForNode={(node) => node.label}
  renderStatus={(node) => <HappierWorkStatusWord tone="neutral" role="rowState">{wordFor(node)}</HappierWorkStatusWord>}
  onOpen={(node) => openRun(node.open)}
/>;
```

Inside a mounted surface these read the theme, page palette and text scale from
the surface environment. The words stay yours: a row says the owner's own state
("Waiting for approval"), never the bucket label. A row carries no answer
controls; open the place where the request is answered once.

## Accessibility and offline snapshots

Use the semantic package's accessibility-aware controls and preserve a logical
reading and focus order. Read locale, direction, color scheme, contrast, text
scale, reduced motion, screen-reader state, and safe-area insets from the
semantic surface context rather than copying host state. Support Dynamic Type,
RTL and long strings, high contrast, reduced motion, and 44×44-point iOS or
48×48-dp Android targets.

The host owns occurrence currentness. Do not retain a competing currentness
flag. If a host operation becomes unavailable, preserve useful rendered state
and present a recoverable status instead of assuming the mutation succeeded.

While disconnected, Happier can retain the mounted visual tree as a
non-interactive snapshot. It blocks pointer, touch, keyboard, focus,
accessibility actions, and host API mutations, then exposes a localized
host-owned static summary using the surface's declared display title. Provide
a meaningful localized title and make the last rendered visual state
understandable without requiring a control. Reconnect supplies a revalidated
context before interaction resumes.

## Build output

For a production artifact, `hdev plugins dev build .` writes the portable
UI artifact tree under `dist/happier-plugin-ui`. The generated
`--ui reactNative` project exposes one exact source entry through
`./happier-plugin-ui/<artifactId>`. The daemon compiler emits one minified
CommonJS bundle that web, iOS, and Android evaluate through the same host-module
contract. Do not run a second platform-specific bundler.

Artifact targets are not a mobile/tablet availability promise. The current host
registry admits every declared UI binding on web/desktop and native tablet. On
native phone it admits only `appPage`/`app`, `settingsPage`/`app`, App and
Session `rightSidebarTab`, `browserPanel`/`browser`, and
`servicesPanel`/`services`; Project phone and the other pane cells remain
unavailable. Let the mount result describe the exact outcome rather than
inventing a plugin-local fallback. Loaded mobile and tablet host validation is
separate from source-level admission.

The manifest declares the direct view and artifact references.
`ui-artifacts.json` describes the emitted files and digests. Authors do not
hand-author the final content digest.

## Failure isolation

Evaluation and render failures are contained to the affected local surface.
Happier presents the standard unavailable-surface state and may retain a
verified last-known-good visual. Crash containment is device-local and is not a
plugin projection or byte-selection input.

## Boundary

The host owns navigation, permissions, app state, session lifecycle, and native services. Use the Plugin UI host API for supported interactions. The package-level trusted-code decision covers this client code, daemon code, dependencies, and build artifacts together.

Cross-plugin contribution points and targeted contributions are available in
Developer Preview where the generated capability matrix marks both rows
`available`. Keep a direct view same-plugin unless a documented protocol package
defines the target relationship; do not copy another plugin's declaration or
invent a target renderer or navigation contract.
