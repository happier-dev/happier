Happier has three public Plugin UI models. Choose the narrowest one that fits the experience:

- **Declarative host-rendered UI** for settings, actions, and other forms the host can render from manifest descriptors.
- **React Native UI** for a trusted, host-integrated component that needs the app's native UI model.
- **Hosted web UI** for an isolated, packaged web artifact whose runtime frame is admitted by the host. The development SDK also accepts [self-contained inline HTML](/plugins/ui/hosted-web#inline-html-in-development) through that frame path.

React Native plugin code is trusted package code and runs in the client realm; it is not a sandbox.

## Hosted web scaffold and availability

The hostedWeb scaffold emits the packaged artifact and canonical bootstrap contract; each host then reports the one physical frame adapter it can construct, so packaged runtime availability is per host rather than a single global claim. See [Hosted web UI](/plugins/ui/hosted-web#build-and-runtime-availability) for the derived per-host status.

Start the source product with the same beginner command as every other plugin:

```bash
hdev plugins create ./my-hosted-plugin \
  --id com.example.my-hosted-plugin \
  --name "My hosted plugin" \
  --ui hostedWeb
```

The generated project contains a conventional hosted artifact directory, relative
assets, loading/error UI, and a public ready-to-bootstrap client. It does not make a
browser, desktop, iOS, or Android runtime-support claim. Do not treat a
development preview, source checkout, or emitted asset tree as packaged frame
support.

The hosted client gets surface facts from the host-issued bootstrap, never by
parsing URL data:

```ts
import { createPluginUiRenderContext } from '@happier-dev/plugin-sdk/ui/client';

const context = await createPluginUiRenderContext();
await context.hostApi.executeAction('save-note', { note: 'hello' }, { signal: context.signal });
```

See [Hosted web UI](/plugins/ui/hosted-web) for the source/runtime boundary.

## React Native host API

Author a semantic surface with `@happier-dev/plugin-ui`.
`defineUiSurface` installs the one provider around the host-supplied
render context:

```tsx
import * as React from 'react';
import { Action, Card, defineUiSurface, Text } from '@happier-dev/plugin-ui';

function ReviewSurface() {
  return (
    <Card>
      <Text variant="title" value="Review summary" />
      <Action.Execute action="review-summary" title="Create summary" />
    </Card>
  );
}

export const renderSurface = defineUiSurface(ReviewSurface);
```

Use `@happier-dev/plugin-ui` for curated semantic controls. `react-native` is
a host-provided framework singleton, not a Happier component contract. Do not
use raw primitives to recreate a curated control, a host provider, bridge, or
navigation root. A plugin-owned implementation may use compatible React Native
primitives only when the generated toolchain declares framework support for
that artifact; it must not assume host styling, overlay, focus, or navigation
behavior. Never construct a host provider or import a Happier-internal
transport.

The root `@happier-dev/plugin-ui` entry is the ergonomic, curated author tier
and the normal starting point. Trusted React Native and React Native Web
authors who need custom composition may also import
`@happier-dev/plugin-ui/presentation` for shared React Native/React Native Web
primitives and behavior, or `@happier-dev/plugin-ui/environment` for
environment facts, hooks, and its standalone fact provider. The explicit
`@happier-dev/plugin-ui/advanced` entry is reserved for isolated tests and
complete standalone mounts that genuinely own provider/Resource lifetime.
`/presentation` does not re-export environment contracts: import
`/environment` directly for theme, localization, accessibility, platform, or
inset facts. Those deliberate advanced tiers share the canonical core
implementations; they are prepublication work in progress and carry no released
stability promise while the package remains on hold.

Advanced imports do not expose an alternate mounted host boundary. Do not
construct a host provider, access internal mount state, import app or host
internals, or import protocol types from an admitted surface.
`defineUiSurface` remains the only provider installation boundary there. Use
root hooks for host-backed Actions and Resources; `/data` remains the dedicated
Collection-query entry.

## UI capabilities in a client Action

In the 0.3 development contract, a client-targeted Action receives
`PluginClientActionContext` from `@happier-dev/plugin-sdk/actions`. Its bounded
`ui` capability is not a mounted surface: `ui.context({ signal })` returns only
`{ targetedContributions }`, where that value is the current contributions
targeted to the Action's plugin or `null`. It does not return a mount, surface,
page, selection, or layout context.

Use `ui.version()` to inspect the advertised methods and
`ui.selectActionInput(...)` when the person must choose an input. Selection
reuses the host's canonical input admission and custody; do not introduce a
parallel picker or copy private selection state. `ui.executeAction(...)` and
`ui.openSurface(...)` remain the ways to invoke an Action or open a declared
destination. This capability subset does not install a Plugin UI provider or
make a client Action a surface occurrence.

An advertised `ui.openNewSession(...)` uses the host's existing New Session
draft and navigation owner; it does not create a Session by itself. Automated
agent, MCP and CLI callers retain their real invocation surface. A client-target
Action needs an answering signed-in client with the exact current plugin
occurrence; without it, execution is unavailable. Approval follows the shared
Action settings, not an invented UI caller identity. These are unreleased 0.3
contracts: rebuild the Action artifact with the matching host and SDK.

## Approval for a direct UI write (development)

The unreleased 0.3 host API lets a direct Account write respect the same approval
settings as its contributed Action:

```ts
const confirmed = await hostApi.confirm('Remove this source?', {
  action: 'sources/administer-v1',
  signal,
});
if (!confirmed) return;
// Continue through the existing domain writer.
```

The host resolves the Action's current declaration and invoking-surface setting.
A waiver skips the dialog and returns `true`; Ask-first asks even for a safe
Action. Missing policy rejects before the write, and no daemon connection is
needed. Without `action`, `confirm` is an ordinary unconditional question.
This is a development contract change: rebuild Plugin UI artifacts using this
option with the matching 0.3 host, rather than expecting an older host to apply it.

## Publish mounted semantic context

The host automatically supplies a privacy-safe, parameter-free navigation
baseline. A mounted surface can optionally enrich that baseline with bounded
semantic data and contextual commands for the lifetime of that exact mount:

```tsx
import * as React from 'react';
import { usePluginHostApi } from '@happier-dev/plugin-ui';

function ReviewDetails() {
  const hostApi = usePluginHostApi();

  React.useEffect(() => {
    hostApi.publishCurrentUiContext({
      entity: {
        kind: 'review',
        label: 'PR #42',
        summary: 'Ready for review',
      },
      detail: { repository: 'example/widgets' },
      commands: [{
        title: 'Open changed files',
        command: {
          kind: 'openSurface',
          destination: 'review-files',
          input: { reviewNumber: 42 },
        },
      }],
    });

    return () => hostApi.publishCurrentUiContext(null);
  }, [hostApi]);

  return null;
}
```

`publishCurrentUiContext(enrichment)` atomically replaces this mount's prior
enrichment; passing `null` clears it. Unmount, parent or Account retirement,
and occurrence replacement also remove it synchronously. The value is strict,
bounded JSON data. It cannot contain a callback or become a second route,
selection, persistence, or navigation owner.

Commands reuse only the existing `executeAction | openSurface` semantic
command union. The host qualifies local references and exposes only an opaque,
snapshot-scoped command id to context readers. It retains the command payload
on the invoking client and resolves the id again against the current snapshot
before any effect. Plugins do not generate or persist those ids.

This publication does not itself send data to a Voice provider. The active
Voice client's privacy mode decides whether current-UI data leaves that client,
and automatic mode sends navigation metadata only; semantic detail and
commands remain on demand. The source contract and external-plugin development
fixture exercise this same public Host API and mount-retirement contract.
Loaded development-stack parity remains the deciding live proof; package code
remains trusted executable code.

## Destinations and form factors

Declare the view's `container`, `target`, and `renderer` in
`definePlugin(...)`; the host registry decides whether that exact pair can be
mounted. The generated `appPage` + `app` view is the portable starting point.
From an admitted surface, request another declared view through the one host
dispatcher rather than a local router:

```tsx
import { Button, usePluginHostApi } from '@happier-dev/plugin-ui';

function OpenDetails({ reviewId }: { reviewId: string }) {
  const hostApi = usePluginHostApi();

  return (
    <Button
      title="Open details"
      onPress={() => {
        void hostApi.openSurface('review-detail', { reviewId }, {
          subPath: `reviews/${reviewId}`,
        });
      }}
    />
  );
}
```

A `subPath` is only a location inside that plugin's `appPage`; it is ignored by
non-page destinations such as `rightSidebarTab`. Do not construct host routes,
choose another plugin's namespace, or add a local fallback destination.

In the current development build, an app page can read
`useSurfaceContext().page?.columnVisible` to see whether its host-provided
navigation column is on screen. A page with its own list can show a selection
prompt beside a visible column and keep the list when the column is hidden,
including on a phone. The `page` fact is absent on other placements.

### Changing your own page's location

`openSurface` selects a destination and adds a history entry. When your own page
changes what it is showing — a filter, an order, a selected row — that is a
location change, not a destination selection, so use `replacePageLocation`
instead. It replaces the current entry, so Back still leaves the page rather
than walking your page's interaction trail, and it resolves with the location
the host settled on, which is the one you render.

```tsx
const settled = await hostApi.replacePageLocation(`reviews/${reviewId}`, {
  // The one page-internal step the next system Back returns to. Omit it and
  // Back leaves the page as usual.
  backLocation: 'reviews',
});
```

The host consumes at most one Back with `backLocation` and then yields, and a
step equal to the location being replaced to is ignored rather than consuming a
press that would visibly do nothing. Any navigation your page did not perform
itself retires the step. `replacePageLocation` is advertised only on a full-page
destination; check `hostApi.version().methods` before relying on it, and never
reach for browser history or a local router instead.

The current registry admits every declared UI binding on web/desktop and
native tablet. On native phone, it admits only `appPage`/`app`,
`settingsPage`/`app`, App and Session `rightSidebarTab`,
`browserPanel`/`browser`, and `servicesPanel`/`services`; Project phone and the
other pane cells are intentionally unavailable. An emitted web, iOS, or Android
artifact does not widen that matrix. Treat these as source-level admission
rules—loaded mobile and tablet validation remains a separate host proof.

## Embedded Session widgets

> **Development preview:** Session Board placement is still being completed and
> validated across Happier's supported hosts. A self-hosted development server
> offers the Board by default unless its operator disables
> `HAPPIER_FEATURE_SESSIONS_BOARD__ENABLED`, and Happier
> exposes the Board only after the current Session System Records contract is
> active. Plugin declarations remain installed and recoverable while the Board
> is unavailable; availability does not grant Session access or Action authority.

A `widget` view with a Session target is embedded Session content, not a destination. Happier
frames it as one *widget* that a person can place on a Session Board and open
from Details, the compact sidebar, the Companion and the mobile Cockpit — all
through the same host. It never appears in navigation, collision domains, or
`openSurface`, and it takes no `instancePolicy`.

In current development source, a widget's App/Session target describes its
data context, not where it can be placed. Configured instances can be hosted
on Home, a personal Work Board, the Session Board, directly in the personal
Companion, or a declared native/declarative plugin-page area. A Session widget
declares typed inputs, an input schema and `sessionInputPath`; the host resolves
that field to an exact Home-qualified Session. Copies can follow the host
context or pin a different Session independently. Existing Companion references
to Board items still read shared Board content; a direct instance keeps its
own personal inputs. A definition is the reusable content/input declaration;
an instance is one configured copy, with order, width and frame belonging to
its host layout. Account-library definition edits affect their references;
Duplicate creates independent content. Setup/edit UI and loaded-platform validation are still
being completed in the widgets program.

```ts
{
  id: 'review-status-widget',
  container: 'widget',
  target: { kind: 'session' },
  sessionInputPath: 'session',
  inputs: { fields: [{ path: 'session', title: 'Session', widget: 'json', required: true, optionsSourceId: 'sessions' }] },
  inputSchema: {
    type: 'object', additionalProperties: false, required: ['session'],
    properties: {
      session: {
        type: 'object', additionalProperties: false,
        required: ['serverId', 'sessionId'],
        properties: { serverId: { type: 'string', minLength: 1 }, sessionId: { type: 'string', minLength: 1 } },
      },
    },
  },
  renderer: 'review-native',
  fallbackRenderers: ['review-web'],
  title: 'Review status',
}
```

For instance Refresh in development source, a widget can declare `resources`
as qualified `{ pluginId, localId }` references to its own declared Resources.
These dependencies do not grant access. Refresh waits for their admitted reads
to settle, and mounts sharing the same Resource context update together;
unavailable declarations or contexts return a typed refusal.

Because it is embedded content rather than a destination, `widget` sits
outside the destination-binding matrix above: the registry declares it for every
supported UI platform, in `content` and `fill` presentations only. Whether a given
person can actually see it still depends on the selected target's access and
their client admitting your renderer. Session Board hosting additionally needs
the Board capability on that Session's Home.

What the host guarantees at every mount:

- `mount.kind` is `embedded`, `role` is `widget`, and `presentation` is
  `content` (a framed card whose host owns bounds and scrolling) or `fill` (the
  expanded host, where your surface owns its own content scroll). There is no
  compact or inline presentation: measured geometry, platform, theme, scale,
  safe area and active state already arrive through the surface context, so
  adapt to the space rather than to a Happier shell name.
- `target` is the currently admitted exact Session selected by the configured
  binding. That Session supplies access, policy and machine routing, even when
  the widget is hosted on Home or beside a different Session. Losing access
  suspends execution; it never borrows the visible Session's authority.
- The stored Board item keeps a distinct instance identity, your qualified
  contribution identity and closed input-binding intents. A plugin update keeps
  the widget in place: the
  host retires the old occurrence and remounts the new one against the same
  surface identity. Declared `fallbackRenderers` may switch renderer within that
  same surface; nothing switches surface, plugin, or machine.
- Each physical placement is its own mount with its own instance identity and
  lifetime. Inactive or offscreen hosts suspend execution through their existing
  activity and demand owners.

When the plugin is disabled, uninstalled, retired, or no longer declares the
surface, Happier keeps the widget's frame and title and shows a localized state
with the recovery the person can actually perform. It never deletes the item,
guesses a replacement surface, or rewrites its stored source.

Installed first-party and external plugins use this same contract with the same
capabilities under equivalent grants: there is no privileged built-in path. A
widget still consumes only its negotiated Host API subset, and each Action and
Resource keeps its ordinary admission and approval policy.

The Board records and organization are shared with everyone who can read the
Session. Which Board view is active and what each person keeps in their Companion
stay local to that viewer and device. Reading Board content requires current
Session transcript access; changing it requires Session-record edit access.
Actions do not bypass those checks or Happier's normal authentication,
confirmation, and approval policy.

Shared credentialed widgets bind to each viewer's existing qualified Connected
Account purpose selection for the declared Resource consumer. Missing
selection asks that viewer to connect; it never borrows the editor's connection.
There is no per-instance viewer override. Pinned Connected Account references
are allowed on personal surfaces only. Changing the existing purpose selection
can affect other viewer bindings using that same qualified purpose, rather than
changing only this copy's connection. Explicit **Post a
snapshot** instead publishes the exact approved fixed output, timestamp and
provenance through the normal Board writer, without live Resource references
or credential bindings. See [configured widgets](/sessions/session-board#configured-widgets-in-development)
for the content and audience distinction, and
[personal widget areas](/plugins/ui/react-native#personal-widget-areas-in-development)
for native and declarative plugin-page embedding. Hosted HTML pages use ordinary
widget Actions without embedding host areas. Project-aside integration separately awaits the
Project program's portable Source producer; an exact checkout is not that Source.

Do not confuse an installed plugin's `hostedHtml` renderer with HTML authored
directly into a Board item. Installed first-party and external plugins are trusted
through the public SDK contract above. Caller-authored Board HTML has no plugin
identity or ambient plugin capability, and its smaller Host API ceiling is limited
to context, Resource reads and watches, Action execution, and notifications. Each
Resource and Action still applies its own admission and approval checks.

Current development source carries caller-authored Board HTML through the shared
frame implementation on web/Tauri, iOS, and Android. That is implementation
reachability, not a released support claim: loaded isolation and lifecycle proof
remains open for each advertised realm. When a current client cannot admit its
renderer, Happier preserves the item and shows a recoverable unavailable state
rather than deleting, retargeting, or rewriting it.

## Linked Session state and permission answers

> **Development preview:** these host methods are in current development source. They
> are not part of a released Happier version yet.

A surface that links its own entries to Sessions can show what those Sessions are
doing, and it can let the person answer a Session that is waiting for permission.
It never opens the Session to do this. A typical case is an issue that an Agent is
fixing. Three mounted host methods provide this, and the `useSessionState` hook
wraps the first two:

| Host method | What it does |
|---|---|
| `readSession(sessionId)` | Returns the Session's current state, or `null` when this Account cannot reach it. |
| `watchSession(sessionId, listener)` | Subscribes to changes. It uses the same acknowledged-async setup and bounded `invalidated` signal as `watchResource`. After each `invalidated` event, re-read with `readSession`. An `error` event means the Session became unreachable. |
| `respondToSessionPermission({ sessionId, requestId, answer })` | Answers one pending permission request with `allowOnce`, `allowForSession` or `deny`. |

```tsx
import { Button, usePluginHostApi, useSessionState } from '@happier-dev/plugin-ui';

function AgentStep({ sessionId }: { sessionId: string }) {
  const host = usePluginHostApi();
  const { status, state } = useSessionState(sessionId);
  const request = state?.pendingPermissions[0];
  if (status !== 'ready' || !request) return null;
  // request.summary / request.command say what it wants to run;
  // state.workspace says where. Offer only request.answers.
  return request.answers.map((answer) => (
    <Button
      key={answer}
      title={answer}
      onPress={() => host.respondToSessionPermission({ sessionId, requestId: request.requestId, answer })}
    />
  ));
}
```

The host owns what these methods return, and the plugin never computes a
second copy:

- **Lifecycle, runtime and operational state** come from Happier's Session
  awareness projection. That is the same answer the Session list shows.
- **`workStatus`** carries the host's shared Work presentation: `bucket`, `tone`
  and localized `word`. Consume this projection for grouping and status
  treatment. Healthy work stays neutral; permission, attention and failure
  facts use the same treatment as Happier's Work surfaces. A lead Session with
  unfinished reports is not Finished, and an offline Session's prior completion
  does not make it currently Finished. Your surface can keep its own story copy
  while using the host's bucket and tone.
- **`pendingPermissions`** are the requests the Session's own permission prompt
  is showing right now. Each one carries the tool, a readable summary, the exact
  command for shell tools, and when it was asked.
- **`answers`** lists what this person may give. It is empty when their Session
  access does not include approving permissions. A standard edit or plan-exit
  tool offers no `allowForSession`, and an Agent with no known prompt protocol
  offers only `deny`.

A Session is reachable when this Account's client can already open it. That is
usually a Session linked to one of your entries, but no plugin-level list
decides it. A plugin cannot widen that scope, and a Session the Account cannot
reach reads as `null`.

`respondToSessionPermission` is not a second permission authority. The host
applies the answer through the same decision path as the Session's own
permission prompt, and records it as that person's answer. Only call it from a
user action in your surface, such as a button press. A request that is no longer
pending, a Session the Account cannot reach, and an answer not listed in
`answers` all resolve as `{ status: 'refused', reason }` without changing
anything. If the answer cannot be delivered, the call rejects with a typed host
error.

These are client host methods of a mounted surface. They are not daemon
Actions: a plugin's daemon code still cannot answer a permission request as the
person.

A Session publishes its review findings as Review comments. To read them for a
linked Session, call the `reviews.comments.list` host Action with that
`sessionId`, or use `useReviewCommentProposalsForEntry` for proposed comments
linked to one entry. Tests can install `readSession`, `watchSession` and
`respondToSessionPermission` handlers in `@happier-dev/plugin-sdk/testing`, and
emit a watch signal with `invalidateSession`.

## Source detail panels and fix pull requests

**0.3 development / Developer Preview:** PRs & Issues sources use
`@happier-dev/triage-protocol/v1`, alongside the public SDK and Plugin UI.
The feature package owns the descriptor, detail input and fix-link Action
contracts. It gives an author no direct access to Triage's Collections.

Declare the tabs per entry kind on your source descriptor:

```ts
import { TriageSourceDescriptorV1Schema } from '@happier-dev/triage-protocol/v1';

export const descriptor = TriageSourceDescriptorV1Schema.parse({
  v: 1, purpose: 'example-errors', displayName: 'Example errors',
  kinds: [{
    id: 'error', workflowSubject: 'errorIssue', displayName: 'Error',
    detailTabs: [
      { kind: 'shared', id: 'overview' },
      { kind: 'shared', id: 'activity' },
      {
        kind: 'source', id: 'stack-trace', title: 'Stack trace',
        titleKey: 'plugins.exampleErrors.ui.tab.stackTrace',
      },
    ],
    detailActions: true,
  }],
});
```

Triage draws the shared Overview, Activity, Files and Checks strip and appends
your declared source tabs. Declare a source tab's optional `titleKey` in your
plugin's translation bundles; the host projects the admitted source's strings
for the active locale, with English fallback, and `title` remains the fallback
when the key is missing. It mounts your existing detail renderer with the
requested `panel`; `detailActions: true` requests the separate `actions` panel
in the detail header. Render only that panel, using your own source terminology
and Action handlers. Parse the input with `TriageDetailSurfaceInputV1Schema`.
When using `Tabs` internally, set its `value` to the requested panel and
`tabList="host"` to avoid drawing a second strip. Without `detailTabs`, the
source keeps its whole-detail body and receives no panel selector.

Panel changes update the same source detail instance. Keep occurrence selection
and settled evidence pages in that instance; do not key the renderer by panel or
put selection in a global cache. Declare retained internal panels through Tabs
and stop hidden-panel reads with their activity signal. Retiring or changing the
entry ends the source instance and its outstanding work.

The [Collection composition](/plugins/ui/react-native#a-collection-with-one-detail-body)
shows public imports for the detail container, `Step`, `Tabs` and
`HappierDisclosure`. Retained tab work uses `useTabPanelActivity().activeSignal`;
the source retains parsed panel state while Triage owns the enclosing frame.

An issue or error can link to a fixing PR from another source. Use the exact
qualified Action references rather than importing a Triage implementation:

```ts
import {
  TRIAGE_READ_FIX_PULL_REQUESTS_ACTION_REF_V1,
  TRIAGE_SET_FIX_PULL_REQUEST_ACTION_REF_V1,
  TriageReadFixPullRequestsResultV1Schema,
  TriageSetFixPullRequestResultV1Schema,
  type TriageEntryRefV1,
} from '@happier-dev/triage-protocol/v1';
import type { PluginUiHostApi } from '@happier-dev/plugin-sdk/ui';

export async function linkFixPullRequest(
  host: PluginUiHostApi,
  entryRef: TriageEntryRefV1,
  issueDisplay: { title: string; scopeLabel: string },
  pullRequest: { entryRef: TriageEntryRefV1; display: { title: string; scopeLabel: string } },
  signal?: AbortSignal,
) {
  const written = TriageSetFixPullRequestResultV1Schema.parse(await host.executeAction(
    TRIAGE_SET_FIX_PULL_REQUEST_ACTION_REF_V1,
    { v: 1, linked: true, entryRef, displayAtMark: issueDisplay,
      fixPullRequest: pullRequest.entryRef, displayAtLink: pullRequest.display },
    { signal },
  ));
  if (written.status !== 'linked') return { written };
  const resolved = TriageReadFixPullRequestsResultV1Schema.parse(await host.executeAction(
    TRIAGE_READ_FIX_PULL_REQUESTS_ACTION_REF_V1, { v: 1, entryRef }, { signal },
  ));
  return { written, resolved };
}
```

The read returns owner-ranked `candidates`, a `primary` PR or `null`, and an
`incomplete` flag when the Session-link page is partial. Candidates carry their
`user` and/or `session` origins and `open`, `merged`, `closed` or `unknown`
status. A currently declared non-PR kind cannot be a fix candidate or a new link;
the write rejects with `PluginError` code `triage_fix_pull_request_kind_invalid`.
An unavailable descriptor preserves an explicit choice with unknown status; a PR closed without merging
stays listed but is never primary. The enclosing Triage detail routes Files and
Checks through the primary PR's own source.

Unlink with the same write reference and `linked: false`, omitting
`displayAtLink`. The owner remembers that dismissal so a co-linked Session
does not immediately propose the PR again. Handle `conflict` by re-reading and
`full` by letting the person remove a choice; transport failure or cancellation
does not prove a write succeeded. A created PR becomes a Session-derived
candidate only after it is linked to that Session. Keep the writer, resolver
and storage private to Triage; callers submit intent and render the resolved read.

## Accessibility, currentness, and offline behavior

Executable UI authors own the semantics inside their renderer while it is
interactive. Treat accessibility and environment support as part of the
renderer contract:

- use semantic controls with localized names, roles, state, reading order, and
  visible keyboard focus
- support keyboard operation, screen readers, Dynamic Type or 200% zoom,
  high contrast, RTL and expanded strings, and reduced motion
- keep touch targets at least 44×44 points on iOS and 48×48 dp on Android
- consume the semantic package's surface-context and accessibility hooks
  instead of guessing host settings or retaining a second host snapshot

The host owns process-local occurrence currentness and host API availability.
Authors must not cache a separate “current” occurrence or implement a
functional offline mode. Handle unavailable host operations and cancellation,
and let the existing render-context/host-API subscription update the
environment.

When the daemon disconnects, Happier may keep the last mounted renderer as a
visual, non-interactive snapshot. Its actions, focus, and host mutations are
blocked. Because arbitrary executable subtrees cannot safely expose controls
as read-only semantics, the host announces a localized static summary from the
surface's declared display metadata. Give every executable surface a meaningful
localized title, and keep the last rendered visual state understandable without
requiring an action. Reconnection revalidates the selected release and digest,
current occurrence, policy, and context; it does not create a second trust
prompt.

## Build artifacts

Executable UI is compiled into one minified CommonJS bundle per artifact under
`dist/happier-plugin-ui` and described by `ui-artifacts.json`. The package
exposes each authored entry as `./happier-plugin-ui/<artifactId>`; the daemon
compiler discovers those exact exports and verifies the emitted artifact tree.
Hosted web stays a separate framed static artifact. See
[UI artifacts](/plugins/ui/ui-artifacts) for the complete build and runtime
contract.

Start from a generated UI project when possible:

```bash
hdev plugins create ./my-plugin \
  --id com.example.my-plugin \
  --name "My plugin" \
  --ui reactNative
```

## Boundaries

- Declare surfaces with `defineUiSurfaceDefinition`. **Advanced:** the raw
  `ui.views` / `ui.renderers` pair — direct `id`, `container`, `target`,
  `renderer`, optional `fallbackRenderers`, `title`, `instancePolicy`, and
  `headerActions` — stays supported for a shared renderer, a fallback chain, or
  a custom artifact. It is not a second beginner path. The host projects either
  form into its own normalized binding.
- Use only public SDK paths. Do not import app, daemon, or protocol internals.
- For cross-plugin behavior, consume a maintained feature-owned operation
  protocol; it binds existing Actions and does not create a separate renderer
  or navigation path.
- Treat the whole installed package as the trust unit, including client code.
- Use `context.ui` from daemon invocations for host-owned prompts, notifications, status, widgets, title, and composer controls; it is separate from executable surface rendering.
