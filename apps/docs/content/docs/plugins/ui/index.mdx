Happier has three public Plugin UI models. Choose the narrowest one that fits the experience:

- **Declarative host-rendered UI** for settings, actions, and other forms the host can render from manifest descriptors.
- **React Native UI** for a trusted, host-integrated component that needs the app's native UI model.
- **Hosted web UI** for an isolated, packaged web artifact whose runtime frame is admitted by the host. The development SDK also accepts [self-contained inline HTML](/plugins/ui/hosted-web#inline-html-in-development) through that frame path.

React Native plugin code is trusted package code and runs in the client realm; it is not a sandbox.

In 0.3 development source, `CapabilityAddBody` places the selected item's single
primary action below its identity and purpose. Supply the action descriptor through
`detailFooter` and render `CapabilityAddDetailAction` once at that position in
`renderDetail`. The [configuration recipe](/plugins/ui/configuration-pages) shows
the shared Add body and its input modes.

For a full Project destination in 0.3 development source, use the existing
`appPage` family with a Project target. The
[Project page recipe](/plugins/ui/configuration-pages#project-pages) covers
accepted context, the shared host DetailsPane and local page navigation.

## Session skills in development

In **0.3 development source**, a Session contribution uses the existing
`rightSidebarTab` placement and `target: { kind: 'session' }`. The mounted
surface context supplies the Session identity; placement and navigation remain
with the host. There is no separate Bot rail contribution family.

The maintained public-authoring companion's `session-skill-reference` view
demonstrates this slot with a typed `skills.read` host Action and
`HappierSavedSkillCard` from `@happier-dev/plugin-ui`. The component
takes semantic text and action controls and performs no reads or mutations.
The example reads only when requested and explicitly leaves runtime application
unknown. A successful read or save is not proof that the running Agent loaded
the skill.

The generated [host Actions](/plugins/api/host-actions) include selected
`skills.list({ skillIds })` reads and acknowledged `skills.create` summaries.
Use the existing Actions for capabilities and reach changes. A live surface may
route those controls through its mounted host; immutable transcript snapshots
retain their supported presentation profile and cannot gain live resources or
mutation controls by embedding a shared card.

## Machine pages in development

In **0.3 development source**, declare a full Machine destination with
`placement: 'appPage'` and `target: { kind: 'machine' }` through
`defineUiSurfaceDefinition`. The existing Surface Registry admits it into the
Machine page catalog. This is an unreleased source contract; check the installed
SDK and host before depending on it.

The mounted `useSurfaceContext().target` (or `await hostApi.context()` in hosted
code) carries `{ kind: 'machine', serverId, machineId }`. Both routing ids are
required. When known, the same target also carries `homeId` (the verified Home
identity, not a device-local profile id) and `installationId` from the addressed
Machine's current enrollment. Missing facts stay absent; do not substitute the
plugin's execution Machine or invent an installation. Read these host-supplied
facts instead of parsing a route or choosing another Machine from a global
inventory. The authored target optionally names
`serverIdPath` and `machineIdPath` for launch-input bindings; those path names
are not mounted identity values.

Use `target: { kind: 'services' }` only for a `servicesPanel`. A Services panel
does not become a Machine page by carrying the same ids. A retired, conflicting
or unavailable contribution cannot keep mounting through a second registry or
fallback target. Ordinary Actions and Resources keep their own authorization,
currentness and cancellation checks; a page target grants no native control.
Contributed plugin Actions still execute at the plugin's selected execution
origin. For a controller-addressed host Action such as
`machines.provisioners.check`, explicitly pass this target's `homeId` and
`controller: { machineId, installationId }`; if those facts are absent, keep that
operation unavailable. Opening a Machine page does not relocate the plugin.

To open Happier's existing managed-Machine configuration draft from this page,
call `hostApi.openManagedMachineConfiguration({ provisioner: { pluginId, localId } }, { signal })`.
Check `hostApi.version().methods` for `openManagedMachineConfiguration` when
supporting an older host. Only a current admitted Machine mount with known Home
and installation facts offers this method. Happier validates the current Account
and exact provisioner, and supplies this Machine as the controller. Opening the
draft creates no Machine and performs no native acquisition; the existing final
review and Action admission still apply. A retired mount or unavailable
provisioner refuses the handoff.

The [Machine page example](/plugins/examples/action-resource-ui-plugin#add-a-machine-page-in-development)
uses only public SDK and Plugin UI imports. Universal service inventory,
controls and logs stay with Happier's Services owners; a plugin page can present
its integration-specific facts without creating another service model.

## Hosted web scaffold and availability

The hostedWeb scaffold emits the packaged artifact and canonical bootstrap contract; each host then reports the one physical frame adapter it can construct, so packaged runtime availability is per host rather than a single global claim. See [Hosted web UI](/plugins/ui/hosted-web#build-and-runtime-availability) for the derived per-host status.

Start the source product with the same beginner command as every other plugin:

```bash
hdev plugins create ./my-hosted-plugin \
  --id com.example.my-hosted-plugin \
  --name "My hosted plugin" \
  --ui hostedWeb
```

The generated project contains a conventional hosted artifact directory, relative
assets, loading/error UI, and a public ready-to-bootstrap client. It does not make a
browser, desktop, iOS, or Android runtime-support claim. Do not treat a
development preview, source checkout, or emitted asset tree as packaged frame
support.

The hosted client gets surface facts from the host-issued bootstrap, never by
parsing URL data:

```ts
import { createPluginUiRenderContext } from '@happier-dev/plugin-sdk/ui/client';

const context = await createPluginUiRenderContext();
await context.hostApi.executeAction('save-note', { note: 'hello' }, { signal: context.signal });
```

See [Hosted web UI](/plugins/ui/hosted-web) for the source/runtime boundary.

## React Native host API

Author a semantic surface with `@happier-dev/plugin-ui`.
`defineUiSurface` installs the one provider around the host-supplied
render context:

```tsx
import * as React from 'react';
import { Action, Card, defineUiSurface, Text } from '@happier-dev/plugin-ui';

function ReviewSurface() {
  return (
    <Card>
      <Text variant="title" value="Review summary" />
      <Action.Execute action="review-summary" title="Create summary" />
    </Card>
  );
}

export const renderSurface = defineUiSurface(ReviewSurface);
```

Use `@happier-dev/plugin-ui` for curated semantic controls. `react-native` is
a host-provided framework singleton, not a Happier component contract. Do not
use raw primitives to recreate a curated control, a host provider, bridge, or
navigation root. A plugin-owned implementation may use compatible React Native
primitives only when the generated toolchain declares framework support for
that artifact; it must not assume host styling, overlay, focus, or navigation
behavior. Never construct a host provider or import a Happier-internal
transport.

The `/components` entry is the author UI layer, re-exported by the root
`@happier-dev/plugin-ui` entry. Trusted React Native and React Native Web
authors who need custom composition may also import
`@happier-dev/plugin-ui/components` for shared React Native/React Native Web
primitives and behavior, or `@happier-dev/plugin-ui/environment` for
environment facts, hooks, and its standalone fact provider. The explicit
`@happier-dev/plugin-ui/advanced` entry is reserved for isolated tests and
complete standalone mounts that genuinely own provider/Resource lifetime.
`/components` does not re-export environment contracts: import
`/environment` directly for theme, localization, accessibility, platform, or
inset facts. Those deliberate advanced tiers share the canonical core
implementations; they are prepublication work in progress and carry no released
stability promise while the package remains on hold.

Advanced imports do not expose an alternate mounted host boundary. Do not
construct a host provider, access internal mount state, import app or host
internals, or import protocol types from an admitted surface.
`defineUiSurface` remains the only provider installation boundary there. Use
root hooks for host-backed Actions and Resources; `/data` remains the dedicated
Collection-query entry.

## Read a Machine display name (development)

In **0.3 development source**, a mounted surface can call
`host.readMachineDisplayName({ serverId, machineId }, { signal })` to label an
already-known Machine. Check `host.version().methods` for
`readMachineDisplayName` before calling an older host. Both native and hosted
surfaces use the same read contract.

The result is `{ status: 'ready', displayName }` or `{ status: 'unavailable' }`.
The name follows Happier's existing Machine display rules, including locked
and unnamed Machines. Unknown ids, revoked Machines, and a Home or Account
outside the mounted surface's currently active Account return unavailable.
This read uses the viewer's existing display projection; it does not load
another Home, enumerate Machines, or grant access to Machine metadata.
Read again when your surface needs a current label; this method installs no
subscription. Retired surfaces and cancelled requests retain the ordinary host
errors.

## UI capabilities in a client Action

In the 0.3 development contract, a client-targeted Action receives
`PluginClientActionContext` from `@happier-dev/plugin-sdk/actions`. Its bounded
`ui` capability is not a mounted surface: `ui.context({ signal })` returns only
`{ targetedContributions }`, where that value is the current contributions
targeted to the Action's plugin or `null`. It does not return a mount, surface,
page, selection, or layout context.

Use `ui.version()` to inspect the advertised methods and
`ui.selectActionInput(...)` when the person must choose an input. Selection
reuses the host's canonical input admission and custody; do not introduce a
parallel picker or copy private selection state. `ui.executeAction(...)` and
`ui.openSurface(...)` remain the ways to invoke an Action or open a declared
destination. This capability subset does not install a Plugin UI provider or
make a client Action a surface occurrence.

An advertised `ui.openNewSession(...)` uses the host's existing New Session
draft and navigation owner; it does not create a Session by itself. Automated
agent, MCP and CLI callers retain their real invocation surface. A client-target
Action needs an answering signed-in client with the exact current plugin
occurrence; without it, execution is unavailable. Approval follows the shared
Action settings, not an invented UI caller identity. These are unreleased 0.3
contracts: rebuild the Action artifact with the matching host and SDK.

## Open an editable authoring draft (development)

In current **0.3 development** source, `session.authoring.open` opens the
ordinary New Session composer in an answering signed-in Happier client. This
is a development contract, not released SDK availability. From an admitted
surface, use the public host Action:

```ts
import type { PluginUiHostApi } from '@happier-dev/plugin-sdk/ui';

export async function requestAuthoringDraft(host: PluginUiHostApi) {
  return host.executeAction('session.authoring.open', {
    seed: { prompt: 'Help me update this review integration.' },
  });
}
```

An `opened` result identifies the host-owned `draftId`, not a Session or a
writable copy of its document. The person can edit the prompt and ordinary
Agent, model, profile, placement and approval options before explicitly
pressing **Send**. Opening creates no Session, sends no message and runs no
setup command. A conversation finishing also does not make project setup
Ready; preparation has its own result and approvals.

Handle the typed result before continuing: `unavailable` with
`reason: 'client_unavailable'` means an answering client is needed. Invalid,
stale and other unavailable outcomes do not acknowledge an opened draft.
An approval-request result is pending, not `opened`. Do not fall back to
`session.spawn_new`, an automatic Send or your own router/clipboard bridge.
Agent, CLI and Voice callers retain their actual invocation authority and the
shared Action policy.

The existing mounted `host.openNewSession(seed)` method consumes the same
seed/draft owner and resolves without returning a draft. To suggest an exact
target, use the qualified machine and directory the person selected:

```ts
import type { PluginUiHostApi } from '@happier-dev/plugin-sdk/ui';

export async function openSelectedAuthoringTarget(
  host: PluginUiHostApi,
  target: Readonly<{ serverId: string; machineId: string; directory: string }>,
) {
  await host.openNewSession({
    prompt: 'Help me update this review integration.',
    placement: { kind: 'exactTarget', ...target },
  });
}
```

This is still an editable suggestion, not permission to execute there.
The host owns Account and mount currentness, attachment admission and navigation;
authors do not supply currentness flags or destination callbacks. See the
generated [host Action reference](/plugins/api/host-actions#sessionauthoringopen)
for the current input and outcome contracts.

## Approval for a direct UI write (development)

The unreleased 0.3 host API lets a direct Account write respect the same approval
settings as its contributed Action:

```ts
const confirmed = await hostApi.confirm('Remove this source?', {
  action: 'sources/administer-v1',
  signal,
});
if (!confirmed) return;
// Continue through the existing domain writer.
```

The host resolves the Action's current declaration and invoking-surface setting.
A waiver skips the dialog and returns `true`; Ask-first asks even for a safe
Action. Missing policy rejects before the write, and no daemon connection is
needed. Without `action`, `confirm` is an ordinary unconditional question.
This is a development contract change: rebuild Plugin UI artifacts using this
option with the matching 0.3 host, rather than expecting an older host to apply it.

## Publish mounted semantic context

The host automatically supplies a privacy-safe, parameter-free navigation
baseline. A mounted surface can optionally enrich that baseline with bounded
semantic data and contextual commands for the lifetime of that exact mount:

```tsx
import * as React from 'react';
import { usePluginHostApi } from '@happier-dev/plugin-ui';

function ReviewDetails() {
  const hostApi = usePluginHostApi();

  React.useEffect(() => {
    hostApi.publishCurrentUiContext({
      entity: {
        kind: 'review',
        label: 'PR #42',
        summary: 'Ready for review',
      },
      detail: { repository: 'example/widgets' },
      commands: [{
        title: 'Open changed files',
        command: {
          kind: 'openSurface',
          destination: 'review-files',
          input: { reviewNumber: 42 },
        },
      }],
    });

    return () => hostApi.publishCurrentUiContext(null);
  }, [hostApi]);

  return null;
}
```

`publishCurrentUiContext(enrichment)` atomically replaces this mount's prior
enrichment; passing `null` clears it. Unmount, parent or Account retirement,
and occurrence replacement also remove it synchronously. The value is strict,
bounded JSON data. It cannot contain a callback or become a second route,
selection, persistence, or navigation owner.

Commands reuse only the existing `executeAction | openSurface` semantic
command union. The host qualifies local references and exposes only an opaque,
snapshot-scoped command id to context readers. It retains the command payload
on the invoking client and resolves the id again against the current snapshot
before any effect. Plugins do not generate or persist those ids.
In 0.3 development source, an unchanged command keeps its address when the same
mount republishes context with an unchanged entity descriptor. Its title, description and
declared Action or surface payload must remain equal; changes to other context
details do not retire it. Removing the command or changing its meaning retires
the old address, as do mount, target and Account retirement. Always discover the
current address rather than saving it for a later mount.

This publication does not itself send data to a Voice provider. The active
Voice client's privacy mode decides whether current-UI data leaves that client,
and automatic mode sends navigation metadata only; semantic detail and
commands remain on demand. The source contract and external-plugin development
fixture exercise this same public Host API and mount-retirement contract.
Loaded development-stack parity remains the deciding live proof; package code
remains trusted executable code.

## Destinations and form factors

Declare the view's `container`, `target`, and `renderer` in
`definePlugin(...)`; the host registry decides whether that exact pair can be
mounted. The generated `appPage` + `app` view is the portable starting point.
In 0.3 development source, an `appPage` may also declare an optional `description`,
either a literal or `{ key, fallback }`, just like its title. The host resolves it
from the declaration for the identity header while the executable surface loads.
Use the same purpose in the loaded page's `PageHeader` so the content stays stable.
Omitting it remains valid; it is presentation metadata and grants no authority.
Published plugins use the existing toolchain-stamped `engines.happier` compatibility
contract when targeting hosts whose strict declaration parser predates a field;
the host does not strip unknown declaration fields or execute a bundle to infer them.

An `appPage` whose loaded page draws a Collection toolbar that leads with the page's name (instead of a page
header) declares `headerStyle: 'toolbar'`. The host then says the page's identity as that same toolbar row while
the surface loads, in the page's full content area with the table's rows, so nothing changes width or shape when the
surface arrives. On a phone the host draws that page's name as a large title above the toolbar,
as Happier's Inbox does, so the toolbar row leaves it out. Omit it for a page header (the default).

From an admitted surface, request another declared view through the one host
dispatcher rather than a local router:

```tsx
import { Button, usePluginHostApi } from '@happier-dev/plugin-ui';

function OpenDetails({ reviewId }: { reviewId: string }) {
  const hostApi = usePluginHostApi();

  return (
    <Button
      title="Open details"
      onPress={() => {
        void hostApi.openSurface('review-detail', { reviewId }, {
          subPath: `reviews/${reviewId}`,
        });
      }}
    />
  );
}
```

A `subPath` is only a location inside that plugin's `appPage`; non-page
destinations such as `rightSidebarTab` reject it. Do not construct host routes,
choose another plugin's namespace, or add a local fallback destination.

In unreleased 0.3 development builds, request a desktop window with
`hostApi.openSurface('review-detail', undefined, { presentation: 'window', subPath: 'recent' })`.
The matching host uses the same destination and window Action as the app. You can
also pass `presentation="window"` to plugin-ui's `Action.OpenSurface`. Omit the
option for ordinary placement. A host or destination without support rejects
with `unsupported_method`; it never silently changes the requested presentation.

Moving or reopening a surface restores its existing persisted state. Launch input
is one-shot, so a new window or relaunch uses the existing restoration fallback
rather than a copied input or component state. Dirty work that is not persisted
uses the host's existing Save/Discard/Keep guard. There is no checkpoint hook.

In the current development build, an app page can read
`useSurfaceContext().page?.columnVisible` to see whether its host-provided
navigation column is on screen. A page with its own list can show a selection
prompt beside a visible column and keep the list when the column is hidden,
including on a phone. The `page` fact is absent on other placements.

In the current development build, `useSurfaceContext().machineConnectionPending`
is true while the host establishes Machine-backed execution or loads the
mounted target, including a retained selection whose live Machine census is
still loading. Account/local work and surface activity remain independent. A Machine-bound host refusal
retains its original diagnostics and adds `plugin_surface_connection_pending`
while those prerequisites are pending. The same refusal after loading settles
is a failure, so do not classify it as pending from its error code alone.

Loading can finish before fresh execution admission returns. In the current
development build, `useSurfaceContext().machineExecutionReady` separately reports
that the exact mounted target is executable. Resource hooks handle these
transitions automatically. For a custom mounted read, consume the shared
`usePluginHostReadiness()` projection: defer the read and show loading while
`pending` is true. Do not acquire while `ready === false`, including a settled
outage with `pending === false`; keep the existing unavailable state and Retry.
Older hosts may omit `ready`, retaining their loading-only observation. Include
`pending`, `ready` and `revision` in the acquisition dependencies so
re-admission re-reads without a manual Retry. Retain the read's existing
cancellation, data and pacing owners. Account-local reads can pass `false` to
ignore unrelated Machine readiness, but must still wait while `ready === false`.
In the current development build, the same context publisher projects
`requesterExecutionReady`: reads wait for the mounted caller's admission and, for
an Account-owned destination, its exact Account origin. Choosing development
renderer bytes does not replace an existing Account destination's custody or
make an interim Machine requester ready. Genuine Machine-only or newly declared
development destinations do not need an unrelated Account origin. Account reads' revision does not change for Machine-only
readiness changes. This applies to custom reads on any surface, not just Settings.
An undemanded reader stays cold; a genuine
outage after readiness stays an error with Retry. These observations grant no
permission: every invocation still revalidates authority.

### Changing your own page's location

In **0.3 development source**, use `replacePageLocation` for your page's own
filters, order and selected detail. Filter and order changes replace the current
entry. Opening a detail whose `backLocation` is the current list adds one history entry; changing the
selection within that detail replaces it. Back returns to the list, and Forward
restores the detail. Render the location the host settles on.

```tsx
const settled = await hostApi.replacePageLocation(`reviews/${reviewId}`, {
  // Opening this detail preserves the current list in ordinary host history.
  backLocation: 'reviews',
});
```

A `backLocation` equal to the selected location declares no detail step.
`replacePageLocation` is advertised
only on a full-page destination; check `hostApi.version().methods` before relying
on it, and use the host API for page navigation.

### Protecting unsaved edits (development)

In **0.3 development source**, an `appPage` plugin can declare its mount's dirty
state with `await hostApi.setUnsavedChanges(isDirty)`. Check
`hostApi.version().methods` for `setUnsavedChanges`; it is unavailable outside a
page. Native and hosted surfaces share this contract. Publish `true` when edits
become unsaved and `false` after a successful save. The host stores only that
boolean, not the notes or a durable draft.

Back, page close, opening another page and a changed `replacePageLocation` use Happier's existing
**Keep editing / Discard** confirmation. Before changing a selected editor's
target, await the location replacement and render its returned `subPath`:
**Keep editing** returns the current location, so retain the current editor and
its text. Updating only `backLocation` at the same location needs no departure.
Browser tab/window unload uses the browser's own confirmation. Account or
credential retirement clears private state immediately without asking; this
declaration cannot prolong that authority or supply a navigation-blocking callback.

For a **React Native/RNW** editor that stays mounted while its layout expands
into a full page, pass `preserveUnsavedChanges: true` with `backLocation` to
`replacePageLocation`. The layout change and its history Back step then keep the
dirty fact armed; a later page close still asks. Use this only when the same
editor and its text continue, including through Back. Hosted document replacement
cannot retain that editor and refuses this option; use the ordinary guarded
replacement there.

The current registry admits every declared UI binding on web/desktop and
native tablet. On native phone, it admits only `appPage`/`app`,
`settingsPage`/`app`, App and Session `rightSidebarTab`,
`browserPanel`/`browser`, and `servicesPanel`/`services`; Project phone and the
other pane cells are intentionally unavailable. An emitted web, iOS, or Android
artifact does not widen that matrix. Treat these as source-level admission
rules—loaded mobile and tablet validation remains a separate host proof.

## Embedded Session widgets

> **Development preview:** Session Board placement is still being completed and
> validated across Happier's supported hosts. A self-hosted development server
> offers the Board by default unless its operator disables
> `HAPPIER_FEATURE_SESSIONS_BOARD__ENABLED`, and Happier
> exposes the Board only after the current Session System Records contract is
> active. Plugin declarations remain installed and recoverable while the Board
> is unavailable; availability does not grant Session access or Action authority.

A `widget` view with a Session target is embedded Session content, not a destination. Happier
frames it as one *widget* that a person can place on a Session Board and open
from Details, the compact sidebar, the Companion and the mobile Cockpit — all
through the same host. It never appears in navigation, collision domains, or
`openSurface`, and it takes no `instancePolicy`.

In current development source, a widget's App/Session target describes its
data context, not where it can be placed. Configured instances can be hosted
on Home, a personal Work Board, the Session Board, directly in the personal
Companion, or a declared native/declarative plugin-page area. A Session widget
declares typed inputs, an input schema and `sessionInputPath`; the host resolves
that field to an exact Home-qualified Session. Copies can follow the host
context or pin a different Session independently. Existing Companion references
to Board items still read shared Board content; a direct instance keeps its
own personal inputs. A definition is the reusable content/input declaration;
an instance is one configured copy, with order, size and frame belonging to
its host layout. Account-library definition edits affect their references;
Duplicate creates independent content. Setup/edit UI and loaded-platform validation are still
being completed in the widgets program.

### Start with one read, widget and page

The development [widget-area example](https://github.com/happier-dev/happier/tree/dev/packages/plugin-sdk/examples/widget-areas)
counts files or folders in a directory on the machine serving the plugin. Its
`directory` and `filter` inputs change the read itself, so two copies can show
different results. Use this example with the current 0.3 development checkout
and its [local authoring toolchain](/plugins/packaging/local-development);
these source contracts do not imply a published SDK or verified support on
every client.

The `count` Resource declares `scope: 'surface'`. Its producer receives the
host-resolved `context.launchInput`, reads the directory with `readdir`, and
returns `{ directory, filter, count }`. Its `observe` callback uses the
filesystem's watch notification to invalidate the same Resource. A filesystem
error remains a read failure; it is never reported as an empty directory.
There is no polling clock. Use an absolute directory path on the serving
machine; `.` means that process's working directory, rather than the browser's
or phone's filesystem. The example counts immediate regular files or folders,
without traversing subdirectories or following symbolic links.

The `counter` widget declares those two inputs, its `inputSchema`, and the
qualified `count` Resource dependency. Its `filter` field uses the plugin's
`count-kind` input type; the global `count-kinds` Resource supplies Files and
Folders through the shared options resolver. The native body uses
`useLivePluginResource('count')`, renders the returned number through `Metric`,
and offers `Action.Refresh` through that hook's `refresh`. Happier supplies the
widget frame and retains the Resource's ordinary loading, refresh and failure
lifetime. The body does not fetch data or arrange its own placements.

The `overview` app page declares a `pinned` area with the same readable context:

```tsx
<WidgetSurface area="pinned" context={{ directory, filter }} title="Pinned" />
```

Open **Widget areas**, enter a directory on the serving machine, choose **Use
directory**, and add
**Directory count** from its Add surface. Bind both inputs to **This page**, then
switch **Files** to **Folders** to see the count change. Add another copy with
its own pinned directory or filter; changing the page follows only the first
copy. Add a file in that directory and the live Resource invalidates; **Refresh
count** also re-reads it explicitly.

Buttons and agents use the same widget Actions. From the mounted native page,
the existing `widgetArea` host method supplies the page's identity and routes
this operation to `widgets.item.add`:

```ts
await host.widgetArea({
  area: 'pinned', context: { directory, filter },
  operation: {
    actionId: 'widgets.item.add',
    size: 'medium',
    instance: {
      v: 1, id: 'directory-count',
      definition: { kind: 'installed', surface: {
        pluginId: 'examples.widget-areas', localId: 'counter',
      } },
      bindings: {
        directory: { kind: 'context', slot: 'directory' },
        filter: { kind: 'context', slot: 'filter' },
      },
    },
  },
});
```

Inspect the acknowledged result before starting dependent operations: refusal
and approval-pending are different from a completed add. Outside that page,
ordinary `widgets.*` Actions take qualified host surface references; they do
not need a plugin-owned layout writer. Native and declarative areas use the
host's shared named-layout tabs. Page-local requests can include `layoutId` and
the ordinary `widgets.area.layout.*` operation; the host supplies the remaining
area identity. Selecting switches the answering mounted area, while
`widgets.item.list` reads a document without switching. A select without a
mounted owner returns typed unavailable. Continue with the generated
[widget Action reference](/plugins/api/host-actions#widgetsitemadd),
[Resource API](/plugins/api/sdk-entrypoints#one-resources-path-three-resource-workflows),
[native widget areas](/plugins/ui/react-native#personal-widget-areas-in-development)
and the advanced [presentation and environment tiers](/plugins/ui/react-native#host-api).

### Declare useful widget sizes

In the **0.3 development contract**, each widget View declares the sizes its
body supports and one default:

```ts
sizeDeclaration: {
  sizes: ['small', 'medium', 'wide'],
  defaultSize: 'medium',
},
```

Put this field on the `container: 'widget'` View in `definePlugin(...)`.
The declared set must be nonempty and contain no duplicates, and the default
must be one of those sizes. Account-library definitions declare the same
field. Size names express width and height intent rather than pixels; the host
maps that intent into the current surface's layout. Declare compositions that
your body can use meaningfully, such as a compact count and a richer summary.

Happier intersects the declaration with the current surface's supported sizes
and uses one canonical order for setup, Customize, menus and `[` / `]`
stepping. The declared default is used when admitted; otherwise the first
admitted size becomes the default. Discover the actual choices on each entry
returned by `widgets.catalog.list` as `presentation.sizes` and
`presentation.defaultSize`. Home, personal Work Boards, Session Board and
plugin areas support size intent; Project aside and Companion remain linear.
Phone reflow keeps the saved choice.

When more than one size is available, the existing setup step lets the person
choose and preview it even if all inputs are already bound. A fully bound
widget with zero or one size choice keeps the direct Add path. Missing or
ambiguous inputs use that same setup step.

Submit `size` with `widgets.item.add`, as in the example above, so placement
and presentation are one operation. Change an existing copy through
`widgets.item.size.set` with `{ ref, size }`; see the generated
[widget Action reference](/plugins/api/host-actions). On grid surfaces, native renderers receive
`RenderContext.widgetPresentation` with the actual `footprint`, a `size` when
that native rectangle matches a named intent, and optional measured `geometry`.
Existing custom Board width/height combinations retain their rectangle without
inventing a size name. Geometry arrives after the host measures the body.
Adapt content to that space while keeping the Resource's normal lifetime and
authority. The host retains the framed full view when a compact renderer is
absent. These are source authoring contracts, not published-SDK or
loaded-platform certification.

### Draw a widget body's rows

In current development source, `WidgetGlanceRow` is the row Happier's own
widgets draw inside a body: a mark, a name with an optional short `tag`, an
optional quiet `fact` beneath (`factTone="attention"` when it needs the person),
and one `trailing` element. With `tagSentence` the tag continues the name as one
sentence (`5 files not committed · 3 included`) that wraps instead of shortening it. Give it `onPress` when the row leads somewhere; leave
it out when the row carries its own control. `variant="fact"` draws a quiet
one-line statement instead of a named thing. `variant="state"` says what is (or
isn't) there, such as "No Environments in this Project": its title and fact wrap
to a second line instead of losing their end. `DiffStat` draws lines added and
removed (`+53 −5`) in the host's version-control inks and leaves out a side that
is zero; pass `locale` to format the counts in the language your surface renders.
Where only text fits (a `List.Item` `detail` or a metadata value),
`formatHappierDiffStat(added, removed, { locale })` returns the same two counts.

`ReviewSeverity` draws a review finding's severity the way Happier's own review
surfaces do: one colour role per severity (Blocker and High in the failure ink,
Medium in the caution ink, Low and Nit in two steps of quiet ink), with your
translated `label`. `presentation="badge"` draws it as a tinted chip among other
facts and `presentation="dot"` as the mark alone. A `Banner` with
`presentation="strip"` is the compact band across the top of a pane: its title
leads when a description finishes the sentence. A card `Banner` keeps its
`action` beside the text while it fits; pass `actionPlacement="below"` to keep
it under the text at every width (several buttons, or a notice whose text is a
list of `points`, which always sit above the action), and
`compactActionPlacement="full-width"` to draw it across the whole banner on a
narrow pane. The strip takes neither.

```tsx
import { DiffStat, WidgetGlanceRow } from '@happier-dev/plugin-ui';

<WidgetGlanceRow mark="change-open" title="fix/settings" tag="Here"
  fact="nl1 · agent working" trailing={<DiffStat added={48} removed={12} />}
  onPress={openCheckout} />
```

While the selected Session's detail is loading, a configured widget shows its
loading state without asking the person to select the Session again. After the
read settles, a missing or denied target shows the existing refusal; an
available target still needs its normal access and runtime admission. This is
the current 0.3 development behavior.

An installed widget also stays loading while its plugin projection is being
established. If the installed descriptor is missing after that settles, the
widget keeps any plugin-management action supplied by its host. Loading does
not offer that action.

```ts
{
  id: 'review-status-widget',
  container: 'widget',
  target: { kind: 'session' },
  sizeDeclaration: { sizes: ['small', 'medium', 'wide'], defaultSize: 'medium' },
  sessionInputPath: 'session',
  inputs: { fields: [{ path: 'session', title: 'Session', widget: 'json', required: true, optionsSourceId: 'sessions' }] },
  inputSchema: {
    type: 'object', additionalProperties: false, required: ['session'],
    properties: {
      session: {
        type: 'object', additionalProperties: false,
        required: ['serverId', 'sessionId'],
        properties: { serverId: { type: 'string', minLength: 1 }, sessionId: { type: 'string', minLength: 1 } },
      },
    },
  },
  renderer: 'review-native',
  fallbackRenderers: ['review-web'],
  title: 'Review status',
}
```

For instance Refresh in development source, a widget can declare `resources`
as qualified `{ pluginId, localId }` references to its own declared Resources.
These dependencies do not grant access. Refresh waits for their admitted reads
to settle, and mounts sharing the same Resource context update together;
unavailable declarations or contexts return a typed refusal.

Because it is embedded content rather than a destination, `widget` sits
outside the destination-binding matrix above: the registry declares it for every
supported UI platform, in `content` and `fill` presentations only. Whether a given
person can actually see it still depends on the selected target's access and
their client admitting your renderer. Session Board hosting additionally needs
the Board capability on that Session's Home.

What the host guarantees at every mount:

- `mount.kind` is `embedded`, `role` is `widget`, and `presentation` is
  `content` (a framed card whose host owns bounds and scrolling) or `fill` (the
  expanded host, where your surface owns its own content scroll). There is no
  compact or inline presentation: measured geometry, platform, theme, scale,
  safe area and active state already arrive through the surface context, so
  adapt to the space rather than to a Happier shell name.
- `target` is the currently admitted exact Session selected by the configured
  binding. That Session supplies access, policy and machine routing, even when
  the widget is hosted on Home or beside a different Session. Losing access
  suspends execution; it never borrows the visible Session's authority.
- The stored Board item keeps a distinct instance identity, your qualified
  contribution identity and closed input-binding intents. A plugin update keeps
  the widget in place: the
  host retires the old occurrence and remounts the new one against the same
  surface identity. Declared `fallbackRenderers` may switch renderer within that
  same surface; nothing switches surface, plugin, or machine.
- Each physical placement is its own mount with its own instance identity and
  lifetime. Inactive or offscreen hosts suspend execution through their existing
  activity and demand owners.

When the plugin is disabled, uninstalled, retired, or no longer declares the
surface, Happier keeps the widget's frame and title and shows a localized state
with the recovery the person can actually perform. It never deletes the item,
guesses a replacement surface, or rewrites its stored source.

Installed first-party and external plugins use this same contract with the same
capabilities under equivalent grants: there is no privileged built-in path. A
widget still consumes only its negotiated Host API subset, and each Action and
Resource keeps its ordinary admission and approval policy.

The Board records and organization are shared with everyone who can read the
Session. Which Board view is active and what each person keeps in their Companion
stay local to that viewer and device. Reading Board content requires current
Session transcript access; changing it requires Session-record edit access.
Actions do not bypass those checks or Happier's normal authentication,
confirmation, and approval policy.

Shared credentialed widgets bind to each viewer's existing qualified Connected
Account purpose selection for the declared Resource consumer. Missing
selection asks that viewer to connect; it never borrows the editor's connection.
There is no per-instance viewer override. Pinned Connected Account references
are allowed on personal surfaces only and must name one of the viewer's active
accounts permitted by the declared Resource. A personal pin does not require
a current purpose selection. Changing the existing purpose selection
can affect other viewer bindings using that same qualified purpose, rather than
changing only this copy's connection. Explicit **Post a
snapshot** instead publishes the exact approved fixed output, timestamp and
provenance through the normal Board writer, without live Resource references
or credential bindings. See [configured widgets](/sessions/session-board#configured-widgets-in-development)
for the content and audience distinction, and
[personal widget areas](/plugins/ui/react-native#personal-widget-areas-in-development)
for native and declarative plugin-page embedding. Hosted HTML pages use ordinary
widget Actions without embedding host areas. Project-aside integration separately awaits the
Project program's portable Source producer; an exact checkout is not that Source.

Do not confuse an installed plugin's `hostedHtml` renderer with HTML authored
directly into a Session visual. Installed first-party and external plugins are trusted
through the public SDK contract above. Caller-authored Session HTML has no plugin
identity or ambient plugin capability, and its smaller Host API ceiling is limited
to context, Resource reads and watches, Action execution, and notifications. Each
Resource and Action still applies its own admission and approval checks.

Current development source carries caller-authored Session HTML through the shared
frame implementation on web/Tauri, iOS, and Android. That is implementation
reachability, not a released support claim: loaded isolation and lifecycle proof
remains open for each advertised realm. When a current client cannot admit its
renderer, Happier preserves the item and shows a recoverable unavailable state
rather than deleting, retargeting, or rewriting it.

For authoring a transcript-first visual through the public Action contract and
bundle helpers, see [Session visual authoring](/plugins/ui/ui-artifacts#session-visual-authoring-in-development).
Pin and Unpin organize that same saved item; they do not create an installed
plugin or a second visual. [HTML network and approval](/sessions/permissions#agent-html-network-in-development)
describes the separate creation setting and per-request viewer admission.

## Linked Session state and permission answers

> **Development preview:** these host methods are in current development source. They
> are not part of a released Happier version yet.

A surface that links its own entries to Sessions can show what those Sessions are
doing, and it can let the person answer a Session that is waiting for permission.
It never opens the Session to do this. A typical case is an issue that an Agent is
fixing. Three mounted host methods provide this, and the `useSessionState` hook
wraps the first two:

In current development source, `useSessionState` and `useSessionStates` pause
reads and release watches when the host marks their surface inactive. They keep
the last ready snapshot, ignore late callbacks, and re-read when activity resumes.
Providers without a host activity fact keep their existing live behavior.

In 0.3 development source, title-only readers can skip transcript activity and
select just the title. Keep the selector stable across renders:

```tsx
const selectTitle = (session: SessionStateV1) => session.title;

function LinkedSessionTitle({ sessionId }: { sessionId: string }) {
  const read = useSessionState(sessionId, { includeActivity: false, select: selectTitle });
  return <Text value={read.state ?? 'Linked Session'} />;
}
```

Import `SessionStateV1` from `@happier-dev/plugin-sdk/ui`, and `Text` and
`useSessionState` from `@happier-dev/plugin-ui`. The same option works with
`useSessionStates` and the host's `readSession` and `watchSession` methods.
`includeActivity: false` omits `latestActivity` and transcript-only invalidations;
omitting it preserves full activity demand.

The hooks distinguish a successful `null` snapshot (`status: 'missing'`) from
a failed read (`status: 'unavailable'`). Keep a missing Session's relationship
visible, but do not offer Retry as though its activity read had failed.
For failed reads, `retryable: false` preserves an explicit non-retryable refusal.
Set readers expose `refresh()` for an explicit recovery attempt; they never
start a retry loop. A refused watch still allows a one-shot snapshot read.

`state.agent`, when present, contains the catalog's `agentId` and `displayName`,
not the Session title. Its optional `brand.pluginId` targets the public
`<BrandMark pluginId={state.agent.brand.pluginId} />` renderer. Keep generic
wording and marks when identity is absent; do not assume a default Agent. A
known Agent without a package reference still supplies its display name.
For Collection glyph badges, capture the optional brand first:

```tsx
import { BrandMark } from '@happier-dev/plugin-ui';

const brand = state.agent?.brand;
const glyphBadge = brand
  ? { mark: (pixelSize: number) => <BrandMark pluginId={brand.pluginId} pixelSize={pixelSize} externallyLabelled /> }
  : undefined;
```

Collection owns the compact slot
size; `BrandMark` shares the host's sizing renderer and leaves any visible name
at its normal text size.

| Host method | What it does |
|---|---|
| `readSession(sessionId)` | Returns the Session's current state, or `null` for confirmed absence or denied access. A failed hydration rejects with its error code and retryability; it does not imply that the Session is missing. |
| `watchSession(sessionId, listener)` | Subscribes to changes. It uses the same acknowledged-async setup and bounded `invalidated` signal as `watchResource`. After each `invalidated` event, re-read with `readSession`. An `error` event means the Session became unreachable. |
| `respondToSessionPermission({ sessionId, requestId, answer })` | Answers one pending permission request with `allowOnce`, `allowForSession` or `deny`. |

```tsx
import { Button, Text, usePluginHostApi, useSessionState } from '@happier-dev/plugin-ui';

function AgentStep({ sessionId }: { sessionId: string }) {
  const host = usePluginHostApi();
  const { status, state } = useSessionState(sessionId);
  if (status === 'missing') return <Text value="Linked Session unavailable" />;
  const request = state?.pendingPermissions[0];
  if (status !== 'ready' || !request) return null;
  // request.summary / request.command say what it wants to run;
  // state.workspace says where. Offer only request.answers.
  return request.answers.map((answer) => (
    <Button
      key={answer}
      title={answer}
      onPress={() => host.respondToSessionPermission({ sessionId, requestId: request.requestId, answer })}
    />
  ));
}
```

The host owns what these methods return, and the plugin never computes a
second copy:

- **Lifecycle, runtime and operational state** come from Happier's Session
  awareness projection. That is the same answer the Session list shows.
- **`workStatus`** carries the host's shared Work presentation: `bucket`, `tone`
  and localized `word`. Consume this projection for grouping and status
  treatment. Healthy work stays neutral; permission, attention and failure
  facts use the same treatment as Happier's Work surfaces. A lead Session with
  unfinished reports is not Finished, and an offline Session's prior completion
  does not make it currently Finished. Your surface can keep its own story copy
  while using the host's bucket and tone.
- **`pendingPermissions`** are the requests the Session's own permission prompt
  is showing right now. Each one carries the tool, a readable summary, the exact
  command for shell tools, and when it was asked.
- **`answers`** lists what this person may give. It is empty when their Session
  access does not include approving permissions. A standard edit or plan-exit
  tool offers no `allowForSession`, and an Agent with no known prompt protocol
  offers only `deny`.

A Session is reachable when this Account's client can already open it. That is
usually a Session linked to one of your entries, but no plugin-level list
decides it. A plugin cannot widen that scope, and a Session the Account cannot
reach reads as `null`.

`respondToSessionPermission` is not a second permission authority. The host
applies the answer through the same decision path as the Session's own
permission prompt, and records it as that person's answer. Only call it from a
user action in your surface, such as a button press. A request that is no longer
pending, a Session the Account cannot reach, and an answer not listed in
`answers` all resolve as `{ status: 'refused', reason }` without changing
anything. If the answer cannot be delivered, the call rejects with a typed host
error.

These are client host methods of a mounted surface. They are not daemon
Actions: a plugin's daemon code still cannot answer a permission request as the
person.

In 0.3 development, host Agent/MCP callers can separately use the existing
`session.permission.respond` Action. It requires approval by default; the user
can explicitly waive that approval in shared Action settings. Current-request,
offered-answer and access checks still apply. This does not expose the raw
Action to plugin daemon code or change the user-action requirement for the
mounted `respondToSessionPermission` method.

A Session publishes its review findings as Review comments. To read them for a
linked Session, call the `reviews.comments.list` host Action with that
`sessionId`, or use `useReviewCommentProposalsForEntry` for proposed comments
linked to one entry. This reader fetches one candidate page per linked Session;
render its optional `loadMore` callback as an explicit continuation (or retry
after `status: 'failed'`). A page can contain no matching proposals and still
offer continuation. Tests can install `readSession`, `watchSession` and
`respondToSessionPermission` handlers in `@happier-dev/plugin-sdk/testing`, and
emit a watch signal with `invalidateSession`.

## Source detail panels and fix pull requests

**0.3 development / Developer Preview:** PRs & Issues sources use
`@happier-dev/triage-protocol/v1`, alongside the public SDK and Plugin UI.
The feature package owns the descriptor, detail input and fix-link Action
contracts. It gives an author no direct access to Triage's Collections.

Declare the tabs per entry kind on your source descriptor:

```ts
import { TriageSourceDescriptorV1Schema } from '@happier-dev/triage-protocol/v1';

export const descriptor = TriageSourceDescriptorV1Schema.parse({
  v: 1, purpose: 'example-errors', displayName: 'Example errors',
  kinds: [{
    id: 'error', workflowSubject: 'errorIssue', displayName: 'Error',
    detailTabs: [
      { kind: 'shared', id: 'overview' },
      { kind: 'shared', id: 'activity' },
      {
        kind: 'source', id: 'stack-trace', title: 'Stack trace',
        titleKey: 'plugins.exampleErrors.ui.tab.stackTrace',
      },
      {
        kind: 'source', id: 'occurrences', title: 'Occurrences',
        // A row fact your snapshots already carry; Triage shows it beside the title.
        summaryFact: 'example-errors/events',
      },
    ],
    detailActions: true,
  }],
});
```

Triage draws the shared Overview, Activity, Files and Checks strip and appends
your declared source tabs. Declare a source tab's optional `titleKey` in your
plugin's translation bundles; the host projects the admitted source's strings
for the active locale, with English fallback, and `title` remains the fallback
when the key is missing. A tab's optional `summaryFact` names one of your row
facts; Triage reads it from the entry's own snapshot and shows its value beside
the title ("Checks 2 failing", "Occurrences 1.2K"). Counts use the reader's
locale (an approximate count keeps a `~`), a status keeps its tone, and an entry
whose snapshot lacks that fact shows no summary. Files and Checks taken from an
issue's linked fix PR use the fix PR source's declaration and facts. It mounts
your existing detail renderer with the
requested `panel`; `detailActions: true` requests the separate `actions` panel
in the detail header. Render only that panel, using your own source terminology
and Action handlers. Parse the input with `TriageDetailSurfaceInputV1Schema`.
When using `Tabs` internally, set its `value` to the requested panel and
`tabList="host"` to avoid drawing a second strip. Without `detailTabs`, the
source keeps its whole-detail body and receives no panel selector.

Panel changes update the same source detail instance. Keep occurrence selection
and settled evidence pages in that instance; do not key the renderer by panel or
put selection in a global cache. Declare retained internal panels through Tabs
and stop hidden-panel reads with their activity signal. Retiring or changing the
entry ends the source instance and its outstanding work.

The [Collection composition](/plugins/ui/react-native#a-collection-with-one-detail-body)
shows public imports for the detail container, `Step`, `Tabs` and
`HappierDisclosure`. Retained tab work uses `useTabPanelActivity().activeSignal`;
the source retains parsed panel state while Triage owns the enclosing frame.

An issue or error can link to a fixing PR from another source. Use the exact
qualified Action references rather than importing a Triage implementation:

```ts
import {
  TRIAGE_READ_FIX_PULL_REQUESTS_ACTION_REF_V1,
  TRIAGE_SET_FIX_PULL_REQUEST_ACTION_REF_V1,
  TriageReadFixPullRequestsResultV1Schema,
  TriageSetFixPullRequestResultV1Schema,
  type TriageEntryRefV1,
} from '@happier-dev/triage-protocol/v1';
import type { PluginUiHostApi } from '@happier-dev/plugin-sdk/ui';

export async function linkFixPullRequest(
  host: PluginUiHostApi,
  entryRef: TriageEntryRefV1,
  issueDisplay: { title: string; scopeLabel: string },
  pullRequest: { entryRef: TriageEntryRefV1; display: { title: string; scopeLabel: string } },
  signal?: AbortSignal,
) {
  const written = TriageSetFixPullRequestResultV1Schema.parse(await host.executeAction(
    TRIAGE_SET_FIX_PULL_REQUEST_ACTION_REF_V1,
    { v: 1, linked: true, entryRef, displayAtMark: issueDisplay,
      fixPullRequest: pullRequest.entryRef, displayAtLink: pullRequest.display },
    { signal },
  ));
  if (written.status !== 'linked') return { written };
  const resolved = TriageReadFixPullRequestsResultV1Schema.parse(await host.executeAction(
    TRIAGE_READ_FIX_PULL_REQUESTS_ACTION_REF_V1, { v: 1, entryRef }, { signal },
  ));
  return { written, resolved };
}
```

The read returns owner-ranked `candidates`, a `primary` PR or `null`, and an
`incomplete` flag when the Session-link page is partial. Candidates carry their
`user` and/or `session` origins and `open`, `merged`, `closed` or `unknown`
status. A currently declared non-PR kind cannot be a fix candidate or a new link;
the write rejects with `PluginError` code `triage_fix_pull_request_kind_invalid`.
An unavailable descriptor preserves an explicit choice with unknown status; a PR closed without merging
stays listed but is never primary. The enclosing Triage detail routes Files and
Checks through the primary PR's own source.

Unlink with the same write reference and `linked: false`, omitting
`displayAtLink`. The owner remembers that dismissal so a co-linked Session
does not immediately propose the PR again. Handle `conflict` by re-reading and
`full` by letting the person remove a choice; transport failure or cancellation
does not prove a write succeeded. A created PR becomes a Session-derived
candidate only after it is linked to that Session. Keep the writer, resolver
and storage private to Triage; callers submit intent and render the resolved read.

### Initial task status (development)

In **0.3 development source**, a task source can advertise the states its

import { TriageSourceDescriptorV1Schema } from '@happier-dev/triage-protocol/v1';

const descriptor = TriageSourceDescriptorV1Schema.parse({

## Accessibility, currentness, and offline behavior

Executable UI authors own the semantics inside their renderer while it is
interactive. Treat accessibility and environment support as part of the
renderer contract:

- use semantic controls with localized names, roles, state, reading order, and
  visible keyboard focus
- support keyboard operation, screen readers, Dynamic Type or 200% zoom,
  high contrast, RTL and expanded strings, and reduced motion
- keep touch targets at least 44×44 points on iOS and 48×48 dp on Android
- consume the semantic package's surface-context and accessibility hooks
  instead of guessing host settings or retaining a second host snapshot

The host owns process-local occurrence currentness and host API availability.
Authors must not cache a separate “current” occurrence or implement a
functional offline mode. Handle unavailable host operations and cancellation,
and let the existing render-context/host-API subscription update the
environment.

When the daemon disconnects, Happier may keep the last mounted renderer as a
visual, non-interactive snapshot. Its actions, focus, and host mutations are
blocked. Because arbitrary executable subtrees cannot safely expose controls
as read-only semantics, the host announces a localized static summary from the
surface's declared display metadata. Give every executable surface a meaningful
localized title, and keep the last rendered visual state understandable without
requiring an action. Reconnection revalidates the selected release and digest,
current occurrence, policy, and context; it does not create a second trust
prompt.

## Boundaries

- Declare surfaces with `defineUiSurfaceDefinition`. **Advanced:** the raw
  `ui.views` / `ui.renderers` pair — direct `id`, `container`, `target`,
  `renderer`, optional `fallbackRenderers`, `title`, `instancePolicy`, and
  `headerActions` — stays supported for a shared renderer, a fallback chain, or
  a custom artifact. It is not a second beginner path. The host projects either
  form into its own normalized binding.
- Use only public SDK paths. Do not import app, daemon, or protocol internals.
- For cross-plugin behavior, consume a maintained feature-owned operation
  protocol; it binds existing Actions and does not create a separate renderer
  or navigation path.
- Treat the whole installed package as the trust unit, including client code.
- Use `context.ui` from daemon invocations for host-owned prompts, notifications, status, widgets, title, and composer controls; it is separate from executable surface rendering.
