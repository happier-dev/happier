---
title: Settings and detail pages
description: Compose plugin settings and detail pages with the same anatomy as Happier's own settings.
---

A plugin page that configures something — a plugin's settings, an account it
connects, a list of things it manages — should look and behave like Happier's
own settings pages. `@happier-dev/plugin-ui/components` exposes the same page anatomy
Happier uses: the page header, sentence-case sections with their explanation
above the rows, one hairline sheet per section, rows divided by full-width
hairlines, the same controls and the same empty states. These components render
through the presentation owners Happier's own pages use, so geometry, type,
colour and the phone recomposition match without any local styling.

<Callout type="info">
  Developer Preview. These components are part of the private, unpublished
  `@happier-dev/plugin-ui` source contract; check the shipped
  `node_modules/@happier-dev/plugin-ui/API.md` for the exact exports.
</Callout>

## A complete page

```tsx
import * as React from 'react';
import { defineUiSurface } from '@happier-dev/plugin-ui';
import {
  BrandMark,
  EmptyState,
  Item,
  ItemGroup,
  PageHeader,
  ScrollArea,
  Select,
  SelectionTiles,
  Toggle,
} from '@happier-dev/plugin-ui/components';

function ReviewBotSettings() {
  const [reviewNew, setReviewNew] = React.useState(true);
  const [channel, setChannel] = React.useState<string>('session');
  const [depth, setDepth] = React.useState<string>('thorough');
  const [layout, setLayout] = React.useState<'compact' | 'detailed'>('detailed');

  return (
    <ScrollArea>
      <PageHeader
        title="Review bot"
        description="Reviews pull requests and posts its findings to your sessions."
        leading={<BrandMark size="medium" externallyLabelled />}
        meta={[{ key: 'version', text: 'v1.4.0' }]}
      />

      <ItemGroup title="Reviews" description="When the bot reviews, and how much it reads.">
        <Item
          title="Review new pull requests"
          subtitle="Start a review when a pull request opens."
          accessory={<Toggle label="Review new pull requests" value={reviewNew} onChange={setReviewNew} />}
          accessoryOutsidePressable
        />
        <Item
          title="Post findings to"
          accessory={(
            <Select
              presentation="field"
              label="Post findings to"
              value={channel}
              onChange={(next) => setChannel(next as string)}
              options={[
                { value: 'session', label: 'The linked session' },
                { value: 'comment', label: 'A pull request comment' },
              ]}
            />
          )}
          accessoryOutsidePressable
          accessoryWraps
          fieldAccessory
        />
        <Item
          title="Depth"
          accessory={(
            <Select
              presentation="segmented"
              label="Depth"
              value={depth}
              onChange={(next) => setDepth(next as string)}
              options={[
                { value: 'quick', label: 'Quick' },
                { value: 'thorough', label: 'Thorough' },
              ]}
            />
          )}
          accessoryOutsidePressable
          accessoryWraps
        />
      </ItemGroup>

      <ItemGroup title="Findings layout" description="How findings look in the session.">
        <SelectionTiles
          variant="visual"
          accessibilityLabel="Findings layout"
          value={layout}
          onChange={(next) => { if (next) setLayout(next); }}
          options={[
            { id: 'compact', title: 'Compact', preview: <CompactFindingPreview /> },
            { id: 'detailed', title: 'Detailed', preview: <DetailedFindingPreview /> },
          ]}
        />
      </ItemGroup>

      <ItemGroup title="History" description="The reviews the bot has posted.">
        <EmptyState layout="line" title="No reviews yet" />
      </ItemGroup>
    </ScrollArea>
  );
}

export const renderSurface = defineUiSurface(ReviewBotSettings);
```

`CompactFindingPreview` and `DetailedFindingPreview` stand for your own
components rendered at static props — show the real thing the option changes,
not a drawing of it.

## Project pages

In the 0.3 Developer Preview source contract, a plugin can add a full Project
destination with the existing `appPage` family. External plugins use the same
contract as bundled plugins. Raw `ui.views` declares:

```ts
{
  id: 'project-review',
  container: 'appPage',
  target: { kind: 'project' },
  title: 'Project review',
  description: 'Review the current Project.',
  renderer: 'review-native',
}
```

The SDK shorthand is `placement:'appPage', target:{kind:'project'}`. An omitted
target keeps the existing app-page meaning. Declare optional repository
applicability with the ordinary expression grammar, for example
`availability:{when:{fact:'project.repository.kind',operator:'equals',value:'github'}}`.
Missing repository facts stay unknown; omitting this condition makes the page
available to any accepted Project. A renderer or permission refusal keeps an
applicable destination visible with its normal unavailable state.

The render context's Project target supplies the logical `projectKey`, an
optional qualified `source`, accepted `checkout`, normalized `repository` and
observed named `branch`.
Read these supplied facts rather than probing the checkout. A page can render
before Run-on is selected and when the checkout Machine is offline. Operations
that need a Machine retain their ordinary execution selection and authority.
Project pages share the normal page metadata; app columns, app-rail placement
and personal widget areas stay app-target-only.

A page may declare two labelled counts over one dynamic JSON Resource:

```ts
counts: {
  resourceId: 'branch-counts',
  items: [
    { field: 'running', label: 'Running' },
    { field: 'failed', label: 'Failed' },
  ],
}
```

Declare that Resource through the normal public Resource contract. It returns
exactly `{running, failed}`, each a nonnegative integer or `null` for unknown;
malformed records make both values unknown. Labels can use normal localized
strings and never come from Resource output. The existing shared count owner
reads/watches without loading the page body; hiding the tab releases badge
demand. Do not turn the pair into a sum or a failed-first scalar.

The contextual Resource producer receives the same admitted target in
`options.context.target`: Project `repository` and `branch`, or Session
`repository`, `branch` and `headOid`. Unknown facts are omitted; detached state
does not invent a branch. A Session target matches the Resource context's
`sessionId`. Use these supplied facts rather than adding a CI-context Action,
SCM probe or page-only launch-input convention.

Use public `Collection` and `DetailsPane` for list/detail composition. The host
uses its existing Project details column on desktop and pushes details on a
phone. Put the shared `DetailsPaneOpenAsPageButton` in `DetailsPane.actions`:

```tsx
import { usePluginHostApi } from '@happier-dev/plugin-ui';
import { DetailsPaneOpenAsPageButton } from '@happier-dev/plugin-ui/components';

const host = usePluginHostApi();
const openAsPage = async () => {
  const settled = await host.replacePageLocation(fullPageSubPath, {
    backLocation: detailSubPath,
  });
  setSubPath(settled.subPath);
};
const detailActions = <DetailsPaneOpenAsPageButton onPress={openAsPage} />;
```

Here `fullPageSubPath`, `detailSubPath` and the list location come from your
plugin's validated local route grammar; `setSubPath` updates the existing
controlled page model. Return replaces the location with `detailSubPath` and
sets `backLocation` to the list. Render the settled result because a navigation
request can be refused. Keep filters, selection, scroll and Find above the
pane/page presentation so moving the same detail does not fetch it again.

The host generates qualified Project URLs, preserves Home/checkout context and
owns Back, reload and ephemeral launch input. Customize tabs uses one
device-local Project layout shared by desktop and phone; pin, reorder, overflow,
hide and reset do not change page authority. Hidden tabs remain addressable.
Only the selected presented page loads its body. The maintained
[public authoring example](/plugins/quickstart) demonstrates the source workflow;
check generated API/capability reports before targeting a published host.

### Project Overview widgets (development)

For an item in the Project Overview rather than a full destination, use
`placement:'widget', target:{kind:'project'}` in the SDK shorthand
(`container:'widget'` in raw `ui.views`). Declare `sizeDeclaration` with its
supported sizes and default size. External plugins use the same contract.

Repository applicability uses the same ordinary `availability.when`
expression as Project pages. The host supplies the admitted Project target;
do not reconstruct it from a widget input, launch input or URL. Existing
Overview widget placement and Add Actions own the instance. This does not
create a personal app `widgetAreas` surface or make a Project widget hostable
on Home or a Session board. These are development-source contracts, not a
released-host support claim.

## Page header

`PageHeader` takes the page's `title`, a one-sentence `description` of what the
page is for, an optional `leading` identity mark (a `BrandMark` or `Image`), a
`meta` line of distinguishing facts, and `actions` (at most one primary action
plus context controls).

The host owns the navigation around your page, and the header follows it:

- when the host's navigation already shows the title (a phone's native header),
  only the purpose line is drawn, so the title never appears twice;
- when the page was opened from another page, the host's back arrow is placed
  in the gutter beside the title, or on the title line when the pane is narrow;
- the header, and every section below it, sit in the host's content column.

Do not draw your own back control or page title.

## Sections and rows

Give an `ItemGroup` a sentence-case `title` and it becomes a page section: the
title and optional `description` sit above one hairline sheet, an optional
`action` (one compact button such as "Add") sits beside the title, and the rows
inside are divided by full-width hairlines. Explain the section in its
`description`; there are no footers under sections. `surface="none"` lays a
section's content on the page with the same insets and no sheet. An
`ItemGroup` without a title keeps its plain semantic role and draws nothing.

When the explanation names a command, flag or identifier, pass the sentence as
rich `description` content and set the code in `InlineCode`, the same chip
Happier's own Scripts and Session guidance draw. The prose stays yours to
localize; the code is never translated, and on the web the chip moves to the
next line as one unit instead of breaking. A string `description` or a
`descriptionKey` keeps the translated-text path.

```tsx
import { InlineCode, Item, ItemGroup } from '@happier-dev/plugin-ui';

<ItemGroup
  title="Agents"
  description={<>Run <InlineCode>happier</InlineCode> on that computer to add it.</>}
>
  <Item title="Claude" subtitle="Ready" />
</ItemGroup>;
```

Inside a section, `Item` takes the page row anatomy: title, one description line
(`subtitle`) and one control per row in `accessory`. Put an interactive control
beside, not inside, the row's own press target with `accessoryOutsidePressable`,
and mark a wide control (a field, a select, a segmented choice) with
`accessoryWraps`: the row measures itself and moves it beneath the label when
the row is too narrow for both, exactly like Happier's own rows. A switch stays
beside its label. Rows carry no decorative icons; identity marks are fine.

In the 0.3 development source contract, also set `fieldAccessory` on an `Item`
whose accessory is a `Select presentation="field"`. When the field fits beside
the label in a narrow desktop column, it keeps its content width; on a phone it
moves beneath the label and spans the row. Happier's app rows and plugin rows
consume the same shared row-field fit rule.

## Controls

In the Developer Preview source contract, use `Button variant="destructive"`
for a consequential operation after the surface's existing confirmation.
Menus can mark the same operation with `destructive: true`. Both use the
host's danger tone; the tone does not add confirmation or change the action.
An icon-only menu trigger keeps the same focus treatment as an `IconButton`.
Menu items may carry an `icon` and a separate `subtitle` to distinguish an
identity without packing its supporting text into the action label.

Choose the control from the decision, as Happier's own pages do:

| Decision | Control |
| --- | --- |
| On or off | `Toggle` |
| Two to four short options | `Select presentation="segmented"` |
| A longer or larger set | `Select presentation="field"` (a bordered field that opens a menu) |
| An option that changes what you see | `SelectionTiles variant="visual"` with a real preview per option |
| A name, number or address typed in place | `TextField presentation="field"` (with `onCommit` to save when focus leaves) |
| A local date and time (a lease's end, an expiry) | `LocalDateTimeField`: typed, or picked with the host's own picker where it has one; read the instant with `resolveHappierFutureLocalDateTime` from `@happier-dev/plugin-ui/components` |
| Several described choices to compare | `Select` (inline) or `SelectionTiles variant="card"` |
| A handful of operations | `SelectionTiles variant="action"` with `onPress` |
| Quiet items folded behind a count or summary | `CountedDisclosureItem` |

Action tiles run the chosen operation; they have no selected value. In a page
section they become rows in one sheet when their measured width is narrow.
Actions with a `renderOptionFooter` keep their cards so their status and
controls have room. A standalone action group keeps its tile presentation.

A setting typed in place keeps a local draft and saves once when focus leaves
the field or on submit — never on every keystroke:

```tsx
<Item
  title="Files per review"
  subtitle="Larger pull requests are reviewed in parts."
  accessory={(
    <TextField
      presentation="field"
      kind="integer"
      label="Files per review"
      value={String(limit)}
      onChange={() => undefined}
      onCommit={(draft) => saveLimit(Number(draft))}
      error={limitError}
    />
  )}
  accessoryOutsidePressable
  accessoryWraps
/>
```

`kind="integer"` or `"decimal"` keeps the draft to digits and opens a number
keyboard; an emptied number returns to the saved value unless `allowEmpty` is
set. Return a string from `onCommit` to show a corrected value (a clamped
number), and pass `error` to show a refusal beneath the field.

In the 0.3 development source contract, `SettingRow` is the same row Happier
draws for its own settings registries: a `title`, a `hint` under it, one
`control`, and a `layout` of `"inline"` (a switch or short value at the end),
`"adaptive"` (a segmented control or field that moves beneath the label when
the row is narrow) or `"stacked"` (a wide field always beneath). Put a typed
value in `SettingValueSlot kind="number" unit="ms"` (a compact box with its
unit) or `kind="text"` (the width the row leaves), and say what is stored, or
why a change was refused, with `SettingStatusLine` under a stacked control
(`tone="danger"` announces the refusal). Drafts, validation and saving stay in
your page; there is no second settings engine.

End a section with its buttons in `Form.Actions`: Save and Cancel, or the
quiet leave-and-destroy actions that close a page. Pass the irreversible one
as `trailing` to push it to the far edge, and a `footnote` for one line
beneath: the consequence of the destructive action, or (`footnoteTone="danger"`)
why it was refused, announced as it appears. Pending state stays with the
buttons.

To hand a link to a person (a pairing, connect or webhook link), use
`LinkDelivery`: the link in one line, its QR beside buttons that copy it through
the host's clipboard and, with `openable`, open it through the host. Pass
`qrActionLabel` to put the QR behind a toggle for a link people open on the
same device. It renders, never stores, the link you give it.

The switch, the field box and the segmented control are drawn by the same
visual owners as Happier's own controls. `presentation="menu"` remains the
compact toolbar pill that names the field and its choice.

For a collection of named things, public `Collection presentation="grid"`
owns its cards. Return `null` for an absent `anatomy.description` and omit
unused footer slots: rows of cards without descriptions, previews or footer
content become compact tiles. Cards in the same row keep equal heights;
one-column cards with descriptions follow their content. Do not copy the
card renderer into the plugin.

In 0.3 development source, public `CountedDisclosureItem` from
`@happier-dev/plugin-ui/components` folds quiet aggregate
details behind one row. Pass `title`, optional `count` and `subtitle`, and the
detail rows as children. Omit `count` for a word summary, rather than inventing
a numeric value. The shared owner retains the fold while the count changes;
the existing disclosure mounts details only when opened. Use public `List`
controlled expansion instead when expansion belongs to a particular collection
item. Check the package API inventory before using this new export with a
published toolchain.

In the same development source, `ItemAddRow` renders a sheet's add action
through the owner used by Happier's own pages: a leading plus, row title and
no chevron. Supply `title`, `onPress`, optional `subtitle` and `disabled`;
pass controlled `expanded` when it opens an inline form. The caller owns the
form, save/cancel actions and translated copy. Check the package API inventory
before using this new export with a published toolchain.

Authors import adapters, domain-neutral shared renderers and metrics from
`@happier-dev/plugin-ui/components`. Host services and mounted runtime controls
remain private to Happier.

## Empty states

`EmptyState` has three layouts:

- `layout="page"` for a whole page with nothing in it: an optional calm glyph
  (`icon`), a short title, one line of purpose, and one action. If the viewer
  cannot take that action, pass `actionUnavailableReason` to say why and who can.
- `layout="line"` for one quiet line inside a list, rail or section — including
  a search with no results.
- the default centred layout for a pane or card.

`LoadingState`, `EmptyState` (centred) and `ErrorState` take a `size` naming the
container they sit in — `"pane"` (a side pane), `"details"` (a details drawer),
`"page"` (an app page's content column) or `"phone"` — which sets the measure,
glyph and type exactly like Happier's own pane states. You rarely need to pass
it: a state with no `size` takes the size of the container Happier mounted your
surface in (a Session sidebar tab is a `"pane"`, a phone surface a `"phone"`).
An explicit `size` still wins.

`EmptyState` takes one `action` (the primary) and an optional `secondaryAction`:
a quiet second way forward under it, such as a plain `Button` that opens another
page. Never pass two primaries.

`variant="add"` frames the state with a dashed outline; use it only for an
invitation to add the first item.

## Loading, failure and recovery

`ErrorState` takes `onRetry` for the one recovery: a Retry button under the
copy (a link in a `line`), with the host's own "Retry" label unless you pass
`retryLabel`. A returned promise keeps it pending until the retry settles. Keep
diagnostic codes in `details`, behind a collapsed Details disclosure.

In the 0.3 development source contract, `SurfaceState` is the full state
composition Happier's own panes use, and `LoadingState` and `ErrorState` are it
with fewer parts. Give it a `kind` (`empty`, `loading`, `success`, `error`,
`warning`, `unavailable` or `denied`), a `title` and `description`, then only
what the state needs: `live` for the present ("Next try in 8 s"), a `body`
summary, one `action` and a quiet `secondaryAction`, a `note` or `learnMore`
link, and `details`. Reading order is fixed: copy, present, summary, actions,
note, details. `size="line"` draws one sentence with an inline recovery.

### Scenes (development)

In 0.3 development source, a centred or page `EmptyState` can draw a small
line-art scene in place of its glyph: a horizon, the Happier planet at a moment
of the day, a few props and some sky. Pass `scene` with a built-in scene id,
such as `noMatch`, `inboxZero`, `noProjects`, `firstRun`, `searchWaiting` or
`homeOffline`. `HAPPIER_SCENE_IDS` lists all of them.

```tsx
<EmptyState scene="noMatch" title="Nothing matches" description="Try fewer words." />
```

A scene appears only where the state has room for it. A `line` state stays text
only, and a host without a scene renderer keeps your `icon`. Happier draws every
scene: it sets the line colour and width, the planet, the size and the one-time
rise of the planet. A rising planet stays still when the viewer has asked for
reduced motion. The title and description still carry the meaning; the scene is
hidden from screen readers.

For your own state, define a scene once at module scope. A scene is a set of
choices, all optional:

- `horizon`: `sea`, `land`, `ridge`, `dock`, `desk`, `orbit`, `dunes`,
  `shore`, `field`, `city` or `none`.
- `moment`: where the planet stands and how it is lit: `predawn`, `rising`,
  `noon`, `golden`, `dusk`, `night` or `eclipse`.
- `planet`: the planet's state, `resting`, `rising`, `pulsing`, `waiting`,
  `paired`, `homes` or `failed`, or `false` for no planet. `planetAt` moves it.
- `props`: up to three props, placed with `x`, plus optional `ground`, `scale`
  and `flip`.
- `sky`: `stars`, `haze`, `comet`, `rain`, `birds` or `clouds`.
- `accent`: the one prop whose accent detail keeps its colour.

Start from a built-in scene with `base` and your props are added to it. A prop
is a built-in catalog prop (`HAPPIER_SCENE_PROP_IDS`) or your own, made with
`defineHappierSceneProp`. Its marks (paths, circles, rectangles and ellipses, in
the scene's `ink` or quieter `faint` line) are drawn around its anchor: the
bottom centre, standing on the ground. Coordinates are in one 160 × 64 scene
box. A mark with `accent: true` is the prop's one accent detail.

```tsx
import { defineHappierScene, defineHappierSceneProp, EmptyState } from '@happier-dev/plugin-ui';

const crate = defineHappierSceneProp({
  name: 'acme.crate',
  marks: [
    { shape: 'rect', x: -8, y: -12, width: 16, height: 12, radius: 2 },
    { shape: 'path', d: 'M-5 -8h10', tone: 'faint' },
  ],
});

const NO_DEPLOYS = defineHappierScene({
  name: 'acme.no-deploys',
  horizon: 'land',
  moment: 'noon',
  props: [{ prop: crate, x: 56 }, { prop: 'flag', x: 80 }],
});

<EmptyState scene={NO_DEPLOYS} title="No deploys yet" description="Deploys you start show up here." />;
```

Scenes shrink with their container. A page shows up to three props and two sky
marks, a pane two props and one sky mark, and a thumbnail one prop and no sky.
List the most important prop first. Your props are drawn in the scene's line;
they cannot set their own colour, width or motion.

## Stale content

When a surface still shows rows it read earlier but can no longer confirm them,
keep the rows at full strength and put one `FreshnessLine` above them. It says
when the rows were read (`asOf`), why they may be behind (`reason`), and offers
one recovery (`action`, for example Retry). Pass `busy` while a reconnect or
refresh is in flight and `tone="warning"` when a refresh failed. It is the same
line Happier's own panes draw. Never show it over an empty body: a surface with
nothing retained shows `LoadingState` or `ErrorState` instead. Pass
`icon="unavailable"` when the cause is that something can't be reached.

`LoadingState` draws its words as one quiet line under the spinner, never as a
heading. When you know the shape of what is coming, pass `rows` instead, so the
rows land in place.

In **unreleased 0.3 development source**, the public shared renderer
`HappierFreshnessLine` also offers `presentation="chip"` for a compact status
at the end of a header or tab bar. It sizes to its words without a filled strip;
an optional `lead` puts a quiet clause before the glyph. The default
`presentation="line"` keeps the full-width line under a surface's header.
`onSheet` removes that line's fill and borders when the surrounding sheet
already provides them. `lead` is used only by the chip.

Keep `FreshnessLine` for the usual retained-content case: it formats `asOf`
and supplies the glyph and recovery from domain facts. Its props do not expose
the chip presentation. Use `HappierFreshnessLine` from the public components
entry point when you need compact composition, supplying the status text, glyph
and recovery yourself. For example, inside a `defineUiSurface` component:

```tsx
import { Button, Icon, Text, usePluginTheme } from '@happier-dev/plugin-ui';
import { HappierFreshnessLine } from '@happier-dev/plugin-ui/components';

function RetainedStatus({ label, refresh }: { label: string; refresh(): void }) {
  const theme = usePluginTheme();
  return (
    <HappierFreshnessLine
      presentation="chip"
      colors={{ background: theme.colors.surface, border: theme.colors.border }}
      icon={<Icon name="refresh" />}
      lead={<Text value="Last known" />}
      action={<Button title="Retry" size="small" onPress={refresh} />}
    >
      <Text value={label} />
    </HappierFreshnessLine>
  );
}
```

Here `label` is the status your data owner already knows, such as “As of 10:42”.
Neither presentation decides when data becomes stale or starts a refresh on its
own. Check your installed API inventory before using these development exports.

## Installable things (development)

In **unreleased 0.3 development source**, a plugin that manages installable
things (extensions, servers, skills) can draw them with the same capability kit
Happier's Skills, MCP servers and Agents pages use. Import it from
`@happier-dev/plugin-ui/components`:

- `capabilityCollectionAnatomy` gives a `Collection` list its rows: the name, where
  it is on at the end of the title line, the description, then one facts line. A
  status that needs attention takes the facts line's place.
- `CapabilityFacts` draws source, trust and cost on one quiet line ("You · Runs
  scripts · 12 tools"). "Runs scripts" is the one fact drawn with more weight.
- `CapabilityStatusChip` shows a status only when it says something. A healthy
  status draws nothing. A stop or a blocked run keeps its pill short and gives
  the reason on its own line. `showFix` adds the status's one fix beside it.
- `CapabilityDetailHeader` is the detail page header: mark, name, purpose, the
  facts on the meta line, and the status when it speaks.
- `CapabilityBlockingBanner` leads a page only for a status that blocks (amber
  for needs-you, rose for a failure), with the fix as its action.
- `pickMostBlockingCapabilityStatus` picks the one status to show when an item has
  several (for example one per machine).
- `WhereItsOnControl` is the "Where it's on" section: the sentence ("On
  everywhere · except Gemini"), Everywhere On | Off, the rules and an add menu,
  and an optional line saying where it is available now. You pass where your item
  is on (`everywhere` and `rules`) and the places to offer; `onIntent` receives the
  person's choice (`everywhere`, `add`, `remove` or `narrow`), which you apply to
  your own rules. Return `{ ok: false, message }` to show that a change failed,
  with Try again.
- `CapabilityAddBody` is the body of an Add flow, for your own page or sheet: the
  ways to add as tabs, a searchable catalog list with each item's details beside
  it (pushed on a phone), the pinned footer with your install action, and an
  optional registry selector. The page or sheet around it and its header stay
  yours; `onLevelChange` tells you when to show a way back.

You supply the data and the fix handlers; the words come from Happier's
defaults or your translation bundle (`happier.plugin-ui.capability.*`).

```tsx
import {
  CapabilityBlockingBanner, CapabilityDetailHeader, pickMostBlockingCapabilityStatus,
  type CapabilityStatus,
} from '@happier-dev/plugin-ui/components';

function ExtensionHeader({ statuses }: { statuses: readonly CapabilityStatus[] }) {
  const status = pickMostBlockingCapabilityStatus(statuses, 'header');
  return <>
    <CapabilityDetailHeader
      testID="extension.header"
      title="Linear"
      purpose="Read and update the issues your team works on."
      facts={{ source: { kind: 'registry', label: 'Extension registry' }, trust: 'runs_scripts', cost: { toolCount: 12 } }}
      status={status}
    />
    {status ? <CapabilityBlockingBanner status={status} title="Linear is signed out"
      body="Sessions can’t use its tools until you sign in." /> : null}
  </>;
}
```

A status's fix is `{ kind: 'sign_in', onPress }` (also `reconnect`, `add_key`,
`how_to_fix`, `try_again`, `review_update`, `compare`, `turn_on`,
`grant_access`); the kind picks the button's words. Check your installed API
inventory before using these development exports.
