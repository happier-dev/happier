---
title: Agent runtime plugins
description: Add AI agents through manifest-declared agent contributions and executable agent runtimes.
---

An Agent runtime plugin adds one or more selectable AI Agents to Happier.
Native `AgentRuntime` supplies sessions and/or execution-runs plus only the
optional typed capabilities it declares. Auxiliary features such as External
Sessions remain separate contributions with host-owned lifecycles.

## Runtime layers

1. The manifest declares `contributes.agents[]` entries. The declaration key is `id`.
2. A declarative ACP entry (`runtime.kind: 'acp'`) stops there: the host owns
   construction, with no plugin factory, registration, or locator.
3. A custom entry (`runtime.kind: 'custom'`) supplies one factory through its
   `agents.<id>.factory` code-defined field; generated activation registers it.
4. A Session-capable custom entry also names a distinct exact factory leaf in
   `sessionRunnerFactory`; an execution-run-only entry must not.
5. The host resolves the chosen runtime, owns its lifecycle, and runs product
   bridges.

## Native Agent contribution

The code-defined declaration owns Agent identity, runtime kind, primary
facility, capabilities, optional provider-neutral CLI/install/auth facts, and
the matching *custom* runtime factory. Its generated activation binds that
factory. Declarative ACP has no plugin runtime leaf at all.

A custom session Agent that launches a declared system tool projects this cold
shape. Ordinary author modules express it with `definePlugin(...)`, rather than
hand-authoring the JSON:

```json
{
  "hostAccess": {
    "required": [{
      "id": "example-agent-process",
      "capability": "process",
      "reason": "Runs the declared Example Agent CLI.",
      "scope": {
        "executables": [{ "kind": "systemTool", "id": "example-agent-cli" }]
      }
    }],
    "optional": []
  },
  "contributes": {
    "agents": [{
      "id": "example",
      "title": "Example Agent",
      "runtime": { "kind": "custom" },
      "primary": "sessions",
      "capabilities": {
        "sessions": {
          "open": ["create", "resume"],
          "delivery": ["newTurn", "steer", "followUp"],
          "cancel": true,
          "configuration": true
        }
      },
      "cli": {
        "executable": {
          "binaryName": "example-agent",
          "sourcePreference": "system-first"
        },
        "install": {
          "managed": null,
          "manual": {
            "kind": "vendor_recipe",
            "recipes": {
              "darwin": [{
                "cmd": "example-installer",
                "args": ["install"]
              }],
              "linux": [{
                "cmd": "example-installer",
                "args": ["install"]
              }],
              "win32": [{
                "cmd": "example-installer.exe",
                "args": ["install"]
              }]
            }
          },
          "guideUrl": "https://example.com/install",
          "docsUrl": "https://example.com/docs"
        },
        "auth": {
          "support": "login_terminal",
          "probe": {
            "parser": "unknown",
            "backgroundChecks": "manual_only",
            "statusArgs": null
          },
          "loginLaunches": [{
            "kind": "primary",
            "args": ["login"]
          }]
        }
      }
    }],
    "systemTools": [{
      "id": "example-agent-cli",
      "title": "Example Agent CLI",
      "executableNames": ["example-agent"]
    }]
  }
}
```

The strict `cli` block is data for Happier's existing executable resolver,
setup UI, auth probe, and login action owners. It does not give plugin code a
raw installer, shell, credential store, or login-command registry:

- `executable` describes canonical binary names and source preference;
- `install` selects supported managed metadata or bounded per-platform manual
  recipes and documentation;
- `auth.probe` selects one host-owned parser and whether background checks are
  safe;
- `auth.loginLaunches` supplies arguments for the already resolved executable.

For a declarative ACP Agent, use
`runtime: { "kind": "acp", "transport": ... }` and declare a strict
`systemTool` or `managedDependency` executable reference for stdio. Do not add
a factory, registration, or locator. A custom runtime keeps
`runtime: { "kind": "custom" }`, implements behavior in its registered native
`AgentRuntime`, and uses `context.protocols.acp.open(...)` only when its own
leaf composes ACP.

Declare only capabilities the runtime actually implements. Unsupported
create/resume/fork, delivery, configuration, compaction, rollback, goal,
catalog, usage-recovery, terminal, or external-session behavior must remain
absent and fail closed through the host's typed unavailable path.

## What agent leaves own

Agent runtime leaves own agent-specific facts:

- agent CLI flags and environment encoding
- agent auth materialization quirks
- agent protocol clients
- agent permission-mode translation
- native transcript parsing
- native event mapping into strict `AgentSessionRuntimeEvent`
- Agent-specific protocol and correlation logic for declared capabilities

## What Happier host owns

The host owns:

- agent runtime resolution
- bounded runtime-context construction
- session and execution-run bridges
- prompt/pending queue lifecycle
- permission request lifecycle
- transcript and session state persistence
- runtime identity publication
- UI and status projection
- process supervision services

Agent leaves should not reimplement those host behaviors. Model-provider selection is a separate domain.
