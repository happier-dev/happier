title: Execution-runs
description: Implement bounded Agent execution through AgentExecutionRunRuntime.

An execution-run-only `AgentRuntime` registers an `executionRuns` factory for host-owned tasks that are not ordinary interactive sessions. `AgentRuntime` is an exclusive union — `sessions` or `executionRuns`, never both — so this factory is the whole registration for an execution-only Agent; a session-capable Agent instead registers a `sessions` factory and the host derives its finite Runs.

In 0.3 development source, declare
`capabilities.executionRuns.workspaceWrites: 'deny'` only when the native factory
enforces an admitted `request.configuration.workspaceWrites: 'deny'` ceiling.
The host delivers that ceiling in the existing Run open configuration. An
undeclared runtime refuses a Role requiring denial with
`role_policy_unenforceable`. Session-derived Runs consume the corresponding
`capabilities.sessions.workspaceWrites` declaration.

## Code-defined runtime binding

Unlike a Session Agent, an execution-run-only Agent needs no separate runner
leaf: the code-defined entry supplies the factory and generated activation
binds it, so one module can hold the whole runtime. It imports only public SDK
types and owns no process-global state:

```ts
import { definePlugin } from '@happier-dev/plugin-sdk';
import type {
  AgentExecutionRunEvent,
  AgentRuntimeFactory,
} from '@happier-dev/plugin-sdk/agents/runtime';

/** The events this leaf publishes, before the host stamps identity and ordering. */
type RunEventInput = AgentExecutionRunEvent extends infer Event
  ? Event extends AgentExecutionRunEvent
    ? Omit<Event, 'sequence' | 'runId' | 'emittedAtMs'>
    : never
  : never;

// Keep the declaration snippet executable. Replace the emit calls with the
// Agent's real bounded work; the lifecycle rules below stay the same.
const createExampleExecutionRunRuntime: AgentRuntimeFactory = () => ({
  executionRuns: {
    open(request) {
      const listeners = new Set<(event: AgentExecutionRunEvent) => void>();
      const history: AgentExecutionRunEvent[] = [];
      let sequence = 0;
      let terminal = false;
      const emit = (event: RunEventInput): void => {
        if (terminal) return;
        if (
          event.kind === 'run-complete'
          || event.kind === 'run-failed'
          || event.kind === 'run-cancelled'
        ) {
          terminal = true;
        }
        const published = Object.freeze({
          ...event,
          sequence: ++sequence,
          runId: request.runId,
          emittedAtMs: Date.now(),
        }) as AgentExecutionRunEvent;
        history.push(published);
        for (const listener of [...listeners]) listener(published);
      };

      emit({ kind: 'run-start' });
      emit({ kind: 'output-delta', channel: 'assistant', text: 'Working…' });
      emit({ kind: 'run-complete' });

      return {
        async send() {
          return {
            status: 'unsupported',
            diagnostic: {
              code: 'example_execution_run_input_unsupported',
              severity: 'error' as const,
              message: 'This bounded run accepts no further input.',
            },
          };
        },
        async stop() {
          return { status: 'notRunning' };
        },
        watch(listener) {
          // Subscribers receive every event already published before they
          // attach, so a Run that terminalizes before open() settles still
          // delivers its terminal fact.
          for (const event of history) listener(event);
          if (!terminal) listeners.add(listener);
          return {
            dispose: () => {
              listeners.delete(listener);
            },
          };
        },
        async dispose() {
          listeners.clear();
        },
      };
    },
  },
});

export const { manifest, activate } = definePlugin({
  id: 'com.example.runs',
  version: '0.1.0',
  entrypoints: { daemon: './dist/index.js' },
  agents: {
    example: {
      declaration: {
        title: 'Example execution runs',
        runtime: { kind: 'custom' },
        primary: 'executionRuns',
        capabilities: {
          executionRuns: {
            open: ['create'],
            checkpoint: false,
            stop: true,
          },
        },
      },
      factory: createExampleExecutionRunRuntime,
      // No `sessionRunnerFactory`: an execution-run-only Agent has no Session
      // runner leaf to locate, and the strict declaration rejects one.
    },
  },
});
```

`AgentExecutionRunRuntime` implements:

- `send(input, options?)`
- `stop(options?)`
- `watch(listener)` returning a `Disposable`
- `dispose()`

Events carry a monotonically increasing `sequence`, the `runId`, and one of the
public shapes: `run-start`, `run-progress`, `output-delta` (assistant or
reasoning text), `checkpoint`, and exactly one terminal `run-complete`,
`run-failed`, or `run-cancelled`. `watch` synchronously replays every event
already published before returning, and a terminal event is published exactly
once. Keep raw Agent protocol messages inside the adapter.

The host owns public run state, cancellation admission, status projection, and persistence. When sessions and execution-runs use the same Agent protocol, share the native adapter and parsing logic rather than maintaining competing protocol implementations.

For bounded work driven by one host input, `createFiniteExecutionRunHostRuntime`
is the public helper that owns event ordering, replay, cancellation settlement,
terminalization, and disposal; supply its `execute` callback and keep
provider-native details inside the Agent adapter.

In 0.3 development source, `createExecutionRunHostBackendFromConversationRuntime`
adapts an existing provider conversation through that same Run lifecycle. Its
optional `observeUsage` callback receives the original active-turn
`usage-observed` and `skill-usage` events. Usage from another turn, before an
active turn, or after settlement is ignored. The callback observes usage without
publishing a second Run event, and a callback failure cannot change the Run's
outcome. A generic event parameter preserves native event metadata:

```ts
import {
  createExecutionRunHostBackendFromConversationRuntime,
  type AgentExecutionRunConversationAdapterOptionsV1,
  type AgentExecutionRunConversationEventV1,
  type AgentExecutionRunConversationRuntimeV1,
  type AgentExecutionRunOpenRequest,
} from '@happier-dev/plugin-sdk/agents/runtime';

export function openConversationRun<Event extends AgentExecutionRunConversationEventV1>(
  request: Extract<AgentExecutionRunOpenRequest, { kind: 'create' | 'resume' }>,
  conversation: AgentExecutionRunConversationRuntimeV1<Event>,
  observeUsage?: AgentExecutionRunConversationAdapterOptionsV1<Event>['observeUsage'],
) {
  return createExecutionRunHostBackendFromConversationRuntime({
    request,
    openConversation: () => conversation,
    ...(observeUsage ? { observeUsage } : {}),
  });
}
```

The adapter forwards the initial input's `localInputId`, `resultContract`, and
`causalPermissionAuthority` to the conversation's `send` options, just as it does
for subsequent sends.

For a Session-capable Agent, register only `sessions`. The host automatically
derives a finite Run projection from the same Session factory and owns sequence
assignment, replay, terminalization, cancellation, and cleanup. The plugin owns
Session opening and its Agent-native event/checkpoint mapping; it does not
register a parallel execution-run lifecycle.

The optional detached `executionRunContextV1.openConversation` facet enables
retained multi-turn interaction. When a Session Agent exposes only the finite
`open` facet, the host uses it for completed-turn work such as fresh Workflow
Judge checks. Session `newTurn` support alone does not assert that the Agent
implements detached retained conversations. This selection applies equally to
bundled and installed Agent plugins in development source.

An execution-run-only custom Agent has no Session runner locator. Use the
explicit finite Run seam only for Agents whose work is inherently bounded and
does not have an interactive Session runtime.

## Turn results and Workflow completion (development source)

An input turn finishing is distinct from its retained Run finishing. For
Session-derived interactive Runs, the host correlates the exact accepted input
turn; completing that turn does not terminalize the Run. A bounded execution-only
runtime still publishes exactly one terminal Run event under the contract above.
See [retained interaction](/development/architecture/runtime/execution-runs#turn-completion-and-run-completion-differ)
for the host's admission and observation boundary.

Workflow Agent steps pass their frozen text, JSON, or decision result contract
to that host path. The shared result codec parses raw JSON text once, validates
already decoded values directly, and reports typed failures with schema paths.
Plugins supply native output and correlation evidence; they do not decide that
a Workflow invocation has committed its result or completed human review.

For host Actions that declare execution-run completion, the Workflow owner
retains the immediate response and launched Run identities, awaits their exact
terminal observations, and validates the declared terminal result. Losing the
invoke response leaves the outcome uncertain; observation recovery does not
invoke the Action again.

Qualified plugin Actions exposed to Agents can run as Workflow steps with
Machine or Account placement. For a Machine step, the execution Machine's
catalog selects the contribution and its schemas. For an Account step, the
Run starter's Account supplies the Action contract, connected sources and
approval policy. If that Action requires the invoking app, the step reports
that the app is unavailable. Use the canonical
[Action contribution contract](/plugins/api/actions-tools-commands) for invocation.

These are current 0.3 development contracts, not release or loaded-runtime
certification.

## Review profile options and evidence

In 0.3 development source, an `executionRunProfiles` declaration can provide
`optionsSchema`. Put this inside the profile passed to `definePlugin`:

```ts
optionsSchema: {
  type: 'object',
  additionalProperties: false,
  properties: {
    effort: {
      type: 'string',
      enum: ['fast', 'deep'],
      description: 'How thoroughly this engine inspects the selected subject.',
    },
  },
},
```

Declare closed objects throughout the schema. The selected profile validates
`intentInput.engines[agentId]` once before loading its prompt or starting work.
Omitted options are validated as an empty object; declare `required` fields when
the engine cannot run without them. Invalid options return
`execution_run_profile_options_invalid`; a profile without a schema rejects
nonempty options with `execution_run_profile_options_unsupported`. The plugin
owns option names and descriptions.

Add `optionsInputHints` beside `optionsSchema` to offer specific options in the
Review launcher's engine controls:

```ts
optionsInputHints: {
  fields: [{
    path: 'effort',
    title: 'Inspection depth',
    widget: 'select',
    options: [
      { value: 'fast', label: 'Fast' },
      { value: 'deep', label: 'Deep' },
    ],
  }],
},
```

This uses the shared static input-hint grammar, including localized titles and
choice labels. Only declared fields become controls; other schema properties
remain available to the engine without appearing in the form. Keep internal
configuration out of this declaration. The launcher writes the selected value
to that engine reviewer's `options`; `optionsSchema` remains the validation
contract.

In matching 0.3 development hosts, call `review.engines.list` with
`includeExecutionRunProfiles: true` to read the Machine launcher’s profile
descriptors in `executionRunProfiles`. Each descriptor includes the declared
`optionsSchema` and `optionsInputHints` when the plugin supplies them.

Findings can carry `extensions` keyed by your complete plugin ID, for example
`{ 'com.example.runs': { evidence: ['slice-1'] } }`. Values must be strict JSON;
unknown namespaces remain opaque content. Keep suggested fixes in the
ordinary `suggestion` and `patch` fields. Extensions never decide finding state
or authorize an operation. Existing findings can omit them.

These additions require matching development host and SDK readers. They do not
change the runtime ABI or promise support from earlier strict manifest readers.

## Review contextual presentation

In matching 0.3 development hosts, contribute a `reviewFinding` view to present
your namespace alongside the opened finding. A `reviewEngineOptions` view can
present the selected options alongside the ordinary profile fields. Both use
the existing renderer contract; this selected-options context is read-only:

```ts
ui: {
  views: [
    { id: 'evidence', container: 'reviewFinding', target: { kind: 'app' },
      renderer: 'review-renderer', title: 'Engine evidence' },
    { id: 'options', container: 'reviewEngineOptions', target: { kind: 'app' },
      renderer: 'review-renderer', title: 'Engine options' },
    { id: 'review-overview', container: 'appPage', target: { kind: 'app', context: 'review' },
      renderer: 'review-renderer', title: 'Engine Review' },
  ],
  renderers: [{ id: 'review-renderer', kind: 'declarative',
    root: { kind: 'text', text: 'Engine evidence is unavailable.' },
    documentSource: { kind: 'resource', resourceId: 'review-content' } }],
},
```

Register `review-content` as a surface-scoped dynamic Resource with the
declarative-document media type and `maxBytes: 512 * 1024`, returning a
[declarative document](/plugins/ui/ui-artifacts). Its `read({ context })` receives
`context.review`: `finding` carries `reviewId`, `commentId`, `namespace` and
`extension`; `engineOptions` carries `engineId`, `profileId` and `options`;
`page` carries `reviewId`. Other renderers receive the same value at
`context.surface.mount.review`. Only your own namespace is supplied to your
finding view. These inputs carry no access or decision authority; ordinary
Action buttons still use the host's Action executor.

The contextual page is offered inside an opened Review and retains that Review's
Artifact route. It uses ordinary plugin page-header Actions, local navigation,
Back and companion surfaces. A page companion receives the same Review identity
in `surface.mount.review` and `surface.openedFrom.review`, separately from launch input.
Unopened findings do
not activate their views, and missing contributions leave the core finding
and its decision controls usable. The bundled clawpatch engine uses one
Resource for these three presentations without a separate UI runtime.

## Per-start cost acknowledgement (development source)

For an optional per-start cost acknowledgement, name an existing boolean option
with `metadata.reviewCostConsentOption` on the profile:

```ts
metadata: { reviewCostConsentOption: 'acceptCost' },
optionsSchema: {
  type: 'object',
  additionalProperties: false,
  properties: {
    acceptCost: {
      type: 'boolean',
      title: 'Accept cost warning',
      description: 'Some review scopes can be expensive. Consent applies to this start only.',
    },
  },
},
```

In matching 0.3 development hosts, Review inventory exposes `costConsent` with
that option's `optionKey`, `title` and optional `description`. This declares
presentation, not whether consent is required. Your engine decides that once at
start before launching vendor work. The caller passes the chosen value through
`intentInput.engines[agentId][optionKey]` for this start only; never save it as a
preference or treat an unchecked option as a refusal for every scope.
