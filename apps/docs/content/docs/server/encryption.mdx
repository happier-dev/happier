title: Encryption & plaintext storage
description: Configure whether the server stores session content end-to-end encrypted or as plaintext.
---

Happier supports explicit **end-to-end encrypted (E2EE)** and **plaintext** storage
modes. In E2EE mode, clients encrypt content locally and the server stores ciphertext.
In plaintext mode, the live server can read the stored value.

For some self-hosted or enterprise deployments, you may want to **opt out of E2EE for storage** so the server can store session content as **plaintext** (for example to enable future server-side indexing/search).

This page explains the **server operator** configuration and what it means for **end users**.

## What changes when plaintext storage is enabled?

- **E2EE storage (default)**: the server cannot read session transcripts (it stores encrypted blobs).
- **Plaintext storage**: the server *can* read and process new session content stored in plaintext.

Important: plaintext storage is a **storage mode**, not an authentication mode.

- Authentication and authorization still apply to both modes.
- A genuine plaintext account can use a token-only credential with no recovery secret,
  Account machine key, Account content key, or fabricated substitute.
- Bearer-token, OAuth/OIDC, GitHub, or mTLS authentication can authorize a plain
  account without creating encryption material.
- Users can choose plaintext for new Sessions only when the server policy allows it.

:::caution Rollout status
Mode-aware storage and token-only credential contracts are being expanded before
activation. The complete genuine-keyless external-auth, UI, and daemon onboarding
flow remains activation-closed until all required account-data domains and composed
checks land. Do not enable a production keyless rollout merely because these
environment variables or `/v1/features` fields exist.
:::

## Storage policy (server-wide)

Configure one of three storage policies:

- `required_e2ee` (default): encrypted-only; plaintext writes are rejected.
- `optional`: encrypted or plaintext is allowed depending on account/session mode.
- `plaintext_only`: plaintext-only; encrypted writes are rejected.

Env var:

```bash
HAPPIER_FEATURE_ENCRYPTION__STORAGE_POLICY=required_e2ee|optional|plaintext_only
```

### Recommended configurations

Default E2EE server:

```bash
HAPPIER_FEATURE_ENCRYPTION__STORAGE_POLICY=required_e2ee
```

Allow plaintext storage (opt-in per account):

```bash
HAPPIER_FEATURE_ENCRYPTION__STORAGE_POLICY=optional
HAPPIER_FEATURE_ENCRYPTION__ALLOW_ACCOUNT_OPTOUT=1
```

Force plaintext-only (for “server-side features first” deployments):

```bash
HAPPIER_FEATURE_ENCRYPTION__STORAGE_POLICY=plaintext_only
```

## Account encryption mode (end-user toggle)

When the server policy is `optional` and account opt-out is enabled, the UI can expose an account-level toggle:

- `e2ee`: new sessions default to encrypted storage
- `plain`: new sessions default to plaintext storage

Env vars:

```bash
HAPPIER_FEATURE_ENCRYPTION__ALLOW_ACCOUNT_OPTOUT=0|1
HAPPIER_FEATURE_ENCRYPTION__DEFAULT_ACCOUNT_MODE=e2ee|plain
```

Notes:
- Switching account mode affects **new sessions** created after the change.
- Existing sessions are **not** migrated (no retroactive decrypt/re-encrypt).
- Switching account mode is an **atomic migration-backed transition** (clients call `POST /v1/account/encryption/migrate`).
- Existing account-scoped rows keep their persisted representation until that
  transition rewrites them. Missing E2EE material is `locked` or
  `migration_required`, never an empty/default value.

### Plaintext accounts and account-scoped data

For plaintext accounts to work across devices (including keyless login), clients must not assume “device-key ciphertext” for account-scoped blobs.

- Plaintext accounts use **settings v2** (`GET/POST /v2/account/settings`) and store settings as a plaintext envelope.
- The legacy settings route (`/v1/account/settings`) is **rejected for plaintext accounts** with `400 { error: "plain_account_requires_settings_v2" }`.

#### Plaintext at-rest sealing (recommended)

Plaintext accounts are server-readable by definition, but you can still reduce disk/backups exposure by sealing sensitive account-scoped blobs at rest using the server master secret.

Env vars:

```bash
# Defaults are server_sealed
HAPPIER_FEATURE_ENCRYPTION__PLAIN_ACCOUNT_SETTINGS_AT_REST=none|server_sealed
HAPPIER_FEATURE_ENCRYPTION__PLAIN_ACCOUNT_CREDENTIALS_AT_REST=none|server_sealed
HAPPIER_FEATURE_ENCRYPTION__PLAIN_ACCOUNT_ARTIFACTS_AT_REST=none|server_sealed
```

Notes:
- These affect **DB storage only**. Wire payloads remain plaintext envelopes for plaintext accounts.
- Connected Services v3 and plain Artifact storage keep canonical plain envelopes on
  the wire and seal their database representations when configured.
- `none` stores the canonical plaintext representation directly in the database.
- `server_sealed` uses server-owned material derived from `HANDY_MASTER_SECRET`. It
  reduces exposure of database files and backups that do not also contain that
  secret; it is not E2EE and does not protect against a compromised live server with
  access to both.

#### Backup, restore, and master-secret rotation

Back up the database and the exact matching `HANDY_MASTER_SECRET` as one recovery set.
For light flavor, also preserve the generated
`~/.happy/server-light/handy-master-secret.txt`. Restoring sealed database values with
a different or missing secret leaves them unavailable.

The current server has one active master-key tree and no built-in multi-key read or
automatic re-seal rotation procedure. Do not replace `HANDY_MASTER_SECRET` in place.
Keep the existing secret through a restore, or first implement and verify an
old-key-to-new-key re-seal migration covering every server-sealed domain. A direct
change can make settings, connected-service credentials, Artifacts, OAuth/service
tokens, and other master-secret-derived auth material unusable.

After restore, verify both:

1. an authorized read of representative server-sealed values; and
2. a canonical wire response containing `{ t: "plain", v: ... }`, not the internal
   `sealed_v1`/`server_sealed` persistence wrapper.

## Per-session encryption mode

Each session has a stable `encryptionMode` (`e2ee` or `plain`) chosen at creation time.

This prevents “mixed-mode” content inside one session and makes it predictable for clients (and for future server-side features).

Session metadata layout 1 is a separate privacy boundary. Its owner envelope is
currently E2EE-only, so fresh layout-1 writes remain closed for plain Sessions. A
future separately authorized Session/CPX vertical must add the plain owner
representation together with the real writer, reader, and recipient projection before
activation.

## Sharing behavior

- **Encrypted (E2EE) sessions**: sharing requires distributing a session data key to recipients (still E2EE).
- **Plaintext sessions**: sharing is purely server-side authorization (no encrypted data key is needed).

Public share links also work for plaintext sessions (the server returns plaintext envelopes).

## Client compatibility

- Older clients that only support encrypted writes continue to work when:
  - policy is `required_e2ee`, or
  - policy is `optional` and they create encrypted sessions.
- Under `plaintext_only`, older clients will fail because encrypted writes are rejected.
- A token-only client that encounters retained E2EE data must show it as locked or
  migration-required and preserve it. It must not silently show an empty Session,
  setting, Todo list, Artifact, Automation, or Machine value.

## Where clients learn the policy

Clients use `GET /v1/features`:
- gates: `features.encryption.plaintextStorage.enabled`, `features.encryption.accountOptOut.enabled`
- details: `capabilities.encryption.storagePolicy`, `capabilities.encryption.defaultAccountMode`

## Security checklist (plaintext mode)

If you store plaintext session content on the server, treat it as sensitive application data:

- Enforce HTTPS/TLS end-to-end (including between proxies and the server).
- Encrypt disks and backups at rest.
- Restrict database access and enable audit logging where possible.
- Define retention and deletion policies appropriate for your org.
- Exercise backup restore with the matching master secret; do not count a database-only
  restore as complete when `server_sealed` is enabled.
- Keep the existing master secret until a verified domain-complete re-seal migration is
  available.
