The question worth asking before you trust anything with your code is: **what
can whoever runs the server actually read?**

The honest answer depends on one setting. On a hosted relay, and on any
self-hosted server left at its defaults, the answer is "not your conversations".
That is not a property of the product in the abstract — it is a property of the
storage policy the server is running.

## End-to-end encryption, and what it is conditioned on

Messages and sensitive session payloads are encrypted on your device before they
are sent. The server stores ciphertext and the sync metadata it needs to route
it, and cannot read the content.

That holds under `required_e2ee`, which is the default
(`HAPPIER_FEATURE_ENCRYPTION__STORAGE_POLICY`). A self-hosted operator can
choose otherwise:

| Storage policy | What the server stores | Who can read it |
| --- | --- | --- |
| `required_e2ee` *(default)* | Ciphertext only | Only your devices |
| `optional` | Ciphertext, or plaintext for accounts and sessions in plain mode | Whoever runs the server, for anything stored in plain mode |
| `plaintext_only` | Plaintext session content | Whoever runs the server |

Plaintext mode is not a loophole — it is a deliberate option for deployments
that need server-side search, keyless logins, or enterprise identity through
[mTLS](/self-hosting/auth-mtls). It is a real trade-off, and it should be a
decision someone makes on purpose.

<Callout>
  The two settings are wired together and fail closed. Keyless account
  auto-provisioning — the thing mTLS login depends on — is refused outright while
  the storage policy is `required_e2ee`. You cannot have enterprise keyless
  identity *and* mandatory end-to-end encryption; the server will not pretend
  otherwise.
</Callout>

If you use a hosted relay, this is settled for you: content is end-to-end
encrypted. If you use somebody else's server, the guarantee is theirs to make.

## What the server can see

Under the default policy:

- Account identifiers and the metadata needed to route sync.
- Encrypted blobs — ciphertext it cannot open.
- Operational metadata: timestamps, sizes, session and message ordering.
- The device push token needed to deliver notifications.
- Identity records and any stored OAuth or refresh tokens for connected
  services, plus certificate identities where mTLS is in use.
- Not your account settings. Under the default policy your account is
  end-to-end encrypted, so its settings — including the API keys you store as
  **Saved Secrets** — are encrypted on your device before they sync, and the
  server holds ciphertext it cannot open.

Under `optional` or `plaintext_only`, add session content itself to that list
for anything stored in plain mode.

## Where your API keys actually live

An API key you save in Happier is stored as a **Saved Secret** in your account
settings. That is account data, not machine-local data: it syncs to your other
signed-in devices. What the server can do with it follows the account's
encryption mode.

- On an **E2EE account**, the value is encrypted on your device with key
  material only your devices hold. The server stores ciphertext.
- On a **plaintext account**, the value is sent and stored in a form the live
  server can read. That is intentional for plaintext accounts — they have no
  account encryption material by design — and the value is protected by
  authentication, authorization and TLS rather than by encryption the operator
  cannot undo.

Server-side at-rest sealing (`server_sealed`, the default for plain accounts;
see [Encryption and plaintext storage](/self-hosting/encryption)) applies only
to that second case. It reduces exposure of database files and backups, but an
operator holding the master secret can open those values, and the live server
opens them for authorized use. It is not end-to-end encryption, and it is never
what protects an E2EE account's secrets.

Connected-service credentials work differently again: the server performs the
OAuth exchange and returns a bundle sealed to your client key, and your client
or daemon opens it locally at the point of use.

If you would rather not store a provider key as account data at all, put it in a
machine environment variable on the execution machine instead.

## API tokens and Action API traffic

In the current Developer Preview source, API Tokens are server-side credentials:
the server retains a digest-backed record, while the full token is shown only to
its creator. They authenticate automation, not a present user, so they cannot
approve requests or loosen the security controls that limit them.

The **API** setting starts **Allowed** for API-eligible Actions, so Action
Settings do not add an approval prompt by default. Before sharing a token, open
each needed Action under **Settings → Actions**, then review **Integrations →
API** and change it to **Ask first** or **Off** where appropriate. A non-safe
contributed Action can still require its own live current-intent confirmation;
**Allowed** does not suppress that independent safety contract. These settings
do not expose host-internal Actions or override present-user-only controls such
as API-token administration, plugin uninstall, Agent session-hook changes,
approval decisions, and security-policy changes. Trusted plugins have the same
account-automation authority ceiling.

The Developer Preview Action API is a separate transport boundary. A configured
server can read a request and response when it mediates that traffic, even when
the daemon remains the Action executor. Current development source implements
that server relay through the daemon's existing server connection, so the daemon
does not need an inbound public address. Neither origin is published or shipped,
and the server origin is not live-proven; use daemon-local transport when direct
local delivery is required.

See [API Tokens](/security/api-tokens) for creation, revocation, and the
daemon-local validation-cache limit.
