Give a script or developer tool account-automation access that you can revoke
separately from your signed-in sessions.

<Callout>
  **Developer Preview:** this guide describes the API Tokens flow in Happier's
  development source. It is not a released or publicly available feature yet.
  Run the CLI examples with `hdev`, unless you have explicitly pointed the
  `happier` shim at the development lane with
  `happier self release-channel use dev`.

  Ordinary and encryption-capable issuance, wrapping, and protected-call owners
  exist in source, with the create → protected invoke → revoke journey covered by
  automated tests on both the direct-daemon and Home-relay origins.
</Callout>

## What you need first

- A development build that includes this preview.
- A signed-in account. Creating or revoking root tokens requires a present user;
  parent tokens can manage only their own children as described below.

## Create a token

1. Open **Settings → Account → Sign-in & security → API tokens**.
2. Choose **Create token**, give it a label you will recognize, and select its
   expiry (30 days, 90 days, one year, or no expiry).
   On an E2EE account, you can also enable **Encryption access** from a trusted
   signed-in device. Happier verifies the current Account content key before it
   creates the token; it never exports your recovery or signing key.
3. Copy the token when it is shown and store it in your secret manager or the
   environment of the tool that needs it.

Happier shows the full secret once. The list keeps only a shortened, non-secret
prefix such as `hap_v1_2c67deea…` plus metadata, so it cannot reveal the same
secret later. Choose full access or a limited grant covering the Actions,
sessions and computers it needs. A limited grant can also restrict models,
permission modes and websites. Content access is a separate choice.

Approvals are opt-in per token. Enabling them lets it decide tool-use prompts
and requests in its granted targets, including requests it started itself.
It cannot change root tokens, security or plugin trust. A token answering an Agent's
question needs conversational Send access; that is separate from approving a
tool or Action.

An encryption-capable credential begins with `hapc_v1`. In the development SDK,
the extra local material protects the complete Action request and result from the
configured Home while it relays them. Only the embedded bearer is sent for authentication.
Keep the complete compound credential in your secret manager: it grants access
to Account-encrypted content, and revocation cannot make already opened keys or
data unknown again.

## Use a token from the CLI

Pass a token for one command with the global, prefix-only `--api-token` flag:

```bash
hdev --api-token 'hap_v1_…' list
```

For automation, set `HAPPIER_TOKEN` instead:

```bash
HAPPIER_TOKEN='hap_v1_…' hdev list
```

The flag takes precedence over `HAPPIER_TOKEN`. Neither form saves the token in
your CLI profile; use your normal secret-management mechanism to provide it.

The normal CLI can use an ordinary `hap_v1` token across its one-shot tmux
continuation. It refuses a compound `hapc_v1` credential before starting a child
process, so the local wrapping secret is never copied into a child environment.
Use `hapc_v1` with the in-process Happier SDK instead.

## Choose what automation and plugins may do

In **Settings → Actions**, open an Action and find its **External API & SDK**
and **Trusted plugins** entries under **Integrations**. Set each independently
to:

- **Allowed** — the Action can run from that integration without an approval
  prompt.
- **Ask first** — a present user must approve the Action before it runs.
- **Off** — the integration cannot invoke the Action.

Every API-eligible Action starts **Allowed**, so API Token calls run without an
approval prompt unless you change that Action's **External API & SDK** setting
to **Ask first** or **Off**. The **Trusted plugins** setting also starts
**Allowed** for Actions available on that surface. Review these defaults before
handing a token to automation. They never override an Action's required
authority, runtime availability, or placement, and host-internal Actions are
not exposed at all.

<Callout type="warn">
  Full access covers API-eligible built-in and contributed Actions allowed by your
  Action settings; approval authority remains opt-in. Before sharing a token,
  choose the grant it needs and review
  **Ask first** or **Off** for Actions that need additional controls.
</Callout>

Limited grants require the exact qualified ids of contributed Actions.
**Full access** also grants contributed invocation, subject to Action settings
and plugin grants.

An API Token invoking an Action follows the **External API & SDK** setting. An installed trusted
plugin follows the **Trusted plugins** setting. Start with the smallest set of
Actions your automation needs.

An API token cannot create, revoke, or replace root API tokens; sign out every
device; change Action, API, or security policy; install or
uninstall plugins; change Agent session-hook installations; or make other
present-user security and trust decisions. Those operations remain discoverable
where applicable but return `present_user_required` instead of treating a
bearer token as an interactive user. Trusted plugins have the same
`account_automation` ceiling: their **Trusted plugins** setting cannot turn one
of these controls into a present-user operation.

## Credentials for an embedded app

Keep the parent API token on your backend. Use the SDK's
`client.apiTokens.createChild({ label, expiresAt, grant })` against the Home
origin to issue a browser credential with only the session and website access
that page needs. The child expiry is required, must be in the future and cannot
exceed the parent's expiry. There is no fixed maximum lifetime.

A child can only narrow its parent's grant. It has no Account content-access
material, cannot create another child and cannot manage root tokens. Use
`client.apiTokens.self()` to inspect its non-secret grant, expiry and parent;
`client.apiTokens.revokeChild(tokenId)` revokes a child owned by that parent.
These operations are Home routes and return `unsupported_endpoint` through a
daemon-local SDK endpoint.

Browser calls need an origin allowed by the grant. Happier's own app origin is
also admitted so its embedded session view can connect. API-token sockets are
bound to one session, and the same grant controls HTTP, messages and session
RPCs. The daemon's loopback endpoint does not enable browser CORS.

Revoking the parent revokes its children. Editing its grant also revokes active
children and disconnects their sockets; mint new children for the updated
access. A label or appearance-only edit keeps their credentials valid.

Narrowing a token's grant also invalidates pending Action approvals authorized
under the old grant, even when the change only removes an unrelated website.
The whole original grant must still fit within the current grant before a
deferred Action can execute. Effects already admitted are not cancelled.

Model defaults come from the first allowed model for the session's Agent, not
another Agent's model. Permission-mode defaults use the grant's order and keep
an already allowed selection.

## CLI and daemon approvals

In 0.3 development, an Agent or MCP call can ask you to create, edit or revoke an
API token (including an embed configuration), or change CLI/daemon approval policy.
These calls always create an Ask-first request; they never apply automatically.
Approving any present-user change requires your signed-in present-user authority.
An Approve-scoped token can reject the request, but cannot approve its own or another
agent's security change. Direct token/security mutations from an API token stay refused.
Agents can read non-secret token summaries and Account security state normally.
When you approve token creation, the deciding app shows the new bearer once in
the existing token reveal dialog; approval history never stores it. Requester-owned
encryption wrapping material is not reconstructed on your device.

CLI and daemon approvals and account changes are allowed by default for a
stored interactive login. Read or change the Account choice with:

```bash
hdev auth cli-approvals get --json
hdev auth cli-approvals set disallowed --yes --json
```

Changing the policy briefly reconnects the Account's CLI/daemon sockets. Set
`HAPPIER_CLI_PRESENT_USER=disallowed` on a computer to opt out independently;
an Account `allowed` value cannot override that machine choice. With the
policy disallowed, restore it from the signed-in app, which retains
present-user authority.

The environment accepts only `allowed` or `disallowed`; leaving it unset uses
the Account choice. An invalid value refuses CLI/daemon startup rather than
silently restoring approval authority.

During this development migration, the CLI may ask you to sign in again when
its stored bearer is an app Account credential rather than a terminal
credential. It clears only that Home's bearer, preserving local Account
material and your other Home profiles.

This prevents supported automation paths from raising their own authority.
A process running as your OS user can still read local credentials; when
CLI/daemon approvals are allowed, a local process able to run the CLI or reach
the daemon control route can approve.

## Revoke access

Use the token's overflow menu to revoke one token, or **Revoke all API tokens**
when you need to remove every automation credential. Revocation takes effect on
the server's next verification.

**Sign out everywhere** is different: it invalidates signed sessions but leaves
API tokens active. Revoke the token separately if the automation credential may
be exposed.

The daemon-local Action API has a bounded positive validation cache. After a
token is revoked, a daemon that already validated it can accept it for up to
60 seconds; it never extends that cached authorization while the server cannot
be reached. Once the cache expires, an unreachable server produces HTTP `503`
with `auth_unavailable` rather than extending access offline.

## Keep the boundary clear

Only API Tokens authenticate public Action API routes. A signed-in session
bearer and the daemon's private control token are not substitutes for one.
Always send a token in the `Authorization` header, never in a URL.
Both public ingress routes verify the bearer before their JSON parser accepts a
request body.

The Action API's server-mediated transport is intentionally readable by the
configured server while it forwards the request to the exact connected daemon.
That relay works without an inbound public daemon address. Choose the
daemon-local transport when direct local delivery is required. Both origins are
available in the current Developer Preview source.

## When it goes wrong

- If you did not save the secret, revoke that token and create another one; it
  cannot be revealed again.
- If encrypted creation reports that Account material is unavailable or stale,
  restore the selected Home's current E2EE material on this device, then retry.
  Happier does not silently create an ordinary token instead.
- If encryption-capable creation loses its final acknowledgement or returns an
  inconsistent token identifier, Happier reveals no credential and does not
  create again automatically. It checks the complete token list for the exact
  identifier chosen before the request. If that row exists, inspect or revoke
  only that row. If a successful refresh shows it is absent—including after
  another client revoked it—the recovery state clears and you can deliberately
  create a replacement.
- If an operation returns `present_user_required`, complete it from the app
  while signed in rather than widening the token's authority.
- `credential_scope_denied` means the Action or target is outside the grant;
  `credential_origin_denied` means the browser website is outside its origin
  allowlist. Correct the parent grant and issue a new child when needed.
- `model_not_granted` or `permission_mode_not_granted` means the effective model
  or mode is outside the grant, including an automatic/default model when the
  grant names specific models. Select an allowed value.
- If **External API & SDK** is **Off**, or is **Ask first** without a completed
  approval, adjust the Action setting or complete the approval from the app.
- At either HTTP origin, a malformed, expired, unknown, or revoked API Token
  receives the same opaque HTTP `401` `invalid_token` response. Create a
  replacement only when you actually need a new credential; a lost token
  cannot be recovered.
- If a just-revoked token still works through a local daemon, wait up to one
  minute for its positive validation cache to expire. A server-origin request
  is checked on its next verification.
- If a daemon-local request returns HTTP `503` `auth_unavailable` after that
  minute, restore the daemon's connection to its configured server and retry.
  Treat it as an unavailable verification service, not proof that the token is
  invalid.
