This page documents how Happier integrates with **OpenCode** and what matters for day-to-day use.

## Requirements

- OpenCode CLI installed on your machine.
- Binary available on `PATH` as the released `opencode` or `opencode2` command.

Happier supports OpenCode V2 through the same integration. See [OpenCode V2](#opencode-v2).

## Install OpenCode

If you use Happier's legacy-named `provider` installer, you can install OpenCode from the CLI:

```bash
happier install provider opencode
opencode --version
```

Or install manually:

```bash
curl -fsSL https://opencode.ai/install | bash
opencode --version
```

On Windows, OpenCode also supports native installs such as:

```bash
npm install -g opencode-ai
opencode --version
```

If Happier offers to run OpenCode’s vendor install recipe for you, it requires explicit confirmation before executing vendor install commands.

## Local authentication in Happier

OpenCode supports machine-local auth management in:

- **Settings → Agents → OpenCode**

From there you can:

- check whether OpenCode is authenticated on the selected machine
- open `opencode auth login` directly inside Happier
- refresh the auth state with **Check now**

Happier reads OpenCode’s local auth state through the CLI’s own auth listing flow when available.

For the shared user guide, see [Agent authentication](/agents/provider-authentication).

## How Happier runs OpenCode

OpenCode has two runtime paths in Happier:

- **Server-native (default)**: Happier talks to the OpenCode server/session APIs directly. This is the normal path for new OpenCode sessions in Happier.
- **ACP (legacy fallback)**: still available when you explicitly switch OpenCode to ACP mode.

For most users, the important part is:

- new OpenCode sessions default to the **server-native** backend,
- Happier can keep the same OpenCode session visible in both the app and the terminal,
- attaching later should use `happier attach <session-id>`, not a raw vendor attach command.

By default, Happier uses a **managed local OpenCode server** on the machine and reuses it across sessions. Advanced users can set an explicit OpenCode server URL in settings; when you do that, Happier will keep using that explicit server for the session.

## OpenCode V2

<Callout type="warn">
  This V2 integration describes current development source, not the Happier CLI 0.2.12 stable
  release. That release sends V1 `/session` requests and cannot start OpenCode 2.x sessions.
</Callout>

Released OpenCode V2 publishes both the `opencode` and `opencode2` command aliases. Happier
recognises both through the same integration — there is no second OpenCode Agent to enable.

The current development integration is pinned to OpenCode 2.0.15 and has been exercised against
that real server binary. Happier adapts the released `/api/*` contract rather than sending V1
shapes to V2 routes:

- prompts use the released flat body (`id`, `text`, files, agents, skills, metadata, delivery, and
  resume fields) rather than nesting it under `prompt`;
- permission rules use `{ action, resource, effect }`, and replies use `{ decision, message? }`;
- `form.created`, `form.replied`, and `form.rejected` replace the old question events; Happier
  preserves field order, typed answers, conditions, defaults, and opaque option values;
- Happier MCP servers register with `PUT /api/experimental/mcp/:name` and `{ config }`, then read
  registration state from `GET /api/mcp`. In OpenCode 2.0.15, that state can become `connected`
  before the asynchronously refreshed tool catalog includes the server's tools. OpenCode exposes no
  public tool-ready signal, so an immediate first invocation can still fail as an unknown tool even
  though later invocations see it;
- conversation fork uses `POST /api/session/:id/fork` with an optional `before` checkpoint, while
  fork from a particular Happier message remains unsupported;
- manual compaction is admitted through the V2 compact route and finishes only when OpenCode emits
  `session.compaction.ended` or `session.compaction.failed`.

The same live check covered session creation, permissions, forms, MCP registration, prompting,
events, ordered message history, conversation fork, diff, and cancellation. Diff exists in the
released API, although Happier does not currently expose a separate user-facing diff action.

**Which executable Happier runs.** Choose **Auto**, **Stable**, or **V2** under
**Settings → Agents → OpenCode**:

- **Auto** prefers `opencode` and falls back to `opencode2`;
- **Stable** requires the `opencode` command. For managed servers Happier reads that executable's
  version, so a released 2.x `opencode` still uses V2 routes;
- **V2** prefers `opencode2`, falls back to `opencode`, and uses the V2 server contract. This lets a
  machine with both released aliases select either one explicitly.

**Starting the server.** Happier waits for a server it starts to report itself ready. An explicit
V2 selection chooses the V2 request contract. Auto and Stable recognise released `opencode` 2.x
by its `--version` result, while the `opencode2` alias identifies V2 directly. OpenCode 2.0.15
answers the authenticated `/api/info` route. Happier chooses the attach argument form from the
resolved executable generation as well as choosing its HTTP dialect.

**Which routes Happier then uses.** The same fact decides that too. When Happier started an
`opencode2` or released `opencode` 2.x server itself, that session uses the V2 request routes with
no configuration. For a server you run yourself, Auto probes the authenticated HTTP surface before
choosing the route; you can instead require V2 through the setting or session launch environment:

```bash
HAPPIER_OPENCODE_SERVER_DIALECT=v2
```

For an attached server in Auto mode, Happier probes through the authenticated managed endpoint
before the first read:

- a shaped `/api/info` answer selects V2;
- a shaped `/global/health` answer selects V1;
- an error or an unrelated `200` response selects neither dialect and the read fails instead of
  guessing.

An explicit V2 selection keeps V2 routing authoritative.

In current development source, V2 model, reasoning and agent-mode controls use
the exact native Session writers before Happier reports them applied, including
idle changes and preparation before opening its TUI. V1 retains selections for
the next Happier-submitted prompt; it does not immediately change an attached
native TUI. The mode picker still exposes a known native inventory when the
current mode cannot be observed, without presenting staged intent as accepted.
Catalog failures retain the last known choices; a successful empty read removes
them. Catalog refresh follows the existing startup, connection and catalog events.

The OpenCode server log records the requested and resolved route choice. For Auto attachments it
also records the deciding probe; for managed servers it records the resolved executable and
readiness route. Explicit attached V2 has no separate health probe.

**The V2 event stream is live, not replayable.** Happier subscribes to `/api/event`, which carries
both durable and live frames but provides no event-id replay cursor. After a disconnect, Happier
subscribes again and resynchronizes the transcript, session status, and outstanding permission and
form requests from their owning APIs. Events published only while the connection was down cannot be
replayed, so the resync repairs current state rather than reconstructing every missed frame.

**Server credentials stay with the host.** For a server Happier starts, the host mints a Basic-auth
password and injects it into the managed OpenCode server and its runner-local native TUI. For a server you configure by URL,
the host uses the password from the **OpenCode server password** setting. The URL itself must not
contain credentials. Connected-account credential projection accepts only end-to-end encrypted
credential material and is separate from the server password. For a server Happier starts, qualified
connected-account OAuth reaches V2 through an isolated provider-scoped request-auth plugin; Happier
does not project that private capability into a server you configured by URL.
In current development source, a managed native attachment fails if its exact server access
is unavailable; it does not substitute ambient credentials. Opening an independent native
TUI through standalone attach for a Plain account remains unsupported pending a private local
credential transport. Restoring the TUI inside its running terminal host reuses runner-local access.

**Native subagents in development source.** A background subagent keeps its own output,
permissions and questions after the main reply finishes. Its success, failure or cancellation
closes its pending prompts; a reply to an old prompt cannot affect a resumed invocation. A
background launch acknowledgement does not mark the subagent complete.

Child outcomes follow the [OpenCode 2.0.20 execution contract](https://github.com/anomalyco/opencode/blob/84c9be93a56304a108f1a22df0c5d62c26d5b6ca/packages/schema/src/session-event.ts).
After reconnecting, Happier reads the child's saved outcome when available and reports missing
outcome evidence instead of guessing successful completion. Shutdown preserves work for resume.
The native child lifecycle has host test coverage; validation against a running native child
remains outstanding. Child approval requests can be answered, but the server path does not yet
link an approval card to its exact launch tool row.

### What V2 does not support yet

These are current development gaps. They are not settings you can turn on:

- **Fork from a particular message.** V2 conversation fork is supported, but the from-message
  checkpoint path is not yet safe to advertise. Forking the conversation at its current point works.
- **The native to-do work state.** V2 publishes `todo.updated` events but offers no route to read
  the list back, so the to-do panel stays empty.
- **Per-prompt configuration overrides**, and OpenCode's global configuration read that Happier uses
  to guess a default model. Model and variant selection themselves do work: Happier sets them on the
  session's own V2 model route immediately before the prompt.
- OpenCode's V2-only configuration keys (for example the V2 `permissions` block) are rejected by
  V1 installations of `opencode`. Keep V2-only configuration for machines running V2.
Browsing external OpenCode sessions works with a Happier-started released V2 server.
Happier reads the resolved executable and version first — the same way a session does — so the
server is checked on its actual readiness route, then listed and paged over V2 routes. For a server
you started, managed-service readiness and subsequent reads use the same authenticated,
shaped-response negotiation described above: released V2 is tried first and retained V1 second,
within the existing readiness deadline. An unrelated successful HTTP response is not treated as
either OpenCode dialect.

## Start OpenCode from a terminal

```bash
happier opencode
```

When you start OpenCode this way:

- the session appears in Happier as a normal session,
- the terminal starts in **local/shared control**,
- the Happier app can still see the same transcript and send messages into the same OpenCode session,
- messages typed directly into the OpenCode TUI also show up in Happier.

This is useful when you want the Agent TUI first, but still want the app to stay attached to the same session.

### Detach from the app

If the session is locally attached, the session header in Happier shows **Detach terminal**.

Using it:

- switches the session back to **remote** control,
- keeps the same session id and transcript,
- closes the attached OpenCode TUI while the Happier session keeps running.

You can later run `happier attach <session-id>` from a terminal on the same machine to get back into the OpenCode TUI.

## Start OpenCode from the app

If you start a new OpenCode session from the Happier app:

- Happier starts it in **remote/server-only** mode in the background,
- the app can use the session immediately,
- no terminal needs to be open yet.

Later, on the same machine, you can attach a terminal to that live session with:

```bash
happier attach <session-id>
```

After attaching:

- the session switches into **local/shared control**,
- the terminal shows the OpenCode TUI,
- the app still stays connected to the same session and transcript.

This is the main “start in the app, continue in the terminal” workflow for OpenCode.

## Local vs remote control in OpenCode

OpenCode uses **shared local control** in Happier.

That means:

- **Remote mode**: Happier drives OpenCode in the background and you use the app/web UI
- **Local mode**: you use the OpenCode TUI in a terminal
- the transcript stays shared in both modes
- the session stays writable from the app even when a terminal is attached
- app messages do not need the pending-queue handoff used by exclusive local-control paths

In practice, you can:

- send a message from the app and watch it appear in the attached OpenCode TUI,
- send a message from the OpenCode TUI and see it appear in Happier,
- detach and reattach without starting a new session.

For the full switching workflow, see [Features → Attach to a running session](/sessions/attach-to-session).

## Authentication (connected services)

On the V1 and V2 server paths and in ACP mode, OpenCode can reuse connected services profiles when
spawned by Happier (for example):

- `openai-codex` (subscription OAuth) or `openai` (API key) for OpenAI-backed usage
- `claude-subscription` setup-token profiles or `anthropic` (API key) for Anthropic-backed usage

If multiple compatible profiles exist, Happier will let you pick one when starting a new session.

OAuth profiles use qualified per-request authorization without exposing access or refresh tokens in
OpenCode configuration. Direct API keys and Claude setup tokens remain on OpenCode's native auth
path. Connected-account authentication requires a server Happier starts; it is rejected for a server
you configured by URL rather than silently changing that external process.

See: [Connected services](/accounts/connected-services)

## Session handoff

OpenCode supports Happier session handoff between machines.

This is a natural fit for OpenCode because Happier can move the same Happier session while preserving OpenCode continuity on the new machine.

Use it when you want to:

- move a live OpenCode session from one machine to another
- keep the same Happier session id
- continue the same work from the target machine

Connected services can help here too, especially when the target machine should reuse account-managed credentials instead of depending only on a local machine login state.

See:

## Permissions, modes, and models

Happier uses the same Agent-agnostic permission picker for OpenCode as it does for other Agents.

Important OpenCode notes:

- permission intent is chosen in Happier,
- Happier maps that intent to the closest OpenCode session permission ruleset,
- some OpenCode behavior still depends on the installed OpenCode runtime.

OpenCode can also expose Agent-native session modes and model choices. When those are available, Happier surfaces them in the session UI.

## Notes

- Resume availability is session-specific in Happier: the session must have valid OpenCode resume metadata, and your current backend/settings must allow resume.
- In current 0.3 development source, cold resume reconciles exact saved message identities before importing missing settled native turns, including histories created by 0.2. Import identities preserve opaque IDs without delimiter collisions; older import identities require a separate matching native-session identity. If older history lacks provable identities, Happier reports the gap instead of duplicating uncertain messages; new native turns continue to sync. Failed or malformed history reads remain unresolved until a later connection or idle update succeeds. This is development behavior, not a shipped-release or authenticated 0.3 live-validation claim.
- Attach availability is also session-specific: the session must have the metadata/context Happier needs to reopen that OpenCode session locally.
- Model, mode, and permission behavior can still vary by installed OpenCode runtime.
- Tool events are normalized into Happier’s canonical tool timeline.
- For OpenCode reattach flows, the supported command is `happier attach <session-id>`.

## Troubleshooting

If OpenCode is not detected:

1. Verify `opencode --version` works.
2. Restart Happier.
3. Set `HAPPIER_OPENCODE_PATH` if your binary is not in PATH.

### The session is visible in the app but I want the TUI again

Use:

```bash
happier attach <session-id>
```

Do this on the same machine and against the same Happier account/server profile that owns the session.

### The terminal is open but no longer accepts prompts

This usually means the session was detached back to remote mode from Happier. Reattach with `happier attach <session-id>` from a terminal on the same machine.
