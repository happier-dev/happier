The Muse Agent integration is part of **unreleased 0.3 development**.
It runs the native Muse executable on the Machine you select.

Choose **Muse** as the Agent when creating a Session. If the selected Machine
needs Muse installed, use its installation action. See
[Muse Agent setup](/agents/provider-integrations#muse-agent-in-03-development)
for native model choices and the distinction between a Muse Session and using
Muse models through a Provider gateway in another Agent.

For native login and API-key connections, see
[Muse accounts](/accounts/connected-services#muse-accounts-in-03-development).

## Models, effort and approvals in 0.3 development

Native Muse model and effort choices come from the selected account's catalog.
When using a Muse model through another Agent, available effort also depends on
what that Agent can apply. See [reasoning effort](/agents/provider-integrations#manual-reasoning-effort-in-03-development).
Codex custom upstreams exclude inherited ChatGPT Apps to avoid unrelated tool
context; see [Codex models and tools](/agents/codex).

A pending approval appears in its approval card. When the Machine is offline
and no card can present the waiting request, the Session status line explains
that permission is required and the Machine is offline. Reconnect the Machine
to answer it. See [Permissions](/sessions/permissions).

## Troubleshooting

### Shell commands fail in a home-directory workspace

In a Coder workspace or devcontainer, Muse can answer text-only turns while
shell commands fail with `Linux sandbox helper ... is under writable sandbox
root` and `Bubblewrap unavailable`. If the writable workspace is your entire
home directory, it can include Muse's own sandbox helper.

Happier uses [Meta's installer](https://dev.meta.ai/install.sh), whose default
location is `~/.local/bin`. A Session opened at `/home/coder`, for example,
includes that installation in its writable workspace. Muse rejects a helper
inside a writable sandbox root: a command allowed to replace the helper could
undermine the sandbox on later commands. This differs from the Ubuntu
user-namespace restriction below.

Create a new Session in a dedicated project directory that does not contain the
Muse installation, rather than selecting your whole home directory. If your
work requires the broader root, ask the Machine administrator to place Muse
outside every writable workspace root. Meta's installer accepts
`MUSE_INSTALL_DIR`, and Happier recognizes that location when the variable is
available to its running process. Moving only a launcher link is insufficient
if the actual helper remains inside the writable root.

Meta documents a bundled Linux bubblewrap helper; a separate system installation
is not always required. An administrator-provided system bubblewrap must also
be outside the writable roots and permitted by the guest's namespace policy.
Changing the install path alone does not remove container or AppArmor
restrictions. In a new Session, ask Muse to run `printf sandbox-ok` to verify
the chosen environment. Text-only success does not verify shell execution.
See [Meta's sandbox requirements](https://dev.meta.ai/docs/muse-code/permissions#run-inside-the-sandbox).

### Approved shell commands fail on Ubuntu

On Ubuntu 24.04 and later, an approved shell command can fail with
`bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted`, or Muse can
suggest installing bubblewrap even when it is already installed. Ubuntu's
`kernel.apparmor_restrict_unprivileged_userns=1` policy can block Muse's bundled
sandbox helper from creating the user namespace it needs. Approval does not
remove this operating-system restriction.

On the Machine running Muse, check the policy:

```bash
sysctl kernel.apparmor_restrict_unprivileged_userns
```

If it reports `1`, ask that Machine's administrator to allow user namespaces
for the Muse executable. An executable-scoped AppArmor profile keeps the global
restriction in place. For an installation under `~/.local/bin/muse-bin-*`, create
`/etc/apparmor.d/happier-muse-userns` with the following content. Replace
`/home/YOUR_USER` with your absolute home directory, or change the attachment to
match your actual Muse executable. AppArmor profiles do not expand `~`.

```text
abi <abi/4.0>,
include <tunables/global>
profile happier-muse-userns "/home/YOUR_USER/.local/bin/muse-bin-*" flags=(unconfined) {
  userns,
}
```

The administrator can then load this profile:

```bash
sudo apparmor_parser -r /etc/apparmor.d/happier-muse-userns
```

Start a new Muse Session on that Machine and ask it to run a harmless shell
command, such as `printf sandbox-ok`, to verify that sandboxed execution works.
Reinstalling bubblewrap alone does not resolve this host-policy restriction.

Meta also documents `--disable-sandbox`. That flag keeps approval prompts but
removes Muse's filesystem confinement, including confinement of its file tools,
and permits unrestricted network access. It changes the security boundary rather
than repairing the sandbox; see [Meta's permissions and safety documentation](https://dev.meta.ai/docs/muse-code/permissions#run-without-guardrails)
for the trade-off.
