---
title: Agent and model selection
description: Choose an Agent, pick native or Provider models, and save exact model choices for new sessions.
---

Happier uses **Agent** for the executable coding tool that runs a session. Some internal and compatibility surfaces still call that choice an engine or backend.

An Agent choice can be:

- a built-in Agent, such as Claude, Codex, Gemini, OpenCode, or Pi
- a configured **Custom ACP** backend
- a configured runtime variant exposed by an Agent plugin

The **Model** section shows the Agent's native models and grouped models from every enabled, compatible Provider connection.

## Where to find it

Open the **new session** flow and use the Agent/model picker in the bottom bar.

The left side shows Agent choices. The right side shows the selected Agent's details, including:

- model choices
- Provider or ACP configuration options
- refresh status when Happier is probing the selected machine
- model-specific controls, when the provider exposes them

Running sessions can also show a model/config picker in the input settings for the current session. Favorites are part of the **new session** picker.

In the current development source, that in-session picker also lists other Agents. Choosing one arms the session to change Agent on your next message rather than changing the model — see [Continue with another Agent](/sessions/continue-with-another-agent).

## Choose an Agent

Pick the Agent that should launch the session.

The list is capability-aware:

- disabled or hidden Agents do not appear;
- configured ACP backends appear as Agent choices;
- profiles can filter which Agents are compatible;
- details can vary by machine, working directory, profile, Provider, and connected-service state.

If only one Agent is available, Happier can skip most of the picker chrome and use it directly.

In the current development source, the same Agent picker rules are used by the composer, New
Session, Workflow editors, role engine fields (Settings › Roles, a Session's roles, Workflow roles
and a Workflow run's "another agent" choice) and the **Who** list when you start a delegate, plan or
review. Each shows every Agent's readiness on the chosen machine:

- an Agent that is not installed there sits under **Not on this machine yet** (or **Can't run on
  this machine**), and one that needs sign-in (and has no connected account set as its default) is
  marked as such; choosing either opens that machine's setup for it instead of picking it;
- if you already chose that Agent, it stays chosen and is labeled as not ready; it is never
  swapped for another Agent, and starting work on it fails with that reason until you sign in,
  install it, or choose again;
- opening the picker reads the machine's Agents when nothing has read them yet; an Agent whose
  readiness the machine has not reported yet is not blocked.

**Get a second opinion**, **Discuss this answer** and a Workflow's participant inputs list only your
existing Sessions, Bots and people. To bring in a new agent, choose **Add an agent** (or **Add
agent** beside the list's label): it shows the same chips a new Session uses (Agent, model and
effort, Runs through, permissions) and one **Where** chip for the machine and folder, starting on
the Session's machine and folder. **Add** puts it at the top of the list, checked; **Change**
reopens the same chips.

Where work can follow the Session it runs in, such as a Session's roles, the picker also offers
**Same as session**: the role then has no Agent of its own and uses the Session's.

When nothing is chosen, a new Session starts on the Agent you used last if it is available,
otherwise the default Agent, preferring one that is ready on the machine. When you switch a
running Session to another Agent, that Agent starts on your default model for it (Settings ›
Agents), the same default a child run uses when it names no model.

## Choose a model

Native model sections may offer **Use CLI settings**.

Use this when you want Happier to avoid setting a native model override and let the Agent CLI/runtime decide from its own settings. Provider-backed selections always identify an exact Provider connection and model.

When you choose a specific model, Happier stores its Agent target, exact Provider connection (or `null` for native), and model id. Apply behavior depends on the Agent runtime: some can change models for the next prompt, while others require a restart or fork. Happier never guesses another connection or silently falls back to a native model.

In unreleased 0.3, if the Agent refuses a model change before receiving the
prompt that triggered it, the Session shows the failure for that prompt. Later
queued messages can continue on the current model when you have no newer model
choice pending. You can choose another model and resend the failed prompt.

For running-session apply timing, see [Permissions](/sessions/permissions).

## Account-only browsing in 0.3 development

The unreleased 0.3 integration lets an Agent's Models settings show its native
static choices alongside compatible declared and manually added Provider models,
even with no machine selected. You can manage manual entries where the connection
allows them and preserve an exact model choice; browsing alone does not start a
session, fetch live models or establish permission to run them.

Provider rows in this view are unverified. Their declared compatibility is not
runtime confirmation, their endpoint health is unchecked, and their load state
is unknown. Runtime confirmation and model-loading controls require the selected
machine's evidence. An unavailable source or missing selected model remains a
setup/recovery state rather than silently switching to native CLI settings.

The development Models view marks exact Account favorites and the saved default
model. Setting a default writes that Agent's exact model reference through the
Account preference Action; it does not change a running session. Reasoning or
effort options remain on the Agent's existing configuration controls rather
than becoming a second model-selection format.

See [Account Provider setup](/agents/provider-integrations#account-setup-in-03-development)
for connection configuration without a machine. Personal live refresh runs from
the selected machine; shared Team sources follow the route described below.

## Source visibility and changes in 0.3 development

The unreleased model-picker integration distinguishes a source's discovery visibility
from its permission to run models. Aggregators default to hidden from ordinary browsing;
direct, cloud, local and custom sources default to shown. Exact current, default and
favorite choices remain identifiable when their source is hidden. Turning a source off
does not change a running session or revoke credentials. In development builds the
model picker lists hidden sources under the models; choosing one browses its models
in place, and only picking a model changes the session. A model whose name appears
in more than one source shows which source it comes from. The composer's account chip
reads **Runs through** followed by where the session's models come from. Picking a
model from another source while the session runs works like choosing another Agent:
the chip reads **Next via …**, the send button reads **Continue via …**, and nothing
happens until you send. Sending restarts the Agent on that source and continues the
same conversation. Before sending, use the cancel control beside the armed
send button to un-arm the change and keep the applied model and source; picking
the current model again also cancels it. In a Provider connection's development
settings, **Show in model picker** saves that connection's Account-wide visibility
choice for every Agent. These controls are not yet a released Settings workflow.

## Child choices in 0.3 development

The unreleased child-session integration lets an attached delegate, plan, review
or conversation inherit the model and source actually running in its parent
session. A pending model change does not become the child's choice. Choosing an
explicit model or native CLI settings overrides inheritance, as do model choices
in a Workflow definition or role. A role's model keeps the exact Provider connection it was chosen
from. A role saved without one runs its model natively, except when it is started directly from a
Session that already runs the same Agent on a connection, which it then reuses.

Inheritance is part of ordinary child launch admission in 0.3 development builds,
without a separate capability toggle. The one-way 0.3 upgrade updates all
components together; older session processes and mixed 0.2/0.3 operation are
unsupported. Unavailable applied state never falls back to Account defaults.

Choosing another Agent still requires a compatible model and source. If that
choice cannot be admitted, the development launcher shows a chooser for that
child Agent: use its Account default, choose an exact model, or cancel without
starting it. Composed live validation, including Reviews with multiple refused
Agents, remains pending. Independent detached or scheduled work uses its own
choices or Account defaults. Resuming a child keeps that child's retained choice,
even after its parent changes.

Development Run rows show the admitted child's model and source, including its
Home, rather than a pending parent choice. Older daemon entries without that
summary use a matching transcript when available; otherwise the source remains
unknown. This presentation is not proof that the source is currently ready.

Voice's **Session model** choice follows the same admission rule; custom chat
and commit model choices remain explicit. Native children created by an Agent
continue to follow its definitions and model rules.

## Live model lists

Provider connections and some native Agent runtimes expose models dynamically. For personal sources, Happier probes from the selected machine and shows the current merged catalog.

This matters because the available list can depend on:

- the installed Agent CLI version
- whether Agent authentication or the Provider connection is ready
- account or subscription entitlements
- selected connected-service profile
- Custom ACP backend args and environment
- the selected working directory, when the provider uses project-local config

Use the refresh button after changing Agent login state, Provider connection settings, CLI config, Custom ACP settings, or working directory.

In development builds with session model refresh, you can also refresh native model choices from
an existing session's picker, including an inactive session. Its machine must be reachable, but
refreshing does not resume the session. Happier keeps previously discovered choices visible while
checking for updates and retains them if the check fails. Retry after restoring the machine
connection or Agent login. Update both the app and daemon to use forced refresh; an older daemon
may still return cached choices.

Refreshing available choices does not change the model already running. Select a model separately;
the Agent's normal apply timing still applies.

### Team model discovery in 0.3 development

In unreleased 0.3 development, a brokered Team Connected account or Pool uses
the credential owner's selected source on the broker machine for model discovery.
Direct delivery instead uses the execution machine's accepted source context:
after delivery, the running session publishes its Agent's model observation
through the existing in-session model list. Browsing Direct declarations before
launch does not deliver credentials or borrow the broker's observation.

An observed model list replaces the static declarations, including when a
successful observation returns no models. Without an observation, the static
fallback is labelled **Not checked**. Route readiness alone does not verify
Account entitlement or a successful model request. Experimental Team
Agent/model pairings show an **Experimental** badge and require no confirmation
from either the credential owner or the recipient; hard incompatibility and
ordinary access checks still apply. The badge is separate from catalog confidence.
See [Shared credentials for a Team](/accounts/team-credentials#model-discovery-in-03-development)
for the delivery choices and their limits.

## Static model lists

Not every Agent or Provider has a dynamic model API.

For static-only sources, Happier uses verified plugin catalog metadata. Claude instead starts from that static catalog and, by default, asks Anthropic for the models available to the selected Connected Service or native Claude Code login.

In 0.3 development, native Claude discovery also supports enabled user settings helpers and configured gateways. Happier executes the user helper as a shell command on the machine running Claude, in the selected workspace directory. If it fails, the picker shows the built-in catalog and a failed refresh without substituting another account's credentials. See [Claude discovery settings](/agents/claude#settings-reference-claude-remote) for credential and failure behavior.

Static model lists can still change when Happier updates its provider catalog.

## Custom model ids

Provider connections that allow manual catalog entries support custom model ids.

Use this for Provider connections whose endpoint cannot list models but whose exact model id you know.

Important details:

- Happier sends the id through the selected Provider connection; the Provider still decides whether it is valid.
- Manual ids are useful for compatible gateways, custom endpoints, or newly released models.
- Manual models retain their provenance and may be favorited as exact structured selections.

In unreleased 0.3 development, manual models can also carry an explicit
[reasoning-effort declaration](/agents/provider-integrations#manual-reasoning-effort-in-03-development)
when the endpoint supplies no reasoning facts. Adding a model id alone does not
enable reasoning controls.

## Model-specific options

Some models expose extra controls, such as thinking, reasoning, effort, or a Provider-specific mode.

When those controls exist, Happier shows them with the selected model. They are part of the Agent/model configuration surface, not a separate global settings page.

Not every Provider exposes these options, and not every model from the same Provider supports the same options.

## Favorite models

Favorite models help you keep a short list of model choices you use often.

To favorite a model:

1. Open the new-session Agent/model picker.
2. Choose an Agent.
3. Select a concrete model.
4. Use the star button on the selected model card.

The filled star means the model is already a favorite. The outline star means it can be added.

The **Use CLI settings** default is not favoritable because it is not a concrete model choice.

## Favorites section

After you save at least one favorite model, the engine picker can show a **Favorites** section in the left rail.

Use it to jump directly to saved engine/model combinations without scanning a long model list.

Selecting a favorite:

- switches to the favorite's Agent
- applies the favorite's model
- keeps other launch settings, such as profile, permissions, modes, and config options, governed by the normal new-session controls

Favorites are account settings. They include the Agent target, exact Provider connection (when present), and model id, so identical model ids from two connections remain separate favorites.

In 0.3 development, you can also star a model from the Agent picker in an
existing Session. On web and desktop, open the model picker and press
**Command** or **Control** plus **1–9** to choose a favorite in saved order.
The picker applies the saved Thinking level where supported and closes after
the choice is applied.

### Favorites in Search (in development)

In 0.3 development source, with a session open, type a model name or "model" in
Search (the command palette). Each favorite for that session's Agent shows up
as a command by name, such as **Use favorite model Opus 5.5**. Its subtitle shows
the saved effort, whether the session already uses that exact model and source,
and the Provider connection the favorite saved. Starring a brokered model in an
existing session saves the model's Connected Account source or its Team and
shared credential reference. If the Team share is withdrawn or you leave the
Team, the favorite stays visible with an unavailable reason. A native favorite for that
same model shows **Restart required** when it would switch the running session
away from the brokered source. Running it switches the session's model the
same way choosing that model in the session's model picker does, through the
`session.model.set` Action. Favorites don't appear while the query is empty.

## Removing favorites

You can remove a favorite by clicking the filled star:

- from the normal model list, when the favorited model is visible
- from the **Favorites** section

Already-favorited models keep showing the filled star so you can remove them without selecting them first.

## Availability rules

Favorites are saved, but selection still respects the current Agent, Provider connection, and target-machine state.

For dynamically probed sources:

- a current favorite is selectable when its exact connection and model are available;
- if a model disappears from the current catalog, Happier keeps the stale reference renderable instead of silently changing it;
- refresh the catalog after fixing authentication or connection configuration.

For static-only sources:

- favorites are checked against verified plugin catalog metadata;

Claude keeps its verified static catalog when dynamic discovery is disabled or no usable Claude credential is available, so native Claude models remain selectable without a successful live probe.

If a saved favorite no longer appears in the current catalog, Happier keeps it visible as a stale reference with a setup hint. It is not silently redirected to another connection or model.

## Profile and Agent compatibility

Favorites respect the current Agent list.

If a selected profile filters out an Agent, favorites for that incompatible Agent are hidden from the Favorites section for that picker state.

This keeps the Favorites section focused on choices that make sense for the current launch configuration.

## What favorites do not store

A favorite stores an exact Agent/connection/model reference. It does not replace profiles, Provider connections, or Agent settings.

Favorites do not store:

- API keys or connected-service credentials
- environment variables
- working directory
- permission mode
- session mode
- model-specific controls such as reasoning effort

Use [Profiles](/agents/profiles) for optional launch preferences such as permission defaults and extra non-routing environment. Use **Settings → Providers** for model endpoints, Provider credentials, catalogs, and model visibility.

## Common use cases

Use favorite models when you want to:

- keep your normal Claude, Codex, or Gemini model one click away
- quickly switch between a fast model and a deeper reasoning model
- save favorite models for several Custom ACP backends
- avoid scrolling through a long live model list
- preserve a favorite while a provider login or entitlement issue is temporarily hiding it

## Troubleshooting

### A favorite is visible but does not start

The model is saved, but the current backend does not report it as available.

Check Agent authentication, the Provider connection, connected-service profile, Custom ACP config, and selected machine. Then refresh the catalog.

### A favorite disappeared from the left rail

The Favorites section only shows favorites for Agents that are currently visible and compatible with the picker state.

Check whether a selected profile or feature setting is hiding that engine.

### I cannot favorite a custom model id

Add the model under **Settings → Providers** for the exact connection first. Manual and probed models then share the same structured selection path.
