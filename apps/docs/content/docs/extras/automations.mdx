title: Automations
description: Run one reusable recipe from automatic triggers, a connected conversation, or an explicit Run now action.
---

Some work is worth doing on a timer rather than when you remember it: a nightly
dependency check, a Monday-morning triage pass, a recurring prompt against a
repository you watch. Automations run that work on your machines without you
opening the app.

<Callout type="warn">
  The Workflow instructions below describe current 0.3 development source,
  not certified stable or preview availability. Use matching development
  components. In that source, **Automations** has graduated: its preference
  defaults on and does not require **Experiments**. The server still needs the
  `automations` and dependent `workflows` feature gates; a missing or disabled
  server gate keeps execution unavailable.
</Callout>

Open **Workflows** from the app's navigation. This is the one destination for
definitions, their triggers, built-ins, and Runs. Choose **New workflow**, write
its first prompt, select where it runs, and save explicitly. **Run now** opens
the run composer to review the inputs and target before starting. **Run settings**
in this destination controls capacity and retention.

Existing schedule automations created by released 0.2 clients remain readable
and runnable through the current 0.3 stored-data readers. Current clients use
the V3 Automation transport; this data compatibility does not require a V2 route.

## One recipe, several ways to start it

A saved Workflow holds a reusable definition. Attaching triggers makes it
automated: each trigger set keeps its machine assignments and either references
that saved Workflow or contains an inline prompt or Action. A referenced
Workflow is read when the daemon claims the occurrence, so saving a change
changes what future claims execute. An admitted Run keeps its frozen definition.
It can start a new Session, continue an existing Session, or run detached work,
depending on the authored target.

For Workflow-backed Automations in current 0.3 development source,
**Runs in: existing session** writes into
that conversation rather than starting another Agent. These writes do not use
machine start capacity, whether the Automation belongs to the Account or is
attached to a Session. Session-attached triggers keep their Session scope.
Run queries can select the destination Session separately from the Session that
started the Run; both kinds of Automation use that same destination relation.

The same Automation can own no automatic triggers, one trigger, or several.
Every enabled trigger is independent: if any one of them fires, the recipe
runs. There is no ordering or requirement that several triggers fire together.
An admitted Run keeps the recipe and assignments resolved for it; later edits
do not rewrite that Run.

An enabled Automation must keep at least one enabled machine assignment — a
Run freezes the assignments it was admitted with, so a Run with no machine
could never start. You can save a paused draft with no assignments and assign
machines before enabling it; removing or disabling the last enabled assignment
of a running Automation is refused until you pause it first.

## What can trigger one

A timer is only one of three automatic sources that can start an Automation.

| Trigger | What starts the run |
| --- | --- |
| **Schedule** | A cron expression or an interval. |
| **Plugin event** | Something a plugin observed — a new issue, a push, a review request. |
| **Session turn finished** | Completion of the exact active parent turn selected while authoring. |

**Run now is an operation, not a trigger.** An Automation with no automatic
triggers can still run when you choose **Run now**, invoke it from the CLI, or
admit an authorized bound conversation.

### Schedule

A schedule is either an interval — every *n* minutes — or a cron expression,
with presets for the common cases (**Every hour**, **Daily midnight**). Cron
schedules run against a timezone you set, so a "daily at midnight" automation
means midnight where you are rather than wherever the machine thinks it is.

### Plugin events

This is the one that makes automations more than a scheduler. A plugin declares
events it can observe, and an automation binds to one — so a GitHub repository
event can start a session on your machine without you or a timer involved.

The GitHub plugin exposes semantic events for a repository push, an issue being
opened, a pull request being opened, and a pull request being merged. Polling
and webhook delivery normalize into those same event identities, so changing
the observation transport does not change what the Automation means.

An event trigger is observed in one of three ways, and the difference matters
operationally:

- **Checkpointed pull** — a watcher materialized on a specific machine polls
  the source and records a checkpoint as it goes. It needs that machine to be
  up; when it comes back, the checkpoint tells it where to resume without
  re-processing earlier occurrences. If the upstream source no longer offers
  the missed range, Happier reports a history gap for that exact trigger so you
  can recover it explicitly.
- **Durable push** — the source calls a webhook endpoint Happier owns.
  Delivery does not depend on one of your machines being awake, and the
  endpoint records the moment observation started so earlier events are not
  replayed at you. This transport is a Developer Preview and best effort
  until a delivery is durably committed: one that arrives while Happier
  cannot commit it is not held or retried, and GitHub does not redeliver on
  its own. When a missed occurrence matters, choose checkpointed pull.
- **Live socket** — a provider connection such as Discord Gateway observes
  events while its machine is connected. Happier resumes the provider session
  when the provider permits it; if that session cannot be resumed, the trigger
  reports a history gap instead of pretending the missed interval was observed.

#### Setting up durable push

Pick **Webhook** when the composer offers the choice, then configure the source
as usual. Happier creates the endpoint for you and shows two values:

- a **payload URL** on your Happier server, and
- a **secret**, shown once and never again.

Nothing arrives until you add that webhook at the source yourself. In GitHub,
open the repository or organization settings, select **Webhooks**, then choose
**Add webhook**. Paste the payload URL, paste the secret into **Secret**, set the content type to
`application/json`, and choose the events you want. Happier verifies every
delivery against that secret and drops anything that does not match, so a
mistyped secret looks like silence rather than an error.

Happier does not create the webhook for you and does not need a GitHub App: a
plain repository or organization webhook is the whole setup. If you lose the
secret, rotate the endpoint credential from its webhook settings rather than
creating a second automation — a new secret means editing the same GitHub
webhook again.

Two limits matter before you rely on webhook delivery. Happier holds a
delivery durably only after it has verified and committed it, so a delivery
lost in that window is gone unless the source sends it again — and GitHub
never resends on its own; a redelivery happens only when you request one for
that specific delivery, to the same URL. And when completeness matters more
than latency, checkpointed pull is the transport that records a cursor as it
goes and reports a history gap when a missed range is no longer available.

An event trigger can also carry a **filter**, and a maximum observation age —
past which an event is considered too old to act on rather than triggering a
run late.

Plugins may optionally replace the generic setup form with their own setup
surface. That surface only collects the same strict setup input; Happier still
owns the trigger, admission, deduplication, and Run history.

### Session lifecycle events

A Session lifecycle trigger can react when a parent turn completes
successfully, fails, is cancelled or stopped, or needs your attention. Select
one or more of those events, then choose how long the trigger remains active:

- **Current turn only** binds to the exact active parent turn and can run once.
- **First matching event** waits for the first selected event in that Session.
- **Next matches** runs for the number of matching occurrences you choose.
- **Every matching event** keeps running while the trigger and Automation are
  enabled.

From a Session, open **Triggers** in its Work tab to attach a scoped trigger.
The **When this turn finishes…** shortcut preselects the active turn. If that
turn changes before you save a current-turn trigger, the editor asks you to
use the new current turn instead.

Happier records each occurrence by its durable Session, turn, and request
identity. Earlier events are not backfilled, reconnecting does not create a
duplicate Run, and pausing or deleting the trigger prevents future matches.
The server remains the authority, so closing the app or taking a machine
offline does not move matching into a client-side watcher.

<Callout type="warn">
  Session-scoped Workflow triggers are development-only, not a shipped stable
  or preview feature. In current development source, a user or another Session's
  turn can fire a turn-end trigger; host and Workflow turns do not. A request for
  your attention still fires during those turns. Archive triggers fire only when
  the Session changes from unarchived to archived.

  Each scoped trigger keeps at most one active Run and one pending occurrence.
  A newer pending occurrence replaces the older one, whose history records it
  as skipped. Review Workflows can opt into skipping an unchanged worktree, but
  only when the previous successful Run's final review panel certified the same
  fingerprint. Missing certification always runs the review. Deleting the
  Session retires its scoped Automations without removing retained Run history.

  Session-start attachment is not yet complete.
  Keep going attachment is refused when the opened Agent already owns native
  goal continuation. The Goal control reports a conflict if an existing Keep
  going attachment meets native goal ownership; automatic reopening cleanup
  is not established by the current source.
</Callout>

In current development source, the Session's Triggers section offers PR comments
and CI failures. Choose a pull request from the Session repository; a single
existing link is preselected. Attaching either kind records that Session↔PR link.
Opening or reusing a pull request through Happier also records the link when the
operation has an origin Session. Removing a trigger retains the link but stops
that trigger's conversation ingress.

If the Session's pull request links cannot be read, ordinary scoped triggers
remain available. The Triggers section shows a separate link-read warning with
a retry action; a failed read is not treated as an empty list of links.

PR comments admit only repository writers. CI observations require the selected
GitHub integration principal's write access. Unknown permission or a mismatched
identity admits no Run, for both plain and E2EE Accounts. Comment text is labelled
as untrusted input. This PR/CI vertical has owner-level tests; current loaded-stack
validation is still pending and it is not a shipped stable or preview feature.

For plugin authors using 0.3 development builds, the separate
`@happier/runtime/turn-start`, `@happier/runtime/turn-complete`,
`@happier/runtime/turn-failed`, and `@happier/runtime/turn-cancelled` Host Event
hooks are daemon-local, in-memory, best-effort notifications. They are not
replayed and do not create Automation Runs. Durable lifecycle triggers are
admitted from persisted Session settlement and minimal pending-request
identity instead.

### Conversation bindings

A channel can bind a conversation to an existing automation. A message admitted
through that binding starts a Run with an immutable conversation cause. The
binding is an invocation path, not another automatic trigger row.

### Active and paused

Each Automation is **Active** or **Paused**, and each automatic trigger can also
be enabled independently. Pausing the Automation keeps its recipe and every
trigger but prevents all automatic admission. Disabling one trigger leaves its
siblings active.

## Running one now

For a Workflow, **Run now** starts the reviewed definition directly, without
waiting for a trigger. Retained 0.2 Automations also support an explicit manual
Run through the CLI below.

It does not create a durable Manual trigger and does not require the Automation
to have any automatic trigger rows.

It queues rather than executing synchronously: the assigned daemon picks it up
when it is available. If the machine is asleep, the run waits rather than
failing.

From a terminal:

```bash
happier automation list [--cursor <opaque>] [--json]
happier automation run <automation-id> [--idempotency-key <key>] [--json]
```

Use `automation list` to find the stable Automation ID accepted by `run`.
Human output includes each ID, name, and active or paused state. `--json`
returns the structured definition-list page, including its continuation cursor
when more Automations are available. To continue, pass that cursor back without
changing it:

```bash
happier automation list --cursor <opaque>
```

Pass `--idempotency-key` when the caller might retry — a repeated key will not
run the automation twice.

## Structured workflows (development source)

A Workflow is a JSON-compatible program that can be started directly, referenced
by a trigger, or authored inline in a trigger. A direct Run has its own Account-scoped identity and does
not create a hidden Session or Automation. An Automation Run also keeps its
immutable trigger cause. Editing or deleting a saved definition does not rewrite
an admitted Run. A managed Run is executable from its frozen snapshot; observed
Agent activity is read-only history and cannot be run, edited, or saved without
a managed definition. Trigger claims resolve the current saved definition;
later edits never change an accepted snapshot.

Definitions have four leaf kinds:

- **Agent** sends a prompt and receives a declared text, JSON, or decision result.
  Each step can run in a Session or as a background run.
- **Action** invokes one declared host or plugin Action with typed input bindings.
  An Action that declares execution-run completion waits for those Runs and uses
  its terminal result.
- **Run a workflow** executes another definition as an inline nested frame in
  the same Run. Its inputs and child definition are frozen at admission.
- **Wait for you** waits for a human response without starting an Agent. If it
  declares a result contract, the response must satisfy it.

In current 0.3 development source, **Call a webhook** and **Run a command** are
presets of the same Action leaf, also available through Action discovery and MCP.
The webhook posts JSON from typed bindings, sends a run/step/attempt idempotency
key, and retains the response body and status. A status of 300 or higher fails
the step without following a redirect. It uses the notification webhook
destination policy: public destinations require HTTPS, explicitly named local
destinations are permitted, and metadata addresses or public-looking names that
resolve to private addresses are refused.

A command runs on the Run's Machine in the step workspace, with the Machine's
normal user permissions. Write shell syntax as literal text and pass dynamic
values through the `env` field; reference those variables using your shell's
syntax. Input or event values cannot become command text. The result retains
`exitCode`, `stdout`, and `stderr`, including output from a failed command.
These are trusted-user operations, not a sandbox, and add no default step
deadline or output truncation limit.

In unreleased 0.3 development source, each block can have its own optional name,
separate from its prompt, Role or selected Action. Rename it inline in the block
heading; **Undo** and **Redo** use the same draft history as other edits. Blank
names use the existing derived label. The authored name appears in the editor,
read-only cards, Flow/Map and Run rows. A fresh Session for a named step starts
with the title `{ordinal} · {step name}`, with ` · {item}` added for per-item
work; the ordinal matches the step heading. Unnamed steps use normal Session
naming. Changing a step name does not rename existing Sessions, and a later
Session rename by you is preserved.

Parallel groups, conditions, and loops arrange those leaves. References select
declared inputs and earlier invocation
results structurally. Happier does not interpolate `${...}`-style text or parse
prose as control flow. Pass dynamic values as declared inputs or typed references.

In current development source, a direct Run started by an Agent returns updates
to its originating Session by default; a Run started by a person opts in. The
Session reads the latest committed Run state and result as worker context, not
as a new user message. A finished Run does not stay unfinished while waiting for
the Session to consume its result.

A scoped Automation also uses its bound Session as the Workflow origin. In
development source, returning results to that Session is opt-in on the trigger;
keeping an origin for steps or context does not enable result return by itself.

A step can choose `origin_session` to work in the Session that started the Run.
It waits behind user input and is checked again before dispatch, so a paused or
cancelled step cannot start from an old queued offer. This is separate from a
Channel conversation's reply handoff.

In development Workflow definitions, `until` and `evaluate` loops accept a
positive whole-number round limit or a reference to a declared number input.
The limit is fixed when the work is admitted. Reaching it completes the loop
with an `exhausted` outcome instead of failing the Run. Later steps can test
the recorded outcome without asking the Agent or rechecking a stop condition.

An evaluator declares `continue` and at least one finishing decision, such as
`done` or `stuck`. It may return the decision alone or an object containing
`decision` and an optional `reason`; the reason is retained. Other decision
steps can declare their own values without being loop evaluators.

An origin-context input includes the goal and recent turns. Its usage comes
from Happier's session accounting, not the Agent's native goal counter. Without
reported usage, a budget stop is unavailable; the authored round limit still
applies. To fit the 256 KiB prepared-input bound, Happier drops the oldest turns
and marks the context as truncated, but never truncates the goal. If that is
still too large, the step fails before sending input. A context binding requires
an originating Session.

Parallel groups and item loops may include `maxConcurrent` as a positive integer.
Omitting it means the Workflow adds no concurrency cap; the selected Session,
provider, and machine still enforce their own real limits. A Session step may
include `timeoutMs`. Omission adds no authored observation deadline. Expiry means
the Run needs attention; it does not prove the agent stopped or cancel its work.

The development CLI projects the canonical Actions directly:

```bash
hdev workflow validate --definition-json @workflow.json --json
hdev workflow run start --run-id <uuid> --source-json '{"kind":"inline","definition":{...}}' --machine-id <machine-id> --json
hdev workflow run get --run-id <uuid> --json
hdev workflow run wait --run-id <uuid> --timeout-seconds 60 --json
hdev workflow run invocations list --run-id <uuid> --cursor <opaque> --json
```

Keep the caller-generated `runId` when admission is uncertain. Repeating it with
the same normalized request rejoins the Run; changing the definition, inputs,
saved revision, or target conflicts. A new ID intentionally starts a new Run.
In development Plan review, reopening after a lost start response rejoins a Run
only when its proposal matches the plan you are reviewing. If the Agent has
published a different proposal, Happier explains that an earlier proposal
already started and offers **Open that run** or **Run the new proposal**. Using
the new plan does not label the earlier Run as having started it.
Cursors are opaque and bound to the supplied filters, so return them unchanged.
Page sizes are preferences: response-byte limits can yield a shorter page and a
continuation cursor.

Pause prevents later work from being admitted while accepted work settles.
Cancel records durable intent but is not a receipt that an offline process
stopped. Recovery may reattach an owner-supported execution or require an
explicit same-conversation or fresh-agent continuation; ambiguous effects are
never silently replayed.

Saved definitions use Account Artifacts and whole-document revision checks. JSON
import/export preserves portable authored content only. Local file handles, raw
credentials, checkpoints, and provider resume state are not portable definition
data. YAML is not supported.

### Review and manual Pause

Turn on **Review before continuing** to hold a step's output before downstream
work can consume it. Inspect the displayed value, discuss changes in the step's
conversation, or edit the result yourself. **Use this result** commits that
value; **Generate result and continue** asks the existing Agent conversation for
a new result and continues automatically when it is valid. A failed generation
keeps the previous reviewable value available. A Wait-for-you step accepts a
human response and cannot generate one.

Independent work can continue while a step awaits review. When only human holds
remain, the Run reads **Waiting for your review** and releases its worker slot;
**Review next** opens a held step. This review is separate from a tool permission
request and from recovery of an interrupted execution. Typing in a conversation
does not accept a held result.

**Pause at boundary** closes admission while accepted work settles. A manually
paused Run stays paused after **Use this result**. You can request generation
while paused, but it starts only after **Resume** and the worker's current
authority and continuation checks. **Stop** cancels the Run rather than accepting
its holds.

### Team visibility

Share a Workflow definition through its access controls. Recipients keep their
own triggers and run on their own machines. A personal definition share lets
the recipient use the Workflow but does not expose the owner's Runs.

A Run from a Team-shared Workflow freezes its visible Team when admitted. When
several Teams have access, choose which Team sees that Run. Visibility requires
current membership in that Team and a live grant on the source Workflow; removing
either removes access. There is no separate single-Run share.

People with **Can edit** or higher access can pause, resume, stop, and answer
review holds; view-only recipients cannot. Human answers record who answered.
E2EE content still requires the recipient's key envelope: a visible row with
unavailable keys stays locked.

## Built-in workflows (development source)

Open the **Built-in** section of Workflows. Session-bound recipes offer
**Choose a session…**; the others offer **Run now**, with workspace and inputs
reviewed in the run composer. Built-in definitions are read-only; copy one into
an unsaved draft when you want to change its recipe.

### Keep going until done

Choose a Session and set its goal through the Goal control. Where the opened
Agent supports native goal continuation, the control uses that; otherwise it
attaches Keep going. A new Keep going attachment is refused when the Agent
already owns native goal continuation; an existing conflict is shown rather
than presenting a second continuation control.

After a matching turn ends, a read-only Judge checks the goal and the latest
turn. It continues the Session, then checks again, until the goal is done, the
reported token budget is spent, there is no progress, or the round cap is reached.
The prefilled cap is **4 rounds** and the strike threshold is **3 consecutive
no-progress checks**; both are editable. Four rounds mean at most four checks
and three continuation turns. Without reported usage, the budget stop is
unavailable; the round and strike stops still apply.

**Ask for a second opinion before finishing** is off by default. When enabled,
only agreement marks the goal complete and removes its trigger. Disagreement
or uncertainty sends **Notify me**, leaves the goal and trigger active, and
completes the Run without a hold. Budget, strikes, and exhaustion also leave the
goal active. **Stopped after \{n\} rounds** is a successful exhaustion outcome,
not a failure; the Session transcript folds the continuation turns.

Pending user messages go before a continuation at its final admission check.
A message arriving after the step has passed that check follows the admitted
step; an already running turn is not interrupted.

### Review & converge

Choose a Session, open its Triggers section, and attach this recipe to a matching
turn-end event. Select the review engines. A panel reviews the changes in
parallel, then a read-only convergence check reads the persisted review comments
and each engine's outcome. Missing or failed coverage cannot count as convergence.

**Verify and fix** is the default mode. Later rounds first ask the Session to
verify and fix the previous findings, then run a new panel. The prefilled,
editable cap is **3 rounds**: at most three panels and two verify turns.
**Verify only** uses one panel and asks the Session to verify remaining findings
without fixing them. The default focus is “Review the changes made in this
session.”

The optional Judge is off by default. When enabled, it rules on disputed findings;
its verdicts must be written to the canonical review comments before the
convergence check reads them. Pending user input delays the next Session verify
turn under the same admission ordering as Keep going.

If the round cap is reached without convergence, **Review didn't converge**
sends **Notify me** and completes the Run. It does not hold for review or create
an Inbox item just because it exhausted its rounds. An unchanged-worktree skip
is allowed only when the final successful panel certified that exact fingerprint;
without certification it reviews again. A firing during an active Run leaves
at most one pending occurrence.

### Plan with a panel

Choose **Run now**, enter the planning request, and optionally select planner
engines. Selected engines plan read-only in parallel as detached background
runs. With no engines selected, the Planner role plans alone. The synthesis
contains a plan document and, when valid, a proposed Workflow; it holds for
your review. There is no additional opinion or Judge stage: synthesis explains
disagreements and open questions for you to decide.

**Use this plan** accepts the document. **Run it as a workflow** is available
only for a valid proposal and accepts the held result once the new Run is
admitted; cancelling the run composer leaves the hold open. **Edit the workflow
first** accepts the result as an editing handoff and opens a draft. The accepted
handoff records the started Run or editing intent so the originating Agent can
follow it. No origin Session is required to run this built-in.

### Open a pull request

Choose **Run now** and supply the base branch and title. The body defaults to an
empty string. The editable opinion question defaults to “Is this change ready
for a pull request? Check correctness, tests and risk.”

A read-only Second opinion checks the change first. Agreement proceeds to the
existing open-or-reuse PR Action in that same workspace. Disagreement or
uncertainty enters **Wait for you**: **Continue** opens the PR anyway, while
**Stop** cancels without opening one. Its final result is the PR Action's output.
When there is an origin Session, a successful open also records the Session↔PR
link; no origin is required to open the PR.

## JSON import and export (development source)

Choose **Import** in Workflows, or **Import JSON** in an editable definition.
Use **Export JSON** from the definition's menu. Export confirms that prompts,
references, and result schemas may contain private information before saving
the file. These are authored definitions, not Run backups: machine placement,
local file handles, credentials, checkpoints, and resume state are excluded.
Choose the execution machine and workspace when you run the imported definition.

The strict JSON wrapper uses `kind: "happier.workflow"` and `version: 1`; the
nested definition has its own `version: 1`. For example, this portable definition
contains one Wait-for-you step:

```json
{
  "kind": "happier.workflow",
  "version": 1,
  "definition": {
    "version": 1,
    "defaults": {},
    "inputs": [],
    "blocks": [
      {
        "kind": "wait",
        "id": "confirm",
        "document": {
          "text": "Review the work, then continue.",
          "references": [],
          "attachments": []
        }
      }
    ]
  }
}
```

Import opens an unsaved review draft and never saves, schedules, or runs it.
Malformed JSON, unknown versions, and invalid wrapper shapes are refused,
preserving the open draft. A structurally readable definition with semantic
errors can open as a repair draft with issues pointing to the affected fields.
Resolve those issues before saving, exporting, or running it. YAML is not supported.

## Concurrency and run history

Each machine runs up to four automation Runs at once by default. Change that
Account setting in Workflows' **Run settings** when the machine should take
more or less work concurrently.

Completed Run history is retained for 30 days by default. Turn on **Keep run
history forever** in the same settings screen to retain it indefinitely, unless
the self-hosted server operator has configured a shorter Automation retention
policy. This setting controls the server-owned history lifecycle; it is not a
second client-side cache.

Retained Automation detail screens also offer **Clear run history** in their
header menu. It removes only server-eligible terminal history for that
Automation, not active work.

Every automatic Run records the stable trigger identity and revision plus an
immutable bounded cause. Editing or removing the current trigger therefore does
not rewrite what historical Runs say happened.

Deleting or disabling an Automation stops future admission; a Run admitted
before that change keeps its frozen recipe and assignments and continues
through the normal Run lifecycle.
