Some work is worth doing on a timer rather than when you remember it: a nightly
dependency check, a Monday-morning triage pass, a recurring prompt against a
repository you watch. Workflows run that work on your machines without you
opening the app.

<Callout type="warn">
  The Workflow instructions below describe current 0.3 development source,
  not certified stable or preview availability. Use matching development
  components. In that source, the **Workflows** preference has graduated: it
  defaults on and does not require **Experiments**. The server still needs the
  single `workflows` feature gate; a missing or disabled canonical server bit
  keeps execution unavailable. Released `automations` configuration names are
  compatibility aliases, not a second switch.
</Callout>

A current client hides Workflows when connected to a 0.2 Home: that Home's
released `automations` bit does not advertise the `/v3` API required by the 0.3
Workflow surfaces. Use a matching 0.3 development Home for this guide.

**Workflow** is the UI name for reusable work, replacing **Automation**. A
trigger is a setting on a Workflow that chooses when it starts, rather than a
separate kind of work. Existing API and configuration names can still contain
`automation` for compatibility.

Open **Workflows** from the app's navigation. This is the one destination for
definitions, their triggers, built-ins, and Runs. Choose **New workflow**, write
its first prompt, select where it runs, and save explicitly. **Run now** opens
the run composer to review the inputs and target before starting. **Run settings**
in this destination controls capacity and retention.

Before **Start**, the Run composer identifies the selected shared Machine and
who owns it. Check that disclosure before sending your work and sign-in there.

In unreleased 0.3 development, you can also choose a Machine shared with you
with **Can use** access for a Workflow or schedule. The review explains that
your full Happier sign-in is stored on that Machine: for a direct Run, while it
runs; for a schedule, while its trigger exists. Disabling or deleting the trigger
retires the sign-in after admitted Runs finish. People with terminal or Agent
access there may use it to access your Account; read the
[Machine-sharing disclosure](/accounts/session-sharing) before continuing.

Choose your own Connected Account credentials for the Agent. The Machine owner's
profile and native login are refused with a typed message; select a profile in
your own Account and update the Workflow's Connected Account selection. Machine
access does not give its owner server access to your private Runs or give you
access to theirs. Revocation refuses the next Run or scheduled occurrence while
admitted Runs can finish. If the Machine loses your saved sign-in context, the
typed refusal asks you to re-save the schedule on that Machine, or start a direct
Run again.

In current development source, saving an unchanged workflow writes nothing and
keeps its saved revision. **Discard changes** on a saved workflow restores its
saved version immediately, with **Undo** available; it does not ask for another
confirmation. Discarding a new, unsaved workflow still asks before losing it.
Your own in-flow confirmation supplies the approval for that operation; an
explicit **Ask first** preference still applies.

In unreleased 0.3 development source, the editor's **Settings** opens on desktop
and phone. Remembering your personal project target is best effort: if that
memory is unavailable or cannot be written, it does not block Save or its
trigger changes.

In unreleased 0.3 source, a step's Agent/model control opens the shared model
picker. Its heading is **Model**, without a separate **Effective** row. For
Agents that expose Thinking, larger or long-labelled choice sets use a select;
short sets can use segments. The choices come from the selected Agent and model.

Existing scheduled recipes created by released 0.2 clients remain readable.
Current 0.3 development source converts them to saved-step Workflows through the canonical
trigger reader, with the retained encrypted case requiring your review below.
Current clients use the V3 Automation transport; this data compatibility does
not require a V2 route.

In current 0.3 development source, an older encrypted Workflow attached to an
encrypted Session on a now-plain Account pauses as **Needs your review** in
Workflows. Open its trigger to review it on a device that still has the old
encryption key. Opening does not save or run it. **Save** stores the reviewed
workflow without end-to-end encryption and resumes its enabled triggers; the
Session itself stays end-to-end encrypted. If the key is unavailable or review
fails, the Workflow stays paused.

In current 0.3 development source, an Agent can also request this conversion
through the existing Workflow trigger Action, including from MCP or the CLI.
The request presents the reviewed Workflow and project for your approval.
Conversion runs only after you approve that exact request; **Always allow**
cannot bypass this confirmation. A denied request leaves the Workflow
unchanged. If the reviewed revision has changed, review it again before
requesting conversion. Automatic recovery does not confirm conversion for you.

### Create or edit with an Agent

In current 0.3 development source, **Create with an agent** opens a focused
sheet containing the ordinary New Session composer. **Edit with an agent**
keeps that composer in the editor's **Agent** tab beside **Settings** on wide
layouts. These are presentations of the same editable draft, not separate
Agent launchers. Review the visible request and normal launch options; only
your explicit **Send** starts the authoring Session.

Opening authoring neither saves nor runs the Workflow. Validation and saving
use the normal Workflow Actions after Send; editing operates on the saved
revision, not your local unsaved draft. Starting the Workflow is a separate
explicit Run action.

### Try a saved workflow in place

In current 0.3 development source, **Test run** runs the saved version for real
after you review its inputs and target. It does not save or run your unsaved
edits, and keeps the editor open. Step cards show the latest recorded occurrence's
status, output preview, and elapsed interval from creation to last update,
including admission and waiting. This is not execution-only time. Open the step's
details to review the full retained result or respond when the run needs you.

In current 0.3 development source, a finished Run's producing step shows its
final output. A Session started without a launch profile can be reused by a
Workflow that also selects no profile; a different named profile still needs
correction.

If **Start** is refused, open **Technical details** beside the failure for its
**Failure code** and, when supplied, **Cause**. If an Agent step cannot start,
an unavailable Connected Account profile can report
`connected_service_auth_group_authority_active_profile_missing`: choose a profile
in your own Account and update the Workflow before a new Run. A missing
credential requires reconnecting your own Connected Account.
After Machine access is revoked, choose another Machine or ask its owner to
restore access; a new Start can report `target_unavailable`. Revocation also
refuses the next Machine read. Your own private Run history remains yours.

**Start from an example** includes recipes to notify you when an agent waits,
send a daily summary into a selected session, create a worktree and install
dependencies there, or run tests after a selected session's turns. Review the
editable commands, session, and trigger before saving; choosing a template
alone does not start work.

Between ordered steps, **Run when** chooses **Success** (the default), **Failure**,
or **Always**, relative to the preceding step in that sequence. You set it in the
step's **Step options**; the editor names a step's edge above it only when it is not
the default ("If it fails", "Either way"). A failure handler
does not erase the failed step. Cancellation, an uncertain outcome, or a step
waiting for your input is not a definitive failure and does not start a handler.

## Run a collaboration pattern (development source)

In current 0.3 development source, **Run…** in a Session or Discussion composer
opens the same Workflow picker and typed inputs. Choose Fresh opinions,
Answer + review, Debate, Plan with a panel, Review & converge, or an accessible
saved or plugin Workflow. Review the question, participants, roles and target
before starting. Browsing choices does not create a participant Session.

A participant can be an existing Session or a model choice. Existing Sessions
keep their selected Agent and model; model choices use the ordinary Session
startup path and may require an invitation approval. Discussion references
remain scoped to their Home and Discussion, and access is checked before their
content is read or a result is posted. A supplied context boundary does not
erase an existing native Agent conversation's earlier history.

The inline Run band opens the exact Run. Available Pause, Resume and Stop
controls use its normal control Actions; a requested stop is not yet a settled
stop. Accepted answers appear independently, with their source attribution.
Answer + review attaches the review to the exact answer. Failed or stopped
work remains distinguishable from an answer or an explicit pass.

After Fresh opinions, Debate or Panel ends, **Another round** starts a new Run
with the same participants and authorized previous-round context. It leaves
the earlier results intact. If a start response is lost, the client reconciles
that same Run rather than starting another one.

### Save an exchange as a pattern

Use **Save as pattern** on a finished exchange or select the messages to capture
from its Discussion. Review each selected message's role, dependency,
instruction and per-run inputs. Unlinked or ambiguous messages need an explicit
choice before opening the editor; unrelated messages are not copied.

**Open editor** creates an editable, unsaved ordinary Workflow. Review and Save
it, then choose it from either composer with a new question or participant
choices. Capture alone does not save, share or start work. Cancel and failed
capture retain the review state so you can repair it. Existing Session
**Make this repeatable** remains an editable, unsent authoring request.

Plugin authors contribute these definitions through the existing Workflow
contribution and use the same typed Actions for start, controls, capture and
save. The [SDK and Action API](/extending/sdk#workflow-actions-development-source)
describes that public boundary. These are development-source contracts;
loaded-runtime and whole-page validation are separate from source availability.

## Roles for this run

In 0.3 development, a workflow whose steps select roles offers **Roles for
this run** in its Run now composer. Change the Agent/model or whether the
role runs in a session or background run, then review before starting.
**Use your role** removes the run-local choice. A test or rehearsal is a real
execution, not a simulation. The accepted run freezes the resolved choices;
later Account or workflow edits do not rewrite them.

`workflow.run.start` accepts these choices as `roleOverrides`; the shared
role resolver applies them above workflow pins, session choices and Account
defaults, per field. Read [Roles](/agents/roles#roles-for-this-run) for precedence,
repeat behavior and effort-picker limits. Other workflow tasks use
`workflow.definition.*`, `workflow.trigger.*`, `session.trigger.*` and
`workflow.run.*` through the same Actions front door. See the
[host Action reference](/plugins/api/host-actions) for their exact schemas,
approval requirements and surfaces. A successful start is admission of a
run; observe that run before claiming its work completed.

Cancel a queued or started Run through its normal cancel control. UI, CLI,
MCP and Agent callers all use `workflow.run.cancel`. Cancelling keeps the Run's
record, and you can start another Run from the recipe. It asks for approval
only when the Action policy says **Ask first**; there is no additional destructive
confirmation. A started Run may show cancellation requested while its work stops.

## One recipe, several ways to start it

A saved Workflow holds a reusable definition. Attaching triggers makes it
automated: each trigger set keeps its machine assignments and either references
that saved Workflow or contains an inline prompt or Action. A referenced
Workflow is read when the daemon claims the occurrence, so saving a change
changes what future claims execute. An admitted Run keeps its frozen definition.
It can start a new Session, continue an existing Session, or run detached work,
depending on the authored target.

For Workflows backed by saved definitions in current 0.3 development source,
**Runs in: existing session** writes into
that conversation rather than starting another Agent. These writes do not use
machine start capacity, whether the Workflow belongs to the Account or is
attached to a Session. Session-attached triggers keep their Session scope.
Run queries can select the destination Session separately from the Session that
started the Run; both kinds of Workflow use that same destination relation.

### See scheduled work in a Session

In unreleased 0.3 development source, open the Session's **Info** page and its
**Habits** section for the schedule, next occurrence, last known Run status,
**History**, **Run now**, and the on/off switch. History uses the same Run rows
as Workflows. Run now is separate from resuming the automatic schedule.

In current development source, **Last run** means the latest Run that actually
started, whatever its outcome. A Run cancelled or skipped before starting does
not replace it. Those unstarted Runs remain visible in history.

**Writes here** lists active Runs by their accepted destination, even when
another Session started them, alongside enabled schedules targeting this
Session. Active rows identify this Session's writers as **step N · title**, show
the overall Run progress and status, and open the Run to inspect individual step
outcomes. A completed iteration is not a claim that a repeating step has finished
all its work. A visible working row also shows the existing live workflow map. Step numbers match
the editor and Run map, including steps inside containers; nested workflows use
their own numbering. The global **Work**
sidebar has a **Scheduled** group with destination links. A pending next
occurrence stays visible rather than being assigned a guessed time.
Upcoming occurrence rows open their existing trigger or workflow, showing the
schedule and what will run. Running and finished occurrences open their Run.

Workflow-injected transcript messages link to their Run. When the authorized
Run title and authored step number are available, the chip reads
**From workflow · step N**. Opening a transcript batches missing facts without
replacing its visible messages; an unavailable number is not guessed from event order.
Public snapshot transcripts do not consult private Account Run content.

**Only if the agent reported something** is part of a **Notify me** step's
**Only run when** in its **Step options**, not a separate setting. It reads the
step's condition: it is on whenever that condition requires an earlier Agent step
to have reported something (its text result is not empty, or one of its named
results is Yes), and turning it off removes exactly those parts. Turning it on
adds the non-empty-result condition when the message is bound to a reachable
earlier Agent step's whole text result; other authored conditions are kept. It
cannot be turned on for a literal message, a JSON result, or a result that is not
reachable from that Action.

The same Workflow can own no automatic triggers, one trigger, or several.
Every enabled trigger is independent: if any one of them fires, the recipe
runs. There is no ordering or requirement that several triggers fire together.
An admitted Run keeps the recipe and assignments resolved for it; later edits
do not rewrite that Run.

An enabled Workflow must keep at least one enabled machine assignment — a
Run freezes the assignments it was admitted with, so a Run with no machine
could never start. You can save a paused draft with no assignments and assign
machines before enabling it; removing or disabling the last enabled assignment
of a running Workflow is refused until you pause it first.

## What can trigger one

A timer is only one of three automatic sources that can start a Workflow.

| Trigger | What starts the run |
| --- | --- |
| **Schedule** | A one-time date and time, a cron expression, or an interval. |
| **Plugin event** | Something a plugin observed — a new issue, a push, a review request. |
| **Session turn finished** | Completion of the exact active parent turn selected while authoring. |

**Run now is an operation, not a trigger.** A Workflow with no automatic
triggers can still run when you choose **Run now**, invoke it from the CLI, or
admit an authorized bound conversation.

### Schedule

A schedule can run once at a date and time, repeat at an interval — every *n*
minutes — or use a cron expression, with presets for the common cases
(**Every hour**, **Daily midnight**). Cron
schedules run against a timezone you set, so a "daily at midnight" workflow
means midnight where you are rather than wherever the machine thinks it is.

In unreleased 0.3 development source, a one-time schedule saves one absolute
instant. Choose a date and time, or enter a relative delay such as **in 20 min**;
the delay is resolved when you confirm the trigger. Save the Workflow to keep
the schedule. You can edit or cancel it before it is due.
After its occurrence, the schedule shows **Done** and stays available with its
Run history. If its target Machine is offline when it is due, History records
the occurrence as **Missed** with that reason. Reconnecting the Machine does
not run that missed occurrence later; schedule another time or use **Run now**.
If processing was delayed and later reconnects have erased the Machine's
presence at the scheduled time, the occurrence is also marked **Missed**, with
a reason explaining that the due-time presence is unavailable.

### Plugin events

This is the one that makes workflows more than a scheduler. A plugin declares
events it can observe, and a workflow binds to one — so a GitHub repository
event can start a session on your machine without you or a timer involved.

The GitHub plugin exposes semantic events for a repository push, an issue being
opened, a pull request being opened, and a pull request being merged. Polling
and webhook delivery normalize into those same event identities, so changing
the observation transport does not change what the Workflow means.

In current 0.3 development source, choose **Plugin event** under a trigger's
**When**, then **Set up event**. Search by the event's name or exact event ID;
each result shows both. The plugin's current setup form collects the source,
and you can then adjust its filter and maximum observation age before saving.

An existing Run detail with readable event evidence also offers **Create a
trigger from this event**. This preselects the event, not its private source
configuration: choose **Runs on** and set up the source normally. **Test this
trigger** checks the configured draft against that retained observation's
event identity, source, filter, and observation age. It reports whether the
event matches without replaying the event, saving the draft, or starting a Run.

An event trigger is observed in one of three ways, and the difference matters
operationally:

- **Checkpointed pull** — a watcher materialized on a specific machine polls
  the source and records a checkpoint as it goes. It needs that machine to be
  up; when it comes back, the checkpoint tells it where to resume without
  re-processing earlier occurrences. If the upstream source no longer offers
  the missed range, Happier reports a history gap for that exact trigger so you
  can recover it explicitly.
- **Durable push** — the source calls a webhook endpoint Happier owns.
  Delivery does not depend on one of your machines being awake, and the
  endpoint records the moment observation started so earlier events are not
  replayed at you. This transport is a Developer Preview and best effort
  until a delivery is durably committed: one that arrives while Happier
  cannot commit it is not held or retried, and GitHub does not redeliver on
  its own. When a missed occurrence matters, choose checkpointed pull.
- **Live socket** — a provider connection such as Discord Gateway observes
  events while its machine is connected. Happier resumes the provider session
  when the provider permits it; if that session cannot be resumed, the trigger
  reports a history gap instead of pretending the missed interval was observed.

#### Setting up durable push

Pick **Webhook** when the composer offers the choice, then configure the source
as usual. Happier creates the endpoint for you and shows two values:

- a **payload URL** on your Happier server, and
- a **secret**, shown once and never again.

Nothing arrives until you add that webhook at the source yourself. In GitHub,
open the repository or organization settings, select **Webhooks**, then choose
**Add webhook**. Paste the payload URL, paste the secret into **Secret**, set the content type to
`application/json`, and choose the events you want. Happier verifies every
delivery against that secret. A mistyped secret rejects the delivery; check
GitHub's delivery response when nothing appears in Happier.

Happier does not create the webhook for you and does not need a GitHub App: a
plain repository or organization webhook is the whole setup.

#### Verify delivery, then verify the Run

Save and enable the Workflow trigger before generating an event you expect to
start a Run. Keep its selected Machine and GitHub plugin available. The steps
below describe the current 0.3 development path; webhook ingress also requires
the server's `plugins.webhooks` feature and its `plugins` dependency.

1. In GitHub, open the configured webhook's **Recent deliveries**. Inspect the
   initial `ping`, or choose a recent delivery's GUID and **Redeliver**. These
   controls and permissions are described in
   [GitHub's redelivery instructions](https://docs.github.com/en/webhooks/testing-and-troubleshooting-webhooks/redelivering-webhooks).
   An empty `202 Accepted` response means Happier verified and durably accepted
   the delivery, not that a Workflow started.
2. Return to the event setup form and choose **Recheck webhook**. This reads the
   existing endpoint readiness. You can also open **Settings → Plugins → Plugin
   webhooks**, in the Plugins developer links, and find the endpoint by its id
   and source. Its status includes readiness, the exact Machine/plugin target,
   and queue counts. `providerConfirmationRequired` means no delivery signed
   with the current secret has been committed yet; `ready` confirms that
   delivery and a currently available binding. `routeUnavailable` or
   `targetUnavailable` needs endpoint or target recovery, rather than repeated
   GitHub setup. Readiness alone does not prove a matching event or a Run.
3. Generate a fresh event of the kind the saved trigger observes. For example,
   open an issue in the configured repository for an issue-opened trigger, with
   **Issues** selected in GitHub's webhook events. GitHub's `ping` checks the
   delivery path but does not start that Workflow. A delivery for another event
   kind or repository, or one excluded by the trigger's filter or maximum
   observation age, also need not start a Run.
4. Open the Workflow's Run history and the resulting Run. Inspect its cause,
   trigger identity, source, event reference, and occurrence key. Where private
   event evidence is readable, compare its source, event time, and payload
   (for example, the issue number) with the GitHub delivery. The occurrence key
   is an opaque digest, not GitHub's delivery GUID; keep the
   `X-GitHub-Delivery` GUID in GitHub's delivery details for provider-side
   troubleshooting. Follow the
   linked Workflow Run or Session to inspect execution and results; admission
   is separate from successful execution.

Where the Run retains readable event evidence, **Test this trigger** checks a
draft against that observation without starting another Run. It does not send
a provider test. Redelivering an already admitted occurrence should not create
a second Run for the same trigger; use a fresh matching event when checking
first execution.

If GitHub shows a failed response, correct its URL or secret and request
redelivery there. If delivery was accepted but processing fails, use **Plugin
webhooks** to inspect queue counts and dead-letter metadata. **Replay delivery**
retries a retained dead letter after you address its failure; it cannot recover
a request Happier never committed. Delivery bodies are not shown on that screen.

#### Recover a lost signing secret

The original secret cannot be read again. In **Settings → Plugins → Plugin
webhooks**, find the same endpoint and choose **Rotate signing credential**.
Save the new secret from **Save the new signing secret** before closing the
message, then replace **Secret** on the existing GitHub webhook and save it.
Keep its payload URL and the Workflow unchanged.

Rotation clears provider confirmation. Send a fresh matching GitHub event or
request redelivery, then recheck until the endpoint reports `ready` under the
new secret. **Finish credential rotation** stops accepting the previous secret;
use it after confirming the provider uses the replacement. If the new one-time
disclosure is lost too, rotate again rather than creating another Workflow.

#### When missed events matter

Two limits matter before you rely on webhook delivery. Happier holds a
delivery durably only after it has verified and committed it, so a delivery
lost in that window is gone unless the source sends it again — and GitHub
never resends on its own; a redelivery happens only when you request one for
that specific delivery, to the same URL. And when completeness matters more
than latency, checkpointed pull is the transport that records a cursor as it
goes and reports a history gap when a missed range is no longer available.
Choose **Poll for changes** in the event setup form for checkpointed pull and
keep its selected watcher Machine available. Its saved checkpoint supports
catch-up after an outage while GitHub still retains the missed history; a
history gap needs explicit recovery. Switching transports is not proof that
earlier missed webhook deliveries have been recovered. Verify the resulting
Run/event evidence for the occurrences you need.

An event trigger can also carry a **filter**, and a maximum observation age —
past which an event is considered too old to act on rather than triggering a
run late.

Plugins may optionally replace the generic setup form with their own setup
surface. That surface only collects the same strict setup input; Happier still
owns the trigger, admission, deduplication, and Run history.

### Session lifecycle events

A Session lifecycle trigger can react when a parent turn completes
successfully, fails, is cancelled or stopped, or needs your attention. Select
one or more of those events, then choose how long the trigger remains active:

- **Current turn only** binds to the exact active parent turn and can run once.
- **First matching event** waits for the first selected event in that Session.
- **Next matches** runs for the number of matching occurrences you choose.
- **Every matching event** keeps running while the trigger and Workflow are
  enabled.

From a Session, open **Habits** on its Info page to attach a scoped trigger.
The **When this turn finishes…** shortcut preselects the active turn. If that
turn changes before you save a current-turn trigger, the editor asks you to
use the new current turn instead.

Happier records each occurrence by its durable Session, turn, and request
identity. Earlier events are not backfilled, reconnecting does not create a
duplicate Run, and pausing or deleting the trigger prevents future matches.
The server remains the authority, so closing the app or taking a machine
offline does not move matching into a client-side watcher.

<Callout type="warn">
  Session-scoped Workflow triggers are development-only, not a shipped stable
  or preview feature. In current development source, a user or another Session's
  turn can fire a turn-end trigger; host and Workflow turns do not. A request for
  your attention still fires during those turns. Archive triggers fire only when
  the Session changes from unarchived to archived.

  Each scoped trigger keeps at most one active Run and one pending occurrence.
  A newer pending occurrence replaces the older one, whose history records it
  as skipped. Review Workflows can opt into skipping an unchanged worktree, but
  only when the previous successful Run's final review panel certified the same
  fingerprint. Missing certification always runs the review. Deleting the
  Session retires its scoped Workflows without removing retained Run history.

  Session-start attachment is not yet complete.
  Keep going attachment is refused when the opened Agent already owns native
  goal continuation. The Goal control reports a conflict if an existing Keep
  going attachment meets native goal ownership; automatic reopening cleanup
  is not established by the current source.
</Callout>

In current development source, the Session's Habits section offers PR comments
and CI failures. Choose a pull request from the Session repository; a single
existing link is preselected. Attaching either kind records that Session↔PR link.
Opening or reusing a pull request through Happier also records the link when the
operation has an origin Session. Removing a trigger retains the link but stops
that trigger's conversation ingress.

If the Session's pull request links cannot be read, ordinary scoped triggers
remain available. The Habits section shows a separate link-read warning with
a retry action; a failed read is not treated as an empty list of links.

PR comments admit only repository writers. CI observations require the selected
GitHub integration principal's write access. Unknown permission or a mismatched
identity admits no Run, for both plain and E2EE Accounts. Comment text is labelled
as untrusted input. This PR/CI vertical has owner-level tests; current loaded-stack
validation is still pending and it is not a shipped stable or preview feature.

For plugin authors using 0.3 development builds, the separate
`@happier/runtime/turn-start`, `@happier/runtime/turn-complete`,
`@happier/runtime/turn-failed`, and `@happier/runtime/turn-cancelled` Host Event
hooks are daemon-local, in-memory, best-effort notifications. They are not
replayed and do not create Workflow Runs. Durable lifecycle triggers are
admitted from persisted Session settlement and minimal pending-request
identity instead.

### Conversation bindings

A channel can bind a conversation to an existing workflow. A message admitted
through that binding starts a Run with an immutable conversation cause. The
binding is an invocation path, not another automatic trigger row.

### Active and paused

Each Workflow is **Active** or **Paused**, and each automatic trigger can also
be enabled independently. Pausing the Workflow keeps its recipe and every
trigger but prevents all automatic admission. Disabling one trigger leaves its
siblings active.

## Running one now

For a Workflow, **Run now** starts the reviewed definition directly, without
waiting for a trigger. Retained 0.2 Workflows also support an explicit manual
Run through the CLI below.

It does not create a durable Manual trigger and does not require the Workflow
to have any automatic trigger rows.

It queues rather than executing synchronously: the assigned daemon picks it up
when it is available. If the machine is asleep, the run waits rather than
failing.

From a terminal:

```bash
happier automation list [--cursor <opaque>] [--json]
happier automation run <automation-id> [--idempotency-key <key>] [--json]
```

Use `automation list` to find the retained workflow's stable `automationId` accepted by `run`.
Human output includes each ID, name, and active or paused state. `--json`
returns the structured definition-list page, including its continuation cursor
when more Workflows are available. To continue, pass that cursor back without
changing it:

```bash
happier automation list --cursor <opaque>
```

Pass `--idempotency-key` when the caller might retry — a repeated key will not
run the workflow twice.

## Structured workflows (development source)

A Workflow is a JSON-compatible program that can be started directly, referenced
by a trigger, or authored inline in a trigger. A direct Run has its own Account-scoped identity and does
not create a hidden Session or saved Workflow. A triggered Run also keeps its
immutable trigger cause. Editing or deleting a saved definition does not rewrite
an admitted Run. A managed Run is executable from its frozen snapshot; observed
Agent activity is read-only history and cannot be run, edited, or saved without
a managed definition. Trigger claims resolve the current saved definition;
later edits never change an accepted snapshot.

Definitions have four leaf kinds:

- **Agent** sends a prompt and receives a declared text, JSON, or decision result.
  Each step can run in a Session or as a background run.
- **Action** invokes one declared host or plugin Action with typed input bindings.
  An Action that declares execution-run completion waits for those Runs and uses
  its terminal result.
- **Run a workflow** executes another definition as an inline nested frame in
  the same Run. Its inputs and child definition are frozen at admission.
- **Wait for you** waits for a human response without starting an Agent. If it
  declares a result contract, the response must satisfy it.

In current 0.3 development source, **Call a webhook** and **Run a command** are
presets of the same Action leaf, also available through Action discovery and MCP.
The webhook posts JSON from typed bindings, sends a run/step/attempt idempotency
key, and retains the response body and status. A status of 300 or higher fails
the step without following a redirect. Authored URLs may use HTTP or HTTPS.
It shares the notification webhook's SSRF and pinned-address owner: explicitly
named local destinations are permitted, while metadata addresses or
public-looking names that resolve to private addresses are refused. Automatic
Activity notifications retain their public-destination HTTPS requirement.

A command runs on the Run's Machine in the step workspace, with the Machine's
normal user permissions. Write shell syntax as literal text and pass dynamic
values through the `env` field; reference those variables using your shell's
syntax. Input or event values cannot become command text. The result retains
`exitCode`, `stdout`, and `stderr`, including output from a failed command.
Stopping the Run retains any definitive command response already returned.
These are trusted-user operations, not a sandbox, and add no default step
deadline. Command output tails fit the existing stored-envelope capacity,
including encryption and other step data, rather than a new per-stream quota.
`stdoutTruncated` and `stderrTruncated` indicate when a prefix was omitted;
small output stays unchanged. Integrated validation of this correction is pending.

In unreleased 0.3 development source, each block can have its own optional name,
separate from its prompt, Role or selected Action. Rename it inline in the block
heading; **Undo** and **Redo** use the same draft history as other edits. Blank
names use the existing derived label. The authored name appears in the editor,
read-only cards, Flow/Map and Run rows. A fresh Session for a named step starts
with the title `{ordinal} · {step name}`, with ` · {item}` added for per-item
work; the ordinal matches the step heading. Steps are numbered 1, 2, 3 … in the
order they run, across lanes, loops and conditions; Side by side, Repeat and If
groups are unnumbered and show their kind instead. A nested workflow numbers its
own steps. Unnamed steps use normal Session
naming. Changing a step name does not rename existing Sessions, and a later
Session rename by you is preserved.

Each lane of a parallel group can be named the same way: rename it in place on
its caption in the editor. An unnamed lane reads "Lane 1", "Lane 2" and so on,
and the name also captions the lane in Flow/Map.

Parallel groups, conditions, and loops arrange those leaves. References select
declared inputs and earlier invocation
results structurally. Happier does not interpolate `${...}`-style text or parse
prose as control flow. Pass dynamic values as declared inputs or typed references.

In current development source, a direct Run started by an Agent returns updates
to its originating Session by default; a Run started by a person opts in. The
Session reads the latest committed Run state and result as worker context, not
as a new user message. A finished Run does not stay unfinished while waiting for
the Session to consume its result.

A scoped Workflow also uses its bound Session as the Workflow origin. In
development source, returning results to that Session is opt-in on the trigger;
keeping an origin for steps or context does not enable result return by itself.

A step can choose `origin_session` to work in the Session that started the Run.
It waits behind user input and is checked again before dispatch, so a paused or
cancelled step cannot start from an old queued offer. This is separate from a
Channel conversation's reply handoff.

In development Workflow definitions, `until` and `evaluate` loops accept a
positive whole-number round limit or a reference to a declared number input.
The limit is fixed when the work is admitted. Reaching it completes the loop
with an `exhausted` outcome instead of failing the Run. Later steps can test
the recorded outcome without asking the Agent or rechecking a stop condition.

An evaluator declares `continue` and at least one finishing decision, such as
`done` or `stuck`. It may return the decision alone or an object containing
`decision` and an optional `reason`; the reason is retained. Other decision
steps can declare their own values without being loop evaluators.

An origin-context input includes the goal and recent turns. Its usage comes
from Happier's session accounting, not the Agent's native goal counter. Without
reported usage, a budget stop is unavailable; the authored round limit still
applies. To fit the 256 KiB prepared-input bound, Happier drops the oldest turns
and marks the context as truncated, but never truncates the goal. If that is
still too large, the step fails before sending input. A context binding requires
an originating Session.

Parallel groups and item loops may include `maxConcurrent` as a positive integer.
Omitting it means the Workflow adds no concurrency cap; the selected Session,
provider, and machine still enforce their own real limits. A Session step may
include `timeoutMs`. Omission adds no authored observation deadline. Expiry means
the Run needs attention; it does not prove the agent stopped or cancel its work.

The development CLI projects the canonical Actions directly:

```bash
hdev workflow validate --definition-json @workflow.json --json
hdev workflow run start --run-id <uuid> --source-json '{"kind":"inline","definition":{...}}' --machine-id <machine-id> --project-directory /path/to/project --json
hdev workflow run get --run-id <uuid> --json
hdev workflow run wait --run-id <uuid> --timeout-seconds 60 --json
hdev workflow run invocations list --run-id <uuid> --cursor <opaque> --json
```

Workflow commands use the same target routing as `hdev actions invoke`: select
an exact Home with `--server-id`, the machine with `--machine-id`, and its project
with `--project-directory`.
Add `--workspace-ref-id` when binding an exact workspace reference; it requires
both selectors. These options route the Action and are separate from its input.
For `workflow run list` and `workflow events list`, use `--action-machine-id`
to filter the returned rows independently of the execution machine.

Keep the caller-generated `runId` when admission is uncertain. Repeating it with
the same normalized request rejoins the Run; changing the definition, inputs,
saved revision, or target conflicts. A new ID intentionally starts a new Run.
In development Plan review, reopening after a lost start response rejoins a Run
only when its proposal matches the plan you are reviewing. If the Agent has
published a different proposal, Happier explains that an earlier proposal
already started and offers **Open that run** or **Run the new proposal**. Using
the new plan does not label the earlier Run as having started it.
Cursors are opaque and bound to the supplied filters, so return them unchanged.
Page sizes are preferences: response-byte limits can yield a shorter page and a
continuation cursor.

Pause prevents later work from being admitted while accepted work settles.
Cancel records durable intent but is not a receipt that an offline process
stopped. Recovery may reattach an owner-supported execution or require an
explicit same-conversation or fresh-agent continuation; ambiguous effects are
never silently replayed.

In unreleased 0.3 development source, an interrupted invocation's offered
fresh-agent retry can use its frozen original input. It does not rebuild that
input from later Workflow edits or conversation history. On daemon startup,
recovery also finishes a cancelled Run's remaining cleanup once child work and
required result publication have settled, without restarting completed work.

Saved definitions use Account Artifacts and whole-document revision checks. JSON
import/export preserves portable authored content only. Local file handles, raw
credentials, checkpoints, and provider resume state are not portable definition
data. YAML is not supported.

### Review and manual Pause

Turn on **Review before continuing** to hold a step's output before downstream
work can consume it. Inspect the displayed value, discuss changes in the step's
conversation, or edit the result yourself. **Use this result** commits that
value; **Generate result and continue** asks the existing Agent conversation for
a new result and continues automatically when it is valid. A failed generation
keeps the previous reviewable value available. A Wait-for-you step accepts a
human response and cannot generate one.

If an Agent publishes a newer result while you are editing, **Keep my edits**
acknowledges that publication while preserving your draft. In unreleased 0.3
development source, **Use this result** then accepts your draft as a human
answer. Another publication warns you again before acceptance; **Use newer**
replaces your draft with the newer result instead.

In unreleased 0.3 source, a human-accepted answer shows **Answered by** using
the authorized People profile for that Home. Your own answer reads **Answered by you**;
an unavailable profile stays anonymous. An Agent result is not attributed to
the person who started the Run.

Independent work can continue while a step awaits review. When only human holds
remain, the Run reads **Waiting for your review** and releases its worker slot;
**Review next** opens a held step. This review is separate from a tool permission
request and from recovery of an interrupted execution. Typing in a conversation
does not accept a held result.

**Pause at boundary** closes admission while accepted work settles. A manually
paused Run stays paused after **Use this result**. You can request generation
while paused, but it starts only after **Resume** and the worker's current
authority and continuation checks. **Stop** cancels the Run rather than accepting
its holds.

### Team visibility

Share a Workflow definition through its access controls. Recipients keep their
own triggers and choose Machines they own or, in unreleased 0.3 development,
have **Can use** access to. A personal definition share lets
the recipient use the Workflow but does not expose the owner's Runs.

A Run from a Team-shared Workflow freezes its visible Team when admitted. When
several Teams have access, choose which Team sees that Run. Visibility requires
current membership in that Team and a live grant on the source Workflow; removing
either removes access. There is no separate single-Run share.

People with **Can edit** or higher access can pause, resume, stop, and answer
review holds; view-only recipients cannot. Human answers record who answered.
E2EE content still requires the recipient's key envelope: a visible row with
unavailable keys stays locked.

In unreleased 0.3 development source, teammates can open a Team-visible
trigger's **History** from its schedule row. It includes only Runs visible to
that Team; the owner's private Runs stay excluded.

## Built-in workflows (development source)

Open the **Built-in** section of Workflows. Session-bound recipes offer
**Choose a session…**; the others offer **Run now**, with workspace and inputs
reviewed in the run composer. Built-in definitions are read-only; copy one into
an unsaved draft when you want to change its recipe.

### Keep going until done

In unreleased 0.3 source, Agents without native goal controls use a
Happier-owned goal. Goal controls also work for retained Sessions when their
Machine is reachable and supports Happier's goal controls.

Choose a Session and set its goal through the Goal control. Where the opened
Agent supports native goal continuation, the control uses that; otherwise it
attaches Keep going. A new Keep going attachment is refused when the Agent
already owns native goal continuation; an existing conflict is shown rather
than presenting a second continuation control.

In unreleased 0.3 source, Claude's native Goal updates publish into the same
Session Goal state through its native owner. They do not need a Keep going
attachment.

After a matching turn ends, a read-only Judge checks the goal and the latest
turn. It continues the Session, then checks again, until the goal is done, the
reported token budget is spent, there is no progress, or the round cap is reached.
The prefilled cap is **4 rounds** and the strike threshold is **3 consecutive
no-progress checks**; both are editable. Four rounds mean at most four checks
and three continuation turns. Without reported usage, the budget stop is
unavailable; the round and strike stops still apply.

**Ask for a second opinion before finishing** is off by default. When enabled,
only agreement marks the goal complete and removes its trigger. Disagreement
or uncertainty sends **Notify me**, leaves the goal and trigger active, and
completes the Run without a hold. Budget, strikes, and exhaustion also leave the
goal active. **Stopped after \{n\} rounds** is a successful exhaustion outcome,
not a failure; the Session transcript folds the continuation turns.

Pending user messages go before a continuation at its final admission check.
A message arriving after the step has passed that check follows the admitted
step; an already running turn is not interrupted.

### Review & converge

Choose a Session, open **Habits** on its **Info** page, and attach this recipe to a matching
turn-end event. Select the review engines. A panel reviews the changes in
parallel, then a read-only convergence check reads the persisted review comments
and each engine's outcome. Missing or failed coverage cannot count as convergence.

**Verify and fix** is the default mode. Later rounds first ask the Session to
verify and fix the previous findings, then run a new panel. The prefilled,
editable cap is **3 rounds**: at most three panels and two verify turns.
**Verify only** uses one panel and asks the Session to verify remaining findings
without fixing them. The default focus is “Review the changes made in this
session.”

The optional Judge is off by default. When enabled, it rules on disputed findings;
its verdicts must be written to the canonical review comments before the
convergence check reads them. Pending user input delays the next Session verify
turn under the same admission ordering as Keep going.

If the round cap is reached without convergence, **Review didn't converge**
sends **Notify me** and completes the Run. It does not hold for review or create
an Inbox item just because it exhausted its rounds. An unchanged-worktree skip
is allowed only when the final successful panel certified that exact fingerprint;
without certification it reviews again. A firing during an active Run leaves
at most one pending occurrence.

### Plan with a panel

Choose **Run now**, enter the planning request, and optionally select planner
engines. Selected engines plan read-only in parallel as detached background
runs. With no engines selected, the Planner role plans alone. The synthesis
contains a plan document and, when valid, a proposed Workflow; it holds for
your review. There is no additional opinion or Judge stage: synthesis explains
disagreements and open questions for you to decide.

**Use this plan** accepts the document. **Run it as a workflow** is available
only for a valid proposal and accepts the held result once the new Run is
admitted; cancelling the run composer leaves the hold open. **Edit the workflow
first** accepts the result as an editing handoff and opens a draft. The accepted
handoff records the started Run or editing intent so the originating Agent can
follow it. No origin Session is required to run this built-in.

### Open a pull request

Choose **Run now** and supply the base branch and title. The body defaults to an
empty string. The editable opinion question defaults to “Is this change ready
for a pull request? Check correctness, tests and risk.”

A read-only Second opinion checks the change first. Agreement proceeds to the
existing open-or-reuse PR Action in that same workspace. Disagreement or
uncertainty enters **Wait for you**: **Continue** opens the PR anyway, while
**Stop** cancels without opening one. Its final result is the PR Action's output.
When there is an origin Session, a successful open also records the Session↔PR
link; no origin is required to open the PR.

## JSON import and export (development source)

Choose **Import** in Workflows, or **Import JSON** in an editable definition.
Use **Export JSON** from the definition's menu. Export confirms that prompts,
references, and result schemas may contain private information before saving
the file. These are authored definitions, not Run backups: machine placement,
local file handles, credentials, checkpoints, and resume state are excluded.
Choose the execution machine and workspace when you run the imported definition.

The strict JSON wrapper uses `kind: "happier.workflow"` and `version: 1`; the
nested definition has its own `version: 1`. For example, this portable definition
contains one Wait-for-you step:

```json
{
  "kind": "happier.workflow",
  "version": 1,
  "definition": {
    "version": 1,
    "defaults": {},
    "inputs": [],
    "blocks": [
      {
        "kind": "wait",
        "id": "confirm",
        "document": {
          "text": "Review the work, then continue.",
          "references": [],
          "attachments": []
        }
      }
    ]
  }
}
```

Import opens an unsaved review draft and never saves, schedules, or runs it.
Malformed JSON, unknown versions, and invalid wrapper shapes are refused,
preserving the open draft. A structurally readable definition with semantic
errors can open as a repair draft with issues pointing to the affected fields.
Resolve those issues before saving, exporting, or running it. YAML is not supported.

## Concurrency and run history

Each machine runs up to four workflow Runs at once by default. Change that
Account setting in Workflows' **Run settings** when the machine should take
more or less work concurrently.

Completed Run history is retained for 30 days by default. Turn on **Keep run
history forever** in the same settings screen to retain it indefinitely, unless
the self-hosted server operator has configured a shorter Workflow retention
policy. Removing an Automation also deletes its past Runs when retention cleanup
runs, including Runs set to keep forever. The removal confirmation warns about
this before you confirm. This setting controls the server-owned history lifecycle;
it is not a second client-side cache.

Retained Workflow detail screens also offer **Clear run history** in their
header menu. It removes only server-eligible terminal history for that
Workflow, not active work.

Every automatic Run records the stable trigger identity and revision plus an
immutable bounded cause. Editing or removing the current trigger therefore does
not rewrite what historical Runs say happened.

In unreleased 0.3 development source, **History** in an Account schedule popover
or a saved Workflow's trigger row opens History filtered to that trigger.
Each occurrence's **Edited by** byline comes from the version accepted for that
Run, so later edits do not change its attribution.

Deleting or disabling a Workflow stops future admission; a Run admitted
before that change keeps its frozen recipe and assignments and continues
through the normal Run lifecycle.
