---
title: Deploy an app on your Machine
description: Create an Environment, deploy an app, add an address, and back up and restore its database.
---

Run an app on a Machine you control, then manage its deployment and database from Happier.
An **Environment** is one place a Project runs, such as staging or production.
It brings together what to run, the Machine that runs it, its variables, addresses,
and deployment history.

<Callout title="Development only · 0.3">
This walkthrough describes unreleased 0.3 development components. It is not a
stable-release guide. Your Home must enable deployments, your deployment feature
preference must be on, and your app and Machine
daemon must support these development flows. If the deployment controls are
unavailable, check with your Home operator before proceeding.
</Callout>

## Describe your app

In **Deploy an app**, choose **Describe your app** and write what you want to
build in your own words. Auto mode reads the current starters, catalog apps,
deployment targets, Stores, Machines, and available repository forges. It runs a
read-only suggestion task on an eligible Machine and Agent. If the setup needs
more information, the questions appear in the same step. Answer them to get
updated suggestions, or choose **Skip** if suggestions are already available.
You can also try again or choose a starter yourself. If no Machine has a ready
Agent, the step shows each Machine's reason and its available next action. If the
suggestion stops at a usage limit, choose another Agent for this attempt and
select **Try again**. Set the default separately under **Agent for app suggestions**
in Settings.

The returned setup cards are checked against that catalog before they are shown.
They identify what the app starts from, where it runs, and any selected data
store. Choose **Use this setup** after reviewing the card. Code-creating choices
then show **Code lives on** and the compatible forge choices in the creation
review. **Back** returns to the same cards without asking again.

Code-creating choices, including a starter or a scratch app, create the reviewed
repository, Source, and Project. The Project opens with a new Session draft.
Your description is ready to edit, and the reviewed setup is attached. You can
change the Agent or model before you send the message. The Agent
builds or customizes the app, runs its own validation scripts, creates a preview
Environment, and checks preview health. Review the preview URL and health before using the ordinary
**Deploy Production** action. Production remains your step.

If the selected catalog app shows **Needs review**, choose **Review** to open
its Store listing and see which template settings need attention.

Choices that already contain code continue directly to **Where it runs**. This
includes a catalog app and the existing repository, Docker image, and Compose
paths. Those paths continue through Details and Review without opening a build
Session. For a catalog app, fill in the addresses and variables its template
requires. Review becomes available once those inputs are complete.

Setup cards, **Where it runs**, and Review show each platform's declared plans:
the plan's price, its other facts, and the provider page and date they were
checked. When a connected Vercel or Cloudflare account reports a plan that matches
one of those declared plans, Review shows **Your plan**. Cards never show your
plan, because the account is chosen after Where it runs. If the account is not
connected or the provider's plan cannot be matched, the dated declared facts stay
visible without a personal plan line. These are reference facts for choosing a
setup, not a live quote.

## Connect Vercel for deployments

In unreleased 0.3 development source, connect Vercel by signing in through a
configured Home or by supplying a personal access token. Select the Vercel team
in Happier. When you choose an existing target, select the project to link.
For Sandbox creation, also select a project on the Connected Account. A
team-only Sandbox check returns `vercel_project_required` with an account link
to [choose a project](/plugins/services/auth-connected-services#choose-a-project-for-vercel-sandboxes).
Development QA exercised the existing-project picker and a signed-in static
deploy. The project-scoped consent and create-project refusal still need a
real-team release check.

## Deploy a GitHub app to Railway

In unreleased 0.3 development source, choose Railway in **Where it runs** to create a service from a
GitHub repository and branch or link an existing Railway service. Select your
Railway Connected Account, project, and environment, then choose an existing
service or create one. To start with a new project, choose **Create Railway project**
in the project picker, select a workspace, and approve the request. Happier
selects the new project and its default environment. Use **Create Railway
environment** in the environment picker to add another environment to that
project. Both Actions require approval for you and for agents. Railway billing
may apply.

When you create
a service, Railway builds the latest commit on the selected branch and
automatically deploys later pushes to that branch. On a linked service,
**Deploy** sends the exact commit you review. Push that commit to the configured
branch first and make sure Railway's GitHub connection can read the repository.
You can add a Railway-assigned address or a custom domain, manage variables, and
read build and runtime log snapshots. Railway creates the service in each
non-fork environment when you select a non-fork environment. Selecting a fork
keeps the service in that fork.

If a Railway-assigned address stays pending after you add it, copy the assigned
hostname from the linked service and environment in Railway. Open **Domains**,
choose **Check again** on the pending address, and enter that hostname. Happier
checks the address and saves it when it finds a match.

### Link a Railway managed database

Choose a Railway project and environment for a PostgreSQL or MySQL template.
After creation, inspect the exact service and confirm adoption before Happier
links it to the Environment. You can also adopt an existing database from
that environment. Workbench can list the linked database.

To read it in Workbench, [enable a TCP proxy for the database service in Railway](https://docs.railway.com/networking/tcp-proxy).
Happier doesn't turn it on for you, and
Workbench asks you to do it if it's off. Workbench then reaches the database
through Railway's public TCP proxy and asks for a read-only login: attach an
existing one from Saved Secrets, or review and create one with the database's
write login. The connection is always encrypted. Railway's database templates
use certificates from their own private authority that don't name the public
proxy, so Happier can't verify the server's identity. Workbench tells you this
when you review a read-only login or review staged changes before applying them.
Before you confirm **Delete** for a linked database, the review shows whether
Railway will remove the volume and its data. If other environments use it, the
review shows how many and links to it in Railway. If Happier cannot check the
volume during review, Railway will remove it only if no other environment uses
it. The receipt says whether the volume was removed or kept, and links to it
when other environments still use it. If Happier could not confirm volume
removal, the receipt directs you to check the volume in Railway.

Live validation of the Railway deployment and database journeys remains pending.

## What you need

- A signed-in Happier app and an online Machine connected to the same Home.
- Permission to manage the Project and deploy on the selected Machine.
- Docker Engine, Compose, and Buildx available to the daemon user on that Machine,
  including permission to access Docker. Buildx is needed even for image-only deployments.
- For a public address: a hostname you control and an ingress route. Direct public
  ingress needs ports 80 and 443 available to Happier's Caddy proxy; Tunnel ingress
  is the alternative when another proxy owns those ports.
- For the backup steps: a deployed PostgreSQL database, S3-compatible backup storage,
  and Saved Secrets for its access key ID, secret access key, and repository password.
  Keep the repository password available for recovery.

The backup and restore example below is PostgreSQL. Do not assume another
database has the same support merely because it appears in the Store.
MySQL backup and restore are not supported yet.

## 1. Set up the Machine

Follow [onboarding](/getting-started/onboarding) to connect the computer to your
Home. In the desktop app, use **Setup wizard** → **Set up this computer** for the
local computer, or **Add machine over SSH** from the Machines settings screen
for another computer.

Wait until the Machine is online before choosing it for deployment. On the
Machine, check that the daemon user can run `docker compose version` and
`docker buildx version`. If deployment preparation offers a Machine setup review,
read and apply the proposed setup before continuing.

## 2. Create and deploy an Environment

For a first deployment, open **Store**, choose an app, and review its installation.
Choose the Machine and either an existing Project or a new Project, then confirm
the reviewed installation. This creates an Environment and attempts its deployment.
Open the resulting Environment to see what completed.

If you already have a definition, open **Apps** in the Store and choose
**Paste a Compose file** or **Run an image**, then choose an existing Project or
**New project**. A new Project is created when you confirm Environment creation.
Supply the Compose document, or the image name and its container
port, then name the Environment and choose its Machine. Review creation before
confirming it, and use **Deploy** to review and run the deployment.

For a repository-backed Project, open its **Deployments** tab and choose
**Add environment**. Select the Machine, branch or ref, and Compose file path
(`compose.yaml` is the initial path). Save and confirm creation, then review
**Deploy**. The Project must first be saved as a Source; follow the page's prompt
if it is not.

If the repository has no Compose file, including a repository with only a
Dockerfile, choose **Prepare with an agent** in the Project's **Deployments**
tab. Choose a workspace checkout and continue in the resulting Session. The
agent prepares repository changes for review and a pull request, preserving
valid deployment files. Review the proposed validation and pull request before
merging, then return to create and deploy an Environment from the updated source.
The handoff itself does not deploy the app or merge the pull request for you.
Validation of the exact PR head needs its own review, using a non-production
Environment or a Dev Container. Inspect the validation operation and its receipt;
without a validation run, treat the proposal as unverified.

To start from another deployment tool, choose **Import from another tool** and
provide the tool name and configuration file paths. Continue the inspection and
mapping in the Session. Backups, data restoration, and moving traffic each need
their own review; starting an import leaves the existing app running.

### Pull request previews

Open **Settings → Previews** on the Environment you want to use as the template.
Choose the repository and base ref, controller, and the data and Domain options
for preview Environments. The source status shows whether the configured trigger
uses webhook delivery or checkpointed pull.

Review the proposed head before deploying changes from a fork. Fork previews
use their own data and bindings. A preview can start with an empty database
where the template offers that choice. See [Saved Secret bindings](/plugins/services/secrets)
for how integrations carry references into a later approved operation.

In **PRs & Issues**, open the pull request to see its preview, serving commit,
and deployment receipt. If publication fails, retry publication there. An
unavailable controller pauses new work until its Machine is reachable or you
choose another controller. Closing a pull request starts cleanup for the
preview's owned resources. If cleanup fails, open the child Environment to
inspect the recorded result and retry the remaining cleanup.

Check **History** for the deployment result. The **Overview** shows services and
health; use **Logs** to inspect build or runtime output. **Variables** holds
values, Saved Secret bindings, and references used by the Environment. Changes
to variables apply on the next deployment.

<Callout title="A partial installation can keep a working deployment">
A Store installation can create the Environment and deploy the app while its
Domain step fails. Read the completed steps and choose **Open environment**.
Resolve the address problem there instead of creating another copy of the app.
</Callout>

### Return to an earlier version

In unreleased 0.3, choose **Roll back** on a retained deployment. Check the
version you’re returning to, the version it replaces, and where it will run
before confirming. A code rollback keeps current data. If you select a
pre-migration backup on your own server, the review tells you that confirming
will replace the current data with that backup.

## Move a stored definition to Git

In the Environment's **Settings**, choose **Move to repository** and select a
checkout on a connected Machine. For a Project open only in a managed
workspace, open a checkout of the Project on a connected Machine first.
Review the file changes before opening the pull request. The Environment
keeps using its stored definition until you accept the merged version.

## Private service connections

To share a database privately in unreleased 0.3, open the source Environment's
**Settings** tab and find **Private sharing**. For a stored Compose definition
on one Machine, choose the service and TCP port, then choose how another app
will reach it.

- **Happier network** creates a loopback publication for Machine forwarding over
  Iroh. The Machines can be on separate networks. Docker chooses a free host
  port when you deploy. Set **Published host port** under **Advanced** to use a
  specific port.
- A joined private network publishes on the selected network address. Both
  Machines need access to that network. Enter a host port so Happier can open it
  in the Machine's firewall before the service starts.

Review and save the share, then deploy the source Environment. On the database
page, use **Connect to an app** to choose the destination Environment and save
the reference variable. Deploy the destination to apply the variable. An
automatic reference prefers an available shared network when the export offers
one, then uses Iroh when the export offers it. The deployment receipt records the
selected route.

The Iroh forwarding path for Compose containers targets native Linux Docker.
Two-Machine connectivity, recovery after a daemon restart, and refusal after
removing an export require separate live verification.

## Production telemetry in development

The unreleased telemetry integration connects an app that already exports
OpenTelemetry traces, logs and selected metrics to a Machine with the **Telemetry** role. It does
not instrument the app automatically. The collector stores telemetry on that
Machine. Captured SQL, traces, and log content stay on the collector. Happier
masks known secret patterns in logs. Expanded log text may still contain
secrets written by the app.

The initial deployment path uses the app's own Machine with native Linux Docker.
The receiver listens on localhost, and the deployment's private container bridge
connects the app to it. Docker Desktop and non-Linux container bridges are not
supported. Cross-Machine and platform collector routes are still being integrated;
do not treat a configured Environment as proof that such a route is reachable.

Metrics is off until selected for the Environment. App LLM cost and Exceptions
are separate choices in the same development setup; Regression uses an armed
Workflow. Project and Source defaults preselect new Environments without changing
existing ones. Turning Metrics off stops new metric batches at the next request
and leaves traces and logs available.

Each Environment has its own ingest token in a Saved Secret. The collector receives
its hash and the selected capabilities. Exporter configuration changes apply on
the next deployment. Rotation keeps the
previous token working until a successful deployment delivers its replacement.
Moving or turning off the collector requires confirmation and deletes that
Environment's telemetry from the previous collector, without copying it to the
new one. Redeploy afterward to start sending to the selected collector.

In the hosted 0.3 development flow, Telemetry shows when the configured
collector needs a deploy. After the provider acknowledges the exporter
configuration, the tab shows **Waiting for first data** until the collector has
retained a sample. Redeploy the app to apply the provider configuration.
**Receiving** shows the latest retained sample time.

In the 0.3 development flow, teammates who can view an Environment can read
its capture from the selected collector without a Machine grant. Withdrawing
Environment access takes effect on the next read request. When you save a
telemetry check, **Check from** uses the collector if it belongs to your Account.
If another Account owns the collector, the check runs on an available Machine
on your Account and reads the collector’s retained measurements. Connect one
of your Machines if **Add check** asks for one.
With end-to-end encryption, a read goes only to the collector that telemetry
setup recorded in the Environment. If that collector is reinstalled, or the
Environment's telemetry was set up before this check existed, reads stop with
a collector key error until you run telemetry setup again.

On a retained failing request in the **Telemetry** tab, choose **Automate** to
open a Workflow draft for that finding. The draft uses the
selected Environment and finding group. After you arm the Workflow, the
collector can deliver distinct findings from that group.

For suspected N+1 and other repeated-query findings, configure a database
finding trigger in Database Workbench. The collector delivers findings when its
Machine Account can resolve one matching database binding. Repeated requests with
the same normalized SQL shape on that binding count toward one finding. Each
shape on that binding can start the armed Workflow once. Other findings stay in
**Telemetry**.

If the collector no longer retains the exact trace cited in a finding brief,
verification reports that the trace is unavailable.

An Environment manager can choose **Clear capture** in the **Telemetry** tab
and confirm to delete that Environment's retained capture. New telemetry can
still arrive while the app continues exporting.

Under **Telemetry settings**, open **Trace sampling** and enter the percentage
of traces to keep. The change applies at the next deploy. Without an Environment
sampler, the SDK uses its default unless the app defines its own sampling.
For Compose services, declare `OTEL_TRACES_SAMPLER` and
`OTEL_TRACES_SAMPLER_ARG` without values to receive the setting. Values you
set explicitly in Compose take precedence at deployment.

If a Team Environment has no collector, **Deploy a collector next to your relay**
opens the collector App review in the same Project. Choose the Machine that will
run it and review the install.

An app's authored collector configuration takes precedence at
deployment. Telemetry reads and the Environment screens are still under
development; this section does not certify the complete telemetry journey.

Each enabled capability in **Telemetry settings** shows the time of its newest
retained sample on the selected collector. After a rotation or capability
change, that time may refer to a sample from before the change. Charts report
retained coverage for their selected time window.

### Verify backend exception capture

Select **Exceptions**, redeploy, and report a controlled server-side failure with
an OpenTelemetry `recordException` span event or a structured exception log.
Include the app's service name, version and deployment environment in the
OpenTelemetry resource attributes. In **PRs & Issues**, choose the Happier source
and open the new issue. Select an occurrence to read the stack from the
collector and check which version emitted it.

### Verify browser exception capture

Select **Exceptions** in the Environment's telemetry setup and redeploy so the
app receives its collector configuration. In 0.3 development builds, open the
Environment's **Telemetry** tab, then choose **Add telemetry to this app** from
the more menu. The editable Session brief includes code for browser errors and
unhandled promise rejections. Database Workbench offers the same setup brief
for a selected worktree.
Adapt it to your framework and route reports through your app's own server or
edge endpoint. Keep the collector credential in the server-side configuration.
A static-only app needs a server or edge endpoint, or an existing error
integration.

Exercise a controlled error and an unhandled rejection in a test deployment.
The Environment's **Telemetry** tab shows the open exception count. While it is
open, the collector updates the latest exception time. If the collector is
unavailable, the summary can show the last time recorded on the Account issue.
Choose **Open in PRs & Issues**, select the Happier source, and inspect the
issue's occurrence. The stack and raw occurrence stay on the collector.
Investigation of a minified stack needs the source map from the matching build.
After deploying a fix, repeat the failing interaction and
record which build and route you exercised.

### Check an endpoint with a Key flow

In **Telemetry → Metrics**, choose the service, version and time window to follow
the selected collector. HTTP duration and traffic, heap, garbage collection and
active requests appear when the app reports them.

Enable **Metrics**, redeploy, and send traffic through a route your app
instruments with OpenTelemetry. In the Environment's **Telemetry** tab, open
the route's menu under **Endpoints** and choose **Add a check…**. The editor
starts with the route and its collector. Name the check, set the measurement
window and threshold, then review **Check every** and **Alert after** before
saving.

Open the saved check in **Monitoring** to see its latest result. No recorded
traffic in the check's window means **Unknown**. A separate trend on the check
page reads measurements retained by the collector.

### View model usage from your apps

Enable **App LLM cost**, redeploy, and emit OpenTelemetry GenAI model and token
usage attributes from your app. In 0.3 development builds, open **Telemetry →
LLM calls** in the Environment to narrow the call list and totals by service,
version and time window. In **Usage**, open **Sources** and choose
**Your apps**, then narrow by app or **Environments**. This view shows app
activity separately from agent activity. Estimated cost uses the model prices
available to the signed-in viewer. Viewers sharing an Environment can see
different estimates for the same token usage. In 0.3 development builds,
a saved spend check applies the model prices of the Account that runs its
observer. Its result names that Account and the price catalog revision.
Missing prices leave the check **Unknown**.

## 3. Add a Domain

Open the Environment's **Domains** tab and choose **Add domain**. Enter the
hostname, select the service that should receive traffic, and enter that service's
**Container port**. Set a path only if the address should route a particular path.
For a native service, enter the **Outside check** path and its **Expected HTTP
status**. Use the app's readiness endpoint and the status it actually returns.
Review the ingress choice and submit the change. Complete any approval the app requests.

Direct public routing needs DNS pointing at the serving Machine and reachable
ports 80/443. If Caddy cannot bind a public port, free the port only when you own
the competing proxy and can safely stop it, or configure Tunnel ingress. The
Cloudflare tunnel controls let you choose the connection, zone, and tunnel;
the connector must be available on the Environment's Machines.

Use **Check again** to inspect the recorded Domain checks. Confirm the address
from outside the Machine before treating it as public.

<Callout title="Public-address validation is still incomplete">
Development testing verified the occupied-port refusal and its recovery message.
A separate test served a Compose app over public HTTPS through a Cloudflare
tunnel configured with the CLI Action. That test found a public HTTP 502
after redeploy and retained the app-created tunnel after the last Domain was
removed. Check the public address after each redeploy.
</Callout>

## 4. Add PostgreSQL and configure backups

If the Environment does not yet have a database, choose **Add a database** in
**Data**, select PostgreSQL, and review **Add**. Adding a Store database deploys
it immediately. For a repository-defined Environment, edit the repository's
Compose file to add the database, then deploy that change instead.

Open the database's **Backups** controls and choose **Set up backups** to open
the Environment's backup settings, then **Set up**. Choose backup
storage; if none is available, use **Open Store** to add it first. Enter its
**Endpoint**, **Bucket**, **Folder in the bucket**, and **Region**, and select the
database service to copy. Save, then choose the Saved Secrets for **Access key ID**,
**Secret access key**, and **Repository password**. Supply a **Session token** only
if your storage requires one.

Use **Test** to check the destination, then run **Back up now** and wait for its
completed result. Open **Verify backup**, select the new snapshot, and use
**Manifest read-back** to read back its manifest and payload. Verification does
not restore the database. Check the recent backup history before relying on it.

<Callout title="Storage evidence">
The development backup → daemon restart → restore journey passed with PostgreSQL
and MinIO S3-compatible storage. A separate real S3 Test probe remains withheld;
this is not a claim of live AWS S3 certification. Test your chosen destination
and perform a restore rehearsal before relying on it for important data.
</Callout>

## 5. Restore the database

Restoring replaces the database's current data. Choose a time when the app can
be interrupted, and make sure the selected backup is the one you intend to use.

1. Open **Restore a backup** and select an available restore point. A snapshot
   marked as unavailable cannot be restored from this screen.
2. Choose **Check backup**. Happier checks the selected backup and saves the
   current data as a safety backup when there is data to save.
3. Read the database and safety-backup details, then choose **Replace data**
   only when ready. This is the confirmation that permits data replacement.
4. Wait for the safety, stop, restore, start, and health steps to settle. Confirm
   the restored data in the app or database, rather than relying only on its health status.

In the tested development journey, a fresh backup remained selectable after the
executing daemon restarted, and restore returned the original PostgreSQL rows.
This does not establish recovery from lost backup records or damaged storage.

## When something needs attention

- **The Machine is offline:** reconnect its daemon. Scheduled jobs and health
  alerts depend on the Environment's controller Machine being online.
- **Docker or Buildx is unavailable:** install the missing tool on the Machine
  named by the preparation result and make it available to its daemon user.
- **A Domain step fails:** inspect its details and current route. Check public
  port ownership before retrying; a failed address step can leave the app deployed.
- **Test says another backup is using the destination:** wait for that operation
  to finish, then retry Test. Do not run Test alongside the backup or restore.
- **A backup cannot be selected:** read the reason. A repository snapshot without
  its required capture record is not a usable restore point in this flow.
- **Restore reports an unknown outcome or recovery needed:** inspect the result
  and actual database state before repeating the operation. Preserve the safety
  backup and use the displayed recovery instructions.

## Deploy a Machine folder with an Action

Open the folder on the build Machine with the Project Open Action. For Own server,
use the resulting WorkspaceRef in the Environment Create Action's folder
definition. Run Deploy and check review for the file count, total size and
excluded paths, including any listed as unsupported file types. A Git worktree
includes tracked and nonignored working files.
A plain folder follows its `.gitignore` files. To include files beginning with
`.env`, explicitly enable that option in the folder definition. Docker applies
its own context exclusions at build time. Deploy again reviews the current files.
