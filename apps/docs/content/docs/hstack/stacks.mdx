# Stacks (multiple local Happier instances)

`hstack` supports running **multiple stacks** in parallel on the same machine.

A “stack” is just:

- a dedicated **server port**
- isolated directories for **UI build output**, **CLI home**, and **logs**
- a repo checkout pin (point at a specific worktree/checkout)
- (when using `happier-server`) isolated **infra** (Postgres/Redis/Minio) managed per-stack

Stacks are configured via a plain env file stored under:

```
~/.happier/stacks/<name>/env
```

## Create a stack

Non-interactive (explicitly disable the TTY wizard):

```bash
hstack stack new exp1 --port=3010 --server=happier-server-light --non-interactive
```

Use an ephemeral port (selected when the stack starts):

```bash
hstack stack new exp2 --non-interactive
```

Power users: choose a DB provider without extra prompts:

```bash
# Light flavor (default): SQLite (no Docker)
hstack stack new exp-light --server=happier-server-light --db-provider=sqlite --non-interactive

# Light flavor (optional): embedded Postgres via PGlite (PG_Light)
hstack stack new exp-pglite --server=happier-server-light --db-provider=pglite --non-interactive

# Full server (default): Postgres (Docker-managed per stack)
hstack stack new exp-full --server=happier-server --db-provider=postgres --non-interactive

# Full server (optional): MySQL (requires an explicit DATABASE_URL; hstack does not provision MySQL)
hstack stack new exp-mysql --server=happier-server --db-provider=mysql --database-url=mysql://user:pass@127.0.0.1:3306/happier --non-interactive
```

## Create a PR test stack (copy/paste friendly)

If you want maintainers to be able to try your PR quickly, you can give them a single command that:

- creates an isolated stack
- checks out PR(s) into worktrees
- pins those worktrees to the stack
- optionally seeds auth
- optionally starts the stack in dev mode

Example (most common):

```bash
hstack stack pr pr123 \
  --repo=https://github.com/happier-dev/happier/pull/123 \
  --seed-auth --copy-auth-from=dev-auth --link-auth \
  --dev
```

Notes:

- `--remote` (default `upstream`) controls which Git remote is used to fetch `refs/pull/<n>/head`.
- `--seed-auth` uses `hstack stack auth <stack> copy-from <source>` under the hood, which also best-effort seeds DB Account rows (avoids FK errors like Prisma `P2003`).
- `--link-auth` symlinks auth files instead of copying them (keeps credentials in sync, but reduces isolation).
- For full-server stacks (`happier-server`), seeding may require Docker infra to be running.
- DB provider flags are forwarded to the underlying `hstack stack new` call:
  - `--db-provider=...`
  - `--database-url=...` (full server only)

## Auth seeding (recommended: dev-auth)

Create the `dev-auth` seed stack once, authenticate once, then reuse it when creating new stacks:

```bash
hstack auth seed
```

Interactive wizard (TTY only):

```bash
hstack stack new --interactive
```

The wizard lets you:

- pick the server type (`happier-server-light` or `happier-server`)
- pick or create a repo worktree for the Happier monorepo
- choose which Git remote to base newly-created worktrees on (defaults to `upstream`)

When creating `--server=happier-server` stacks, hstack will also reserve additional ports and persist
the stack-scoped infra config in the stack env file (so restarts are stable):

- `HAPPIER_STACK_PG_PORT`
- `HAPPIER_STACK_REDIS_PORT`
- `HAPPIER_STACK_MINIO_PORT`
- `HAPPIER_STACK_MINIO_CONSOLE_PORT`
- `DATABASE_URL`, `REDIS_URL`, `S3_*`

## Run a stack

Dev mode (interactive, recommended):

```bash
hstack tui stack dev exp1
```

Dev mode (non-interactive / no TUI):

```bash
hstack stack dev exp1
```

Dev mode (background):

```bash
hstack stack dev exp1 --background
```

Production-like mode (interactive):

```bash
hstack tui stack start exp1
```

Production-like mode (non-interactive / no TUI):

```bash
hstack stack start exp1
```

Production-like mode (background):

```bash
hstack stack start exp1 --background
```

Build stack artifacts:

```bash
hstack stack build exp1
hstack stack build exp1 --web
hstack stack build exp1 --server
hstack stack build exp1 --daemon
```

Build and activate a fresh full runtime snapshot:

```bash
hstack stack build exp1 --activate-runtime
hstack stack start exp1 --runtime
```

Activate only selected components into the active runtime:

```bash
hstack stack runtime exp1 activate --web
hstack stack runtime exp1 activate --server
hstack stack runtime exp1 activate --daemon
hstack stack runtime exp1 activate --all
```

Notes:

- `hstack stack build <name>` with no component flags keeps the legacy behavior and builds the web bundle only.
- Managed server and web artifacts are independent. A server-only request does not build or publish a web bundle; runtime launch supplies the selected web artifact separately.
- `hstack stack build <name> --activate-runtime` assembles a complete runtime snapshot (`web + server + daemon`) in the repository build-authority stack and selects it for `<name>`.
- Every named stack pinned to the same repository uses the same build authority by default. Artifact and snapshot requests share the repository-wide lock; a waiter re-inspects and reuses the newest compatible publication before running workspace preparation again. A requested component is compatible when it was newly published while waiting or already matches the request's current recipe, so a newer full snapshot is reused while a web-only publication cannot hide stale requested server or daemon bytes.
- Snapshot identity comes from the exact immutable component artifacts, target, server flavor, database provider, and build recipe it contains. Unrelated edits elsewhere in a busy checkout do not invalidate a completed artifact set or prevent it from becoming the latest usable snapshot; a later request can publish newer component artifacts when needed.
- `hstack stack runtime <name> activate ...` creates a new active runtime snapshot by combining the selected latest artifact(s) with the currently active runtime for unselected components.
- `hstack stack runtime <name> select` adopts the build authority's already-active snapshot without building, publishing, changing that producer's selection, or changing the consumer's launch mode.
- Building an artifact alone does **not** change the selected runtime. Selecting or activating a snapshot also does **not** restart a running stack: server and daemon bytes change only after an explicit restart.
- `--tauri` remains the legacy local `hstack build` flag. It is not part of named-stack artifact/runtime builds in v1.
- Runtime snapshots are currently for **named stacks**. Repo-local `yarn tui` / `hstack start` remain source-backed flows.
- `hstack stack auth <name> login` follows the same mode: if a valid runtime snapshot is active, guided login uses the stack-served runtime UI instead of waiting for Expo.

Select how a named stack starts:

```bash
# use source code directly (default)
hstack stack start exp1 --source

# require the active runtime snapshot
hstack stack start exp1 --runtime

# persist the default launch mode in the stack env
hstack stack env exp1 set HAPPIER_STACK_RUNTIME_MODE=prefer
```

## Shared runtime flow (for producer-owned named stacks)

Create a named stack pinned to a checkout/worktree:

```bash
hstack stack new dev-built --repo=/absolute/path/to/your/dev-checkout
```

Build or reuse the repository's shared runtime snapshot and select it for this stack:

```bash
hstack stack build dev-built --activate-runtime
```

Persist runtime preference for future `start` and `service` runs:

```bash
hstack stack env dev-built set HAPPIER_STACK_RUNTIME_MODE=prefer
```

Start it from the activated runtime snapshot:

```bash
hstack stack start dev-built --runtime
```

Update flow after code changes:

```bash
# rebuild a fresh runtime snapshot from the pinned checkout
hstack stack build dev-built --activate-runtime

# restart the service so it picks up the new active snapshot
hstack stack service dev-built restart
```

Component-only update flows:

```bash
# UI-only change: build the new web artifact, activate only web, then reload the browser
hstack stack build dev-built --web
hstack stack runtime dev-built activate --web
```

```bash
# Server-only change: build + activate only server, then restart the stack or service
hstack stack build dev-built --server
hstack stack runtime dev-built activate --server
hstack stack service dev-built restart
```

```bash
# CLI/daemon-only change: build + activate only daemon, then restart the daemon or service
hstack stack build dev-built --daemon
hstack stack runtime dev-built activate --daemon
hstack stack service dev-built restart
```

Important:

- You do **not** need to reinstall the named-stack service after rebuilding a runtime snapshot.
- The service keeps pointing at the stack env file; it picks the active snapshot on the next start/restart.
- `hstack stack info dev-built --json` reports `runtime.selectedSnapshotId`, `runtime.selectedProducerStackName`, `runtime.loadedSnapshotId`, `runtime.pendingManualRestart`, and (for the checkout-derived producer) `runtime.runtimePublication`. A pending restart is expected after selecting a newer snapshot while the stack is running.
- If the stack is in `prefer` mode, it will use the active runtime snapshot when valid, otherwise fall back to source.
- In `require` mode, source/watch fallback is disabled. `hstack stack dev <name>` is rejected so an automation or QA stack cannot accidentally re-enter the hot-reloading path.
- For web-only activation, reload the browser after the running stack has crossed the explicit restart boundary and loaded that selection.
- For server-only or daemon-only activation, restart the stack process or stack service so it re-resolves the updated runtime.
- Runtime snapshots and component artifacts are pruned automatically after successful activation/builds.
  - Default retention is the active build plus the previous one (`2` total).
  - A producer keeps snapshots selected by other managed stacks, even when they are older than the normal retention window.
  - Override with `HAPPIER_STACK_RUNTIME_SNAPSHOT_KEEP_COUNT=<n>` and `HAPPIER_STACK_RUNTIME_ARTIFACT_KEEP_COUNT=<n>`.
  - Set either value to `1` if you want to keep only the current runtime/artifact generation.
- Runtime-backed daemon/session runner copies are mutable process state, not part of a shared snapshot. They live under the consuming stack's CLI home and have their own bounded retention, so running a stack cannot grow or modify the producer's shared runtime snapshot.

These are four policies over the same owners: source validation reads source and does not publish runtime artifacts; source development starts from a valid last-green output and refreshes changed outputs in the background; managed publication builds only requested component code/support and commits a reference-only snapshot; release/self-host packaging uses the existing per-target self-contained builders directly from settled component inputs and does not consume or flatten a managed snapshot. A controlled consumer selects the newest valid snapshot and starts immediately, then reloads newly selected server/daemon bytes only after an explicit restart.

For the checkout-derived repository producer, `dev.mjs` automatically requests publication after successful non-destructive server/daemon preparation. Live activation remains separately fenced when newer source arrives, so a superseded restart does not discard useful completed bytes. The background publisher keeps one publication in flight, coalesces later requests into one trailing identity recomputation, reconciles web/server/daemon identities on restart, preserves the current snapshot and source services on failure, and does not restart consumers.

## Controlled stacks for agent QA

A controlled stack is an ordinary named stack that requires shared runtime snapshots and changes only when its operator explicitly restarts it. It has no separate QA runtime architecture.

Run these commands from the checkout under test with its existing checkout-local launcher, not a bare `hstack` found on `PATH`. The launcher is part of the stack toolchain: it binds the command to this checkout and prevents re-exec into another installed checkout.

Keep controlled stacks in that launcher's canonical managed stack storage. Do not redirect `HAPPIER_STACK_STORAGE_DIR` to `.project/tmp` or another workspace-local directory just because an agent sandbox cannot write the managed root. A different storage root is a separate stack universe: repository build-authority discovery, shared artifact reuse, and approved auth-source discovery no longer refer to the same owners. Grant the agent narrowly scoped access to the canonical stack root, or treat stack creation as blocked instead of manufacturing a parallel root or copying credentials by hand.

```bash
# Create an isolated stack. Choose the server/database options needed by the test.
node ./apps/stack/scripts/repo_local.mjs stack new agent-qa-17 --repo=/absolute/path/to/your/dev-checkout --server=happier-server-light --db-provider=sqlite --no-copy-auth --non-interactive

# Never fall back to source watchers for this stack.
node ./apps/stack/scripts/repo_local.mjs stack env agent-qa-17 set HAPPIER_STACK_RUNTIME_MODE=require

# Default to the repository stack's existing Expo/Metro process.
node ./apps/stack/scripts/repo_local.mjs stack env agent-qa-17 set HAPPIER_STACK_EXPO_SOURCE_STACK=<repository-stack>

# Verify that a human-approved source actually has reusable auth before copying.
node ./apps/stack/scripts/repo_local.mjs stack auth <approved-auth-source> -- status --json

# Only then seed this fresh stack's auth.
node ./apps/stack/scripts/repo_local.mjs stack auth agent-qa-17 -- copy-from <approved-auth-source>

# Verify the repository producer has an active snapshot, then select it for this consumer.
node ./apps/stack/scripts/repo_local.mjs stack info <repository-stack> --json
node ./apps/stack/scripts/repo_local.mjs stack runtime agent-qa-17 select --json

# Start the runtime server from built bytes and borrow the producer's Expo endpoint.
node ./apps/stack/scripts/repo_local.mjs tui stack start agent-qa-17 --runtime --mobile
```

`stack new` normally inherits auth from `main` for convenience. `--no-copy-auth` is mandatory for a controlled stack: it keeps credential provenance under the later human approval rather than silently copying a machine identity. `--non-interactive` is part of that controlled command contract, so a terminal does not reopen the ordinary stack-creation wizard. Continue only when the source status reports `auth.ok: true`; otherwise stop and obtain human direction to reauthenticate that source or select another one. Auth seeding never copies or shares a source database; a SQLite source is read without reconciling its migration ledger.

Before approved auth is seeded, a non-interactive runtime start still brings up the stack's server, but leaves its credential-dependent daemon stopped. It does not require an extra `--no-daemon` flag; after the approved copy, the next explicit start launches the daemon from the selected runtime too.

If a controlled stack was created without `--no-copy-auth`, do not delete auth files or recreate the stack. After the human approves the replacement source, replace its target auth:

```bash
node ./apps/stack/scripts/repo_local.mjs stack auth agent-qa-17 -- copy-from <approved-auth-source> --force
```

`--force` is not a broad recovery mechanism: it replaces target auth only after Account seeding proves the target data compatible, and it rejects conflicting target Account rows before replacing the target secret, credentials, or settings. It does not copy or reconcile the source stack's database or SQLite migration ledger.

A complete runtime snapshot selects independent web, server, and daemon artifacts. A borrowed-Expo consumer does not build a web artifact by default: server-only requests publish server code/support only, while strict snapshot UI requires an explicit `--web` request. Managed snapshots and support references are dev/QA-only; release and self-host packaging use their existing per-target self-contained builders directly from target-owned component/support inputs and do not consume or flatten a host-target snapshot.

`stack runtime agent-qa-17 select` is the zero-build path: it adopts the authority's active snapshot without changing running processes. If that snapshot already contains the bytes under test, reuse it.

When current server or daemon bytes are required, request the narrow build through the remembered consumer. The command resolves the repository authority and joins/reuses a publication already in flight; it does not create a consumer build store or take over the producer's running services:

```bash
node ./apps/stack/scripts/repo_local.mjs stack build agent-qa-17 --server --daemon --json
node ./apps/stack/scripts/repo_local.mjs stack runtime agent-qa-17 activate --all --json
node ./apps/stack/scripts/repo_local.mjs stack info agent-qa-17
# The TUI shows "pending manual restart" until you press r.
```

Use only `--server` or `--daemon` when one component changed. Run one build request and wait for it instead of launching retries or another publisher. `runtime activate --all` composes the latest authority web, server, and daemon artifacts and selects that exact snapshot; selection still cannot restart the consumer.

For a UI-only controlled-live check, manually reload the browser to receive the producer's current Expo bundle; do not build a web artifact. For explicitly strict snapshot UI, use the same checkout-local launcher:

```bash
node ./apps/stack/scripts/repo_local.mjs stack build agent-qa-17 --web --json
node ./apps/stack/scripts/repo_local.mjs stack runtime agent-qa-17 activate --all --json
node ./apps/stack/scripts/repo_local.mjs stack runtime agent-qa-17 select --json
```

Selection remains non-disruptive. Restart the remembered consumer deliberately, then inspect
`stack info --json` and require `selectedSnapshotId == loadedSnapshotId` before claiming the
strict UI bytes are loaded.

Each controlled stack still owns its mutable state: ports, server database, CLI home, daemon state, logs, and process lifecycle. Only immutable runtime artifacts are shared. In particular, creating a controlled stack does not copy or share the repository stack's SQLite database.

### Default browser QA with the repository Expo server

By default, a controlled stack borrows Expo/Metro from the repository stack while keeping its own snapshot-backed server and daemon:

```bash
node ./apps/stack/scripts/repo_local.mjs stack list
node ./apps/stack/scripts/repo_local.mjs stack env agent-qa-17 set HAPPIER_STACK_EXPO_SOURCE_STACK=<repository-stack>
node ./apps/stack/scripts/repo_local.mjs tui stack start agent-qa-17 --runtime --mobile
```

The TUI reports Expo as borrowed, displays the producer's Expo logs in the Expo pane, and routes the browser or development client to the consumer stack's server. Even with `--mobile`, the consumer does not start, own, restart, or stop Expo; the producer is its sole lifecycle owner. Browser URLs use the consumer's named `.localhost` origin, include its `server` URL, and set `happier_hmr=0`; the tab stays on its currently loaded UI until you reload it manually. On reload it receives the producer's latest development bundle, so this is intentionally controlled-live rather than immutable.

Only when strict or reproducible UI bytes are requested, unset `HAPPIER_STACK_EXPO_SOURCE_STACK` and use the static web UI served by the selected runtime snapshot instead of borrowed Expo. `happier_hmr=0` is web-only; an installed native development client can use the producer's advertised/tunnelled Metro URL, but its native Fast Refresh behavior is unchanged.

Doctor:

```bash
node ./apps/stack/scripts/repo_local.mjs stack doctor agent-qa-17 --runtime
```

## Edit a stack (interactive)

To change server flavor, port, or repo worktree for an existing stack:

```bash
hstack stack edit exp1 --interactive
```

## Switch server flavor for a stack

You can change `happier-server-light` vs `happier-server` for an existing stack without re-running the full edit wizard:

```bash
hstack stack srv exp1 -- status
hstack stack srv exp1 -- use happier-server-light
hstack stack srv exp1 -- use happier-server
hstack stack srv exp1 -- use --interactive
```

## Switch repo worktree for a stack (`stack wt`)

If you want the **exact** same UX as `hstack wt`, but scoped to a stack env file:

```bash
hstack stack wt exp1 -- status
hstack stack wt exp1 -- use pr/my-ui-pr
hstack stack wt exp1 -- use default
```

This updates the stack env file (`~/.happier/stacks/<name>/env`), not repo `env.local` (legacy path still supported).

## Run the Happier CLI against a specific stack (`stack happier`)

If you want to run a `happier` CLI command against a specific stack (instead of whatever your current shell env points at), use:

```bash
hstack stack happier exp1 -- status
hstack stack happier exp1 -- daemon status
```

When the named stack has a selected runtime snapshot and you want that admitted
CLI instead of the live source checkout, pass `--runtime` before the separator:

```bash
node ./apps/stack/scripts/repo_local.mjs stack happier exp1 --runtime -- status
```

This path does not publish or wait for source workspace packages. It is the
preferred form for controlled stacks because the CLI command and the running
server/daemon use the same selected snapshot. Omit `--runtime` only when you
intentionally want the source CLI and its freshness preflight.

Stack shorthand also works:

```bash
hstack exp1 happier status
```

These commands run with the stack env file applied:

- `hstack stack dev <name>`

- `hstack stack build <name>`
- `hstack stack runtime <name> activate ...`
- `hstack stack runtime <name> select`
- `hstack stack doctor <name>`

- `hstack stack srv <name> -- status|use ...`
- `hstack stack wt <name> -- <wt args...>`
- `hstack stack tailscale:status|enable|disable|url <name>`
- `hstack stack service:* <name>`

Tip: `hstack stack eas <name> env:sync --environment production` syncs the stack’s `EXPO_*` config values into the Expo project’s EAS Environment Variables.

- (advanced) `hstack bootstrap` (clone/install monorepo + deps)

## Services (autostart)

Each stack can have its own autostart service (so multiple stacks can start at login).

```bash
hstack stack service exp1 install
hstack stack service exp1 enable
hstack stack service exp1 status
hstack stack service exp1 restart
hstack stack service exp1 logs
```

First-time auth (recommended):

```bash
hstack stack service exp1 enable --auth-now -- --method=mobile --no-open
```

Notes:

- Services keep the server/UI up even if the daemon is not authenticated yet, and will start the daemon automatically once credentials exist.
- Named-stack services follow the same runtime mode as `hstack stack start <name>`.
  - `HAPPIER_STACK_RUNTIME_MODE=source`: always run from the live checkout.
  - `HAPPIER_STACK_RUNTIME_MODE=prefer`: use the active runtime snapshot when present, otherwise fall back to source.
  - `HAPPIER_STACK_RUNTIME_MODE=require`: fail unless a valid active runtime snapshot exists.
- `--method=mobile` requires a public-reachable URL for your phone (e.g. Tailscale Serve HTTPS, or a reverse proxy). If the stack’s public URL resolves to `localhost` / `127.0.0.1`, mobile auth won’t work until you configure remote access.

Implementation notes:

- Service name/label is stack-scoped:
  - `main` → `dev.happier.stack`
  - `exp1` → `dev.happier.stack.exp1`
- macOS: implemented via **launchd LaunchAgents**
- Linux: implemented via **systemd user services** (if available)
- The service persists `HAPPIER_STACK_ENV_FILE`, so you can edit the stack env file without reinstalling.
- Activating runtime changes does **not** hot-swap a running service process. After `hstack stack build <name> --activate-runtime` or `hstack stack runtime <name> activate ...`, run `hstack stack service <name> restart` when you are ready for the service to load the new selection. A browser reload is enough only after that running process serves the selected web snapshot.

## Tailscale Serve for a named stack

If you want phone/remote access and secure browser features, expose the named stack over HTTPS:

```bash
hstack stack tailscale:enable dev-built
hstack stack tailscale:url dev-built
```

Then persist the shareable URL in the stack env so auth flows and clients prefer it:

```bash
hstack stack env dev-built set HAPPIER_STACK_SERVER_URL=https://your-machine.your-tailnet.ts.net
```

Named-stack services and runtime-backed auth flows will then use that public URL where appropriate.

## Repo/worktree selection per stack

When creating a stack you can point the stack at a repo worktree:

```bash
  hstack stack new exp3 \\
  --repo=local/my-feature \\
  --server=happier-server
```

Worktree specs are interpreted relative to the workspace:

```
main                -> <workspace>/main
dev                 -> <workspace>/dev
pr/<...>            -> <workspace>/pr/<...>
local/<...>         -> <workspace>/local/<owner>/<...>
tmp/<...>           -> <workspace>/tmp/<owner>/<...>
```

So `--repo=pr/foo` maps to:

```
<workspace>/pr/foo
```

You can also pass an absolute path.

## Stack env + repo env precedence

On startup, `hstack` loads env in this order:

1. `~/.happier-stack/.env` (defaults)
2. `~/.happier-stack/env.local` (optional global overrides; prefer stack env for persistent config)
3. `HAPPIER_STACK_ENV_FILE` (stack env; highest precedence)

`hstack stack ...` sets `HAPPIER_STACK_ENV_FILE=~/.happier/stacks/<name>/env` and clears any already-exported `HAPPIER_STACK_*` variables so the stack env stays authoritative.

For a full explanation of the different folders/paths (`home` vs `workspace` vs `runtime` vs stack storage) and the exact env precedence rules, see: [[Paths and env](/hstack/paths-and-env)](/hstack/paths-and-env).

Cloned-repo fallback (before you run `hstack init`):

1. `<repo>/.env` (defaults)
2. `<repo>/env.local` (optional overrides)
3. `HAPPIER_STACK_ENV_FILE` (stack env)

## Manage per-stack environment variables (including API keys)

To add/update environment variables in a stack env file from the CLI:

```bash
hstack stack env <stack> set KEY=VALUE [KEY2=VALUE2...]
```

To remove keys:

```bash
hstack stack env <stack> unset KEY [KEY2...]
```

To inspect:

```bash
hstack stack env <stack> get KEY
hstack stack env <stack> list
hstack stack env <stack> path
```

Notes:

- This is the recommended place for **provider API keys** the daemon needs (example: `OPENAI_API_KEY`).
- Changes apply on the **next start** of the stack/daemon. Restart to pick them up:
  - `main`: `hstack start --restart`
  - named stack: `hstack stack start <stack> -- --restart` (or `hstack stack dev <stack> -- --restart`)

Self-host shortcut (defaults to `main` when not running under a stack wrapper):

```bash
hstack env set OPENAI_API_KEY=sk-...
```

## Daemon auth + “no machine” on first run

On a **fresh machine** (or any new stack), the daemon may need to authenticate before it can register a “machine”.
If the UI shows “no machine” (or the daemon shows `auth_required`), it usually means the stack-specific CLI home
doesn’t have credentials yet:

- `~/.happier/stacks/<stack>/cli/access.key`

To check / authenticate a stack, run:

```bash
hstack stack auth <stack> status
hstack stack auth <stack> login
```

Notes:
- You can run **multiple daemons for the same stack** on **different accounts** using `--identity=<name>`.
  - `default` (no flag): `~/.happier/stacks/<stack>/cli/...`
  - `--identity=account-b`: `~/.happier/stacks/<stack>/cli-identities/account-b/...`
- To authenticate an identity without auto-opening a browser, use `--no-open` (it prints the URL so you can open it
  in the browser profile/incognito window you want):

```bash
hstack stack auth <stack> login --identity=account-a --no-open
hstack stack auth <stack> login --identity=account-b --no-open
```

- To start/stop an identity’s daemon explicitly:

```bash
hstack stack daemon <stack> start --identity=account-a
hstack stack daemon <stack> stop  --identity=account-a
```

- For the **main** stack, use `<stack>=main` and the default `<port>=53288` (unless you changed it).
- If you use Tailscale Serve, `HAPPIER_WEBAPP_URL` should be your HTTPS URL (what you get from `hstack tailscale url`).
- Logs live under:
  - default identity: `~/.happier/stacks/<stack>/cli/logs/`
  - named identities: `~/.happier/stacks/<stack>/cli-identities/<identity>/logs/`
