---
title: Remote development targets
description: Mirror one checkout to Linux, macOS, or Windows machines and place development services or commands on a selected target.
---

Remote development targets let one local Stack checkout drive Happier builds, tests, daemons,
Expo/Metro, and optionally the development server on other machines. Stack uses
[Mutagen](https://mutagen.io/) for one-way source synchronization and reuses the existing Stack
development lifecycle on every target. The local checkout, TUI, Mutagen process, and stable
localhost ports remain on the editing machine.

This is intended for maintainers who want macOS, Linux, and Windows daemons connected to the same
development server while editing one checkout.

## Prerequisites

On the computer running `yarn dev` or `yarn tui`:

- install Mutagen and make `mutagen` available on `PATH`;
- configure non-interactive OpenSSH access to every target;
- accept each target's SSH host key before starting the TUI.

On every target:

- run an OpenSSH server;
- install Node.js 22 or newer and Corepack;
- install any native developer tools remote commands will use, such as ripgrep (`rg`);
- allow enough disk space for a source mirror, target-local dependencies, and build output.

Stack deliberately does not install or update the host's SSH server, Node.js, Corepack, or Mutagen
CLI. Those are machine prerequisites. Mutagen automatically installs its own small synchronization
agent over SSH when a project starts.

The PATH-provided `mutagen` process and its `MUTAGEN_DATA_DIRECTORY` belong only to Stack's
development-target mirror. Happier workspace relationships use the separately managed,
license-checked `happier-mutagen` manager/agent artifact under the daemon data root; they never
reuse this Stack data directory or a system Mutagen executable.

Verify a target without changing it:

```bash
hstack dev-targets doctor linux --stack=repo-dev
```

`doctor` checks the local Mutagen CLI, passwordless SSH, and remote Node.js/Corepack availability.
It does not provision or inventory optional developer tools. Omit the target name to check every
target configured for the stack.

## Add and manage targets

Target configuration is stack-scoped and stored at:

```text
~/.happier/stacks/<stack>/dev-targets.json
```

Use the command rather than editing the JSON directly:

```bash
hstack dev-targets path --stack=repo-dev
hstack dev-targets list --stack=repo-dev
hstack dev-targets show linux --stack=repo-dev
```

### One-command macOS or Linux setup

For a macOS or Linux target reachable over SSH, `add --host` owns the complete connection setup:

```bash
node ./apps/stack/scripts/repo_local.mjs dev-targets add mac --host=100.98.30.76 --user=leeroy
```

The command:

- creates a dedicated ed25519 key under the selected Stack's private state directory;
- uses a target-specific `known_hosts` file and accepts only a previously unseen host key (a changed
  key still fails closed);
- checks whether that dedicated key already works;
- when necessary, runs `ssh-copy-id` through that same isolated target configuration so the remote
  account password can be entered once;
- verifies non-interactive dedicated-key authentication;
- discovers the remote home, operating system, login-shell `PATH`, Node.js, and Corepack;
- rewrites the target config from first-contact `accept-new` to strict host-key checking, proves the
  strict connection, and registers the target only after those checks pass.

By default the mirror is `<remote-home>/happier-dev` and target-local state is
`<remote-home>/.happier/dev-targets/<name>`. Override either when needed:

```bash
node ./apps/stack/scripts/repo_local.mjs dev-targets add mac \
  --host=100.98.30.76 \
  --user=leeroy \
  --repo-dir=/Volumes/Work/happier-dev \
  --cli-home-dir=/Volumes/Work/.happier-mac
```

The discovered PATH is persisted with the target, so non-interactive commands can use installations
managed by tools such as NVM or Volta even when the SSH daemon's default PATH cannot see them. If a
version-manager shim exposes Node but omits `corepack`, provisioning also discovers the Corepack
binary beside Node's actual `process.execPath`. Rerunning the
same command reuses the target-specific key and refreshes the connection facts. This provisioning
shortcut currently supports macOS and Linux targets; configure Windows targets explicitly as below.

The local machine needs `ssh`, `ssh-keygen`, and `ssh-copy-id`. Provisioning never installs Node.js,
Corepack, package managers, or system services on the remote host; it diagnoses missing prerequisites
and stops before registering a target.

### Explicit setup

Add a Linux or macOS target:

```bash
hstack dev-targets add linux \
  --stack=repo-dev \
  --platform=posix \
  --ssh=happier-stack-linux \
  --repo-dir=/home/dev/happier \
  --cli-home-dir=/home/dev/.happier/dev-targets/repo-dev-linux
```

Add a Windows target using forward-slash paths:

```bash
hstack dev-targets add windows \
  --stack=repo-dev \
  --platform=windows \
  --ssh=happier-stack-windows \
  --repo-dir=C:/Users/dev/happier \
  --cli-home-dir=C:/Users/dev/.happier/dev-targets/repo-dev-windows
```

`--ssh` can be a normal OpenSSH alias or `user@host`. If a target uses a generated or isolated SSH
configuration, pass its absolute path:

```bash
hstack dev-targets add linux \
  --stack=repo-dev \
  --platform=posix \
  --ssh=lima-happier \
  --ssh-config-file=/absolute/path/to/lima/ssh.config \
  --lima-instance=happier-linux \
  --lima-home=/absolute/path/to/lima-home \
  --repo-dir=/home/dev/happier \
  --cli-home-dir=/home/dev/.happier/dev-targets/repo-dev-linux
```

When both Lima options are present, Stack runs `limactl start` before SSH preparation. It does not
stop the VM when the TUI exits, so target-local dependency and build caches remain warm.

### Set shared and dedicated capacity for a managed Lima target

Managed Lima targets can keep two CPU and memory presets in this stack's `dev-targets.json`. The
editing stack is the configuration authority: it resolves the selected preset and applies it to the
target's Lima host through the managed connection. Nothing inside the worker VM owns or rewrites
this policy.

Configure both presets the first time and select the mode that should be active:

```bash
hstack dev-targets capacity set mac3-linux dedicated \
  --shared-cpus=8 \
  --shared-memory-gib=24 \
  --dedicated-cpus=12 \
  --dedicated-memory-gib=32 \
  --force \
  --stack=repo-dev
```

After both presets exist, switching modes only needs the target, mode, and `--force`:

```bash
hstack dev-targets capacity set mac3-linux shared --force --stack=repo-dev
hstack dev-targets capacity set mac3-linux dedicated --force --stack=repo-dev
hstack dev-targets capacity show mac3-linux --stack=repo-dev
```

`--force` authorizes the exact managed worker VM to stop, apply its selected CPU and RAM values,
restart, and refresh its generated SSH endpoint. Other targets and the editing VM keep running. If
the selected resources differ and `--force` is absent, the command leaves both the VM and config
unchanged and tells you to rerun with `--force`. A matching preset can be stored without a restart.

Capacity does not change the target's disk size, architecture, VM type, or provisioning policy;
those remain owned by its managed Lima profile. This makes it safe to give machines different
shared and dedicated CPU/RAM values without silently growing a retained worker disk. Run
`hstack dev-targets status <name>` afterward to verify the target is synchronized, running, and has
no managed-runtime drift.

Adding a target with an existing name replaces that target's configuration. Remove one with:

```bash
hstack dev-targets remove windows --stack=repo-dev
```

From a source checkout, use its direct repo-local launcher so target management is pinned to that
checkout without a package-manager startup:

```bash
node ./apps/stack/scripts/repo_local.mjs dev-targets list
node ./apps/stack/scripts/repo_local.mjs dev-targets add ...
node ./apps/stack/scripts/repo_local.mjs dev-targets show linux
node ./apps/stack/scripts/repo_local.mjs dev-targets doctor
node ./apps/stack/scripts/repo_local.mjs dev-targets remove linux
```

The repo-local wrapper selects that checkout's Stack automatically.

## Choose where work runs

Placement settings are supported by the stack-scoped target configuration. Managed Lima ownership
and per-target capacity use its current version 3 shape. Use the command owner instead of editing
JSON:

```bash
# Keep the server and daemon local, but run Expo/Metro on the Mac target.
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set expo mac

# Route common commands across the least-loaded healthy targets.
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set commands auto --targets=mac,mac2 --fallback=local

# Optional capabilities; keep the server local until its persistence is target-ready.
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set daemon mac
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set server mac

# Development-only: build named-stack artifacts in a separate worker workspace.
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set build linux

# Development-only: try workers in order, then fall back locally.
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set build ordered --targets=linux,mac --fallback=local

# Development-only: build on one worker, run controlled QA on other workers.
# Set the QA default on the checkout's existing producer stack.
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set build mac2-linux --stack=<producer>
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set qa auto \
  --targets=linux2,linux3,windows1-linux,windows2-linux,linux1 \
  --fallback=local --stack=<producer>

# Override only this consumer, or restore its local execution.
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set qa ordered --targets=linux3,linux2 --fallback=local --stack=<qa>
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set qa local --stack=<qa>

node ./apps/stack/scripts/repo_local.mjs dev-targets placement show
```

Runtime surfaces accept `local` or one configured target name. `build` and `qa` also accept `ordered`
with `--targets=NAME,...` and local fallback. `qa` additionally accepts `auto` over its configured
pool, using the existing least-load command selector without competing local execution.
QA placement is currently explicit per-stack opt-in: the producer QA default is stored but its
automatic rollout remains inactive until the complete remote path has passed live verification.
Existing stacks therefore retain local behavior. Retained local server data always requires the
explicit data handoff, even when that consumer has an explicit QA policy.
`commands` additionally accepts
`auto`, optionally with `--targets`, `--include-local`, `--fallback=local|error`,
`--load-probe-ttl-ms`, and `--unavailable-probe-ttl-ms`. The available surfaces are:

| Surface | What moves to the target | What stays local |
|---|---|---|
| `commands` | Common test, Vitest, and typecheck script processes | Source edits and Git |
| `expo` | Metro/Expo watch, bundle, and restart work | TUI, Mutagen, stable Expo port/tunnel |
| `daemon` | CLI build/watch and daemon process | TUI, Mutagen, server tunnel |
| `server` | Server watch/build/restart and its selected database | TUI, Mutagen, stable server port/tunnel |
| `build` | Named-stack runtime preparation and component compilation | Producer admission, artifact store, snapshot publication and selection |
| `qa` | Controlled snapshot server and daemon, with isolated mutable state and workspace | Controller, borrowed Expo ownership, stable server forwards |

In current development source, `build` placement uses a dedicated workspace beneath the target's
CLI home, separate from its continuously synchronized source mirror and live service outputs.
Configure `build` on the producer stack: its target registry and ordered worker list govern every
consumer request. Controlled QA ignores a consumer's `runtimePlacement.build` entry with a warning
pointing to the producer config; consumers can keep their own QA target registries.
Each admitted producer flight captures its current source; later edits do not change that worker
build, including its referenced TypeScript configs and manifest-declared native resources.
Dependencies and generated outputs remain target-local; preparation uses the same QA-runtime
last-green policy as a local named-stack build. Finished component and support
artifacts return to the producer through the existing manifest and snapshot owners.

By default the requested artifact retains the producer's operating system and architecture.
An explicit `stack build <qa> --target=linux-x64` requests that target through the same producer
publication path; it does not create a consumer publisher. Server and web
builds can use a worker of another architecture on the same operating system. Server support
installs target-native Sharp packages through npm's CPU/OS selection; cross-target server builds
require npm with those options. Bun and Prisma retain their explicit build targets.
Linux x64 workers can build Linux ARM64 daemon support with npm, Python, make and the
`aarch64-linux-gnu` C/C++ toolchain installed. The support builder installs target dependencies
separately from host build tools and cross-builds the terminal's `node-pty` addon. Other daemon
cross-target pairs require a matching native worker. An ordered list tries the next worker when preflight finds a worker
unavailable, incompatible with the requested components, or unable to admit the runtime build now,
and reports the reason. It checks admission again without waiting when dispatching; a capacity change
before dispatch tries the next worker. If none can run the build, the logged local fallback may wait
for local admission. Compilation uses the existing memory-aware worker admission policy. Once
compilation starts, a failure propagates without replaying the build elsewhere.
Native Windows worker placement is not supported by this build transport; matching WSL targets
use the POSIX path. Build placement does not move running services or their databases.

Current development source ties routed POSIX commands to the controller's lifetime. Linux controller
disconnect or exit terminates the command's process group, including its descendants; interactive
commands retain their terminal input. Recovery uses the existing execution IDs and PID records to
cancel positively identified abandoned commands, rather than killing unrelated SSH connections or
matching jobs by name. Linux recovery checks process start identities before delayed cancellation.
Heavyweight reservations are reclaimed after their owning processes exit. Native macOS cleanup is
incomplete for descendants that ignore termination: without a strong process-incarnation witness,
delayed forced cancellation is skipped rather than risking a reused process ID.

A synchronized target does not have to participate in automatic command
execution. For example, a `mac-host` target can remain configured as the
Mutagen mirror and macOS service-placement endpoint while the automatic pool
uses only Linux workers plus local fallback:

```bash
node ./apps/stack/scripts/repo_local.mjs dev-targets placement set commands auto \
  --targets=mac2-linux,mac3-linux \
  --include-local \
  --fallback=local
```

An exact `dev-targets exec mac-host` remains available when a command genuinely
requires macOS. Omitting it from `--targets` only removes it from automatic
selection; it does not remove the target, synchronization, or service
placement.

Setting any placement upgrades the existing version 1 file without losing configured targets.
The old version 1 behavior is local server + local Expo + local daemon, with an additional daemon
on every configured target. To deliberately restore exactly that behavior:

```bash
node ./apps/stack/scripts/repo_local.mjs dev-targets placement clear --downgrade-v1
```

Removing a target that still owns an exclusive runtime or fixed command placement is rejected. An
automatic all-target command pool follows target additions and removals.

Before starting an exclusively placed service, Stack checks Mutagen and
the target host/toolchain. Expo and daemon placement can fall back locally when this preflight
cannot reach the host. Persisted remote server placement is authoritative: an unavailable server
target fails startup rather than opening a different local database. A service process exiting is not treated as host unreachability: in
particular, Expo/Metro is restarted on its configured target while the independent SSH tunnel keeps
the local port stable. This prevents a normal Expo crash from creating a competing local Metro
process.

Expo startup first looks for a structurally complete shared source-development output closure. When
one exists, Stack starts or adopts that last-green closure immediately and refreshes it in the
background. This applies to local Expo and to remote Expo placement: the local server and remote
worker are not held behind a full workspace/plugin UI refresh on every TUI start. If no usable
closure exists and preparation fails, Stack still starts Expo in a degraded state so the server,
TUI, and recovery loop remain available; routes that import a missing generated artifact can fail
until a refresh succeeds. The failure is reported in the Stack logs. The next successful refresh
publishes the canonical workspace outputs and bundled-plugin projection together through one
prevalidated mounted-tree transaction. Known-invalid inputs fail before replacement; a caught commit
failure rolls the live tree back to last green, and the next canonical preflight repairs any
interrupted partial replacement. This is not a generation-pointer, journal, or power-loss atomicity
contract across package-owned source trees. Each target continues to use its target-local synchronized
build cache rather than copying build output between machines.

Reachability of the SSH worker is not service readiness. Stack verifies Expo through the local
tunnel and verifies a remote daemon from that server identity's daemon state plus its live process.
Runtime status records those results per service, so a healthy Expo endpoint remains available when
the colocated daemon is rebuilding or degraded, and the TUI never labels the daemon running merely
because the remote worker is connected.

When the server or Expo is remote, SSH local forwards preserve the selected local ports. When the
server stays local but Expo or a daemon is remote, an SSH reverse forward gives the remote process
the same server endpoint. Browsers, local tools, and installed development clients therefore keep
using the local URL. A remotely placed server is launched with the originating stack's canonical
server origin, so the audience it signs for key-challenge authentication stays the origin URL those
clients already use instead of one derived from the target's own stack name and port. For phones,
the tunnel's LAN bind accepts both IPv4 and IPv6 connections and
Expo advertises a LAN-reachable URL. Set `HAPPIER_STACK_LAN_IP` to the machine's Tailscale IPv4
address when a phone should connect through Tailscale instead of the selected LAN interface.

Other named stacks can borrow that Expo endpoint by setting
`HAPPIER_STACK_EXPO_SOURCE_STACK=<producer-stack>`. The producer remains the only process owner:
the consumer TUI tails the producer's local or remote tee log but cannot stop or restart Expo. If a
remote Expo worker crashes while its host is still reachable, the producer supervisor retries it on
that target instead of starting a competing local Metro process. Local fallback is reserved for a
target that fails the reachability preflight. The stable local tunnel/port therefore remains the URL
used by browsers and installed development clients.

This borrowed endpoint is the default UI mode for controlled QA stacks. Their server and daemon
still load shared runtime snapshots; static snapshot UI is reserved for explicitly strict or
reproducible UI QA.

Remote server placement currently supports the light server with SQLite. Its database file belongs
to the machine running the server; Stack does not mount or proxy a local SQLite file over SSH.
Setting placement changes configuration only; it does not transfer retained data. For a stopped
stack with retained local data, use the explicit handoff before remote startup:

```bash
node ./apps/stack/scripts/repo_local.mjs dev-targets move-server <target> --stack=<qa>
```

The handoff copies and verifies the full light-server directory, including SQLite, signing secret,
public and private files, checks database integrity, and retains the local source. It commits
placement only after verification. It refuses conflicting destination data and a running stack;
it does not stop the stack or delete either copy. An already-remote stack keeps its current data
authority. A network database does not remove the light-server/SQLite placement restriction.

### Controlled runtime stacks (0.3 development)

A [controlled QA stack](/hstack/stacks#controlled-stacks-for-agent-qa) started with
`stack start --runtime` resolves an explicitly set `runtimePlacement.qa` from its own dev-targets
config for a stack without retained local server data. The producer QA default is not activated
yet; unplaced existing stacks stay local without probing workers, even if that default is invalid.
Build placement belongs to the producer: changing a consumer's `qa` chooses its runtime host,
while the producer's `build` setting chooses compilation workers. Changing `build` never moves
a running stack. Offline targets are skipped with an
observable reason; ordered pools try the next worker and automatic pools use the existing
least-load selector. Local execution is the final fallback. Once server data lives on a remote
target, that persisted server placement is authoritative: unavailability fails closed rather than
opening a fresh local database. A local QA override cannot bypass it.

`stack runtime <qa> select` chooses the newest complete producer snapshot matching the selected
worker's observed platform and architecture. Explicit snapshot ids remain exact pins and must
match that target. If none exists, build a matching snapshot through the producer; do not relabel
ARM64 bytes as x64. Windows WSL workers consume Linux snapshots, not native Windows snapshots.
The first complete target publication uses `stack build <qa> --all --activate-runtime --target=linux-x64`;
later narrow component builds reuse that target's other published components. This initial shared
publication is not a per-QA build, and borrowing Expo does not make a foreign snapshot portable.
The existing supervisor transfers and validates the complete component/support closure, launches
the snapshot lifecycle rather than source watch, and reuses the existing SSH forwards. Each stack
has separate CLI state and a writable session workspace outside the one-way source replica.
Observe the selected and remotely loaded snapshot identities before claiming remote QA success.
This is development-source behavior, not certification of every target or a released availability
claim.

## Run heavy commands on a target

Once synchronization is active—either through Stack or the independent synchronization
service—use the same source replica at `repoDir` for searches, tests, typechecks, and
builds:

```bash
node ./apps/stack/scripts/repo_local.mjs dev-targets status linux
node ./apps/stack/scripts/repo_local.mjs dev-targets exec linux -- rg -n "RunnerAgentExecutionGrant" apps packages .project/plans
node ./apps/stack/scripts/repo_local.mjs dev-targets exec linux --cwd=apps/cli -- corepack yarn test
node ./apps/stack/scripts/repo_local.mjs dev-targets exec linux --env=CI=1 -- corepack yarn typecheck
```

For ordinary work, internal workspace scripts choose among configured healthy targets automatically:

```bash
corepack yarn -s typecheck
corepack yarn --cwd apps/cli -s test
corepack yarn --cwd packages/plugins/claude -s typecheck
corepack yarn --cwd apps/server -s vitest run sources/example.spec.ts
```

For a focused Vitest file, use that package's routed `vitest` command. Do not
append the file or `-t` filter to an aggregate `test` or `test:unit` command
unless its script explicitly supports forwarding: a compound aggregate can
start its complete test suite before the appended filter reaches its last
child command.

Do not invoke a `*:local` script directly. Those scripts are implementation targets for
`hstack-exec`, which owns target selection and local fallback.

Automatic selection synchronizes the chosen checkout before executing the
command remotely. If no configured remote is usable, `fallback=local` runs the
command through the same launcher in the editing VM; forcing `--local` is
reserved for commands that genuinely require that machine. Capacity presets
do not impose a fixed job-count limit: normal load and health observations
continue to choose among local and remote executors.

In 0.3 development, concurrent commands for the same target can share a successful
Mutagen flush only when it started after their synchronization requests. A command
requested during a flush waits for a later cycle, preserving source files written
just before that request. Every command still checks the session's current health
before remote dispatch. Failed or canceled flushes cannot satisfy a queued request.
On platforms without `flock`, each command performs its own flush.

The repository root and every internal workspace route their ordinary `test`, `test:unit`,
`typecheck`, and `vitest` entry points when present. Their `*:local` counterparts are the canonical
local implementations.
For a broad command without a public package entry point, use the launcher directly:

```bash
./apps/stack/bin/hstack-exec -- rg -n "RunnerAgentExecutionGrant" apps packages .project/plans
```

`./apps/stack/bin/hstack-exec --local -- <command> [args...]` keeps one invocation local without
pinning later descendant commands to the local host.
The checkout-local `./apps/stack/bin/hstack-exec -- ...` launcher exposes that same owner for
potentially broad read-only repository work (`rg`, `find`, inventories/counts), tests, typechecks,
lint/static analysis, and builds that write only ignored artifacts. Keep tracked-source or Git
mutations, generators/codemods/formatters, databases/migrations, Stack lifecycle, devices,
simulators, and unforwarded secrets local.

Automatic routing is also best-effort. It probes configured targets concurrently, normalizes load
by CPU count, adds a low-memory penalty, and randomly distributes commands among near-equal hosts.
Healthy samples are cached briefly (15 seconds by default); unavailable samples are cached longer
(2 minutes by default). Refreshes are coalesced with a lightweight filesystem lock, so concurrent
agents do not each probe the same host. The selector excludes a target that cannot launch the
requested top-level executable or does not have enough filesystem scratch space, and adjusts
each cached score for commands already dispatched there
but not yet visible in its next load sample. Pass the executable directly when practical: wrapping
it in `sh -lc` hides inner tool requirements from this preflight. If the selected host cannot
establish its command connection, the launcher temporarily excludes it and tries another configured
target before applying `fallback=local|error`. Once a command starts, its result is authoritative
and is never replayed elsewhere. `includeLocal` controls whether local load normally competes; it is
independent from allowing local fallback.

Before the selected remote command starts, the launcher flushes that target's named Mutagen session.
If the flush fails, it releases the dispatch reservation and applies `fallback=local|error` instead
of running the remote command against an older checkout.

On Linux, recognized typecheck, Vitest, build-like, and direct dependency-install commands share a
host-global admission queue without a fixed job-count ceiling. The launcher reports waiting
provenance and pauses new starts below the class's available-memory floor, below 10% available
memory, or at memory PSI `avg10` of 10 or higher. It also pauses when the runnable count is at least
twice the online CPU count and CPU PSI `avg10` is at least 50. An interrupted command releases its
admission record. Searches and ordinary control commands keep their normal dispatch path.

In 0.3 development, the shared command policy sizes admission by workload. Measured cli-common
and Protocol dist builds use the 6 GiB package-dist envelope. Canonical runtime worker requests
use an 18 GiB runtime-build envelope: a successful full daemon build peaked at about
15.68 GiB of process-tree RSS. Adding at least the measured package envelope's 1.53 GiB of
spare headroom and rounding up to whole GiB gives 18 GiB. Full typechecks and unmeasured
builds retain the conservative 21 GiB compilation envelope. Focused validation and dependency
installation retain their existing 6 GiB envelope. Automatic routing excludes workers whose
total RAM cannot hold the selected class, including cached samples and local candidates.
Linux and WSL reserve each admitted job's full class envelope until exit or orphan reclamation and
subtract those reservations from available memory before admitting more work. Authenticated nested
commands share their parent's reservation. Memory-wait and capacity-exclusion diagnostics name the
class, required memory and existing reservations. These requirements reserve admission headroom;
they do not limit the command's actual memory use.

In current development source, each Linux worker owns `/tmp/happier-heavyweight-admission-v1`.
Task-private mirrors, caller admission roots and machine aliases cannot create independent queues.
The configured execution account must own this directory; unavailable or foreign-account state fails
closed rather than falling back to a private queue. Live older private-root owners are counted during
cutover; already-loaded older launchers must drain before all writers use the new authority.

Runtime service placements do not exclude a host from commands. The worker measures current
server/Expo process-tree resident memory from existing Stack PID state and generation witnesses,
including standalone Expo state. Total capacity reserves that memory without subtracting it twice
from available memory. An active runtime build reserves its existing runtime-build envelope.
Admission diagnostics expose both reservations; there is no separate service-host configuration list.

Fitting small jobs can backfill a blocked larger queue head. Backfill stops after consuming that
head's existing class envelope or when one candidate envelope would bridge its capacity gap.
Only successful starts consume this allowance, not retries or readiness probes. This protects the
older job from starvation without adding a timeout.

Explicit `--local` changes placement and uses the same Linux admission owner: heavyweight work
waits for local memory to recover, while light commands run immediately. A class that cannot fit
total local memory minus service reservations fails immediately with an instruction to route it
remotely. It does not bypass
memory admission. macOS selection applies the class's total-capacity filter, but does not have
the Linux admission queue or available-memory floor. Native Windows command execution remains local.

In the current development checkout, automatic routing and named POSIX-target execution from a
macOS or Linux computer use the same dispatcher. Recognized searches and validation commands run at
background priority on Linux and macOS targets. Their Vitest, ripgrep, and native TypeScript worker
budgets share the target's CPU capacity with active dispatches; Linux also contributes runnable and
pressure measurements. Explicit worker overrides are preserved. These are per-command hints, not a
global memory limit: an unreserved macOS target can still give its first job the full CPU budget,
and already-running jobs are not resized. Linux admission remains Linux-only.

When a Linux target has a ready systemd user manager and a loaded `happier-jobs.slice`, an admitted
job runs in a transient user scope in that slice at nice level 10. The launcher does not create or
configure the slice; targets without that prepared boundary run the same admitted command directly.

The normal scratch floor is 1 GiB. A target whose synchronized checkout has not installed the
current dependencies needs at least 16 GiB for automatic dependency-backed routing, covering the
Yarn cache and linked workspace tree. Already-prepared targets keep using the normal floor, and
source searches can still use an otherwise healthy unprepared target. An explicit
`dev-targets exec <name>` remains an operator override and can still attempt dependency preparation
on that target.

On POSIX, the checkout-local launcher first performs a conservative filesystem check. If no
repository target configuration can exist, it replaces itself with the requested command without
starting Node, Yarn, Mutagen, SSH, or a load probe. Node validates configuration and publishes a
private shell-safe execution projection only when target configuration changes. Steady-state sync
health checks, cached load probes, host selection, SSH execution, cancellation, and fallback are
native shell operations. A `--script` invocation starts Yarn only on the selected execution host
because Yarn owns package-script semantics. Windows deliberately executes locally for this
POSIX-only routing feature.

A running Stack is not required when the independent synchronization service owns a healthy mirror.
If no remote is usable, the launcher follows the configured fallback. After the actual remote command has
started, its result is authoritative: a failing remote test is never replayed locally and replaced
with different evidence. A local fallback marks nested workspace scripts local as well, so one
command cannot oscillate between machines.

Everything after `--` belongs to the remote command, so child flags such as `--json` are preserved.
`--cwd` is relative to the synchronized repository root and cannot escape it. `--env=KEY=VALUE` can
be repeated; unrelated local environment variables are not forwarded implicitly. Explicit Vitest
worker settings and `GOMAXPROCS` are inherited by the native dispatcher, and a supplied `--env`
assignment takes precedence. The remote command's exit
status is returned by `hstack`. On `Ctrl-C`/termination, `hstack` cancels the execution-scoped remote
process tree and then stops its local SSH client. Use `--tty` only for a command that genuinely needs
an interactive terminal.

Every routed `exec` first requires a healthy synchronization session and then flushes that existing
Mutagen session immediately before SSH launch. This makes edits observed by the synchronization
owner available to the command before it starts, avoiding stale post-edit validation. Continuous
synchronization remains active while the command runs: the flush does not pause the mirror, create a
staging tree, or provide an immutable snapshot, so later edits can still arrive during execution.

The standalone synchronization command remains useful when a caller needs a barrier without starting
a command. The legacy exact-target `--flush` option is accepted for compatibility and preserves the
same single pre-launch barrier; it does not add a second flush:

```bash
node ./apps/stack/scripts/repo_local.mjs dev-targets sync linux
node ./apps/stack/scripts/repo_local.mjs dev-targets exec linux --flush -- corepack yarn test
```

A flush is a point-in-time launch barrier, not a snapshot. Commands that require an immutable source
tree must use a separate workspace/snapshot mechanism rather than assuming the live Dev Target mirror
stops changing.

`hstack` does not queue or globally cap `exec` commands. Separate invocations launch in parallel so
a dedicated target can use all of its CPU and memory. The invoked tools may still contend for their
own package locks, generated directories, ports, databases, simulators, or other exclusive
resources. Partition agent lanes by package or output ownership when those resources overlap; file
sync itself is not a command scheduler.

Capacity changes affect new work; they do not migrate commands that are already running. The
editing VM also continues to host Agent sessions and Stack control processes, while a freshly
restarted worker begins with no retained process load. A temporarily lower worker load therefore
does not by itself mean dispatch is bypassing it. Use the TUI execution-fabric pane or its retained
provenance to compare recent admissions, and inspect long-running local work separately.

The remote repository is an execution mirror, not a second authoring checkout. Keep source edits,
formatting, source-generating codemods, Git mutations, and commits on the authoritative computer.
Remote tests and builds may write ignored target-local outputs such as `node_modules`, build
directories, coverage, and caches. Mutagen's `one-way-replica` mode can overwrite source changes
made directly in the remote mirror.

## Keep synchronization independent of Stack

For remote commands to remain available while Stack starts, stops, or rebuilds, start the canonical
Mutagen project independently:

```bash
# Start synchronization in the background. Mutagen remains the only resident owner.
node ./apps/stack/scripts/repo_local.mjs dev-targets sync-service start --detached

# Or keep this command attached and see live Mutagen activity.
node ./apps/stack/scripts/repo_local.mjs dev-targets sync-service start

node ./apps/stack/scripts/repo_local.mjs dev-targets sync-service status
node ./apps/stack/scripts/repo_local.mjs dev-targets sync-service stop
```

Detached mode does not leave a Stack or Node wrapper running. Mutagen's daemon owns the live
sessions. `start` resumes and checks each configured synchronization session; it does not install
dependencies or build outputs. Command and service preflight own executable/dependency readiness.
In 0.3 development, command-only and captured-build workers synchronize on demand through the
forced barrier before dispatch. Their source endpoints use Mutagen's `no-watch` mode. Runtime
service hosts and configured QA service pools keep watching, even when they also run commands.
Startup seeds a newly created unwatched session through that same flush barrier before command
admission; resuming an already scanned session does not force another startup scan.
Synchronization includes the checkout by default, excluding the existing artifact, cache, and
security paths. New packages, package-root files, and root files synchronize without regenerating
the project. Keep unrelated clones outside the checkout to avoid synchronizing them.
Dependencies and published plugin artifacts remain target-local. Service status uses current session
health; the separately reported startup preparation history can retain an earlier, recovered error.
A one-way replica can occasionally retain ignored generated files after their local source root is
deleted. On startup, the sync service repairs that narrow conflict only when the local root is still
absent and the remote residue is limited to target-local generated artifacts. Source conflicts,
unknown paths, and roots that reappear locally remain untouched and keep the target unavailable for
inspection.
A configured Windows mirror remains sync-only because the native automatic execution launcher does
not select Windows. `status` reports synchronization transport separately from command readiness.
When Stack starts, it renders synchronization from every
configured target—even when only a subset runs commands or services—detects the equivalent
independent project, borrows it, and shows
the same synchronization activity in the TUI without pausing, resuming, replacing, or terminating
it. Stopping Stack therefore leaves independent synchronization active. `sync-service stop` pauses
and releases that independent project so a later Stack generation can own its lifecycle again.

## What starts automatically

`yarn dev` and `yarn tui` resolve one service plan for the Stack generation. Version 1 configuration
keeps all local services and adds remote daemons. Version 2 starts each requested service at its
configured placement, after the best-effort target preflight described above. Remote preparation
runs independently by target:

1. validate the locally installed Mutagen CLI;
2. borrow the equivalent all-configured-target independent Mutagen project when one exists,
   otherwise create the canonical `one-way-replica` project with every session paused;
3. independently start any target's configured Lima instance and create its directories over SSH;
4. resume that target's Mutagen session when Stack owns the project;
5. install its target-local dependencies with the synchronized lockfile;
6. when the target owns a daemon, copy the current Stack daemon access key into its target-specific
   CLI home;
7. open the required local and/or reverse SSH forwards for that target's services;
8. start one nested `hstack dev --watch` lifecycle containing exactly the target's server, Expo,
   and/or daemon services.

An unavailable target selected during preflight falls back locally rather than making the Stack
unbootable. Version 1's extra target daemons remain background best-effort and do not gate local
services. After remote startup, a worker exit restarts the target lifecycle and reuses a healthy
tunnel; a tunnel exit rebuilds the transport. A slow or retrying target does not delay another ready
target. Windows dependency installation retries transient package-manager failures before reporting
the target as failed.

Each remote daemon builds from source on its own operating system and receives its own machine
identity. It connects to the same Stack server as the local daemon; Stack does not copy the local
machine identity or general settings.

The TUI adds and reports:

- an `execution fabric` pane with cached load/capacity bars, active command reservations, memory
  headroom, PSI when the target exposes it, sample age, last-hour delegation, and the retained
  dispatch spread. It reads the scheduler's existing cache and bounded rotating
  `dev-target-command-load-native/provenance.jsonl` history; opening the TUI does not add another
  remote probe or telemetry writer;
- a `mutagen sync` pane for synchronization output and status;
- one `remote <name>` pane per target for dependency, build, daemon, and reconnect output;
- service placement plus each remote target's `starting`, `running`, or `retrying` status. Remote
  processes are not represented as local PIDs.

Stopping the TUI stops its remote workers and pauses only a Stack-owned Mutagen project. An
independently owned project continues synchronizing. Target-local dependencies and build caches
remain for the next run. `status`, `sync`, and `exec` work with either lifecycle owner; a paused,
missing, conflicted, first-cycle-incomplete, or unhealthy session fails with a diagnostic instead
of silently executing against an abandoned mirror.

To run only the local Stack:

```bash
yarn dev --no-dev-targets
yarn tui --no-dev-targets
```

## Synchronization policy

The local checkout is authoritative. Do not edit the remote mirror: Mutagen may overwrite target
changes.

Stack excludes source-control metadata and target-local artifacts such as `.git`, `node_modules`,
ordinary `dist` directories, `.happier`, coverage output, Rust targets, CocoaPods, and known
review/build artifacts. Dependencies and build output are produced independently on every operating
system. Tracked `dist` content used by the packed external-plugin test fixture is explicitly retained.

The whole `.project` tree is not synchronized because this checkout can contain extremely large
generated maps, transient state, binary QA evidence, and sensitive local journals. The searchable,
source-like surfaces agents need are retained selectively:

- `.project/*.md`;
- `.project/plans/**`;
- `.project/tasks/**`;
- `.project/scripts/**`.

Known giant generated maps, the local audit journal, images, recordings, HAR files, bytecode, logs,
traces, and Finder metadata inside plans remain excluded. This keeps plan and task discovery usable
on the remote machine without turning transient or sensitive project state into part of the mirror.

The initial synchronization and dependency installation can take time. After startup, source
changes are incremental and every remote daemon watches and builds its own target-local mirror.

## Platform notes

### Lima

Use Lima's generated SSH config with `--ssh-config-file`. Add `--lima-instance` and `--lima-home`
when Stack should start that instance automatically. The VM still needs Node.js and Corepack;
`hstack dev-targets doctor` verifies them before the full TUI starts.

### Windows

Use Windows OpenSSH Server and forward-slash target paths. The Stack sends encoded PowerShell
commands, so spaces in paths are supported.

For administrator accounts, Windows OpenSSH may read
`C:\ProgramData\ssh\administrators_authorized_keys` instead of the user's
`.ssh\authorized_keys`. Confirm that the exact configured alias works non-interactively:

```bash
ssh -o BatchMode=yes happier-stack-windows "echo ok"
```

Mutagen documents possible slow or stalled streams with Windows OpenSSH Server. Validate the real
target with `doctor` and one complete `yarn tui` synchronization before relying on it for unattended
QA.

## Troubleshooting

- **Mutagen not found:** install Mutagen locally and confirm `mutagen version`.
- **SSH authentication fails:** make the configured alias work with `BatchMode=yes`; the TUI cannot
  answer password or host-key prompts.
- **Node.js/Corepack check fails:** install them on the target, then rerun `doctor`.
- **A target should not start today:** use `--no-dev-targets`, or remove it from this stack's config.
- **Synchronization diagnostics:** inspect the `mutagen sync` TUI pane, run
  `hstack dev-targets status <name>`, and use the normal `mutagen` CLI when deeper inspection is
  needed. Stack intentionally leaves Mutagen under user control.
