## Core

- Setup (from source): `hstack setup-from-source --profile=dev|selfhost` (deprecated alias: `hstack setup`)
- Run: `hstack start` / `hstack dev`
- Interactive runner (preferred): `hstack tui <...>` (example: `hstack tui stack dev dev --mobile`)
- Stop: `hstack stop`
- Diagnose: `hstack where`, `hstack doctor`, `hstack logs`
- Contribute: `hstack contrib status|ensure-dev|sync|extract|pr`

Common run flags (root commands):

- `--server=happier-server|happier-server-light`
- `--restart`
- `--no-ui`, `--no-daemon`
- `--no-browser`
- `--mobile`
- `--expo-tailscale`
- `--bind=loopback|lan` (aliases: `--loopback`, `--lan`)

Remote development targets:

- Add: `hstack dev-targets add <name> --platform=posix|windows --ssh=<alias> --repo-dir=<path> --cli-home-dir=<path> [--ssh-config-file=<path>] [--stack=<name>]`
- Provision macOS/Linux SSH and add: `hstack dev-targets add <name> --host=<host> --user=<user> [--repo-dir=<path>] [--cli-home-dir=<path>] [--stack=<name>]`
- Inspect: `hstack dev-targets list|path [--stack=<name>]`, `hstack dev-targets show <name> [--stack=<name>]`
- Preflight: `hstack dev-targets doctor [name] [--stack=<name>]`
- Synchronization: `hstack dev-targets status|sync <name> [--stack=<name>]`, or `hstack dev-targets sync-service start [--detached]|status|stop [--stack=<name>]`
- Remote execution: `hstack dev-targets exec <name>|auto [--cwd=<repo-relative-path>] [--env=KEY=VALUE]... [--flush] [--tty] [--stack=<name>] -- <command> [args...]`
- Remove: `hstack dev-targets remove <name> [--stack=<name>]`

See: `/docs/hstack/dev-targets`.

## Stacks

Lifecycle:

- Create: `hstack stack new <name> [--interactive|--non-interactive] [--db-provider=pglite|sqlite|postgres|mysql] [--database-url=<url>]`
- Edit: `hstack stack edit <name> --interactive`
- List/info: `hstack stack list`, `hstack stack info <name>`
- Run: `hstack stack dev <name>`, `hstack stack start <name>`
- Stop: `hstack stack stop <name>`
- Build: `hstack stack build <name>`, `hstack stack build <name> --web|--server|--daemon|--all`, `hstack stack build <name> --activate-runtime`
  - Named stacks pinned to the same repository publish/reuse artifacts through one repository build authority; selecting a snapshot does not restart a running consumer.
  - `--tauri` is still the legacy local `hstack build` flag, not a named-stack artifact/runtime target in v1.
- Activate runtime from existing artifacts: `hstack stack runtime <name> activate --web|--server|--daemon|--all`
- Diagnose: `hstack stack doctor <name>`

Pin a stack to a worktree/checkout:

- `hstack stack wt <name> -- use <spec>`

Server flavor:

- `hstack stack srv <name> -- use happier-server-light|happier-server`

Auth:

- `hstack auth seed` (create the `dev-auth` seed stack)
- `hstack stack auth <name> status|login|copy-from`

Stack-scoped app CLI (runs the Happier CLI/daemon in stack context):

- `hstack stack happier <name> -- <args...>`

Services:

- `hstack stack service <name> install|enable|status|restart|logs|tail`

Menu bar:

- `hstack menubar install --stack=<name> --mode=selfhost`

Typical production-like named-stack flow:

```bash
hstack stack new dev-built --repo=/absolute/path/to/checkout
hstack stack build dev-built --activate-runtime
hstack stack env dev-built set HAPPIER_STACK_RUNTIME_MODE=prefer
hstack stack service dev-built install
hstack stack service dev-built enable
hstack menubar install --stack=dev-built --mode=selfhost
```

Controlled/manual-restart stack:

```bash
# Run from the checkout under test.
node ./apps/stack/scripts/repo_local.mjs stack new agent-qa --repo=/absolute/path/to/checkout --server=happier-server-light --db-provider=sqlite --no-copy-auth --non-interactive
node ./apps/stack/scripts/repo_local.mjs stack env agent-qa set HAPPIER_STACK_RUNTIME_MODE=require
node ./apps/stack/scripts/repo_local.mjs stack env agent-qa set HAPPIER_STACK_EXPO_SOURCE_STACK=<repository-stack>
node ./apps/stack/scripts/repo_local.mjs stack auth <approved-auth-source> -- status --json
# Continue only when the approved source reports auth.ok: true.
node ./apps/stack/scripts/repo_local.mjs stack auth agent-qa -- copy-from <approved-auth-source>
# Select the active complete snapshot already published by the repository producer.
# Do not build or activate a runtime from the controlled consumer.
node ./apps/stack/scripts/repo_local.mjs stack info <repository-stack> --json
node ./apps/stack/scripts/repo_local.mjs stack runtime agent-qa select --json
node ./apps/stack/scripts/repo_local.mjs tui stack start agent-qa --runtime --mobile
```

- Inspect selected versus loaded bytes: `node ./apps/stack/scripts/repo_local.mjs stack info agent-qa --json`
- Load a newly selected snapshot: press `r` in that stack's TUI, or explicitly restart its stack/service.
- Borrowing the repository stack's existing Expo process is the controlled-stack default. Unset `HAPPIER_STACK_EXPO_SOURCE_STACK` only for explicitly strict snapshot-UI QA.
- The first full candidate may still build one shared static web artifact because the server snapshot consumes it; consumers reuse it and do not start or copy their own Expo process.
- `HAPPIER_STACK_RUNTIME_BUILD_AUTHORITY_STACK=<stack>` overrides the repository-derived build authority for an advanced managed-stack setup.
- `--force` is not a general recovery switch: it replaces target auth files only after Account seed compatibility succeeds and rejects conflicting target Account data. Do not use it to repair a controlled stack; re-authenticate an approved source or obtain human direction instead.

Component-only runtime refreshes:

```bash
# UI-only refresh
hstack stack build dev-built --web
hstack stack runtime dev-built activate --web
```

```bash
# Server-only refresh
hstack stack build dev-built --server
hstack stack runtime dev-built activate --server
hstack stack service dev-built restart
```

PR stacks:

- `hstack stack pr <name> --repo=<pr-url|number> [--dev|--start] [--server-flavor=light|full] [--db-provider=...] [--database-url=...]`

## Mobile (iOS)

- Install the shared dev-client app (USB iPhone): `hstack mobile-dev-client --install`
- Install an isolated per-stack app (Release, no Metro): `hstack stack mobile:install <stack> [--device=...] [--name=...]`
- Regenerate native projects (Pods, deployment target patches): `hstack mobile --prebuild [--clean]`

## EAS (Expo Application Services)

EAS wrapper (runs EAS CLI from `apps/ui`, best-effort ensures deps are installed):

- Cloud build: `hstack stack eas <stack> ios|android [--profile production] [--interactive|--non-interactive]`
- Pass-through: `hstack stack eas <stack> <eas args...>`

Sync stack env → EAS Environment Variables UI (project settings):

- `hstack stack eas <stack> env:sync --environment production [--dry-run] [--hide-values]`

See: `/docs/hstack/mobile-ios` (EAS builds per stack).

## Worktrees (`wt`)

Create worktrees (defaults to an upstream-based local worktree):

- `hstack wt new local/<slug> [--from=upstream|origin] [--base=<ref>] [--use]`

PR worktrees:

- `hstack wt pr <pr-url|number> [--use] [--update] [--stash]`

Select the active repo checkout:

- `hstack wt use <spec>`

Status/list/update:

- `hstack wt status <spec>`
- `hstack wt list`
- `hstack wt update <spec>`
- `hstack wt update-all`

Push:

- `hstack wt push <spec|active> --remote=origin`

## Providers

List supported provider CLIs and whether auto-install is available on your platform:

- `hstack providers list`

Install provider CLIs (best-effort):

- `hstack providers install claude,codex,gemini`
- `hstack providers install claude codex gemini`

Useful flags:

- `--dry-run` / `--plan` (show what would run)
- `--force` / `--reinstall` (re-run installer even if already installed)
- `--json` (scripting)

See also: `/docs/providers`.

## Remote

Provision a remote machine over SSH (install Happier, pair credentials, optionally install/start the background service):

- `hstack remote daemon setup --ssh user@host [--channel stable|preview|dev] [--service user|none]`

Provision a remote machine over SSH to run the self-hosted server as a managed service:

- `hstack remote server setup --ssh user@host [--channel stable|preview|dev] [--mode user|system] [--env KEY=VALUE]...`

See:

- `/docs/hstack/remote-daemon`
- `/docs/hstack/remote-server`

## Self-host runtime (`self-host`)

Install and manage the self-host runtime (server + optional UI web bundle) as a managed service:

- Install: `hstack self-host install [--channel stable|preview|dev] [--mode user|system]`
- Status: `hstack self-host status`
- Manual update: `hstack self-host update`
- Roll back: `hstack self-host rollback --to <version>`

Auto-update scheduling (opt-in):

- Enable daily window: `hstack self-host install --auto-update --auto-update-at=03:15`
- Change schedule after install: `hstack self-host config set --auto-update --auto-update-at=03:15`

Config inspection / tweaks:

- View: `hstack self-host config view`
- Set (and apply scheduler changes): `hstack self-host config set ...`
- Set (write only): `hstack self-host config set ... --no-apply`

Related Happier CLI surfaces used by setup/repair workflows:

- Default release channel: `happier self release-channel use stable|preview|dev`
- Managed Relay runtime bind flags: `happier relay host install --lan|--expose|--host <ip>`
- Local Relay aliases: `happier relay use --local`, `happier relay add --local`, `happier relay set --local --use`
- Repair existing drift/broken state: `happier doctor repair`

`happier setup` configures this computer for a Relay, auth, background service, and providers. `happier doctor repair` is the supported repair path once setup already exists and state has drifted.

## Contributor workflows (`contrib`)

These commands help you work with a long-lived `dev/` checkout while still producing clean PR branches:

- Ensure `dev/` exists: `hstack contrib ensure-dev`
- Sync `dev/`: `hstack contrib sync`
- Extract a feature branch: `hstack contrib extract <name> --mode=reset|stack [--push] [--open]`
- Print/open PR URL: `hstack contrib pr <branch> [--open]`
