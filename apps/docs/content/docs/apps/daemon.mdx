## What is the background service?

The Happier **background service** keeps Happier available on your machine.

In practice, it starts and manages sessions even when you do not have a terminal open. This is especially important for features like **remote start** from the app or web UI: the local runtime on your computer receives that request and launches the session locally.

It also helps the CLI:

- keep long-running sessions alive
- reconnect to and manage existing sessions
- support remote control / orchestration features without requiring your terminal to stay open

## Machine Pools

Machine Pools are a per-Home capability. A self-hosted Home offers them unless its
operator sets `HAPPIER_FEATURE_MACHINES_POOLS__ENABLED` to a false value.

> **Availability:** Machine Pools are in the current unreleased 0.3 checkout; the rest of this page describes the released background service. Stable 0.2 has no Pools — check the version of the server binary you are running.

A Machine Pool is a named group of your own persistent Machines on one Home. In
**Settings → Machines**, you can create a Pool, give it an optional description,
enable or disable members, and place members in priority tiers. Offline Machines can
stay in a Pool so you can configure or repair it before they reconnect.

Each save replaces the whole definition together: its details, enabled members, and
tiers share one revision. If another device saved the Pool first, Happier reports the
conflict and keeps your unsaved form so you can reload the current definition. Empty
Pools are valid. Deleting a Pool leaves already selected exact Machines unchanged
and does not delete Machines or stop Sessions running on them. A shared credential
that uses the Pool as its broker location loses that location and needs a new one
before brokered use can continue.

Pool names, descriptions, membership, and priority settings are administration data
that the Home can read, including when your Account uses end-to-end encryption. Do
not put secrets in a Pool name or description. Machine and Session content keeps its
existing encryption behavior.

In **New Session**, a Pool appears in the same **Run on** picker you already use to
choose a specific machine. Happier asks that Home to choose an available member from the
first eligible priority tier, then starts the session on the returned exact Machine.
Machines in the same tier are spread deterministically across separate session
requests.

Availability is an observation, not stored capacity. A Pool can therefore remain
visible while its Home is signed out, loading, or temporarily unable to observe
Machine presence, but it is unavailable for a new selection until that Home has a
current projection. A failed request keeps the definition or draft available for
recovery. Refresh the Home, choose a specific Machine, or deliberately choose the
Pool again; Happier does not silently rotate an existing exact target.

The background service receives that exact Machine target and, when it advertises
support, a small informational Pool origin. Without that support, Happier omits the
origin before starting the Session. The service does not monitor the Pool or
automatically move, retry, or fail over the session if the chosen Machine becomes
unavailable. Pool availability means a
member is generically connected; the usual Agent, Provider, folder, permission, and
launch checks still apply before a session can start.

Machine Pool support is decided separately for each Home. A current client hides
Pool controls for a Home that does not advertise the feature — see [feature
environment variables](/self-hosting/feature-env) — while ordinary exact-Machine
session creation continues to work there. Saves notify your other connected
clients through the Account change feed; the notification carries only the Pool
identity, and each client reloads the definition from that same Home.

Six generated Actions are also exposed for listing, reading, creating,
updating, deleting, and resolving personal Machine Pools. They use the same
authenticated Home and Account permissions as the UI. They do not make Pool
membership a permission grant.

<Callout type="warning">
  A **Machine Pool** chooses where work runs. A **Connected Service Pool** groups
  credential sources. They are separate features even where both appear near a
  Session workflow. Choosing a Machine Pool never grants connected-service access.

  A [shared Team credential](/accounts/team-credentials) can use a personal Machine
  Pool as its broker location. For a new broker connection, the source-owning Machines
  report whether that credential source is usable without returning credentials or
  settings; the Home selects one eligible exact Machine, and the ordinary broker path
  continues there. Capacity-aware admission and Team-owned Pools do not exist today.
  Machine sharing is incomplete 0.3 development work and has not shipped.
</Callout>

For the surrounding launch flow, see [Start a new session](/sessions/start-a-session).
When starting from a project or an existing Session, also see [New session
shortcuts](/sessions/new-session-shortcuts).

## Embedded terminal support

The in-app embedded terminal also depends on the background service.

That is what allows Happier to:

- create the terminal session on your machine,
- reconnect to that same terminal after refresh/navigation,
- stream output back into the app UI,
- resize and restart the terminal from the app.

If the background service is not running or the machine is unreachable, the embedded terminal cannot work.

Full guide: [Embedded terminal](/extras/embedded-terminal).

## Agent authentication and Provider support

Agent login flows in Agent settings depend on the background service because Happier runs the real Agent CLI on the target machine. Provider probing, local discovery, and scoped credential materialization also happen in the background service rather than the browser.

That is what allows Happier to:

- launch Agent login commands on the selected machine
- stream the Agent's terminal output back into the app
- detect URLs printed during login flows
- refresh machine-local auth state after the login flow exits

Full guides: [Agent authentication](/agents/provider-authentication) and [Provider integrations](/agents/provider-integrations).

## Local memory search support

Local memory search also depends on the background service.

That is what allows Happier to:

- build the machine-local memory index
- maintain light or deep transcript indexing in the background
- run optional local embeddings models on the machine
- query the local index from the app/web UI

Because the index is machine-local, memory search is scoped to the specific machine where the background service runs.

Full guide: [Local memory search](/organize/local-memory-search).

## When does it run?

You can run it in two ways:

- **On-demand**: start it when you need it (some CLI commands may start it automatically).
- **Automatic startup (recommended)**: install it as a **user service** so it starts after login and keeps running in the background.

Why automatic startup is recommended:

- It makes your machine **ready to start sessions remotely** at any time.
- It avoids “why can’t I start a session?” situations where the background service simply is not running yet.
- It’s the smoothest experience on headless servers (or laptops you want to control remotely).

## Common commands

```bash
happier service status
happier service start
happier service stop
happier service list
happier service logs
```

`happier daemon ...` remains available as a legacy alias for background-service commands.

## Release lanes

The background service follows the CLI/runtime lane you installed on that machine:

- `stable` CLI install -> stable background-service runtime
- `preview` CLI install -> preview background-service runtime
- `dev` CLI install -> dev background-service runtime

Default-following automatic startup tracks the selected managed release channel. To inspect or change that default:

```bash
happier self release-channel status
happier self release-channel use stable
happier self release-channel use preview
happier self release-channel use dev
```

When you change the default release channel, Happier syncs the shims and runs or prompts for the background-service restart follow-up when a default-following automatic startup entry is installed.

Updater commands stay lane-specific:

```bash
happier self update
hprev self update
hdev self update
```

There is no separate public background-service installer endpoint today. Install the CLI first, then use setup or service commands on the machine you want to configure.

### Side-by-side installs (stable vs preview vs dev)

You can install all three public lanes side-by-side (`happier`, `hprev`, `hdev`) without them overwriting each other.

Runtime state is lane-scoped, and automatic startup entries (LaunchAgent/systemd/Scheduled Task) use lane-scoped service identifiers.
To inspect the exact service name/label/unit on your platform, run:

```bash
happier service paths
hprev service paths
hdev service paths
```

Recommendation: keep only one lane’s automatic startup entry enabled for a given Relay profile unless you have a specific reason to run multiple local runtimes concurrently.

### The desktop app's own service

> **Availability:** in the current unreleased 0.3 checkout. Stable 0.2 desktop setup follows the default server profile.

Each Home runs its own background service. When the desktop app sets up this computer for a Home it selected, such as your Personal Home, it:

- saves that Home as a server profile **without making it your default**, so `happier` in your terminal keeps using the server you chose;
- installs a service **pinned** to that Home, next to any service you set up yourself (Cloud, a self-hosted server, another account) — it never repoints or restarts yours;
- when asked to replace conflicting services, removes only the ones serving that same Home, never other Homes' services.

The app decides which service serves a Home from the services that exist, not from your terminal's current server: a Home's own pinned service stays its service even if you later run `happier server use` for that Home, and a Home with no service gets its own pinned one. Only when your existing default-following service already serves that Home (your terminal follows it and the Home has no pinned service) does the app use it instead of adding a second one. If you run `happier server use` for a Home whose own pinned service is running, your default background service stands by for it rather than running a second daemon for the same Home: the command names the Home's service and offers to restart the default one only so it stops serving the server you left, and the default service follows the next server you select. If you stop the Home's own service, the default background service serves that Home again. The app's Settings, tray and status all describe and control the service of the Home the app is using, not whichever server your terminal follows. If the CLI has two saved profiles for the same address (for example after you erased and recreated your Personal Home), the app picks the one for that exact Home and refuses to guess when it cannot tell. Desktop setup also needs a CLI that can save a server profile without selecting it; with an older CLI it stops with a named error instead of switching your terminal's server.

The desktop app also never switches your default release channel: a preview app next to a stable CLI keeps `happier` on stable.

To see every installed service and which Home it serves:

```bash
happier service list
```

## Always-on: install as a user service

Install for your current default server profile:

```bash
happier service install
```

Advanced lifecycle control (and dry-run planning):

```bash
happier service status
happier service install --dry-run
happier service restart
```

Platform notes:

- **macOS**: LaunchAgent
- **Linux**: `systemd --user`
- **Windows**: Scheduled Task (user-level)

To remove it:

```bash
happier service uninstall
```

On Windows, `happier service paths` prints the Scheduled Task name and wrapper path.

## Headless authentication (no TTY)

On headless servers (or anywhere you don’t have an interactive TTY), use:

```bash
happier auth login --no-open --method web
```

This prints an authorization URL and waits until you approve it in your browser (the request can expire; if it does, rerun the command).

### Recommended: remote pairing over SSH

If you have SSH access, run this from a machine already authenticated to the Home you want the remote machine to join:

```bash
happier auth pair-remote --ssh user@host --json
```

This carries the selected Home's strict target through remote request, local approval, and credential write without copy/pasting URLs. To target another saved Home without changing the default, use `happier --server <saved-home> auth pair-remote --ssh user@host --json`. URL-only flags remain advanced HTTPS compatibility aliases.

## Troubleshooting

- **Check status**: `happier service status`
- **Find logs**: `happier service logs`
- **Service paths**: `happier service paths`
- **Repair drift or broken state**: `happier doctor repair`
