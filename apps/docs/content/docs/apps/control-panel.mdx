The desktop app is the main control panel for Happier setup and machine management.
It hosts the full-screen onboarding wizard, plus the settings surfaces for Relay, machines, remote hosts, and local relay control.

Use it to keep four things aligned:

1. **Relay selection**
2. **Account sign-in**
3. **Background service and machine setup**
4. **Optional secure access for self-hosted Relays**

## Recommended flow

### 1. Choose your Relay first

Open the desktop app and choose the Relay you want to use before creating or signing into an account.

This avoids the common mistake where:

- the app signs into one Relay
- the CLI or background service points at another Relay
- terminal/background-service setup later looks “broken” even though the account is valid

### 2. Sign in on that Relay

After selecting the Relay, sign in or create an account there.

The app keeps account state scoped to the selected Relay, so switching to another Relay later does not overwrite the first one.

### 3. Set up a machine

From the desktop app, you can choose between:

- **Set up this computer** — configure the local background service against the active Relay
- **Add machine over SSH** — set up a remote machine from the desktop app

The primary entrypoint for these flows is the in-app **Setup wizard** (a full-screen onboarding modal, not a settings page).

User guide: [Setup wizard](/apps/setup-wizard).

The local flow is best when the background service should run on your laptop or desktop. The SSH flow is best when the background service should run on a remote box but you still want to manage it from your laptop.

## What the control panel can manage

### Relay settings

Use the Relay settings screen to:

- add and save multiple Relay profiles
- switch the active Relay
- see when the background service is connected to a different Relay
- repair Relay drift from the app instead of redoing setup manually

The relay selection list also uses reachability state directly:

- unreachable rows stay selected if they are the active Relay
- the row menu stays available for retry/remove actions
- `Continue` stays disabled until you choose a reachable option

### Machines

Use the Machines screen to:

- set up the current computer
- set up a remote machine over SSH
- continue provider setup for the specific machine that was just prepared

If you repeatedly manage the same SSH targets, save them as **Remote hosts** in settings and reuse them in the setup wizard.
Saved remote hosts are synced, so the same host list can follow you across devices when your policy allows it.

User guide: [Remote hosts (SSH)](/apps/remote-hosts).

In the 0.3 development Machine picker, **On a computer you control** groups
local runtimes, **Cloud sandboxes** groups hosted sandboxes, and **Cloud
servers** groups hosted servers. Crabbox's local-container mode runs on a
computer you control; its coordinator-backed mode is cloud-hosted.

The Docker container option creates a managed child from an image, with an
optional setup script. It uses Docker or Podman on the selected computer. An
optional workspace folder can bind host files; otherwise the workspace uses a
container-owned volume. File or inline Dev Container configuration is an
advanced option. See [Devcontainer child machines](/organize/projects-and-worktrees#devcontainer-child-machines).
This is unreleased 0.3 development behavior.

In 0.3 development, a created machine's detail can show which Session or task it
was created for, even when its retention choice is Keep. If that lookup fails,
the section shows a warning with **Retry**. Retry reads that relationship again;
a failed lookup does not mean the machine had no source or change its retention
rule.

#### Local virtual machines (0.3 development)

Lima, Lume, Cua local sandboxes (container and QEMU runtimes) and newly created Cua Spaces are under development for 0.3. They are not released managed Machine support. The selected computer must have the native runtime installed and be reachable; a phone or browser controls that computer rather than running the guest itself.

On macOS, Cua QEMU also needs the `cua-netgw` network gateway. The pinned Cua
0.27.5 macOS archives omit it. When your Mac has QEMU and Cua cannot find the
gateway, Happier shows that requirement and marks the QEMU option unavailable.
Use a Cua installation on that Mac that can find the gateway, then check the
option again.

For Lima, choose a human-readable machine name; Happier generates the native
instance name. There is no separate native instance-name field. Recovery and
cleanup keep the recorded storage and native identity, including after you edit
the VM's CPU, memory or disk through Lima.

New Lima machines default to 4 GiB of memory. Create requires at least 2 GiB
because measured agent Session startup peaked at 1.80 GiB. If Create refuses the
size, choose 4 GiB in the size controls.

Lume requires an Apple silicon Mac, a qualified image with a private SSH setup path, and Lume's own server running on that Mac (`lume serve`): Happier does not start it, and the Lume card says so while the server isn't answering. In 0.3 development, a missing Lume command offers **Install Lume**, which downloads the verified native app bundle after confirmation. This does not start the server or create a VM. A Cua card that finds its command missing, or Cua older than the supported version, names that state and where to get or update it. Storage and the Happier-generated VM name identify the guest together. macOS virtual machines belong to Lume alone: Cua does not offer a Lume runtime. Cua creation selects the local runtime and image explicitly. Runtime and image determine supported power operations, disk retention and display capture. Native installation and image licenses must be checked separately; an installed SDK does not grant permission to redistribute every native component.

In 0.3 development source, a custom Lume image can declare its prepared Linux or macOS SSH account explicitly. It must support Lume's native default-password setup path; choosing an operating system does not infer a login or qualify an arbitrary image. Setup checks the observed guest operating system before installing the controller-held public key. CPU, memory, disk size and storage remain reviewed inputs rather than guessed hardware presets.

With Lume 0.6.1, if macOS rejects the guest's memory setting after Lume accepts the start, Lume does not report the failure to Happier. The guest stays in the starting state until you select **Cancel**. Then select **Delete** for the failed guest before creating it again with a supported memory setting.

In this development version, Happier enables Lume's image cache during host preparation before creating a guest, keeping any cache directory you already configured. The Lume card reports whether caching is enabled, disabled or unavailable to check. If enabling it fails, creation continues with a warning; Lume can still download the image normally.

For qualified published macOS images, **Prepare** installs the CLI and reusable Setup steps in a separate base VM, then stops it. Each sandbox clones that base. The base contains no Happier sign-in or controller SSH key; its SSH host keys are removed so macOS generates a fresh host identity in each clone. Guest access uses the image's published initial login after SSH host trust is approved. Each clone receives its own controller-held key, then disables password SSH. An interrupted build can be inspected and deleted without treating an incomplete VM as ready.

A local Cua sandbox or Space that is unused for the selected time is parked with Cua's native suspend (memory kept, nothing deleted) and wakes when work arrives; only a rule you set to Delete removes it. Cua's Stop and Suspend are the same native suspend, so a suspended machine offers one way to wake, not two.

Installation retry uses the retained guest. An unreachable controller or failed native read does not prove that it has been deleted. For a created Cua Space, removing its registry entry alone is incomplete cleanup: the owned sandbox must also be deleted. Existing VMs and Spaces use ordinary connection setup and do not acquire managed deletion authority.

#### Coder workspaces (unreleased development)

The Coder machine integration is under development for 0.3 and is not released.
It runs Happier inside a selected workspace agent. Files, SCM and Agent execution
therefore use that workspace's computer.

Setup uses a reachable controller Machine with the Coder CLI installed, and a
Connected Account containing your deployment URL and personal Coder token.
The controller checks the saved token when you check or use the connection.
Install the CLI version that matches your deployment on the controller Machine
before setup. See [Coder's CLI installation guide](https://coder.com/docs/install/cli)
and your deployment's installation instructions at `<deployment>/install.sh`.
Happier uses that system executable through its managed-dependency owner.
The guest must provide the POSIX shell commands used by native installation.
Choose a template or template version, an explicit agent name, and the template's
parameter values. Template presets can supply values; required parameters still
need values accepted by Coder. Full conditional template forms and resizing are
outside this first version.

Start, Stop and Delete affect the whole Coder workspace, including sibling
resources. Storage retention depends on the template: use a persistent home to
retain Happier's Machine identity across Stop and Start. Coder's own scheduling
and dormancy rules still apply; Happier does not keep the workspace awake or
automatically reactivate a dormant workspace. A running workspace with a
disconnected agent remains running, while Happier reports its connection
separately. Reconnect the Coder account if its token is rejected or the deployment
configuration changes.

#### Cloud Machines (0.3 development)

Hetzner, DigitalOcean Droplets and Fly Machines integration is under development
for 0.3; it is not released managed Machine support. Cloud creation needs a
selected cloud account. DigitalOcean creation runs from the Account in a native
app with SSH support, without a controller Machine; browser SSH bootstrap is
unavailable. Other integrations use their declared execution host. A native
resource becomes a Happier Machine only after protected installation and ordinary
enrollment.

Stopped [Hetzner servers](https://docs.hetzner.com/cloud/billing/faq/) and
[DigitalOcean Droplets](https://docs.digitalocean.com/products/droplets/details/pricing/)
continue to incur compute charges. Native prices keep their currency and billing
unit; an hourly price is not converted into a guessed monthly cost. Retained
storage and network attachments can have separate charges.

In 0.3 development source, Fly uses the selected image, defaulting to Ubuntu,
and keeps Happier and the workspace in a volume-backed home. After installation
and enrollment, its boot configuration starts the foreground daemon. Stopping
resets the root filesystem while keeping the volume. Stop and suspension do not
promise RAM continuity, and a resume may cold-start. Real Fly cold-boot continuity
still needs qualification against an authorized vendor resource.
Deleting a Machine does not authorize deleting an existing app or an attached
pre-existing volume. Cleanup that has not been confirmed remains visible, with
possible charges; an unavailable controller does not prove deletion.

In 0.3 development source, Cua BYOC selects a cloud-account reference and a Cua
login separately. Both refer to the same existing native Cua setup on the chosen
controller; creation checks the selected cloud, region, image, size and native
lifetime without changing that setup. The native lifetime is whatever the Cua
connection is configured with: a connection with no TTL can be kept until you
delete it, while a finite TTL (Cua's default connection TTL is 8 hours, so most
AWS/GCP connections are finite unless you changed it) means the machine is
deleted when it expires, and Happier then offers deletion rather than Keep.
Modal lifetimes are always finite. These are distinct choices, not a shared
promise of indefinite compute. Existing Spaces use ordinary connection setup,
without managed deletion authority.

Cua can also give a coding agent its own computer tools directly:
`cua agents setup` registers them for Claude Code or Codex on that computer.
That path is outside Happier, so Happier's approvals, consent and transcript do
not apply to what those tools do. To keep every computer action under Happier's
approvals, do not run it; Happier's own computer tools and managed Machines use
the same Cua runtime through Happier.

Cua Cloud and Fleets ended on 2026-10-18, so remote Cua compute is BYOC on your
own cloud account. Real BYOC installation and cleanup still need qualification
against authorized native resources; this is not released managed Machine support.

#### Managed sandbox creation (0.3 development)

Docker Sandboxes, Modal, Vercel Sandbox and Crabbox integration is under development for 0.3; it is not released managed Machine support. Native allocation alone does not establish that Happier is installed, connected or ready to run a Session.

The Docker Sandboxes and direct Crabbox checks use the installed command's
readiness rather than requiring one exact researched version. Native output and
resource identity still have to be understood; removing the version pin does not
promise compatibility with every future native release.

- **Docker Sandboxes:** creating a sandbox alone does not keep it running. Docker documents separate foreground sessions and a detached running mode; the selected native version and guest daemon lifetime must be qualified before managed creation is available. This integration is separate from ordinary Docker containers and Devcontainers. See [Docker's sandbox usage guide](https://docs.docker.com/ai/sandboxes/usage/).
- **Modal:** creation reviews the existing App, image, CPU, memory and finite native duration together. The duration is not an observed expiry timestamp; an unknown deadline stays unknown. Expiry or termination ends that resource; creating another Sandbox from a snapshot creates a new resource and cannot resume the expired Machine. See [Modal's Sandbox guide](https://modal.com/docs/guide/sandboxes).
- **Crabbox:** recovery must target the retained lease, backend and namespace. Current development source uses the selected coordinator for cloud backends; direct local-container creation uses native warmup from private non-repository staging and temporary host-owned SSH key delivery. Native lease records remain the recovery authority. Retention flags do not remove native expiry, and ending a lease can release its resource. A setup that copies the authoritative workspace or uploads enrollment credentials is unavailable. Uploaded scripts are not a private credential channel. See the [Crabbox v0.71.0 run contract](https://github.com/openclaw/crabbox/blob/v0.71.0/docs/commands/run.md).

##### Vercel Sandbox

Managed Vercel Sandbox creation is in unreleased 0.3 development source.
End-to-end Sandbox creation with Vercel sign-in still needs live validation.
Connect Vercel by signing in or using a personal access token, and select the
team and project that will host the Sandbox. A team-only account returns
`vercel_project_required`. Use the account link shown with that reason to
[choose a project](/plugins/services/auth-connected-services#choose-a-project-for-vercel-sandboxes).
The guest must reach your Home outbound over the public internet.

The planned creation review includes the image, region, CPU, run timeout and
snapshot retention. Vercel's default image is `vercel/sandbox/universal:latest`;
custom images must be prepared for `linux/amd64` in Vercel Container Registry.
Vercel allocates 2 GB of memory per vCPU, with 1 or an even number of vCPUs and
plan-specific ceilings.
See [Vercel images](https://vercel.com/docs/sandbox/concepts/images) and
[resource limits](https://vercel.com/docs/sandbox/pricing#resource-limits).

The planned controls are Start, Stop, Resume and Delete, without Suspend. In Vercel,
stopping or reaching the timeout preserves files when snapshotting succeeds,
while running processes end. Resume starts a fresh VM; the integration must
restart the enrolled Happier daemon. Inspection must not wake a stopped sandbox
or create a replacement when a snapshot
is missing or expired. Vercel's default run timeout is five minutes, with a maximum
of 45 minutes on Hobby or 24 hours on Pro/Enterprise. Automatic timeout extension
and sandbox rotation are outside the planned integration. See [Vercel runtime limits](https://vercel.com/docs/sandbox/pricing#runtime-limits).

The planned Keep policy cannot remove the run deadline and requires explicit
snapshot retention. Retained snapshots can incur storage charges after compute
stops. Deleting the sandbox alone does not finish cleanup: its owned snapshots
must also be accounted for. Vercel preserves snapshots another sandbox still
uses; surviving snapshots or uncertain cleanup must remain visible with possible
storage charges. Same-Machine recovery and complete cleanup still need qualification
against an authorized Vercel resource. See
[Vercel persistence and deletion](https://vercel.com/docs/sandbox/concepts/persistent-sandboxes#delete-a-sandbox).

### Local self-hosted Relay runtime

If you are running a self-hosted Relay locally, the app can also manage the local Relay runtime:

- inspect status
- install or update it
- start or stop it
- surface the local Relay URL

### Private access for other devices

For local or self-hosted Relays, the app can guide secure private access setup so phones or other computers can still reach the Relay without exposing it publicly.

Today this is surfaced as a local secure-access task from the desktop app.

User guide: [Relay access](/apps/relay-access).

## Relay drift

Relay drift means the app is using one Relay while the background service is configured against another one.

The desktop app surfaces this explicitly and offers a repair action.

This is important because many “why can’t I connect my background service / terminal / machine?” issues are really Relay mismatches, not auth failures.

## Common setups

### Hosted Relay + local background service

- Choose Happier Cloud in the app
- Sign in
- Use **Set up this computer**

### Self-hosted Relay + local background service

- Add/select your self-hosted Relay in the app
- Sign in there
- Use **Set up this computer**
- Optionally enable private access for phones and other devices

### Self-hosted Relay + remote background service

- Add/select your self-hosted Relay in the app
- Sign in there
- Use **Add machine over SSH**
- Continue provider setup for the returned machine

### Mixed setup (remote Relay + remote background service + laptop control panel)

- Keep the desktop app on your laptop as the control surface
- Run the Relay on one machine
- Run the background service/agents on another machine
- Manage both from the desktop app

## CLI fallback

The CLI still exposes the underlying commands (`server`, `auth`, `service`, and the legacy `daemon` alias), but the recommended user flow is:

- pick the Relay in the app
- sign in there
- let the desktop app drive machine setup actions

That keeps Relay/account/machine state visible and reduces mismatches.

## Web vs desktop

The web app is great for onboarding, status, and settings, but it cannot execute local system tasks on your computer.
If a setup step needs to install a service or run privileged operations, use the desktop control panel (one-click) or copy/paste the provided CLI commands.
