The desktop app is the main control panel for Happier setup and machine management.
It hosts the full-screen onboarding wizard, plus the settings surfaces for Relay, machines, remote hosts, and local relay control.

Use it to keep four things aligned:

1. **Relay selection**
2. **Account sign-in**
3. **Background service and machine setup**
4. **Optional secure access for self-hosted Relays**

## Recommended flow

### 1. Choose your Relay first

Open the desktop app and choose the Relay you want to use before creating or signing into an account.

This avoids the common mistake where:

- the app signs into one Relay
- the CLI or background service points at another Relay
- terminal/background-service setup later looks “broken” even though the account is valid

### 2. Sign in on that Relay

After selecting the Relay, sign in or create an account there.

The app keeps account state scoped to the selected Relay, so switching to another Relay later does not overwrite the first one.

### 3. Set up a machine

From the desktop app, you can choose between:

- **Set up this computer** — configure the local background service against the active Relay
- **Add machine over SSH** — set up a remote machine from the desktop app

The primary entrypoint for these flows is the in-app **Setup wizard** (a full-screen onboarding modal, not a settings page).

User guide: [Setup wizard](/apps/setup-wizard).

The local flow is best when the background service should run on your laptop or desktop. The SSH flow is best when the background service should run on a remote box but you still want to manage it from your laptop.

## What the control panel can manage

### Relay settings

Use the Relay settings screen to:

- add and save multiple Relay profiles
- switch the active Relay
- see when the background service is connected to a different Relay
- repair Relay drift from the app instead of redoing setup manually

The relay selection list also uses reachability state directly:

- unreachable rows stay selected if they are the active Relay
- the row menu stays available for retry/remove actions
- `Continue` stays disabled until you choose a reachable option

### Machines

Use the Machines screen to:

- set up the current computer
- set up a remote machine over SSH
- continue provider setup for the specific machine that was just prepared

If you repeatedly manage the same SSH targets, save them as **Remote hosts** in settings and reuse them in the setup wizard.
Saved remote hosts are synced, so the same host list can follow you across devices when your policy allows it.

User guide: [Remote hosts (SSH)](/apps/remote-hosts).

#### Local virtual machines (0.3 development)

Lume, Cua local sandboxes and newly created Cua Spaces are under development for 0.3. They are not released managed Machine support. The selected computer must have the native runtime installed and be reachable; a phone or browser controls that computer rather than running the guest itself.

Lume requires a Mac and a qualified image with a private SSH setup path. Storage and the Happier-generated VM name identify the guest together. Cua creation selects the local namespace, runtime and image explicitly; it does not fall back to Fleet. Runtime and image determine supported power operations, disk retention and display capture. Native installation and image licenses must be checked separately; an installed SDK does not grant permission to redistribute every native component.

In 0.3 development source, a custom Lume image can declare its prepared Linux or macOS SSH account explicitly. It must support Lume's native default-password setup path; choosing an operating system does not infer a login or qualify an arbitrary image. Setup checks the observed guest operating system before installing the controller-held public key. CPU, memory, disk size and storage remain reviewed inputs rather than guessed hardware presets.

Installation retry uses the retained guest. An unreachable controller or failed native read does not prove that it has been deleted. For a created Cua Space, removing its registry entry alone is incomplete cleanup: the owned sandbox must also be deleted. Existing VMs and Spaces use ordinary connection setup and do not acquire managed deletion authority.

#### Cloud Machines (0.3 development)

Hetzner, DigitalOcean Droplets and Fly Machines integration is under development
for 0.3; it is not released managed Machine support. Cloud creation needs a
reachable controller and a selected cloud account. A native resource becomes a
Happier Machine only after protected installation and ordinary enrollment.

Stopped [Hetzner servers](https://docs.hetzner.com/cloud/billing/faq/) and
[DigitalOcean Droplets](https://docs.digitalocean.com/products/droplets/details/pricing/)
continue to incur compute charges. Native prices keep their currency and billing
unit; an hourly price is not converted into a guessed monthly cost. Retained
storage and network attachments can have separate charges.

In 0.3 development source, Fly uses the selected image, defaulting to Ubuntu,
and keeps Happier and the workspace in a volume-backed home. After installation
and enrollment, its boot configuration starts the foreground daemon. Stopping
resets the root filesystem while keeping the volume. Stop and suspension do not
promise RAM continuity, and a resume may cold-start. Real Fly cold-boot continuity
still needs qualification against an authorized vendor resource.
Deleting a Machine does not authorize deleting an existing app or an attached
pre-existing volume. Cleanup that has not been confirmed remains visible, with
possible charges; an unavailable controller does not prove deletion.

In 0.3 development source, Cua BYOC selects a cloud-account reference and a Cua
login separately. Both refer to the same existing native Cua setup on the chosen
controller; creation checks the selected cloud, region, image, size and native
lifetime without changing that setup. AWS/GCP no-TTL and finite Modal lifetimes
are distinct choices, not a shared promise of indefinite compute. Existing
Spaces use ordinary connection setup, without managed deletion authority.

Cua Fleet uses a selected gateway account and a private resource-specific guest
token. A pending claim retains its identity while binding; retry and inspection
do not acquire another claim or renew its lease. Native expiry is independent of
Happier connectivity. Release deletes only the acquired claim and its private
Secret, never the shared Fleet pool. Real BYOC and Fleet installation and cleanup
still need qualification against authorized native resources; this is not
released managed Machine support.

#### Managed sandbox creation (0.3 development)

Docker Sandboxes, Modal and Crabbox integration is under development for 0.3; it is not released managed Machine support. Native allocation alone does not establish that Happier is installed, connected or ready to run a Session.

- **Docker Sandboxes:** creating a sandbox alone does not keep it running. Docker documents separate foreground sessions and a detached running mode; the selected native version and guest daemon lifetime must be qualified before managed creation is available. This integration is separate from ordinary Docker containers and Devcontainers. See [Docker's sandbox usage guide](https://docs.docker.com/ai/sandboxes/usage/).
- **Modal:** creation reviews the existing App, image, CPU, memory and finite native duration together. The duration is not an observed expiry timestamp; an unknown deadline stays unknown. Expiry or termination ends that resource; creating another Sandbox from a snapshot creates a new resource and cannot resume the expired Machine. See [Modal's Sandbox guide](https://modal.com/docs/guide/sandboxes).
- **Crabbox:** recovery must target the retained lease, backend and namespace. Current development source uses the selected coordinator for cloud backends; direct local-container creation uses native warmup from private non-repository staging and temporary host-owned SSH key delivery. Native lease records remain the recovery authority. Retention flags do not remove native expiry, and ending a lease can release its resource. A setup that copies the authoritative workspace or uploads enrollment credentials is unavailable. Uploaded scripts are not a private credential channel. See the [Crabbox v0.71.0 run contract](https://github.com/openclaw/crabbox/blob/v0.71.0/docs/commands/run.md).

### Local self-hosted Relay runtime

If you are running a self-hosted Relay locally, the app can also manage the local Relay runtime:

- inspect status
- install or update it
- start or stop it
- surface the local Relay URL

### Private access for other devices

For local or self-hosted Relays, the app can guide secure private access setup so phones or other computers can still reach the Relay without exposing it publicly.

Today this is surfaced as a local secure-access task from the desktop app.

User guide: [Relay access](/apps/relay-access).

## Relay drift

Relay drift means the app is using one Relay while the background service is configured against another one.

The desktop app surfaces this explicitly and offers a repair action.

This is important because many “why can’t I connect my background service / terminal / machine?” issues are really Relay mismatches, not auth failures.

## Common setups

### Hosted Relay + local background service

- Choose Happier Cloud in the app
- Sign in
- Use **Set up this computer**

### Self-hosted Relay + local background service

- Add/select your self-hosted Relay in the app
- Sign in there
- Use **Set up this computer**
- Optionally enable private access for phones and other devices

### Self-hosted Relay + remote background service

- Add/select your self-hosted Relay in the app
- Sign in there
- Use **Add machine over SSH**
- Continue provider setup for the returned machine

### Mixed setup (remote Relay + remote background service + laptop control panel)

- Keep the desktop app on your laptop as the control surface
- Run the Relay on one machine
- Run the background service/agents on another machine
- Manage both from the desktop app

## CLI fallback

The CLI still exposes the underlying commands (`server`, `auth`, `service`, and the legacy `daemon` alias), but the recommended user flow is:

- pick the Relay in the app
- sign in there
- let the desktop app drive machine setup actions

That keeps Relay/account/machine state visible and reduces mismatches.

## Web vs desktop

The web app is great for onboarding, status, and settings, but it cannot execute local system tasks on your computer.
If a setup step needs to install a service or run privileged operations, use the desktop control panel (one-click) or copy/paste the provided CLI commands.
