The Happier CLI is the power-user client for:

- installing and updating Happier
- authenticating to one or more servers
- selecting a default server profile or targeting one command
- creating, listing, resuming, attaching to, and managing sessions
- listing machines and targeting an exact machine
- discovering and invoking built-in and plugin-contributed Actions
- running the external Happier MCP server
- inspecting Happier tools and action-driven workflows

## Install

```bash
curl -fsSL https://happier.dev/install | bash
```

Public installer lanes:

- `stable`: `curl -fsSL https://happier.dev/install | bash` -> `happier`
- `preview`: `curl -fsSL https://happier.dev/install-preview | bash` -> `hprev`
- `dev`: `curl -fsSL https://happier.dev/install-dev | bash` -> `hdev`

The installer installs or refreshes the CLI payload and shims for that lane. On a fresh interactive install it continues into `happier setup`; unattended installs and already-configured computers skip that handoff. Run `happier setup` yourself to resume an incomplete first setup.

Windows (PowerShell):

```powershell
irm https://happier.dev/install.ps1 | iex
```

To pass installer flags like `-SetupRelay` or `-Run`, invoke it as a script block:

```powershell
& ([ScriptBlock]::Create((irm https://happier.dev/install.ps1))) -SetupRelay
```

npm fallback (power-user / Node workflow):

```bash
npm install -g @happier-dev/cli
```

Important:

- npm installs expose the npm dist-tags (`@latest` and `@next`).
- The rolling `dev` lane is installer-managed (`install-dev` / `hdev`), not a separate npm dist-tag.

## Updates

How you update depends on how you installed the CLI:

- **Installer install**: run the lane-specific command (`happier`, `hprev`, or `hdev`) with `self check` / `self update` (or rerun the matching installer endpoint). Installer installs keep the full CLI payload under `~/.happier/cli/current` and refresh the selected lane shim for you.
- Stable is `~/.happier/cli/current`; preview/dev use `~/.happier/cli-preview/current` and `~/.happier/cli-dev/current`.
- **npm install**: `npm install -g @happier-dev/cli@latest` (or `@next` for preview). npm does not currently expose a separate public `dev` dist-tag.

For installer-managed installs, the default `happier` shim can follow a selected release channel:

```bash
happier self release-channel status
happier self release-channel list
happier self release-channel use stable
happier self release-channel use preview
happier self release-channel use dev
```

If this computer has a default-following automatic startup entry, changing the release channel also handles the background-service follow-up so automatic startup keeps using the selected lane.

The CLI can also show periodic update notices in TTY sessions; disable with:

```bash
HAPPIER_CLI_UPDATE_CHECK=0
```

Full matrix (all apps/assets): [Updates](/releases/updates).

## Authenticate

```bash
happier auth login
```

`happier auth login` prints both web and mobile connection options (URLs).
By default it prints a single QR code for the mobile deep link, plus the web URL as a fallback.
When using self-hosted servers, run login against the correct server profile (see below).

Recommended first-run flow:

- Use the mobile app path first (QR/deep link) to sign in/create account and approve terminal connection.
- If you already use Happier on another device, sign in with that same account.
- If you open a terminal-connect link while logged out, Happier routes you through sign in and then returns you to terminal approval automatically.

Notes:
- The CLI never needs your secret key directly. For device-key accounts, restore happens in the app (mobile/web UI).
- The target enterprise/keyless flow (mTLS or keyless OAuth) uses the same
  `happier auth login` entry point and a token-only credential with zero Account E2EE
  material. That complete browser/app/daemon flow is still activation-closed; do not
  infer production readiness from `GET /v1/features` fields alone.
- **Terminal connect is separate from account restore.** In the app, use **Scan QR to connect terminal** only for terminal/background-service approval. To sign a phone into the same account, use **Add your phone** on an already-signed-in desktop/web app and **Restore account** on the phone.
- If the mobile QR/deep link does not include a server URL, your current server is probably loopback-only (`localhost` / `127.0.0.1`). Configure the phone to a reachable server URL first, then retry.

Advanced:
- To also print optional “configure server” links (rarely needed): `happier auth login --print-configure-links`

User guide: [Features → Device linking & restore](/accounts/device-linking-and-restore)

## API Tokens (Developer Preview)

API Token authentication for automation is available in the current Developer
Preview source; it is not a released CLI feature yet. Create a token from
**Settings → Account → API Tokens**. Supply it for one invocation without
changing your saved CLI credential:

```bash
happier --api-token 'hap_v1_…' list
```

For unattended automation, provide `HAPPIER_TOKEN` instead:

```bash
HAPPIER_TOKEN='hap_v1_…' happier list
```

`--api-token` is a global prefix flag and takes precedence over
`HAPPIER_TOKEN`. Neither form persists the token. API Tokens authorize broad
account automation but not present-user approvals, API/security-policy changes,
or other security and trust controls.

API-eligible Actions are allowed and unprompted by default. A present user can
change an Action's **External API & SDK** setting to **Ask first** or **Off**
before sharing a token with automation. The same credential-aware Action
transport supports delegated work, planning, and voice-agent runs; these retain
the API Token's account-automation ceiling.

See [API Tokens](/security/api-tokens) for creation, revocation, the one-minute
daemon-local validation-cache limit, and Action settings.

## Discover machines and Actions (Developer Preview)

The root `machines` and `actions` commands are available in the current
Developer Preview source. They use the same Action catalog, schemas, settings,
approval rules, and execution paths as the app, SDK, HTTP API, plugins, and MCP.

### List Account machines

List the machines registered to the current Account before targeting work:

```bash
happier machines list
happier machines list --json
```

Human output shows each machine's ID, label, and current state: active,
inactive, revoked, or replaced. JSON output uses the standard CLI envelope and
places the array at `data.machines`.

The plural `happier machines` command lists Account machines. The singular
`happier machine` command manages remote-machine setup over SSH; it is a
different workflow.

### Search and inspect Actions

Search the catalog by words from an Action's ID, title, or description:

```bash
happier actions search session --limit 10
happier actions search review comments --machine-id <machine-id>
```

An empty query lists the catalog. `--limit` accepts a value from 1 through 100.
The results include both Happier's built-in Actions and Actions contributed by
currently installed plugins.

Inspect one Action before invoking it:

```bash
happier actions get session.status.get
happier actions get acme.notes/actions/save-note --machine-id <machine-id>
```

The human view shows the Action's title, description, safety classification,
and input schema. Use `--json` when another program needs the complete
machine-readable specification.

### Invoke an Action

Pass the Action input as JSON. Omitting `--input-json` sends an empty object.

```bash
happier actions invoke session.status.get \
  --machine-id <machine-id> \
  --input-json '{"sessionId":"<session-id>"}'
```

Plugin-contributed Actions use the qualified ID shown by `actions search`:

```bash
happier actions invoke acme.notes/actions/save-note \
  --machine-id <machine-id> \
  --input-json '{"note":"Remember this"}'
```

Bundled and externally installed plugins use the same discovery, invocation,
settings, approval, and currentness rules. Happier stamps the plugin identity
and invocation authority; callers do not provide either in Action input.

For mutation workflows, `--request-id <id>` supplies the Action request
identifier. Reusing an identifier is safe only where that Action's own contract
documents idempotent handling; the CLI does not automatically replay a failed
mutation.

### Authentication and exact machine targeting

These commands can use either authentication mode:

```bash
# Saved interactive sign-in
happier auth login
happier actions search session

# API Token for this process
HAPPIER_TOKEN='hap_v1_…' happier actions search session

# API Token for one invocation
happier --api-token 'hap_v1_…' actions search session
```

A saved interactive sign-in carries present-user authority. An API Token
carries account-automation authority: it cannot approve its own request or
change the security controls that govern it. Both modes invoke Actions through
the configurable **External API & SDK** surface.

`--machine-id` is an exact target, never a best-effort hint. When the selected
endpoint cannot reach that machine, the command returns a typed target error
instead of silently using another machine. If an Account-server connection has
multiple eligible machines and an Action cannot determine its machine from its
input, use `happier machines list` and pass the intended ID.

When a command talks directly to a daemon, omitting `--machine-id` means that
daemon's current machine. Through the Account server, Happier can relay the
same Action to a NAT-hidden connected machine after exact target selection.

### JSON output and failures

Add `--json` to receive the standard versioned CLI envelope:

- `machines list` returns `kind: "machines_list"` with `data.machines`.
- `actions search` returns `kind: "actions_search"` with `data.actionSpecs`.
- `actions get` returns `kind: "actions_get"` with `data.actionSpec`.
- `actions invoke` returns `kind: "actions_invoke"` with the Action result in
  `data`.

Without `--json`, search and machine results are compact lists, Action details
are formatted for inspection, and Action results are pretty-printed JSON.
Expected input, authentication, settings, approval, placement, transport, and
Action-domain failures exit with status 1. Unexpected internal or dependency
faults exit with status 2. In JSON mode, failures use `ok: false` and include a
stable error code in `error.code`.

## Bootstrap & setup (one-command)

`happier setup` guides initial setup from the terminal. It settles the Relay first, signs in if needed, configures the service, and optionally sets up Agents using the existing Relay, auth, service, Agent, and Relay-access commands.

Use it when you want Happier to do the work instead of only previewing a plan:

```bash
happier setup --relay-url https://YOUR_RELAY_URL
```

Run without a Relay flag and setup asks where your Relay lives — Happier Cloud, a Relay you already run, or one on this computer — before it signs you in. Your account is stored per Relay, so signing in first and pointing at your own Relay afterwards creates a second account instead of moving the first one. Setup asks only when this computer has no account on its current Relay yet; passing `--relay-url` (or `--server`) answers the question up front.

Choosing **On this computer** runs `happier relay host install`. If the installed Relay ends up reachable from this computer only, setup then offers the [Relay access](/apps/relay-access) methods — the same ones `happier relay access` configures — so your phone can reach it.

Useful flags:

- `--skip-daemon` (historical flag name; skips background-service install/enable)
- `--skip-providers` (don’t run provider setup)
- `--provider <id>` (preselect providers to set up)
- `--yes` (with an explicitly named Relay, perform deterministic work and stop before the human-approved sign-in)
- `--non-interactive` (change nothing)

`--yes` without a Relay choice refuses to guess, because that could create an account on the wrong Relay. `--yes` and `--non-interactive` have opposite contracts and cannot be combined.

Dry-run the plan only if you want to inspect the steps before running them:

```bash
happier setup plan --relay-url https://YOUR_RELAY_URL
```

`happier setup plan` previews the work. `happier setup` applies it.
Note: `--json` output is currently supported for `happier setup plan` only.

### Repair an existing setup

Use setup for first-time configuration of this computer. Use doctor repair when an existing install has drifted or broken state: wrong automatic startup lane, stopped background service, stale service definition, missing auth, or mismatched Relay state.

```bash
happier doctor repair
happier doctor repair --report-only
happier doctor repair --json
```

`happier doctor repair` is the supported repair entrypoint. It shares the same repair model used by installer preflight and service diagnostics; `--report-only` prints guidance without applying changes.

Agent-only setup:

```bash
happier agents setup
```

## Remote machine setup (SSH)

If you want to set up a remote machine to run the background service and providers (VPS, home server, dev box):

```bash
happier machine setup --ssh user@host
```

Common flags:

- `--ssh-user <user>` / `--ssh-host <host>` / `--ssh-port <port>` (split SSH form)
- `--install-relay-runtime` (also install the managed Relay runtime on that host)
- `--service-mode user|none` (background-service mode)
- `--relay-runtime-mode user|system` (relay runtime install mode)
- `--ssh-auth agent|keyfile|password` (select auth mode)
- `--identity-file <path>` (for `keyfile` mode)
- `--ssh-config-file <path>` (use an explicit SSH config)
- `--known-hosts-path <path>` (override host-key storage)
- `--trusted-host-key <line>` (pin a host key)
- `--server-url <url>` / `--local-server-url <url>` / `--webapp-url <url>` (target a specific Relay profile)
- `--require-local-approval` (fail closed when the current machine cannot approve the pairing request)
- `--yes` (auto-accept prompts for non-interactive runs)
- `--json` (stream protocol JSON events/results)

SSH auth modes:

- `agent` uses your SSH agent
- `keyfile` uses a private key path
- `password` prompts for a password in the terminal when supported

Tip: if you want to save the host for later reuse in the app, use the desktop Remote Hosts screen instead of a one-off inline SSH bootstrap. The inline SSH bootstrap is intentionally one-off; reusable SSH profiles live in the app.

Self-hosted Relay runtime (managed service):

```bash
happier relay host install
happier relay host status
```

By default this installs the Relay runtime in `user` mode (no root required).
To install as a system-wide service, use `--mode system` (requires root/sudo):

```bash
sudo happier relay host install --mode system
```

Remote host (over SSH):

```bash
happier relay host install --ssh user@host
```

```bash
happier relay host uninstall --ssh user@host
```

Local bind flags:

```bash
happier relay host install --lan
happier relay host install --expose
happier relay host install --host 192.168.1.25
```

- `--lan` binds the local Relay to a private LAN address.
- `--expose` binds the local Relay to all interfaces.
- `--host <ip>` binds the local Relay to a specific local address.

These flags apply only to local `install`; they are intentionally separate from `happier relay access ...`, which configures the share/public URL strategy.

Local Relay profile aliases:

```bash
happier relay use --local
happier relay add --local
happier relay set --local --use
happier relay start-daemon
happier relay auth
```

By default, local Relay aliases target the local Relay installed for the current CLI release channel. Pass `--local-channel stable|preview|dev` to target another installed lane explicitly.

Service lifecycle helpers:

```bash
happier relay host start
happier relay host stop
happier relay host restart
happier relay host uninstall
```

Background service reference: [Background service](/apps/daemon).

## Relay access (share/public URL strategy)

If your self-hosted Relay is only reachable locally (for example `localhost`), other devices (phones, other computers) won’t be able to use it until you expose a reachable Relay URL (often HTTPS).

Inspect and configure the relay access method:

```bash
happier relay access status
happier relay access configure --provider tailscaleServe --upstream-url http://127.0.0.1:53288
```

You can also apply the same configuration on a remote host:

```bash
happier relay access status --ssh user@host
happier relay access configure --ssh user@host --provider tailscaleServe --upstream-url http://127.0.0.1:53288
```

User guide: [Relay access](/apps/relay-access).

### Remote machine pairing (SSH, automated)

If you want to run Happier on a **remote machine** (VPS, home server, dev box) but approve/authenticate it from a machine where you're already signed in:

```bash
happier auth pair-remote --ssh user@host --json
```

Notes:

- This orchestrates a claim-gated pairing flow over SSH (remote request → local approve → remote wait).
- Add `--server ...` or `--server-url/--webapp-url` if you're targeting a self-hosted server.

### Pairing (JSON, manual / scripting)

Split the flow when you want full control (automation, custom SSH, etc):

```bash
# On the remote host (prints a request + publicKey)
happier auth request --json

# On a local machine that's already authenticated (approves the public key)
happier auth approve --public-key <publicKey> --json

# Back on the remote host (waits, claims, and writes credentials)
happier auth wait --public-key <publicKey> --json
```

This is terminal/CLI pairing, not the same flow as device restore inside the app.

## Server profiles

### Save and switch servers

```bash
happier server list
happier server current
happier server add --name company --server-url https://api.company.example --webapp-url https://app.company.example --use
happier server use company
```

`--use` (and `happier server use ...`) sets the **default server** for future commands, so you can usually omit `--server ...` once it’s selected.

### Target a server for one command

Use per-invocation targeting when you do not want to switch the default:

```bash
happier --server company auth login
happier --server personal service status
```

You can also use URL flags:

```bash
happier --server-url https://api.company.example --webapp-url https://app.company.example auth login
happier --server-url https://api.company.example --webapp-url https://app.company.example auth pair-remote --ssh user@host --json
```

## Attach to an existing session

If a supported session is already running, you can reattach to that same live session from a terminal:

```bash
happier attach
happier attach <session-id-or-prefix-or-tag>
```

This is the main “start in the app, continue in the terminal” workflow. In a supported TTY, `happier attach` opens an interactive picker of active sessions:

- **local attachable sessions** are selectable immediately
- **active but non-attachable sessions** stay visible but disabled with a reason
- **remote-capable Agent sessions** are marked as remote; press `P` in the picker to run a reachability check before attaching

If the session is stopped, use `happier resume` instead.

Important notes:

- tmux and other terminal-host attach flows work only for sessions that are still owned by the current machine.
- You must target the same Happier account/server profile that owns the session.

Attach strategy depends on the Agent:

- Some Agents use Happier's `tmux`-backed attach flow.
- OpenCode uses an Agent-native attach flow for server-backed sessions.

For OpenCode, the supported reattach command is still `happier attach <session-id-or-prefix-or-tag>`. Do not rely on a raw vendor `opencode attach ...` command as your normal Happier workflow.

Supported attach styles include:

- **tmux-backed sessions** on machines where tmux is enabled
- **Windows Terminal** or **Console** hosted sessions on Windows
- **Agent-native attach** for supported Agent sessions such as OpenCode

For the full workflow, see [Features → Attach to a running session](/sessions/attach-to-session).

## Resume an inactive session

If a Happier session is inactive but still vendor-resumable, you can resume it directly from the CLI.

### Interactive selector

```bash
happier resume
```

In a supported TTY, Happier shows an interactive picker of resumable inactive sessions.

### Resume by id

```bash
happier resume <session-id-or-prefix-or-tag>
```

You can use a full Session id, an unambiguous id prefix, or an exact Session tag.

Important behavior:

- resume is strict: if the Agent resume fails, Happier errors instead of starting a fresh session
- archived or already-active sessions cannot be resumed
- the command restores the session working directory before launching the Agent again

For the full user guide and the meaning of “resumable”, see [Features → Resume inactive sessions](/sessions/session-resume).

## List sessions

Use:

```bash
happier list
```

The default output is a table that includes session id, agent, recent activity, active state, resume state, title, and path.

Useful variants:

```bash
happier list --resumable
happier list --plain
happier list --json
```

- `--resumable` filters to sessions that can currently be resumed
- `--plain` restores the older one-line output
- `--json` is for scripting

## Session control (non-interactive)

Use the first-class top-level commands for everyday session work:
`spawn`, `list` (or `ls`), `send`, `history`, `wait`, `stop`, and `delegate`.
The established `happier session ...` family remains available for advanced,
administrative, and existing scripted workflows.

These top-level commands are first-class entries in the current development
CLI command registry. They are not released yet; existing released CLI
capabilities such as `attach`, `resume`, session status, archive, metadata
updates, and Action discovery remain under their established commands.

Use `--machine-id <machine-id>` when an automated command must target a known
machine. It is available on these first-class session commands and is especially
useful with an API Token when more than one current machine is available.

Deep reference: [CLI sessions](/apps/cli-sessions), including the shared full-id,
prefix, or tag selector.

### Create a session (scriptable)

```bash
happier spawn --title "My session" --message "Hello"
```

Optional targeting:

```bash
happier spawn --path /path/to/repo --agent <agent-id> --title "My session"
```

`--agent` accepts a friendly Agent id from the installed Agent catalog:

```bash
happier spawn --agent <agent-id>
```

Use `happier spawn` to create a session from the top-level CLI. With
`--follow --jsonl`, its first line is the normal `session_create` envelope
containing `data.session.id`; later lines are compact transcript rows.

### Send messages

```bash
happier send <session-id-or-prefix-or-tag> "ping"
```

Wait for an agent response (useful for scripts; can time out if the agent is busy/offline):

```bash
happier send <session-id-or-prefix-or-tag> "ping" --wait --timeout 60
```

### Status, stop, archive

```bash
happier session status <session-id-or-prefix-or-tag>
happier history <session-id-or-prefix-or-tag>
happier wait <session-id-or-prefix-or-tag> --timeout 60
happier stop <session-id-or-prefix-or-tag>
happier session archive <session-id-or-prefix-or-tag>
happier session unarchive <session-id-or-prefix-or-tag>
```

### Set title / model / permission mode

```bash
happier session set-title <session-id-or-prefix-or-tag> "New title"
happier session set-model <session-id-or-prefix-or-tag> <model-id>
happier session set-model <session-id-or-prefix-or-tag> <model-id> --provider-connection <connection-id|native>
happier session set-permission-mode <session-id-or-prefix-or-tag> <mode>
```

`<mode>` accepts common aliases (for example `ask`, `default`, `yolo`). Use `--json` to script and see the normalized `permissionMode` value.

### Approvals from CLI commands

Some actions can be configured as **approval-gated** on the CLI surface.

In that case, the CLI command does not execute immediately; it creates an approval request instead.
Use the app’s **Inbox** to review/approve/deny and see the final execution result:

- [Inbox and approvals](/sessions/inbox-and-approvals)
- [Happier tools & actions](/extending/happier-tools)

For advanced automation, approvals can also be decided with
`happier session actions execute`:

```bash
happier session actions execute <session-id-or-prefix-or-tag> approval.request.decide --input-json '{"artifactId":"<id>","decision":"approve"}' --json
```

### Action catalog from the CLI

Use the Account-aware root commands to discover and invoke built-in and
plugin-contributed Actions:

```bash
happier actions search [query...] [--limit <n>] [--machine-id <id>]
happier actions get <action-id> [--machine-id <id>]
happier actions invoke <action-id> --input-json '<json>' [--machine-id <id>]
```

See [Discover machines and Actions](#discover-machines-and-actions-developer-preview)
for authentication, exact targeting, contributed Action IDs, JSON envelopes,
and error behavior.

The established session-scoped forms remain available when a workflow already
starts from a session selector:

```bash
happier session actions list
happier session actions describe <action-id>
happier session actions execute <session-id-or-prefix-or-tag> <action-id> --input-json '<json>'
```

### Execution runs (review / plan / delegate / voice agent)

Execution runs are the structured “run” layer for multi-step flows in a session (for example: start a review run, then send follow-up messages, then stop).

```bash
happier session run list <session-id-or-prefix-or-tag>
happier session run start <session-id-or-prefix-or-tag> --intent <intent> --agent <agent-id>
happier session run send <session-id-or-prefix-or-tag> <run-id> "message"
happier session run stop <session-id-or-prefix-or-tag> <run-id>
```

## Happier tools

The CLI also exposes the unified **Happier tools** surface directly.

Use it when you want to:

- inspect which built-in Happier tools are currently available
- inspect which custom MCP tools resolve in the current machine/workspace context
- call one of those tools directly from the terminal

### List tools

```bash
happier tools list
```

Optional:

```bash
happier tools list --directory /path/to/project
```

This lists:

- built-in Happier tools
- custom MCP tools that resolve for the selected directory and machine

`list` does **not** require a session id.

### Call a tool

```bash
happier tools call --session-id <session-id> --source happier --tool action_spec_search --args-json '{"query":"plan mode","limit":5}'
```

Examples:

- `--source happier --tool review_start`
- `--source happier --tool subagents_plan_start`
- `--source happier --tool action_spec_get`
- `--source happier --tool action_options_resolve`
- `--source playwright --tool browser_navigate`

Use the Happier built-in discovery tools when you do not know the exact action id or valid option values yet.

For the broader product model, see [Happier tools & actions](/extending/happier-tools).
