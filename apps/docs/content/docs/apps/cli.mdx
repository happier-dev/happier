The Happier CLI is the power-user client for:

- installing and updating Happier
- authenticating to one or more servers
- selecting a default server profile or targeting one command
- creating, listing, resuming, attaching to, and managing sessions
- listing machines and targeting an exact machine
- discovering and invoking built-in and plugin-contributed Actions
- running the external Happier MCP server
- inspecting Happier tools and action-driven workflows
- backing up, restoring, verifying, and erasing Personal Home data

## Install

```bash
curl -fsSL https://happier.dev/install | bash
```

Public installer lanes:

- `stable`: `curl -fsSL https://happier.dev/install | bash` -> `happier`
- `preview`: `curl -fsSL https://happier.dev/install-preview | bash` -> `hprev`
- `dev`: `curl -fsSL https://happier.dev/install-dev | bash` -> `hdev`

The installer installs or refreshes the CLI payload and shims for that lane. On a capable terminal it introduces Happier with a static Braille planet. On a fresh interactive install it continues into `happier setup`, which picks up the planet without repeating the welcome; unattended installs and already-configured computers skip that handoff. Run `happier setup` yourself to resume an incomplete first setup.

Windows (PowerShell):

```powershell
irm https://happier.dev/install.ps1 | iex
```

To pass installer flags like `-SetupRelay` or `-Run`, invoke it as a script block:

```powershell
& ([ScriptBlock]::Create((irm https://happier.dev/install.ps1))) -SetupRelay
```

npm fallback (power-user / Node workflow):

```bash
npm install -g @happier-dev/cli
```

Important:

- npm installs expose the npm dist-tags (`@latest` and `@next`).
- The rolling `dev` lane is installer-managed (`install-dev` / `hdev`), not a separate npm dist-tag.

## Updates

How you update depends on how you installed the CLI:

- **Installer install**: run the lane-specific command (`happier`, `hprev`, or `hdev`) with `self check` / `self update` (or rerun the matching installer endpoint). Installer installs keep the full CLI payload under `~/.happier/cli/current` and refresh the selected lane shim for you.
- Stable is `~/.happier/cli/current`; preview/dev use `~/.happier/cli-preview/current` and `~/.happier/cli-dev/current`.
- **npm install**: `npm install -g @happier-dev/cli@latest` (or `@next` for preview). npm does not currently expose a separate public `dev` dist-tag.

For installer-managed installs, the default `happier` shim can follow a selected release channel:

```bash
happier self release-channel status
happier self release-channel list
happier self release-channel use stable
happier self release-channel use preview
happier self release-channel use dev
```

If this computer has a default-following automatic startup entry, changing the release channel also handles the background-service follow-up so automatic startup keeps using the selected lane.

Updating another lane (for example `hprev self update`) or letting the desktop app install its own CLI never changes which lane `happier` runs; only `self release-channel use` or the installer's channel choice does.

### Using the desktop app with a CLI you installed yourself

In the current development build (unreleased), when the desktop app sets up this computer and finds
that new terminals run a `happier` it did not install (npm, Homebrew or a manual copy), it asks once,
naming that CLI's version and path:

- **Let Happier manage it** — the app installs its own CLI, puts it first on your `PATH` for new
  terminals, and moves its background service to it. Your old copy is left in place; Settings ›
  This computer › Command line shows the command that removes it (for example
  `npm uninstall -g @happier-dev/cli` or `brew uninstall <formula>`). The app never runs it for you.
- **Keep my own** — the app installs nothing and adds nothing to your `PATH`; the app, its background
  service and your terminal all use your CLI. Updating it stays with you (for example
  `npm install -g @happier-dev/cli@latest`). If it is too old for desktop setup, the app says so and
  names that command instead of replacing it.

The answer applies to every Happier app on this computer. Change it any time in Settings › This
computer › Command line. You are asked again only if the CLI you kept disappears or cannot serve
setup; if it disappears, the app asks before installing anything in its place. Until you answer, the
app adds nothing to your `PATH` in front of your own `happier`.

On Windows, a `happier` on the system-wide `Path` (for example from a machine-wide Node.js install)
still runs first in new terminals after **Let Happier manage it**, because Windows puts the system
`Path` ahead of yours. Remove that copy with the command Settings shows.

The CLI can also show periodic update notices in TTY sessions; disable with:

```bash
HAPPIER_CLI_UPDATE_CHECK=0
```

## Authenticate

```bash
happier auth login
```

`happier auth login` prints both web and mobile connection options (URLs).
By default it prints a single QR code for the mobile deep link, plus the web URL as a fallback.
When using self-hosted servers, run login against the correct server profile (see below).

Recommended first-run flow:

- Use the mobile app path first (QR/deep link) to sign in/create account and approve terminal connection.
- If you already use Happier on another device, sign in with that same account.
- If you open a terminal-connect link while logged out, Happier routes you through sign in and then returns you to terminal approval automatically.

Notes:
- The CLI never needs your secret key directly. For device-key accounts, restore happens in the app (mobile/web UI).
- The target enterprise/keyless flow (mTLS or keyless OAuth) uses the same
  `happier auth login` entry point and a token-only credential with zero Account E2EE
  material. That complete browser/app/daemon flow is still activation-closed; do not
  infer production readiness from `GET /v1/features` fields alone.
- **Terminal connect is separate from account restore.** In the app, use **Scan QR to connect terminal** only for terminal/background-service approval. To sign a phone into the same account, use **Add your phone** on an already-signed-in desktop/web app and **Restore account** on the phone.
- If the mobile QR/deep link does not include a server URL, your current server is probably loopback-only (`localhost` / `127.0.0.1`). Configure the phone to a reachable server URL first, then retry.

Advanced:
- To also print optional “configure server” links (rarely needed): `happier auth login --print-configure-links`

User guide: [Features → Device linking & restore](/accounts/device-linking-and-restore)

## Account security (Developer Preview)

The development CLI can inspect the selected Home's safe Account Security
projection and manage native email/password sign-in from a trusted terminal:

```bash
hdev auth security get
hdev auth password enroll-email-request --email person@example.com
hdev auth password enroll --email person@example.com
hdev auth password change
hdev auth password remove
```

Password enrollment prepares the credential on the selected Home, then asks you
to complete a currently linked OAuth or mTLS login that authorizes that exact
email and prepared credential. OAuth uses the browser and returns to the CLI's
temporary loopback listener; mTLS completes directly. The CLI keeps the prepared
credential and proof in this process only. It does not offer a separate resume or
precomputed-proof command.

Password and recovery-key input uses a no-echo prompt. For bounded automation,
pipe one strict secret document to `--secrets-json-stdin` instead of placing a
password or verification bearer in process arguments:

```bash
hdev auth password enroll --email person@example.com --yes \
  --secrets-json-stdin <<'JSON'
{"v":1,"secrets":{"password":"…","verificationToken":"…"}}
JSON
```

Every password or email mutation requires the selected Home's stored
present-user credential and an explicit confirmation. An authenticated API Token
may run `auth security get`, which returns only the safe projection, but it cannot
perform these mutations.

## API Tokens (Developer Preview)

API Token authentication for automation is available in the current Developer
Preview source; it is not a released CLI feature yet. Create a token from
**Settings → Account → Sign-in & security → API tokens**. Supply it for one invocation without
changing your saved CLI credential:

Run the commands in this Developer Preview section with `hdev`, unless you have
explicitly pointed the `happier` shim at the development lane with
`happier self release-channel use dev`.

```bash
hdev --api-token 'hap_v1_…' list
```

For unattended automation, provide `HAPPIER_TOKEN` instead:

```bash
HAPPIER_TOKEN='hap_v1_…' hdev list
```

`--api-token` is a global prefix flag and takes precedence over
`HAPPIER_TOKEN`. Neither form persists the token. API Tokens authorize broad
account automation but not present-user approvals, API/security-policy changes,
or other security and trust controls.

The ordinary CLI accepts a `hap_v1` bearer across its one-shot child or tmux
continuation. It refuses an encryption-capable `hapc_v1` compound credential
before starting that child: the local wrapping material is never copied into a
child environment or silently reduced to its embedded bearer. Use `hapc_v1`
with the in-process SDK when whole-Action protection is required.

API-eligible Actions are allowed and unprompted by default. A present user can
change an Action's **External API & SDK** setting to **Ask first** or **Off**
before sharing a token with automation. The same credential-aware Action
transport supports delegated work, planning, and voice-agent runs; these retain
the API Token's account-automation ceiling.

See [API Tokens](/security/api-tokens) for creation, revocation, the one-minute
daemon-local validation-cache limit, and Action settings.

## Discover machines and Actions (Developer Preview)

The root `machines` and `actions` commands are available in the current
Developer Preview source. They use the same Action catalog, schemas, settings,
approval rules, and execution paths as the app, SDK, HTTP API, plugins, and MCP.

Run the commands in this Developer Preview section with `hdev`, unless you have
explicitly pointed the `happier` shim at the development lane with
`happier self release-channel use dev`.

### List Account machines

List the machines registered to the current Account before targeting work:

```bash
hdev machines list
hdev machines list --json
```

Human output shows each machine's ID and current state: active,
inactive, revoked, or replaced. JSON output uses the standard CLI envelope and
places the array at `data.machines`.

The plural `hdev machines` command lists Account machines. The singular
`happier machine` command manages remote-machine setup over SSH; it is a
different workflow.

### Search and inspect Actions

Search the catalog by words from an Action's ID, title, or description:

```bash
hdev actions search session --limit 10
hdev actions search review comments --machine-id <machine-id>
```

An empty query lists the catalog. `--limit` accepts a value from 1 through 100.
The results include both Happier's built-in Actions and Actions contributed by
currently installed plugins.

Inspect one Action before invoking it:

```bash
hdev actions get session.status.get
hdev actions get acme.notes/actions/save-note --machine-id <machine-id>
```

The human view shows the Action's title, description, safety classification,
and input schema. Use `--json` when another program needs the complete
machine-readable specification.

### Invoke an Action

Built-in Actions accept friendly field flags derived from their canonical input
schema. JSON remains the escape hatch for nested values and contributed Actions
whose specification is discovered remotely. `--input-json` supplies a base
object and distinct field flags overlay it; supplying the same field twice is an
error instead of silently choosing one value. Omitting both sends an empty
object.

```bash
hdev actions invoke session.status.get \
  --machine-id <machine-id> \
  --input-json '{"sessionId":"<session-id>"}'
```

Plugin-contributed Actions use the qualified ID shown by `actions search`:

```bash
hdev actions invoke acme.notes/actions/save-note \
  --machine-id <machine-id> \
  --input-json '{"note":"Remember this"}'
```

Bundled and externally installed plugins use the same discovery, invocation,
settings, approval, and currentness rules. Happier stamps the plugin identity
and invocation authority; callers do not provide either in Action input.

Use `--` to end option parsing when a positional value begins with a dash. After
that marker, even `--help` and `--json` are literal Action input rather than CLI
flags:

```bash
happier send <session-id-or-prefix-or-tag> -- --help
```

For mutation workflows, `--request-id <id>` supplies the Action request
identifier. Reusing an identifier is safe only where that Action's own contract
documents idempotent handling; the CLI does not automatically replay a failed
mutation.

### Friendly command families derived from Actions

Some Action families also have a friendly command path, so you do not need
`actions invoke` and a JSON body for them. These roots appear in
`happier --help` alongside the hand-written commands:

| Root | Covers |
| --- | --- |
| `happier teams` | Teams, members, and Team policy |
| `happier identity` | Managed identity providers and GitHub Apps |
| `happier credentials` | Team credential resources and their usage |
| `happier secrets` | Shared Saved Secrets |
| `happier workflow` | Running, inspecting, and managing reusable workflows |

Use `happier <root> --help` to list a family's subcommands and flags. Root help,
nested help, completion, and execution are compiled from the same Action
declarations, so a family that dispatches always has a root line and a flag that
appears in help also exists in the parser. No working command is hidden behind a
root you have to guess.

### Authentication and exact machine targeting

These commands can use either authentication mode:

```bash
# Saved interactive sign-in
hdev auth login
hdev actions search session

# API Token for this process
HAPPIER_TOKEN='hap_v1_…' hdev actions search session

# API Token for one invocation
hdev --api-token 'hap_v1_…' actions search session
```

A saved interactive sign-in carries present-user authority. An API Token
carries account-automation authority: it cannot approve its own request or
change the security controls that govern it. Both modes invoke Actions through
the configurable **External API & SDK** surface.

The selected credential resolves one exact Home identity and endpoint for the
complete invocation. Switching the app or CLI's active Home after that point
does not retarget an in-flight Action or combine one Home's identity with
another Home's URL.

`--machine-id` is an exact target, never a best-effort hint. When the selected
endpoint cannot reach that machine, the command returns a typed target error
instead of silently using another machine. If the selected Home has multiple
eligible machines and an Action cannot determine its machine from its input,
use `hdev machines list` and pass the intended ID.

When a command talks directly to a daemon, omitting `--machine-id` means that
daemon's current machine. Through the Home, Happier can relay the
same Action to a NAT-hidden connected machine after exact target selection.

### JSON output and failures

Add `--json` to receive the standard versioned CLI envelope:

- `machines list` returns `kind: "machines_list"` with `data.machines`.
- `actions search` returns `kind: "actions_search"` with `data.actionSpecs`.
- `actions get` returns `kind: "actions_get"` with `data.actionSpec`.
- `actions invoke` returns `kind: "actions_invoke"` with the Action result in
  `data`.

Without `--json`, search and machine results are compact lists, Action details
are formatted for inspection, and Action results are pretty-printed JSON.
The development-only `projects execution output read` and `projects execution
output copy` commands instead write the retained terminal's decoded bytes to
stdout, without adding a newline or converting binary data to text. Redirect
stdout to preserve those bytes. Output gaps are reported separately on stderr;
a gap means the returned bytes are incomplete. `copy` returns retained output,
not a claim that a remote clipboard was changed. With `--json`, both commands
keep the canonical versioned envelope, byte frames and cursors unchanged.
Expected input, authentication, settings, approval, placement, transport, and
Action-domain failures exit with status 1. Unexpected internal or dependency
faults exit with status 2. In JSON mode, failures use `ok: false` and include a
stable error code in `error.code`.

Friendly Session commands resolve a full ID, unambiguous prefix, or tag to one
exact Session before invoking the Action. A missing or ambiguous selector fails
with a typed JSON error (and candidates when available); Happier does not retry
against another Session, Home, Machine, or execution run.

### Shell completion

Generate the completion script for your shell from the same command registry
used by parsing, help, and dispatch:

```bash
happier completion bash
happier completion zsh
happier completion fish
happier completion powershell
```

Source or install the emitted script using your shell's normal configuration.
Completion includes Action-derived paths, aliases, flags, and enum choices,
including commands contributed by trusted external plugins. Dynamic choices,
such as enabled Agents for `session run start --agent`, are resolved through the
canonical Action option source when it is reachable; static completion remains
available when it is not.

The envelope, exit codes, and stream rules above are instances of the one
[CLI automation contract](#cli-automation-contract) that every scripted
command follows.

## CLI automation contract

One contract covers every scripted CLI invocation, whichever command the script
calls. Command pages link here instead of restating it.

**Envelope.** `--json` prints exactly one versioned record to stdout —
`{ "v": 1, "ok": true, "kind": "<operation>", "data": … }` on success or
`{ "v": 1, "ok": false, "kind": "<operation>", "error": … }` on failure.
`kind` names the operation (`machines_list`, `actions_invoke`, `session_create`,
`session_history`, `session_wait`, `session_stop`, …), and a JSON failure
carries a stable code in `error.code`.

**JSON vs JSONL.** Use `--json` when the command produces one record. A
streaming command that emits many records takes `--jsonl`: one self-contained
JSON record per line, no array wrapper. `--follow --json` is rejected because
one record cannot represent a multi-line stream; use `--follow --jsonl`.

**Stdout purity.** In JSON mode stdout carries only the envelope or the
records — no progress lines, tables, or banners. Never parse the CLI's
human-readable output; pass an explicit `--json` or `--jsonl` instead.

**Spawn envelope, then stream rows.** `hdev spawn … --follow --jsonl` emits
the normal `session_create` envelope as its first line, including
`data.session.id`, followed by one compact history row per transcript update. A
session that produces no rows still emits the creation envelope and exits
successfully. If creation requires approval, the command emits the successful
`approval_request_created` creation envelope and does not start following; if
creation fails, one failure envelope is the whole stream.

**Terminal framing.** Without `--json`/`--jsonl`, output is compact text for
people: tables, short rows, and history rows printed as they arrive, with long
values truncated (compact history rows cap at 24 lines or 2,000 characters).
That framing is for reading, not for scripting.

**Exit codes.** `0` success; `1` expected failure — invalid input,
authentication, settings, approval, placement, transport, and Action-domain
failures; `2` unexpected internal or dependency fault. Exit codes never
downgrade: an unexpected fault stays `2` even when a later step also reports a
failure.

**Cancellation.** Ctrl-C (SIGINT) cancels a `--follow` stream or an in-progress
`wait`; an active transcript follow lease is released, rows already emitted
stay valid, and the interrupted process does not report success.

**jq without swallowing failures.** Run pipelines with `set -o pipefail` and
use `jq -e` (usually `jq -er`) so a failed CLI call, a missing field, or a
`null`/`false` result fails the pipeline instead of printing empty output and
exiting `0`:

```bash
set -o pipefail
SESSION_ID="$(hdev spawn "Fix the failing tests" --json | jq -er '.data.session.id')"
DAEMON_PORT="$(happier daemon status --json | jq -er '.daemon.httpPort')"
```

## Connect this computer to a Home

> **Availability:** This Home-aware setup and the Personal Home commands are in the current unreleased 0.3 checkout. Stable 0.2 continues to use the Relay-oriented setup documented with that release.

`happier setup` gets this computer onto a Home: it can discover or connect to
an existing one, or delegate local Personal Home creation to the canonical Home
creator. A Home is where an Account, credentials, sessions, settings, and data
live; it is not the server process or an Iroh relay. Setup selects the Home,
authenticates once, registers the machine, reconciles the background service
once, and optionally sets up Agents.

Use it when you want Happier to do the work instead of only previewing a plan:

```bash
happier setup
```

On a capable interactive terminal, the current unreleased 0.3 setup uses the
refreshed branded presentation and animated progress. Wide terminals place the
planet beside the setup choices, slowly growing and shrinking while you choose.
Use the arrow keys to select and Enter to continue; letter shortcuts remain
available. Narrow terminals use a compact text layout. Set
`HAPPIER_NO_ANIMATION=1` to keep it static. `NO_COLOR` disables colour;
`TERM=dumb` and non-interactive output suppress cursor animation and decorative
art automatically.

On capable terminals, the corresponding installer introduces Happier with a static numeric planet
and groups its work into Download, Verify, and Install. It retains detailed
failure output and hands over to setup without repeating the welcome. Colours
use your terminal's capabilities; its font and background remain yours.

With no usable active Home, setup starts with four choices:

1. Find linked Homes through the selected sign-in service (recommended;
   Happier Cloud is the default service).
2. Connect to an existing Home by saved name, HTTPS address, or Home descriptor
   file.
3. Create a Personal Home on this computer.
4. Exit.

An explicit Home target skips both interactive menus. A valid active Home also
skips selection and continues with readiness or machine-registration repair. If
the active Home cannot be reached, setup keeps its target and stored credential
and offers retry, another Home, or exit before showing fresh-setup choices.
Discovery through the sign-in service enrolls the preferred linked Home; if none is
available, its recovery path offers creation, direct connection, or exit. Local
creation delegates to the same canonical flow as `happier home create`. The
sign-in service is optional discovery and sign-in authority; Home traffic
continues directly to the Home.

Connect directly when you already have a saved Home, HTTPS address, or strict descriptor:

```bash
happier setup --home personal
happier setup --home-url https://home.example.test
happier setup --home-descriptor-file ./home.json
```

A strict descriptor can select an Iroh-only Home without inventing a public HTTPS endpoint. Manual HTTPS and the older URL/server flags remain compatibility inputs.

On a wide interactive terminal, the Relay question appears beside a planet drawn in Braille dots. It rises into view, turns briefly and comes to rest, then keeps breathing slowly; once you move the selection with the arrow keys it dims so the choices lead. Enter picks the highlighted answer, and letter shortcuts still work. Terminals that report a light background through `COLORFGBG` get the light planet. On Windows the planet needs a host that can draw Braille characters, such as Windows Terminal; the legacy console and narrow terminals get a compact text layout. Set `HAPPIER_NO_ANIMATION=1` to keep it static. `NO_COLOR` disables colour only; `TERM=dumb` and non-interactive output also drop motion and art automatically.

Useful flags:

- `--skip-daemon` (historical flag name; skips background-service install/enable)
- `--skip-providers` (don’t run provider setup)
- `--provider <id>` (preselect providers to set up)
- `--yes` (with an explicitly named Home, save deterministic target metadata and stop incomplete before interactive approval)
- `--non-interactive` (change nothing)
- `--replace-services` (explicitly allow replacement of conflicting Happier service registrations)
- `--switch-channel` (explicitly allow the default managed release channel to change)

`--yes` is not an unattended setup mode. With an explicit target it prints the interactive continuation and exits nonzero; without a target it writes nothing. `--non-interactive`, `HAPPIER_NONINTERACTIVE=1`, and a no-TTY invocation also write nothing. Run the printed continuation in a terminal to finish approval, registration, and service setup.

Dry-run the plan only if you want to inspect the steps before running them:

```bash
happier setup plan --home-url https://home.example.test
```

`happier setup plan` previews the work. `happier setup` applies it.
When an authenticated Home is temporarily unavailable, setup keeps the selected Home and its stored credential, reports the outage, and offers retry, another Home, or exit. It does not call the state authenticated or use an outage as evidence that a new account is needed.

### Create a Personal Home

Setup's local-creation choice delegates to the canonical Personal Home creator.
Invoke that owner directly when you want to start with creation or create the
Home over SSH:

```bash
happier home create
happier home create --ssh user@host
```

Both forms use the same managed Happier server runtime and atomic Personal Home bootstrap. The fixed preset creates or verifies the initial account, keeps its credential in the host's secure store, closes anonymous signup, verifies the result, waits for the server-published stable Home identity and descriptor, then adopts that identity. An SSH Home remains loopback-bound and can be reached over Iroh, so public ingress is optional. Personal Home data is plaintext at rest on its host; use a computer or provider you trust.

Creation is interactive unless you explicitly pass `--yes`. That `home create --yes` consent is separate from `setup --yes`: a successful creation can complete deterministically, while setup still needs human enrollment approval.

`home create --yes` never authorizes replacing an existing service or changing the default managed release channel. If creation reports either conflict, review it first and rerun with the narrow flag that matches your decision: `--replace-services` allows replacement of conflicting Happier services, and `--switch-channel` allows the default managed channel to change. The flags work with local and `--ssh` creation. Among `happier home` subcommands only `create` accepts them; `happier setup` accepts the same two flags for the background service it installs.

After creation, re-enter the device and discovery flows with:

```bash
happier home pair-device [--home PROFILE] [--copy-link]
happier home link-account [--home PROFILE] [--relink]
happier home unlink-account [--home PROFILE]
```

`pair-device` requires the Home's current `bound-qr-v2` capability and starts a new short-lived QR/link session; expired or cancelled sessions are not resumable. `link-account` publishes the Home to the sign-in service you are signed in to, so your other devices can discover it. Linking is optional and never puts the sign-in service in the Home traffic path.

`unlink-account` is the reverse: it stops the selected sign-in service from signing in to this Home. The Home refuses future delegated sign-ins from that service, but it does **not** revoke Home credentials the service already issued — devices that are signed in keep their access until you sign them out on the Home itself. The same action is available in the app under **Settings → Account → Homes** as **Stop delegated sign-in to this Home**.

You can also inspect, change, or sign out of the sign-in service this CLI uses:

```bash
happier auth service status
happier auth service use <endpoint>
happier auth service logout
```

`status` verifies the selected service's current identity and sign-in role before naming it. `use` selects a service and signs in to it: in a terminal it asks how you want to sign in, and a still-valid stored sign-in is reused without asking. It only signs in; it never enters or switches your active Home (run `happier setup` for that). Without a terminal, `use` succeeds only when a valid sign-in is already stored; otherwise it exits with an error and names the command to run in a terminal. `logout` drops only this CLI's sign-in credential; Homes you already entered keep their own credentials.

### Repair an existing setup

Use setup for first-time connection of this computer. Use doctor repair when an existing install has drifted or broken state: wrong automatic startup lane, stopped background service, stale service definition, missing auth, or mismatched Home state.

```bash
happier doctor repair
happier doctor repair --report-only
happier doctor repair --json
```

`happier doctor repair` is the supported repair entrypoint. It shares the same repair model used by installer preflight and service diagnostics; `--report-only` prints guidance without applying changes.

Agent-only setup:

```bash
happier agents setup
```

In the current unreleased 0.3 checkout, interactive setup lists the installable
agents from the live catalog, lets you select several, and includes **Skip for
now**. Skipping leaves the computer connected but not coding-ready when no agent
is already installed. A successful install only makes the agent executable
available; finish that agent's own authentication separately. For scripts,
select exact ids with repeated `--provider <id>` (or `--providers id1,id2`), or
use `--yes` for the catalog's recommended defaults.

## Remote machine setup (SSH)

If you want to set up a remote machine to run the background service and providers (VPS, home server, dev box):

```bash
happier machine setup --ssh user@host
```

Common flags:

- `--ssh-user <user>` / `--ssh-host <host>` / `--ssh-port <port>` (split SSH form)
- `--service-mode user|none` (background-service mode)
- `--relay-runtime-mode user|system` (relay runtime install mode)
- `--ssh-auth agent|keyfile|password` (select auth mode)

For advanced operator workflows, `--install-relay-runtime` installs the generic managed relay runtime on the remote host. It does not create or convert a Personal Home.
- `--identity-file <path>` (for `keyfile` mode)
- `--ssh-config-file <path>` (use an explicit SSH config)
- `--known-hosts-path <path>` (override host-key storage)
- `--trusted-host-key <line>` (pin a host key)
- the global `--server <saved-home>` prefix (target one saved Home)
- `--server-url <url>` / `--local-server-url <url>` / `--webapp-url <url>` (advanced compatibility/manual URL targeting)
- `--require-local-approval` (fail closed when the current machine cannot approve the pairing request)
- `--yes` (auto-accept prompts for non-interactive runs; this also replaces conflicting Happier background services on the remote host, so pass `--service-mode none` to leave them untouched)
- `--json` (stream protocol JSON events/results)

SSH auth modes:

- `agent` uses your SSH agent
- `keyfile` uses a private key path
- `password` prompts for a password in the terminal when supported

SSH host identity:

`--yes` behaves like OpenSSH's `accept-new`. It trusts an unknown host on first use, and it refuses a host whose stored key has *changed* — that prompt is the one case where the key on the wire may not belong to the host you meant. Confirm a legitimate key change in an interactive terminal, or pass the exact new `known_hosts` line with `--trusted-host-key <line>` for an unattended run. The same rule applies to every `happier home` command that reaches a host over SSH, including `home create`, `home relocate`, and `home restore`.

<Callout type="warn">
Changed in 0.3: `--yes` no longer accepts a changed SSH host key. Unattended runs against a rebuilt host now need `--trusted-host-key <line>`.
</Callout>

Tip: if you want to save the host for later reuse in the app, use the desktop Remote Hosts screen instead of a one-off inline SSH bootstrap. The inline SSH bootstrap is intentionally one-off; reusable SSH profiles live in the app.

## Personal Home data operations

When the managed runtime on this computer runs your Personal Home, the `happier home` commands let you inspect, back up, restore, and erase that data from the terminal. Every operation runs through Happier's managed system tasks and one shared operation owner, so you never copy or edit the Home's data directory by hand, and two operations cannot run on the same Home at once.

All subcommands require the installed managed runtime to be a Personal Home. They target the current CLI release channel and user-mode runtime by default; use `--channel stable|preview|dev` and `--mode user|system` to select another installed managed runtime explicitly. With `--json`, successful operations stream machine-readable JSON Lines task events followed by the final task result; command-level failures use the CLI error envelope. Running `happier home` with no arguments prints the usage summary.

### Inspect and back up

```bash
happier home status
happier home backup [--output PATH]
happier home verify-backup PATH
happier home status --ssh user@host
happier home backup --ssh user@host [--output PATH]
happier home verify-backup --ssh user@host PATH
```

`status` shows where the Home keeps its data — the data directory, database, public and private file stores, and backups directory — plus whether the Home is running, the database size, how many backup archives are present, and the exact data paths erase would remove with their estimated size. Add `--json` for the full machine-readable inspection, including the Home identity and master-secret fingerprint (never the secret itself). Use `verify-backup` when you need to establish that an archive is valid.

`backup` creates a verified archive of the complete Personal Home: the SQLite database, public and private files, the master secret, and a small, fixed allowlist of Home configuration — the Home's identity, its canonical server URL, its plain-at-rest policy settings, and any explicit Iroh relay policy and custom relay URLs, taken from the runtime's own managed configuration. Credentials, ports, and transport keys are never copied; restore re-applies exactly this allowlist before the Home starts again. If the Home is running, it is stopped first, the database is checkpointed and integrity-checked before any bytes are copied, and the Home is started again afterwards. The archive is created with restrictive permissions (0600 on POSIX), hash-verified by reading it back, and only then reported as usable. Without `--output PATH` the archive is written into the Home's backups directory with a timestamped name. Happier does not automatically delete older user-created backups.

`verify-backup` re-checks an archive's integrity and manifest and reports the backup's Home identity, creation time, and schema version, along with whether that identity matches, mismatches, or cannot be compared against the current Home. Add `--ssh user@host` to run any of these operations against the managed Personal Home on a trusted remote host.

A backup is plaintext by design. It contains readable conversations, Home data, the Home master secret, and trusted-device state. Anyone who can restore the complete archive can operate a clone of this Home, so save backups somewhere you trust.

### Restore

```bash
happier home restore PATH [--yes]
happier home recover-restore [--yes]
happier home restore --ssh user@host PATH [--yes]
happier home recover-restore --ssh user@host [--yes]
```

Restore verifies the archive and inspects the destination before touching anything. A backup whose Home identity mismatches the current Home is refused, as is an archive whose schema is newer than the installed runtime can handle. Restoring over a Home that already contains data requires an explicit confirmation — the interactive prompt, or `--yes` in non-interactive runs.

The restore itself is staged: the new data is extracted and validated beside the Home, migrated forward using only the migrations shipped with the installed runtime (never a downgrade), then swapped in and health-checked with its Home identity verified before success is reported. If a step after the swap fails, Happier attempts to restore the previous data; if rollback itself cannot finish, the Home stays stopped with recovery material retained instead of silently running mixed data.

`recover-restore` inspects the canonical restore journal and, when a rollback is available, requires explicit confirmation before restoring the retained previous destination. It is a no-op when no interrupted restore exists. Ambiguous recovery state fails closed and leaves the Home stopped for manual repair instead of guessing which bytes are authoritative. The SSH forms run the same owner-controlled workflow remotely; destructive approval is bound to the reported SSH host, Home identity, paths, and estimated size.

### Erase

```bash
happier home erase [--yes]
happier home erase --ssh user@host [--yes]
```

`erase` permanently deletes the Personal Home's data — the database, public and private files, master secret, configuration, and local backups. It is explicit and destructive, runs under the same operation lock as backup and restore, and is never triggered by uninstall, logout, or restore. The single confirmation names the affected Home and shows the exact owner-resolved paths while the Home still runs. Its size estimate is bounded and may be unknown. The command revalidates those facts before stopping the Home and checking the deletion targets. A failure before deletion attempts to restart a previously running Home; a partial deletion leaves it stopped. Non-interactive runs require `--yes`. If you want a recovery copy, create and verify an external backup separately before erasing; erase never creates one implicitly.

Uninstalling the managed runtime (`happier relay host uninstall`) is different and safe: it removes the service registration, runtime binaries, and logs, and preserves the database, files, master secret, configuration, and backups. Deleting data is always `happier home erase`, never uninstall.

### Relocation (0.3 development)

```bash
happier home relocate --target user@host [--yes]
happier home relocate --target user@host --recovery-action finish_move|return_to_source [--yes]
```

`relocate` moves this computer's Personal Home to the explicit SSH destination in `--target`. It is the terminal form of the same **Move Home** operation Desktop settings starts, and both run through the one relocation coordinator — there is no second move workflow. Use `--target`, not `--ssh`: the destination is the move's target, not a remote host the command is executed on.

The move is staged by the coordinator: it inspects the source Home, verifies that the active Home profile is this computer's managed Personal Home, transfers and activates the Home on the destination, and publishes the destination descriptor. The single destructive confirmation names the source Home and the SSH destination; non-interactive runs require `--yes`.

If a move is interrupted, the next `relocate` against the same destination requires `--recovery-action`: `finish_move` completes the activation on the destination, and `return_to_source` restores the source Home. `return_to_source` is refused once destination publication has advanced, and a destination that does not match the interrupted move's reserved destination is refused rather than resumed. Ambiguous recovery state fails closed and asks for repair instead of guessing which Home is authoritative.

The current SSH transfer path is POSIX-oriented. Do not claim or automate a general Windows headless destination until the destination-owned opaque upload locator or authenticated machine carrier is implemented and validated.

Related: [Self-host runtime](/self-hosting/self-host-runtime).

## Relay access (share/public URL strategy)

If your self-hosted Relay is only reachable locally (for example `localhost`), other devices (phones, other computers) won’t be able to use it until you expose a reachable Relay URL (often HTTPS).

Inspect and configure the relay access method:

```bash
happier relay access status
happier relay access configure --provider tailscaleServe --upstream-url http://127.0.0.1:53288
```

You can also apply the same configuration on a remote host:

```bash
happier relay access status --ssh user@host
happier relay access configure --ssh user@host --provider tailscaleServe --upstream-url http://127.0.0.1:53288
```

User guide: [Relay access](/apps/relay-access).

### Remote machine pairing (SSH, automated)

If you want to run Happier on a **remote machine** (VPS, home server, dev box) but approve/authenticate it from a machine where you're already signed in:

```bash
happier auth pair-remote --ssh user@host --json
```

Notes:

- This opens one authenticated SSH session and performs one short-lived streaming enrollment. The local CLI verifies the selected Home identity before approving the remote request; the remote CLI writes its profile and credentials only after enrollment completes.
- The current selected Home is the default. Use the global saved-Home form `happier --server <saved-home> auth pair-remote --ssh user@host --json` when you need another saved Home.
- `--server-url-for-remote <https-url>` (and its released URL aliases) remains an advanced HTTPS compatibility form. Strict descriptor/Iroh targets are carried from the selected Home without inventing a public URL.

### Pairing protocol primitives (advanced tooling)

`auth request`, `auth approve`, and `auth wait` remain JSON protocol primitives for operator tooling and released compatibility. They are not the routine onboarding recipe: use `happier setup` for this computer and `happier auth pair-remote --ssh user@host` for a remote machine. If you build custom transport around the primitives, treat the complete request envelope as a short-lived secret and keep every step bound to the same selected Home.

Current approvals produce one authenticated terminal-v3 result. Plain Homes persist a token-only
credential without synthesizing a secret; E2EE data-key Homes persist their data-key fields without
converting them to legacy secret material. Previously issued legacy responses remain a bounded
reader-compatibility path and are not newly emitted by current approval writers.

This is terminal/CLI pairing, not the same flow as device restore inside the app.

## Attach to an existing session

If a supported session is already running, you can reattach to that same live session from a terminal:

```bash
happier attach
happier attach <session-id-or-prefix-or-tag>
```

This is the main “start in the app, continue in the terminal” workflow. In a supported TTY, `happier attach` opens an interactive picker of active sessions:

- **local attachable sessions** are selectable immediately
- **active but non-attachable sessions** stay visible but disabled with a reason
- **remote-capable Agent sessions** are marked as remote; press `P` in the picker to run a reachability check before attaching

If the session is stopped, use `happier resume` instead.

Important notes:

- tmux and other terminal-host attach flows work only for sessions that are still owned by the current machine.
- You must target the same Happier account/server profile that owns the session.

Attach strategy depends on the Agent and terminal host:

- Terminal-hosted sessions reconnect to their existing `tmux`, zellij, or Herdr terminal.
- OpenCode uses an Agent-native attach flow for server-backed sessions.

For OpenCode, the supported reattach command is still `happier attach <session-id-or-prefix-or-tag>`. Do not rely on a raw vendor `opencode attach ...` command as your normal Happier workflow.

Supported attach styles include:

- **tmux-backed sessions** on machines where tmux is enabled
- **zellij- and Herdr-hosted sessions** on supported macOS and Linux machines
- **Windows Terminal** or **Console** hosted sessions on Windows
- **Agent-native attach** for supported Agent sessions such as OpenCode

For the full workflow, see [Features → Attach to a running session](/sessions/attach-to-session).

In development builds, `happier herdr` opens Herdr from the terminal. Both the installed executable and the running server must be a stable Herdr release, version `0.9.2` or newer. If you are already inside a Herdr pane, use Herdr's pane controls instead of starting a nested client.

Development builds can recover an owned Claude terminal that survives its Happier controller without starting another Claude process. Recovery remains unavailable until Happier verifies the exact host and receives an authenticated observation of the requested Claude session. A restored foreground shell is borrowed, so stopping its Happier runner does not close that shell.

After a Herdr server restart, development builds can open a recorded local pane as a restoration candidate once Happier confirms that its old controller has exited. The pane's saved Happier resume command still uses normal sign-in and session admission. A running or unverifiable controller is not bypassed, and opening the candidate does not by itself establish that the session is ready or transfer ownership of an independent native client.

Current development source also includes a strict same-pane path when the shared headless controller survives: explicit `happier attach` inside the recorded restored pane admits the native client only after checking the current conversation, terminal and process custody. Once admitted, it has managed status and Detach. Detach closes that exact native client, not the borrowed shell, and explicit Attach can reuse the same pane. Ordinary independent native clients still do not claim managed status. This source-checked path is not a claim of a shipped release, automatic installed-channel replay, or completed authenticated cold-restart validation on 0.3.

Cold attachment verifies the original saved Herdr namespace and never switches to another server with the same name. If a stopped server uses an unsupported custom persistence location, reopen its original server before retrying attachment; an already-running custom socket remains supported.

## Continue a session

`happier resume` attaches to a running, attachable session or resumes a stopped, vendor-resumable session.

### Interactive selector

```bash
happier resume
```

In a supported TTY, Happier shows running sessions you can attach to and stopped sessions you can resume in one picker.

### Resume by id

```bash
happier resume <session-id-or-prefix-or-tag>
```

You can use a full Session id, an unambiguous id prefix, or an exact Session tag.

Important behavior:

- resume is strict: if the Agent resume fails, Happier errors instead of starting a fresh session
- active sessions use the existing attach flow; an attachment failure does not launch a second Agent
- archived sessions cannot be continued
- for stopped sessions, the command restores the working directory before launching the Agent again

### Execution runs (review / plan / delegate / voice agent)

Execution runs are the structured “run” layer for multi-step flows in a session (for example: start a review run, then send follow-up messages, then stop).

```bash
happier session run list <session-id-or-prefix-or-tag>
happier session run start <session-id-or-prefix-or-tag> --intent <intent> --agent <agent-id>
happier send <session-id-or-prefix-or-tag> "message" --run <run-id>
happier session run stop <session-id-or-prefix-or-tag> <run-id>
```

These one-shot lifecycle commands are friendly projections of the canonical
`execution.run.*` Actions. `start` uses `--agent` (not a separate CLI-only
backend flag), and `list`, `get`, `start`, `stop`, `wait`, `stream-start`,
`stream-read`, and `stream-cancel` share the same parser, help, completion,
authorization, JSON-error, and exact-Session behavior as the rest of the
Action-driven CLI. `session run action` remains a dedicated multi-step workflow
because it selects another Action dynamically.

Sending to a session-owned run is the ordinary send command with one extra
destination. Omitting `--run` keeps the main-session path unchanged; supplying it
addresses exactly that run and never falls back to the parent session. The
released spelling `happier session run send <session-id> <run-id> "message"`
remains available as a deprecated compatibility alias for the same operation. It
no longer accepts `--resume`: activation is owned by the execution-run resume
operation, not by the send command.
