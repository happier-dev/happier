---
title: Relay access
description: Configure a reachable Relay URL for other devices (Tailscale, Cloudflare, LAN, or local-only).
---

Relay access is the “share/public URL strategy” for a self-hosted or local Relay.

This is an advanced/operator feature. A 0.3 Personal Home created with `happier home create` publishes Iroh reachability and does not require public ingress. Stable 0.2 retains the released URL-oriented Relay access workflow.

It answers the question:

> What Relay URL should other devices (phones, browsers, other computers) use to reach this Relay?

This is important when your Relay is only reachable locally (for example `http://127.0.0.1:53288`), because phones and other devices cannot sign in or connect until you expose a reachable URL (often HTTPS).

Note on browsers (web + mobile web):
- `http://localhost` is treated as a secure context by browsers.
- `http://<lan-ip>` / `http://<tailscale-ip>` is **not**, so WebCrypto and login flows may fail or be blocked.
For phone/laptop access, prefer an **HTTPS** Relay URL (for example Tailscale Serve, or a reverse proxy).

## Common methods

Happier supports multiple relay-access providers (availability depends on your server/build policy):

- `localOnly` — no share URL (local-only development)
- `tailscaleServe` — Tailscale Serve HTTPS URL (private, simplest for multi-device)
- `tailscaleFunnel` — Tailscale Funnel public URL (**only** when Funnel is enabled for that Serve target)
- `lan` — a LAN URL you provide (works only on the same network)
- `cloudflareNamed` — a named Cloudflare Tunnel hostname (see the development credential and verification limits below)

### Provider notes

- `tailscaleServe`
  - Best default for multi-device access inside a tailnet.
  - Produces an `https://*.ts.net` URL.
- `tailscaleFunnel`
  - Only usable if Funnel is enabled; otherwise Happier will not infer a public URL.
  - Produces a public URL (internet-reachable).
- `cloudflareNamed`
  - In **unreleased 0.3 development source**, provide the hostname and select a
    Cloudflare Connected Account for tunnel management. Configuration carries
    that account reference, never a raw Cloudflare token; the old `--token`
    flag is not accepted by this development CLI.
  - Saving a hostname and account reference does not verify a running connector,
    DNS or a public route. The current configuration leaf reports unknown until
    the admitted controller verifies it; it does not claim a ready tunnel.
  - Connector changes and teardown require that admitted controller. This
    configuration leaf does not start or remove the connector itself.

## CLI usage

### Relay host bind flags vs Relay access

`happier relay host install --lan|--expose|--host <ip>` controls which network interface the local Relay runtime listens on:

```bash
happier relay host install --lan
happier relay host install --expose
happier relay host install --host 192.168.1.25
```

`happier relay access ...` is a separate share/public URL strategy. Installing with `--lan` can make a LAN URL possible, but it does not configure Tailscale, Cloudflare, or any other access provider.

Inspect current relay access status:

```bash
happier relay access status
```

Configure a provider (example: Tailscale Serve from a loopback upstream):

```bash
happier relay access configure --provider tailscaleServe --upstream-url http://127.0.0.1:53288
```

In **unreleased 0.3 development source**, `--provider` selects a declared Home
access method. Nonsecret fields accept `--config <json>` or individual string
flags such as `--hostname`; `--credential-refs <json>` carries purpose-bound
Saved Secret or Connected Account references. Configuration is the selected
method, its configuration and those references, not an embedded credential.
Machine-only Tailscale membership and Caddy are not Home relay methods.
Published share URLs omit userinfo, query and fragment while keeping port and
path; private execution configuration is not rewritten.

When a local provider returns a share URL, Happier reconciles that route through the canonical descriptor owner and retains the local upstream for connections from this computer. The route does not replace the Home's stable identity or independently choose its authentication audience. Disabling access uses the selected method's teardown; Cloudflare requires its admitted controller and does not remove a connector through this configuration leaf. Configuring access with `--ssh` changes the remote host only; it does not switch the Home profile on the computer running the command.

Disable relay access (remove the persisted configuration):

```bash
happier relay access disable
```

### Apply relay access on a remote host (SSH)

You can read/write the relay-access configuration on a remote machine:

```bash
happier relay access status --ssh user@host
happier relay access configure --ssh user@host --provider tailscaleServe --upstream-url http://127.0.0.1:53288
```

Host-key safety notes:

- SSH always uses `StrictHostKeyChecking=yes` (no silent host trust).
- By default, relay-access SSH uses your **system** `known_hosts`.
- If you want Happier to manage host trust prompts for relay-access SSH, pass an app-managed file:

```bash
happier relay access status --ssh user@host --known-hosts-path /tmp/happier_known_hosts --yes
```

You can also pin a host key explicitly:

```bash
happier relay access status --ssh user@host --known-hosts-path /tmp/happier_known_hosts --trusted-host-key "<single known_hosts line>"
```

## Troubleshooting

### Serve change refused

If a Serve change fails with `401 … must be root, or be an operator`, check
the host account's authorization. On Linux with Tailscale 1.104.2, an empty
account display name (GECOS) can also cause this refusal for a configured
operator: [upstream issue #21204](https://github.com/tailscale/tailscale/issues/21204).
The bug uses the display name instead of the login name when checking a
configuration containing file-path or Unix-socket handlers; an existing handler
can therefore make a proxy-only change fail. [Fix PR #21257](https://github.com/tailscale/tailscale/pull/21257)
remains open as of 29 October 2026.

On an affected Linux host, set the display name to the account's login name
with `sudo usermod --comment <login-name> <login-name>`, then retry. Alternatively,
run the exact refused `tailscale` command with `sudo`. If the account is not an
operator, the host owner can run `tailscale set --operator=<login-name>` (with
`sudo` when required); see [Tailscale's operator permissions guide](https://tailscale.com/docs/reference/troubleshooting/linux/linux-operator-permission).
