title: Connected services
description: Link account/subscription credentials to Happier, reuse them across supported Agents, and monitor quota snapshots where available.
---

Connected services let you store supported account/subscription credentials once in Happier and reuse them across compatible Agents and sessions.

They are different from **Agent authentication** and first-class **Provider connections**:

- **Connected services** are account/subscription credentials stored in Happier and reusable across compatible Agents;
- **Agent authentication** reflects the native login state of an Agent CLI on one machine;
- **Provider connections** configure model-source endpoints, catalogs, and API-key bindings under **Settings → Providers**.

See [Agent authentication](/agents/provider-authentication) and [Provider integrations](/agents/provider-integrations).

They exist so you can:

- connect subscriptions and API keys without manually re-entering them for every backend
- store credentials once instead of re-entering them, with what the server can read following your account's encryption mode (see [Security model](#security-model) below)
- choose per-service auth at session start instead of relying only on each Agent's native auth
- monitor usage / quota snapshots for supported services
- make multi-machine workflows easier when the target machine should reuse the same Happier-managed credential

## What a connected service is

Happier models different credential types as distinct connected services:

- `openai-codex`: ChatGPT subscription auth (shown as **ChatGPT**; Codex is the agent that uses it)
- `openai`: OpenAI API key auth
- `claude-subscription`: Claude subscription auth
- `anthropic`: Anthropic API key auth
- `gemini`: Gemini account credentials (in development builds, an API key or Google service account)
- `github`: GitHub token auth for source-control workflows, in builds that expose GitHub connected accounts

This split is intentional. Subscription auth and API-key auth have different account behavior, billing paths, and Agent materialization requirements, so Happier does not merge them into a single generic "Claude" or "OpenAI" credential type. A model Provider connection may bind an appropriate Saved Secret independently; it is not automatically a connected-service account.

GitHub is different from the agent/backend credentials above. When enabled, it is used by source-control features such as GitHub repository publishing and GitHub pull request operations.

In 0.3 development, GitHub source workflows can also use the executing machine's
GitHub CLI login without storing a token in Happier. This native choice is
configured with the source, not by creating a Connected Account; an explicitly
selected Connected Account still takes precedence. See
[PRs & Issues](/code/prs-and-issues#use-a-machines-github-cli-login).

## Where you manage them

In the app:

- Settings -> Connected services

The page lists each service with the agents that use it, and each account with how much of each limit
is left and when it resets. From there you can:

- connect a service or add another account using the sign-in flow on the machine you pick
- sign an account in again from its row when the provider signed it out
- give accounts custom labels
- choose, per agent, which account (or pool, or the agent's own login) it signs in with under
  **How accounts are used**
- inspect an account's usage, the agents and pools that use it, and how it signed in
- remove individual accounts (an account a pool uses is removed from the pool first)

In 0.3 development, service cards still expand sign-in in place. **Add account**
opens the same flow in the account detail, retaining its machine choice and
recovery steps rather than starting a different authentication flow.

In the CLI:

- `happier connect status`
- `happier connect codex ...`
- `happier connect claude ...`
- `happier connect gemini`

The 0.3 development storage contract keeps personal labels and dismissal choices
with your signed-in Account, while account and pool-member expansion choices
stay on the device. These presentation choices do not change credentials, pool
membership or which account an Agent uses.

In 0.3 development, you can open a saved account's details and change its label
without selecting a machine, including when a previously selected machine is
offline. Sign-in, account-credential configuration and requesting fresh quota still
require an available machine for those operations; choosing one does not unlock
or change which Happier Account owns the saved details.

In 0.3 development, a service that declares **service-wide configuration** can
also have that configuration read and edited for the signed-in Account without
selecting a machine. Saving checks the configuration revision; a concurrent edit
keeps your draft instead of overwriting the newer configuration. New secret
values and their configuration references are saved together, and reads show
which secret fields are configured without returning their values.

This saves configuration, not a machine's sign-in or running process. A later
runtime operation uses the new revision; any required refresh or reconnect still
happens on the machine. Account-specific credentials and in-progress sign-in
configuration remain machine operations. If a save's outcome is unknown, read
the saved configuration before deciding whether to retry; do not assume it failed.

## GitHub CLI import in 0.3 development

In development builds, **Import GitHub CLI login** saves a machine's existing
GitHub CLI login as a connected GitHub account in Happier. Choose **GitHub account**
in Connected services, add an account, select that method and choose the machine
where you signed in to `gh`. Continue through the normal approval flow.

The credential goes through the existing connected-account storage and your
Account's encryption mode. If the machine has no available GitHub CLI login,
install `gh`, sign in there with `gh auth login`, then retry the import.

## Gateways in 0.3 development

The unreleased gateway integration projects your managed Provider connections
into Connected services using the same connection and detail as Providers.
Gateways use existing single-vendor accounts and pools; enabling a pool for a
chosen gateway assigns that vendor slot, and disabling it clears the slot only
if it still belongs to that pool. Multiple gateways require an explicit choice.
These operations use the existing approval policy and revision-checked
connection update, rather than a separate pool-routing setting.

The current 0.3 development add flow opens an unsaved gateway draft in Connected
services, including when opened from a pool. Opening or discarding the draft
does not create a connection. **Create** saves the selected contribution, vendor
slots and placement through the existing Provider connection operation and its
approval policy. Saved gateway details use the same body and controls as Providers.

In development builds, choosing or clearing this pool slot does not require a
selected or online machine. It saves Account configuration, not a gateway start
or a runtime-readiness check. An unavailable unrelated source does not hide a
gateway whose own declaration is available.

The gateway configuration and collection integration are still being validated.
See [managed gateways](/agents/provider-integrations#managed-gateways-in-development)
for placement, Claude helper-model choices and experimental routing limits.

## Google Antigravity in 0.3 development

The unreleased integration adds **Google Antigravity** as its own Connected
Account. Sign in with Google through the existing paste-code flow, label each
account, and choose an account or pool for Antigravity. Gemini credentials are
separate; connecting the same Google identity to both requires separate sign-ins.

Selected-account launches keep token and authentication settings private while
inheriting the configured skills, hooks and MCP settings. The default shared-state
policy links only ACP conversation and artifact directories, so account changes
can use the same history. Choosing isolated state, or being unable to establish
shared links, prevents cross-account resume before cutover. Account-selected discovery
probes use temporary isolated conversation state without changing the saved sharing
policy. With machine-local authentication, successful ACP discovery can leave empty
conversations in the native history.

When switching an account's existing isolated history to shared state, differing
copies of the same conversation are preserved as separate files. Antigravity
continues to load the native shared copy under the original conversation ID; the
imported `.happier-import-*` copy is not automatically merged or selected.

Each ACP process needs its own restart to consume changed credentials. Account
usage comes from Google's selected-account quota response; the context indicator
uses ACP turn usage. These are different measurements. Sign-in, refresh, quota
attribution and A→B→A resume still require authenticated validation, including
native Windows and macOS isolation checks. The integration uses Antigravity's own
OAuth client and Google's internal quota API, which Google can change or block.

[Google's FAQ](https://www.antigravity.google/docs/faq/) says third-party access
can lead to account suspension or termination, and consumer-plan account rotation
is unsupported. This development integration does not establish Google approval
or an exception for Happier's use of the official ACP server.

See [Antigravity](/agents/antigravity) for the managed ACP/native CLI boundary.

## Continuing after a usage limit in 0.3 development

Development-only usage-limit recovery lets a waiting session continue after a
reported usage-limit reset, including sessions using a native provider login.
It requires usage-limit recovery support on the relay and automatic resume to be
enabled. Checks from an active session, the CLI and MCP use the same recovery
attempt; changing how you check does not start a separate recovery loop.

Happier manages the wait even when the Agent has no separate quota-check command.
A reported reset time determines when it can try to continue; without a reliable
reset time, Happier tries again using its recovery backoff. Temporary check
failures keep the wait active.

Happier sends the configured continuation prompt, not a replay of your original
request. Once the continuation is accepted into Pending, its normal queue and
delivery status take over from the usage-limit wait. A queued prompt does not
confirm that the provider will accept another turn. Cancelling the wait, stopping
the session or sending newer work takes precedence over automatic continuation.
Quota readiness, an account switch or a successful runtime launch alone does not
dismiss the warning. Accepted Pending delivery, explicit cancellation, or
subsequent Agent activity can end the wait presentation. If
**Apply reset** fails, its action becomes available again.
This integration is unreleased and still being validated.

Cancelling recovery for an earlier failure does not hide a new usage-limit issue.
If an older saved wait cannot be associated with the current failure, the banner
shows the current issue's actions without attaching the saved wait's timing or
cancellation state. A live **Check limit now** reads the current issue from the
session's relay; if that read is unavailable, retry after connectivity returns.

## Model-capacity retries

In development builds, a terminal model-capacity failure such as Codex
`server_overloaded` keeps the same session and selected model. Happier waits before
retrying, with longer delays for consecutive capacity failures: the initial delay
is about five seconds and the exponential schedule levels off at about five
minutes. Each delay varies by up to 20% to spread retries across sessions. A
provider-supplied retry time can extend the wait.

Capacity retries have no attempt limit. A continuation being accepted or queued
does not reset the delay; a successfully completed model turn does. Authentication
failures and exhausted subscription quota follow their separate recovery paths.
Stopping retries or stopping the session takes precedence over automatic recovery.

## Automatic quota resets for Codex pools

In development builds with a supporting relay and Codex plugin, a subscription
pool's Behavior section includes **Automatically use quota resets**. It is off by
default. Enabling it authorizes spending a banked reset only after ordinary recovery
finds no ready pool account and a quota-exhausted account is eligible for a reset.
Normal account selection and session continuation still apply; this does not
authorize resets for authentication failures or unrelated cooldowns.

The option is hidden when the relay or applied service does not support it.
Turning it off prevents future automatic spending; it cannot restore a reset
already consumed.
If a reset response is lost or cannot confirm the outcome, Happier pauses further
automatic resets for that account for the current daemon lifetime; a newer quota
observation alone does not authorize another credit.

Confirmed automatic spending sends a notification through your enabled quota-recovery
notification channels, identifying the account and pool. This reports that a reset
was used; session recovery may still be in progress. Uncertain outcomes do not send
a success notification, and replaying the same receipt does not send another one.

## Choosing accounts on a swap

In development builds, **Expiring first** is the default selection strategy for
new pools. When a swap is needed, Happier prefers an eligible account with enough
fresh quota whose long usage allowance resets sooner or whose subscription ends
sooner with renewal off. A renewing billing period is not a subscription expiry.

The pool's existing early-switch threshold defines enough quota. If no account
has that much left, selection falls back to the account with the most usable quota.
Stale, missing, or passed dates add no preference. Equal deadlines are resolved by
remaining quota, then member order. A healthy active account stays active; this
strategy does not schedule switches or restart sessions.

Existing explicit **Least limited**, **In order**, and **Manual** choices are
preserved. Change the selection strategy in the pool's Behavior section to opt in.

## Choosing which limits drive a pool

In development builds, a pool's Behavior section can use **All usage limits** (the
default) or a selected set of the provider's reported limits. The selected limits
drive capacity ranking and automatic soft- and hard-limit switching for that pool.
This is useful when a provider reports independent allowances for different model
families, such as a dedicated Codex model allowance or a Claude scoped allowance.

Happier shows the allowance identities reported by the provider; it does not keep a
separate model list or silently change the session model. A selected allowance that
is temporarily absent from an account's latest quota response remains selected and
is shown as unavailable. Happier treats that account as having insufficient quota
evidence for the policy instead of silently falling back to all limits.

This setting does not change which accounts belong to the pool, and it does not
filter authentication, plan, or model-entitlement errors. Choose **All usage
limits** to restore the predecessor behavior.

The filter governs quota evidence used to select an account before a request.
A supported account-scoped usage-limit error that actually fails the Agent's main
operation still follows the pool's configured switching rules and limits. Use
separate pools when sessions need different quota filters; provider-enforced usage
and spending limits still apply.

Pool member capacity, usage rows, and session usage badges use the pool's selected
allowances. Account-wide facts such as the plan, subscription identity, and reset
credits remain visible. When the provider reports a window duration, the selector
shows that duration (for example, `5h + 7d`) instead of a generic count; a single
window with no reported duration is left unlabeled rather than shown as “1 window”.


### Composer gauges in development builds

Choose **Gauge windows** under **Settings → Connected services → Usage**
or **Settings → Session → Limits and usage → Usage**. Both
locations edit the same preference for all accounts. The default is one
**Most constrained** gauge; select several windows, such as **Daily** and
**Weekly**, to display one gauge for each available window.

For pooled sessions, gauges use only the allowances selected in that pool. A
pool that tracks only Fable allowances shows Fable's selected windows, even if
the account reports other allowances. Missing windows do not produce extra
gauges. **Short window** includes allowances such as a five-hour window;
**Daily** means a daily allowance.

Account favorites select summary meters in account views and add extra composer
gauges for the account currently used by the session, alongside the global windows.
Favorites respect the pool’s selected limits and need a reliable percentage to produce a ring. **Show usage labels** and the
provider-gauge visibility toggle are available in both locations too.

## Connection methods

### OpenAI Codex

Supported methods:

- device code
- paste redirect URL
- in-app browser on native only

OpenAI Codex can also be connected with an API key, but that is modeled as the separate `openai` service.

### OpenAI API key

Supported methods:

- manual API key entry

Use this when you want OpenAI-backed backends to run against your own API key instead of your Codex subscription login.

### Claude subscription

Supported methods:

- setup-token
- paste redirect URL
- in-app browser on native only

Setup-token is the recommended default. Generate it on any machine already logged into Claude Code:

```bash
claude setup-token
```

Then paste it into Happier.

In development builds, Claude subscription quota is tied to both the provider
user and organization. Two connections for the same user can have different
organization budgets. Changing or reconnecting a connection therefore clears
quota from a different organization until current usage is available. Connections
for the same user and organization can share usage even if their labels differ.

If the organization cannot be verified, Happier keeps global usage unlinked.
Usage verified with the current credential can still support that connection's
local recovery. Reconnecting with a different credential requires fresh evidence.
This does not identify every cause of a Claude rate-limit or spend-limit response.

### Anthropic API key

Supported methods:

- manual API key entry

This is the Anthropic Console API-key path. It is separate from `claude-subscription`.

### Gemini

Gemini uses a Gemini account or API key; Happier does not offer a native Gemini login terminal. In development builds, supported connection methods are:

- manual Gemini API key entry
- Google service-account JSON entry

### GitHub source-control credentials

When GitHub connected accounts are enabled in the build, supported methods are:

- token / Personal Access Token entry
- local GitHub CLI auth outside Connected services

A connected GitHub token can let Happier use GitHub REST APIs for:

- publishing a local repository to GitHub
- listing and opening pull requests for the current branch
- creating or reusing pull requests

The local `gh` CLI is not stored as a connected service. If `gh` is installed and authenticated with `gh auth login`, Happier can use it as an optional fallback for GitHub source-control workflows.

GitLab is not currently documented as a connected service in Happier. GitLab merge-request workflows use an authenticated local `glab` CLI when available, or a no-auth compare URL fallback.

### Why web behaves differently

Happier does not use embedded OAuth capture on web. Web falls back to paste-based flows because a browser app cannot reliably auto-capture provider redirects to `localhost`.

## Agent compatibility

Connected services are not global “works everywhere” credentials. Each Agent declares which service ids and credential kinds it can consume.

| Agent | Supported connected services |
| --- | --- |
| Claude | `claude-subscription` (setup-token or OAuth), `anthropic` (API key) |
| Codex | `openai-codex` (OAuth), `openai` (API key) |
| Gemini | `gemini` (API key or Google service account in development builds) |
| OpenCode | `openai-codex` (OAuth), `openai` (API key), `claude-subscription` (setup-token only), `anthropic` (API key) |
| Pi | `openai-codex` (OAuth), `openai` (API key), `claude-subscription` (setup-token only), `anthropic` (API key) |

Important limitations:

- OpenCode accepts `claude-subscription` only when the profile is a setup-token profile, not a Claude OAuth profile.
- Pi accepts `claude-subscription` only when the profile is a setup-token profile, not a Claude OAuth profile.
- `anthropic` is API-key only in Happier.
- `github`, when enabled, is not consumed by agent backends. It is consumed by source-control workflows.

## Source-control compatibility

| Source-control workflow | Preferred credential | Fallback |
| --- | --- | --- |
| Publish repository to GitHub | Connected `github` token when enabled | Authenticated `gh` CLI |
| GitHub pull requests | Connected `github` token when enabled | Authenticated `gh` CLI, then compare URL |
| GitLab merge requests | Not a connected service today | Authenticated `glab` CLI, then compare URL |
| Bitbucket pull requests | Not a connected service today | Compare URL only |

This means a user who already has `gh` installed and authenticated can use GitHub PR/publish features without connecting GitHub in Happier first when the source-control integration supports that fallback. Connecting GitHub is still the preferred cross-machine path where available because the credential can be reused by the daemon on the target machine.

## Using connected services in the new-session flow

If the selected backend supports connected services, the new-session screen shows an auth picker.

That picker is dynamic:

- it appears only for backends that support connected services
- it shows only services compatible with the selected backend
- it shows only connected profiles that are valid for that backend
- it lets you choose `native` auth or `connected` auth for each compatible service

If no compatible connected profile exists for a service, Happier keeps that service on native auth and offers a shortcut to open Connected services settings.

In development builds, an unreadable or malformed explicit auth selection blocks
session launch or resume instead of being treated as native auth. Review the
session's connected-service selection before retrying; an invalid selection does
not authorize using a different account or the machine's ambient credentials.

## Instructions, plugins, and hook trust in development builds

Linked and copied configuration include Claude's user-level `CLAUDE.md` and
Codex's installed `plugins` directory. Existing managed homes receive these
entries the next time Happier materializes them; isolated configuration does not
import them. Credentials and session-history sharing remain separate.

When copying home-level Codex hooks into a managed home, Happier translates the
file-path keys for existing hook decisions and preserves their trust hashes and
disabled choices. Decisions already made in that managed home take precedence.
Codex still checks the hook contents: an edited hook is not automatically trusted.
This applies to hooks in `hooks.json` and `config.toml`, without changing
project-level trust.

## Connected services and browsing sessions (Codex)

For some providers, your connected-service choice affects which provider “home” Happier should use for session browsing.

The most important example is **Codex**:

- With **native auth**, Happier browses sessions from the machine’s standard Codex home.
- With a **connected service profile** selected for Codex, Happier browses sessions from that connected-service-backed Codex home.

In 0.3 development builds, materialized Codex homes with shared state
use one native session database across your connected accounts on that machine
and keep the full native history linked. Sharing also includes pending inputs,
generated memories and local
diagnostic entries that can contain account identifiers. A pool switch can
continue a thread's pending input using the next account. Authentication
credentials stay separate. Isolated homes and discovery probes select their
own session database. Browsing, hooks, handoff and takeover reuse the stored database
selection when they reopen a connected home.

This matters in two places:

- **Direct → Browse provider sessions**: you can explicitly choose a source/home when browsing.
- **Resume ID browse**: the picker is locked to the effective Codex home implied by your new-session selection so the chosen session can actually be resumed under that auth.

If you need to browse a different Codex home, switch the auth choice first and then browse again.

## Connected services and session handoff

Connected services are often the easiest way to preserve session continuity across machines.

Why:

- the credential is stored in Happier, not only in one machine-local provider login
- compatible backends can materialize that credential again on another machine
- you can hand off the same Happier session and continue without depending only on native Agent CLI auth on the destination

This is especially useful for:

- moving a session from one desktop/laptop to another
- moving between a host machine and a VM
- keeping continuity when only one side had previously been set up through the app

Connected services do not replace every native provider login flow. Some providers and runtimes still depend on machine-local authentication. But for supported backends, connected services are the preferred path for cross-machine continuity.

See:

- [Session handoff](/sessions/session-handoff)
- [Agent authentication](/agents/provider-authentication)

## Quotas

Quota / usage surfaces are behind the `connectedServices.quotas` feature gate.

Current quota snapshots are available for:

- `openai-codex`
- `claude-subscription`
- `gemini`

GitHub connected accounts do not currently expose quota meters in Happier.

They appear in:

- the Connected services page, beside each account (what is left and when each window resets)
- account detail pages
- the **Usage** popover in the app's sidebar rail (hover for a one-line peek); the Usage icon shows a
  red count only when an account needs a new sign-in, never for low limits
- a session banner above the composer when an account has 10% or less left and a usage reset can be
  applied (once per limit window, dismissible)
- the new-session auth picker for connected profiles

Each profile detail view lets you:

- refresh the snapshot
- inspect the provider plan label when available
- pin specific meters so the same meters appear as summary badges elsewhere in the UI

### Usage reset credits in 0.3 development

Eligible Claude subscription OAuth accounts can show saved usage resets alongside
ordinary quota and spending. A saved reset that cannot be used yet shows its count
and availability reason with **Apply reset** disabled. Claude setup tokens and
Anthropic API keys do not provide this OAuth operation.

The account controls and session recovery use the same reset owner. Refresh reads
current inventory; applying a reset checks the provider again and sends one
redemption request. For subscription pools, automatic reset use must be explicitly
enabled and the grant must cover a currently exhausted allowance selected by the
pool. A reset for another window cannot authorize automatic spending.

If the provider's answer is uncertain, Happier holds further manual and automatic
reset attempts for that account instead of retrying the debit with another key.
Availability, expiry and grant quantities come from Claude. Applying a reset is
irreversible and leaves the ordinary weekly reset schedule unchanged; see
[Claude's limit-reset guidance](https://support.claude.com/en/articles/17007452-what-is-a-limit-reset).

This integration uses an undocumented provider endpoint. Read-only discovery was
verified during development; redemption has boundary tests but has not been
verified by spending a live grant. It requires a supported Claude CLI identity
on the executing machine. Older components can retain the base usage snapshot
while omitting supplemental saved counts and reasons.

## Usage in 0.3 development

Open **Settings → Usage** to inspect recorded accounting, add usage sources from
your machines, or choose **Plans** to compare allowances and their history. These
workflows are unreleased and still being validated in 0.3 development builds.
The Usage entry requires **Usage reporting**, which is enabled by default;
allowance surfaces also require the quota support described above. Source
discovery and capture need a connected, available machine with a supported
accounting reader.

### Capture usage from outside Happier

Choose **Sources** in Usage. Happier discovers source metadata on your machines;
finding a source does not grant permission to read its accounting records.
Choose **Add** on the source you want to count, then read and confirm the
disclosure for that Agent, machine and source folder. **Not now** dismisses the
card without enabling capture. Continuing an outside session in Happier is a
separate operation and does not grant capture consent.

Consented sources read existing accounting incrementally and capture subsequent
changes in the background. Charts fill in as records arrive. Check the source's
reading status and coverage: unreadable or unsupported history stays unknown,
and a source still being read is not zero usage. Once accounting is durably
captured, later cleanup of the Agent's original logs does not erase that history.

Usage capture sends numbers, token categories, models, Agents and times to the
Happier server, where they are queryable **even on an E2EE account**. Accounting
records contain no prompts, replies, file paths or file contents. Machine
identity and opaque source-root, native-session and project keys associate the
records; readable project labels follow your account's encryption mode. This numeric disclosure is
different from quota history, which retains its account-mode protection. See
[Security](/security) for the wider encryption boundary.

- **Stop** ends collection and keeps captured history. **Resume** asks for consent
  before reading again.
- **Delete history** is separately confirmed. It removes the selected source's
  captured accounting and stops collection until you consent again; usage from
  Happier sessions is unaffected.
- **Change folder** or **Use default folder** changes the source root and ends its
  previous consent. Confirm capture again for the resulting source.

### Retained allowance history and pacing

In **Plans**, current capacity and recorded quota history are separate readings.
Happier retains accepted allowance observations, so the history describes what
was actually recorded. Missing earlier readings remain missing. Quota and
subscription history follows your account's encryption mode; authorized clients
open encrypted history for E2EE accounts.

Compare each allowance with its own reset window. The even-pace marker shows how
much of that window had elapsed at the reading; the projection estimates what
would be used or left at reset if the observed pace continued. These are estimates,
with the recorded readings and coverage as their basis. Stale observations, unknown
window duration, moved resets, changed limits or changed plans can make a
projection unavailable. Percentages from different allowances are not a single
interchangeable pool balance.

An optional **Personal pace target** expresses how much of a window you aim to
use. It is advice: it does not limit spending or switch accounts. Plan-fit
history shows how recorded, comparable ended windows finished; partial history
does not establish your complete past usage or how a different plan would have
behaved.

### Routing hints in the model picker

The model picker can show **Uses first** for the selected Agent's pools, including
the account in use, the order that follows and why an active account is kept.
This reads the existing account selector's decision. Opening or hiding the hint
does not switch accounts, and it does not rank unrelated Agents' allowances.
Choose **Hide** in the hint, or change **Routing hints in the model picker** in
the same Usage settings group as [composer gauges](#composer-gauges-in-development-builds).

### Prices and plan fit

In **Plans**, open a plan's **Details → Your monthly price** to enter a monthly
amount and currency. Save it or use **Remove entered price** to clear it. The
price belongs to that connected account and follows your account's encryption
mode. Its meaning stays explicit:

- **You entered** is your own price, not a verified payment.
- **list price …, as of …** is a dated published price for a matching plan.
- **You paid** requires a provider-reported payment fact; a plan label or list
  price cannot establish it.

The Costs view's **Model prices** editor lets you set token rates, price a model
as another model, or reset an override. API-equivalent values use the effective
catalog and overrides at query time, so changing a rate can re-price historical
usage. Vendor-reported costs stay unchanged. An unknown or unpriced model remains
unpriced rather than becoming zero cost.

Plan value uses priced API-equivalent accounting attributed to that exact
connected account. Unknown attribution and unpriced usage are excluded with
partial coverage. A price multiple is available only when the queried range fits
the witnessed current subscription period and both values are USD with a
positive subscription price. It compares recorded API-equivalent value with the
entered, reported-paid or list price; it is not a bill, paid savings or a forecast
of the whole billing period. Read the price basis, dates and coverage before
using it to judge plan fit. The billing control opens the provider's billing
page; subscription changes remain with the provider.

## Security model

For OAuth-based services, Happier clients do not exchange provider codes for tokens directly.

Instead:

1. the client receives an OAuth code through device auth, paste, or embedded browser capture
2. the client calls Happier server `/v2/connect/<serviceId>/oauth/exchange`
3. the server exchanges the code with the provider
4. the server returns an encrypted bundle sealed to the client public key
5. the client decrypts the bundle locally and stores the resulting credential record

This keeps provider secrets, including server-side OAuth client secrets, out of the UI bundle.

Token-based services, including GitHub token profiles when enabled, are stored as connected-service credentials and opened where the client/daemon needs to use them.

How the stored record is protected then follows your **account encryption mode**, exactly as it does for Saved Secrets:

- on an **E2EE account**, the record is stored as ciphertext that only your devices hold key material for;
- on a **plaintext account**, the record is stored in a form the live server can read. That is intentional — plaintext accounts have no account encryption material by design — and the record is protected by authentication, authorization, TLS and server-side at-rest sealing rather than by encryption the operator cannot undo.

See [Security](/security) for what the server can and cannot read under each mode.

When a session starts, the daemon decrypts the selected records locally and materializes only the backend-specific auth it needs for that spawn.

## Sharing one with a Team

A connected account, a connected-service pool or a provider connection can be shared with a
Team, so everybody in it uses the credential without ever holding it. **Brokered** access keeps
usable credential material on the exact Machine making the provider request; recipients do not
receive it. **Direct** access deliberately delivers usable material to the recipient. Removing
direct access stops later retrieval but cannot recall material already delivered or control
requests made outside Happier.

A shared Saved Secret remains one shared resource rather than becoming a copied personal secret for
each recipient. Happier rechecks the current Account, Team or Group grant at use time. A missing
source, stale direct preparation, unavailable broker, lost membership, or encryption-readiness
problem stays visible as a typed unavailable state with its recovery action; Happier does not
silently choose a personal credential or change delivery modes.

For the whole workflow — audience, broker placement, limits, usage and activity — see
[Shared credentials for a Team](/accounts/team-credentials).
