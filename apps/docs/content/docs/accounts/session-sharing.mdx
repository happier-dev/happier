title: Sharing
description: Share sessions and reusable work with people or Teams, choose their access, and recover when sharing is refused.
---

Give someone access to a session or to the reusable work you want them to use.
Sharing the original lets collaborators see subsequent changes; sending a copy
gives them an independent document.

## Availability

The unified sharing sheet described here is **0.3 development behavior**, not
stable-release availability. It serves sessions, workflows, roles, Launch
Profiles and Saved Secret audiences. Use a current 0.3 client and Home with the
relevant feature enabled; workflows also require the Home's Workflows feature.
Session access requires session sharing, and session public links require public
sharing. Missing server support does not grant access.

The released sharing workflow supports two paths:

- **Direct sharing with a friend** inside Happier
- **Public links** for read-only access

The current 0.3 development channel also has a collaboration path for **Teams**
and **Groups**. It is part of the normal session-sharing feature, so it is
available wherever session sharing is on, and a Home with session sharing turned
off closes it too. It uses the same access authority as direct sharing. This is development-channel behavior, not a stable-release
availability claim.

## Share reusable work (0.3 development)

Open a saved workflow and choose **Share** from its menu, or an Account role and
choose **Share…**. For a saved custom Launch Profile, open its detail page and
choose **Share…**. The first share publishes a value-free profile document;
publication can require approval.
Built-in or plugin-owned definitions do not become editable shared originals:
make an editable copy first where that surface offers it.

The sheet shows **Who has access**. Search for a person, Team or Group, add them,
then choose their access on the row. Open a row to remove access and confirm the
removal. You need owner or Admin access to manage document grants; only the
owner can assign **Admin**. The roster can be read without permission to edit it.

| Shared item | First level | Second level | Admin |
| --- | --- | --- | --- |
| Session | **Can view**: read the session | **Can steer**: contribute input and pending messages | Manage session access; runtime approval delegation is separate |
| Workflow | **Can use**: see and run it | **Can edit**: change the shared original | Edit and manage document grants |
| Role | **Can use**: use it, with personal overrides in your own Settings | **Can edit**: change it for everyone it is shared with | Edit and manage document grants |
| Launch Profile | **Can use**: start sessions with it | **Can edit**: change the shared original | Edit and manage document grants |
| Saved Secret | **Can use**: use the referenced secret in supported launches | No edit level in the audience sheet | No Admin level in the audience sheet |

A workflow shared personally can be run on the recipient's machines. Its runs
and triggers stay with the person who starts them; sharing the definition does
not share one of those runs. A Team-shared workflow run is visible to its selected
Team, subject to current membership and the surviving workflow grant. When the
workflow has several Team grants, the launch must choose its run's Team rather
than exposing the run to every Team. Session access and Team policy still control
what somebody can do in a workflow's step sessions.

**Copy link** copies an in-app address. It does not add a grant or create a
public link. The recipient must already have access on that Home. For workflows,
roles and published profiles, **Send a copy instead** exports the readable
document through the device's save/share flow. Later edits to the original do not
update that copy, and removing a grant cannot withdraw a copy already sent.

### Launch Profiles and Saved Secret references

A shared Launch Profile carries variable requirements and Saved Secret
references, never stored environment-variable values. Publication refuses a
profile with nonempty configured values. Replace those values with requirements
and appropriate secret bindings before trying **Share…** again. This restriction
applies to configured values even when a variable was not marked secret.

Sharing the profile does not grant access to its referenced secrets. Manage the
secret's audience separately from **Manage access** in the Saved Secret editor,
or use **Add a shared secret** to create one for sharing. People, Teams and Groups
all have the locked **Can use** level; adding or removing rows edits a draft until
you confirm the editor's save/share operation. A personal Saved Secret remains
personal until you explicitly share it.

The audience sheet does not reveal the value. An authorized launch can supply
that value to an Agent, app or local tool, so grant access only for uses you
intend. A recipient with a missing or revoked reference must choose an accessible
secret or configure the required value through the launch's supported input
flow. See [Saved Secrets](/accounts/team-credentials#shared-saved-secrets).

## Where shared sessions appear

Shared sessions live in the **Sessions** tab, not in Inbox.

Released 0.2 places them in a dedicated **Shared sessions** subgroup within
the normal **Active** and **Inactive** sections. In the 0.3 development channel,
there is no separate ownership group at all — shared sessions enter the same
list as your own, and the selected session-list layout controls their placement:

- **Projects** places shared sessions in their project groups.
- **Recent activity** places shared sessions in its date groups.
- **Active & inactive** places them in the groups of the matching status section.

Each row still shows who shared it, so nothing about the session's origin is
hidden by dropping the separate group.

That means shared sessions behave like regular sessions in the list:

- you can open them from the main session list
- you can pin them like other sessions
- they stay grouped with the rest of your real session workflow

Inbox does **not** list sessions just because they are shared with you.

## Direct sharing with a friend

Direct sharing is the normal collaborator workflow.

Released 0.2 uses the session’s **Sharing** screen. In the 0.3 development
channel, open **Collaboration → Access**; the old `/sharing` URL remains only as
a compatibility deep link and opens that same Access view.

### Access levels

The 0.3 sheet uses **Can view**, **Can steer** and **Admin**. Released 0.2
uses the older **View only**, **Can edit** and **Can manage** labels for these
levels.

### Can view

Use this when someone should be able to read the session but not contribute new work.

### Can steer

Use this when someone should be able to participate in the session itself.

This is the collaborative mode for continuing the transcript together. It also applies to session-wide features such as the pending queue.

### Admin

Use this when someone should be able to manage sharing for the session, including other direct shares and public-link settings.

## Permission-approval delegation

For direct shares with **Can steer** or **Admin** access, Happier can also optionally allow that recipient to approve permission prompts for the shared session.

This is a separate per-recipient setting, not a separate access level.

Use it when:

- the shared session runs against the owner’s machine,
- the collaborator needs to keep work moving,
- and you trust them to approve runtime permission prompts on that session.

If this option is available, you can turn it on when adding the share or later from the share-management dialog.

## Managing existing direct shares

From **Sharing** on released 0.2, or **Collaboration → Access** in the 0.3
development channel, you can:

- review everyone the session is shared with
- change their access level
- turn delegated permission approvals on or off when supported
- stop sharing with that person

Non-managers can still open the shared session itself, but they do not get the full sharing-management surface.

## Team and Group access (0.3 development)

When the collaboration feature is enabled, the access editor can grant a
Session to a **Team** or a **Group** as well as to an individual Account. A
member receives the Session capabilities supplied by the current grant and
their active membership. Removing the last applicable direct, Team, or Group
grant removes access; another surviving grant can keep the member's access.

Team and Group visibility is separate from personal attention. Being able to
browse a Session does not create an unread row, Follow, Inbox item, Activity
entry, badge, local notification, or push event. Follow and assignment are
personal choices with their own settings.

### Session discussions (0.3 development)

When both session sharing and `sessions.conversations` are enabled, a
current Session reader can read its human discussions. People with edit access
can start discussions and post messages; discussion creators can rename or
archive their own active discussions while Session managers can also restore
them. Archived discussions remain readable. In current 0.3 development source
the Conversations feature is on by default, with
`HAPPIER_FEATURE_SESSIONS_CONVERSATIONS__ENABLED=0` as the operator opt-out
([feature flags](/extras/feature-flags)). It still resolves false whenever
Session collaboration is absent, disabled or malformed, and a declared client
capability alone does not enable it. The feature has not shipped in a public
release.

Discussion access always follows the Session's current direct, Team, or Group
access. A mention does not grant access, and removing someone's final Session
grant removes their discussion access as well. Unread position is private to
each personally tracked Account; fetching a page does not mark it read.

In E2EE mode, titles and message bodies are encrypted on the client. The sync
service still sees the identifiers, ordering, authorship, mentioned Account
IDs, timestamps, archive state, read cursor, and ciphertext size needed to
synchronize and present the feature. The feature fails closed if the Session
key is not ready or stored content does not match the Session's encryption
mode.

Human posts retain the authenticated Account that submitted them. Posts made
through an Agent retain the actual admitted runtime Account plus explicit Agent
provenance; asking an Agent to post does not make the requester the author or
lend the Agent that person's private settings. An Agent's authority stays the
principal its runtime was started with, whoever wrote the most recent message.
Reading or posting does not by itself Follow the Session.

Attribution is accountability, not containment. Knowing which Account or Agent
wrote a discussion message says nothing about what that Agent can reach on disk:
a discussion, a selected folder, or a Session boundary does not restrict an
Agent's shell access. The OS and Agent sandbox configuration on the machine
running the Session is the actual boundary, and sharing a Session does not narrow
it. Share edit access only with people whose use of that machine you intend.

Conversation drafts for an existing Session use the same Session encryption
owner as its transcript. Retrying creation preserves the original creation and
first-message identities so an uncertain response can rejoin instead of
silently creating a second discussion. Linked Agent activity remains the
canonical Run activity; the discussion does not copy or become another Agent
transcript.

The Team policy can propose or require an explicit Team grant for a Session
created in that Team context. In the current development contract, both
`team_default` and `team_required` start at **Can steer** without permission-
approval delegation. A required grant cannot be removed or reduced below **Can
steer** while that policy still applies. An explicitly stronger Admin grant
remains stronger and can later return to Can steer.

The Session's primary Team can also restrict sharing outside that Team:

- **Allowed** permits normal external Account, Team, Group, and public-link
  changes.
- **Team admins only** requires current Team policy-management authority before
  external access is added or increased.
- **Disabled** blocks new or increased external access and public-link
  publication while still allowing access to be reduced or removed.

Changing the primary Team can change which existing recipients count as
external. Happier previews that consequence and asks for confirmation, then the
Home rechecks the current policy when it commits the change. Tightening a Team
policy does not pretend to recall content or keys that were already disclosed.

### Assign responsibility (0.3 development)

A Session can name one responsible person from its current readable audience.
Responsibility is accountability, not access: assigning someone grants no new
capability, and losing the final applicable access clears the assignment. A
read-only collaborator can see the assignee but cannot change it unless their
current Session capabilities allow assignment.

Assignment can opt the assignee into Follow with important notifications through
their own settings. An explicit per-Session Follow choice still wins, assigning
yourself does not send a redundant self-notification, and choosing **No one**
clears the assignment.

### See who is viewing (0.3 development)

Mounted Session surfaces share one live presence view. The Session header shows
a compact facepile when other named viewers are present, including named guest
Accounts, and the **Collaboration** surface shows the full **Viewing now** list.
At compact widths the facepile remains a direct way to open Collaboration.

Presence is deliberately temporary. Multiple qualified tabs or devices for one
Account appear once, and **Typing…** appears only while that viewer currently has
permission to submit input. A Session leaves the declaration when its last mounted
surface closes, and backgrounding the app sends an empty declaration; typing also
expires automatically.

If the socket disconnects, the server does not support this protocol version, or
a current snapshot has not arrived, Happier treats the viewer list as unknown.
A previous observation may remain visible as stale context, but it is not an
online/offline claim. A current empty list means only that no other authorized
viewer is in the Session presence room at that moment.

Viewing and typing do not mark a Session read, change unread state, Follow it,
add it to My Work or Activity, suppress notifications, or create a badge. Human
presence is negotiated independently of the session-sharing feature. It is
visible in the 0.3 development Collaboration host whenever normal Session
sharing is available, as are Team/Group grants and responsibility. Loaded web/native and clustered access-loss journeys
are still validation gates, not stable-release availability claims.

## Public links

Public links are for **view-only** access.

They are useful when you want to share the session with someone who does not need a normal collaborative share.

### Public-link options

When you create or regenerate a public link, Happier can configure:

- **expiration**: 7 days, 30 days, or never
- **max uses**: unlimited, 10, or 50
- **consent requirement**: whether the viewer must explicitly consent before opening

### Public-link management

After a public link exists, Happier shows:

- a QR code
- the URL
- the token or a note that the token is not recoverable
- expiration details
- usage count
- whether consent is required

You can also:

- open the link
- copy the link
- regenerate it
- delete it

For a Session with a primary Team, enabling or widening a public link follows
that Team's external-sharing policy. Disabling or deleting the link remains
available to an otherwise authorized manager even when the policy prevents new
external publication.

## Encryption and sharing readiness

On encrypted deployments, a direct, Team, or Group recipient must be ready for
secure sharing before the recipient can read encrypted content. The trusted
Happier app or CLI host opens the Session's existing data key and seals only that
same key for a ready direct recipient; the public access Action stays key-free.
This keeps encryption preparation separate from deciding who is allowed access.

In practice, a grant can become visible before its recipient envelope is ready.
The Session then remains explicitly **preparing** or **locked** until the
envelope is available; it never falls back to plaintext. Some recipients may be
temporarily unavailable until their account or device has the required sharing
keys ready.

The current 0.3 development source also has the bounded Team/Group membership-
history preparation resource and its client host. It reuses the same canonical
recipient-envelope owner rather than creating Team or Group keys. This is source
implementation, not a claim that native, large-corpus, or release validation has
completed.

On plaintext-storage deployments, sharing still works as a normal product feature. The difference is the storage mode behind the scenes, not the user-facing sharing model.

A Session's storage mode does not describe how content reaches it. Content sent
through the external Action API or SDK with an ordinary `hap_v1` API Token is
readable by the Home relaying it, even when the Session it lands in is E2EE;
sealing at rest does not seal ingress. Use a direct daemon endpoint, or the
development encryption-capable `hapc_v1` credential that protects the whole
request and result, when that transit matters. Details are in
[SDK and Action API](/extending/sdk#server-relay-readability-and-revocation).

For the storage model itself, see [Encryption model](/security/encryption).

## Shared sessions and other session features

Shared sessions are still normal sessions, but access and attention are
separate decisions.

That means shared sessions can still have:

- per-Account unread state and read-state actions when your Account is tracked
  for the Session
- permission or user-action prompts
- pending messages
- active/inactive status

The important difference is where each kind of attention appears:

- the session itself appears in the **Sessions** list, grouped by the selected
  session-list layout
- urgent decisions and unread follow-up can still appear through the normal attention surfaces such as **Inbox**

### Session-to-Session Follow context (0.3 development)

An Agent Session can follow another authorized Session and receive bounded
optional context from it during a normal turn. The source and destination keep
their ordinary Session identities and access rules; Follow does not create a
second Session type or grant access. Before each injection, Happier rechecks the
current Follow edge and the source/destination audience relationship. It
acknowledges only the exact update accepted by the Agent provider, so omitted
context remains available for a later turn.

The ordinary Account-backed daemon path is wired in current development source,
and the restricted temporary-computer Runner installs the same scoped source key
through the ordinary preparation contract rather than a separate Runner path.
Following is on by default (`HAPPIER_FEATURE_SESSIONS_FOLLOWING__ENABLED=0` is the
operator opt-out); end-to-end validation of the temporary-computer leg is a release
check, separate from the Home feature decision.

For details, see [Session read and unread state](/organize/session-read-state).

## Typical workflows

### Share a session directly with a teammate

1. Open the session
2. On released 0.2, open **Sharing**. In the 0.3 development channel, open
   **Collaboration → Access**.
3. Search for the person.
4. Choose **Can view**, **Can steer**, or **Admin** in 0.3 (the older labels
   above apply on released 0.2).
5. Optionally allow permission approvals for edit/admin recipients.

### Grant Team or Group access (0.3 development)

1. Open the Session's Collaboration surface.
2. Open **Access** and search for a Team or Group.
3. Choose the access level for that principal.
4. Review any policy-required state and confirm the change.

The Team or Group grant controls visibility and capability. It does not
subscribe every member to personal notifications or create read state for
members who have not started following the Session.

### Give someone read-only public access

1. Open the session
2. On released 0.2, open **Sharing**. In the 0.3 development channel, open
   **Collaboration → Access**.
3. Open **Public link**.
4. Choose the expiration, usage limit, and consent settings
5. Create the link
6. Share the URL or QR code

### Find sessions shared with you

1. Open **Sessions**
2. Find the session in **Shared sessions** under **Active** or **Inactive** on
   released 0.2; in the 0.3 development channel it sits in the ordinary group
   supplied by your selected layout, or search for it by name
3. Open or pin the session you need

## When access or approval is refused (0.3 development)

If an administrator removes the grant that gives them their final document
access, a successful removal closes their access too. The sheet clears the
roster and editing controls and says **You no longer have access**. Another
surviving personal, Team or Group grant can preserve a lower level of access;
it does not preserve the removed Admin permission. Ask the owner or a current
administrator to restore access if the removal was unintended.

An approval request is pending work, not confirmation that sharing changed.
Open its details and have an authorized person decide it, then refresh or reopen
the shared item to inspect the acknowledged state. After an uncertain response,
check the roster before repeating the change. A retryable failure offers retry;
missing access, unavailable support or an ineligible recipient needs its stated
prerequisite repaired first.

If approval says **This sign-in cannot approve requests**, sign in to the same
Home with that Account's recovery key, or approve from another device with an
Account sign-in. A terminal-derived sign-in can request an operation without
having authority to approve it. Home administration privileges, a content
encryption key or another Account's sign-in do not replace the required Account
authority. See [Account security](/accounts/account-security).

For encrypted content, permission and key readiness are separate: access may
still be preparing or locked. Use the displayed preparation/recovery action;
the app does not reinterpret unavailable encrypted content as plaintext.

Sharing with an existing Team is distinct from inviting somebody into it.
[Team invitations](/accounts/team-invitations) need a published authenticated
Home address and an application address for the join screen. A Home that has
not published these cannot issue a transferable invitation link. Email delivery
is a separate prerequisite for email invitations, not a substitute for those
addresses.
