## Current contract

Happier has a real plugin runtime today, and the installable package format is in a transitional Wave 1/Wave 2 state:

- Installable packages are discovered from a local directory or installed archive.
- The package manifest is `.happier-plugin/plugin.json`, with `schemaVersion: 2` as the canonical install/runtime authoring shape.
- `schemaVersion: 1` remains as a narrow compatibility bridge for older static manifest provider/backend/action/hook fixtures.
- The CLI runtime loads executable plugin code from the **daemon target only**.
- The daemon module activates through `export async function activate(api) { ... }`, and activation-time registrations must declare matching `runtime.capabilities` and `permissions`.

Important: the CLI/plugin loader now reads canonical manifest V2 packages directly and upconverts manifest V1 through a compatibility bridge. When you author `activate(api)` registrations, use `schemaVersion: 2` and declare the runtime families and permissions you consume.

## Package anatomy

The practical local authoring layout is:

```text
my-plugin/
├─ .happier-plugin/
│  └─ plugin.json
├─ daemon.mjs
└─ resources/
   └─ ...
```

Minimal activation-time manifest:

```json
{
  "schemaVersion": 2,
  "id": "com.example.my-plugin",
  "version": "0.1.0",
  "displayName": "Example Plugin",
  "description": "Local development plugin",
  "engines": {
    "happier": "^0.2.0"
  },
  "runtime": {
    "apiVersion": 1,
    "capabilities": ["actions"]
  },
  "permissions": [
    {
      "capability": "actions.register",
      "reason": "Register the example action during activation"
    }
  ],
  "targets": {
    "daemon": {
      "entry": "./daemon.mjs"
    }
  },
  "contributions": []
}
```

Daemon entry files must currently resolve to `.js`, `.mjs`, or `.cjs`.

## Local development workflow

The supported dev loop is **local path + explicit reload**:

```bash
happier plugins install /absolute/path/to/my-plugin
happier plugins show com.example.my-plugin
happier plugins reload com.example.my-plugin
```

Recommended loop:

1. Create a plugin folder with `.happier-plugin/plugin.json` and `daemon.mjs`.
2. Install it from its local directory with `happier plugins install /abs/path/to/plugin`.
3. Verify the source and manifest path with `happier plugins show <pluginId>`.
4. Edit `daemon.mjs`, resources, or descriptor metadata in place.
5. Run `happier plugins reload <pluginId>` after each change.

Notes:

- There is **no filesystem watcher** for plugins in this wave.
- Reload is explicit and generation-based.
- If a reload fails after a plugin edit, the host keeps the last known good runtime registry when one exists.
- `happier providers list` is the fastest way to confirm provider/backend contributions became visible after install or reload.

## Session-driven self-improvement

The current Happier equivalent of Pi-style self-extension is **real, but still explicit**.

What is proven today:

- a live Happier session can scaffold a local plugin inside the workspace
- that same plugin can be installed as a trusted local path plugin
- the same active session can use the shell/CLI bridge to execute the new capability immediately
- the same active session can then edit the plugin again, reload it, and use the changed capability again

The exact proven loop is:

1. Start a normal Happier session with workspace edit access.
2. Have the session create a plugin folder with `.happier-plugin/plugin.json` and `daemon.mjs`.
3. Install it from the local path with `happier plugins install /abs/path/to/plugin`.
4. Execute the new capability from the active session through the Happier bridge.
5. Edit the plugin in place.
6. Run `happier plugins reload <pluginId>`.
7. Execute the same capability again and confirm the changed behavior.

For plugin-owned tools/actions, the most direct bridge path is:

```bash
happier tools call \
  --session-id <sessionId> \
  --directory /abs/path/to/repo \
  --source happier \
  --tool action_execute \
  --args-json '{"actionId":"com.example.my-plugin.tool","input":{}}' \
  --json
```

This explicit `action_execute` path matters because a newly edited local plugin capability can be usable before every discovery surface has refreshed.

## Current gaps vs Pi

Compared with Pi’s smoother package loop, Happier still has deliberate friction:

- install/link is explicit
- reload is explicit
- there is no filesystem watch/hot-reload
- the best current self-improvement path is still CLI/shell-driven rather than a dedicated in-product “develop this plugin” flow
- dedicated browser/manual validation of detail-page reload continuity is still less mature than the CLI/runtime proof path

So the current recommendation is:

- use local-path plugins for active development
- keep the session in the same workspace
- edit in place
- reload explicitly
- call the plugin capability again through the Happier bridge to confirm the new generation

## Activation API

Runtime activation is daemon-side:

```js
export async function activate(api) {
    api.registerAction({
        id: 'com.example.echo',
        title: 'Echo',
        surface: 'cli',
        handler: async (request) => ({
            ok: true,
            data: { input: request.input }
        })
    });

    api.onDispose(async () => {
        // close handles, flush state, etc.
    });
}
```

Current host API methods:

- `registerProvider(...)`
- `registerBackend(...)`
- `registerAction(...)`
- `registerTool(...)`
- `registerCommand(...)`
- `registerHook(...)`
- `registerLifecycleHandler(...)`
- `registerRuntimeAdapter(...)`
- `registerDisposable(...)`
- `onDispose(...)`

Recommended rule: use a named `activate` export even though the loader also accepts a default-export fallback.

What is **not** available yet:

- a plugin-side `requestReload(...)` API
- executable UI plugins
- executable server plugins

## Contribution families

### Supported today

These families are live in the current CLI/runtime:

| Family | Current declaration path | Notes |
| --- | --- | --- |
| Providers | Manifest V1 compatibility bridge and activation-time `registerProvider` | Provider definitions join the same merged registry as built-ins. |
| Backends | Manifest V1 compatibility bridge and activation-time `registerBackend` | Backend runtime adapters still need daemon-side handlers. |
| Runtime adapters | Backend manifest entries or activation-time `registerRuntimeAdapter` | Handler execution stays daemon-local. |
| Actions | Manifest V1 compatibility bridge and activation-time `registerAction` | Current real action path is plugin-owned daemon execution. |
| Hooks | Manifest V1 compatibility bridge and activation-time `registerHook` | Hook coverage is real but still narrower than the long-term plan. |
| Tools | Activation-time `registerTool` | Tool registrations are daemon-hosted and require the `tools` runtime capability plus `tools.register`. |
| Commands | Activation-time `registerCommand` | Command registrations are daemon-hosted and require the `commands` runtime capability plus `commands.register`. |
| Resources | Static `contributions.resources` / `contributes.resources` manifest data | Resources are descriptor-only projection data and are not created by activation-time API calls. |
| UI descriptors | Static `contributions.uiDescriptors` / `contributes.uiDescriptors` manifest data | UI descriptors are host-rendered descriptor-only projection data and are not created by activation-time API calls. |

### Not supported yet

These surfaces exist in the plan or protocol drafts, but not in the live install/runtime contract:

- npm/package/git install sources
- automatic plugin watch/reload
- plugin-triggered reload APIs
- executable UI/server plugin code

## Reload workflow

`happier plugins reload [pluginId]` rebuilds the executable plugin runtime registry.

Today that means:

- plugin daemon modules are re-imported with cache-busting
- activation runs again against a fresh API host
- activation-time registrations replace the old runtime registry on success
- old disposables are disposed after the new registry becomes active
- activation failures keep the prior last-known-good registry when available

This is the intended loop for self-extension work today: edit a local plugin, then trigger reload from the CLI.

## Trust and source model

Source support is intentionally conservative.

Direct install currently supports:

- local directories
- local archives (`.tar.gz`, `.tar.xz`, `.zip`)
- remote archive URLs
- marketplace catalogs whose entries resolve to archives

Source kinds that are **not** installable today:

- npm/package sources
- git sources

Trust behavior:

- Local directories resolve as `path` + `local_trusted` + `link`.
- Local archives install as `archive` + `local_trusted` + `managed_install`.
- Remote archives and marketplace archive installs currently resolve as `archive` + `prompt` + `managed_install`.
- `untrusted` plugin code is refused before daemon import.
- `prompt` plugin code also fails closed before daemon import because the explicit trust-approval UX is not finished yet.

Practical implication: **local path authoring is the supported executable development flow** right now. Remote archive and marketplace installs are useful for catalog/install plumbing, but executable daemon loading still requires the trusted local-dev path until the approval surface lands.

Additional safeguards:

- archive installs reject symlinks in the extracted payload
- daemon code only runs on the machine-local daemon side
- UI descriptors are projected into host-rendered settings/setup/status surfaces rather than running arbitrary plugin UI code
