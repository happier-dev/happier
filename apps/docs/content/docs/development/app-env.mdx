The Happier app (`apps/ui`) uses Expo. Expo supports loading `.env*` files for **local** development and then inlining `EXPO_PUBLIC_*` variables into the JS bundle at bundle/build time.

## Local overrides (recommended)

To keep repo-local settings out of Git, use a local env file:

```bash
cd apps/ui
cp .env.local.example .env.local
```

Then edit `apps/ui/.env.local` and restart the dev server (Metro) so the bundle is rebuilt with the new values.

## First-run build profile (0.3 development)

Source builds have no hosted Happier Cloud defaults. On first run, choose a sign-in service or Home; a self-hosted web app still uses its own origin when no Home is configured. Saved selections remain authoritative over build defaults.

Set `EXPO_PUBLIC_HAPPIER_BUILD_DEFAULT_PROFILE_JSON` before bundling the app. CLI builds use `HAPPIER_BUILD_DEFAULT_PROFILE_JSON`; the CLI-common build embeds it in the published runtime, so people do not need the build environment when running the CLI.

```bash
EXPO_PUBLIC_HAPPIER_BUILD_DEFAULT_PROFILE_JSON='{"accountService":{"url":"https://accounts.example.com"},"home":{"url":"https://home.example.com","webappUrl":"https://app.example.com"},"personalHome":{"value":"offer"}}'
```

`accountService.url` selects the default sign-in service independently of `home.url`. Optional `home.webappUrl` supplies a separate web client; otherwise Home links use the Home origin. `personalHome.value` accepts `auto`, `offer`, or `off`: automatic bootstrap, a one-click full Personal Home setup offer, or no new local installation. It never stops or removes an existing Home. Each field accepts an optional `locked` boolean in the shared profile schema, reserved for policy composition; the build profile supplies defaults.

Official builds supply the Cloud Account service and Home with `personalHome.value: "offer"`. A missing profile supplies no hosted endpoints. A present malformed profile is a configuration error naming its field path without echoing values. Profile values are public; do not include credentials.

## Disabling features at build time

You can disable specific UI features at build time by setting:

- `EXPO_PUBLIC_HAPPIER_BUILD_FEATURES_DENY`

Example:

```bash
EXPO_PUBLIC_HAPPIER_BUILD_FEATURES_DENY=voice,social.friends
```

This is a comma-separated list of **feature ids** (for example `voice`, `social.friends`, `bugReports`, `connectedServices.quotas`).

Setup/bootstrap examples:

```bash
# Hide self-host + SSH bootstrap surfaces from the UI bundle
EXPO_PUBLIC_HAPPIER_BUILD_FEATURES_DENY=setup.relay.allowLocalRelayHost,setup.relay.allowRemoteSshRelayHost,setup.machine.allowRemoteSshMachineSetup,remoteHosts.management
```

### Connected services build gates

Optional Connected Accounts quota surfaces have an explicit build-time gate:

- `EXPO_PUBLIC_HAPPIER_FEATURE_CONNECTED_SERVICES_QUOTAS__ENABLED` (default: `false`)

Examples:

```bash
# Enable Connected Services quota UI surfaces
EXPO_PUBLIC_HAPPIER_FEATURE_CONNECTED_SERVICES_QUOTAS__ENABLED=1
```

## Socket transport override (rare)

By default, the app uses Socket.IO / Engine.IO defaults (HTTP long-polling, then upgrade to WebSocket when possible). This is the most compatible option for corporate proxies and restrictive networks.

If you need to force WebSocket-only (for example: you run a multi-server deployment without sticky sessions and you prefer failing fast over long-polling), set:

- `EXPO_PUBLIC_HAPPIER_SOCKET_FORCE_WEBSOCKET=1`

## Security note (important)

Only `EXPO_PUBLIC_*` variables are inlined into the app bundle. Treat all `EXPO_PUBLIC_*` values as **public** (never store secrets here).

## EAS builds (cloud)

EAS build workers do not use your local `.env.local`. For cloud builds, set these variables in one of:

- `apps/ui/eas.json` under `build.<profile>.env`, or
- the Expo project’s EAS environment variables UI (and ensure the build profile sets the matching `"environment"`).

If you’re using `hstack` stacks and you’ve set **non-public** Expo config env vars (for example `EXPO_APP_*`, `EXPO_EAS_PROJECT_ID`, `EXPO_UPDATES_URL`) in a stack env file, you can sync them into EAS with:

```bash
hstack stack eas <stack> env:sync --environment production
```

See: [Mobile (iOS)](/hstack/mobile-ios) (EAS builds per stack).
