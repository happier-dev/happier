---
title: Server feature flags
description: Control which user-facing capabilities are enabled for a given server.
---

Happier supports server-advertised feature flags so each environment can expose only the features it wants.

Common examples:

- disable social/friends features,
- disable voice features,
- disable bug report upload features,
- disable pet companions or synced custom pet libraries,
- disable connected services entirely,
- disable only connected-services quota surfaces while keeping basic connected auth enabled.

Clients (mobile/web/desktop) adapt to advertised flags so disabled features do not appear as active workflows.

## Why this matters

- Cleaner UX for enterprise/self-hosted deployments.
- Better policy control without client forks.
- Fewer user surprises when a server intentionally restricts capabilities.

## Typical workflow

1. Configure feature flags on your server.
2. Restart/redeploy server if required by your deployment setup.
3. Reopen Happier clients so they refresh capabilities from the server.

## Continuing a session with another Agent

`sessions.agentSwitching` controls whether a running session can have its Agent replaced in place. It
is a server-represented flag, it depends on `sessions`, and it is **allowed by default** so the
capability appears wherever the client build supports it.

To disable it for every connected client:

```bash
HAPPIER_FEATURE_SESSIONS_AGENT_SWITCHING__ENABLED=0
```

Restart the server afterwards — the feature registry is resolved at process start.

With the flag off, the in-session Agent picker offers no target Agents and the fork flow drops its
**Configure a new session** choice. Clients treat a missing or malformed flag as disabled, so a
server that never advertises it behaves the same as one that turned it off.

This capability is in the current development source and is not yet available in released builds. See
[Continue with another Agent](/features/continue-with-another-agent).

## Pets

Pet companions use two server flags:

- `pets.companion` controls whether pet companion surfaces and local pet package actions are available.
- `pets.sync` controls synced account pet libraries.

The server allows `pets.companion` by default, but each user still has to enable pets in **Settings -> Pets** before a pet appears. This lets self-hosted and company-managed servers expose the setting without forcing pets on for everyone.

To disable pets for every connected client:

```bash
HAPPIER_FEATURE_PETS_COMPANION__ENABLED=0
```

To disable account pet library sync while still allowing built-in and local pets:

```bash
HAPPIER_FEATURE_PETS_SYNC__ENABLED=0
```
