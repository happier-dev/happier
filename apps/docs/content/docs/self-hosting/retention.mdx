title: Server retention policies
description: Configure operator age-based cleanup for self-hosted Happier servers and understand intrinsic expiry.
---

Operator-configured age-based retention is optional and disabled by default. Without retention env
vars, the server keeps sessions and records that have no intrinsic expiry forever. Records such as
RepeatKeys that carry their own `expiresAt` remain subject to that validity boundary and are reclaimed
by the same bounded sweep worker.

In unreleased 0.3 development, provider usage history has a default policy of 90 days of detailed
observations, followed by daily summaries. This policy runs even when the global retention switch
is off; set `HAPPIER_SERVER_RETENTION__PROVIDER_ACCOUNT_USAGE_HISTORY__MODE=keep_forever` to keep
all detail.

Public share access logs are kept for 90 days by default. This rule runs even when the global
retention switch is off; set `HAPPIER_SERVER_RETENTION__PUBLIC_SHARE_ACCESS_LOGS__MODE=keep_forever`
to keep them, or change `HAPPIER_SERVER_RETENTION__PUBLIC_SHARE_ACCESS_LOGS__DAYS` to choose another
window.

## What retention currently covers

Retention is implemented as one server-side sweep worker backed by one domain registry. Each registry
entry owns its domain id, environment keys, policy shape, and deletion rule, so configuration parsing,
execution, and public disclosure cannot silently maintain different domain lists. The generated
[Data and retention reference](/self-hosting/env#data-and-retention) lists the supported domains,
their environment keys, and defaults.

## How session retention works

The session rule is intentionally conservative.

When `HAPPIER_SERVER_RETENTION__SESSIONS__MODE=delete_inactive`, the 0.3 server removes the cloud copy of an eligible session. The session stays in the owner's list. A session with an existing external transcript link can open from its originating machine while that machine and the local transcript are available. Shared access ends when the cloud copy is removed. The rule checks that:

- the session `updatedAt` is older than the configured cutoff
- the session `lastActiveAt` is older than the configured cutoff
- the persisted session `active` flag is `false`
- the runtime does not currently observe the session as active in memory
- the session is not pinned

This means the server does not need to inspect or decrypt stored transcript content to apply the current session rule.

The session rule does not prune individual messages inside an otherwise-kept session. A separate
sidechain transcript policy can remove old subagent and other sidechain transcripts while preserving
the session's main transcript.

## How sidechain transcript retention works

Set a shorter sidechain policy when users should retain old main sessions but do not need every old
subagent transcript:

```bash
HAPPIER_SERVER_RETENTION__SESSION_SIDECHAIN_MESSAGES__MODE=delete_older_than
HAPPIER_SERVER_RETENTION__SESSION_SIDECHAIN_MESSAGES__DAYS=7
```

The server deletes a sidechain only when its newest stored message is older than the cutoff. A
sidechain with any newer message is preserved in full. Main transcript messages, whose `sidechainId`
is empty, are never selected by this rule. The worker scans and deletes in bounded batches using the
existing transcript index, so it does not need to inspect or decrypt message content or monopolize the
database for one unbounded scan.

## How tool output retention works

Detached tool output bodies use `HAPPIER_SERVER_RETENTION__TOOL_OUTPUTS__MODE` and
`HAPPIER_SERVER_RETENTION__TOOL_OUTPUTS__DAYS`. Expiry leaves the surrounding transcript
messages and tool metadata in place. Pins protect the main transcript from inactivity retention.
Subagent transcripts and detached outputs age out on their own schedules, including in pinned sessions.
Named plans can set each of the three periods independently.

## Review retention (0.3 development)

Reviews default to `keep_forever`. To expire completed Review history, configure the existing
`HAPPIER_SERVER_RETENTION__REVIEWS__MODE=delete_older_than` and
`HAPPIER_SERVER_RETENTION__REVIEWS__DAYS` policy and enable operator retention.

Only Reviews with a terminal `finishedAt` older than the configured cutoff are eligible. Unfinished
Reviews remain available. Deletion uses the Artifact lifecycle, removes the associated Review graph,
and publishes the removal to its recipients. Expiring a linked execution run leaves the Review intact.

## Default behavior

Operator-configured age-based retention only becomes effective when both of these are true:

- `HAPPIER_SERVER_RETENTION__ENABLED=1`
- at least one retention domain is configured with a finite policy

If retention is disabled, or if every domain is still set to `keep_forever`, the effective operator
policy remains keep-forever for every domain. Intrinsic lifecycle rules such as RepeatKey expiry still
run; they preserve rows whose intrinsic expiry is in the future.

## Provider usage history (0.3 development)

Provider usage history records quota and capacity observations shown in Plans and Limits. It is
separate from the usage events used for token and cost accounting. Its default policy is:

```bash
HAPPIER_SERVER_RETENTION__PROVIDER_ACCOUNT_USAGE_HISTORY__MODE=delete_older_than
HAPPIER_SERVER_RETENTION__PROVIDER_ACCOUNT_USAGE_HISTORY__DAYS=90
```

With automatic deletion enabled, the existing retention worker can remove detailed observations
older than this window only after their day has a summary covering its accepted observations. Days
without a summary keep their detail. A normal usage write by a client that can open the history backfills every missing day it can
read; no server decryption or separate cleanup timer is involved.

Summaries group observations by UTC day and retain each provider window's last accepted reading, peak usage, first and last
observation times, and every witnessed reset with its time and usage before the reset. Older Plans
and Limits charts use these daily observations and preserve resets within a day. Quota readings
are not additive, so these summaries do not represent conserved token, cost, or consumption totals.
Individual historical observations and exact reset-witness actions are no longer available after
their detail is deleted. Daily summaries remain available beyond the detail window.

For encrypted Accounts, a client with the Account material seals the summaries. The server stores
them and selects eligible detail for deletion without opening their content. Change the mode to
`keep_forever` to preserve detail, or change `DAYS` to choose a different detail window. These options
also appear in the existing Home data and retention settings.

## Global retention env vars

These env vars control the retention worker itself:

```bash
HAPPIER_SERVER_RETENTION__ENABLED=1
HAPPIER_SERVER_RETENTION__INTERVAL_MS=3600000
HAPPIER_SERVER_RETENTION__BATCH_SIZE=500
HAPPIER_SERVER_RETENTION__MAX_DELETES_PER_RULE_PER_RUN=100000
HAPPIER_SERVER_RETENTION__MAX_CANDIDATES_PER_RULE_PER_RUN=10000
HAPPIER_SERVER_RETENTION__SWEEP_TIME_BUDGET_MS=10000
HAPPIER_SERVER_RETENTION__DRY_RUN=1
```

- `HAPPIER_SERVER_RETENTION__ENABLED`
  - `0` or unset: operator-configured age retention is off; intrinsic lifecycle rules still run
  - `1`: configured finite domain policies can run in the same worker
- `HAPPIER_SERVER_RETENTION__INTERVAL_MS`
  - sweep interval in milliseconds
  - default: `3600000` (1 hour)
- `HAPPIER_SERVER_RETENTION__BATCH_SIZE`
  - maximum number of rows selected or deleted in one database page
  - default: `500`
- `HAPPIER_SERVER_RETENTION__MAX_DELETES_PER_RULE_PER_RUN`
  - hard cap per rule for actual deletions in one sweep
  - default: `100000`
- `HAPPIER_SERVER_RETENTION__MAX_CANDIDATES_PER_RULE_PER_RUN`
  - hard cap on candidate records examined by one rule in one sweep
  - default: `10000`
- `HAPPIER_SERVER_RETENTION__SWEEP_TIME_BUDGET_MS`
  - wall-time budget shared by the complete sweep
  - default: `10000` (10 seconds)
- `HAPPIER_SERVER_RETENTION__DRY_RUN`
  - `1` or unset: log what would be deleted without deleting it
  - `0`: apply eligible deletions
- `HAPPIER_SERVER_RETENTION__STARTS_AT` is the earliest time the session and subagent rules can remove data in 0.3. Set it to an ISO 8601 timestamp with a timezone.
- `HAPPIER_SERVER_RETENTION__NOTICE_DAYS` sets how many days before a session leaves it appears in the notice. The default is seven.

The retention worker reads these values at server startup, runs one sweep immediately, then continues
on the configured interval. Restart the server after changing retention configuration. Within a
sweep it gives each enabled domain one bounded database page in registry order, then starts another
round for domains that still have work. It stops when the data is exhausted or a row, candidate, or
wall-time budget is reached. The next scheduled sweep resumes sidechain discovery from a persisted
cursor. Successful runs log per-rule delete counts, candidates examined, database pages, stop reasons,
and whether the run was a dry run.

The one-hour default keeps expiry reasonably current and gives a backlogged server up to 24 bounded
cleanup opportunities per day. Lower intervals are supported, but keep the interval comfortably above
the sweep time budget. The worker skips overlapping runs in one process and uses a database lock to
prevent multiple server replicas from sweeping at the same time.

## Session policy env vars

Sessions use a dedicated policy shape:

```bash
HAPPIER_SERVER_RETENTION__SESSIONS__MODE=delete_inactive
HAPPIER_SERVER_RETENTION__SESSIONS__INACTIVITY_DAYS=30
```

Supported session modes:

- `keep_forever`
- `delete_inactive`

`HAPPIER_SERVER_RETENTION__SESSIONS__INACTIVITY_DAYS` must be a positive integer and is required when the mode is `delete_inactive`.

## Age-based domain policy env vars

All non-session retention domains use the same two-key pattern:

```bash
HAPPIER_SERVER_RETENTION__<DOMAIN>__MODE=delete_older_than
HAPPIER_SERVER_RETENTION__<DOMAIN>__DAYS=30
```

Supported age-based modes:

- `keep_forever`
- `delete_older_than`

Use the domain-specific keys in the generated
[Data and retention reference](/self-hosting/env#data-and-retention).

Connected-account OAuth and device attempts use expiring RepeatKey rows. A live CLI daemon reclaims
its exact durable transaction when the attempt expires, and an exact server read or mutation also
removes that row after expiry. If the daemon exits first and the exact attempt is never accessed
again, the server's existing bounded RepeatKey sweep still reclaims the row after its intrinsic
`expiresAt`, including when global retention is disabled or `REPEAT_KEYS` is `keep_forever`.
Keep-forever continues to preserve RepeatKeys whose intrinsic expiry is still in the future; it does
not extend an expired authentication transaction's validity or physical lifetime. The API bounds each
attempt row's payload size and lifetime but does not impose an arbitrary per-account count quota.

Example:

```bash
HAPPIER_SERVER_RETENTION__ACCOUNT_CHANGES__MODE=delete_older_than
HAPPIER_SERVER_RETENTION__ACCOUNT_CHANGES__DAYS=30
```

## Recommended rollout

Start conservatively:

1. Enable only the rules you actually need.
2. Preview the sweep with `HAPPIER_SERVER_RETENTION__DRY_RUN=1`. This is the default in 0.3 development.
3. Begin with session retention and one or two short-lived operational domains such as auth requests or access logs.
4. Review the server logs to confirm the expected records would be deleted.
5. Set `DRY_RUN=0` after the dry-run output matches your intended policy.

For many self-hosted setups, a good first production policy is:

```bash
HAPPIER_SERVER_RETENTION__ENABLED=1
HAPPIER_SERVER_RETENTION__INTERVAL_MS=3600000
HAPPIER_SERVER_RETENTION__BATCH_SIZE=500
HAPPIER_SERVER_RETENTION__MAX_DELETES_PER_RULE_PER_RUN=100000
HAPPIER_SERVER_RETENTION__MAX_CANDIDATES_PER_RULE_PER_RUN=10000
HAPPIER_SERVER_RETENTION__SWEEP_TIME_BUDGET_MS=10000
HAPPIER_SERVER_RETENTION__SESSIONS__MODE=delete_inactive
HAPPIER_SERVER_RETENTION__SESSIONS__INACTIVITY_DAYS=30
HAPPIER_SERVER_RETENTION__SESSION_SIDECHAIN_MESSAGES__MODE=delete_older_than
HAPPIER_SERVER_RETENTION__SESSION_SIDECHAIN_MESSAGES__DAYS=7
HAPPIER_SERVER_RETENTION__ACCOUNT_CHANGES__MODE=delete_older_than
HAPPIER_SERVER_RETENTION__ACCOUNT_CHANGES__DAYS=30
HAPPIER_SERVER_RETENTION__TERMINAL_AUTH_REQUESTS__MODE=delete_older_than
HAPPIER_SERVER_RETENTION__TERMINAL_AUTH_REQUESTS__DAYS=7
HAPPIER_SERVER_RETENTION__ACCOUNT_AUTH_REQUESTS__MODE=delete_older_than
HAPPIER_SERVER_RETENTION__ACCOUNT_AUTH_REQUESTS__DAYS=7
```

## What users see in the app

Happier surfaces the server's complete retention policy so users understand what it keeps and what it
eventually deletes. The UI renders the server-provided domain list generically, including domain ids a
newer server adds before the client has a dedicated label.

Today that information is exposed in:

- the active server settings screen
- the login and registration entry screen, before authentication
- session info for sessions affected by finite session retention
- saved server rows

Clients first read the unauthenticated `GET /v2/retention-policy` endpoint. It returns a complete array
of effective domains. Older servers fall back to `GET /v1/features`, under
`capabilities.server.retention`; that legacy response is explicitly treated as partial because v1
cannot represent message-level or usage-event policies. This keeps independently upgraded servers
parseable by released strict v1 clients.

## Operational notes

- Session retention is based on server-side metadata such as `updatedAt`, `lastActiveAt`, and `active`, not by decrypting stored messages.
- Sidechain transcript retention uses server ingestion timestamps and deletes only wholly expired sidechains; it does not decrypt message content.
- Account change retention can advance the server `changesFloor`. After old account changes are pruned, very old `/v2/changes` cursors can become invalid and return `410 cursor-gone`.
- Retention deletes are permanent. There is no built-in quarantine or archive stage before deletion.
- Like any timestamp-based cleanup system, retention depends on accurate server time and correct stored timestamps. If you manually corrupt timestamps in the database or run with a badly wrong system clock, the policy can make wrong decisions.

## Keep-forever example

If you want to keep the current behavior explicitly, either do not set any retention env vars, or set:

```bash
HAPPIER_SERVER_RETENTION__ENABLED=0
```

## Dry-run example for 30-day inactive sessions

```bash
HAPPIER_SERVER_RETENTION__ENABLED=1
HAPPIER_SERVER_RETENTION__DRY_RUN=1
HAPPIER_SERVER_RETENTION__SESSIONS__MODE=delete_inactive
HAPPIER_SERVER_RETENTION__SESSIONS__INACTIVITY_DAYS=30
```
