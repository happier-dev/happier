---
title: Setup & bootstrap policy
description: Control which setup surfaces (Relay selection, hosting, SSH bootstrap, Remote hosts) are available to clients.
---

Happier clients (desktop/web/mobile/CLI) discover what setup surfaces are allowed by calling:

- `GET /v1/features`

These are build/server policy gates, not user-facing settings toggles. They let a deployment hide setup surfaces entirely without changing the app UI copy or introducing alternate code paths.

This matters for enterprise and embedded deployments where you may want to:

- pin users to a single Relay (no Relay selection UI),
- disable Happier Cloud in favor of an internal Relay,
- disable self-host/relay-host installation surfaces,
- disable SSH bootstrap surfaces,
- allow SSH bootstrap but disallow persisting remote-host profiles,
- disallow syncing secret material (passwords/private keys) even when remote hosts are enabled.

## First-run defaults (0.3 development)

Custom source builds do not include hosted Happier Cloud endpoints by default. A self-hosted web deployment keeps its same-origin Home fallback; native clients and the CLI ask for a service or Home when none is configured. Existing saved selections are retained.

Builds can supply independent Account-service, Home, and Personal Home defaults using the [first-run build profile](/development/app-env#first-run-build-profile-03-development). Official builds select the Cloud Account service and Home, and offer the full local Personal Home setup when the person chooses it. These defaults do not replace the setup feature gates below.

For machine-level desktop and CLI/daemon defaults and locks, see [Organization policy](/self-hosting/organization-policy) (unreleased 0.3 development). Its feature policy is deny-only; the existing build and server gates still narrow availability.

## Feature gates vs capabilities

`/v1/features` contains:

- `features.*.enabled` — the **only** authoritative boolean gates clients should use
- `capabilities.*` — configuration details and diagnostics (clients must not treat these as gates)

If a gate is missing or malformed, clients should treat it as disabled.

## Setup surface feature ids

These feature ids control which setup surfaces the clients will offer:

### Relay selection & hosting

- `setup.relay.allowRelaySelection`
- `setup.relay.allowHappierCloud` (Happier Cloud is `https://api.happier.dev`)
- `setup.relay.allowCustomRelayUrl`
- `setup.relay.allowLocalRelayHost`
- `setup.relay.allowRemoteSshRelayHost`

### Relay access helpers (optional)

- `setup.relayAccess.allowTailscale`
- `setup.relayAccess.allowCloudflareTunnel`

### Machine setup

- `setup.machine.allowLocalMachineSetup`
- `setup.machine.allowRemoteSshMachineSetup`

### Provider onboarding

- `setup.providers.allowProviderSetup`

### Remote hosts (SSH profiles)

- `remoteHosts.management` (allows saved remote-host profiles in the UI)
- `remoteHosts.secretMaterial` (allows saving synced secret material; depends on `remoteHosts.management`)

Notes:

- If `remoteHosts.management` is disabled, clients can still support one-time SSH setup without persisting hosts.
- If `remoteHosts.secretMaterial` is disabled, hosts can be saved without saving passwords/private keys.

## Build policy denies (shipping policy)

Some builds (for example enterprise desktop/mobile builds) need to remove surfaces entirely.

Build policies apply a global allow/deny list to `/v1/features` before clients see it, so:

- disabled features don’t appear as available,
- clients don’t need ad-hoc “enterprise checks”,
- the same binary can target multiple server policies safely.

Common policy inputs:

- Server/build: `HAPPIER_BUILD_FEATURES_ALLOW`, `HAPPIER_BUILD_FEATURES_DENY`
- App build (Expo): `EXPO_PUBLIC_HAPPIER_BUILD_FEATURES_DENY`

Example (deny remote SSH setup + remote-host persistence surfaces):

```bash
HAPPIER_BUILD_FEATURES_DENY=setup.machine.allowRemoteSshMachineSetup,setup.relay.allowRemoteSshRelayHost,remoteHosts.management
```
