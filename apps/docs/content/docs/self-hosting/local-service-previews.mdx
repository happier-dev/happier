title: Local service previews
description: Let people open a dev server running on their machine from the Happier app — what to configure, and what each missing piece looks like when it is wrong.
---

Someone runs `npm run dev` on their laptop, opens Happier on their phone, and taps the
service in the launchpad. The page loads. That is a **local service preview**: the app
reaches a port bound to `127.0.0.1` on a machine, through your relay, without that port
being exposed to anything else.

This page is about turning that on for a self-hosted relay. It also covers **public
exposure** — the shareable-link feature that puts one of those services on the open
internet — which is disabled by default and remains a development feature.

## Availability

| Capability | Status | Default |
| --- | --- | --- |
| Detecting local services and listing them in the launchpad | Shipped | On |
| Opening a private preview from the app | Shipped, with a usable signer and a relay port allowlist | Feature on; relay tunnel and ports need configuration |
| Public exposure through a shareable secret link | Development only | Off |

Private previews are the normal path and the rest of this page is mostly about them.

**Local service scan needs attention** describes a discovery problem. Its detail
identifies an unreadable or missing Project folder, unavailable open-project
information, a partial scan, or a failure to list the Machine's processes. A
partial scan means some services may be missing; it does not mean a service
failed to start. Restore the named folder access or Machine prerequisite before
refreshing discovery. Service start and preview failures have their own outcomes.

In unreleased 0.3 development builds, every Home derives its route-grant signer from its
existing master secret by default, including generic, Team/shared, dev, QA, preview and
self-hosted Homes. Explicit signing variables remain an operator override. This signer
default is a development-source contract, not a stable or preview availability claim.

<Callout type="warn">
  **Public exposure is not a released availability claim.** Leave
  `HAPPIER_FEATURE_LOCAL_SERVICES_PUBLIC_PREVIEW__ENABLED` unset for the default private-only
  deployment. Development builds use the actual server policy and the prerequisites below;
  there is no separate “until review” activation switch.
</Callout>

## What you need first

- A relay you control the environment of. All of this is server-side; **nothing is
  configured on the machine running the dev server.**
- For an explicit override, the ability to generate and store a private key as an
  environment variable.
- A rough idea of which ports your people actually develop on. The relay needs an explicit
  allowlist and it starts empty.

## How a preview actually travels

Worth thirty seconds, because every failure below is one of these three steps refusing.

1. **The machine registers a preview.** Its daemon tells the relay "session X can reach
   `127.0.0.1:5173` on this machine".
2. **The relay mints a route grant.** A short-lived Ed25519-signed token that names the
   account, the machine, the flow, the route and the exact destination port. This is the
   step that needs a usable signer. In 0.3 development, the Home derives it automatically.
3. **Bytes ride the existing machine connection.** The relay forwards the HTTP request
   over the machine's socket as framed envelopes, the daemon opens a loopback connection
   to the port, and the response comes back the same way. The destination must be a
   loopback address; a grant for any other host is refused.

The daemon verifies every grant against the relay's public key, which it learns from the
relay's own capability payload. That is why there is nothing to configure on the machine —
and why a signing key you rotate takes effect as soon as machines refresh.

### Project Service previews in 0.3 development

Current development source also registers an owned Project Service without creating an
Agent Session. A Machine, workspace and declaration identify the requested service; they
do not grant access. The relay checks the exact running managed occurrence and its actual
starter against current Machine access. A URL-less service can be Running without having
an HTTP endpoint to preview.

Hiding a service or clearing its launch history does not stop it or revoke its preview.
Workspace-scoped history clearing preserves history from other workspaces on the same
Machine; use Stop to end the owned service lifetime.

Development tools can read a Project Service's public exposure status against the
exact managed occurrence, without borrowing an Agent Session.

Opening an already registered preview requests a fresh URL using the viewer's Account and
Home, including when the Browser target has no local preview snapshot. Web and server
fallback use this admission rather than another person's cached URL. Native direct access
still needs the actual registered native descriptor and its signed grant; a Browser target
alone cannot create that capability.

If an acquired native preview connection ends, the current 0.3 source releases that
viewer lease and requests fresh server-preview access through the same Home and
Account. Where that server route is available, the pane resumes there with its
in-preview path preserved. This remains development-source behavior; native-device
validation is separate.

Cooperative web previews in unreleased 0.3 builds stream the page after checking its
HTML head for script policy, including compressed responses. Each pane keeps its own
navigation identity when following links, even when several panes open the same
service. Preview admission remains separate from that identity, and the page's
original Content Security Policy still applies.

In 0.3 development, private and public preview cookies use `SameSite=None; Secure;
HttpOnly; Partitioned` within the preview's own host and path. This lets a preview embedded
under another site retain its admission. Browsers that support
[partitioned cookies](https://privacysandbox.google.com/cookies/chips) keep that admission
scoped to the top-level viewer site; opening under another site needs a fresh admission.
Older browsers that block cross-site cookies and do not support partitioning may still
refuse the embedded preview.

Unreleased 0.3 local-service previews also accept plain HTTP when the Home and its
isolated preview domain are `localhost` or subdomains of it. The preview retains the
Home's scheme and port. Other names, including `.local` and raw loopback IP addresses,
require HTTPS. Set the preview domain even for a local Home; previews still need
their own hostnames and never share the Home's API origin.

The cookie attributes above remain required on loopback HTTP. Chromium accepts them
on localhost names, including subdomains. WebKit support depends on the operating
system's cookie storage, so Safari and Tauri's WebKit clients need a check on the
actual target system. If exchange fails there, use HTTPS or a supported native direct
preview. See [WebKit's loopback-cookie support change](https://github.com/WebKit/WebKit/commit/aa297f89b9a6)
for its platform restrictions. This exception concerns local-service previews; it
does not change the stored-content public-link requirements below.

In 0.3 development, disabling the Home preview feature refuses new admissions and subsequent
requests from existing viewers. Registrations remain available if the feature is enabled again.
If a Home configuration read fails during a WebSocket upgrade, that socket closes and the server
continues serving other requests.

Final effective access loss closes the affected viewer's streams. Losing the starter's
serving admission retires the service's exposures immediately, even if native Stop is
unsupported or its outcome is still uncertain. Another valid overlapping grant preserves
access. A shared actor without a genuine requester credential channel gets
`requester_credentials_unavailable`; the daemon cannot borrow its custodian's credential.

These are development-source contracts, not certification of a loaded Project journey,
native-device support or released availability. The private relay configuration below
continues to apply.

### Process ownership and restart in development

In the current unreleased 0.3 source, a service's process attribution comes from
the same ownership evidence as the [Processes](/accounts/processes) tab. A port
is not proof of ownership, and access to a Machine is not ownership of another
operating-system user's process. A detected listener is checked again before
termination, including whether it is still the expected process and listening
on that port. If the listener is the terminal's own shell, freeing the port asks
you to confirm that this closes the terminal.

**Start again** reuses the service definition reviewed at its original start.
A changed definition is refused until the existing service-start review has
shown the actual new effect and you accept it. Declining starts nothing. The
Processes Action does not inherit a different service Action's approval or
bypass this definition review. These development contracts do not certify the
integrated authenticated restart journey.

## Turn on private previews

### 1. Use the Home's default signer

In 0.3 development, leave all four `HAPPIER_PEER_MEDIATION_ROUTE_GRANT_SIGNING_*`
variables unset to derive a stable Ed25519 signer from `HANDY_MASTER_SECRET` under the
`happier.machine-route-grant.v1` domain. This works on every Home, regardless of runtime
purpose. Local-data server runtimes load or create the existing `handy-master-secret.txt`
in their data directory; managed stacks retain the same master secret. Servers using
external backends already require `HANDY_MASTER_SECRET` for authentication.

The same master secret produces the same signing key after restart. Keep it with the
Home's existing retained data. Rotation uses the existing mechanism: change the master
secret or set an explicit signing override below. Machines learn the public key from
the authenticated server feature snapshot; they need no additional configuration.

### 2. Optional: configure an explicit signer

Use this override when you want to control the signing key or its expiry.

The private key is a **32-byte Ed25519 seed, base64url-encoded without padding**. The
relay derives the public key from it.

<Tabs items={['macOS / Linux', 'PowerShell']}>
<Tab value="macOS / Linux">
```bash
openssl rand -base64 32 | tr '+/' '-_' | tr -d '='
```
</Tab>
<Tab value="PowerShell">
```powershell
$bytes = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
[Convert]::ToBase64String($bytes).TrimEnd('=').Replace('+','-').Replace('/','_')
```
</Tab>
</Tabs>

Padding characters and `+` / `/` are rejected, so do not skip the substitution.

Set the key id and private key; the public key and expiry are optional:

```bash
HAPPIER_PEER_MEDIATION_ROUTE_GRANT_SIGNING_KEY_ID=relay-2026-08
HAPPIER_PEER_MEDIATION_ROUTE_GRANT_SIGNING_PRIVATE_KEY=<the generated value>
# Optional:
HAPPIER_PEER_MEDIATION_ROUTE_GRANT_SIGNING_PUBLIC_KEY=<derived public key, base64url>
HAPPIER_PEER_MEDIATION_ROUTE_GRANT_SIGNING_EXPIRES_AT=1788000000000
```

- **`…_KEY_ID`** is any short label you choose. It travels with every grant so a machine can
  tell which key signed it, which is what makes rotation possible. Change it whenever you
  change the private key.
- **`…_PRIVATE_KEY`** is the seed. Without it — or without the key id — the relay behaves as
  if the whole feature does not exist once any override field is present. Partial or
  invalid overrides refuse signing even when the Home has a usable master secret.
- **`…_PUBLIC_KEY`** is optional and is only ever checked, never trusted: the relay derives
  the real public key from the seed and refuses to start signing if the two disagree. Set it
  if you want a guard against pasting a mismatched pair.
- **`…_EXPIRES_AT`** is epoch **milliseconds**. Machines drop a key once that instant passes,
  so a grant signed by an expired key stops verifying. Leave it unset for a key with no
  expiry, or set it when you are staging a rotation.

In the 0.3 development implementation, the relay also refuses an expired signing key and
reports preview relay readiness as unavailable. Configuring key bytes is not enough: the
key must still be valid when a preview is admitted. This does not expire an already-open
TCP tunnel.

### 3. Allow the ports previews may reach

```bash
HAPPIER_FEATURE_MACHINES_TUNNEL_SERVER_ROUTED__ENABLED=true
HAPPIER_FEATURE_MACHINES_TUNNEL_ALLOWED_PORTS=3000,4200,5173,8000,8080
```

These two are a pair and both are restrictive by default: the relay-routed tunnel is **off**
unless you turn it on, and the allowlist is **empty**, which denies every port. A preview to
a port outside the list is refused when the grant is minted — the port is checked before any
connection is attempted, not after.

Pick the ports your framework defaults actually use rather than a wide range. The allowlist
is the only thing standing between "preview my dev server" and "preview anything listening
on loopback", including a database admin console or another person's tool.

### 4. Optional: private preview settings

| Variable | Default | What it does |
| --- | --- | --- |
| `HAPPIER_FEATURE_LOCAL_SERVICES_PREVIEW__ENABLED` | on | The private preview feature itself. Loopback-only, no internet exposure, so it defaults on. |
| `HAPPIER_FEATURE_LOCAL_SERVICES_PREVIEW__TOKEN_TTL_MS` | 5 minutes | How long a preview access token stays valid. |
| `HAPPIER_FEATURE_LOCAL_SERVICES_PREVIEW__HOST_ORIGIN_DOMAIN` | unset | A base domain for host-mode previews, so each preview gets its own origin instead of a path under the API host. |

The complete index of every variable in this family is on
[Feature environment variables](/self-hosting/feature-env).

## When it goes wrong

The app names the specific unmet prerequisite on the service row itself, so start there
rather than in the logs. Each sentence maps to exactly one thing:

| What the app says | What is missing |
| --- | --- |
| "The server relay for machine tunnels is turned off." | `HAPPIER_FEATURE_MACHINES_TUNNEL_SERVER_ROUTED__ENABLED` |
| "The server allows no tunnel ports." | `HAPPIER_FEATURE_MACHINES_TUNNEL_ALLOWED_PORTS` |
| "Local service previews are turned off on the server." | `HAPPIER_FEATURE_LOCAL_SERVICES_PREVIEW__ENABLED` |
| "Public previews are turned off on the server." | `HAPPIER_FEATURE_LOCAL_SERVICES_PUBLIC_PREVIEW__ENABLED` — expected, and correct |

An unavailable signer has no sentence of its own, because the relay does not advertise
route grants when signing refuses. In 0.3 development, check for a missing master secret
or a partial, invalid or expired explicit override; otherwise signing is derived by default.
Its symptoms:

- **Opening a preview fails with a server error**, and the relay logs
  `local_service_preview_tunnel_unavailable:grant_signing_unavailable`.
- **The route grant endpoint returns `404 Not Found`** rather than an error explaining
  itself. This is deliberate: a relay with no signing keys does not claim to offer route
  grants. A 404 there can indicate unavailable signing authority rather than a bad URL.

Two more that look alike and are not:

- **A preview to one port works and another does not.** The second port is not in
  `HAPPIER_FEATURE_MACHINES_TUNNEL_ALLOWED_PORTS`. Ports are matched exactly; there are no
  ranges.
- **Previews worked and then stopped everywhere at once.** Check
  `HAPPIER_PEER_MEDIATION_ROUTE_GRANT_SIGNING_EXPIRES_AT`. Once it passes, machines stop
  trusting the key. The 0.3 development relay also stops advertising that signer and
  refuses new grants until usable signing configuration is restored.

<Callout type="info">
  `HAPPIER_FEATURE_MACHINES_TUNNEL_DIRECT_PEER__ENABLED` sounds like it would help here and
  does not enable the server-relayed preview path. That path needs the server-routed gate
  and port allowlist above. In 0.3 development, native direct preview admission additionally
  uses the direct-peer policy and an actually available Machine native transport; turning
  on that gate alone does not supply the transport.
</Callout>

## Public exposure, and why it is off

Public exposure takes a private preview and gives it a URL anyone on the internet can open,
with no sign-in, for a limited time. It is gated behind
`HAPPIER_FEATURE_LOCAL_SERVICES_PUBLIC_PREVIEW__ENABLED`, which defaults to off.

The default private-only deployment leaves it off. Enabling public exposure makes a port on
someone's Machine reachable without sign-in; only use a development deployment whose
operator intends that exposure. Current development admission is controlled by the real
server policy, not a separate review-completion condition.

In current 0.3 development, browser sharing offers secret links and public access
when allowed by the relay policy. The **Signed-in people** mode is hidden from
that sheet until browser sign-in is supported for public sharing. Authenticated
API and agent requests can still use that mode; an ordinary browser cannot open
its URL using the Happier app's sign-in.

If you enable it, the relay still refuses to mint links until six further prerequisites
are all satisfied, and the app names whichever ones are missing on the service row:

- an allowed exposure mode,
- a maximum link lifetime,
- a host origin base domain **and** an `https:` canonical server URL — each exposure is served
  from its own origin, so there is no path-mode fallback here,
- a durable audit sink,
- a rate limit profile,
- a working rate limiter behind that profile.

The last one used to be advisory and is now required, because abuse control on an
unauthenticated public URL is not an optional extra. There is no switch to turn the audit
requirement off.

Satisfying those prerequisites allows the configured development admission; it is not a
release certification. The default stays off regardless.

In unreleased 0.3 builds, a secret link can be opened by multiple recipients until it
expires or is revoked. Opening it yourself and copying it again does not consume or
replace it. Each viewer receives a scoped admission cookie; the sharing credential
is removed from the address before the request reaches the service.

Revocation and expiry close existing preview connections even when the audit sink is
unavailable. The exposure status records the audit failure; new access still requires
working audit storage.

## Stored-content public links in 0.3 development

Public links for Sessions and documents publish stored content rather than a
port on a Machine. This is **development-only, unreleased 0.3 behavior**. They
have their own public-sharing feature decision and retain the public rate-limiter
requirement. They do not require
enabling public local-service exposure or configuring its lifetime and audit
policy.

Before creating these links, the Home operator must provide:

- An HTTPS `HAPPIER_PUBLIC_SERVER_URL`.
- A viewer origin: preferably
  `HAPPIER_FEATURE_LOCAL_SERVICES_PREVIEW__HOST_ORIGIN_DOMAIN`, with wildcard DNS
  and TLS routing each resource's separate HTTPS hostname to this Home. When
  that domain is unavailable, the Home owner can enable **Allow public links on
  this hostname** in **Home administration → Reach** to use the configured HTTPS
  public server address instead.
- `HAPPIER_FEATURE_LOCAL_SERVICES_PUBLIC_PREVIEW__RATE_LIMIT_CHECKER=fixed_window`,
  with positive `HAPPIER_FEATURE_LOCAL_SERVICES_PUBLIC_PREVIEW__RATE_LIMIT_MAX_REQUESTS`
  and `HAPPIER_FEATURE_LOCAL_SERVICES_PUBLIC_PREVIEW__RATE_LIMIT_WINDOW_MS` values
  chosen for the deployment's traffic policy.

The hostname option is off by default and applies live. An explicit deployment
value for `HAPPIER_PUBLIC_SHARES_ALLOW_SUBPATH` overrides the saved Home setting;
the row shows **Fixed by your deployment**. Admins can read it, but only owners
can change it. Restart after changing restart-applied isolated-host or limiter
configuration. An isolated domain stays preferred when configured.

Links on the Home's own hostname use the same restricted HTML sandbox. PDFs are
download-only there; isolated share hosts retain inline PDF preview. Turning the
option off blocks links on the main hostname without deleting their stored
shares. Turning it back on restores those links, subject to expiry, revocation,
use limits and the configured limiter.

This option does not supply a fallback for local-service public exposure,
private local-service web previews, or private HTML Artifact previews. Those
still need isolated origins. A single-hostname HTTPS endpoint, including
Tailscale Serve, does not change who can reach that endpoint.

Without an admitted viewer origin or limiter, creation returns HTTP 503
`public_share_isolation_unavailable`. Its `missingPrerequisites` list identifies
`viewer_origin`, `public_rate_limiter`, or both, so the operator can correct the
required configuration. No link is created; the app keeps it Off.
An HTTP-only local deployment cannot provide these public links by enabling
the sharing feature or the hostname option alone.

See [Session sharing](/accounts/session-sharing#public-links) for creating and
managing a link once the Home is ready.
