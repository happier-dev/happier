This section is about running **your own Happier relay** (the sync backend that
clients and machines connect to). Everything here is optional: Happier Cloud
exists so you do not have to.

Your clients and machines then point at your URL — say `https://api.example.com`
— instead of the Cloud one. Nothing else about how you use Happier changes.

Most production self-hosts need at least:

- `HANDY_MASTER_SECRET` — required.
- `HAPPIER_CANONICAL_SERVER_URL` — stable server identity and authentication audience.
- `HAPPIER_PUBLIC_SERVER_URL` — optional reachable ingress used by QR/deep links and public callbacks.
- `HAPPIER_WEBAPP_URL` — when you host the web client yourself, or use OAuth return-to.
- the env for your chosen storage backend (`DATABASE_URL`, `S3_*`, and so on).

## Flavors

Both flavors run the same API and the same logic. The difference is only which
storage backends they use.

- **Full** — external Postgres (default) or MySQL 8.0.17+, with S3 or a
  compatible store (default; `HAPPIER_FILES_BACKEND=local` switches to disk).
  Redis is optional and only needed for multi-replica realtime.
- **Light** — SQLite (default) or embedded Postgres (PGlite) on disk, with local
  file storage served by the server at `GET /files/*`.

Use **full** for a shared server; use **light** for the easiest single node.

<Callout>
  With SQLite and no `DATABASE_URL`, the server requires
  `HAPPIER_SERVER_LIGHT_DATA_DIR` and refuses to start without it.
</Callout>

## Roles and scaling

One process is the simple case. To split it, set `SERVER_ROLE`:

| `SERVER_ROLE` | What the process does |
| --- | --- |
| unset (default `all`) | API, realtime and background work together |
| `api` | API and realtime only — this is what clients connect to |
| `worker` | background work only, no HTTP listener |

Two things about that table are worth knowing before you rely on it:

- **An unrecognized value is not an error.** Anything other than `api` or
  `worker` — including a typo — silently resolves to `all`. A misspelled
  `SERVER_ROLE=wroker` gives you a second full server, not a worker.
- **`worker` requires the Redis adapter.** The process throws at startup unless
  `REDIS_URL` is set and `HAPPIER_SOCKET_ADAPTER=redis-streams`, because a
  worker publishes to rooms it has no direct sockets for.

The converse also holds: once the Redis adapter is on, durable presence writes
are consumed by a worker. An all-`api` deployment with Redis enabled will log
that it needs one, and presence will not be written durably until you run one.

For multi-replica API deployments, enable Redis fanout and configure sticky
sessions at your load balancer. [Docker](/self-hosting/docker) has a working
example, plus a [Kubernetes recipe](/self-hosting/docker#kubernetes).

## Redis cluster transport

The following applies to development builds using Redis Streams adapter `0.3.1`;
it does not establish availability in a stable or preview release. With `REDIS_URL`
and `HAPPIER_SOCKET_ADAPTER=redis-streams`, API replicas join one Socket.IO cluster.

**Each API process opens four Redis connections, not one.** A root client for
publishing and commands, one blocking stream reader, one Pub/Sub subscriber,
and one dedicated client for exact peer-tunnel relay admission. The adapter's
three connections are named for diagnostics, so `CLIENT LIST` shows
`happier-socket-cluster:root`, `happier-socket-cluster:adapter-1`, and
`happier-socket-cluster:adapter-2` per replica; the fourth is
`happier-socket-cluster:relay-admission`. Size managed-Redis connection limits
for all four transport connections plus ordinary application and worker connections.

**Two backplanes carry different traffic.** Ordinary room broadcasts go through
Redis Streams. Cross-node socket lookups (`fetchSockets`) and server-to-server
emission go through Redis Pub/Sub. The Pub/Sub path is transient by design: a
request issued while Redis is unavailable fails with its normal timeout rather
than being replayed later. Retry once the adapter connections have recovered.

### Redis ACL

For Redis 6.2+ ACL users, the adapter requires these permissions:

```text
~socket.io &socket.io#*
+auth +info +client|setname
+xadd +xread
+publish +subscribe +pubsub|numsub
```

These are Redis ACL rule tokens, not a shell command or a complete API-user ACL.
Preserve the existing permissions for application, worker and tunnel operations
using the same `REDIS_URL`; do not reset that user's ACL to this list. The channel
pattern covers both common requests and node-private replies. Socket.IO
connection-state recovery is disabled, so its session-key permissions are not
needed. Keep Redis authenticated and on private networking, with TLS where
appropriate: adapter messages have no separate authentication or encryption.

`SPUBLISH`, `SSUBSCRIBE`, and `PUBSUB SHARDNUMSUB` are not needed — Happier does
not use sharded Pub/Sub. Verify the ACL *before* rolling a new pool: a missing
Pub/Sub permission may leave startup healthy while cross-node discovery fails.
Check Redis command failure metrics and Redis ACL denial logs as well as a real
cross-node lookup; a successful local connection or ordinary broadcast is insufficient.

Peer-tunnel relay admission is deliberately separate from the adapter. When
server-routed peer tunnels are enabled, the API Redis credential also needs
`SET`, `GET`, `DEL`, and `EVAL` on
`peer-tunnel-relay-grant:v1:*` so it can reserve and commit one-time relay claims.
Do not broaden the adapter-only rule above or treat relay claim commands as
Socket.IO adapter requirements.

### Upgrading API replicas

Adapter `0.3.x` routes cross-node lookups over Pub/Sub; adapter `0.2.x` routes
them over the Stream. Check the adapter version in the server build you deploy. **Mixing
the two in one serving pool is not supported** — replicas would broadcast to each
other while failing to discover each other's sockets, which is worse than a
visible outage.

- One API replica: restart normally.
- Several API replicas: drain and stop the old pool, confirm it is out of
  rotation, then start the new pool as a unit. Roll back the same way: stop all
  `0.3` API replicas before starting `0.2` replicas.

Watch Redis connection count (four transport connections per API replica),
`redis-socket-cluster` error logs, and socket
reconnect health during the transition.

### Validate recovery before rollout

Use an isolated two-API-node environment with the intended Redis version and ACL.
Connect clients to different nodes and verify room updates, remote socket discovery,
RPC calls and a binary tunnel/transfer operation. Stop and restart Redis while both
API processes stay running. An in-outage transient request must fail or time out;
after all eight transport connections recover, repeat those operations and verify
server-to-server acknowledgements. Disconnect the remote client and confirm it no
longer appears in discovery.

Shut down the API nodes normally. With a separate operator credential, use
`CLIENT LIST` to verify that no `happier-socket-cluster:*` connection remains or
reappears after more than five seconds. Repeat the full recovery and shutdown
sequence twice. Also test a silently dropped connection and a deliberately missing
Pub/Sub permission in this isolated environment. Do not restart a production Redis
instance merely to follow this validation recipe.

## Reverse proxy basics

In production, run the API behind a proxy that:

- terminates TLS,
- supports WebSocket upgrades — Socket.IO realtime lives at `/v1/updates`,
- uses timeouts long enough for a long-lived connection,
- and keeps secrets in your platform's env or secret manager rather than in git.

If you serve `/files/*` from the server (light flavor), allow those routes too.

<Callout type="warn">
  Broken `/v1/updates` upgrades are the single most common self-hosting failure,
  and they do not look like a networking problem: machines register fine and
  then sit there offline, reported as `machine.none_online`.
</Callout>

### Keep capability tokens out of your access logs

Some Happier links carry a bearer capability **in the URL path**, because that is the only
place a link can carry one. Anyone who reads such a URL can use it until it expires or is
revoked. Happier redacts them everywhere it controls — server request logs, error responses,
crash reporting and client navigation logging all template the token out — but your proxy,
CDN and log pipeline are yours.

Three path shapes matter:

```text
/join/<token>                                          Team invitation (development)
/share/<token>  and  /v1/public-share/<token>          public share links
/v1/plugins/availability/ui-artifacts/browser/<token>  browser plugin Artifacts
```

Redact the segment after those prefixes in every access log, log shipper and analytics
integration that sees a request path, including the one in front of the web app if you host
it yourself — `/join/…` is a web-app route, so an API-only rule will miss it. Replacing the
segment with a fixed placeholder keeps the logs useful. Do the same for anything that
forwards a full URL, such as a `Referer` header sent to a third party.

This is an operator responsibility on a self-hosted deployment. If you cannot redact in the
proxy, shorten retention on those logs and restrict who can read them.
