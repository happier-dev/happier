When the work is done, the next step is usually a pull request. Happier can
publish the branch and open or reuse the request without you switching to a
browser or a terminal.

<Callout type="warn">
  Pull-request actions are Git write operations, so they need
  **Settings → Features → Source control operations**, which is experimental and
  **off by default**.
</Callout>

## Pull requests and merge requests

The Git tab includes a pull request / merge request surface for the current
branch when Happier can detect a hosting provider from the repository remotes.

It can show:

- an existing pull request or merge request for the current branch
- the target repository and branch direction
- whether the branch is ready to open a request
- blocked reasons and the next safe action when a request cannot be opened yet

### Hosting providers are plugins

Source control is not built into the core any more. Two version-control
backends and four hosting providers ship as bundled plugins, and each provider
brings its own authentication, pull-request operations and issue triage:

| Plugin | What it covers |
| --- | --- |
| `scm-git` | Git itself — status, branches, worktrees, checkpoints. |
| `scm-sapling` | Sapling, as an alternative version-control backend. |
| `scm-github` | GitHub and GitHub Enterprise-style remotes. |
| `scm-gitlab` | GitLab, including self-managed instances. |
| `scm-bitbucket` | Bitbucket. |
| `scm-azure-devops` | Azure DevOps Services and Server. |

Practically, that means a provider Happier does not ship can be added the same
way these are — see the [SCM guide](/plugins/guides/scm) in the Plugin SDK.

### Provider support

| Provider | Creating a request | Credential |
| --- | --- | --- |
| GitHub | Connected-account REST first, then authenticated `gh`, then a no-auth compare URL | Connected GitHub account |
| GitLab | Development source: connected-account REST, then a no-auth compare URL | Connected GitLab account; see the version note below |
| Bitbucket | Bitbucket REST API | Connected account: email or username, plus an API token |
| Azure DevOps | Azure DevOps REST API | Connected account: an explicitly configured organization (Services) or collection path (Server), plus a PAT |
| Unknown remotes | Safe unsupported state, no write actions | — |

Two provider-specific details are worth knowing before you plan around them:

- **GitHub Enterprise** remotes are detected, but the connected-account REST
  path is built for github.com. Enterprise and self-hosted remotes generally
  fall through to `gh` or to the compare URL.
- **GitLab development change:** the provider now uses the selected Connected
  Account's REST API binding for merge-request reads and creation, including
  draft requests. The Account's deployment must match the repository host.
  Older daemon/plugin versions use authenticated `glab` instead. This is a
  development-source contract, not a claim that the change has been released;
  availability depends on the installed daemon and plugin version.

If Happier cannot create a request directly, it opens the provider's compare
page so you can finish in the browser.

In development builds, that fallback is reported as input still needed, not as
a created request. An uncertain response after a write requires checking for
the existing request before trying again.

### Default branch guard

If the current branch is the repository's default branch, Happier avoids opening a request directly from that branch when the backend policy requires a feature branch.

Instead, the UI offers the safe next step:

- create a feature branch first, or
- when local commits and capabilities allow it, create the feature branch and continue the pull-request flow as one guided action

This keeps the user in Happier instead of blocking them with an instruction to go to the terminal.

### Dirty and unpublished branches

Happier does not silently create a pull request from a dirty unpublished branch.

If the branch has uncommitted work or no published upstream, commit and publish the branch first. The stacked action can combine supported steps such as commit, push, and create request when the repository state allows it.

### Checkout a PR or MR

The branch menu can checkout a pull request or merge request into the current worktree.

Accepted references include:

- `42`
- `#42`
- a GitHub pull request URL
- a GitLab merge request URL
- `gh pr checkout 42`
- `glab mr checkout 17`
- a branch name when the text is not a URL or numeric request id

Local checkout uses the existing Git protections for dirty worktrees and conflicts. Happier does not discard local changes to make checkout succeed.

### Open a PR or MR in a worktree

You can also open a pull request or merge request in a separate worktree-backed session.

Happier resolves the request through the hosting-provider adapter, prepares the checkout through the existing worktree/source-controller path, and opens a new session at that worktree path.

Use this when:

- you want to review a request without disturbing your current branch
- you want to test someone else's branch in isolation
- you want to keep your current worktree clean while opening an external PR/MR

## Comparison evidence in development

In unreleased 0.3 development source, GitHub comparison retrieval records the
PR's merge-base-to-head diff endpoints separately from its base-tip freshness
witness and pages through changed files independently of the small detail
preview. Missing or truncated patches stay explicitly incomplete; absent patch
text does not prove an empty diff or a binary file. A failed page retains usable
earlier evidence, and a changed base/head requires refresh rather than combining
different versions into one exact comparison.

Reading this evidence does not checkout the PR into your worktree. A PR
comparison can explain or inform a review, but cannot authorize local commit
proposals. When a Session comparison is bound to that PR source, Files and
Walkthrough use the captured PR evidence, not the local pending diff. Missing
patches and stale evidence remain visible. Reopening a pinned comparison reads
the saved evidence rather than silently capturing a newer PR version.

Development source adds **Walk through** to PR details in PRs & Issues. It uses a
linked Session when its workspace is reachable; otherwise it asks for placement
through New Session. Reading uses a reference-only Session, without checking out
the PR or sending a prompt. **Start review** still uses its isolated review
workspace and selects walkthrough output by default. If comparison evidence is
unavailable, resolve that first or turn walkthrough off to request findings only.
Before review starts, the host's existing launch controls select Secret or Team
credentials and check the exact Home and machine, resuming a stopped Session
when supported. Cancelling those controls does not start a review.
These entrances still await end-to-end runtime certification; this is not a
released-availability claim. **Request review** remains the existing human
reviewer flow.
See [Diffs and review](/code/diffs#walk-through-changes) for the implemented reading
workflow and its current limits.
