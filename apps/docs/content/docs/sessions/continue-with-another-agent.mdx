---
title: Continue with another Agent
description: Switch the Agent running a session without leaving the session — same id, same transcript, a transition divider in place of a fork.
---

Sometimes the Agent you started with is not the one you want to finish with. Claude has mapped the
problem and you want Codex to write the patch; Codex is stuck and you want a second opinion on the
same conversation.

**Continue with another Agent** replaces the Agent running a session while the session itself stays
put. The session id, the URL, the list row, the transcript, sharing and participants are all
unchanged. A divider is written into the transcript where the change happened, and the conversation
carries on below it.

This is different from:

- [Session forking & replay](/sessions/session-forking), which branches into a **new** session
- [Session handoff](/sessions/session-handoff), which moves the same session to another **machine**
- [Agent and model selection](/agents/model-and-engine-selection), which chooses the Agent for a
  **new** session and the model for a running one

## Development status

This capability exists in the current development source and is **not yet available in released
Happier builds**. It has not passed an integrated live gate, so treat the behavior below as the
current development contract rather than as shipped behavior. Availability, copy, and failure
handling can still change.

## Selecting is arming

There is no Apply button and no confirmation step. Opening the Agent picker in a running session and
choosing another Agent arms that choice; nothing is sent, nothing is stopped, and the session keeps
running exactly as it was.

Two things then tell you the session is armed:

- the picker's detail pane is headed **Continue with Codex** and states the terms plainly — *"Your
  recent conversation carries over as text; images and files don't. Nothing is sent until your next
  message."* Screen readers hear the rows as *"Claude. Running this Session."* and *"Codex. Selected
  for your next message."*, and selecting announces *"Codex selected for the next message. Nothing
  has been sent."*
- the composer's send button changes from **Send** to **Continue with Codex**, carrying the target
  Agent's icon

The armed choice is part of the session draft, not transient screen state. Navigate away, come back,
or reload the page and both your draft text and the armed Agent are still there. Selecting the
running Agent's own row clears the arm and the button returns to **Send**.

Happier re-validates a restored arm rather than trusting it: if the Agent is no longer offered for
that session, is no longer eligible, or the session has since changed Agents underneath you, the arm
is dropped instead of firing at the wrong target.

## What happens when you send

The switch happens on the next message, as one operation:

1. Happier confirms the current Agent has actually stopped, or confirms that a cold inactive Session
   is already stopped. If it cannot confirm that, nothing on the target side is started.
2. The session's current Agent is changed to the one you armed.
3. A transition divider is appended to the transcript.
4. Your message is taken into custody and delivered to the new Agent, exactly once.

Because your message is the trigger, a switch always has something to do. You never end up with a
freshly started Agent sitting idle.

### What carries over and what resets

The session's identity and history carry over: id, title, transcript, sharing, participants, unread
state, archive and pin state, project and working directory, past turns and usage. Your permission
mode carries too — it is a Happier safety intent for the session, not an Agent setting, so switching
Agents never quietly loosens it.

What the old Agent owned does not carry. Its slash commands, tools, capabilities, mode and config
catalogs, model selection, work state, activity and thinking state are cleared, and the new Agent
republishes its own. The old Agent's task and to-do list is not simply discarded, though: it is
summarized into the recap below as plain text — each item's title and status — so the new Agent
knows what was under way. It arrives as context to read, not as a live checklist the new Agent
inherits.

Archive state is deliberately untouched: it is your intent, and stopping the old Agent leaves the
session inactive and resumable rather than archived.

The new Agent is given a bounded recap of the conversation so far rather than the raw transcript. It
is the same replay-seed machinery [session forking](/sessions/session-forking) uses, in its
recent-messages form — a switch never runs a model-generated summary first, because the old Agent is
already stopped and you are waiting.

**The recap is text.** Images and files attached earlier in the session do not carry over to the new
Agent, and the picker says so before you commit. They remain in the transcript; the new Agent simply
does not receive them as context.

The recap has one true total budget, taken from the machine running the session
(`HAPPIER_REPLAY_MAX_SEED_CHARS`, default `120000`). The per-fork **max seed characters** setting does
not apply here. Everything counts against that one number, including the session-reference block
Happier appends, and when the conversation does not fit, the omission is marked rather than silently
dropped. The recap is delivered with your first message and retires only once the Agent has actually
accepted it, so a rejected or cancelled first turn does not lose the context.

## The transition divider

The change is recorded in the transcript as a separator row reading **"Continued this Session from
Claude to Codex"**, in the same visual family as the fork-lineage divider — not as a generic
informational message.

The divider is deliberately quiet. It does not mark the session unread, does not move a badge, does
not count as meaningful activity, and does not send a notification, for you or for anyone you share
the session with. That stays true after a reload, because attention is re-derived from the transcript
on every read rather than stamped once when the row is written.

## How older messages are labelled

After a switch, the transcript contains work from more than one Agent. Happier labels a historical
message by the dividers around it: messages after a divider belong to the Agent named on its right,
messages before the first divider belong to the Agent named on its left.

This is an approximation with one known edge. If the outgoing Agent's last output is accepted just
after the divider is written, that row lands on the new Agent's side of the boundary and is labelled
with the new Agent. The message is still there and still visible; only its Agent label is affected.
Where no divider can place a row, Happier shows the session's live Agent instead of guessing.

## Returning to an Agent you used earlier

Switching back is an ordinary switch: arm the earlier Agent and send.

When Happier still holds a machine-local note of the earlier Agent's own session, it resumes that
native session instead of starting a fresh one, and hands it only what happened while it was away.
That note is written on the machine that ran the session, is never uploaded, and is only usable
there — a session on one machine cannot be resumed on another. Happier does not pre-check whether the
session is still alive. The cutoff advances only when the provider accepts the requested native
identity, including when no replay seed is needed; prompt delivery or seed retirement alone is not
that proof. If the requested identity fails, Happier leaves the earlier cutoff untouched and does not
offer that failed identity again as a valid native return. Without a usable note, the Agent starts
fresh with the same carried-over context as any other switch.

## When a switch does not go through

Failures surface in the composer banner, not in a modal you dismiss and lose. There are deliberately
no separate *Check status*, *Resume source*, or *Resume target* flows to reason about — Happier
reconciles against the canonical Session and input facts, then shows you one accurate line.

- **Nothing happened.** The old Agent is still running and your draft is untouched. Sending again is
  the retry; Happier reuses the same message identity so a successful retry cannot duplicate your
  message.
- **The old Agent stopped but nothing else changed.** Same as above: the session is still on the old
  Agent, and sending again retries the whole switch.
- **The session moved but the target did not start.** Your exact message is already queued and will
  be delivered when the Session resumes; do not send it again. The banner offers **Resume session**
  only when the Session is already the target and has no running Agent.
- **Happier could not confirm the outcome.** Sending is blocked for one reconciliation pass while
  Happier re-reads the session, so you cannot send the same message twice into an unknown state.

Some switches are refused before anything is attempted, and Happier says which: the current Agent is
still working, the target is not available to the CLI performing the operation, the session changed while you were
choosing, you do not have permission, or the session already runs that Agent. Each of these ends with
*"Nothing was sent."*

A switch is also refused when the message already has another destination — a voice adapter or an
execution run is not this session's Agent, so an armed switch cannot ride along on it — and when no
reachable CLI can perform the operation. In both cases the arm is kept rather than
silently dropped, because you chose it deliberately.

## Carrying a conversation into a new session instead

If you want a branch rather than a replacement, the fork flow now offers a third choice next to
native fork and replay: **Configure a new session**, which opens the normal new-session screen
pre-loaded with this conversation as removable source context, so you can change Agent, model,
machine, and folder before starting. See [Session forking & replay](/sessions/session-forking).

## Turning it off

The capability is a server feature and is **enabled by default**. Self-hosted and company-managed
servers can disable it for every connected client:

```bash
HAPPIER_FEATURE_SESSIONS_AGENT_SWITCHING__ENABLED=0
```

Restart the server after changing it — the feature registry is resolved at process start.

When it is disabled, the in-session Agent picker shows no target Agents at all, so no arm can be
formed and no switch can be attempted, and the **Configure a new session** fork choice is hidden. The
setting is scoped to the server that owns the session, so clients connected to several servers can
see it available on one and not another.

The server also rejects direct switch requests while disabled; the picker is not the enforcement
boundary.

There is no per-user toggle for this in client settings.
