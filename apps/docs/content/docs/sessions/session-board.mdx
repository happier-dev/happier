---
title: Session Board and Companion
description: Keep notes, interactive views and plugin widgets with a session — shared with everyone who can read it — and pin the ones you want beside chat.
---

A transcript is a good record and a poor dashboard. The **Board** is where a
session keeps the things you want to look at rather than scroll back to: notes,
interactive views, widgets from installed plugins. Its contents are shared with
everyone who can read the session. The **Companion** is the personal half —
whatever you want pinned beside chat, on this device only.

> **Availability:** The Board and Companion are in the current unreleased 0.3 checkout. Stable 0.2 has no Board — check the version of the server binary you are running.

## Availability

The Board is a per-Home capability. A self-hosted Home offers it unless its
operator sets `HAPPIER_FEATURE_SESSIONS_BOARD__ENABLED` to a false value. It
also needs a Home that supports the current session-records contract, so an older
Home will not offer it. Each session uses its own Home's decision, so one Home
having it does not mean another does.

## What is shared and what is yours

A session's Board items, its Board views, their order and their semantic sizes
are shared session state: everyone who can read the session can read them. Which
Board view you have open, and what you keep in your Companion, are local to your
viewer and this device. Opening either one does not follow the session, mark it
read, or create an unseen badge.

## Where the Board appears

Where it shows up depends on the space you have. On a wide window the Board is a
**Board** tab in Details beside chat, with a compact **Board** tab in the right
sidebar that offers **Open in Details** rather than acting as a second editor. On a
phone it is one destination in the session cockpit. The session's overflow menu
reaches it everywhere the Home has the feature on, whether or not the Board has
content yet; a dedicated header button appears once the session has something on
its Board. There is no unread count or badge for Board activity.

## Adding and arranging items

Inside the Board, a quiet **Board views** strip appears once a session has more than
the default **Overview** view, and stays hidden until then. Adding offers **Note**,
**Interactive view**, and **From plugins…**. Items keep one shared order and a
semantic size — **Compact** through **Full width**, and **Fit content** or a fixed
height — rather than free coordinates, so the same Board linearizes predictably on a
phone. An empty Board offers **Ask the agent**, which only puts an editable
suggestion in the composer; it never sends on your behalf.

## Access and encryption

Board access follows the Session's existing access and encryption model. Reading
requires current transcript access; adding, editing, organizing, or removing an
item requires Session-record edit access. Plain Sessions store explicit plain
record envelopes. E2EE Sessions use the Session's existing data key and remain
locked when that key is unavailable; Happier never interprets failed E2EE data
as plaintext.

## Configured widgets in development

The 0.3 development **Add** surface supports independently configured copies.
Select a widget in its list to see it beside the list: its inputs first, then
its live body at the size you choose, then **Add** (⌘↵). A fully bound widget
needs no inputs; select it and add. Nothing reads until you select a widget,
and a refused or approval-pending Add is reported in place. **Edit inputs** changes
that copy. A widget can follow context or pin a different Session, whose own
access and machine serve the read. An unavailable or revoked pin asks for
repair rather than switching to the Session you are viewing.

Each widget offers the sizes its definition declares for the Board. Choosing a
size sets width and height intent through the Board's existing layout; a narrow
window reflows the item while retaining that choice. The Companion stays
linear. Plugin authors can define these choices in their
[widget size declaration](/plugins/ui#declare-useful-widget-sizes).

Reusable Account definitions appear under **Your widgets**. Editing a
definition affects its references; **Duplicate** makes independent content.
**Save as your widget** copies admitted Session content into that library and
keeps the original Board item. Adding a private definition to a shared Board
copies the admitted definition into shared content rather than granting access
to its private Account document. This publication uses the shared Board's
approval policy; pending approval does not mean the item has been saved.

Credentialed shared widgets use each viewer's own existing Connected Account
purpose selection, qualified to the declared Resource consumer. A missing
connection gives that viewer a Connect state. There is no per-copy viewer
override; the editor's connection is never a substitute for the viewer's
selection. Pinned Connected Account references are allowed only in personal
widgets, not shared Board content. Changing the existing purpose selection can
affect other viewer bindings using that same purpose; it is not an instance-only
connection setting.

**Post a snapshot** previews and confirms fixed output with its as-of time and
provenance. It publishes exactly that approved inert preview as a normal shared
Board item, with no live Resource, credential binding or executable control and
no new read after approval. Later source or definition changes do not change
the snapshot. The normal Session audience, editor rights and approval policy
still apply.

Refresh, a sleeping machine or a failed read can retain authorized last-known
content with a freshness notice. Losing the read's identity or access removes
private prior output. These are development-source behaviors; package and
loaded-platform validation are still being completed.

## When the agent puts something on the Board

When an agent creates or updates a Board item through a Board Action, the
transcript row for that call shows the resulting widget in place, with an **Open
Board** action that opens it on the Board. That inline card is a mirror of the
shared item, not a second copy: it reads the same record and shows the same
loading, encrypted, unreadable, removed, and unavailable states. Interactive
content runs in one placement at a time, so the inline card stays a preview while
the Board, Details, or your Companion is running it.

Actions can ask Happier to change the Board, but confirmation and authorization
remain separate. Requiring or skipping a confirmation never supplies missing
Session access, enables the Board, or grants a renderer, plugin, Resource, or
Action more authority. Removing an installed widget removes the shared Board
item and its placements; it does not uninstall the plugin.

## Conflicts and offline editing

If another editor changes the same item or layout, Happier reports a conflict and
refreshes the shared state for review instead of silently overwriting it. While
offline, the last-known Board can remain visible, but editing pauses. If a request
loses its result and Happier cannot tell whether it committed, refresh the Board
before retrying; it does not guess or submit the change again automatically.
Viewer-layout requests from an agent follow the same rule: they can open or focus
content only for the currently bound viewer, keep the person's layout reversible,
and do not change the shared Board.

## The Companion

The Companion is the personal side of this. **Add to companion** keeps a Board
widget — or the first-party session summary, with waiting approvals, running
workflows, changed files and context use — beside chat, on whichever edge you
choose. It is a preference on this device only: adding, removing, reordering or
collapsing it changes nothing for anyone else, and **Remove from companion** does not
touch the shared Board. When the window is narrow, a pane is open, text is large, or
the keyboard is up, the Companion collapses to a header affordance rather than
covering chat.

## Plugin widgets and authored HTML

Installed first-party and external plugins are trusted installed code and use
the same public Plugin SDK path under equivalent grants. HTML authored directly
into a Board item is different: it has no plugin identity or ambient plugin
authority, receives only the caller-hosted method ceiling, and still passes each
Resource and Action's normal checks. Rendering it uses a per-platform frame on
web, desktop, iOS and Android; where a renderer is unavailable, the item is kept
and offered with a recovery action rather than deleted or rewritten.

Plugin authors can declare embedded Session content with
`container: 'widget'` and `target: { kind: 'session' }`; see [Embedded Session widgets](/plugins/ui#embedded-session-widgets).
