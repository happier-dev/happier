The **Session** settings screen controls how Happier sessions behave in the app.

Recent versions split the advanced controls into focused sub-screens so the root page stays easier to scan:

- **Permissions**
- **Session handoff**
- **Transcript**
- **Tool Rendering**

The root session settings screen keeps the most common session-wide controls in one place and links to the more detailed sections when needed.

## Where to find it

Open:

1. **Settings**
2. **Session**

From there, use the dedicated entries to open:

- **Permissions**
- **Session handoff**
- **Transcript**
- **Tool Rendering**

## What stays on the main Session screen

The root Session screen keeps the controls that affect how you work day to day:

- **Session list** behavior such as density, grouping, hidden inactive sessions, and tags
- **New session shortcut** behavior such as whether project shortcuts reuse the newest project session selections
- **Mobile session layout** for choosing the phone session cockpit or the classic focused-screen layout
- **Message sending** behavior such as interrupt vs queue/pending strategies
- **Composer input behavior** such as **Enter to Send**, action-bar layout, chip density, and context-size display
- **Message history** scope as a dropdown
- **Replay / resume** defaults
- **Session handoff** defaults
- **Terminal connect** options
- **Attach / local-control launch defaults** such as tmux and Windows remote session mode

This keeps the root screen focused on common workflow choices instead of mixing them with large advanced settings groups.

## Session Instructions (development integration)

Development source lets an ordinary Session or Bot select a Prompt Library
document as its Instructions. The selection changes only its reserved Session
context entry, preserving other context, Roles and Notes. Detaching leaves the
document in the library. Empty instructions are valid; a deleted required document
needs repair or detachment before another preparation can proceed.

Supported coding and bound Voice preparations read the current document again.
Changes take effect from the next supported preparation, while an already-prepared
turn or Voice attempt keeps its instructions. Temporary read failures keep new
preparation pending for retry. This is development integration: the Work editor
and all-carrier Voice delivery are not released workflows.

Sharing a Session does not share its Instructions document. A separate document
grant permits its covered content, while the owner's Session selection and Voice
preference stay private. Document edits use ordinary Actions approval and the
Action's exact surface setting across Sessions, rather than a Bot-specific grant.
See [Prompts and skills](/extending/prompts-and-skills) and
[Inbox and approvals](/sessions/inbox-and-approvals).

## Memory upkeep for new Bots (development integration)

The development Account preference **Memory upkeep for new Bots** defaults on.
Normal Bot creation uses it once to install the weekly memory-upkeep habit,
independently of whether the Session uses memory. The habit is visible in
**Triggers** and can be paused there. Changing the preference does not install,
remove or change habits on existing Bots, including Sessions later promoted to
Bots or resumed Bots.

The preference uses the existing Account-settings Actions. Its visual settings
row is still being integrated; this is not a claim of released availability.

## Per-session Voice preference (development integration)

Development source adds a private voice preference for one session, separate
from the account-wide settings described above. Unset follows the account's voice
provider. A selected voice changes only that provider's declared voice choice and
keeps credentials, model and speed inherited. Missing, unsupported or
other-provider choices require repair; they do not silently select a new provider.
This preference stays owner-private when the Session is shared, even if an
associated instructions document is separately shared.
Saving a choice does not start Voice or rename the voice already speaking.
Voice controls retain their normal human approval and microphone-permission flow.

The Work picker and bound-instruction carriers are still being integrated, so this
is not released availability or all-carrier support. [Voice](/voice) explains the
distinction between an exact session target and global mode.

## Per-session tool-call visibility (development)

Development source supports a human-owned tool-call visibility preference for
one Session. Show or hide tool calls for that Session, or reset the preference
to follow its default. This changes transcript presentation, not which tools
the Agent can use.

Agents and MCP callers can read settings, but cannot change this visibility
preference. The Session preference is development integration, not a claim of
released availability.

## Confidential credential requests (development)

Confidential credential requests are handled in the existing Session/Inbox request
detail, not in Session settings or chat. The 0.3 development flow offers masked
one-time entry and explicit, off-by-default Remember, with separate entry, submit,
and save outcomes. See [confidential browser entry](/agents/profiles#confidential-browser-entry-development)
for its target review and current limits.

## Session handoff settings

The dedicated **Session handoff** screen controls the defaults used when you move a session between machines.

It includes:

- **Transfer workspace**
- **Workspace conflict policy**
- **Ignored files**
- **Direct session target mode**

### Workspace transfer defaults

By default, Happier keeps workspace transfer **off**.

You can change the default behavior to:

- transfer the workspace by default
- keep the target workspace unchanged by default

The handoff modal still lets you override this per handoff.

### Conflict policy

The default conflict policy can be:

- **Create sibling copy**
- **Replace existing path**

This controls what should happen if the destination path already exists.

### Ignored files

The default ignored-file mode can be:

- **Exclude ignored files**
- **Include selected ignored files**

If you choose **Include selected ignored files**, you can set comma-separated include globs such as:

- `dist/**`
- `.env.local`

### Direct session target mode

This applies only when the source session is currently **Direct**.

You can choose:

- **Keep direct**
- **Convert to Happier**

That setting becomes the default choice in the handoff modal, but you can still override it case by case.

For the full workflow, see [Session handoff](/sessions/session-handoff).

## Attach and local-control settings

The root Session screen also contains the defaults that control how app-started sessions can later be continued from a terminal.

### Terminal host for new sessions

Choose whether supported app-started sessions use no terminal host, `tmux`, zellij, or Herdr. A per-machine override can replace the account default. Herdr and automatic presentation of supported server-backed sessions are currently development-build features.

In development builds, machine details shows **Override account default**. With it off,
new sessions inherit the account choice; the effective host remains visible. Turning it
on selects a host for that machine only. It does not disable the account preference.

When `tmux` is selected, its session name, isolated-server option, and temporary directory
remain editable account defaults that a machine override can replace.

New sessions with a meaningful terminal surface start in the selected host. This includes server-backed Codex and OpenCode sessions: their native TUI starts against the same provider session Happier is driving. Headless runtimes such as ACP stay headless and do not receive an invented terminal UI.

Resuming an inactive session from the app or taking over an external session uses that account’s current terminal preferences, including overrides for the target machine. Changing the preference does not move a session that is already running to another host.

Use a terminal host when you want sessions to appear in that host immediately and remain locally attachable. Select **None** when you want supported sessions to stay in their normal background/server-backed presentation until you attach. Herdr requires a supported local Herdr installation and is unavailable as an attach host on native Windows.

In development builds, a missing supported Herdr/Zellij installation or an older running
Herdr server produces a terminal-host setup message rather than an agent error. Install
or update the host and restart its server on the selected machine, or choose another
terminal host. Your session draft is kept while you correct the setup.

### Windows remote session mode

For Windows machines, the Session screen also exposes a **default Windows remote session mode**.

The available modes are:

- **Hidden** — keep the session in the background for remote app usage
- **Windows Terminal** — start the session in a dedicated Windows Terminal host so you can later continue there locally
- **Console** — start the session in a visible console host

This is the global default. You can still override it:

- per machine from the machine details screen
- per session from the new-session flow when the selected machine is Windows

Precedence is:

1. per-session choice
2. machine override
3. global Session setting

For the full workflow, see [Attach to a running session](/sessions/attach-to-session).

## Permissions screen

The dedicated **Permissions** screen separates two different concerns:

### 1. Default permissions

This section shows one row per enabled backend choice and lets you choose the default permission mode for new sessions.

Important details:

- the list is **dynamic**
- it comes from the resolved backend catalog
- built-in backends and configured **Custom ACP** backends can both appear here
- if a backend choice is not enabled for your account/build/settings, it should not appear

### 2. Apply permission changes

This is now a separate dropdown group.

It controls **when** a permission change should take effect for a running session:

- **Immediate**
- **Next prompt**

Use **Immediate** when you want the running session to react right away. Use **Next prompt** when you want the change to arm for the next turn instead of changing the current one mid-flight.

The same screen can also show related permission/session-default controls such as where prompts appear and transcript-storage defaults for backend choices when those features are available.

Full guide: [Permissions](/sessions/permissions)

## Watching a computer in development builds

Computer watching is a **0.3 development-build feature**. It uses the session's
machine, including an enrolled graphical guest, and the same viewer on desktop
and phone. A machine must be online, have a desktop, and have its native screen
driver ready. Opening the viewer does not start or wake a managed machine.

**Watch** opens the viewer. On a desktop it floats beside the conversation,
above the composer; the reading column moves aside so nothing is covered, and
the viewer keeps clear of the Voice orb or island and the pet. Who is acting
(the agent, or you after **Take control**) shows below the picture. While you
only watch, drag the picture itself to move the viewer and double-click it to
expand; once you take control, the picture takes your clicks and keys and the
viewer moves by its controls or the corner grip. Snap it to a corner with the
arrow keys or its menu, and resize it from the grip. **Expand view** covers the
conversation on purpose; **Restore view**, Escape or Back returns it to its
corner. **Dock view** puts the same picture in the Session's pane. Pressing the
current **Computer** source opens the window and display picker beside it; a
watched browser's Back, Forward and Reload are in the viewer's menu. On a phone
the viewer sits at the top of the conversation with its controls always
visible. **Close view** only closes the
viewer: the session, the machine and any shared window keep running, and the
viewer stays closed until you open it again. Stopping sharing is a separate
choice in the viewer's menu.

Choose an actual window or display from that machine's source picker. An empty
window list does not authorize sharing a display. Sharing a whole display exposes
everything visible there, including other apps and notifications; review that
consequence when choosing what to share. Viewing and mouse/keyboard use are
separate choices, subject to current machine access and your Actions approval
preferences.

Linux X11 window and primary-display capture are supported by the development
native driver. The macOS implementation uses the same source and control path;
physical macOS permission and input certification remains pending. The current
driver exposes the primary display, not an independently selectable list of
physical monitors. Windows and Wayland computer capture remain unsupported.

On a Mac, **Screen Recording** permits watching, while **Accessibility** permits
mouse and keyboard use. Grant them on the target Mac, even when watching from a
phone. Opening privacy settings only opens the relevant OS page: grant the
permission yourself, return to Happier, and check the sources again. A fresh
permission check must confirm the grant. You can still choose viewing only when
capture is allowed and input is denied.
Viewing-only access limits the Agent, not your own controls: you can still use the
shared computer yourself when its OS input permission is granted.

If a window closes, a display becomes unavailable, or access is removed, choose
an available source again. A changed screen size or scale needs a fresh capture
before input. If Happier cannot confirm the last input or that the Agent stopped,
check the screen before continuing; retrying must not repeat that physical input.
A missing screen driver needs setup on the target machine; a headless machine
may still provide its terminal or browser. Native confidential credential entry
is currently unavailable because the driver cannot verify the exact focused
field; ordinary keyboard entry is not a substitute for secure fill.

## New session shortcut settings

The root **Session** settings screen includes a **New session modal** group.

This group contains shortcut settings for project-based session creation.

The **Remember last project session selections** setting controls what happens when you use the project **+** action in the session list.

When it is on, Happier seeds the new-session screen from the newest session in that project group. This reuses selections such as machine, folder, engine, profile, permissions, model, session mode, MCP selection, connected services, and provider config options.

When it is off, the project **+** action only preselects the project machine and folder. The rest of the new-session screen follows the normal draft/default behavior.

Contextual shortcuts preserve typed draft content, such as an unsent prompt, while replacing launch selections with the shortcut source. This keeps your written intent without carrying stale choices from another project.

Full guide: [New session shortcuts](/sessions/new-session-shortcuts)

## Transcript screen

The **Transcript** screen controls how session conversations are presented:

- transcript layout
- thinking display
- tool chrome mode
- tool grouping / collapsed preview behavior
- motion / scrolling defaults
- code and diff presentation

This is a presentation layer. It does not change provider behavior or tool permissions.

Some transcript-related defaults, such as transcript-storage defaults for new sessions, are still backend-aware. That means a built-in backend and a configured ACP backend can have different default behavior.

## Tool Rendering screen

The **Tool Rendering** screen controls how tool calls appear in the transcript.

It contains:

- default tool-detail behavior
- per-tool overrides
- separate overrides for the expanded/full view

This is useful when you want different defaults for tools like:

- `Bash`
- `Read`
- `Edit`
- `Diff`
- `WebSearch`

For example, you might keep most tools compact in the timeline but still expand `Diff` or `Patch` more aggressively when opened.

Related guide: [Tool timeline & normalization](/organize/tool-timeline)

## Composer input behavior

Session settings also includes controls for how the message composer behaves and how its controls are arranged.

These settings change the app input experience. They do not change provider permissions, model behavior, or transcript storage.

### Enter to Send

**Enter to Send** controls what the Return/Enter key does in the composer.

When it is off:

- pressing Enter inserts a new line in the composer
- use the send button to send the message

When it is on:

- on web, pressing Enter sends the message
- on web, pressing Shift+Enter inserts a new line
- on iOS and iPadOS with a physical keyboard, pressing Enter sends the message
- on iOS and iPadOS with a physical keyboard, pressing Shift+Enter still inserts a new line

Happier only sends when the composer has sendable content. That can be typed text, attached files, or included review-comment context. Empty composers and disabled send states are ignored.

Use **Enter to Send** when you prefer a chat-style workflow. Leave it off when you often write longer prompts, code blocks, logs, or multi-line instructions.

The web and native app settings are stored separately, so you can use Enter-to-send on one platform and keep Enter-for-new-line on another.

On phones and tablets without a physical keyboard, the visible send button remains the clearest way to send a prompt.

## Mobile session layout

**Mobile session layout** controls how phone-sized session screens are organized.

The setting is synced with your account and defaults to **Cockpit**.

### Cockpit

Cockpit is the default phone layout.

It shows a bottom session tab bar with the session’s main work surfaces:

- the current agent chat, labeled by backend such as **Claude**, **Codex**, or **OpenCode**
- **Files**
- **Git**
- **Tabs** for open file previews, editors, Review, commit details, stash details, and other detail views
- **Terminal** when the embedded terminal is enabled and available as a session tab

Use Cockpit when you want mobile sessions to behave like a compact workspace instead of a single long chat screen.

### Classic

Classic keeps the older focused-screen layout for phone-sized sessions.

Use Classic if you prefer opening Files, Git, Terminal, and details as separate focused routes instead of switching through the cockpit tab bar.

You can change the setting at any time from **Settings → Session → Mobile session layout**.

### Input layout

The input layout controls decide how composer action chips are shown.

The layout can:

- wrap chips across rows when there is enough room
- use horizontally scrollable chip rows on narrower layouts
- collapse controls into the action menu when you want the most compact composer

Primary controls and secondary controls stay separated in wrap and scroll layouts. In collapsed layout, those controls move into the action menu.

Chip density controls whether chips prefer labels, icons, or automatic label hiding.

### Message history

Message history is now a dropdown instead of an inline toggle pair.

The options let you choose whether composer history is kept:

- per session, or
- globally

This makes the current selection easier to understand at a glance.

## Why this structure changed

The goal of the split is simple:

- keep the main Session page fast to scan
- move high-detail controls into dedicated screens
- make advanced settings easier to reason about
- preserve the same underlying logic instead of creating separate implementations

If you are looking for a setting and no longer see it inline on the root Session screen, it most likely moved into one of the dedicated sub-screens rather than being removed.
