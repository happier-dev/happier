The new-session flow is the place where you decide the session context before the first message is sent.

That includes:

- which machine the session should run on
- which folder or checkout it should use
- whether you want to attach local files before the first message
- whether you want to resume an existing provider session by **Resume ID**
- which session-only controls should apply, such as **MCP**, model/engine, profile, and permission-related choices

The important product rule is simple:

- large pickers and browsers open **inside the current new-session flow**
- smaller chip controls stay close to the composer on desktop and expand into wider touch-friendly pickers on phones and mobile web
- opening those controls does **not** mean your new session was canceled

The new-session composer follows the same input rules as the normal session composer. If **Enter to Send** is enabled in [Session settings](/sessions/session-settings), Enter starts the session when the first message is ready to send. Shift+Enter still inserts a new line on web and on iOS/iPadOS with a physical keyboard.

## What the new-session flow controls

Think of session start as three layers:

### 1. Where the session runs

You choose:

- the **machine**
- the **folder / checkout / path**

That path becomes the main project context for the session.

It affects things such as:

- the default workspace the agent sees
- path-sensitive setup such as project review comments
- workspace-relative upload paths when you use attachments

If you already know the path, you can type it directly.

If not, use the **folder browser** from the path field.

### 2. What extra context goes into the first message

Before the session starts, you can also add context such as:

- **attachments**
- **review comments** when they exist for the selected path
- a **Resume ID** if you want the new Happier session to reopen an existing provider session

### 3. How this one session should behave

The composer chips let you adjust session-specific controls such as:

- **MCP**
- **model / engine**
- **profile**
- **permissions / modes** when supported by the selected backend

These controls are contextual:

- they reflect the machine, backend, and path you already selected
- changes apply to the session you are about to start
- they do not silently rewrite your saved global defaults unless you explicitly edit those defaults in Settings

## Choosing the machine and folder

The most common start flow is:

1. choose the machine
2. confirm or change the folder
3. review any session-only chips such as MCP or Resume ID
4. send the first message

### Typing a path vs browsing

Use manual entry when:

- you already know the exact absolute path
- you want to paste it quickly

Use the folder browser when:

- you want to inspect the machine’s folders first
- you are not sure of the exact path
- you want to confirm the folder visually before starting

The folder browser opens as a dedicated in-place browser surface, not as a separate “leave this flow and come back later” workflow.

That matters especially on desktop and mobile web, because it keeps the new-session context visible and reduces the feeling that the whole session setup disappeared.

### What the folder browser is scoped to

The browser always uses the machine you already selected.

If the current new-session flow is already running inside another modal or contained sheet, the folder browser still opens inside that same active flow.

## Attachments before the first message

You can add attachments directly in the new-session composer before the session exists.

This is useful for:

- screenshots
- logs
- PDFs or docs
- images you want the agent to inspect in the very first prompt

Important behavior:

- attachments stay as **draft state** while you keep working in the same new-session flow
- you can still open other setup controls, then come back and send
- opening image previews does not kick you out of the current new-session flow

For the full attachment model, see [Attachments & image previews](/apps/attachments).

## Resume an existing provider session with Resume ID

If the selected backend supports it, the Resume ID field can show a **browse** button.

Use that when:

- you already have a provider session outside Happier
- you want to start a **new Happier session** that reconnects to that provider session

You can either:

- paste the Resume ID manually, or
- browse existing provider sessions and pick one

The Resume ID browser follows the same design as the path browser:

- it opens as an in-place browser surface
- it keeps you inside the current new-session flow
- picking a session fills the Resume ID field and returns you to session start

The browser is intentionally locked to the current session context:

- selected machine
- selected provider/backend
- selected auth/source context when the provider supports more than one source

That prevents choosing a session that belongs to the wrong machine, wrong provider, or wrong provider home.

For the full Resume ID workflow, see [Resume an Agent session (Resume ID)](/sessions/resume-provider-sessions).

## MCP and the other session chips

The chips under the composer are session-start controls.

Some are broad defaults you may already know from Settings. In the new-session flow, they become **context-aware overrides** for the session you are about to start.

### MCP

The **MCP** chip shows the current MCP count for the selected context.

Use it when you want to:

- confirm which Happier-managed MCP servers are included by default
- remove one default server for this session only
- add another Happier-managed MCP server for this session only
- see provider-native detected MCP entries for the current backend/context

Changing the MCP chip affects this upcoming session, not every future session.

For the full MCP model, see [MCP servers](/extending/mcp-servers).

### Other chips

Other chips such as model/engine, profile, and permission-related controls follow the same general rule:

- they stay close to the composer
- they reflect the current backend and machine context
- they act as session-start choices, not global settings edits

The model/engine picker can also show live provider model lists, static provider catalogs, model-specific controls, and favorite model shortcuts.

For the full guide, see [Model and engine selection](/agents/model-and-engine-selection).

### Starting from a shortcut

Some entry points open the same new-session flow with contextual launch selections already filled in.

The project **+** action can seed the flow from the newest session in that project, and **New session with same setup** on Session info can seed it from the exact session you are viewing.

Those shortcuts keep draft prompt content, then replace launch selections such as machine, folder, backend, model, permissions, mode, MCP, connected services, and provider options with the shortcut source.

For the full guide, see [New session shortcuts](/sessions/new-session-shortcuts).

### Composer action chips

The composer also includes action chips for context that can become part of the first turn:

- **Attachments** bring local files from your device into the new session
- **Link file** lets you pick files from the selected machine + path and inserts workspace-relative links where possible
- **Review comments** appears when the selected machine + path has saved review-comment drafts

On wider screens, these actions can stay visible as chips near the composer. On narrower screens, chip rows can scroll horizontally or collapse into the action menu while keeping the text box available.

Review comments are included by default when matching drafts exist. Turning the **Review comments** chip off detaches them from this new session without deleting the saved drafts.

## Desktop vs mobile behavior

Happier keeps the same overall workflow across desktop, web, and mobile, but the presentation adapts to the screen.

### Desktop and large screens

On larger layouts:

- the new-session flow stays more compact
- smaller controls open as anchored pickers near the composer
- larger browsers such as folder selection or Resume ID browsing open as dedicated modal surfaces

### Phones and mobile web

On smaller layouts, the flow becomes more touch-friendly:

- the composer stays bottom-anchored while you draft the first message
- when the software keyboard opens on mobile web, the composer lifts so it stays usable
- larger browsers use wider, roomier modal surfaces
- chip pickers become wider so they are easier to scan and tap

In practice, that means the mobile layout should still feel like one continuous start flow rather than a chain of fragile nested popovers.

## Common session-start patterns

### Start from a project folder with local files

Use this when you want the agent to start with the exact project context:

1. choose the machine
2. choose the folder or worktree
3. attach screenshots, logs, or documents if needed
4. send the first message

This is the best fit for repo work, debugging, or review follow-up.

### Reopen an existing provider session inside a new Happier session

Use this when the provider session already exists outside Happier:

1. choose the machine and backend
2. open **Resume ID**
3. browse existing sessions or paste the id manually
4. start the session

### Temporarily add or remove MCP tools for one session

Use this when the next task needs a slightly different tools surface:

1. open the **MCP** chip
2. include or exclude the relevant servers
3. start the session

Your saved MCP defaults stay unchanged.

## Important things to know

- Opening a folder browser, Resume ID browser, or image preview is still part of the same new-session flow.
- Session-start controls are contextual. Changing machine, path, backend, or auth can change what other controls show.
- Draft attachments are temporary until you send the first message.
- MCP chip changes are session-only overrides unless you separately edit MCP settings.
- Resume ID browsing is intentionally scoped so the chosen session can actually be resumed in the current context.
