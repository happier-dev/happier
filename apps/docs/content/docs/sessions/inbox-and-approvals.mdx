Happier has a **global Inbox**.

Inbox is the place to answer one question:

> What needs my attention right now?

It is not a replacement for the Sessions tab. The Sessions tab is where you browse and organize sessions. Inbox is where Happier gathers the things that currently need review, action, or follow-up.

## What appears in Inbox

Inbox can surface:

- **Approval requests** for higher-level actions that require review before they run
- **Session requests** that need a decision now, including permission requests and user-action requests
- **Unread sessions** so you can quickly find sessions that changed since you last viewed them
- **Friend requests** and outgoing friend requests that are still pending
- **Activity/feed updates**
- important banners such as app updates or recovery reminders when relevant

## What does not appear in Inbox

Two distinctions matter:

### Shared sessions are not listed in Inbox just because they are shared

Shared sessions live in the **Sessions** tab. Released 0.2 shows them in a
dedicated **Shared sessions** subgroup within the normal **Active** and
**Inactive** sections. In the 0.3 development channel there is no separate
ownership group: shared sessions join the same list as everything else, and the
selected session-list layout decides where those rows appear — **Projects** and
**Active & inactive** place them in their project or date groups, and **Recent
activity** places them in its date groups. Each row still shows who shared it.

That keeps shared sessions feeling native to the main session list instead of turning Inbox into a second session browser.

### Pending queue messages are separate from unread

Queued messages do not make a session “unread”.

Instead, the session shows its own pending-message badge and pending UI. See [Pending queue](/sessions/pending-queue).

## Work attention in 0.3 development

In **unreleased 0.3 development source**, Inbox also brings together reporting
sessions and workflow runs that need your review. Work is grouped under its
root where that relation is available. A step session's request can appear
under its run instead of as an unrelated conversation. A reporting relation
does not grant you the right to answer another Account's requests.

Open a row or **Review** to inspect its current request. On a wide page,
selection opens its detail beside the list; on a phone it opens the detail
screen. An unavailable attention source is reported as unavailable or unable
to refresh, rather than proof that you are caught up. Reconnect and use the
offered retry. Previously loaded content may remain visible with its freshness
state. A stale request needs a current read before you answer it.

**Stalled** identifies a worker whose machine became unavailable with a turn
in flight. Inspect the session and restore connectivity before assuming the
work failed or launching it again. See [Work](/sessions/work).

### Settle or snooze a session

Use the session row's menu to **Settle** when you have reviewed it and do not
want to keep it standing in attention. Settle clears your attention standing
and marks the session read. It does not stop work, archive the session,
answer a permission request or clear another viewer's read state. New activity
or a stronger actionable request can still bring it back.

**Snooze** selects a future reminder time. It changes your attention handling,
not execution; remove the reminder to cancel that choice. For reminder timing
and the interaction with kept/unread sessions, see
[Session read and unread state](/organize/session-read-state).

The development **Landing** presentation depends on a current linked PR state.
That producer and the full open-PR/automatic-settle-on-merge journey are still
being integrated; an idle session or a PR number alone is not proof of merge.
Use explicit Settle after reviewing work rather than assuming automatic cleanup.

### The same tasks through Actions

Settle uses `session.attention.set` with `standing: false`, followed by
`session.read_state.set` with `read: true`. Snooze uses `session.attention.set`
with `remindAt` in epoch milliseconds; `null` removes the reminder.
`inbox.mark_all_read` covers the bulk read operation. These use the same
Account-scoped owners and normal Action approval for agent requests.

Approval requests use `approval.request.create`, `.get`, `.list` and `.decide`;
deciding still needs authenticated human or the explicitly admitted approval
credential. Tool answers use `session.permission.respond`, while structured
user questions use `session.user_action.answer`. In development, the host
agent/MCP permission-answer path requires approval by default; an explicit
Action waiver changes that requirement without bypassing pending-request,
offered-answer or viewer-access checks. Requesting approval never supplies
the human decision itself. The optional [Approval reviewer](/sessions/approval-reviewer)
has its own request-scoped host decision path.

Inspect the [host Action reference](/plugins/api/host-actions) for the exact
inputs and available surfaces. CLI calls use
`happier actions invoke <action-id> --input-json '<json>'`; the app's row
selection and detail placement are presentation, not another mutation owner.

## Attention indicators across the app

Inbox is only one part of the attention model.

### Inbox dot

The **Inbox** tab or sidebar button shows a dot when Inbox has important content, such as:

- open approval requests
- session requests that need a decision
- unread sessions
- friend requests or pending outgoing requests
- feed items
- unread changelog/update attention

### Sessions dot

The **Sessions** tab also shows a dot when any session needs attention.

That can include:

- unread activity
- permission requests
- user-action requests
- queued input that still needs processing

This lets you notice session-specific attention even before opening Inbox.

### Session-row indicators

Inside the session list itself, Happier also emphasizes sessions that need attention.

Examples include:

- unread sessions
- sessions with permission or action-required state
- sessions with pending messages

## Approval requests

Approval requests are the user-facing review layer for actions that should not run immediately.

Instead of executing directly, Happier creates an approval item that you can open, review, and approve or reject.

Common examples:

- prompt or saved configuration updates proposed by an agent
- filesystem changes, installs, or exports routed through the approval queue
- session-control or tool-like actions that are configured to require explicit approval

### What an approval contains

An approval request can include:

- the action being requested
- the target arguments
- a short summary
- optional preview information such as files, paths, or a mutation plan
- a current status

Typical statuses include:

- open
- approved
- executing
- rejected
- executed
- failed

In the current development approval contract, **approved** records the user's
decision and **executing** means one executor has durably claimed the effect.
While an item is executing, Happier does not offer another approval or retry
that could perform the same effect twice. If the effect may have completed but
the final result could not be saved, the item stays executing and reports an
unknown outcome instead of guessing or replaying it.

Historical approval items remain readable. Older items that do not contain the
original execution authority cannot be executed by a current client; Happier
reports that the approval is stale and asks you to start the operation again.
The person who approves an item authorizes the decision but does not become the
operation's identity: Happier rechecks the original Account, Home, runtime,
target, Action policy, and resource access before the effect runs.

### Reviewed prompt edits (development integration)

A prompt-document update can carry the revision read for its reviewed change.
If someone edits that document before execution, Happier returns a conflict and
keeps the winning content. Read the current version and review the proposed change
again; approval does not silently rebase it. A competing write during execution
is checked too. An update without a reviewed revision retains the write-time
check, but cannot establish that an earlier preview is still current.

Prompt edits proposed by automation use ordinary Actions approval, defaulting to
**Ask first**. An explicit **Allowed** setting covers that Action on its exact
surface across Sessions; it does not grant one Bot special authority. Agents and
Voice can request required approval, but the decision requires authenticated human
authority. **Approved** records that decision; only the execution result establishes
that the document saved. The Session Work editor and its review presentation are
still being integrated, so this is not a released editor workflow.

### Why Happier uses approvals

Approvals give you:

- a durable review point before sensitive work happens
- a record of what was requested
- one shared model that works across app UI, CLI, tools, and other surfaces

## Permission requests

Permission requests are about **runtime tool access inside a session**.

Examples:

- allow a command to run
- allow a file write
- allow a tool invocation pattern

These are different from approvals:

- **Permission request** = “may this tool/action run in this session?”
- **Approval request** = “should Happier execute this higher-level action?”

## User-action requests

Some requests are not simple tool permissions.

Happier also supports **user-action requests**, where the agent needs a structured human response before it can continue.

Common examples:

- **AskUserQuestion**
- **Exit Plan Mode**
- provider-specific review/approval flows

Depending on the request, you might be asked to:

- approve
- reject
- request changes
- answer one or more questions
- choose a provider-specific approval variant

## Unread sessions

Unread sessions are first-class Inbox items.

If a session has new activity since you last viewed it, Happier can show it in the **Unread sessions** section of Inbox so you can jump back to it quickly.

This matters because “nothing is blocked” and “you should still look at this” are different states. Inbox handles both.

For the full read/unread model and manual actions, see [Session read and unread state](/organize/session-read-state).

### How unread works in practice

Think of unread as:

> this session changed, and you have not reviewed that change yet

Inbox only shows the session once. If a session already has a stronger attention reason, such as a permission or user-action request, Happier surfaces it in that request-focused section instead of duplicating it again under unread.

## Session requests in Inbox

When a session needs an immediate decision, Inbox shows the request with session context.

That context can include:

- the session name
- the machine/device label
- the relevant path
- the permission prompt or user-action prompt itself

This makes Inbox a good place to handle urgent session work without first browsing the full session list.

## Notifications and Inbox

Push notifications and Inbox work together, but they are not the same thing.

- Notifications are the fast re-entry path when something happens away from the app
- Inbox is the in-app queue that collects attention items once you are back inside Happier

For push behavior, see [Notifications](/extras/notifications-setup) and [Notification routing](/extras/notifications-routing).

## Common workflows

### Review an approval request

1. Open **Inbox**
2. Open the approval item
3. Review the summary and preview information
4. Approve or reject it

### Handle a session request

1. Open **Inbox**
2. Find the session that needs action
3. Review the permission request or user-action request
4. Respond in context

### Catch up on unread work

1. Open **Inbox**
2. Look at **Unread sessions**
3. Open the sessions you have not reviewed yet
4. Continue from the session transcript

### Find a shared session

1. Open **Sessions**
2. Find the session in **Shared sessions** under **Active** or **Inactive** on
   released 0.2; in the 0.3 development channel it sits in the ordinary group
   supplied by your selected layout, or search for it by name
3. Open or pin the session
