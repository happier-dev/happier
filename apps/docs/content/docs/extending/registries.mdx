Registry sources let you review reusable skills and plugins before adding them
to Happier. Your source list belongs to your Account; a source is a location,
not a second copy of your library or permission to run its contents.

## Availability

This guide describes **0.3 development source**, not a released stable version.
The shared registry controls and their consumer pages are being validated. Personal token management is available through Actions and the CLI; the registry form's token controls remain in integration. Skill readers include Git, `skills.sh` and Claude marketplace catalogs. MCP and ACP registries feed their own add flows; plugin browsing reads Happier catalogs and community npm. Happier picks appear first when the curated catalog supplies entries.

## Before you begin

Use your qualified Home and Account. Public GitHub skills and public plugin
catalogs can be read directly by the client. Web browsing of `skills.sh` and
non-GitHub Git repositories needs a reachable connected machine. Native clients
read public GitHub repositories over HTTPS and HTTP catalogs directly. Non-GitHub
Git repositories and older saved SSH/Git/local-checkout sources need a connected
machine on native clients too.

## Browse and add content

Use **Settings → Skills** and the add dialog's registry selector to browse skill sources. Its **Manage registries** view manages the same source list. **Settings → Plugins → Discover** browses plugin listings directly;
it does not need a Machine simply to show a public catalog. Source management
uses the Account list rather than a selected Machine's private source file.

For a new Git source, use a credential-free HTTPS repository URL. Git sources
are scanned for `SKILL.md` bundles. `skills.sh` uses its public search/featured
surface. Claude marketplace catalogs expose their skills, not their hooks,
commands, Agents or MCP servers.

Read an item's details before adding it. Skills are installed into the library
at the reviewed commit with their supporting files and executable modes.
Adding a skill to the library and explicitly installing it outside Happier are different operations. See [Skills](/extending/skills).
Plugin install review and installation still run on the chosen connected
Machine and use that Machine's credential-profile owner.

The development CLI exposes `happier registries` and `happier skills` through
the same Actions. Consult the generated [host Action catalog](/plugins/api/host-actions)
for current argument schemas and approval requirements. CLI and Agent callers
ask by default; browsing does not grant installation or token disclosure.

## App templates in development

The built-in Dokploy source lists its published catalog and reads only the
selected app's Compose and TOML files. Review includes the Compose document and
any public supporting files. Contained relative binds keep their native Compose
behavior, including writable directories; host mounts remain visible for review.
Happier preserves vendor file paths and contents. An upstream template's file,
directory or unused environment mismatch is not silently repaired.

In unreleased 0.3 source, routed app-template Domains can declare an HTTP health
path and exact expected status. A supported Compose HTTP status assertion can
supply them. A template without these operands still installs through ordinary
reviewed approval; health remains **Not checked**. Happier does not substitute
`/` and HTTP 200, run an invented probe, or exempt an unprobed route from
authentication. Supplied health declarations must be valid.

Installing a template with a required Domain creates its Environment, runs the
reviewed deployment, then adds the Domain. If deployment is refused or fails,
the Environment remains and no Domain is added. Retry uses that retained
Environment for a new deploy attempt before adding the Domain.

## Coder server and Docker workspaces in development

The unreleased 0.3 Machine recipes include **Coder** for Debian/Ubuntu Linux
with systemd. It installs Coder 2.39.0 through the official installer. Install
**Docker Engine** first if this server will provision Docker workspaces. Supply
your credential-free external HTTPS URL; the recipe listens on
`127.0.0.1:3000`. Configure your HTTPS reverse proxy before connecting clients
or workspace agents. Coder uses its built-in PostgreSQL database for this
starter installation; preserve the service user's data directory.

For a container deployment, choose **Coder** from the Store's app templates.
It includes PostgreSQL 17 with a generated database password managed by the
ordinary deployment secret owner, a persistent database volume, and a required
HTTP Domain. Set **Docker socket group ID** to the numeric group owning
`/var/run/docker.sock` on the Linux Machine (`stat -c %g /var/run/docker.sock`).
The reviewed Docker socket mount lets Coder provision sibling containers on
that host. Complete Coder's first-user setup privately in its web UI; neither
recipe creates or prints an administrator password.

The **Coder Docker workspaces** project starter uses Coder's official repository.
Its build instructions select the `v2.39.0` Docker example under
`examples/templates/docker`. Import that directory as a template in Coder,
including its `build` directory. The example keeps the workspace home in a
Docker volume across Stop and Start. Workspace agents must reach your external
Coder URL; a loopback-only URL cannot serve containers on the Docker network.
Do not put Happier enrollment keys or your Coder account token in Terraform,
images, startup scripts, or template parameters.

After first-user setup, follow the [Coder connected-account and workspace
flow](/apps/control-panel#coder-workspaces-unreleased-development). Use the deployment
URL and your personal Coder token in the existing Connected Account form.
The installer does not sign in the controller or create a Happier Machine.

Removal of the Machine recipe stops and disables Coder while retaining its
binary, database, workspaces and configuration. Delete workspaces in Coder
before deliberately removing their volumes. For a failed install, inspect the
Machine setup result and retry after correcting the reported prerequisite or
network failure. Back up PostgreSQL before an upgrade; Coder does not support
rolling its database back by installing an older binary.

The vendor basis is Coder's [Docker installation guide](https://coder.com/docs/install/server/docker),
[official v2.39.0 installer](https://github.com/coder/coder/blob/v2.39.0/install.sh),
[Docker template](https://github.com/coder/coder/tree/v2.39.0/examples/templates/docker),
and [upgrade guidance](https://coder.com/docs/install/operate/upgrade/), checked
on November 13, 2026. This development entry does not establish release certification.

## Browser extensions in development

The development `browserExtension` catalog kind supplies Chrome Web Store IDs
to the managed Chromium browser. Packages and enablement belong to a persistent
profile on the selected Machine. Load-unpacked uses a directory on that Machine.
Installing, updating, enabling or removing an extension needs Machine Manage
access. Package changes apply when the browser restarts; an active profile asks
for confirmation first.

Extension updates use the existing Store update check and review flow. An update
that adds permissions needs another permission review. Action popups and options
pages run as managed browser views. Native webviews use the “available in the
managed browser” presentation state. The Store screens for these contracts are
still being integrated and reviewed in 0.3 development source.

## Private sources

Create a private Saved Secret, then select it when adding a source:

```bash
happier secrets create registry-token
happier registries add https://github.com/owner/private --token-secret registry-token
```

The secret value comes from a hidden prompt or stdin, never a command-line value.
The source stores the Saved Secret's reference. Token-protected requests run on
the CLI or a connected machine; the browser does not materialize the token.
Private Saved Secrets do not require Teams.

A bound token prevents deletion of its Saved Secret. Clear or replace the binding
first with `happier registries token <source> --clear` or
`happier registries token <source> --secret <name-or-id>`. Removing a source keeps
the content already imported into your library.

## Supplied sources and failures

Built-in and plugin-supplied sources can be disabled, but their declarations
cannot be edited or removed as personal rows. Removing a supplying plugin
removes its source from discovery; content already in your library stays there.
A daemon-placed plugin source needs one of its supplying Machines, not merely
any online Machine.

A failed source reports its own problem while other sources remain usable.
When a registry supplies a rate-limit reset time, Happier shows that time and
holds requests to the host until it resets. Without a reset time it shows
“Rate limited”; use Retry or refresh to try again manually. No cooldown is guessed.
An explicit refresh retries the current request. Last-known items are not a
substitute for current source authority: disabling/removing a source or retiring
its supplier withdraws its old results. If a skill write succeeded but a later
reach step failed, repair that step rather than install another copy.

In 0.3 development source, `registries.updates.check` returns each failed
check's source ID and, when available, its source title alongside the existing
reason. Plugin authors can present those facts from the typed Action result:

```ts
import type { RegistriesActionResultById } from '@happier-dev/plugin-sdk/actions';

function failedSources(check: RegistriesActionResultById['registries.updates.check']) {
  return check.results.flatMap(item => item.upstream.state === 'unchecked'
    ? [{ source: item.sourceTitle ?? item.sourceId, reason: item.upstream.reason }]
    : []);
}
```

Older results may omit the source labels; their reason remains usable. These
labels do not grant permission to read or install from a source. Store Updates
uses reported App, Skill, MCP server, Agent, browser extension and Plugin
observations in 0.3 development source. App checks review the installed
Environment's template; Plugin observations retain their Machine placement.
Plugin updates keep their existing installation and access review. Applied Machine
recipes have no separate upstream-update observation; their provider Plugin
uses the Plugin update flow.

### Chrome Web Store (development)

The built-in Chrome Web Store source uses the store’s unofficial search and detail endpoints. Browse shows featured extensions, the Google collection and the Extensions category. These endpoints are not an official Google API and can become unavailable when the store changes. The source then shows the registry’s unavailable state; paste-link or extension-ID installation remains available. Download, CRX3 verification, update checks and permission review use the managed browser extension flow.
