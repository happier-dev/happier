Use the SDK or HTTP API to drive Happier Actions from a trusted developer tool.

<Callout>
  **Developer Preview:** `@happier-dev/sdk` is a private `0.0.0` workspace
  package, not a package-registry install. It remains private until its
  first-publication gates pass and release work is explicitly authorized. A
  release pipeline can produce a
  candidate tarball for its proof workflow, but no candidate is currently
  published. The Action API is also development source only. Neither is
  released or publicly available; the server origin has not completed
  composed/live proof.
</Callout>

## What you need first

- A development checkout that supplies the SDK package and a signed-in daemon
  connected to its configured Account server. There is no separate Action API
  feature toggle and not yet a supported `npm install @happier-dev/sdk`
  workflow.
- An API Token created by a present user. Public Action API routes accept API
  Tokens only; signed-session bearers and daemon control tokens are rejected.

## Supported environment

The current supported consumer is a server-side Node.js program. The Action API does not
enable CORS, and no same-origin browser delivery is proven in this preview. Do
not put an API Token in browser code or expect an arbitrary browser origin to
call either Action endpoint.

## Install and run a candidate

When the release workflow provides an exact candidate tarball, install that
local file—not a registry version. The pipeline output is a `.tgz` under its
SDK candidate directory; replace the placeholder with the absolute path you
received.

```bash
mkdir happier-sdk-consumer && cd happier-sdk-consumer
npm init --yes
SDK_TARBALL='/absolute/path/to/sdk-candidate.tgz'
npm install --ignore-scripts --no-audit --no-fund "$SDK_TARBALL"
```

The candidate includes a TypeScript end-to-end example. Install its development
runner and launch it with Node.js:

```bash
npm install --save-dev --no-audit --no-fund tsx
HAPPIER_API_ENDPOINT='https://configured-server.example' \
HAPPIER_TOKEN='hap_v1_…' \
HAPPIER_ENDPOINT_MODE=server \
node --import tsx ./node_modules/@happier-dev/sdk/examples/basic/index.ts
```

Set `HAPPIER_ENDPOINT_MODE=server` for a configured server endpoint. The
example uses the authenticated machine-list bootstrap and binds every Action to
the selected machine. Set `HAPPIER_MACHINE_ID` only when you already know the
exact server machine to use.

For a daemon-local endpoint, read the daemon's current HTTP port, then run the
same example in `daemon` mode. The daemon uses its current machine, so do not
set `HAPPIER_MACHINE_ID` or expect the example to discover one.

```bash
DAEMON_PORT="$(happier daemon status --json | jq -er '.daemon.httpPort')"
HAPPIER_API_ENDPOINT="http://127.0.0.1:$DAEMON_PORT" \
HAPPIER_TOKEN='hap_v1_…' \
HAPPIER_ENDPOINT_MODE=daemon \
node --import tsx ./node_modules/@happier-dev/sdk/examples/basic/index.ts
```

The example performs spawn, wait, bounded transcript follow with iterator
cleanup, send, snapshot transcript read, and stop. This is candidate proof
guidance, not a published installation method.

## Connect with an explicit endpoint and token

The SDK accepts its endpoint and token explicitly. It does not read a CLI
profile, persist credentials, or accept an Account signing seed or encryption
material. If your program reads an environment variable, that is your program's
choice; `connect()` does not implicitly read `HAPPIER_TOKEN`.

For daemon-local use, get the current HTTP port from the daemon status JSON;
the port is not fixed:

```bash
DAEMON_PORT="$(happier daemon status --json | jq -er '.daemon.httpPort')"
export HAPPIER_API_ENDPOINT="http://127.0.0.1:$DAEMON_PORT"
```

```ts
import { connect } from '@happier-dev/sdk';

const token = process.env.HAPPIER_TOKEN;
if (!token) throw new Error('Set HAPPIER_TOKEN before starting this script.');
const endpoint = process.env.HAPPIER_API_ENDPOINT;
if (!endpoint) throw new Error('Set HAPPIER_API_ENDPOINT before starting this script.');

const happier = connect({
  endpoint,
  token,
});

try {
  // Call a typed Action method or actions.execute(...) with its typed input.
} finally {
  happier.close();
}
```

## Choose the SDK call style

The SDK offers three capabilities over the same Action API:

- **Raw:** `actions.execute(actionId, input, options)` is useful when the
  Action id is selected at runtime.
- **Typed Action methods:** use the matching path under `actions` when the
  Action is known in your code.
- **Session helpers:** use `sessions` for daemon-local work, or
  `machine(machineId).sessions` when an exact remote/server machine must stay
  bound to the workflow.

At a daemon-local endpoint, `happier.sessions.spawn(...)` omits the routing
target and the daemon uses its current machine. It does not perform machine
discovery or choose a fallback. A server endpoint has no default machine: an
unbound `happier.sessions.spawn(...)` rejects with `HappierActionError` whose
`code` is `target_required`, so select an exact id and use
`happier.machine(machineId).sessions`.

This is an admitted Action failure, not a transport failure.
`HappierTransportError` instead reports that the SDK could not complete or
validate the HTTP exchange, such as a network failure, non-success HTTP status,
invalid JSON, or an invalid response envelope. These errors reject the SDK
promise; they are not returned as successful values.

```ts
const target = { kind: 'machine', machineId: 'machine-id' } as const;

// Raw Action id with its explicit routing target
await happier.actions.execute('action.spec.search', { query: 'session', limit: 5 }, { target });

// Typed Action method bound to the same target
await happier.machine('machine-id').actions.search({ query: 'session', limit: 5 });

// Fluent Session creation on a daemon-local endpoint uses its current machine.
const created = await happier.sessions.spawn({
  directory: '/path/to/project',
  agent: 'codex',
  initialMessage: 'Inspect the failing tests.',
});
await created.waitForIdle();

// A selected machine and an existing Session
const existingSession = happier.machine('machine-id').sessions.get('session-id');
await existingSession.send('Please inspect the failure.');
await existingSession.waitForIdle();
await existingSession.stop();
```

### Recover when the initial message is not admitted

Fluent `sessions.spawn()` has a deliberate partial-success case. Happier can
commit the Session and then reject the requested `initialMessage`, or be unable
to determine whether that message was admitted. In that case, the promise
rejects with `HappierSessionInitialInputError`; it does not erase the committed
Session.

Inspect both `error.session` and `error.result.initialInput` before deciding how
to recover:

```ts
import { HappierSessionInitialInputError } from '@happier-dev/sdk';

try {
  const session = await happier.machine('machine-id').sessions.spawn({
    directory: '/path/to/project',
    agent: 'codex',
    initialMessage: 'Inspect the failing tests.',
  });
  await session.waitForIdle();
} catch (error) {
  if (!(error instanceof HappierSessionInitialInputError)) throw error;

  console.error('Initial input disposition:', error.result.initialInput);
  const recentHistory = await error.session.history({ limit: 20 });
  console.error('Recent history:', recentHistory);
  // The Session already exists. Use its history and current state to decide
  // whether to send, keep, or explicitly stop it.
}
```

The disposition is `rejected`, `outcomeUnknown`, or `notRequested` in this
error. Do not blindly retry `sessions.spawn()` or delete `error.session`: either
choice can create duplicate work or discard a valid committed Session. Inspect
the disposition and current Session state, then continue with `error.session`,
keep it for later, or stop it explicitly when that is the intended outcome.

The raw `session.spawn_new` Action does not turn this partial success into an
exception. It returns the successful creation result, including `sessionId` and
`initialInput`, for the caller to interpret.

### Invoke an Action contributed by a plugin

Use Action discovery to obtain the exact qualified id and declared input of an
Action supplied by an installed plugin, then invoke it dynamically. Discovery
is target-bound: it reports the contributed Actions currently available from
that selected machine and enabled for the API surface.

```ts
const machine = happier.machine('machine-id');
const matches = await machine.actions.action.spec.search({
  query: 'save note',
  limit: 10,
});
const match = matches.actionSpecs.find(
  (action) => action.id === 'acme.notes/actions/save-note',
);
if (!match) throw new Error('The contributed Action is not available.');

const { actionSpec } = await machine.actions.action.spec.get({ id: match.id });
console.log(actionSpec.inputSchema);

const result = await machine.actions.invoke(
  { pluginId: 'acme.notes', localId: 'save-note' },
  { note: 'Remember this' },
);
```

Contributed Actions use their qualified plugin-and-Action identity in Action
settings. Their **API** enablement and approval choice is enforced just like the
corresponding setting for a built-in Action; installing an Action does not
bypass an **Off** or **Ask first** decision.

The **API** setting starts **Allowed** for API-eligible built-in and contributed
Actions, so Action Settings add no approval prompt unless the user changes that
control under **Settings → Actions → Integrations**. A non-safe contributed
Action still requires the host's live current-intent confirmation; **Allowed**
does not suppress the Action's independent safety contract. The corresponding
**Trusted plugins** setting is also **Allowed** by default for Actions it
supports. Those settings cannot elevate a PAT or trusted plugin above
`account_automation`: present-user-only controls such as approval decisions,
plugin uninstall, Agent session-hook changes, and security-policy changes return
`present_user_required`.

The generated [SDK API inventory](https://github.com/happier-dev/happier/blob/dev/packages/sdk/API.md)
is an export census, not a complete Action method reference. Use the generated
[Host Actions reference](/plugins/api/host-actions) for built-in Action
contracts. At runtime, use `actions.search(...)` and
`actions.action.spec.get(...)` to inspect available Actions, then call the raw
`actions.execute(...)` primitive when the Action id is selected dynamically.
Do not copy a method list into an integration.

For raw `session.spawn_new`, pass a machine target once in the outer
`options.target` when targeting a server or remote machine; omit it at a
daemon-local endpoint to use that daemon's current machine. The public input
deliberately omits `executionTarget`; the daemon supplies its local placement
after resolving the target. Supplying `executionTarget` in a public request is
rejected as invalid input. The server relay forwards the exact machine target
without receiving or inventing a daemon-local server id. Use
the SDK types and the Action reference for the remaining spawn fields, such as
`directory`, `agentTarget`, and an optional `creationKey`.

## Call the HTTP API

The v1 protocol has one relative path:

```text
POST /v1/actions/:actionId
Authorization: Bearer <API Token>
Content-Type: application/json
```

Both forms are implemented in the current Developer Preview source:

```text
POST http://127.0.0.1:<daemon-port>/v1/actions/:actionId

POST https://<configured-server>/v1/actions/:actionId
```

Use a direct daemon origin when the caller can reach that daemon. Use the
configured server origin when the target daemon is connected to that server:
the server authenticates and relays over the daemon's existing connection, so
the daemon does not need an inbound public address. This remains a Developer
Preview contract, not a published integration surface. The server origin has
not completed composed/live proof.

The request envelope is strict. `target` is routing metadata, never action
input or caller authority.

```json
{
  "v": 1,
  "requestId": "optional-correlation-id",
  "target": { "kind": "machine", "machineId": "machine-id" },
  "input": {}
}
```

`target` may be omitted, a machine target, or a session target
(`{ "kind": "session", "sessionId": "session-id" }`). The daemon-local
route defaults an omitted target to its current machine. The server origin has
no default machine: callers first select one through the API Token-authenticated
`GET /v1/machines` discovery route (the SDK exposes this as
`happier.machines.list()`), then send that exact machine target. A session
target is also valid when Happier can establish one exact current machine for
that Session. An omitted server target returns the typed `target_required` Action
result; the server never silently selects another machine. Account-level
Actions still run through the selected daemon.

An admitted response preserves the Action result without an SDK-specific
remapping:

```json
{
  "v": 1,
  "actionId": "session.spawn_new",
  "requestId": "optional-correlation-id",
  "execution": { "ok": true, "result": {} }
}
```

Failed Actions use the same `execution` field with `ok: false`, an error code,
an error string, and optional details. Authentication failures are HTTP `401`
with `invalid_token`; malformed outer envelopes and unknown Action ids are HTTP
`400` with `invalid_request` and a typed code.

## Try the HTTP API with curl

For the configured server origin, first find an available machine with the API
Token-authenticated bootstrap route. Its `id` is the value used in the Action
target.

```bash
curl --fail-with-body \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  "$HAPPIER_API_ENDPOINT/v1/machines"
```

Then use the safe, read-only Action discovery operation. The same request also
works against a daemon-local endpoint when `machine-id` is that daemon's
current machine.

```bash
curl --fail-with-body --request POST \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{
    "v": 1,
    "target": { "kind": "machine", "machineId": "machine-id" },
    "input": { "query": "session", "limit": 5 }
  }' \
  "$HAPPIER_API_ENDPOINT/v1/actions/action.spec.search"
```

If you already have a Session id, this safe status lookup is a real operation
against that Session. The Session target and `input.sessionId` must name the
same Session; the server derives its current owning machine rather than asking
you to duplicate that machine in the input.

```bash
curl --fail-with-body --request POST \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{
    "v": 1,
    "target": { "kind": "session", "sessionId": "session-id" },
    "input": { "sessionId": "session-id", "live": false }
  }' \
  "$HAPPIER_API_ENDPOINT/v1/actions/session.status.get"
```

The server does not choose a machine on your behalf. For example, omitting
`target` from that server request returns HTTP `200` with this Action error
envelope, not a request sent to an arbitrary daemon:

```json
{
  "v": 1,
  "actionId": "action.spec.search",
  "execution": {
    "ok": false,
    "errorCode": "target_required",
    "error": "target_required"
  }
}
```

## Transport limits

v1 uses finite JSON request/response messages—there is no SSE endpoint. Public
Action ingress verifies the API Token before JSON parsing. The shared request
body ceiling is 32 MiB (33,554,432 bytes); the server-to-daemon relay admits a
33 MiB (34,603,008-byte) request carrier, reserving one MiB for relay framing.
Responses send `Cache-Control: no-store`, and public Action routes do not enable
CORS. Put the bearer token in the `Authorization` header, never in a query
string.

At both the daemon-local and server origins, the complete serialized response
envelope—not only `execution.result`—is limited to 24,000,000 UTF-8 bytes. If an
Action finishes but its response would exceed that limit, the request remains
an admitted Action call and returns the normal envelope with this typed
execution failure:

```json
{
  "ok": false,
  "errorCode": "result_too_large",
  "error": "Action execution completed, but its response exceeded the external Action response limit and could not be represented.",
  "details": {
    "executionCompleted": true,
    "maxSerializedBytes": 24000000
  }
}
```

The SDK rejects that response with `HappierActionError`; its `code` is
`result_too_large` and its `details.executionCompleted` is `true`. The Action
may already have committed a mutation, so do not blindly retry it. Inspect
current state or use the Action owner's idempotency contract. For large data,
return Artifact references, use an existing stream Action, or design bounded or
paginated reads instead of one oversized inline result.

The SDK supports `AbortSignal` and closes outstanding calls when `close()` is
called. It does not replay a mutation or move a failed mutation to another
endpoint. For mutating Actions, the SDK generates a request ID when you do not
supply one, but that generated value is not returned to the caller. If you may
need to reconcile an uncertain mutation outcome, generate and retain the ID in
your own code and pass it as `options.requestId`. A request ID provides
correlation unless the Action's own contract also gives it idempotency
semantics; the SDK adds no receipt store or automatic retry subsystem.

`session.followTranscript()` is a finite, demand-driven async iterator. It
pauses between pages while the consumer is not awaiting another item, and an
early loop exit or `close()` releases its canonical follow lease. For a genuine
execution-run stream, use `client.runs.startStream(...)`. The returned handle
has `runId`, `streamId`, `cancel()`, and an async iterator; normal completion,
early return, caller abort, and `close()` cancel that stream. On a
machine-bound client, stream start, read, and cancel remain on its selected
machine. Snapshot Actions remain ordinary methods.

## Server relay, readability, and revocation

The configured server deliberately can read requests and responses while it
relays them to the exact target daemon. This is not direct-server E2EE. The
server authenticates the API Token, validates the outer envelope, and proves
placement; the selected daemon handles the Action using its configured Action
settings.
Use the daemon-local transport when you need direct local delivery.

Server-side token verification observes revocation on the next verification. A
daemon-local positive validation cache can remain valid for at most 60 seconds;
after expiry, an unreachable server returns `auth_unavailable` instead of
extending access offline.
