Use the SDK or HTTP API to drive Happier Actions from a trusted developer tool.

<Callout>
  **Developer Preview:** the SDK and Action API are implemented in current
  development builds but have not shipped in a public Happier release. Use the
  current workspace source with a development stack.
</Callout>

The SDK, direct HTTP calls, CLI, MCP, and trusted plugins all reach the same
Action contracts. The adapter changes how a caller connects; it does not create
a second operation or permission model. Happier validates the Action at the
daemon that owns execution, applies the Account's Action settings, and returns
the same Action result to every external client.

## What you need first

- A development checkout with the SDK source and a signed-in daemon connected
  to its configured Account server. There is no separate Action API feature
  toggle.
- An API Token created by a present user. Public Action API routes accept API
  Tokens only; signed-session bearers and daemon control tokens are rejected.

## Supported environment

The SDK requires Node.js 18.17 or newer and supports server-side Node.js
programs. Direct HTTP clients may use any language that can send JSON over
HTTPS. The Action API does not enable CORS, and no same-origin browser delivery
is proven in this preview. Do not put an API Token in browser code or expect an
arbitrary browser origin to call either Action endpoint.

## Choose how to connect

Every mode below uses the same Action registry, input schemas, settings and
approval system, and result contracts. Happier still applies the setting for
the surface that made the call. Choose the interface that fits the caller
rather than building a new integration protocol around Happier.

| Interface | Best fit | Authentication and targeting | Live output |
| --- | --- | --- | --- |
| Human CLI | Interactive terminal work | Saved sign-in or an API Token; current machine or `--machine-id` | `hdev history <session> --follow` |
| CLI JSON | Shell scripts and agent tooling | API Token through `HAPPIER_TOKEN` or `--api-token`; `--machine-id` when needed | `--follow --jsonl` |
| Fluent SDK | Node.js Session workflows | Explicit `connect({ endpoint, token })`; root client for a local daemon, machine-bound client for the server | Demand-driven async iterators with `AbortSignal` and cleanup |
| Raw SDK | Dynamic Action discovery and invocation from Node.js | Same client and target rules as the fluent SDK | Compose the finite follow/read/cancel Actions |
| HTTP | Other languages and infrastructure tools | Bearer API Token; omit the target at a local daemon, select an exact machine at the server | Finite Action calls in v1; there is no SSE endpoint |

Use the CLI for terminal and shell workflows, the fluent SDK when a Node.js
program works primarily with Sessions, the raw SDK when it selects Action ids
dynamically, and HTTP when Node.js is not the right client runtime. MCP and
trusted plugins are additional capabilities over the same Action owner.

## First five minutes

This page describes the current workspace source, so the commands below invoke
the CLI through `hdev`, the development lane that tracks that source (install
it with `install-dev`, or point the stable `happier` shim at this checkout
with `yarn cli:activate` — every command is identical after that).

Use the checked-in basic example for one deterministic daemon-local run. It
connects with an explicit token and endpoint, creates a Session on the daemon's
current machine, sends one message, reads the assistant response, stops the
Session, and closes the client.

1. In **Settings → Account → API Tokens**, create a token and copy it when
   it is shown. The SDK does not load this token from a CLI profile or any other
   credential store.
2. Start a signed-in daemon, then read its current HTTP port. The port is not
   fixed.
3. Choose an Agent installed and enabled on this machine. Discover the exact
   ids through the existing read-only catalog Action instead of guessing
   (`agents.backends.list` is the same inventory `sessions.spawn()` resolves
   your `agent` value against):

   ```bash
   hdev actions invoke agents.backends.list --input-json '{"includeDisabled":true}' --json \
     | jq -er '.data.items[] | select(.enabled == true) | .agentId'
   ```

   The example uses `codex` unless you set `HAPPIER_AGENT_ID` to one of the
   ids this prints.
4. From the repository root, run:

```bash
hdev daemon start
DAEMON_PORT="$(hdev daemon status --json | jq -er '.daemon.httpPort')"
HAPPIER_API_ENDPOINT="http://127.0.0.1:$DAEMON_PORT" \
HAPPIER_TOKEN='hap_v1_…' \
HAPPIER_AGENT_ID='codex' \
yarn tsx packages/sdk/examples/basic/index.ts
```

The example prints the most recent assistant text, or its explicit placeholder
when no assistant text is available. Its `finally` blocks stop the
demonstration Session and await `happier.close()` even when a later step fails.
The example's environment lookup is caller code: `connect()` itself requires
`endpoint` and `token` and never reads environment variables implicitly.

These failures are expected typed outcomes rather than reasons to retry the
whole recipe blindly:

| What happened | SDK result | What to do |
| --- | --- | --- |
| The selected Agent is missing, disabled, or lacks a Session identity | `HappierAgentUnavailableError` with `reason` set to `not_installed`, `disabled`, or `identity_unavailable` | Install or enable that Agent on the target machine, or use its exact available id. |
| Action policy is **Off** or **Ask first** | `HappierActionError` with `code` `action_disabled` or `approval_required` | Change **External API & SDK** or complete the approval from a signed-in app. The token cannot approve its own request. |
| A server-origin call has no exact machine or resolvable Session target | `HappierActionError` with `code` `target_required` | Select a machine as shown below and use a machine-bound client. |
| The Session committed but its requested initial message did not settle as admitted | `HappierSessionInitialInputError` with the committed `session` and `result.initialInput` | Inspect that Session instead of spawning another one blindly. |
| Authentication, HTTP admission, networking, JSON, or response validation fails | `HappierTransportError`; HTTP failures retain `status` and a typed `code` when supplied | Correct the token or endpoint. Inspect current state before retrying an interrupted mutation. |

### Use the configured server and an exact machine

The checked-in comprehensive example covers the server origin. List eligible
machines first and select the intended id explicitly; neither the SDK nor the
server silently chooses among several candidates.

```bash
export HAPPIER_API_ENDPOINT='https://configured-server.example'
export HAPPIER_TOKEN='hap_v1_…'

curl --fail-with-body \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  "$HAPPIER_API_ENDPOINT/v1/machines" \
  | jq -er '.[] | select(.active and .revokedAt == null and .replacedByMachineId == null) | .id'
```

After choosing one printed id, make the machine, installed Agent, and a
directory that exists on that machine explicit:

```bash
HAPPIER_ENDPOINT_MODE=server \
HAPPIER_MACHINE_ID='machine-id' \
HAPPIER_AGENT_ID='codex' \
HAPPIER_WORKSPACE_PATH='/path/on/selected-machine' \
yarn tsx packages/sdk/examples/comprehensive/index.ts
```

The comprehensive example also refuses to guess: if `HAPPIER_MACHINE_ID` is
omitted, it auto-selects only when exactly one active, non-revoked,
non-replaced machine exists.

## Keep request identities for mutations

For a generic CLI Action mutation, provide a request id you can keep with your
automation log:

```bash
hdev actions invoke session.title.set \
  --request-id onboarding-title-1 \
  --input-json "{\"sessionId\":\"$SESSION_ID\",\"title\":\"SDK onboarding\"}"
```

The SDK puts the same correlation id in execution options, outside the Action
input:

```ts
await happier.actions.execute(
  'session.title.set',
  { sessionId, title: 'SDK onboarding' },
  { requestId: 'onboarding-title-1' },
);
```

For a fluent Session message, retain both the Action request id and the
message's retry-safe `localId`:

```ts
await happier.sessions.get(sessionId).sendAndWait(
  'Summarize the current work.',
  { localId: 'onboarding-message-1', timeoutSeconds: 300 },
  { requestId: 'onboarding-send-1' },
);
```

Direct HTTP uses the same request id in the outer envelope. A Session target
works at both origins: the local daemon verifies that it owns the Session, and
the configured server resolves the Session's exact connected machine.

```bash
curl --fail-with-body --request POST \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  --header 'Content-Type: application/json' \
  --data "{
    \"v\": 1,
    \"requestId\": \"onboarding-title-1\",
    \"target\": { \"kind\": \"session\", \"sessionId\": \"$SESSION_ID\" },
    \"input\": { \"sessionId\": \"$SESSION_ID\", \"title\": \"SDK onboarding\" }
  }" \
  "$HAPPIER_API_ENDPOINT/v1/actions/session.title.set"
```

A request id is correlation unless that Action documents stronger idempotency.
Happier does not automatically replay an uncertain mutation.

## Follow output and stop cleanly

Human output stays compact; JSONL emits one record per line. Press Ctrl-C to
cancel either command and release the follow lease:

```bash
hdev history "$SESSION_ID" --follow
hdev history "$SESSION_ID" --follow --jsonl
```

The fluent SDK exposes the same lifecycle as a demand-driven iterator:

```ts
const controller = new AbortController();
try {
  for await (const item of happier.sessions.get(sessionId).followTranscript({
    cursor: 'tail',
    signal: controller.signal,
  })) {
    console.log(item);
    break; // An early return releases the lease.
  }
} finally {
  controller.abort();
}
```

Raw SDK and HTTP clients call the finite `transcript.follow` and
`transcript.unfollow` Actions with one retained lease id. V1 deliberately does
not add a second SSE lifecycle.

## Connect with an explicit endpoint and token

The SDK accepts its endpoint and token explicitly. It does not read a CLI
profile, persist credentials, or accept an Account signing seed or encryption
material. If your program reads an environment variable, that is your program's
choice; `connect()` does not implicitly read `HAPPIER_TOKEN`.

For daemon-local use, get the current HTTP port from the daemon status JSON;
the port is not fixed:

```bash
DAEMON_PORT="$(hdev daemon status --json | jq -er '.daemon.httpPort')"
export HAPPIER_API_ENDPOINT="http://127.0.0.1:$DAEMON_PORT"
```

```ts
import { connect } from '@happier-dev/sdk';

const token = process.env.HAPPIER_TOKEN;
if (!token) throw new Error('Set HAPPIER_TOKEN before starting this script.');
const endpoint = process.env.HAPPIER_API_ENDPOINT;
if (!endpoint) throw new Error('Set HAPPIER_API_ENDPOINT before starting this script.');

const happier = connect({
  endpoint,
  token,
});

try {
  // Call a typed Action method or actions.execute(...) with its typed input.
} finally {
  await happier.close();
}
```

## Choose the SDK call style

The SDK offers three capabilities over the same Action API:

- **Raw:** `actions.execute(actionId, input, options)` is useful when the
  Action id is selected at runtime. Its generated types follow the registry's
  current public Action classification rather than a separately maintained SDK
  allowlist.
- **Typed Action methods:** use the matching path under `actions` when the
  Action is known in your code.
- **Session helpers:** use `sessions` for daemon-local creation and for handles
  to existing Sessions at either origin, or `machine(machineId).sessions` when
  an exact remote/server machine must stay bound to the workflow.

At a daemon-local endpoint, `happier.sessions.spawn(...)` omits the routing
target and the daemon uses its current machine. It does not perform machine
discovery or choose a fallback. A server endpoint has no default machine: an
unbound `happier.sessions.spawn(...)` rejects with `HappierActionError` whose
`code` is `target_required`, so select an exact id and use
`happier.machine(machineId).sessions`.

`machine(id)` returns a target-bound view that shares the root client's
lifecycle. Calling `await close()` on either view aborts outstanding work for both.
An existing `happier.sessions.get(sessionId)` handle automatically uses that
Session as its transport target, so send, wait, history, follow, and stop work
through either origin without repeating the target. An explicit target can still
override this when deliberate machine pinning is required.

This is an admitted Action failure, not a transport failure.

```ts
const target = { kind: 'machine', machineId: 'machine-id' } as const;

// Raw Action id with its explicit routing target
await happier.actions.execute('action.spec.search', { query: 'session', limit: 5 }, { target });

// Typed Action method bound to the same target
await happier.machine('machine-id').actions.search({ query: 'session', limit: 5 });

// Fluent Session creation on a daemon-local endpoint uses its current machine.
const created = await happier.sessions.spawn({
  directory: '/path/to/project',
  agent: 'codex',
  initialMessage: 'Inspect the failing tests.',
});
await created.waitForIdle();

// A selected machine and an existing Session
const existingSession = happier.machine('machine-id').sessions.get('session-id');
await existingSession.sendAndWait('Please inspect the failure.', {
  localId: 'inspect-failure',
  timeoutSeconds: 300,
});
await existingSession.stop();
```

`sendAndWait(message, input?, executionOptions?)` uses the canonical
`session.message.send` Action with `wait: true`. Use `input.localId` to safely
retry an uncertain send and `input.timeoutSeconds` to bound only the
observation; it does not make a second idle-wait call.

### Follow transcript and execution-run streams

Streaming helpers compose the existing finite Actions rather than opening a
second streaming protocol. Transcript iteration fetches only while the consumer
asks for another item. Leaving the loop, aborting, or closing the client releases
the follow lease.

```ts
const session = happier.sessions.get('session-id');

for await (const item of session.followTranscript({
  cursor: 'tail',
  maxItems: 20,
})) {
  console.log(item);
  if (shouldStop(item)) break;
}
```

Execution runs use the same pattern. A machine-bound client keeps start, read,
and cancel on that machine. Normal completion and early loop exit both cancel
the canonical stream handle. On a root client, an input with `sessionId`
automatically binds start, read, and cancel to that Session. A detached run still
needs an explicit machine target at a server endpoint.

```ts
const stream = await happier.machine('machine-id').runs.startStream({
  sessionId: 'session-id',
  runId: 'run-id',
  message: 'Continue the review.',
});

for await (const event of stream) {
  console.log(event);
}
```

### Recover when the initial message is not admitted

Fluent `sessions.spawn()` has a deliberate partial-success case. Happier can
commit the Session and then reject the requested `initialMessage`, or be unable
to determine whether that message was admitted. In that case, the promise
rejects with `HappierSessionInitialInputError`; it does not erase the committed
Session.

Inspect both `error.session` and `error.result.initialInput` before deciding how
to recover:

```ts
import { HappierSessionInitialInputError } from '@happier-dev/sdk';

try {
  const session = await happier.machine('machine-id').sessions.spawn({
    directory: '/path/to/project',
    agent: 'codex',
    initialMessage: 'Inspect the failing tests.',
  });
  await session.waitForIdle();
} catch (error) {
  if (!(error instanceof HappierSessionInitialInputError)) throw error;

  console.error('Initial input disposition:', error.result.initialInput);
  const recentHistory = await error.session.history({ limit: 20 });
  console.error('Recent history:', recentHistory);
  // The Session already exists. Use its history and current state to decide
  // whether to send, keep, or explicitly stop it.
}
```

The disposition is `rejected`, `outcomeUnknown`, or `notRequested` in this
error. Do not blindly retry `sessions.spawn()` or delete `error.session`: either
choice can create duplicate work or discard a valid committed Session. Inspect
the disposition and current Session state, then continue with `error.session`,
keep it for later, or stop it explicitly when that is the intended outcome.

The raw `session.spawn_new` Action does not turn this partial success into an
exception. It returns the successful creation result, including `sessionId` and
`initialInput`, for the caller to interpret.

### Invoke an Action contributed by a plugin

Use Action discovery to obtain the exact qualified id and declared input of an
Action supplied by an installed plugin, then invoke it dynamically. Discovery
is target-bound: it reports the contributed Actions currently available from
that selected machine and enabled for the API surface.

```ts
import { isHappierActionApprovalRequestCreated } from '@happier-dev/sdk';

const machine = happier.machine('machine-id');
const matches = await machine.actions.search({
  query: 'save note',
  limit: 10,
});
if (isHappierActionApprovalRequestCreated(matches)) {
  throw new Error(`Approval required: ${matches.artifactId}`);
}
const match = matches.actionSpecs.find(
  (action) => action.id === 'acme.notes/actions/save-note',
);
if (!match) throw new Error('The contributed Action is not available.');

const definition = await machine.actions.get({ id: match.id });
if (isHappierActionApprovalRequestCreated(definition)) {
  throw new Error(`Approval required: ${definition.artifactId}`);
}
const { actionSpec } = definition;
console.log(actionSpec.inputSchema);

const result = await machine.actions.invoke(
  { pluginId: 'acme.notes', localId: 'save-note' },
  { note: 'Remember this' },
);
if (isHappierActionApprovalRequestCreated(result)) {
  throw new Error(`Approval required: ${result.artifactId}`);
}
console.log(result);
```

Validate against the complete `inputSchema`, including `oneOf` and `anyOf`
branches. A contributed Action can require fields inside one of those branches
even when the schema has no top-level `required` array.

Contributed Actions use their qualified plugin-and-Action identity in Action
settings. Their **External API & SDK** enablement and approval choice is
enforced just like the corresponding setting for a built-in Action; installing
an Action does not bypass an **Off** or **Ask first** decision.

The **External API & SDK** setting starts **Allowed** for API-eligible built-in
and contributed Actions, so Action Settings add no approval prompt unless the
user changes that control under **Settings → Actions → Integrations**. A
non-safe contributed Action still requires the host's live current-intent
confirmation; **Allowed** does not suppress the Action's independent safety
contract. The corresponding **Trusted plugins** setting is also **Allowed** by
default for Actions it supports. Those settings cannot elevate a PAT or trusted
plugin above `account_automation`: present-user-only controls such as approval
decisions, plugin uninstall, Agent session-hook changes, and security-policy
changes return `present_user_required`.

Use the types exported by `@happier-dev/sdk` as the canonical static contract
for SDK methods, inputs, and results. The generated
[SDK API inventory](https://github.com/happier-dev/happier/blob/v0.3/packages/sdk/API.md)
and [exported declarations](https://github.com/happier-dev/happier/blob/v0.3/packages/sdk/api-declarations.md)
show that public surface. At runtime, use `actions.search(...)` and
`actions.get(...)` to inspect the Actions available from the selected machine,
then call the raw `actions.execute(...)` primitive when the Action id is
selected dynamically.
The generated raw `actions.action.spec.search(...)` and
`actions.action.spec.get(...)` methods remain available. Do not copy a method
list into an integration.

For raw `session.spawn_new`, pass a machine target once in the outer
`options.target` when targeting a server or remote machine; omit it at a
daemon-local endpoint to use that daemon's current machine. The public input
deliberately omits `executionTarget`; the daemon supplies its local placement
after resolving the target. Supplying `executionTarget` in a public request is
rejected as invalid input. The server relay forwards the exact machine target
without receiving or inventing a daemon-local server id. Use the SDK types for
the remaining spawn fields, such as `directory`, `agentTarget`, and an optional
`creationKey`.

## Call the HTTP API

The v1 protocol has one relative path:

```text
POST /v1/actions/:actionId
Authorization: Bearer <API Token>
Content-Type: application/json
```

Both forms are implemented in the current Developer Preview source:

```text
POST http://127.0.0.1:<daemon-port>/v1/actions/:actionId

POST https://<configured-server>/v1/actions/:actionId
```

Use a direct daemon origin when the caller can reach that daemon. Use the
configured server origin when the target daemon is connected to that server:
the server authenticates and relays over the daemon's existing connection, so
the daemon does not need an inbound public address. This remains a Developer
Preview contract. A Happier server may expose it before the npm SDK package is
published; HTTP deployment and npm publication have separate readiness and
release decisions.

The request envelope is strict. `target` is routing metadata, never action
input or caller authority.

```json
{
  "v": 1,
  "requestId": "optional-correlation-id",
  "target": { "kind": "machine", "machineId": "machine-id" },
  "input": {}
}
```

`target` may be omitted, a machine target, or a session target
(`{ "kind": "session", "sessionId": "session-id" }`). The daemon-local
route defaults an omitted target to its current machine. The server origin has
no default machine: callers first select one through the API Token-authenticated
`GET /v1/machines` discovery route (the SDK exposes this as
`happier.machines.list()`), then send that exact machine target. A session
target is also valid when Happier can establish one exact current machine for
that Session. An omitted server target returns the typed `target_required` Action
result; the server never silently selects another machine. Account-level
Actions still run through the selected daemon.

An admitted response preserves the Action result without an SDK-specific
remapping:

```json
{
  "v": 1,
  "actionId": "session.spawn_new",
  "requestId": "optional-correlation-id",
  "execution": { "ok": true, "result": {} }
}
```

Failed Actions use the same `execution` field with `ok: false`, an error code,
an error string, and optional details.

## Handle Action outcomes and transport failures

A syntactically valid Action request can reach the selected daemon and still be
unable to run. Those are admitted Action outcomes, so raw HTTP clients receive
HTTP `200` and inspect `execution`; the SDK rejects them as
`HappierActionError` with the Action error code. For example,
`action_disabled`, `present_user_required`, and `target_required` are Action
outcomes, not proof that the HTTP transport failed.

An **Ask first** setting creates an approval request instead of running the
Action. Raw clients receive that admitted approval result; the SDK surfaces it
as `HappierActionError` with code `approval_required`. Complete the approval
from a signed-in app. An API Token cannot approve its own work.

Transport admission failures have a different shape and status:

- Both origins return HTTP `401` with `invalid_token` for a malformed, expired,
  unknown, or revoked API Token.
- Both origins return HTTP `400` with
  `{ "error": "invalid_request", "code": "invalid_action" | "invalid_envelope" }`
  for an unknown Action id or malformed outer envelope. A request body over 32
  MiB returns the same shape with `request_too_large` and HTTP `413`.
- The daemon-local origin can return HTTP `503` with `auth_unavailable` once a
  positive token validation cache has expired and its configured server cannot
  verify the token. This is an availability failure, not `invalid_token`.

The SDK raises `HappierTransportError` for these non-success HTTP responses,
network errors, invalid JSON, or an invalid response envelope. It does not
automatically retry a mutation or move it to another origin: after an
interrupted mutation, inspect the Action's current state and use its own
idempotency contract when one exists.

## Try the HTTP API with curl

For a daemon-local origin, omit `target`; the daemon executes on its current
machine. This read-only discovery call is a useful first connectivity check:

```bash
DAEMON_PORT="$(hdev daemon status --json | jq -er '.daemon.httpPort')"
curl --fail-with-body --request POST \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{
    "v": 1,
    "input": { "query": "session", "limit": 5 }
  }' \
  "http://127.0.0.1:$DAEMON_PORT/v1/actions/action.spec.search"
```

For the configured server origin, first find an available machine with the API
Token-authenticated bootstrap route. Its `id` is the value used in the Action
target.

```bash
curl --fail-with-body \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  "$HAPPIER_API_ENDPOINT/v1/machines"
```

The response is a narrow routing bootstrap rather than the full Machine model:

```json
[
  {
    "id": "machine-id",
    "active": true,
    "revokedAt": null,
    "replacedByMachineId": null
  }
]
```

Select only a row that is active, not revoked, and not replaced. For example,
this prints the eligible ids without silently choosing among them:

```bash
curl --fail-with-body \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  "$HAPPIER_API_ENDPOINT/v1/machines" \
  | jq -er '.[] | select(.active and .revokedAt == null and .replacedByMachineId == null) | .id'
```

Then use the safe, read-only Action discovery operation with that selected
machine. The bootstrap route is server-origin only; a daemon-local client does
not need it because omitting an Action target uses that daemon's current
machine.

```bash
curl --fail-with-body --request POST \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{
    "v": 1,
    "target": { "kind": "machine", "machineId": "machine-id" },
    "input": { "query": "session", "limit": 5 }
  }' \
  "$HAPPIER_API_ENDPOINT/v1/actions/action.spec.search"
```

For a contributed Action, use its qualified discovery id
`<plugin-id>/actions/<local-id>` to obtain the two identity fields. For
`acme.notes/actions/save-note`, send `pluginId: "acme.notes"` and
`localId: "save-note"`; do not include the literal `/actions/` delimiter in
`localId`. Inspect the declared input, then invoke it through the same target.
This example uses a placeholder contributed Action and input; replace both with
the discovered contract.

```bash
curl --fail-with-body --request POST \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{
    "v": 1,
    "target": { "kind": "machine", "machineId": "machine-id" },
    "input": {
      "action": { "pluginId": "acme.notes", "localId": "save-note" },
      "input": { "note": "Remember this" }
    }
  }' \
  "$HAPPIER_API_ENDPOINT/v1/actions/action.invoke"
```

If you already have a Session id, this safe status lookup is a real operation
against that Session. The Session target and `input.sessionId` must name the
same Session; the server derives its current owning machine rather than asking
you to duplicate that machine in the input.

```bash
curl --fail-with-body --request POST \
  --header "Authorization: Bearer $HAPPIER_TOKEN" \
  --header 'Content-Type: application/json' \
  --data '{
    "v": 1,
    "target": { "kind": "session", "sessionId": "session-id" },
    "input": { "sessionId": "session-id", "live": false }
  }' \
  "$HAPPIER_API_ENDPOINT/v1/actions/session.status.get"
```

The server does not choose a machine on your behalf. For example, omitting
`target` from that server request returns HTTP `200` with this Action error
envelope, not a request sent to an arbitrary daemon:

```json
{
  "v": 1,
  "actionId": "action.spec.search",
  "execution": {
    "ok": false,
    "errorCode": "target_required",
    "error": "target_required"
  }
}
```

## Transport limits

v1 uses finite JSON request/response messages—there is no SSE endpoint. Public
Action ingress verifies the API Token before JSON parsing. The shared request
body ceiling is 32 MiB (33,554,432 bytes); the server-to-daemon relay admits a
33 MiB (34,603,008-byte) request carrier, reserving one MiB for relay framing.
Responses send `Cache-Control: no-store`, and public Action routes do not enable
CORS. Put the bearer token in the `Authorization` header, never in a query
string.

At both the daemon-local and server origins, the complete serialized response
envelope—not only `execution.result`—is limited to 24,000,000 UTF-8 bytes. If an
Action finishes but its response would exceed that limit, the request remains
an admitted Action call and returns the normal envelope with this typed
execution failure:

```json
{
  "v": 1,
  "actionId": "action.spec.search",
  "execution": {
    "ok": false,
    "errorCode": "result_too_large",
    "error": "Action execution completed, but its response exceeded the external Action response limit and could not be represented.",
    "details": {
      "executionCompleted": true,
      "maxSerializedBytes": 24000000
    }
  }
}
```

The SDK rejects that response with `HappierActionError`; its `code` is
`result_too_large` and its `details.executionCompleted` is `true`. The Action
may already have committed a mutation, so do not blindly retry it. Inspect
current state or use the Action owner's idempotency contract. For large data,
return Artifact references, use an existing stream Action, or design bounded or
paginated reads instead of one oversized inline result.

The SDK supports `AbortSignal`; `await close()` is idempotent and aborts
outstanding calls. During shutdown, it gives active transcript and execution-run
cleanup requests up to one second to settle before destroying its transport. It
does not replay a mutation or move a failed mutation to another endpoint. For
mutating Actions, the SDK generates a request ID when you do not supply one, but
that generated value is not returned to the caller. If you may need to reconcile
an uncertain mutation outcome, generate and retain the ID in your own code and
pass it as `options.requestId`. A request ID provides correlation unless the
Action's own contract also gives it idempotency semantics; the SDK adds no
receipt store or automatic retry subsystem.

`session.followTranscript()` is a finite, demand-driven async iterator. It
pauses between pages while the consumer is not awaiting another item, and an
early loop exit or `await close()` releases its canonical follow lease. For a
genuine execution-run stream, use `client.runs.startStream(...)`. The returned
handle has `runId`, `streamId`, `cancel()`, and an async iterator; normal
completion, early return, caller abort, and `await close()` cancel that stream.
On a machine-bound client, stream start, read, and cancel remain on its selected
machine. Snapshot Actions remain ordinary methods.

## Server relay, readability, and revocation

The configured server deliberately can read requests and responses while it
relays them to the exact target daemon. This is not direct-server E2EE. The
server authenticates the API Token, validates the outer envelope, and proves
placement; the selected daemon handles the Action using its configured Action
settings.
Use the daemon-local transport when you need direct local delivery.

Server-side token verification observes revocation on the next verification. A
daemon-local positive validation cache can remain valid for at most 60 seconds;
after expiry, an unreachable server returns `auth_unavailable` instead of
extending access offline.
